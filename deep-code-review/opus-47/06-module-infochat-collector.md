### F2. NEEDS_REVIEW cap-exhaustion transition is unreachable in production

- **Category:** MAINTAINABILITY-RULES-DRIFT
- **Severity:** critical
- **Location:** `infochat-collector/src/main/java/app/zcat/infochat/collector/eval/reeval/ReEvaluationJob.java:106-127, 282-311`

**Current code:**

The `processOne` cap check:

```java
void processOne(@NonNull ReEvalCandidate candidate) {
    int cap = candidate.stage2Failed() ? infraFailureCap : unknownCap;

    if (candidate.reEvalAttempts() >= cap) {
        transitionToNeedsReview(candidate);
        return;
    }
    ...
}
```

The enumeration filter:

```java
final String sql =
    "SELECT id, fetched_at, stage2_failed, re_eval_attempts FROM post "
        + "WHERE ("
        + "  (stage2_failed = TRUE AND status != 'NEEDS_REVIEW' AND re_eval_attempts < ?)"
        + "  OR "
        + "  (status = 'QUARANTINED' AND stage2_done = TRUE AND stage2_failed = FALSE "
        + "   AND re_eval_attempts < ?)"
        + ") ORDER BY fetched_at, id LIMIT ?";
...
ps.setInt(1, infraFailureCap);
ps.setInt(2, unknownCap);
```

**Why this is wrong / suboptimal / risky:**

`enumerateCandidates` only returns rows with `re_eval_attempts < cap`. A candidate is therefore guaranteed to enter `processOne` with `reEvalAttempts() < cap`, so the `reEvalAttempts() >= cap` branch is dead code in the scheduled path. The post's attempts counter climbs from 0 to `cap−1` over `cap−1` ticks; on the tick that would push it to `cap` the verdict-driven `incrementAttemptCounter` advances the counter to `cap`, and the post is then permanently excluded from re-enumeration. It stays QUARANTINED forever, never transitions to NEEDS_REVIEW, and the throttled `re-eval-cap-exhaustion` admin notification never fires.

This contradicts `docs/spec/security.md` §Re-evaluation job: "After cap exhaustion the post transitions to `NEEDS_REVIEW`" and breaks the operator alerting commitment in §Failure handling ("Throttled NEEDS_REVIEW notifications. Admin notifications for `NEEDS_REVIEW` transitions are coalesced...").

The test `ReEvaluationJobTest.infraFailureCapExhaustion_transitionsToNeedsReview` only passes because it bypasses `enumerateCandidates` and hand-constructs the cap-exceeded candidate, so green tests mask a production bug.

**Recommended fix:**

Loosen the enumerate filter to include cap-exceeded rows still in a re-eval-eligible state, and let `processOne` drive the transition:

```java
final String sql =
    "SELECT id, fetched_at, stage2_failed, re_eval_attempts FROM post "
        + "WHERE ("
        + "  (stage2_failed = TRUE AND status NOT IN ('NEEDS_REVIEW', 'READY'))"
        + "  OR "
        + "  (status = 'QUARANTINED' AND stage2_done = TRUE AND stage2_failed = FALSE)"
        + ") ORDER BY fetched_at, id LIMIT ?";
```

Drop the two `re_eval_attempts < ?` predicates; `processOne` already short-circuits on `reEvalAttempts() >= cap`. The `LIMIT ?` and `ORDER BY` already bound per-tick cost.

Alternatively, do the transition in-SQL as a separate sweep that filters `re_eval_attempts >= cap AND status != 'NEEDS_REVIEW' AND ...` and runs before/after the re-eval enumeration. Either shape closes the gap; the first is the smaller diff.

**Reasoning:**

The current filter encoded "cap not yet reached" because the design-time intent was probably to skip cap-exceeded rows from re-eval cycles. But the SAME query feeds the NEEDS_REVIEW transition path, and that path requires cap-exceeded rows to be visible. The fix separates "is this candidate eligible for another re-eval attempt?" (the in-process cap check in `processOne`) from "is this candidate eligible for the job at all?" (the broader enumerate filter).

**Trade-offs:**

The enumeration returns a slightly larger candidate set, but processOne's first-line check filters out cap-exceeded rows immediately into the transition path. No additional LLM calls. The added cost is one extra DB UPDATE per cap-exceeded row per tick — bounded by the existing `LIMIT ?` plus the existing batch cadence.

The test `ReEvaluationJobTest.infraFailureCapExhaustion_transitionsToNeedsReview` should be supplemented with an IT that exercises the full scheduled path (enumerate + processOne) on a seeded cap-exceeded row.

### F3. Kind-6 repost edge to_post is never resolvable to a real post

- **Category:** MAINTAINABILITY-RULES-DRIFT
- **Severity:** high
- **Location:** `infochat-collector/src/main/java/app/zcat/infochat/collector/stream/nostr/Kind6Handler.java:141-167`, `infochat-collector/src/main/java/app/zcat/infochat/collector/outbox/PostPersister.java:108-119`, joined by `infochat-provider/src/main/java/app/zcat/infochat/provider/chat/tool/GetReferencesTool.java:67-80`

**Current code:**

Kind6Handler:

```java
private void writeRepostEdge(UUID fromPostId, String originalEventId) {
    UUID toPostUuid = deriveToPostUuid(originalEventId);
    TransactionHelper.inTransaction(dataSource, "Kind6Handler", conn -> {
        final String sql =
            "INSERT INTO post_reference (from_post, to_post, link_type, score) "
                + "VALUES (?, ?, 'repost', 1.0)";
        ...
    });
}

static UUID deriveToPostUuid(@NonNull String originalEventId) {
    return UUID.nameUUIDFromBytes(originalEventId.getBytes(StandardCharsets.UTF_8));
}
```

PostPersister persistence:

```java
"INSERT INTO post ("
    + "  id, uid, source_id, upstream_identifier, ..."
    + ") VALUES ("
    + "  gen_random_uuid(), ?, ?, ?, ..."
```

Provider join:

```java
"  JOIN post_reference pr ON pr.from_post = p1.id "
    + "  JOIN post p2 ON p2.id = pr.to_post "
```

**Why this is wrong / suboptimal / risky:**

The kind-6 `to_post` is a deterministic UUID v3 derived from the Nostr event id bytes. The original kind-1 post (when it later arrives via the regular stream path) is persisted with `id = gen_random_uuid()` — a fresh random UUID with no relationship to the event id. Therefore the JOIN `p2.id = pr.to_post` cannot match: the right-hand side is a derived UUID, the left-hand side is a random UUID. Every kind-6 repost edge written by this handler is structurally unresolvable through the Provider's tool.

The spec is explicit (`docs/spec/architecture.md` §Source identity, "Kind-6 cross-source linking"):

> The link is written as `(kind-6 post UID) →repost→ (original upstream_identifier)`, resolved to a post UID if and when the original event is also seen and stored.

The spec wants `upstream_identifier` (a 64-char hex string) stored as the edge target, with resolution to the post UID happening when the original lands. The implementation's `nameUUIDFromBytes` derivation is one possible encoding, but only works if the kind-1 path also persists the original post with `id = nameUUIDFromBytes(event_id)` — and PostPersister doesn't. No code anywhere re-derives this UUID at query time either, so even moving the resolution to the JOIN side is not in place.

The result: kind-6 repost edges are written, indexed, and stored, but `getReferences` returns zero rows for the repost edge family. The entire M1-100 ticket's user-visible payoff is absent.

**Recommended fix:**

Two viable shapes. The smaller-diff choice is to resolve at query time by including the upstream identifier alongside the edge:

Option A (recommended): change Kind6Handler to store the upstream identifier in a dedicated nullable column on `post_reference` (e.g. `to_upstream_identifier TEXT`) and leave `to_post` NULL when resolution hasn't happened yet. A V31 migration adds the column. A nightly resolver UPDATEs `post_reference SET to_post = p.id FROM post p WHERE p.upstream_identifier = pr.to_upstream_identifier AND pr.to_post IS NULL`. GetReferencesTool already filters out NULL `to_post` rows naturally via the JOIN.

Option B: change `PostPersister.persist` to use `id = deriveToPostUuid(upstream_identifier)` for Nostr-kind posts (or for every post — UUID v3 of `(source_id || '|' || upstream_identifier)` is deterministic and already aligns with the existing `uid` semantics). This makes `nameUUIDFromBytes(originalEventId)` match `post.id` naturally for any subsequently-arriving kind-1.

The smaller commit is Option B if the change is scoped to Nostr posts only (kind 1 and 6 paths). Be aware that doing it for every post changes the `post.id` semantics across modules; that may need an architecture-level commitment.

**Reasoning:**

The current shape is a half-implementation. Either the storage side or the join side must change so the link resolves. The spec wording implies the join side stores the upstream identifier (the protocol-level stable key); Option A is the closest match to the spec.

**Trade-offs:**

- Option A adds a column + nightly job (more code, more moving parts). Closest to spec wording.
- Option B is a 2-line code change but redefines what `post.id` means for Nostr posts (or for every post). Provider code that relies on `post.id` being random would not be impacted (random vs. deterministic UUIDs are interchangeable as primary keys), but operator-side mental model changes.

**Alternative options:**

- **Option A** — add `to_upstream_identifier` column + resolver
- **Option B** — make `post.id` deterministic for Nostr (or all) posts
- **Option C** — defer kind-6 resolution to v2 and remove the repost edge write entirely; current spec text on "resolved to a post UID if and when" reads as a contract, so this needs a spec amendment

### F4. Stage 2 `emitQuarantineNotifyForPendingRows` re-fires PENDING on every verdict

- **Category:** MAINTAINABILITY-RULES-DRIFT
- **Severity:** high
- **Location:** `infochat-collector/src/main/java/app/zcat/infochat/collector/eval/stage2/Stage2VerdictHandler.java:145-153, 269-281` and `infochat-collector/src/main/java/app/zcat/infochat/collector/eval/stage1/QuarantineDao.java:66-90`

**Current code:**

Stage 1 inserts a PENDING quarantine row in `QuarantineDao.insert` with no NOTIFY:

```java
"INSERT INTO quarantine ("
    + "  post_id, post_uid, post_fetched_at,"
    + "  flagged_by, rule_id, span_start, span_end,"
    + "  original_html, placeholder_id, status"
    + ") VALUES ("
    + "  ?, ?, ?, 'stage1', ?, ?, ?, ?, ?, 'PENDING'"
    + ")"
```

Stage 2 INJECTION/MALWARE/UNKNOWN path:

```java
private void applyQuarantineVerdict(UUID postId, Instant postFetchedAt, Verdict verdict) {
    TransactionHelper.inTransaction(dataSource, "Stage2VerdictHandler", conn -> {
        updatePostQuarantined(conn, postId, postFetchedAt, /* stage2Failed */ false);
        setStage2Verdict(conn, postId, postFetchedAt, verdict.name());
        emitQuarantineNotifyForPendingRows(conn, postId);
    });
    ...
}

private void emitQuarantineNotifyForPendingRows(Connection conn, UUID postId) throws SQLException {
    final String sql =
        "SELECT id FROM quarantine WHERE post_id = ? AND status = 'PENDING'";
    ...
    quarantineNotifyEmitter.emit(conn, "quarantine", quarantineId, "PENDING");
}
```

**Why this is wrong / suboptimal / risky:**

`docs/spec/architecture.md` §Inter-service communication enumerates the `quarantine_review` channel triggers:

> fires on quarantine state-machine transitions reachable by Provider (`PENDING` insert, `BENIGN_CLOSED`, `APPROVED`, `REJECTED`)

The contract is "PENDING fires on insert" — i.e., when the row is created. The current code emits PENDING NOTIFY at Stage 2 verdict time, not at insert time. Two real problems:

1. **Spec drift on the PENDING trigger.** A Stage 1 hit followed by a Stage 2 BENIGN never fires the PENDING NOTIFY (`updateStage1QuarantineRowsToBenignClosed` precedes the emit-closed-rows call, so the row is already BENIGN_CLOSED by the time the SELECT runs and the PENDING-rows query returns zero). A Stage 1 hit followed by no Stage 2 (which doesn't happen in this flow but could under future re-routes) also misses the PENDING. The spec semantics say "Provider sees the PENDING as soon as the row exists"; the current code says "Provider sees PENDING only when Stage 2 finalizes a quarantine verdict."

2. **Redundant signal.** When Stage 2 fires INJECTION/MALWARE/UNKNOWN, every PENDING row attached to the post triggers a PENDING NOTIFY. But the Provider's high-water mark advances on `reviewed_at` (the quarantine row's `updated_at` for `quarantine` events) — and the Stage 2 path didn't `UPDATE quarantine` for these PENDING rows, so their `updated_at` is still the Stage 1 insert time. The Provider's cursor moves past these rows once, then re-receives the NOTIFY for them on Stage 2 verdict — but the cursor compare-and-swap suppresses the second hit, so the NOTIFY is wasted bandwidth, not a duplicate side effect. Still, the contract drift is real.

**Recommended fix:**

Move PENDING NOTIFY emission to QuarantineDao.insert so it fires per row insertion, inside the Stage 1 transaction:

```java
public void insert(Connection conn, QuarantineRow row, QuarantineNotifyEmitter notify) {
    // ... existing INSERT ...
    // After successful insert, fetch the generated id and emit PENDING NOTIFY.
    // The INSERT can RETURNING id to avoid the second roundtrip.
    UUID quarantineId = ...;
    notify.emit(conn, "quarantine", quarantineId, "PENDING");
}
```

Update `QuarantineDao.insert` to `RETURNING id` and emit the PENDING NOTIFY inside the same transaction (Stage 1's transaction wraps both the INSERT and the parent post UPDATE per `Stage1Pipeline.handleSuccess`). Drop `emitQuarantineNotifyForPendingRows` from `Stage2VerdictHandler.applyQuarantineVerdict` — the rows are already PENDING-NOTIFIED at insertion time. The handler still needs to emit nothing extra (or could emit a per-verdict NOTIFY if the spec required one, but it doesn't).

**Reasoning:**

Moving the emit to insertion time aligns code with spec text ("PENDING insert"). The Provider's existing high-water mark + cursor handles the rest. This also simplifies the handler (one fewer SQL roundtrip per quarantine verdict).

**Trade-offs:**

- The Provider receives the PENDING NOTIFY sooner — within Stage 1's transaction, not after Stage 2. For a Stage 1 hit that quickly resolves to BENIGN, the Provider may see PENDING followed immediately by BENIGN_CLOSED rather than just BENIGN_CLOSED. This is what the spec asks for and matches the cursor semantics (the Provider would advance its high-water mark on both events).
- A small refactor of `QuarantineDao` to plumb the notifier through. The DAO becomes notifier-aware (modest layering change but acceptable since the DAO already owns the row's existence).

### F5. `latestPublishedAtEpochSeconds` on every Nostr reconnect lacks supporting index

- **Category:** PERFORMANCE
- **Severity:** medium
- **Location:** `infochat-collector/src/main/java/app/zcat/infochat/collector/stream/nostr/NostrStreamSource.java:439-458`

**Current code:**

```java
private OptionalLong latestPublishedAtEpochSeconds(UUID sourceUuid) {
    final String sql = "SELECT MAX(published_at) FROM post WHERE source_id = ?";
    try (Connection conn = dataSource.getConnection();
         PreparedStatement ps = conn.prepareStatement(sql)) {
        ps.setObject(1, sourceUuid);
        ...
    }
}
```

**Why this is wrong / suboptimal / risky:**

The `since` cursor is supplied to every relay subscription, and every reconnect (after a backoff or after a peer-IP-divergence hard-close) issues the query again — once per relay per reconnect across the lifetime of the Collector. The available indexes are:

- `idx_post_source ON post(source_id, fetched_at DESC)`
- `idx_post_published ON post(published_at DESC)` (global, no source filter)

Neither index covers `WHERE source_id = ? ORDER BY published_at DESC LIMIT 1`. PostgreSQL has two query plans here:

- Use `idx_post_source` to find all rows for the source, scan them for the max `published_at` — bounded by source size.
- Use `idx_post_published` (descending) and filter on `source_id = ?` — bounded by the rank of the source's latest post in the global stream.

For an active Nostr source with millions of posts, the first plan walks the source's slice; for a low-volume source on a busy Collector, the second plan walks many irrelevant rows before finding one matching. Both scale poorly. The reconnect path runs at a frequency the operator does not control (it fires on any disconnect, including DNS-rebind peer-IP changes), so a flapping relay can produce many of these queries.

**Recommended fix:**

Add a composite index on `(source_id, published_at DESC)` in a new migration. PostgreSQL can then plan the query as a one-row index probe:

```sql
CREATE INDEX idx_post_source_published ON post(source_id, published_at DESC);
```

Alternatively, cache the value in memory inside the StreamSource. Each event sink-write updates an in-memory `volatile long latestPublishedAtEpoch`; reconnect reads the cached value. On Collector restart the cache is rebuilt by the single query above (which then becomes a once-per-startup cost rather than once-per-reconnect).

**Reasoning:**

The query is correct; the underlying index does not back it. A composite index is the standard remedy. The in-memory cache is an alternative that avoids the index but introduces a startup-cost question on Collectors with long-running Nostr sources.

**Trade-offs:**

- The index doubles the write amplification on `post` INSERT (one more index to maintain), but `post` writes are batched per fetcher tick / per Nostr event and are not the hot path that gates throughput. The READ benefit dominates.
- The in-memory-cache alternative removes the per-reconnect query but adds a startup-cost query. Both are acceptable; the index is the lower-risk change.

### F6. Upstream-supplied pagination cursors are concatenated into URLs without encoding

- **Category:** SECURITY
- **Severity:** medium
- **Location:** `infochat-collector/src/main/java/app/zcat/infochat/collector/fetcher/bluesky/BlueskyFetcher.java:110-117`, `infochat-collector/src/main/java/app/zcat/infochat/collector/fetcher/reddit/RedditFetcher.java:108-114`

**Current code:**

```java

    StringBuilder sb = new StringBuilder(xrpcBase)
        .append("?actor=").append(actor);
    if (cursor != null) {
        sb.append("&cursor=").append(cursor);
    }
    return URI.create(sb.toString());
}
```

RedditFetcher:

```java
private static URI buildPageUri(String identifier, String afterCursor) {
    String url = identifier + ".json";
    if (afterCursor != null) {
        url += "?after=" + afterCursor;
    }
    return URI.create(url);
}
```

**Why this is wrong / suboptimal / risky:**

`docs/spec/security.md` §Threat model: "The Collector is exposed to arbitrary feed content. Every RSS publisher, Reddit poster, Bluesky user, etc. is untrusted." The `cursor` (Bluesky) and `after` (Reddit) values are extracted from upstream JSON responses; they are *not* operator-trusted. A hostile or buggy upstream that emits a cursor like `abc&actor=evilhandle&x=` injects an extra `actor=` parameter into the next request, redirecting the fetch to a different identifier. A cursor containing `#` truncates the URL at the fragment delimiter. A cursor containing space or other reserved characters breaks the URL parse.

The SSRF guard at `SsrfGuardedHttpClient` checks the resolved host and IP, not the path/query shape; an injection that keeps the same host but flips other query parameters survives the SSRF guard. The blast radius is bounded to "what the upstream API does with extra query params" — for Bluesky this is "fetch a different actor's feed"; for Reddit "fetch a different listing window." Neither escalates to RCE, but it does break the spec's "trust commitments live in the per-source trust boundaries section" principle: the boundary is "the URL we GET is the one we constructed from operator config + our own pagination semantics," and the boundary is currently leaky.

A coupled risk: the upstream identifier (`actor` for Bluesky, the subreddit URL for Reddit) is also concatenated without encoding. Identifiers come from `bootstrap-sources.json` and `/add-source`, which are operator/admin trusted, but should still be encoded as a hardening measure — bootstrap JSON is parsed without URL-shape validation.

**Recommended fix:**

Use `URLEncoder.encode` for every query-parameter value, including operator-supplied identifier values:

```java
private URI buildUri(String actor, String cursor) {
    StringBuilder sb = new StringBuilder(xrpcBase)
        .append("?actor=").append(URLEncoder.encode(actor, StandardCharsets.UTF_8));
    if (cursor != null) {
        sb.append("&cursor=").append(URLEncoder.encode(cursor, StandardCharsets.UTF_8));
    }
    return URI.create(sb.toString());
}
```

Same shape for `RedditFetcher.buildPageUri` (encode `afterCursor`; the identifier is already a full URL with `.json` appended, so URL-encoding it would break the path — that one needs a separate `URI.create` + `URI.resolve("?after=...")` pattern).

**Reasoning:**

`URLEncoder.encode` percent-encodes every reserved character including `&`, `#`, `?`, space, and unicode bytes. An upstream that emits `abc&actor=evil` becomes `abc%26actor%3Devil` in the URL — a single opaque token to the upstream's parser, no parameter injection. The CoingeckoSnapshotSource already follows this pattern (line 103: `URLEncoder.encode(slug, StandardCharsets.UTF_8)`), so the codebase has a local precedent.

**Trade-offs:**

None — URL-encoding is strictly safer and what upstream APIs already expect for query values. The only downside is one extra method call per page; negligible.

### F7. Dead semaphores in TaggerWorker and EntityExtractorWorker

- **Category:** SIMPLIFICATION
- **Severity:** medium
- **Location:** `infochat-collector/src/main/java/app/zcat/infochat/collector/eval/tagger/TaggerWorker.java:159-220`, `infochat-collector/src/main/java/app/zcat/infochat/collector/eval/entity/EntityExtractorWorker.java:153-220`

**Current code:**

TaggerWorker:

```java
@ConfigProperty(name = "infochat.llm.tagger.max-concurrency")
int maxConcurrency;

private Semaphore concurrencyPermits;

@PostConstruct
void init() {
    ...
    this.concurrencyPermits = new Semaphore(maxConcurrency);
    ...
}

@Scheduled(every = "{infochat.llm.tagger.poll-interval}")
public void onTick() {
    List<PostRow> pending;
    try {
        pending = enumeratePending(maxConcurrency);
    } catch (SQLException e) { ... }
    for (PostRow row : pending) {
        try {
            processOne(row);
        } catch (RuntimeException e) { ... }
    }
}

void processOne(PostRow row) {
    concurrencyPermits.acquireUninterruptibly();
    try {
        TaggerOutcome outcome = invokeWithFallbackChain(row);
        persistCursor(row, outcome);
    } finally {
        concurrencyPermits.release();
    }
}
```

`EntityExtractorWorker.processOne` (lines 202–220) mirrors this shape with its own semaphore.

**Why this is wrong / suboptimal / risky:**

`enumeratePending(maxConcurrency)` caps the batch to `maxConcurrency` rows; the `for` loop iterates them serially on the scheduler-tick thread; `processOne` acquires the semaphore, runs synchronously through the LLM call + DB write, then releases. The semaphore therefore never sees a count above 1 — the only thread inside `processOne` at any moment is the scheduler thread. `acquireUninterruptibly()` on a 4-permit semaphore from one caller is a no-op.

The class-level javadoc cites `docs/spec/llm.md` §Bounded concurrency and observability and the `infochat.llm.tagger.max-concurrency` profile-driven value as the rationale, but the actual concurrency bound comes from the sequential loop, not the semaphore. If a future refactor introduces parallel processing (e.g., a `parallelStream` or virtual-thread fan-out), the semaphore would suddenly become live again, but as written, it is dead code that misleads a reader about what bounds the in-flight LLM call count.

Same story in EntityExtractorWorker.

**Recommended fix:**

Two reasonable shapes:

**Option A (recommended)**: drop the semaphore; document that the batch-per-tick + serial-loop shape is the concurrency bound.

```java
@Scheduled(every = "{infochat.llm.tagger.poll-interval}")
public void onTick() {
    int perTickCap = maxConcurrency;
    List<PostRow> pending = ...;  // capped at perTickCap
    for (PostRow row : pending) {
        try {
            processOne(row);
        } catch (RuntimeException e) { ... }
    }
}

void processOne(PostRow row) {
    TaggerOutcome outcome = invokeWithFallbackChain(row);
    persistCursor(row, outcome);
}
```

**Option B**: make the loop actually parallel — fan out via `Thread.ofVirtual()` per row inside the batch, gated by the semaphore. The LLM call then runs concurrently up to `maxConcurrency` per tick, draining the batch faster and bounding tail-latency on heterogeneous response times.

```java
@Scheduled(every = "{infochat.llm.tagger.poll-interval}")
public void onTick() {
    List<PostRow> pending = ...;
    List<Thread> workers = new ArrayList<>();
    for (PostRow row : pending) {
        workers.add(Thread.ofVirtual().start(() -> processOne(row)));
    }
    for (Thread w : workers) w.join();
}
```

The codebase already uses `Thread.ofVirtual()` in `NostrRelayConnection` and elsewhere, so the pattern is in scope.

**Reasoning:**

Option A removes a misleading abstraction with no behavioral change. Option B matches the documented intent ("bounded concurrency") but is a larger change with a real behavioral implication (per-tick throughput goes up, peak provider load also goes up to `maxConcurrency`). Pick A unless the throughput improvement is needed.

**Trade-offs:**

- Option A: simpler code, but the per-tick worst-case latency is `pending.size() × per-LLM-call-time`. With profile defaults `maxConcurrency=4` (laptop) and one tick every 5s, a slow LLM dominates the pipeline drain rate.
- Option B: better throughput, but each tick spawns up to `maxConcurrency` virtual threads — fine on JDK 25 but adds a coordinated stop concern if a graceful shutdown lands mid-tick.

### F8. Defensive `catch (RuntimeException)` between internal classes in AssetSnapshotFetcher

- **Category:** MAINTAINABILITY-RULES-DRIFT
- **Severity:** medium
- **Location:** `infochat-collector/src/main/java/app/zcat/infochat/collector/assets/AssetSnapshotFetcher.java:188-198`

**Current code:**

```java
} catch (FetchException e) {
    recordFailure(row, e);
    return;
} catch (RuntimeException e) {
    // Defensive guard: an impl bug must not break the tick
    // loop for sibling pairs. Treat as a failure for D42
    // counter purposes — operator visibility is the priority.
    LOG.warnf(e, "AssetSnapshotFetcher: %s.fetchSnapshot threw RuntimeException for asset=%s vs=%s",
        host, row.asset(), row.defaultQuoteCurrency());
    recordFailure(row, new FetchException(
        "RuntimeException from " + host + ".fetchSnapshot: " + e.getClass().getSimpleName(), e));
    return;
}
```

**Why this is wrong / suboptimal / risky:**

Engineering rule §7: "No defensive code for impossible scenarios. Don't add error handling, fallbacks, or validation for scenarios that cannot happen given the trust boundary the code lives in." The `AssetDataSource` implementations (`CoingeckoSnapshotSource`, `KrakenSnapshotSource`, `BitfinexSnapshotSource`) are internal first-party beans inside the same module. Their contract is "throw `FetchException` on a failure to fetch the snapshot." A `RuntimeException` other than `FetchException` is a bug, not a runtime condition.

The "defensive guard" comment acknowledges this is a paranoid catch — "an impl bug must not break the tick loop for sibling pairs". But the tick loop already wraps each `tickOnePair` call: catching at this finer granularity is the rule violation.

There is a legitimate case for catching broad exceptions at the *outer* scheduler-loop boundary (one bad pair shouldn't kill sibling pairs) — that catch belongs in `runHostTick`'s outer loop, NOT around the single `fetchSnapshot` call where the SPI contract should be honored. As written, the catch lets internal bugs slip into the D42 failure-counter pipeline silently and misattributes them as upstream fetch failures.

**Recommended fix:**

Drop the `catch (RuntimeException)` clause inside `tickOnePair`. Let an SPI-contract violation propagate; the outer `runHostTick` loop's `for (EnabledPair row : rows) { tickOnePair(host, row); }` should catch RuntimeException at that level, log loudly with a distinct error class (e.g. `asset.spi_bug`), and continue iterating sibling pairs.

```java
public void runHostTick(@NonNull String host) {
    List<EnabledPair> rows;
    try { rows = enumerateEnabled(host); } catch (SQLException e) { ... return; }
    for (EnabledPair row : rows) {
        try {
            tickOnePair(host, row);
        } catch (RuntimeException e) {
            // Outer-loop boundary: an SPI-contract violation in one
            // pair must not break sibling pairs. Distinct error class
            // so it does NOT feed the D42 upstream-fetch ladder.
            LOG.errorf(e, "AssetSnapshotFetcher: SPI contract violation for asset=%s vs=%s",
                row.asset(), row.defaultQuoteCurrency());
        }
    }
}
```

`tickOnePair` then catches only `FetchException` (the legitimate SPI failure mode).

**Reasoning:**

The fix preserves loop continuity (rule §7's allowed pattern: boundary-level catches at iteration sites) while removing the internal catch that the rule forbids. Misattributing internal bugs as D42 fetch failures distorts operator visibility — a Coingecko code bug should look different from a Coingecko outage.

**Trade-offs:**

None — strictly better separation of failure modes. The fix is a small refactor of where the catch sits, not new logic.

The record's javadoc says:

**Why this is wrong / suboptimal / risky:**

`long dispatch = 1L` is a local variable in `enumerateActiveSources`, reset each call. The first source in each enumeration receives `dispatchKey=1`, regardless of which source it actually is. Or fix the implementation to actually be per-startup-stable (assign keys in the bootstrap loader to the `source.id → dispatchKey` map, or use a hash of `source.id`).

The first change is the cheaper one and matches actual usage (Fetcher does not rely on stability).

**Reasoning:**

Either the contract is "stable across the JVM" (in which case the implementation is broken), or the contract is "per-tick" (in which case the comment is wrong). The implementation is the source of behavior; the comment is the cheaper fix.

**Trade-offs:**

None.

### F10. Two distinct SHA-256-to-hex helpers

- **Category:** SIMPLIFICATION
- **Severity:** low
- **Location:** `infochat-collector/src/main/java/app/zcat/infochat/collector/bootstrap/BootstrapLoader.java:276-290`, `infochat-collector/src/main/java/app/zcat/infochat/collector/outbox/PostPersister.java:168-177`

**Current code:**

BootstrapLoader:

```java
private static String sha256Hex(byte[] data) {
    MessageDigest md;
    try {
        md = MessageDigest.getInstance("SHA-256");
    } catch (NoSuchAlgorithmException e) {
        throw new IllegalStateException("SHA-256 unavailable in this JRE", e);
    }
    byte[] digest = md.digest(data);
    StringBuilder hex = new StringBuilder(digest.length * 2);
    for (byte b : digest) {
        hex.append(String.format("%02x", b & 0xff));
    }
    return hex.toString();
}
```

PostPersister:

```java
private static String sha256Hex(byte[] data) {
    MessageDigest md;
    try {
        md = MessageDigest.getInstance("SHA-256");
    } catch (NoSuchAlgorithmException e) {
        throw new IllegalStateException("SHA-256 unavailable in this JRE", e);
    }
    return HexFormat.of().formatHex(md.digest(data));
}
```

**Why this is wrong / suboptimal / risky:**

Two implementations of the same function, both private to their respective classes, with different hex encoding (BootstrapLoader uses `String.format("%02x", ...)` per byte, PostPersister uses `HexFormat.of().formatHex(...)`). Both produce lowercase hex. The duplication is small but it is a smell: a third caller will produce a third copy.

`HexFormat.of()` is the JDK-17+ idiomatic shape and shorter; `String.format("%02x", ...)` in a loop is the pre-JDK-17 idiom.

**Recommended fix:**

Move the helper to `infochat-core` (or a shared utility within `infochat-collector` if dependency direction matters) and have both callers use it. Use the `HexFormat` shape.

```java
// In some shared utility:
public static String sha256Hex(byte[] data) {
    try {
        return HexFormat.of().formatHex(
            MessageDigest.getInstance("SHA-256").digest(data));
    } catch (NoSuchAlgorithmException e) {
        throw new IllegalStateException("SHA-256 unavailable in this JRE", e);
    }
}
```

**Reasoning:**

Single source of truth for a 5-line cryptographic primitive. The fix size is small.

**Trade-offs:**

Requires a shared module location (`infochat-core` makes sense since both Collector and Provider potentially need it). If the shared location adds a dependency hop, the current duplication may be the better trade-off; but `infochat-core` is already a parent dependency of `infochat-collector`, so no new edges.

  1. Executive Summary                                                                                                                                                                                                                                  
                                                                                                                                                                                                                                                        
  I read all 11 spec documents (SPEC.md, decisions.md, architecture.md, security.md, schema.md, commands.md, llm.md, messaging.md, deployment.md, verification.md, 00-mvp.md). Overall verdict: the spec is strong — unusually thorough for a project at
   this stage — but carries a handful of gaps and inconsistencies that would cause two competent engineers to build different things. The determinism boundary, threat model, and adapter SPI are well-defined. The spec/design split is mostly clean.  
  The top issues are: (1) non-admin users can overwrite operator-seeded bootstrap tags globally via /add-source, breaking the deterministic tagger fallback; (2) the price_snapshot entity and its Provider-Collector contract are described across
  three files but the entity definition itself is missing from schema.md, and the bootstrap-assets-to-Provider handoff is unspecified; (3) the /retry anchor's persistence story and the auto-compress trigger threshold are both undefined at the spec 
  level.          

  ---
  2. Findings
                                                                                                                                                                                                                                                        
  ▎ F1 — /add-source tag replacement is a global mutation without admin gating
                                                                                                                                                                                                                                                        
  Severity: blocker                                                                                                                                                                                                                                     
  Category: security / inconsistency                                                                                                                                                                                                                    
  Location: commands.md § Source management (L193–201), security.md § Failure handling (L387), schema.md § Sources and tags (L45–46)                                                                                                                    
  Confidence: high                                                                                                                                                                                                                                      
                                                                                                                                                                                                                                                        
  What the spec says:                                                                                                                                                                                                                                   
  - commands.md: "When the source (kind, identifier) already exists… the new call's --tags replace the existing bootstrap_tags for that source row."                                                                                                    
  - security.md: "Tagger failure → fall back to source.bootstrap_tags."                                                                                                                                                                                 
  - schema.md: source carries "bootstrap tags (the tagger's deterministic fallback per decision D22)."
                                                                                                                                                                                                                                                        
  Why it's a problem:                                                                                                                                                                                                                                   
  A non-admin user (DM, and in groups any group member) can issue /add-source <existing-url> --tags foo and globally replace operator-seeded bootstrap tags for everyone. Source rows are global (decision D7). The bootstrap_tags column is the        
  tagger's deterministic safety net: when the LLM tagger fails, every user's summaries and digests fall back to these tags. A malicious user replaces ["news", "politics"] with ["cute", "harmless"] and suddenly a compromised tagger hides content    
  from all subscribers. This violates the trust model (operator-configured bootstrap JSON is trusted, user input is untrusted). Compounding the problem, on the next Collector restart the bootstrap loader "updates name/category/tags/config in place 
  when entries differ" (deployment.md L98), silently reverting the user's change — so the user's tag change is both globally destructive AND silently undone later.                                                                                     
                  
  Suggested resolution:                                                                                                                                                                                                                                 
  The smallest fix: restrict tag replacement on an existing source to bot admins only. Non-admin re-/add-source calls on an existing (kind, identifier) must be idempotent (upsert subscription only, tags ignored with a friendly note). Draft: "When
  the source already exists, the call is idempotent on the source row; the caller's subscription is upserted. Tags on the existing source row are not replaced by non-admin callers. Bot admins may supply --tags to update bootstrap tags."            
  Trade-offs: an alternative is a separate /source-retag admin command; it's cleaner but introduces another command.

  ▎ F2 — price_snapshot entity is referenced across three files but never defined in schema.md                                                                                                                                                          
                                                                                                                                                                                                                                                        
  Severity: blocker
  Category: gap                                                                                                                                                                                                                                         
  Location: schema.md § Entities, commands.md § Asset commands (L122–161), architecture.md § Ingest SPIs (L91–98)                                                                                                                                       
  Confidence: high                                                                                                                                                                                                                                      
                                                                                                                                                                                                                                                        
  What the spec says:                                                                                                                                                                                                                                   
  - architecture.md L97: "price_snapshot is keyed by (asset, sub-verb) alone, not by a source.id."                                                                                                                                                      
  - commands.md L123: "The Collector owns price_snapshot: its asset Fetchers INSERT new rows."                                                                                                                                                          
  - schema.md invariant 6 (L165–173): references price_snapshot in the TTL-by-partition invariant.
  - Nowhere in schema.md § Entities is price_snapshot defined as a top-level entity with columns, relationships, or invariants.                                                                                                                         
                                                                                                                                                                                                                                                        
  Why it's a problem:                                                                                                                                                                                                                                   
  An implementer cannot build the asset-command data path without knowing the schema of price_snapshot. Is there one row per (asset, sub-verb) (overwritten on each poll), or a time-series of rows (new row per poll)? The key (asset, sub-verb)       
  doesn't include a timestamp, suggesting one row per source — but if there's only one row per sub-verb, the "retention by partition drop" invariant (invariant 6) makes no sense (you can't drop the current row). If it's a time-series, the key must 
  include a timestamp. The "latest snapshot" query implied by commands.md L127 requires a time column that doesn't appear in the stated key. Two engineers will build two different tables.                                                             
                                                                                                                                                                                                                                                        
  Suggested resolution:                                                                                                                                                                                                                                 
  Add a price_snapshot entity to schema.md § Entities with: columns (asset, sub_verb, price, currency, captured_at, source_url, and any other fields), the actual unique constraint, whether rows are INSERT-only or UPSERT, the partition key, and the
  retention horizon invariant. Spec-level shape, not DDL — that stays in design notes.

  ▎ F3 — /retry anchor survival across restarts is promised but no storage entity is named
                                                                                                                                                                                                                                                        
  Severity: blocker
  Category: gap / inconsistency                                                                                                                                                                                                                         
  Location: schema.md § Per-scope state (L122–130), llm.md § Determinism boundary (L202–208), decisions.md D36                                                                                                                                          
  Confidence: high                                                                                                                                                                                                                                      
                                                                                                                                                                                                                                                        
  What the spec says:                                                                                                                                                                                                                                   
  - schema.md L123–127: "Chat session / context window… persistence is required by two spec commitments: auto-/compress near the context-window ceiling… and the /retry anchor (decision D36) survives Provider restart for the bounded retry window."  
  - llm.md L202–208: "/retry (decision D36) reuses the deterministic post selection and clustering captured by the original summary-producing command; it does not re-execute the SQL against current DB state."                                        
  - decisions.md D36: "reusing the deterministic post selection and clustering (D19); only the non-deterministic prose layer is re-rolled."                                                                     
                                                                                                                                                                                                                                                        
  Why it's a problem:                                                                                                                                                                                                                                   
  The /retry anchor needs to store the set of post IDs and clusters from the original summary-producing command so /retry can replay them. The spec says this persistence happens in chat_session — but chat_session is described as "Per-(user, scope) 
  live context state, persisted in the database (not in-process)" holding the "active context window." A list of post IDs from a /summary SQL query is not the same thing as a chat context window. Does chat_session carry arbitrary key-value state?  
  Does the retry anchor overwrite the chat context? An implementer reading only schema.md would not know where to store the anchor or that chat_session must carry it.                                                                                  
                                                                                                                                                                                                                                                        
  Suggested resolution:                                                                                                                                                                                                                                 
  Either (a) explicitly state in schema.md that chat_session stores the retry anchor as part of its payload (and define what other state it holds), or (b) add a dedicated retry_anchor column or row to scope_preferences (since the anchor is
  per-scope and cleared by any non-/retry input). I lean toward (b) — it's a simpler contract and avoids overloading chat_session.

  ▎ F4 — How the Provider learns which assets and sub-verbs are enabled is unspecified
                                                                                                                                                                                                                                                        
  Severity: blocker
  Category: gap                                                                                                                                                                                                                                         
  Location: commands.md § Asset commands, deployment.md § Operator inputs, schema.md § Entities                                                                                                                                                         
  Confidence: high                                                                                                                                                                                                                                      
                                                                                                                                                                                                                                                        
  What the spec says:                                                                                                                                                                                                                                   
  - deployment.md L97–100: The Collector loads bootstrap-assets.json and "upserts the per-asset enabled-sub-verb allowlist."                                                                                                                            
  - commands.md L165–166: "Only operator-enabled assets appear in /help; only enabled sub-verbs appear in per-command help."                                                                                                                            
  - schema.md: no entity defined for the asset/sub-verb allowlist.                                                          
  - security.md L433–442: DB roles — Collector INSERT/UPDATE on ingest-owned tables; Provider SELECT-only on collector-owned tables.                                                                                                                    
                                                                                                                                                                                                                                                        
  Why it's a problem:                                                                                                                                                                                                                                   
  The Provider must know which assets and sub-verbs are enabled to (a) list them in /help, (b) accept or reject /zcash invocations, (c) validate sub-verb arguments. But: what table does the Collector write this allowlist to? The Provider needs to  
  SELECT from it, so the table must be in the shared schema and the Provider DB role must have SELECT access. The spec names no such table. Without it, an implementer might have the Provider read bootstrap-assets.json directly (creating a          
  shared-file coupling that violates the "no shared file state" principle in deployment.md L24), or hardcode the allowlist (defeating the operator-configurability commitment).                                                                         
                                                                                                                                                                                                                                                        
  Suggested resolution:                                                                                                                                                                                                                                 
  Add an asset_config entity to schema.md with (asset, sub_verb, enabled, default_quote_currency, …). State that the Collector upserts it at bootstrap and the Provider reads it at command-dispatch time. The bootstrap-assets.json file is the source 
  of truth; the table is the runtime copy.

  ▎ F5 — Auto-compress trigger threshold is undefined ("near the context-window ceiling")
                                                                                                                                                                                                                                                        
  Severity: major
  Category: ambiguity                                                                                                                                                                                                                                   
  Location: schema.md § Per-scope state (L123–125), decisions.md D24, llm.md § Hardware profile contract                                                                                                                                                
  Confidence: high                                                                                                                                                                                                                                      
                                                                                                                                                                                                                                                        
  What the spec says:                                                                                                                                                                                                                                   
  - schema.md: "auto-/compress near the context-window ceiling (decision D24) needs the full live history to summarize."                                                                                                                                
  - decisions.md D24: "Auto-triggered near the context-window ceiling."                                                                                                                                                                                 
  - llm.md design-notes trailer: "Per-profile context-window sizes and auto-compress thresholds."
                                                                                                                                                                                                                                                        
  Why it's a problem:                                                                                                                                                                                                                                   
  "Near the ceiling" is stated as a spec commitment (it's in schema.md) but the threshold is entirely undefined at the spec level. Does auto-compress trigger at 75%? 90%? A fixed token count before the ceiling? The answer matters because           
  compressing too late leaves insufficient context-window headroom for the LLM to generate the compression itself (the compress operation consumes tokens). Compressing too early wastes the LLM call. The design-notes trailer says thresholds live in 
  design notes, but the existence of a spec-level threshold category (e.g., "a profile-driven percentage of the context window") belongs in the spec.                                                                                                   
                                                                                                                                                                                                                                                        
  Suggested resolution:
  Add to llm.md or architecture.md: "Auto-compress triggers when the context window reaches a profile-driven occupancy threshold (e.g., 75%—85% of the profile's context-window size). The remaining headroom is reserved for the compression prompt and
   reply. The exact threshold per profile lives in design notes."

  ▎ F6 — Stage 1 is undefined for StreamSource (Nostr) events
                                                                                                                                                                                                                                                        
  Severity: major
  Category: inconsistency                                                                                                                                                                                                                               
  Location: security.md § Nostr (L114–152), security.md § Ingest pipeline (L54–64)
  Confidence: medium                                                                                                                                                                                                                                    
                                                                                                                                                                                                                                                        
  What the spec says:                                                                                                                                                                                                                                   
  - security.md L54–64: Stage 1 runs "HTML sanitization against an allowlist" and "prompt-injection regex set" on every post.                                                                                                                           
  - security.md L136–140: "the kind filter is part of Stage 1. The kind filter applies after the signature check and before any body interpretation."                                                                                                   
  - D38 says: "every received event MUST pass signature verification against its claimed pubkey before Stage 1."                                     
                                                                                                                                                                                                                                                        
  Why it's a problem:                                                                                                                                                                                                                                   
  Stage 1 is defined as HTML sanitization + regex + Unicode normalization. But Nostr events don't carry HTML — they're JSON with a content field that is plain text. Applying "HTML sanitization" to plain text is a no-op, but the spec claims "the    
  kind filter is part of Stage 1." This conflates two different concepts: the kind filter (a protocol-level filter that drops unwanted Nostr kinds) and the Stage 1 content-safety pipeline (HTML/regex/Unicode). The statement "kind filter is part of 
  Stage 1" means either (a) Stage 1 has a different meaning for stream sources (breaking the pipeline abstraction), or (b) the kind filter runs in parallel with Stage 1 (making the ordering "signature → kind filter → Stage 1 content checks"        
  ambiguous). Two implementers will put the kind filter in different places.                                                                                                                                                                            
                  
  Suggested resolution:                                                                                                                                                                                                                                 
  Separate the kind filter from Stage 1 explicitly. In security.md Nostr section: "The kind filter is a pre-pipeline protocol gate that runs after signature verification and before Stage 1. Stage 1 (HTML sanitization, regex, Unicode normalization)
  applies to the content field of allowed kinds. Non-HTML content passes the HTML sanitizer as a no-op. The kind filter is NOT part of Stage 1; it is a Nostr-specific trust boundary that prevents unallowed event types from entering the pipeline at 
  all."

  ▎ F7 — provider_state entity is underspecified — the (s) in "singleton(s)" hides needed design
                                                                                                                                                                                                                                                        
  Severity: major 
  Category: ambiguity                                                                                                                                                                                                                                   
  Location: schema.md § Operational (L134–135), architecture.md § Inter-service communication (L39–46), decisions.md D4, D41                                                                                                                            
  Confidence: medium                                                                                                                                                                                                                                    
                                                                                                                                                                                                                                                        
  What the spec says:                                                                                                                                                                                                                                   
  - schema.md: "Provider state. Singleton(s) holding catch-up high-water marks for the LISTEN/NOTIFY reconciler."                                                                                                                                       
  - architecture.md: "The catch-up query uses > last_ready_post_at; the high-water mark is advanced in the same DB transaction as the side effect it triggers."                                                                                         
  - decisions.md D4: "plus a high-water mark for catch-up after restarts."                                                                                     
                                                                                                                                                                                                                                                        
  Why it's a problem:                                                                                                                                                                                                                                   
  "Singleton(s)" with a parenthetical (s) tells the implementer nothing. Is there one row per notification channel? One row total? The architecture says the high-water mark advances "in the same DB transaction as the side effect it triggers" — but 
  the spec never defines what that side effect IS for each channel. For new_post notifications, what is the side effect? Updating a summary cache? Sending a push to group subscribers? The Provider may not even send pushes (it just processes the    
  event). The high-water-mark advancement has no defined coupling to a specific side effect.                                                                                                                                                            
                                                                                                                                                                                                                                                        
  Suggested resolution:                                                                                                                                                                                                                                 
  Define provider_state as having one row per notification channel (new_post, new_price_snapshot, quarantine state changes). The last_ready_post_at column is advanced in the same transaction that processes the corresponding NOTIFY payload. The side
   effect for new_post is the Provider's processing of the event (e.g., group subscription fan-out, summary cache invalidation); the high-water mark must not advance past a row that hasn't been processed.

  ▎ F9 — Slow-start tier: auto-promotion at probation_until has no background mechanism specified
                                                                                                                                                                                                                                                        
  Severity: major 
  Category: gap                                                                                                                                                                                                                                         
  Location: security.md § Slow-start tier (L310–329), decisions.md D45                                                                                                                                                                                  
  Confidence: medium                                                                                                                                                                                                                                    
                                                                                                                                                                                                                                                        
  What the spec says:                                                                                                                                                                                                                                   
  - "After the probation window elapses, the user is automatically promoted to full access — no admin action required."                                                                                                                                 
  - "Probation state is a single probation_until timestamp on the users row. NULL means full access. Checking it is a single indexed read in the permission step."                                                                                      
                                                                                                                                                                  
  Why it's a problem:                                                                                                                                                                                                                                   
  The spec describes checking probation_until on every request (the permission step checks the timestamp). This works — the user is "automatically promoted" in the sense that once probation_until passes, the permission check returns full access.   
  But the spec says NULL means full access, implying that probation_until transitions from a future timestamp to NULL at promotion time. Who sets it to NULL? If the check is probation_until IS NULL OR probation_until < NOW() then no explicit update
   is needed — but the users row still has a non-NULL probation_until forever, which is semantically inaccurate (the user isn't "in probation" anymore, they just have a past timestamp). If a scheduled job is supposed to set it to NULL, the spec    
  doesn't mention it.                                                                                                                                                                                                                                   
                  
  Suggested resolution:
  State explicitly: the permission check uses probation_until IS NULL OR probation_until < NOW(). A background job (or lazy check on next request) may set probation_until to NULL once it has passed, but this cleanup is optional/cosmetic. The user
  is effectively promoted the instant NOW() > probation_until, regardless of whether the column has been nulled.

  ▎ F10 — /forget purges chat_memory and saved_post but not chat_session
                                                                                                                                                                                                                                                        
  Severity: major
  Category: inconsistency / gap                                                                                                                                                                                                                         
  Location: commands.md § Conversation control (L258–265), schema.md § Per-scope state (L122–130), decisions.md D37                                                                                                                                     
  Confidence: medium                                                                                                                                                                                                                                    
                                                                                                                                                                                                                                                        
  What the spec says:                                                                                                                                                                                                                                   
  - commands.md: "/forget — immediate purge of the calling (user, scope)'s chat memory and saved-post list."                                                                                                                                            
  - schema.md: chat_session holds "Per-(user, scope) live context state, persisted in the database (not in-process)" including the full live chat history for auto-compress.

  Why it's a problem:                                                                                                                                                                                                                                   
  /forget is the user-facing privacy lever — "anything kept on the user's behalf is removed" (commands.md). But chat_session persists the live context window (complete chat history) in the database (schema.md L123). If /forget doesn't purge        
  chat_session, a user who issues /forget believing they've deleted their conversation history has left the full unsummarized chat transcript intact in chat_session. This undermines the privacy-by-minimization commitment (D37).                     
                                                                                                                                                                                                                                                        
  Suggested resolution:                                                                                                                                                                                                                                 
  Either (a) add chat_session to the list of tables /forget purges, or (b) if chat_session must survive for the retry anchor, explicitly state the trade-off: "chat_session is not purged by /forget because it carries the /retry anchor and in-flight
  context. Use /clear to wipe the active context window; /forget removes the durable memory and saved posts."

  ▎ F11 — Nostr event replay on reconnect: "will reappear on the next relay connection" is not guaranteed
                                                                                                                                                                                                                                                        
  Severity: major
  Category: failure-mode / gap                                                                                                                                                                                                                          
  Location: architecture.md § Ingest SPIs (L108–112), security.md § Nostr (L114–152)
  Confidence: high                                                                                                                                                                                                                                      
                                                                                                                                                                                                                                                        
  What the spec says:                                                                                                                                                                                                                                   
  - architecture.md L112: "Events not drained within that window are dropped and will reappear on the next relay connection."                                                                                                                           
  - D38 (Nostr): no mention of relay replay semantics.                                                                                                                                                                                                  
                                                      
  Why it's a problem:                                                                                                                                                                                                                                   
  Nostr relays do not universally replay historical events on reconnect. A relay may send only events published after the subscription is established. If the Collector disconnects mid-event (event received from relay but not written to outbox      
  before the drain timeout), that event is lost forever unless the relay happens to replay it. The claim "will reappear on the next relay connection" assumes relay-side replay, which is not guaranteed by the Nostr protocol. The at-least-once       
  delivery guarantee (architecture.md L107: "Delivery to the outbox is at-least-once") cannot be fulfilled for events that a relay delivers only once.                                                                                                  
                                                                                                                                                                                                                                                        
  Suggested resolution:                                                                                                                                                                                                                                 
  Replace the claim: "Events not drained within that window are dropped. On reconnect, the implementation requests events since the last persisted event timestamp for each relay; relays that support since filters will replay missed events. Relays
  that do not support replay may result in permanent gaps. A per-relay counter tracks missed-drain events." The at-least-once guarantee applies to events successfully received from the relay and persisted to the outbox within the drain window — not
   to events the relay delivered and the Collector failed to persist.

  ▎ F13 — UNKNOWN Stage 2 verdict → quarantine with no stated degradation behavior
                                                                                                                                                                                                                                                        
  Severity: major
  Category: failure-mode                                                                                                                                                                                                                                
  Location: security.md § Failure handling (L364–365), security.md § Failure handling (L371–372)                                                                                                                                                        
  Confidence: medium                                                                                                                                                                                                                                    
                                                                                                                                                                                                                                                        
  What the spec says:                                                                                                                                                                                                                                   
  - "Stage 2 verdict of INJECTION, MALWARE, or UNKNOWN → post stays QUARANTINED until admin review. The judge model treating UNKNOWN as a soft injection signal is intentional: a degraded judge must never auto-release."                              
  - The profile-driven flag that lets production profiles invert the release-on-failure default only applies to infrastructure failure, not to UNKNOWN verdicts.                                                                                        
                                                                                                                                                                
  Why it's a problem:                                                                                                                                                                                                                                   
  If the judge model is underpowered (as it may be on pi or laptop profiles), it may return UNKNOWN for a significant fraction of content. Every UNKNOWN post is quarantined permanently until an admin manually reviews it — there's no automatic      
  re-evaluation for UNKNOWN (the re-evaluation job only covers Stage 2 infrastructure failures, not UNKNOWN verdicts). On a busy feed, this could quarantine hundreds of posts per day with no automatic resolution path. The Stage2UnknownRateHigh     
  alert (deployment.md L161) will fire, but the operator's only remediation is manual review.                                                                                                                                                           
                                                                                                                                                                                                                                                        
  Suggested resolution:                                                                                                                                                                                                                                 
  Either (a) add UNKNOWN posts to the re-evaluation job (so they're periodically re-submitted to Stage 2 on the assumption the model may recover), or (b) explicitly state the trade-off: "UNKNOWN verdicts are quarantined permanently until admin
  review; there is no automatic re-evaluation for UNKNOWN. Operators who observe high UNKNOWN rates should upgrade the security-judge model or switch profiles."

  3. Cross-cutting Observations                                                                                                                                                                                                                         
                                                                                                                                                                                                                                                        
  1. The tagger deterministic-fallback chain is the most cross-cut concern and has the most fragility. The bootstrap_tags column connects: the bootstrap loader (deployment.md), source creation (commands.md), tagger failure handling (security.md),
  and the controlled vocabulary (schema.md). The global tag-replacement via /add-source (F1) breaks the trust model at the most critical point — the safety net that prevents the LLM tagger from silently dropping content.                            
                  
  2. price_snapshot / asset commands are specified across six files but the central entity is missing. This is the clearest example of a cross-file gap: architecture.md keys it, commands.md queries it, security.md role-gates it, schema.md          
  partitions it, deployment.md bootstraps its allowlist — but schema.md never defines the entity itself (F2, F12).
                                                                                                                                                                                                                                                        
  3. Storage entities for command-level state are inconsistently mapped. The /retry anchor (F3), the auto-compress trigger (F5), and the confirmation-token state machine all need persistence. The spec points at chat_session for some and is silent  
  for others. The set of "per-scope state" entities in schema.md doesn't account for every piece of state the commands need to persist.
                                                                                                                                                                                                                                                        
  4. The spec has a recurring pattern of describing the happy path fully but leaving the degradation path underspecified. All-relays-bad (F18), all-sources-failed, UNKNOWN verdict flood (F13), and pagination-cap saturation (F16) all lack defined   
  behavior. The failure-handling section (security.md) is thorough for per-stage failures but doesn't close the loop on systemic degradation.
                                                                                                                                                                                                                                                        
  5. The Provider-Collector handshake for bootstrap data is only partially specified. Source bootstrap is clear: Collector loads bootstrap-sources.json into source rows, Provider reads source rows. Asset bootstrap is unclear: Collector loads       
  bootstrap-assets.json into... what? (F4, F12). If future bootstrap artifacts are added, the same gap will recur. A general principle — "operator-provided bootstrap files are loaded by the Collector into DB tables; the Provider reads those tables"
   — would prevent this pattern.                                                                                                                                                                                                                        
                  
  6. verification.md is strong on core invariants but has noticeable gaps around background/scheduled behaviors. The scheduler, pruner, re-evaluation job, StreamSource lifecycle edge cases, invite-code flow, and slow-start auto-expiry are all      
  stated spec commitments without corresponding verification entries (F15).

  4. Spec Evaluation
                                                                                                                                                                                                                                                        
  Completeness — does it cover what a v1 build needs?
                                                                                                                                                                                                                                                        
  Mostly. The core ingest pipeline, command surface, security model, and adapter contract are covered. The gaps are concentrated in three areas: the asset-command data path (entity missing), the persistence story for command-level state (retry     
  anchor, auto-compress trigger), and the recovery/troubleshooting surface (failed-source recovery command, admin visibility into soft-deleted sources).                                                                                                
                                                                                                                                                                                                                                                        
  Consistency — do the parts agree?                                                                                                                                                                                                                     
  
  Mostly, with one notable conflict. The /add-source tag replacement (commands.md) contradicts the operator-trusted bootstrap model (deployment.md, security.md). The Nostr kind-filter-as-Stage-1 (security.md) doesn't align with the Stage 1         
  definition elsewhere. The invite-code EXPIRED status handling has a denormalization tension. Otherwise, cross-references hold — decisions.md aligns well with the section files, and the architecture principles (determinism boundary,
  no-LLM-in-trust-path) are consistently applied.                                                                                                                                                                                                       
                  
  Implementability — can an engineer build from this without daily clarification?                                                                                                                                                                       
  
  Yes, for the main paths. An experienced engineer can build the RSS ingest pipeline, command router, and chat agent from the spec alone. They will need daily clarification for: the price_snapshot schema, the retry anchor persistence, the asset    
  bootstrap handoff, and the exact behavior of the auto-compress trigger. The design notes are expected to fill in DDL and values, but the entities and contracts those design notes hang on must exist in the spec first.
                                                                                                                                                                                                                                                        
  Testability — does verification.md actually pin down what "done" means?                                                                                                                                                                               
  
  Strong for core invariants, weak for scheduled/background behaviors and the full invite+probation flow. The verification spec is unusually concrete — it specifies test categories, assertion types, and fake/mock strategies. But it has blind spots 
  (F15) that would let regressions slip through in features that aren't part of the MVP slim path but ARE part of v1.
                                                                                                                                                                                                                                                        
  Evolvability — how well does the spec/design split hold up? What's most likely to leak?                                                                                                                                                               
  
  The split is well-conceived and mostly well-maintained. The "What lives in design notes" trailer on every file is a good discipline. The leaks I found are: the auto-compress threshold ("near the ceiling" is too vague for spec), the confirmation  
  timeout is mentioned as profile-tunable but its relationship to the retry cap and other timeouts isn't systematized, and the bootstrap_tags column name itself is a design-level name that leaked into the spec (the spec should call it "fallback
  tags" or "source tags" and leave the column name to design). The most likely future leak: adding a third adapter will pressure the capability-flag system to grow transport-specific flags, and the spec doesn't provide a principle for when a flag  
  graduates from "adapter quirk" to "spec-level capability."

  5. Pros and Cons of the Current State
                                                                                                                                                                                                                                                        
  Pros
                                                                                                                                                                                                                                                        
  - The determinism boundary is the strongest design decision in the spec. It's stated in architecture.md, enforced in commands.md, verified in verification.md, and cross-referenced in decisions.md (D19). Every command and LLM call site is         
  classified as inside or outside the boundary. This is the kind of architectural clarity that prevents entire classes of bugs.                                                                                                                         
  - The threat model and layered ingest security (Stage 1 deterministic + Stage 2 LLM) is unusually thorough for a pre-implementation spec. The verdict-vs-infrastructure split (D22) is precisely the right abstraction. The re-evaluation job closes

# Decisions log

Cross-cutting choices that shape the rest of the spec. Each row is a settled
*direction*, not an implementation detail. Concrete values (DDL, class names,
property keys, retry counts, model names, sizes) live in `docs/design/`.

If a row here changes, the spec changes; if a value in `docs/design/` changes,
the spec does not.

**D-number policy.** D-numbers are append-only. They are never reused
and never reordered. Editing an existing row requires a sync-check
pass against every spec section that cites it. Adding a new direction
appends a new row at the next D-number; deprecating a direction
edits the existing row and notes the supersession (do not delete).

| D15 | Per-scope tag prefs | `/follow-tag` / `/unfollow-tag` control which tags appear in periodic digests; default is "all tags from subscribed sources". |
| D16 | Group bot behavior | Replies only on @mention; group-admin-only destructive ops; periodic morning/evening digest by per-group timezone. |

Stage 2 *infrastructure* failure → release with Stage 1 redactions retained, flagged for re-evaluation. Tagger fallback → source's bootstrap tags. Embedding/entity failure → release without that artifact. Admin notifications throttled. |

| D25 | `/clear` semantics | Wipes only the active context window for the calling (user, scope). Long-term memory is independent. |

| D28 | Memory retrieval | Hybrid: deterministic keyword pre-fetch (cheap, always) plus an agent tool for deeper recall. |
| D29 | Translation | English by default. Per-scope language opt-in via `/lang`. Source bodies are never translated; translation is presentation-only. Pluggable provider SPI; v1 ships English + Czech. |
| D30 | Output formatting | Plain text. Inline code in single backticks; multi-line in triple backticks; URLs bare. Adapters expose a capability flag for richer rendering. |
| D31 | Progress notifications | Long-running requests publish stage events to a cross-cutting notifier; the notifier renders them via adapter capabilities (in-place edit / typing indicator) and falls back to a single final send when the adapter doesn't support edits. User input is never interpolated into progress strings. |
| D32 | Adapters as SPIs | `LlmProvider`, `EmbeddingProvider`, `MessagingAdapter`, `TranslationProvider` are pluggable interfaces. Concrete impls picked by config. v1 ships SimpleX, Signal, and an in-memory test adapter. |
| D33 | TTL strategy | Old post-derived rows expire by partition drop, not row-level DELETE. Post bodies have a fixed retention horizon; saves are exempt via snapshot copy. |
| D34 | DB roles | Least-privilege split per service role; LLM-reachable code paths run under read-only roles where possible. |
| D35 | Request cancellation | `/stop` cancels the calling (user, scope)'s in-flight interruptible request (chat-mode agent loop, user-issued `/summary`, user-issued `/retry` re-roll) **immediately**, freeing the worker for others: the in-flight LLM stream is closed and any in-flight read-only tool call (e.g., DB query) is cancelled. The cancellation window covers the LLM and tool-call stages only — once outbound delivery has begun, the message is not unsent. Per-(user, scope) isolated. Idempotent. Periodic digests, ingest, and already-completed work are not interruptible (`/retry --digest` against a periodic digest is also non-interruptible since it shares the periodic-digest worker path). Progress notifier renders a final "stopped" state. |
| D36 | Summary regeneration | `/retry` re-runs the LLM prose stage of the last summary-producing command for the calling (user, scope), reusing the deterministic post selection and clustering (D19); only the non-deterministic prose layer is re-rolled. Bounded by a small fixed retry cap (value in design notes) anchored to the most recent summary-producing command. The retry anchor is cleared by any non-`/retry` input from the same (user, scope); `/retry` itself never advances or resets the anchor. No eligible anchor (or anchor cleared, or prior command cancelled by `/stop`) → friendly error. For periodic group digests `/retry` requires group admin or bot admin and replaces the cached digest (D17). |
| D37 | User data minimization | Privacy is achieved by **minimization, not application-layer encryption**. Per-user encryption with a server-held key would be obfuscation (the Provider must read plaintext to summarize, run the chat agent, and produce digests). DB-at-rest encryption is an operator concern (LUKS, managed-DB transparent encryption). v1 commitments: (a) `chat_memory` entries that are not `/save`d carry a fixed TTL (value in design notes); (b) `/forget` purges the caller's `(user, scope)` chat memory and saved-list, audit-logged, requires confirm; (c) `/export` returns the caller's own data; (d) `chat_memory` content and saved-post bodies never appear in non-audit logs, even at DEBUG. Per-user encryption with user-supplied keys is deferred — it would require disabling periodic digests and asynchronous features for opted-in users, and is gated on a future product decision. |
| D38 | Nostr ingestion (v1) | Nostr is a v1 source, ingested by a new **`StreamSource` SPI** that is separate from the existing polled `Fetcher` SPI (subscription lifecycle is fundamentally different from polled). `StreamSource` is named around long-lived event streams, not websockets specifically, so future non-websocket streams (SSE, gRPC, message broker) fit without rename. The Collector is **forever read-only** for Nostr: no key handling, no signing, no publishing — lifting this requires a spec amendment. v1 surface: kinds 1 (text notes) and 6 (reposts) only; kind 6 reposts are stored with a reference to the original event id but the original is **not** auto-resolved in v1; all other kinds (DMs/4, reactions/7, etc.) are dropped without parsing. Relay list is **operator-configured** via `application.properties` / bootstrap JSON; **no NIP-65 auto-discovery in v1** — the trade-off is that content posted only to relays outside the operator's list is invisible to the bot (deliberate v1 simplification, not a bug). Trust boundary: every received event MUST pass signature verification against its claimed pubkey **before** Stage 1; failed sigs are dropped + counted, never enqueued. This is the ingest-layer mirror of D10. Cross-relay dedup (same event-id from N relays → one `posts` row) and per-relay degradation handling (one bad relay must not block the StreamSource; mark-bad threshold and cooldown in design notes) are spec-level commitments. Source identity generalizes from `(fetcher, url)` to `(kind, identifier)` as the unique key, with `config` as a mutable value attached to that key (not part of the unique key): identifier is the URL for HTTP-shaped sources and the filter spec for Nostr; config is opaque per-kind JSON. **`config` mutation in v1 is restart-only** — the only path is editing `bootstrap-sources.json` and restarting the Collector, which re-runs the idempotent loader and updates `config` in place on existing `(kind, identifier)` rows. There is no v1 chat command that mutates `config` (no `/source-config`, no `--config` flag on `/add-source`); a runtime admin command for `config` mutation is a v2 candidate. |
| D39 | Asset commands (v1) | Per-asset top-level commands (`/zcash`, `/monero`) expose price/market data and, in the future, asset-specific verbs (e.g. shielded-pool stats, ring size, halving math). Each command's first positional argument is a **sub-verb** that selects a data source: `coingecko` (aggregated snapshot), `kraken`, `bitfinex` (per-exchange snapshots) in v1. Bare `/zcash` / `/monero` resolves to the per-asset default sub-verb declared in `bootstrap-assets.json`; when no default is configured for the asset, bare invocation returns the friendly "not configured" error (no implicit fallback to a hard-coded source — silent fallback would mask operator misconfiguration). Sub-verbs are exact-match against an allowlist; unknown sub-verbs produce a friendly error with fuzzy suggestions, consistent with tag-argument handling. The set of enabled assets and per-asset enabled sub-verbs is operator-configured and seeded from `bootstrap-assets.json` (parallel to `bootstrap-sources.json`). Permissions: any non-banned user, DM and group, no admin tier. Data is **not posts**: snapshots live in a collector-owned `price_snapshot` (or equivalent) table outside the post pipeline — no Stage 1/2, no tagging, no embedding, no quarantine. Polled data sources reuse the existing `Fetcher` SPI on a profile-driven refresh interval; results are cached so repeated user calls are served from cache, not refetched per request. **Mandatory data-source attribution**: every reply names the data source in the header (`Zcash (kraken)`, `Zcash (coingecko)`) and includes the source URL bare (D30) so per-source ToS attribution is satisfied per reply. **v1 exchange allowlist**: CoinGecko **free public endpoint** (no API key required), plus Kraken and Bitfinex public REST as the per-exchange fallbacks if CoinGecko's free policy changes. Exchanges that require an API key or auth token (KuCoin, Gemini for most endpoints, the CoinGecko Pro tier, operator-provided keys for any free tier) are **out of v1** — adding them requires the operator-secret SPI surface, which is its own decision. Asymmetric availability is permitted by design: `/monero binance` and `/monero coinbase` are not enabled because XMR is not listed there; the per-asset sub-verb allowlist captures this. **Live ticker mode (websocket-driven, in-place edits) is explicitly deferred to v2** — it requires a new `TickerStream` SPI, a "background subscription" cross-cutting concept, and capability-gated message-edit semantics that v1 does not commit to. |
| D40 | `chat_memory` TTL (v1) | `chat_memory` rows carry a **fixed retention horizon** in v1 (value profile-driven and in design notes). A scheduled pruner removes expired rows; this is the privacy-by-minimization commitment behind D37 §(a). `/save`d posts are stored separately (D13) and are **not** affected by the pruner. `/forget` (D37) is the user-initiated immediate purge and runs independently of the scheduled pruner. The TTL is not user-configurable in v1 — users control purge via `/forget`, not by tuning TTL. This row settles a prior contradiction between the spec (which committed to a TTL+pruner via schema invariant 9 and D37) and earlier design notes that said "no pruner in v1": the spec direction wins, and design notes follow. |
| D41 | Deployment topology (v1) | **Exactly one Collector and exactly one Provider** against a shared Postgres in v1. The `LISTEN/NOTIFY` + outbox + high-water-mark design is correct for that topology; running more than one of either service is unsupported and would produce duplicate fetches, duplicate periodic digests, and contention on `provider_state`. The "independent scaling" benefit of the service split is about deploying the two services on different hosts with different resource shapes (Collector wants disk + RAM for embeddings; Provider wants steady CPU for chat), not about running N copies. Operators who need more throughput pick a heavier hardware profile (D27). Multi-instance horizontal scaling is a v2 spec amendment: it needs per-source leasing (or partitioned fetcher assignment), per-group digest leasing, and a coordination story for the high-water mark. |
| D42 | Fetcher failure policy | A `Fetcher` failure (HTTP error, connection timeout, feed parse failure) on an HTTP-shaped source retries on the next scheduled tick — no immediate same-tick retry storm. After *N* consecutive per-source failures (profile-driven, value in design notes) the source's `status` transitions to `'failed'`, the scheduler stops scheduling it, and a throttled admin notification is sent with the error class and source id. Other sources are unaffected — one bad RSS feed must not stall the rest of the ingest pipeline. The source returns to `status='active'` only via an admin command (an explicit re-enable; no automatic recovery). This row is the Fetcher mirror of D38's per-relay degradation commitment for `StreamSource`, so HTTP-shaped and stream-shaped sources have parallel failure-isolation contracts. The source `status` state machine (`active`/`failed`/`disabled`, orthogonal to `deleted_at`) is in `schema.md` §Sources and tags. |
| D43 | Localization vs. translation | Two distinct paths for non-English output. **Deterministic strings** (`/help` and other deterministic-command output, friendly errors, the banned-user fixed reply, progress-notifier stage strings, the "source already existed, tags updated" line, etc.) come from a **localization bundle** keyed by string id; v1 ships **`en` and `cs` (Czech)** bundles and adding a third language is a bundle drop-in. **LLM-authored prose** (cluster summaries, chat replies, periodic digest prose) goes through `TranslationProvider` (D29) when the scope's `/lang` is non-English. The two paths are **never mixed** — running deterministic command output through a model would introduce non-determinism into deterministic surfaces and is a sanitizer-bypass risk; running LLM prose through the localization bundle is impossible (no fixed key). v2 may add bundles for further languages, an LLM-backed bundle generator, or both, but the routing rule (deterministic = bundle, LLM-authored = translator) does not change. **Localization bundle completeness** is enforced at build time: every shipped language bundle MUST contain every key in the registry; CI fails on a missing key. Missing keys in `en` are a startup error (no runtime fallback to a different language). |
| D44 | Invite-code registration | DM access is gated by a bot-admin-issued invite code applied uniformly across all adapters. `/invite create --adapter <name>` requires exactly one of two mutually exclusive flags: `--contact <id>` (strict — code bound to a specific (contact\_id, adapter) pair, no confirm required) or `--open` (adapter-bound — first unknown contact on that adapter to present the code is registered, requires confirm due to broader blast radius). Providing neither flag returns a hint; providing both is an error; no code is created in either case. An unknown DM contact's first message must equal a PENDING, non-expired invite code; the match rules differ by invite type: `--contact` requires contact\_id + adapter + code to match; `--open` requires only adapter + code. Any failure returns a fixed "access requires an invitation" reply; no registration occurs. On success: user row created, code transitions to USED (race-safe consume via a conditional UPDATE — `schema.md` §Identity), user enters slow-start tier (D45), invite-acceptance is audit-logged. `/invite revoke <code>` requires confirm (matches `commands.md` §Admin). Codes are single-use and carry an operator-configured TTL. The stored status enum is `{PENDING, USED, REVOKED}` (no stored `EXPIRED`); the intake path treats a `PENDING` row whose `expires_at` has passed as expired without writing a transition. A per-`(adapter, contact_id)` brute-force rate limit applies (`security.md` §Invite-code registration). Pre-banned-contact `/invite create --contact <id>` returns a friendly error and creates no invite. Group @mention registration is removed by D47 — the DM invite gate is the universal registration path. Group interaction requires a prior DM-side registration; group membership alone does not confer bot access. Bot admin and bootstrap-seeded users are exempt. `/ban <contact>` against an unknown contact pre-creates a banned row without an invite. |
| D45 | Slow-start tier | Every newly registered user starts in a probation period whose duration is profile-driven (value in design notes). During probation the user may issue the read-only subset plus the user's own privacy/locale levers: `/help`, `/status`, `/get-tags`, `/get-sources`, `/list-sources`, `/summary`, `/saved`, asset commands, `/export`, **`/forget`** (privacy lever per D37), **`/lang`** (single-row UPDATE, no LLM cost). All other write operations (`/add-source`, `/save`, `/unsave`, `/follow-tag`, `/unfollow-tag`, `/clear`, `/compress`, `/group-timezone`, `/retry`) and chat mode are blocked with a friendly "account is in the probation period, access broadens in N hours" reply. `/stop` is not blocked: it returns the standard idempotent no-op reply during probation regardless of in-flight state, because it has no side effect. After the probation window elapses the user is automatically promoted to full access with no admin action. A bot admin can issue `/vouch <contact>` at any time; `/vouch` sets `probation_until = NULL` (immediate graduation). For a row already past probation, `/vouch` is a no-op with a friendly reply. The two-step path `/invite create --contact <id>` followed by user consume does not clear probation — a vouched user gets full access immediately, an invited user serves out the probation window first. Probation state is stored as a `probation_until` timestamp on the `users` row; null means full access. The auto-promotion mechanism is **lazy**: the permission check is `probation_until IS NULL OR probation_until < NOW()` — the user is promoted at the instant `NOW() > probation_until`, regardless of whether the column has been nulled. A passive sweep clears the column on the next request from a promoted user; no background job is required. |
| D46 | Multi-adapter Provider topology (v1) | One Provider may run **one or more** messaging adapters simultaneously (any non-empty subset of SimpleX / Signal / the in-memory test adapter, per D32 and D41); operators are not required to deploy one Provider per adapter. The architectural drivers: (a) the LLM concurrency cap is a per-process value (`llm.md` §Bounded concurrency) and splitting it across Provider instances would multiply load on a shared local model — decisive on `laptop` and `pi` profiles; (b) the schema's `(adapter, contact_id)` keying and cross-adapter isolation invariants are load-bearing only when one Provider sees both adapters; (c) D41's "exactly one Provider per deployment" is preserved unchanged. Bot-admin contact id is configured **per adapter and is optional per adapter** — only the union of bootstrap admin contacts across enabled adapters MUST be non-empty (`deployment.md` §Operator inputs item 2). `/grant-admin` and `/revoke-admin` are scoped to the inbound adapter (no cross-adapter elevation; bounds the blast radius of a single-adapter compromise). Last-admin protection is **global across adapters** — the trigger counts `is_admin = true` rows across the whole `users` table, not per `(adapter)`. Per-adapter compromise threat profiles (Signal SIM-swap exposure vs. SimpleX cryptographic-queue ephemerality) are documented in `security.md` §Per-adapter admin threat profile so operators can choose admin placement deliberately. The in-memory adapter is exercised in a separate test-time deployment shape; production deployments MUST NOT enable it alongside the production adapters. |
| D47 | Group authorization gate | Group interaction requires two gates (registered-only + admin-approved). (1) The bot processes group @mentions only from users with `registration_state IN ('invited', 'vouched')`; unknown contacts receive no reply and no registration — the group auto-registration path (v1-pre-D47 auth step 3) is removed and `registration_state = 'group_only'` is removed from the enum. (2) Every `groups` row carries `approval_status ∈ {pending, approved, rejected}`; a group enters as `'pending'` on first registered-user @mention; while pending or rejected the bot sends one fixed reply (per-group rate-capped) and performs no further processing (no commands, no chat, no digests). `/approve-group` and `/reject-group` are bot-admin commands; `/reject-group` requires confirm. Per-group rate caps (profile-driven values in design notes) bound total command volume and LLM calls per approved group; the same per-group reply rate bucket bounds outbound cost for pending/rejected groups. A per-user group activation cap (profile-driven) bounds how many groups a single user can activate. A global max-groups cap (profile-driven) is the absolute ceiling. Periodic digests fire only for approved groups. The `activated_by` column on `groups` tracks which user activated each group for accountability. |
| D48 | §7a contract enforcement | The §7a "method parameter contracts" rule is enforced by **NullAway** (built on **Error Prone**), wired into the Maven build so it gates `mvn verify` — superseding the earlier author-side regex lint. The model is **non-null-by-default**: each module's packages are null-marked (via NullAway `AnnotatedPackages`), so only genuinely-nullable parameters/returns/fields carry `@Nullable` (JSpecify) and `@NonNull` is no longer written by hand. Error Prone's default bug-pattern checks run alongside NullAway (`NullAway:ERROR`); a curated set of additional checks is promoted to ERROR. Adoption is **incremental per Maven module** (foundational module first); framework-initialized fields (`@PostConstruct` / CDI `@Inject`) are handled via NullAway's excluded-field-annotations config and generated sources are excluded. When every module is onboarded, the regex lint and its baseline are retired and the §7a rule text in the engineering docs is rewritten to describe the non-null-default + NullAway model. The §7a **goal** — explicit, machine-checked nullability contracts — is unchanged; only the enforcement mechanism changes. |
| D49 | llama.cpp standalone backend + embeddings shape | llama.cpp is a **real standalone local LLM backend**, not a stub: `llama-server` is started with an explicit model + host bind (reachable over the compose network as `llamacpp:8080`) and serves the OpenAI-compatible API the LLM adapter already speaks (`infochat.llm.*.provider=openai-compatible`). Because **one `llama-server` instance serves exactly one model**, the generative model and the fixed-dimension nomic embedder (`infochat.embeddings.dimension=768`, `allow-model-change=false`) cannot share a server. The operator therefore picks one of **two embeddings shapes**: (a) *pure llama.cpp* — a **second** `llama-server` instance in embedding mode serving a nomic-class GGUF on its own port + healthcheck, which `infochat.embeddings.*` points at; or (b) *Ollama embeddings* — the `ollama` service runs **alongside** the generative `llamacpp` service and `infochat.embeddings.*` points at the Ollama nomic endpoint. Shape (b) **relaxes the earlier "operator picks ONE local LLM backend" guidance**: two local LLM services (generative llama.cpp + embeddings Ollama) MAY run together, because no single llama.cpp server can be both the generative model and a second fixed-dimension embedder. In **both** shapes the embedder is nomic-class and 768-dim, and embeddings **never** point at the generative model. The generative backend defaults to a curated checksum-pinned GGUF and the operator may override it; an embeddings override must remain 768-dim (the wizard guards/warns, consistent with `allow-model-change=false`). Concrete values — image tags, pinned GGUF URLs + SHA-256, Compose profiles, env-var wiring — live in `docs/design/07-deployment.md`. |
| D50 | SimpleX bootstrap admin via claim-token (per-adapter bootstrap split) | The bootstrap-admin path differs **per adapter** because the adapters expose different identity primitives. **Signal** has a real cryptographic account id (ACI), so its admin stays **configure-by-ACI**: the operator sets the ACI in config and Provider pre-seeds an `is_admin = true` row at startup (D9). **SimpleX has no pre-configurable cryptographic sender address** — identity is the per-connection id the transport assigns, and a sender's advertised profile address (`contact.profile.contactLink`) is **self-asserted, not verified** ("the sender's own published address is not verified … out of scope of SMP protocol", simplexmq `protocol/simplex-messaging.md`). Configure-by-address is therefore impossible for SimpleX: there is no stable address to pre-seed, and trusting the advertised one lets any contact spoof the admin (the discarded M1-505 approach). Instead SimpleX bootstrap admin is established by a **single-use claim-token**: the operator configures a secret `infochat.adapters.simplex.admin-token`; the **first** DM whose normalized body equals the token registers the *sending connection's* contact id and sets `is_admin = true` on that `(simplex, contact_id)` row. The token is **single-use** — while a SimpleX admin exists, a later presentation of the same token (same or different contact) grants nothing and yields the same fixed reply an invalid invite would (no validity oracle); operators unset the token once the first admin is established (the residual caveat — a still-configured token could re-arm if the SimpleX admin is later revoked — and its mitigation are detailed in `security.md` §Per-adapter admin threat profile, with permanent-single-use deferred as future work since a durable token-spent marker would require a schema change the audit-write-only app role cannot avoid). Nothing is pre-seeded for SimpleX (`AdminBootstrap` skips it). The token is the same shape as the D44 invite-code mechanism (a secret presented in a first DM grants access), extended to also flip `is_admin`. A configured SimpleX admin-token counts as SimpleX's bootstrap-admin path for the union-non-empty constraint (`deployment.md` §Operator inputs item 2). The DM identity stays the connection-based `contact_id`; the advertised address never influences it (trust boundary 1). v1 is one operator-configured single-use first-admin token; rotation / multi-admin issuance / token lifecycle are future work. The by-address admin *commands* (`/grant-admin <contact>` etc.) carry the same broken "stable public SimpleX address" assumption and need a separate connection/handle-based rework (tracked as a follow-up, not part of this decision). |
| D51 | SimpleX group mention recognition anchored to the per-group memberId | The cross-adapter mention-recognition rule is unchanged (`messaging.md` §Required SPI surface, design §6.2.3/§6.10): a group message counts as an `@mention` of the bot **only** by **byte-equality against the bot's own cryptographic contact id**, never display-name text. What changes is **SimpleX's concrete anchor**. The earlier model byte-matched the bot's **queue address** against a `formattedText[].format.memberRef` queue address; live simplex-chat **v6.5.4.1 carries no queue address in the mention payload** — the `formattedText` mention segment is `{type:"mention",memberName:"<name>"}`, member identity lives in a separate top-level `mentions{}` object keyed by display name (each carrying a per-group `memberId`, simplex `CIMention.memberId`), and the bot's own per-group memberId is in the same frame at `chatInfo.groupInfo.membership.memberId`. ## How to evolve this list

- **Adding a row** is a spec change: open it for review, then update the
  affected spec section.
- **Removing a row** requires identifying what replaces it; "we changed our
  minds" is fine, but the replacement direction goes in a new row so the
  history is legible.
- **Refining values** (e.g. retry count, model name, schema column) is *not*
  a decision change — that lives in `docs/design/`.

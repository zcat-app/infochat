## Finding 1 — `commit` step's stale-log check fires on every low-risk ticket

**Location:** `.claude/skills/m1-tick/SKILL.md` `## commit <id>` step 1–2.

**Behavior today:**
- Step 1 collects "commit candidates" via `git diff --name-only HEAD`, excluding only the ticket file.
- Step 2 (low-complexity / low-risk path) compares the most recent test-log mtime against the max mtime among commit candidates. If the log is older than any candidate, refuses the commit.
- But `STATUS.md` is regenerated by the *preceding* `/m1-tick review` step's APPROVE branch — *after* the `mvn verify` that produced the test log. So `STATUS.md`'s mtime is always later than the test log's mtime at commit time.
- Result: every low-risk ticket trips a false-positive stale-log refusal at `commit`, requiring an unnecessary `mvn verify` re-run.

**Why this slipped through:** `STATUS.md` is a workflow-artifact regeneration, not a source-code edit; the freshness check is designed to catch "developer edited code after running tests" and shouldn't apply to it.

**Fix options (pick the simpler):**
- **(A)** Exclude `docs/plan/m1/STATUS.md` from the commit-candidate set in step 1 alongside the ticket file. The freshness check then runs only against real source candidates. Simplest.
- **(B)** Move STATUS.md regeneration in `review`'s APPROVE branch to *before* `mvn verify` is captured (i.e. regenerate it before the test runs). Requires a more invasive reordering of the review step. Probably overkill.

**Recommendation:** option A. The fix is a one-line change to the commit-step procedure: extend the "exclude the ticket file" carve-out to "exclude the ticket file and STATUS.md".

**Acceptance criterion suggestion:** after the fix, `/m1-tick commit <id>` on a low-risk ticket whose only post-test-log workflow mutation is STATUS.md must NOT refuse the commit.

## Finding 2 — STATUS.md is one step behind the ticket commit

**Location:** `.claude/skills/m1-tick/SKILL.md` `## commit <id>` steps 4–7.

**Behavior today:**
- Step 4: set ticket frontmatter `status: done`.
- Step 5: stage commit candidates + ticket file.
- Step 6: `git commit`.
- Step 7: regenerate STATUS.md.

The committed STATUS.md reflects the *pre-commit* state (e.g. `M1-NNN: in-review`) because regeneration happens after the commit. Step 7's regenerated STATUS.md sits as an uncommitted modification, which then blocks the next `/m1-tick start`'s "clean working tree" precondition.

In M1-001 we resolved this by adding a follow-up commit on the branch (`M1-001: regenerate STATUS.md (post-done)`); squash-merge to main collapses both into one. Workable but ugly.

**Fix:** move STATUS.md regeneration to *before* the commit. Sequence becomes:

1. Identify commit candidates (current step 1).
2. Test-freshness check (current step 2).
3. Build commit message (current step 3).
4. Set ticket frontmatter `status: done` (current step 4).
5. **NEW:** regenerate STATUS.md (currently step 7, moved up).
6. Stage commit candidates + ticket file + STATUS.md (current step 5, with STATUS.md added explicitly to the staged set).
7. `git commit` (current step 6).
8. (delete the old step 7.)

This requires Finding 1 to also be fixed, otherwise the STATUS.md mtime will be even *later* relative to the test log when freshness is checked.

**Acceptance criterion suggestion:** after the fix, the working tree is clean immediately after `/m1-tick commit M1-NNN` returns; `git log --name-only -1` shows STATUS.md as part of the ticket commit; the committed STATUS.md shows the ticket as `done`.

## Finding 3 — `review` captures an empty diff before the commit exists

**Location:** `.claude/skills/m1-tick/SKILL.md` `## review <id>` step 2 + `docs/process/reviewer-prompt.md` "## Diff" header.

**Behavior today:**
- Step 2 says: capture `git diff main...HEAD` as the full diff for the reviewer.
- But `/m1-tick commit` runs *after* `/m1-tick review`. At review time, no commit exists on the branch yet (the implementation is in the working tree). So `git diff main...HEAD` is always empty for round-1 reviews.

In M1-001 we worked around this by running `git add -N <new-files>` (intent-to-add — does not create a commit) and using `git diff main` (working-tree vs main) as the substitute. The reviewer received the right diff but the prompt header still said `git diff main...HEAD`, which was misleading.

**Fix:** change the canonical command in two places:
- `.claude/skills/m1-tick/SKILL.md` `## review <id>` step 2: replace `git diff main...HEAD` with the actual procedure: `git add -N <untracked-files-in-diff>` then `git diff main` (or the equivalent, whatever produces the working-tree-vs-main diff including untracked files).
- `docs/process/reviewer-prompt.md`: update the `## Diff` header to say `git diff main` (working tree vs main) on branch `{{BRANCH}}` rather than `git diff main...HEAD`.

This also affects diff-stats capture (current round and previous round): the `--shortstat` invocation must match the diff command.

**Open question for the next session:** does `git add -N` cause any side effects we should clean up? In M1-001 it had none — the entries were absorbed by the actual `git add` at commit time. But the spec should call out that the `-N` entries persist until `commit`'s explicit add.

**Acceptance criterion suggestion:** after the fix, the reviewer's `{{DIFF_OUTPUT}}` substitution shows the full implementation diff (including untracked-but-newly-created files) on round 1, before any commit exists on the branch.

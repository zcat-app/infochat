RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: DOS
    SEVERITY: low
    PROMISE: "the threat model is updated, not silently diverged" (ticket R3, 2026-08-03) — and security.md §Failure handling, "Provider-side (user-facing) LLM failures" / "Chat-mode replies": "the deterministic digest-first semantic pre-fetch, which runs once before the LLM call by design (the D28 'always runs, folded in' pattern): on an LLM-unreachable turn that read-only retrieval may already have executed (one local embed + one scoped pgvector probe) before the failure surfaced. It is bounded — read-only, capped in time (the pgvector probe by statement_timeout, the embed HTTP call by infochat.embeddings.timeout-ms), and gated by the same per-user LLM rate bucket as the turn itself".
    GAP: The diff routes a generative ModelTask.TRANSLATOR call into the D28 pre-fetch for every non-English scope — QueryAnchorTranslator.translate (QueryAnchorTranslator.java:148-235, the provider call at :192-194) invoked from SemanticSearchTool.execute (SemanticSearchTool.java:126-127) BEFORE the embed (:132) — but the R3 amendment updated only the semanticSearch tool row and §Rate limiting, not the §Failure handling paragraph. That paragraph still describes the pre-fetch as "one local embed + one scoped pgvector probe" and still claims it is "gated by the same per-user LLM rate bucket as the turn itself" — while the new §Rate limiting text added by this very diff says the translation leg "draw[s] NO per-user bucket token (the bucket counts turns, not generative calls inside them)", and the sub-call is bounded by the TRANSLATOR breaker + translator transport timeouts, not `infochat.embeddings.timeout-ms`. The threat model is therefore diverged on the cost surface and gating of the pre-fetch it itself describes: a reader of §Failure handling would believe an LLM-unreachable turn costs at most one embed + one pgvector probe with a bucket token, when a non-English scope's turn additionally fires one unbucketed generative call per turn (plus one per DISTINCT model-elected semanticSearch query, per the new §Rate limiting text).
    REPRO: Multi-provider config (chat on a remote provider that is failing but has not tripped the chat breaker; translator on a healthy local backend). A non-English-scope user sends chat turns; each admitted turn (InboundRouter.java:1142 bucket gate) executes the pre-fetch translator call at QueryAnchorTranslator.java:192-194 before the doomed chat call fails into the friendly "chat assistant is unavailable" reply (ChatAgent.java:337-338). The spend is still bounded per turn, so this is not an unbounded-cost hole — but the spec paragraph that operators and future auditors rely on to bound the pre-fetch now understates its cost surface and mis-states its gating, and the diff's own "not silently diverged" claim is only partially delivered.
    SUGGESTED-FIX-CLASS: other (spec-consistency: amend the §Failure handling "Chat-mode replies" paragraph to name the translator sub-call, its breaker/timeout controls, and the no-bucket-token gating).

  - CATEGORY: DOS
    SEVERITY: low
    PROMISE: "it is the R1 memory bound that keeps the cache from amplifying a hostile endpoint's up-to-8-MiB response into tens of gigabytes of retained heap (the transport cap's memory-protection purpose survives retention)" (QueryAnchorTranslator.java:77-80); "let the cache retain an arbitrarily large body (a hostile endpoint can return up to the 8 MiB transport cap) and amplify it 10,000 ways into the heap" (QueryAnchorTranslator.java:221-224); ticket R1: "the cache cannot amplify a hostile endpoint's up-to-8-MiB response into tens of gigabytes of retained heap".
    GAP: The retained-value cap is `translated.length() > inputMaxLength` (QueryAnchorTranslator.java:226), where `inputMaxLength` is the operator-configurable `infochat.chat.tool.input-max-length` (QueryAnchorTranslator.java:123-124, default 500). The retention bound therefore scales linearly with the operator knob: at the default the cache (QueryTranslationCache.java:56-59, maximumSize 10_000, expireAfterWrite 24h) retains ~10 MB, but a deployment raising the cap toward the 1-8 MiB transport ceiling (security.md §Trust boundaries item 9) lets a hostile translator endpoint fill 10,000 entries of up-to-cap values — at 8 MiB, ~78 GiB of retained heap plus equally-sized plaintext keys (QueryTranslationCache.java:54, 97-100), resurrecting the exact amplification R1 claims to have closed. "The transport cap's memory-protection purpose survives retention" holds only at default config.
    REPRO: Operator sets infochat.chat.tool.input-max-length=8000000. An attacker in one non-English scope sends 10,000 DISTINCT queries over time (per-turn rate caps bound the rate, but the cache retains across turns for 24h, so the fill is a slow drip); the hostile translator endpoint returns an 8-MiB string per call, each length <= the cap, so each is cached (QueryAnchorTranslator.java:226-233). ~78 GiB retained heap for 24h — the R1-fixed amplification returns at raised config.
    SUGGESTED-FIX-CLASS: input-sanitization (decouple retention from the input cap with a hard ceiling: cache only translations <= min(inputMaxLength, fixed KiB ceiling)).

OUT-OF-MODEL:
  - Within-scope (group) translation-cache oracle: the R2 partition keys by (scope_kind, scope_id, source text, source language) (QueryTranslationCache.java:54, 97-100), so all members of a group share one partition: member B can time-probe (cache hit vs miss) whether member A searched identical text, and receives A's cached translation of that text. The R2 commitment ("no cross-scope cache state... hit/miss latency cannot be a cross-scope oracle for another user's query text") is met at the scope level; the finer cross-USER oracle inside an already-shared group scope (members already share the group's posts and /lang) sits outside the documented model. Extending the model to per-(user, scope) keys would multiply translator cost per group member.
  - Hard-coded temperature 0 on the shared ModelTask.TRANSLATOR key (OpenAiCompatibleProvider.java:239-241, AnthropicProvider.java:185-187) silently changes the ingest and presentation translation legs' sampling behavior (same task key per the design note "shares today") — a determinism improvement, not a security regression, but a cross-leg behavior coupling the query-leg wire tests do not scope-check, and which a future operator tuning another leg's sampling cannot override.

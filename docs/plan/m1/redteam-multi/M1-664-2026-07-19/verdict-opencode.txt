RED-TEAM VERDICT: CLEAN

Audit scope: M1-664 adds the seventh chat tool `helpLookup` — a read-only
pgvector cosine probe over the new Provider-owned `doc_embedding` corpus
(V60), returning `{command, description}` to the model context with the
tier filter bound INSIDE the SQL WHERE and the description composed at
call time from the runtime catalogue (match-not-assert). The diff also
adds the corpus builder (`CommandIntentIndexBuilder`), the JDBC DAO
(`DocEmbeddingDao`), the `CommandIntentIndex` constants/record, widens
four `HelpCommandHandler` API members from package-private to public,
adds a new `resolveCallerTier(userId, scopeKind, scopeId)` resolver, and
lands the matching spec rows (`security.md` tool-allowlist table,
`commands.md` "Command-intent retrieval is match-not-assert", `llm.md`
"Second embedded corpus", decision D66).

Each threat-model commitment on the new tool was traced to its delivery
in the diff and verified:

- Tier-filter-before-return (security.md `helpLookup` row, M1-647
  widened): `HelpLookupTool.execute` computes `visibleTargets` from
  `helpHandler.visible(entry, caller)` BEFORE any SQL, then binds it
  via `target_ref = ANY(?)` INSIDE the WHERE (`HelpLookupTool.java:184`
  lookup SQL, lines 184-191). `resolveCallerTier` reads `is_admin` from
  the DB by user id and resolves group-admin via the same
  `groupMembershipRepository.isGroupAdmin` path `/help` bottoms-out on.
  Admin-only commands cannot surface to a non-admin caller even if their
  embedding is nearest — pinned by `adminOnlyCommandNeverSurfacesToNonAdmin`.

- Match-not-assert (security.md `helpLookup` row; D66): the SELECT
  returns only `target_ref`; `describe()` looks the command up in the
  runtime `CATALOGUE` and resolves the bundle key via `bundleLoader.get`
  — the row's `content_hash`/embedding text is never read into the
  description. Pinned by `toolOutputComesFromRuntimeCatalogueNotFromIndexedText`.

- Length cap (security.md `helpLookup` row "length-capped by the
  dispatcher's per-turn input cap"): `ChatToolDispatcher.validateValue`
  rejects any `String` arg whose length exceeds `inputMaxLength` (default
  500) before any SQL runs; `helpLookup`'s `query` arg is a top-level
  String in the args map, so it is covered by the same uniform check
  every other tool's string args are.

- Local embedding backend / D54 (security.md trust boundary 8): the
  query is embedded via the injected `EmbeddingProvider`, the same SPI
  `SemanticSearchTool` uses; the configured model is the same one
  `CommandIntentIndexBuilder` wrote the corpus with.

- Below-threshold no-match (security.md `helpLookup` row): the SQL
  filters `(embedding <=> ?::vector) < (1.0 - SIMILARITY_THRESHOLD)`
  and `LIMIT 1`; below the cutoff the tool returns `{"command":null}`
  and `ChatAgent.TOOL_INSTRUCTIONS` directs the model to say it does
  not know and point at `/help`. Pinned by `belowThresholdReturnsNoCommand`.

- `/stop` cancellation (commands.md `/stop` paragraph; security.md
  closed-allowlist): the pooled connection is armed via
  `cancellationService.armToolConnection` immediately after acquisition
  and before the pgvector probe (`HelpLookupTool.java:163-166`). The
  embed call's pre-arm placement matches the threat model's
  `pg_cancel_backend`-DB-query-only commitment and mirrors
  `SemanticSearchTool`; the embed HTTP call itself is bounded by
  `infochat.embeddings.timeout-ms` per the existing chat-degradation
  rule.

- D19 determinism (security.md `helpLookup` row; D66): the match is
  decided entirely by SQL (HNSW cosine distance + threshold + tier
  filter + ORDER BY distance ASC LIMIT 1). The LLM never picks the match.

- Tool surface boundary — "Never exposed (forever)" (security.md):
  `helpLookup` is a read-only SELECT against `doc_embedding`; it
  mutates nothing in `users`, `group_membership`, `is_admin`,
  `is_banned`, `audit_log`, `source`, or `source_subscription`. It
  runs no arbitrary SQL, sends no messages, fetches no URLs.

- Delivery-ordering contract (security.md "Delivery-ordering
  contract"): the matched command name and description enter the model
  context as tool output; whether they reach the user is the model's
  decision, so any reply text the model composes from them is
  LLM-authored and routed through the outbound sanitizer like any other
  chat-mode reply. The diff's new `noToolDerivedTextIsAppendedAfterSanitize`
  regression guard asserts (a) the sanitizer runs exactly once on the
  model's final reply, (b) tool-result bytes are not pre-pended
  pre-sanitize, and (c) tool-result bytes are not appended
  post-sanitize — pinning the M1-648 r2 regression class on this
  surface.

- Tool-allowlist parity (security.md "Verification (`verification.md`
  §Security`) asserts the registry's name set equals the table"):
  `ChatToolRegistry` adds `helpLookup` (now seven names); the
  marker-delimited table in `security.md` adds the `helpLookup` row
  inside the same markers; `ChatToolRegistryTest.registryContainsExactlySpecTools`
  lists seven names; `ChatAgentTest.everyRegisteredToolIsAdvertised`
  asserts every registry name appears in `ChatAgent.TOOL_INSTRUCTIONS`,
  which the diff extends with the `helpLookup` line.

- DB role grants (security.md §DB roles, D34 least-privilege): V60
  grants the provider role `SELECT, INSERT, DELETE` on `doc_embedding`
  and explicitly `REVOKE`s UPDATE — matching the existing Provider-owned
  pattern (`saved_post` V15: SELECT+INSERT+DELETE; `summary_cache` V23:
  SELECT+INSERT+DELETE). The runtime read path uses only SELECT; the
  INSERT/DELETE grants are exercised solely by `CommandIntentIndexBuilder`
  at startup. A SQL-injection foothold in the Provider cannot escalate
  these grants to UPDATE — the grant is the boundary.

Per-category adversarial review:

- AUTH-BYPASS: the dispatch identity `(userId, scopeKind, scopeId)`
  arrives validated from chat-turn intake (which itself runs after
  steps 1-9 of the authorization model). The tool adds no new intake
  path. No bypass.
- INFO-LEAK: tool output is `{command, description}` from the runtime
  catalogue (trusted operator config). Tier filter prevents invisible
  commands from entering the model context. No other-user data, no
  stack-trace leak, no exfiltration channel — the user's query text is
  embedded into a numeric vector before any SQL and never appears in
  the SQL text.
- INJECTION: every SQL statement uses `?` placeholders for all values
  (`ps.setString`, `ps.setArray`, `ps.setDouble`). The vector literal
  is composed via `Float.toString` of float array elements inside
  `[...]`, so its character set is `{[0-9.\-eE,]}` — no SQL metachar
  can appear. No command execution, no header injection, no log
  injection (the tool logs nothing; the user's query is not logged by
  the diff's new code).
- DOS: one embed call + one LIMIT-1 pgvector probe per tool call, both
  subject to per-turn tool-call cap (`TurnContext.callCap`) and the
  per-minute LLM rate bucket; the corpus is ~41 rows so the HNSW probe
  is O(log n); `statement_timeout` bounds the worst case.
- PERM-ESCAL: `resolveCallerTier` reads `is_admin` and `is_group_admin`
  from DB state, not from caller-supplied input; `visible()` semantics
  are unchanged by the private-to-public widening (diff comment
  explicit, body untouched). No escalation path.
- AUDIT-EVASION: read-only tool; the chat turn itself is audit-logged
  at the higher intent/step-8 layer; sanitizer matches (per-occurrence)
  remain audit-logged by existing commitment. The diff does not touch
  any audit-write path.

Notes on items reviewed and intentionally not flagged:

- `lookupIsAdminById` throws `IllegalStateException` with the userId in
  the message if no users row exists. userId is an internal UUID (not
  user-authored prose per §User content in exceptions; not a contact id
  requiring redaction). The path is defensive — the chat dispatch
  identity is upstream-resolved and always carries a live users row —
  and the dispatcher's chat-degradation posture handles a propagating
  IllegalStateException at the outer worker boundary. No threat-model
  commitment is broken by the message contents.

- The `doc_embedding` PRIMARY KEY is `doc_id` alone, not
  `(doc_kind, doc_id)`. This is a forward-compat concern for M1-649's
  USER_GUIDE-topics corpus (a second `doc_kind` whose doc_id values
  could collide), not a v1 security gap: v1 ships exactly one
  `doc_kind` value (`command_intent`) and the migration's doc comment
  states the v1-only shape explicitly. The threat model does not
  promise multi-corpus PK collision protection, so this is not raised
  as a finding.

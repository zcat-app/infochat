RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: INFO-LEAK
    SEVERITY: low
    PROMISE: security.md §Secrets handling → "User content in exceptions":
             "Exception messages and stack traces emitted via the
             application logger MUST NOT contain user-authored prose
             (chat-mode message bodies, post bodies, saved-post
             annotations, command arguments). The application provides a
             `SafeLog` utility that drops the exception message body,
             retains only the exception class name, and truncates the
             cause chain to class names (depth-capped at 5). The original
             `Throwable` is never passed to the underlying SLF4J logger."
    GAP: The new LLM call site bypasses SafeLog and hands the raw
         Throwable to the logger.
         infochat-provider/src/main/java/app/zcat/infochat/provider/digest/CategoryRollupGenerator.java:149-152
         (diff.patch lines 570-572): `catch (RuntimeException e) {
         LOG.warnf(e, "category roll-up LLM call failed; ...")`. The
         guarded call is `provider.generate(ModelTask.SUMMARIZER,
         ROLLUP_SYSTEM_PROMPT, userPrompt)` where `userPrompt` (built at
         CategoryRollupGenerator.java:167-183) interpolates full post
         titles, BODIES, and URLs for every cluster in the category —
         exactly the "post bodies" class the MUST enumerates. An LLM
         transport/parse exception can embed request or response
         fragments (HTTP-client exceptions that quote the response body;
         unparseable-reply exceptions that carry the raw model output
         derived from the attacker's post), so the original Throwable's
         message/cause chain is a conduit for that prose into the
         operator log stream, which D37 promises never carries post
         bodies at any log level. Severity is low, not medium: the
         feature is behind `infochat.digest.category-summary-enabled`
         (default false), the leak target is the operator-side log
         stream (API-key shapes in it are separately caught by the
         console redactor), exploitation needs a provider client whose
         exceptions embed body content, and the identical pattern
         already exists outside this diff (SummaryProseGenerator.java:105-106,
         136-138) — but the diff introduces a NEW instance of the
         surface SafeLog exists to close, so the structural guarantee is
         not delivered for this call site.
    REPRO: (1) Operator enables `infochat.digest.category-summary-enabled`.
           (2) Attacker who controls or can inject into a subscribed feed
           publishes a post whose body survives Stage 1/2 (ordinary prose
           does) and is crafted to make the roll-up request fail at the
           provider with a content-bearing exception — e.g. content that
           drives the model into schema-/format-violating output the
           provider client rejects with the raw reply quoted in the
           exception message, or that inflates the request past a
           provider limit returning a 4xx whose client exception echoes
           request context. (3) On the next digest slot for any group
           whose world includes the source, `generateRollup` catches the
           RuntimeException and logs the original Throwable; the
           attacker-derived post text lands verbatim in the production
           log stream that the threat model commits is free of post
           bodies at every log level.
    SUGGESTED-FIX-CLASS: other

OUT-OF-MODEL:
  - Empty-sequence counter increment on the new public chokepoint method:
    `OutboundDelivery.deliverSequenceToGroup` (OutboundDelivery.java:988-1013
    region of diff.patch) applies `onPermanentGroupFailure(channel, groupId)`
    whenever `anyDelivered` is false — including for an EMPTY `messages`
    list, which increments the per-group consecutive-permanent-failure
    counter with zero sends and zero failures; three such calls would
    silently soft-remove a healthy group, contradicting the D63/"always
    > 1" calibration the same diff pins in messaging.md. This is not an
    in-model finding because no adversary input reaches the argument and
    no current caller can produce an empty list (DigestWorker only enters
    the branch for a non-empty post set, and renderSections always yields
    at least the Other section), so it is an internal-caller trap rather
    than an attack path — flagged because M1-652's gap-filling redelivery
    is slated to add a new caller that FILTERS the section list before
    calling this method, at which point a fully-delivered-then-retried
    slot filtering down to zero sections would make the trap reachable in
    normal operation.

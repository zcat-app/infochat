RED-TEAM VERDICT: CLEAN

Audited M1-664 (the `helpLookup` chat tool, the `doc_embedding` corpus, and
the `CommandIntentIndexBuilder` startup pipeline) against every commitment
in `docs/spec/security.md`. The diff lands a new LLM-callable tool and its
backing corpus; the audit focuses on the LLM↔system-state trust boundary
(§Trust boundaries #5), the tool allowlist (§Prompt-injection defenses),
the LLM output sanitizer boundary, the match-not-assert + tier-filter
invariants (D66), the failure-degrades-quality posture (§Failure handling),
and the DB role grants (§DB roles).

Commitments verified as delivered by the diff:

- Closed tool allowlist, spec-level. `helpLookup` is added to the
  marker-delimited `<!-- tool-allowlist:begin -->`/`<!-- tool-allowlist:end -->`
  table in security.md; ChatToolRegistry carries the seven-tool set;
  ChatToolRegistryTest pins the registry's name set byte-for-byte against
  the spec table; ChatToolDispatcher wires `helpLookupTool` and
  `requireHandlerForEveryAdvertisedTool` refuses startup on registry/wiring
  drift; ChatAgent.TOOL_INSTRUCTIONS advertises the tool and the new
  everyRegisteredToolIsAdvertised test guards prompt-side drift. Spec-level
  closure is maintained in both directions.

- Read-only / no path to mutating authorization state. HelpLookupTool
  issues one SELECT against `doc_embedding`; no DB writes; no path to
  `users`, `group_membership`, `is_admin`, `is_banned`, `audit_log`,
  `source`, or `source_subscription`. The V60 migration grants the
  provider role SELECT + INSERT + DELETE on `doc_embedding` only, with
  UPDATE explicitly revoked (and revoked from PUBLIC), and grants the
  collector role nothing on the table — the narrow-grant posture the
  M1-648 r2 CLEAN audit carried forward. CommandIntentIndexBuilder is
  the sole writer (DELETE-then-INSERT upsert, never UPDATE — matches
  the grant).

- Length caps on free-form inputs. The spec commits `query: string` to
  be "length-capped by the dispatcher's per-turn input cap"; the
  dispatcher's `validateInputLengths` applies `inputMaxLength`
  (`infochat.chat.tool.input-max-length`, default 500) uniformly to every
  String arg on every tool, so helpLookup's `query` is bounded before
  any SQL runs. Type-checked: the tool requires `query` be a non-blank
  String; the dispatcher catches IllegalArgumentException as a typed
  ValidationError. The lookup SQL is fully parameterized (doc_kind,
  target_ref array, vectorLiteral, distance threshold) — no string
  concatenation of attacker-influenced bytes. The vectorLiteral is
  derived from a float[] via `Float.toString`-shaped formatting, so no
  SQL metacharacters can enter through it.

- Match-not-assert. HelpLookupTool.describe() resolves the matched
  command's one-line description at call time from the runtime
  HelpCommandHandler.CATALOGUE's bundleKey via BundleLoader.get — never
  from the indexed text, never from any value carried by the
  doc_embedding row. A stale or attacker-edited intent row can degrade a
  match but cannot produce wrong syntax. The
  toolOutputComesFromRuntimeCatalogueNotFromIndexedText IT mutates the
  indexed row's content_hash + embedding and asserts byte-identical
  description output before and after — pinning the invariant at the
  tool level.

- Tier-filter-before-return. The caller's visible command-name set is
  computed via the SAME `HelpCommandHandler.visible` predicate `/help`
  applies at listing time, resolved for the chat-tool dispatch identity
  via `resolveCallerTier(userId, scopeKind, scopeId)`; it is bound as
  `target_ref = ANY(?)` INSIDE the WHERE of the pgvector query, never
  applied as a post-filter. An invisible command's name cannot enter
  the model context via this path (the M1-647 existence-oracle defense
  widened to free-text input). The adminOnlyCommandNeverSurfacesToNonAdmin
  IT seeds `grant-admin` CLOSER to the query than the legitimate
  non-admin match, so only the WHERE-clause tier filter can exclude it;
  the test asserts both that `unfollow-source` is returned AND that the
  `grant-admin` byte sequence never appears in the result JSON.

- D19 determinism. The match is decided entirely by SQL (pgvector
  cosine distance + calibrated similarity threshold + tier filter +
  LIMIT 1); the LLM never picks the match.

- D54 local embedding backend. The query is embedded through the
  injected EmbeddingProvider (local backend); the same model key the
  startup builder used to write the corpus is read at runtime, so query
  and stored vectors live in the same vector space.

- Failure-degrades-quality. CommandIntentIndexBuilder.onStart catches
  RuntimeException from buildCorpus and logs ERROR — it does NOT rethrow
  to abort Provider startup. This is the correct posture under §Failure
  handling ("A complete LLM outage degrades quality, not safety"): an
  embedding-backend failure at boot leaves the corpus empty (cold start)
  or at its prior-boot state (warm restart), and the chat-time tool
  returns `{"command":null}` — the chat path's friendly-degradation
  behaviour. The embeddingBackendFailureAtStartupDoesNotAbort IT pins
  this; the prior rethrow-as-IllegalStateException posture would have
  converted a chat-tier convenience outage into a total Provider outage
  (every adapter, ban intake, admin auth, invite gate, digests), which
  the spec forbids. Chat-turn embed failure is similarly caught in
  HelpLookupTool.execute and degrades to noMatchJson rather than
  aborting the turn.

- /stop cancellation. HelpLookupTool arms the pooled connection via
  CancellationService.armToolConnection before the lookup runs, so an
  in-flight helpLookup call is interruptible by /stop — the same
  pg_cancel_backend primitive every other chat tool uses. The spec
  text in commands.md and 03-commands.md was updated to include
  helpLookup in the cancellation surface.

- LLM output sanitizer boundary. The tool's result JSON is intermediate
  model context, not user-facing bytes; the model's reply still goes
  through the outbound regex sanitizer. The M1-648 r2 regression class
  (post-sanitize append of tool-derived privileged command usage into
  the delivered reply) is structurally refused here: the new
  noToolDerivedTextIsAppendedAfterSanitize test in ChatAgentTest asserts
  that a unique sentinel carried by a tool-result description appears
  in neither the sanitizer's input nor the delivered reply.

- No INFO-LEAK / PERM-ESCAL / AUTH-BYPASS. The tool cannot escalate
  privileges (read-only), cannot leak data the caller cannot already
  see (tier filter inside WHERE + match-not-assert), and cannot reach
  any authenticated functionality without satisfying the same
  authorization checks the deterministic command path enforces (the
  tool runs after the intake authorization pipeline has resolved the
  user; the dispatcher hands it only `(userId, scopeKind, scopeId)`
  for a caller that already cleared steps 1–7).

- No DOS. Inbound cost is bounded by the dispatcher's inputMaxLength,
  the per-turn callCap (default 25), the per-user interruptible
  concurrency cap, and the per-user LLM rate bucket; the SQL is armed
  for /stop cancellation and runs under the profile-driven
  statement_timeout that bounds every read-only chat-tool query; the
  embed HTTP call is bounded by `infochat.embeddings.timeout-ms`; and
  the corpus is small (~41 rows), so the HNSW probe is O(1)-ish.

Residual observations considered and judged NOT findings:

- TOCTOU between `resolveCallerTier` and the lookup SQL: the visible
  set is computed before the embed HTTP round-trip; a caller demoted
  in that window could briefly see a command name they could see a
  moment ago. The spec makes no freshness commitment — the
  tier-filter-before-return commitment is about WHERE the filter runs
  (inside the SQL), not about staleness — and the LLM output sanitizer
  still strips admin command strings from the reply. Not exploitable
  as a privilege escalation.

- The `scopeId == groups.id` claim in resolveCallerTier's javadoc: if
  the claim were ever wrong, the worst case is `groupAdmin` returning
  false for an actual group admin (under-visibility, quality bug), not
  over-visibility. A bot admin's visibility does not depend on
  groupAdmin (the BOT_ADMIN and USER_OR_GROUP_ADMIN branches both
  short-circuit on caller.botAdmin()).

- Bundle short-help strings are operator-trusted (§Trust boundaries:
  "Operator-set config … is trusted"); if a bundle value ever
  contained an admin command string, the tier filter ensures only
  callers who can already see that command would receive the
  description in their model context, and the outbound sanitizer
  strips it from any LLM-authored reply regardless.

No gaps between the threat model's commitments and the diff's delivery
were identified. The verdict is CLEAN.

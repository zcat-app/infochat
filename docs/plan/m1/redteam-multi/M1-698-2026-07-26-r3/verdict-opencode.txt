    SEVERITY: medium
    PROMISE: "The 'structural' reach is the provider module, which the
      module DAG makes total today: only infochat-provider depends on
      infochat-messaging-adapter (enforcer rules block the edge in every
      other module), so the universe of possible senders is the provider
      main source the test scans." And: "A direct `adapter.send` from a
      seventh call site — the bypass that would make the break miss an
      outbound body — is therefore unlandable in CI, rather than
      invisible." (docs/spec/security.md, §"Sanitizer output never
      contains ](" → "The chokepoint's totality is mechanically guarded",
      added by this diff.)
    GAP: The guard's package scope is `app.zcat.infochat.provider..`
      only (OutboundChokepointArchTest.java:225 —
      `importPackages("app.zcat.infochat.provider..")`). Its totality
      rests on NO other module being able to compile a caller of
      MessagingAdapter.send/update/finalizeMessage. That property is
      enforced by maven-enforcer `bannedDependencies` rules in FOUR of
      the five sibling modules — infochat-collector/pom.xml:198,
      infochat-llm-adapter/pom.xml:140, infochat-ssrf/pom.xml:64, and
      infochat-messaging-adapter/pom.xml:126 (siblings ban) — but NOT in
      infochat-core: infochat-core/pom.xml declares NO maven-enforcer
      plugin and NO bannedDependencies rule (the parent
      pluginManagement entry at pom.xml:126-130 carries the version
      only, with no execution; the parent's own comment says the
      module-DAG ban is activated per-module). So for the core edge the
      spec's parenthetical "enforcer rules block the edge in every other
      module" is false: today only census (nobody happened to add the
      dependency) keeps core off infochat-messaging-adapter, which is
      precisely the convention-over-structure posture the ticket claims
      to eliminate. A caller compiled under
      `app.zcat.infochat.core..` is outside the test's import scope and
      invisible to it, with no enforcer rule to keep the dependency edge
      from opening.
    REPRO: (1) A future change adds `<dependency>infochat-messaging-adapter`
      to infochat-core/pom.xml. `mvn verify` does NOT fail at enforcer:
      unlike collector/llm-adapter/ssrf, infochat-core has no
      bannedDependencies rule excluding the artifact, so the DAG edge
      opens with no trip. (2) A class under
      `app.zcat.infochat.core..` (a package the ArchUnit test never
      imports) calls `adapter.send(new OutboundMessage(scope,
      "[evil](https://x)", now, id))` — a body carrying un-broken `](`
      adjacency, never passed through OutboundDelivery's
      neutralizeLinkSyntax / LlmOutputSanitizer.breakLinkAdjacency.
      (3) OutboundChokepointArchTest imports
      `app.zcat.infochat.provider..` only, so it never sees the caller;
      the assertion stays green. (4) The `](`-free OUTBOUND property —
      the spec's load-bearing guarantee — is silently violated: a
      label-hiding markdown link ships to the transport with no WARN
      and no `LLM_OUTPUT_SANITIZED` audit row, exactly the
      "seventh call site" bypass the guard exists to make unlandable.
      Reachability is bounded to a developer/insider action (adding a
      dependency + writing a send call), not an external adversary —
      which is what holds this at medium rather than high — but the
      guard's STATED purpose is to catch accidental seventh sites
      ("rather than invisible"), and on the core edge it does not.

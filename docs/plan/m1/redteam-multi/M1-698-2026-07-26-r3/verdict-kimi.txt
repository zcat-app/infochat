RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: INJECTION
    SEVERITY: medium
    PROMISE: docs/spec/security.md §"Sanitizer output never contains `](`" —
      "every outbound body — chat reply, progress placeholder/finalize,
      periodic digest, group announcement — has its `](` adjacency broken
      before it reaches the transport, regardless of how it was assembled",
      and the diff's own new spec paragraph (security.md:629-649):
      "only infochat-provider depends on infochat-messaging-adapter
      (enforcer rules block the edge in every other module), so the
      universe of possible senders is the provider main source the test
      scans."
    GAP: The "universe of possible senders is the provider main source"
      inference is false even under today's module DAG. The guard only
      flags a call whose bytecode target owner is assignable to
      MessagingAdapter (OutboundChokepointArchTest.collectViolator,
      diff.patch lines 305-313) and only scans packages
      `app.zcat.infochat.provider..` (diff.patch lines 223-225). A
      static helper added to the infochat-messaging-adapter module
      itself — e.g. `MessagingAdapters.sendWithRetry(adapter, msg)`
      whose body calls `adapter.send(msg)` — defeats both filters at
      once: the provider-side call site targets the helper class (not
      assignable to MessagingAdapter, so collectViolator returns early),
      and the helper's own `adapter.send` edge lives in module classes
      the importer never scans. Extracting send logic into a shared
      helper in the adapter module is a natural, accidental refactor
      shape — precisely the "accidental seventh call site" class the
      guard exists to catch (the javadoc itself frames reflection as the
      only deliberate-evasion hole, implying everything else is caught).
      The new spec text overclaims totality the test does not deliver.
    REPRO: (1) A contributor lands `public final class MessagingAdapters {
      public static void send(MessagingAdapter a, OutboundMessage m) {
      a.send(m); } }` in infochat-messaging-adapter. (2) A new outbound
      path in a provider main class calls
      `MessagingAdapters.send(adapter, assembledBody)` instead of routing
      through OutboundDelivery. (3) `mvn verify` is green: the provider
      call's owner is MessagingAdapters (isAssignableTo fails) and the
      helper's `a.send` bytecode is outside the imported packages. (4)
      assembledBody now reaches the transport without the `](` adjacency
      break; a feed publisher whose title ends with `]` joined against a
      display name or URL beginning with `(` delivers a working
      label-hiding markdown link to every subscriber — the exact residual
      M1-691 closed at the chokepoint — with no WARN and no audit row.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening
  - CATEGORY: INJECTION
    SEVERITY: low
    PROMISE: Same section — the OUTBOUND `](`-free property is promised
      for "every outbound body", and the diff's spec paragraph commits
      the guard to "MessagingAdapter.send, .update, or .finalizeMessage"
      as the mutating entry points whose bypass "would make the break
      miss an outbound body."
    GAP: GUARDED_METHODS is a hardcoded name set {send, update,
      finalizeMessage} (diff.patch lines 218-219) with no assertion that
      the set equals the actual mutating surface of the MessagingAdapter
      SPI. If the interface later grows a fourth delivery-mutating method
      (e.g. `delete`, `react`, `edit`), direct calls to it bypass both
      the chokepoint and the guard silently — the build stays green and
      the spec paragraph's enumeration quietly goes stale, the same
      drift failure the spec's own §"Match-set derivation" section
      closes for the sanitizer's command list via a CI byte-for-byte
      check. Nothing in the diff derives the guarded set from the
      interface the way the match-set is derived from the closed
      privileged-tier list.
    REPRO: (1) MessagingAdapter gains `void edit(String messageId,
      String newBody)`. (2) A provider main class calls
      `adapter.edit(id, attackerInfluencedBody)` directly. (3)
      OutboundChokepointArchTest passes — "edit" is not in
      GUARDED_METHODS — and the body reaches the transport with no `](`
      break, no WARN, no audit row, while security.md still claims the
      chokepoint's totality is "structural".
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

OUT-OF-MODEL:
  - Reflective invocation of MessagingAdapter.send/update/finalizeMessage
    (Method.invoke, MethodHandle, dynamic proxy) leaves no bytecode edge
    and is invisible to the guard. Explicitly accepted as residual risk
    in both the diff's spec paragraph (security.md:646-649) and the test
    javadoc — noted here only so the acceptance is a conscious one:
    unlike the helper-indirection finding above, this shape requires
    deliberate evasion, and the threat model's adversaries are external
    with the codebase trusted-reviewed.
  - Sibling-module senders if the module DAG ever changes (another module
    gaining a dependency edge on infochat-messaging-adapter): flagged in
    the test javadoc as requiring the guard's package scope to widen with
    the DAG; not a current gap given the claimed enforcer rules.

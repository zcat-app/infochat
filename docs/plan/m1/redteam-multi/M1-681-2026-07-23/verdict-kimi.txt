OUT-OF-MODEL:
  - Zombie-reader TOCTOU in SignalJsonRpcClient.latchTransportDeath
    (diff hunk at infochat-messaging-adapter/.../SignalJsonRpcClient.java,
    new method ~lines 864-929 of the file): the `readerSocket != socket`
    guard is evaluated once at latch entry, but the subsequent mutations
    (`closed = true`, the pending-drain, `dispatchExecutor.shutdownNow()`,
    and the `restartRequested` CAS + hungRestartHook fire) are not atomic
    with it. A reader thread that outlived disconnect()'s bounded join,
    passed the guard while the old socket was still published, and is then
    preempted before `closed = true` can resume after connect() has
    published the new socket and reset both latches (connect() resets
    `closed`/`restartRequested` deliberately, per the diff comment). It
    would then latch the NEW connection dead, drain its pending futures,
    shut down its fresh dispatcher, and fire a second subprocess restart
    for the same death — violating the "at most once per death" wording
    the diff adds to docs/spec/messaging.md. Outside the documented
    threat model: the adversary's reach in security.md is arbitrary text
    over the messaging protocols, while this socket is the Provider's
    loopback channel to a co-located signal-cli subprocess (operator
    infrastructure, same trust class as the SimpleX channel in §Trust
    boundaries 7); triggering it also requires a nanosecond-scale
    preemption spanning an entire reconnect, and the outcome self-heals
    on the fired restart's reconnect. If adopted as a reliability
    hardening, the fix class is to make guard + mutations atomic
    (synchronize the latch body, or CAS a per-connect generation token
    instead of comparing socket references).
  - AdapterReadinessCheck now folds MessagingAdapter.connected() into
    readiness (infochat-provider/.../AdapterReadinessCheck.java, the
    `transportConnected` term), but the SPI declares connected() with an
    interface default of `true` (per the ticket's own clarity-check note,
    MessagingAdapter :362-364). Both v1 production adapters report
    honestly — SimpleX via its pre-existing rebuild latch and Signal via
    this diff's delegation to SignalJsonRpcClient.isConnected()
    (`dispatchQueue != null && !closed`) — so the "no false green"
    property the messaging.md edit promises holds today. A future adapter
    that forgets to override connected() would silently report
    transport-up forever and reintroduce the false-green outage this
    change removes, with no compile-time or test signal. Outside the
    documented threat model (trust boundary 6 already accepts the health
    surface's topology disclosure, and no current adapter breaches the
    honesty commitment); flagged as an SPI-hardening candidate — drop the
    default-true or have readiness fail closed for adapters that do not
    override it.

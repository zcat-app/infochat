FINDINGS:
  - CATEGORY: INJECTION
    SEVERITY: low
    PROMISE: "It is now structural, like the closed-list match-set
              derivation below ... A direct `adapter.send` from a seventh
              call site — the bypass that would make the break miss an
              outbound body — is therefore unlandable in CI, rather than
              invisible." The thesis sentence frames this as a property
              of every outbound body: "The `](`-free OUTBOUND property
              above holds only because every outbound path routes through
              `OutboundDelivery`'s entry points ... It is now structural."
              (docs/spec/security.md:629-639, added by this diff.)
    GAP: The structural guard is scoped to a single Maven module. The
         test imports only `app.zcat.infochat.provider..`
         (OutboundChokepointArchTest.java:76), but `MessagingAdapter`
         itself lives in a sibling module, package
         `app.zcat.infochat.messaging`
         (infochat-messaging-adapter/src/main/java/app/zcat/infochat/messaging/MessagingAdapter.java:1,51),
         and no other module is imported. A `MessagingAdapter.send` /
         `.update` / `.finalizeMessage` call site added to any sibling
         module's main source (infochat-messaging-adapter, infochat-core,
         infochat-collector, or a future module) is never imported, so
         the violator loop at OutboundChokepointArchTest.java:108-126
         never evaluates it and the build stays green. The false-green
         count guard is itself coupled to the single-module scope:
         `countProductionClassFiles()`
         (OutboundChokepointArchTest.java:143-157) walks only the
         provider module's `target/classes`, so the guard cannot be
         widened to sibling modules without rework — the narrow scope is
         structural to the test, not an oversight. The spec's
         "structural" / "unlandable in CI" claim is therefore broader
         than what the test enforces. (Today all production senders DO
         live in the provider module — only OutboundDelivery and
         DigestDelivery.RecordingAdapter call the guarded methods on a
         MessagingAdapter receiver, and both are allowlisted — so the
         invariant holds at HEAD; the gap is the unqualified commitment
         vs. the module-scoped delivery.)
    REPRO: A future feature adds an outbound-sending class outside
           `app.zcat.infochat.provider..` — e.g. an adapter-side
           proactive-notification helper in infochat-messaging-adapter,
           or a shared outbound helper in infochat-core — that holds a
           `MessagingAdapter` reference and calls
           `adapter.send(new OutboundMessage(scope, title + "](" + url, ...))`
           with an assembled body (exactly the feed-title-plus-URL join
           §"Sanitizer output never contains ](" says the chokepoint
           exists to neutralize). `mvn verify` then: the test imports
           `app.zcat.infochat.provider..` only, so the new class is
           never imported; the violator loop never sees it; the count
           check walks only the provider's `target/classes`; the build
           is GREEN. The body skips
           `OutboundDelivery.neutralizeLinkSyntax` (the only `](`-break
           site, OutboundDelivery.java:142,153,189,219,232), so a
           `](`-bearing body reaches the transport — the precise bypass
           the spec calls "unlandable in CI". A chat client then renders
           the label-hiding markdown link the `](`-free guarantee exists
           to prevent. No in-model adversary (feed publisher, chat user,
           hostile LLM endpoint) can land this today; it is a
           future-developer-accident surface, which is the exact
           accident class the "convention → structural" upgrade exists
           to make impossible — and on sibling modules it remains
           convention, not structure.

OUT-OF-MODEL:
  - Reflective invocation (`Method.invoke` / `MethodHandle` / dynamic
    proxy) of `MessagingAdapter.send`/`update`/`finalizeMessage` leaves
    no bytecode call edge to `MessagingAdapter`, so the guard cannot see
    it. The test's own Javadoc ("Detection model — what this guard does
    and does not catch") explicitly accepts this as an out-of-model
    residual on the basis that the codebase is trusted-reviewed and the
    threat model's adversaries are external. Flagged here so the
    residual is visible: a malicious or compromised contributor is
    outside the documented threat model, so reflection-bypass is not a
    FINDING — but the spec's unqualified "structural" / "unlandable in
    CI" wording does not extend to it, and a reader could over-read the
    claim's reach.

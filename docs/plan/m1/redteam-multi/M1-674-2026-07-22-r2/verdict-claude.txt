RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: DOS
    SEVERITY: medium
    PROMISE: docs/spec/messaging.md:341-357 (added by this diff): "**A
              peer-initiated connection close is a transport-death event.**
              When the peer closes (or a transport error kills) the connection
              an adapter depends on — the SimpleX bot WebSocket, the Signal
              JSON-RPC channel — the adapter MUST latch that connection as
              dead and drive recovery of the transport ... The outage stays
              operator-visible for as long as it lasts (`connected()` /
              `adapter.connection.status` report the dead transport — no false
              green)". This also backs docs/spec/security.md §Trust boundaries
              item 6, whose health surface is supposed to disclose "which
              messaging adapters are enabled and up".
    GAP: The commitment is written for BOTH v1 production adapters, but the
         diff ships SimpleX code only. On the Signal side nothing latches a
         dead JSON-RPC channel:
         - infochat-messaging-adapter/.../signal/SignalJsonRpcClient.java:783
           and :812-814 — the reader loop exits silently on EOF
           (`while ((c = r.read()) != -1)`) or on IOException (caught, logged
           at DEBUG, `return`). No flag is set, no drain of `pending`, no
           notifier, no hook.
         - SignalJsonRpcClient.java:942-944 — `isConnected()` returns
           `dispatchQueue != null`, and `dispatchQueue` is nulled ONLY by
           `disconnect()` (:413-420). A dead reader thread leaves it non-null.
         - SignalAdapter.java:404-409 — `connected()` = subprocess RUNNING &&
           `client.isConnected()`. Daemon alive + socket dead therefore reads
           TRUE: `adapter.connection.status` stays 1 — the exact "false green"
           the new bullet forbids.
         - Recovery: the only escalation is `recordTimeout()`
           (SignalJsonRpcClient.java:717-728), reachable solely from a
           response TIMEOUT in `call()` (:669-673). A write on a closed socket
           throws IOException at :661-665 and returns TRANSIENT WITHOUT
           touching the counter, so the hung-restart hook may never fire at
           all; and with no outbound traffic it can never fire, leaving the
           adapter permanently deaf. The class javadoc concedes this at :138
           ("The request timeout is the only liveness [check]").
         The SimpleX arm of the same bullet IS delivered
         (SimpleXWebSocketClient.java:547-555, SimpleXAdapter.java:544-663);
         the Signal arm is asserted in spec and absent in code.
    REPRO: 1. Operator runs the Provider with the Signal adapter enabled.
           2. signal-cli (still RUNNING under its supervisor) drops the
              JSON-RPC TCP connection — an idle/socket reset, a daemon-side
              listener recycle, or any IOException on the socket.
           3. `readerLoop` returns; the reader thread dies. No inbound
              notification is ever demultiplexed again: every user message,
              including a bot admin's `/ban` or `/revoke-admin`, is silently
              lost. Intake steps 1–9 of security.md §Authorization model never
              run because nothing reaches them.
           4. The operator polls the health/metrics surface (trust boundary 6):
              `adapter.connection.status{adapter="signal"} == 1`,
              `connected() == true`. The outage is invisible.
           5. If the Provider has no outbound traffic for that adapter, or its
              sends fail at the write with IOException, `recordTimeout()` is
              never reached and the daemon is never restarted — the deaf state
              is permanent until a human notices users stopped getting replies.
           The system should not have allowed a spec-level MUST ("latch as
           dead", "no false green") to be recorded for an adapter that has no
           implementation of it.
    SUGGESTED-FIX-CLASS: other

  - CATEGORY: DOS
    SEVERITY: low
    PROMISE: docs/spec/messaging.md:355-357 (added by this diff): "sends
              attempted before recovery completes classify transient — unless
              the supervising component has terminally failed, which
              classifies permanent per the default above." The diff's own
              inline rationale restates the stake: "Once the supervisor has
              terminally FAILED nothing will ever rebuild the transport, and
              TRANSIENT would loop Provider's retry forever"
              (SimpleXAdapter.java:1155-1158).
    GAP: The new terminal-failure arm is placed BEHIND the pre-existing
         `reconnecting` branch and is shadowed by it.
         SimpleXAdapter.java:1142-1145 returns TRANSIENT whenever
         `reconnecting` is set, before the new
         `ws.isClosed() && supervisorTerminallyFailed() -> PERMANENT` arm at
         :1159-1167 is ever evaluated. And `reconnecting` is deliberately
         PARKED true forever by the exit arm on a failed rebuild
         (SimpleXAdapter.java:483-488: "`reconnecting` stays set: the outage
         continues ... until the next restart notification (or the
         supervisor's FAILED transition)") — but nothing clears it on the
         FAILED transition: `SimpleXSubprocess.runSupervisor` returns after
         `failToAdmin` (SimpleXSubprocess.java:305-323), so no further
         `onRestart` fires, and the new peer-close campaign only spawns on a
         FRESH transport-death notification, which cannot occur because the
         only client is already latched dead.
    REPRO: 1. simplex-chat crashes; the supervisor respawns it and fires
              `onRestart`; `reconnect()` sets `reconnecting = true`
              (SimpleXAdapter.java:456) and its rebuild fails
              (ready-probe timeout / handshake failure) — the flag stays set.
           2. The daemon keeps crash-looping until the crash cap is exhausted;
              the supervisor latches `State.FAILED` and admin-notifies.
           3. Every subsequent Provider send now hits :1142 and receives
              TRANSIENT "SimpleX transport is reconnecting after a subprocess
              restart" — forever — instead of the PERMANENT the spec sentence
              this diff added promises for a terminally-failed supervisor.
           4. Outbound work (digests, replies, retries) keeps burning the
              retry ladder against a transport that can never come back; no
              caller ever learns the failure is permanent.
    SUGGESTED-FIX-CLASS: other

  - CATEGORY: DOS
    SEVERITY: low
    PROMISE: docs/spec/messaging.md:341-348 (added by this diff): "the adapter
              MUST latch that connection as dead and **drive recovery of the
              transport**, paced per the design-tier reconnect cadence ...
              not merely drain the in-flight command futures on the dead
              connection."
    GAP: The two recovery arms share one single-flight latch, and only ONE of
         them was hardened against losing its wakeup. The new campaign waits
         for the flag rather than returning (SimpleXAdapter.java:545-557, with
         the javadoc at :529-542 explaining precisely why a notification must
         never be dropped), but the process-exit arm still drops its
         notification on contention: `reconnect()` at
         SimpleXAdapter.java:439-441 does `if (!reconnectInFlight
         .compareAndSet(false, true)) { return; }`. The campaign is supposed
         to cover the dropped restart ("the campaign's next paced attempt
         picks the respawned child up"), but the campaign ABANDONS whenever it
         observes a non-RUNNING subprocess (:589-597) and only releases the
         flag afterwards in its `finally` (:655-662). The decision to abandon
         and the flag release are not atomic with respect to an incoming
         restart notification, so both arms can drop the same event.
    REPRO: 1. simplex-chat crashes. The WS terminal event latches the client
              dead and spawns the recovery campaign, which takes
              `reconnectInFlight` and sleeps a ladder rung.
           2. The campaign wakes and reads `sub.state()` == RESTARTING
              (:591-592) and commits to `return`.
           3. In the window between that read and the `finally` at :655-662
              (widened by any carrier-thread preemption / GC pause), the
              supervisor sets RUNNING (SimpleXSubprocess.java:302) and fires
              `notifyRestartListener()` (:304); the spawned `reconnect()`
              CAS-fails against the not-yet-released flag and returns at
              SimpleXAdapter.java:440.
           4. End state: subprocess RUNNING, `webSocket` latched dead,
              `reconnecting` false, `reconnectInFlight` false, and NO thread
              rebuilding — the exact MSG-1 shape the diff exists to close.
              Every send returns TRANSIENT "recovery pending"
              (:1165-1166) although no recovery is pending; the adapter stays
              deaf until the next unrelated daemon crash.
    SUGGESTED-FIX-CLASS: other

OUT-OF-MODEL:
  - Loopback WS-port hijack on rebuild. Neither `start()` nor the new
    peer-close campaign verifies that the listener answering
    127.0.0.1:<ws-port> is the supervised child: `waitForWebSocketReady`
    (SimpleXAdapter.java:1206-1231) is a bare TCP dial and `rebuildWebSocket`
    (:386-406) connects to whatever answers. A local process that wins the
    port while the child's socket is down could feed the adapter fabricated
    inbound frames (spoofed `contactId` → identity assertion at security.md
    §Trust boundaries item 1) and read outbound. security.md boundary 7 treats
    the loopback channel as trusted and unauthenticated by design ("the bot's
    identity lives in the subprocess data-dir, not in a presented
    credential"), so a same-host unprivileged attacker is outside the
    documented model — flagged in case the model should be extended.
  - Test-seam visibility widening: `SimpleXWebSocketClient.Listener` went from
    `private` to package-private (SimpleXWebSocketClient.java:470) and
    `onTransportDeath` is a package-private last-registration-wins setter
    (:462-464). Only reachable from inside the adapter package, so not
    attacker-reachable under this threat model, but it does move two
    lifecycle-critical entry points out of the class's own trust boundary.
  - Spec drift, not an attack: messaging.md:396-403 still asserts "SimpleX
    classifies a send on a closed or not-yet-started WebSocket as an IMMEDIATE
    PERMANENT", which the new `requireConnected` peer-close arm
    (SimpleXAdapter.java:1159-1167) changes to TRANSIENT. The direction is
    safer for the per-group permanent-failure counter (fewer false
    soft-removals), so no finding — noted only because that paragraph's stated
    calibration basis is now stale.

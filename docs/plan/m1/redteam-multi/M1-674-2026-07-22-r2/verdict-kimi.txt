OUT-OF-MODEL:
  - Daemon-supplied WebSocket close reason embedded verbatim in exception
    messages. SimpleXWebSocketClient.Listener.onClose builds
    "WebSocket closed by peer: " + statusCode + " " + reason (diff.patch
    hunk at SimpleXWebSocketClient.java:510-516) and routes it through
    latchTransportDeath as the drain cause for pending send futures, so
    peer-written bytes propagate toward the Provider send path inside a
    MessagingException message. Within the documented model this is safe:
    the "peer" of this socket is the co-located simplex-chat subprocess
    (security.md §Trust boundaries 7 — trusted only while loopback-bound),
    not a remote SimpleX contact, and security.md §User content in
    exceptions covers user-authored prose, which a daemon close-reason is
    not. If the operator voids boundary 7 (binds the ws-port off-loopback)
    or the daemon is compromised, this becomes a log-injection channel
    (control bytes in a ≤123-byte UTF-8 reason string) into whatever logs
    full exception messages. Flagging so the user can decide whether
    boundary-7-voided deployments warrant sanitizing the reason at intake.
  - Recovery-flag waiters accumulate without an explicit bound under a
    flapping daemon. Every transport-death notification spawns a virtual
    thread that parks in the reconnectInFlight CAS-wait loop, ticking one
    CAS per RECOVERY_FLAG_POLL (50 ms) until the flag frees
    (SimpleXAdapter.java recoverFromTransportDeath, diff.patch hunk at
    lines 166-179). The notifier fires at most once per client and the
    ladder paces fresh clients (hence fresh deaths) to at most one per
    rung, so growth is slow and waiters drain via the stale-notification
    exit once any campaign ends — but a daemon that kills every rebuilt
    WebSocket while the holding campaign never succeeds parks one extra
    virtual thread per death indefinitely. Reaching this requires a
    misbehaving co-located simplex-chat process, i.e. trusted operator
    infrastructure per security.md §Trust boundaries 7 ("Operator-set
    config is trusted"; the subprocess is operator-run), so it is outside
    the documented model; noted as a hardening candidate (e.g. coalescing
    waiters into a single queued notification).
  - Ownership-split race between the WS-death campaign and the
    process-exit arm can leave recovery unowned. recoverFromTransportDeath
    exits whenever subprocess.state() != RUNNING, and its javadoc states a
    restart notification landing mid-campaign "no-ops" because the
    campaign holds reconnectInFlight (diff.patch SimpleXAdapter.java
    hunk at lines 137-149, 213-218). If the supervised respawn completes
    after the campaign's state check has already returned, the diff shows
    no third party that rebuilds the transport — the design relies on the
    exit arm's notification semantics, which live in onSubprocessRestart /
    SimpleXSubprocess and are not in this diff. This is an availability
    (lost-recovery) concern, not adversary-reachable — the trigger is
    daemon crash timing, not inbound content — so it falls outside the
    security.md threat model's DOS commitments (bounding adversary-driven
    cost). Flagged for reliability review rather than as a security
    finding.

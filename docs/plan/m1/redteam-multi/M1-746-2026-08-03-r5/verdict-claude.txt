    PROMISE: security.md §Prompt-injection defenses, `semanticSearch` tool row (amended by this diff): "Query anchoring (M1-746, D58): when the scope declares a non-English `/lang`, the query text is first translated to the corpus anchor language (English, D29) by a generative `ModelTask.TRANSLATOR` call (decoded greedily — temperature 0 on the wire; language-only prompt; result cached per (scope, query, language); accepted translation capped at the tool's input length)". And the standing D21 commitment the class claims to implement: "Every prompt that includes user-derived text is wrapped in a delimiter block whose marker contains a per-call random value."
    GAP: The user's query text is NEVER sent to the translator. QueryAnchorTranslator.java:211-218 builds the prompt as `PROMPT_TEMPLATE.replace("{{SOURCE_LANGUAGE}}", ...).replace("{{id}}", ...)` and calls `provider.generate(ModelTask.TRANSLATOR, "", prompt)` — the `query` parameter is used only for the `en` short-circuit (line 172), the cache key (line 194), and the fallback returns; it appears nowhere in the prompt. PROMPT_TEMPLATE (QueryAnchorTranslator.java:110-123) contains no `{{QUERY}}` placeholder and no wrapped content block — the `<<<UNTRUSTED_CONTENT id>>> ... <<<END id>>>` text in it is instruction prose describing a wrapper that is never constructed (compare every other prompt site, which builds real open/close markers around the payload: ChatAgent.java:711-713, SummaryProseGenerator.java:171-172, CategoryRollupGenerator.java:296-297 all use `UNTRUSTED_CONTENT_OPEN_FORMAT`/`CLOSE_FORMAT`; this class has no equivalent). Consequences: (1) for every non-English scope — `cs` is enabled today per the diff's own §Rate limiting amendment — the model receives an instruction referencing an empty wrapper and its reply, an endpoint-chosen value under Trust boundary 9 with zero anchoring to any user input, is used verbatim as the search text for BOTH retrieval arms and for the D28 per-turn pre-fetch that grounds every chat reply; (2) the failure is silent — a typical reply ("Please provide the query to translate", or a hallucinated phrase) is non-blank and under the 500-char cap, so none of the fallback legs (blank at :237, over-cap at :251, exception at :220) fires, and the hallucination is then CACHED under (scope, SHA-256(real query), lang) at :264-265, making the wrong result deterministic and durable for 24h; (3) the per-call random delimiter id (:216, the D21 anti-forgery device) guards an empty block, and if the missing query is later patched in naively there is no wrapper mechanism in this class to receive it. The test suite cannot see this: QueryAnchorTranslatorTest asserts the prompt contains instruction substrings ("Change ONLY the language", "UNTRUSTED_CONTENT" — languageOnlyPromptPinsNoExpansionAndOutputIsUsedVerbatim) and the declared language ("from cs to English"), but no test anywhere asserts the query text itself is present in the prompt the provider receives, and SemanticSearchToolHybridIT's CannedTranslationProvider returns its canned string regardless of prompt content — so the promised control's central data flow (query in, translation of THAT query out) is unpinned end to end.
    REPRO: (1) Operator runs the shipped config with a real translator model; user in a `cs`-declared scope (a supported, normal-operation state — the diff itself asserts "cs is enabled today ... the standing posture for the current user base") sends a chat message or the model elects `semanticSearch` with query "kvantový router exploit". (2) SemanticSearchTool.execute (SemanticSearchTool.java:889-890 in the diff) calls translate(); the TRANSLATOR endpoint receives ONLY the instruction text — no query. (3) The model replies with whatever a query-less translation instruction elicits; that string is embedded and handed to `plainto_tsquery`, the result set is retrieved from posts matching model-invented text, re-injected into the chat prompt as grounding, and the reply carries the "grounded-with-count" provenance notice — the user's actual question never influenced retrieval. (4) The invented string is cached per (scope, query-hash, lang), so every repeat of the same query deterministically reproduces the wrong grounding. Additionally, under Trust boundary 9 a hostile or compromised translator endpoint now chooses the ENTIRE search text (not a translation of user input, which the spec's wording promises), within the length cap — the spec's "the query text is first translated" anchoring property, which is what bounds an endpoint's influence to a rendering of the user's own words, is absent. The system shouldn't have allowed any of this because the threat model this same diff amends promises the query text is what gets translated, inside the D21 wrapper, with the output anchored to it.

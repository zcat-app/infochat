RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: INJECTION
    SEVERITY: high
    PROMISE: >-
      The amended `semanticSearch` tool row (docs/spec/security.md, §Prompt-
      injection defenses, tool-allowlist) commits that "when the scope
      declares a non-English `/lang`, the query text is first translated to
      the corpus anchor language (English, D29) by a generative
      `ModelTask.TRANSLATOR` call (decoded greedily — temperature 0 on the
      wire; language-only prompt; result cached per (scope, query,
      language))", and that the query rides "inside the spec's
      `<<<UNTRUSTED_CONTENT>>>` delimiter with a per-call id" so the model
      treats it as data (D58 (d) LANGUAGE-ONLY: "the pipeline uses the
      provider's output VERBATIM"). The same row's D19 promise — the fused
      candidate set is "decided entirely by SQL ... reproducible on unchanged
      DB state and never chosen by the LLM" — is carried into the amended
      text. The promise is that the model translates THE USER'S QUERY, and
      that the anchored string is a function of that query.
    GAP: >-
      The user's query is never inserted into the translator prompt.
      QueryAnchorTranslator.PROMPT_TEMPLATE
      (infochat-provider/src/main/java/app/zcat/infochat/provider/chat/tool/
      QueryAnchorTranslator.java:110-123) carries a LITERAL `...` between the
      `<<<UNTRUSTED_CONTENT id="{{id}}">>>` and `<<<END id="{{id}}">>>`
      markers, and translate() (same file, lines 211-218) interpolates only
      `{{SOURCE_LANGUAGE}}` and `{{id}}` before calling
      provider.generate(ModelTask.TRANSLATOR, "", prompt); the `query`
      parameter appears nowhere in the prompt assembly (its only uses are the
      cache get/put and the fallback returns at lines 194-207, 226-228,
      237-240, 251-255). The model therefore receives an instruction-only
      prompt containing NO user text. Whatever it answers — a non-blank echo
      of the instruction, hallucinated text, or, per trust boundary 9 (a
      hostile or compromised endpoint is explicitly in scope), an
      attacker-chosen string — is accepted verbatim (lines 237-256, 271) and
      becomes the anchoredQuery that BOTH arms consume
      (infochat-provider/src/main/java/app/zcat/infochat/provider/chat/tool/
      SemanticSearchTool.java:126-138: embedded at line 132, bound into
      plainto_tsquery('english', ?) at lines 273 and 278). The user's real
      query is silently discarded for every non-English scope; the retrieval
      key is a pure function of the translator endpoint's arbitrary output,
      so the "never chosen by the LLM (D19)" property the spec row asserts is
      false for every non-English search. No test catches it: every test
      drives the translator through a canned/stub provider
      (QueryAnchorTranslatorTest.java:1118-1124, SemanticSearchToolHybridIT
      .java:1498-1508) and asserts prompt SHAPE ("from cs to English",
      "UNTRUSTED_CONTENT", "do not expand") — none asserts that the query
      text is present in the prompt, so a prompt that omits the query
      entirely is green across the whole suite.
    REPRO: >-
      A scope declares /lang cs (security.md §Rate limiting states "cs is
      enabled today", so the leg is live for the current user base). The user
      sends "kvantový router exploit". The D28 pre-fetch (or a model-elected
      semanticSearch call) invokes QueryAnchorTranslator.translate(), which
      builds the query-less prompt ("Translate the search query inside the
      <<<UNTRUSTED_CONTENT id=...>>> ... <<<END id=...>>> wrapper from cs to
      English ..."). The translator model — local llama.cpp/Ollama under the
      shipped defaults, but any endpoint-chosen output is in scope per trust
      boundary 9 — returns any non-blank string (an echo of the instruction,
      hallucinated prose, or, for a hostile/compromised endpoint, an
      attacker-chosen string <= input-max-length). That string is embedded
      and matched against post.search_tsv; the user's query never reaches
      either arm. The result set is keyed on the endpoint's arbitrary text,
      so a hostile endpoint controls the retrieval key for every non-English
      search in the deployment — steering which READY in-world posts are
      surfaced and (via the D28 pre-fetch re-injection of retrieved posts
      into the chat prompt) which content the chat LLM is grounded on — and
      the D58 (d) "language-only translation of the user's query" contract is
      not delivered at all: the ticket's headline behavior silently does the
      wrong thing for every non-English scope.

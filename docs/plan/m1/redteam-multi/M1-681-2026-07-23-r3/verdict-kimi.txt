RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - (DOS, local-scheduling, unsteerable) latchTransportDeath's restart gate
    is check-then-act: daemonGeneration.getAsLong() == conn.daemonGeneration,
    then the CAS, then hungRestartHook.run()
    (SignalJsonRpcClient.java, latchTransportDeath). A supervised respawn
    landing in the nanoseconds between the read and the hook would SIGKILL
    the healthy successor — the same shape as RT-M1-681-r2-1 but in a
    measure-zero window instead of the 15 s respawn-before-retire window.
    The diff comment argues the respawn's backoff (>= hundreds of ms) cannot
    slip into that gap; that is a probabilistic scheduling argument, not a
    happens-before guarantee. Not adversary-steerable (local thread
    scheduling on a loopback channel), self-limiting (one burned restart-
    budget unit), and the same class prior rounds of this ticket ruled
    out-of-model. Noted so the user can decide whether locking the spawn
    path against the fire path is worth a future hardening ticket.
  - (DOS, previously adjudicated residual) A daemon that is alive but
    wedged, holding the JSON-RPC socket open, with ZERO outbound traffic,
    remains undetectable: the reader stays parked in read() so the new
    latch never fires, and the consecutive-timeout escalation (the
    detector the amended messaging.md §Failure handling text assigns to
    this shape) only counts outbound timeouts that never occur. The
    readiness payload can then read green over a hung adapter. This is
    unchanged by the diff (the keepalive/ping bullet is explicitly
    out-of-scope in the ticket; r2 recorded it as "a residual the diff
    narrows rather than a regression"), so it is not a finding — restated
    only because the new spec text removes the old sentence that admitted
    the no-outbound-traffic hole, and a reader of the amended text alone
    could over-read the two-detector coverage.
  - (hardening, future-misuse hazard) The 7-arg SignalJsonRpcClient
    constructor defaults daemonGeneration to () -> 0L, which makes the
    RT-M1-681-r2-1 restart gate a silent no-op. Today's only production
    call site wires SignalSubprocess::generation (SignalAdapter.java), so
    the gate is live everywhere it matters; but nothing structurally
    prevents a future production wiring from pairing a real
    hungRestartHook with the 0-default supplier and silently reopening
    the fixed finding. Same pattern the project already filed as M1-682
    for MessagingAdapter.connected(); a contract test or constructor-shape
    guard is the analogous fix if the user wants it.

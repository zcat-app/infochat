FINDINGS:
  - CATEGORY: DOS
    SEVERITY: low
    PROMISE: The round-2 red-team disposition, quoted in this diff's own
              ticket record (M1-767-2026-08-04-r2.md), commits: "/retry
              --digest BINDS the pool (Option B), with a new pre-charge
              gate in RetryCommandHandler so a refused retry burns no
              token, no D47 draw and no cooldown." That commitment is
              restated in the round-3 mechanism this diff ships ("the
              fallback-boundary gate ... with RetryCommandHandler
              refunding the per-user token on that refusal — so a doomed
              re-run burns no personal budget and no cooldown").
              Underlying spec promise, docs/spec/security.md §Rate
              limiting ("Per-group LLM rate (D47)"): "a separate
              sub-bucket per approved group bounding LLM-triggering
              operations (chat replies + on-demand `/summary` + `/retry`
              re-rolls) across all group members." The sub-bucket bounds
              LLM-triggering operations; a zero-LLM refusal is not one.
    GAP: The D47 per-group LLM token is deterministically burned on a
          system-budget-refused re-run. In
          RetryCommandHandler.handleDigestRetry the group sub-bucket is
          drawn BEFORE the service is consulted —
          `rateCapBucket.tryAcquireGroupLlm(groupDbId)` at
          RetryCommandHandler.java:555, then
          `digestRetryService.retryDigest(groupDbId)` at :559. When the
          fallback boundary refuses (DigestRetryService.java:250-252,
          `if (!systemLlmBudget.canStartRender()) return
          RetryResult.SYSTEM_BUDGET_REFUSED;`), the new switch arm
          (RetryCommandHandler.java:573-586) refunds ONLY the per-user
          token (`llmRateCap.refund(actor.id)`, :582). There is no
          group-token refund: RateCapBucket exposes no refund for the
          group-LLM bucket (only `tryAcquireGroupLlm` at
          RateCapBucket.java:469 and `refundCheapCommand` for the cheap
          bucket), so the D47 token consumed at :555 stays consumed. The
          arm's own comment overstates the delivered guarantee — "so a
          system-exhausted re-run costs no personal budget"
          (RetryCommandHandler.java:577-579) is true of the per-user
          token only; the group's shared budget is spent. Two amplifiers
          live on the same new path: (a) the refusal never stamps the
          retry cooldown (gate at DigestRetryService.java:250 precedes
          the stamp at :263), so refusals are not self-throttling — the
          only rate limit on repeat refusals is the very D47 sub-bucket
          the refusals drain; (b) the same draw-before-gate ordering
          applies to the worker-gate leg: a re-run admitted by the
          fallback gate can still be degraded by the SECOND gate in
          DigestWorker.executeSlot (DigestWorker.java:231-232) when the
          window fills between the two checks — and that interval spans
          the cache-boundary read, post collection and group-metadata
          read (DigestWorker.java:200-205), not the "millisecond-scale"
          the ticket acceptance claims; that path returns SUCCESS, so the
          per-user token, the D47 token and the cooldown are all burned
          for a degraded (non-refused) re-run. The D47 burn is the
          deterministic leg of the same promise gap and is the one this
          finding stands on; the race is the documented-but-optimistically
          bounded leg.
    REPRO: 1) Unrelated groups' scheduled slots drive the PT24H
            deployment-wide window to the 3000 ceiling (nominal load
            reaches it at the ticket's own stated capacity of ~50
            full-mode groups at two slots/day; the documented
            admission-only overshoot reaches it sooner). 2) Group admin
            of group B issues `/retry --digest` for a slot with no
            persisted sections (a degraded slot persists
            renderedSections=null, so the retry takes fallbackRerun).
            3) The fallback gate refuses with SYSTEM_BUDGET_REFUSED: B's
            per-user LLM token is refunded, but B's D47 per-group token
            stays consumed and no cooldown is stamped. 4) The admin
            repeats — each refusal consumes another D47 token until B's
            sub-bucket is empty (attempts are bounded only by that
            bucket). 5) B's D47 sub-bucket — the budget bounding chat
            replies, `/summary` and `/retry` re-rolls across ALL group
            members — is now exhausted by zero-LLM refusals, so other
            members' LLM-triggering commands hit the fixed
            group.llm_rate_limit reply. The round-2 acceptance's "burns
            no D47 draw" is not delivered: a refused re-run consumes the
            group's shared LLM budget for an LLM call that never
            happened.
    SUGGESTED-FIX-CLASS: rate-limit

OUT-OF-MODEL:
  - The window is in-memory and per-JVM (`SystemLlmBudget.callTimestamps`),
    so a restart, redeploy or crash-loop resets a 24-hour control to zero,
    and a future multi-instance Provider would silently multiply the
    ceiling by the instance count. The spec already accepts in-memory
    state for the circuit breaker ("State is in-memory only — a restart
    resets to CLOSED") and process restarts are not an external-adversary
    lever here. Flagged for the spec owner, not filed.
  - The refusal path performs a `ThrottledAdminNotifier.notifyOnce` JDBC
    UPSERT on every refusal, and the distinct
    `error.retry.digest_system_budget` string is a cross-tenant load
    oracle (it tells a group admin the deployment-wide pool is exhausted).
    Both are bounded by the D47 per-group command sub-bucket and are
    admin-tier, metadata-only signals; accepted in round 3 as advisory,
    re-flagged here for the spec owner.

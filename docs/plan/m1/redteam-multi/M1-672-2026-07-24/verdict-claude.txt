RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: PERM-ESCAL
    SEVERITY: medium
    PROMISE: docs/spec/security.md:1512-1519 (§DB roles, Provider role — the
              bullet this diff itself writes): "`users.is_admin`,
              `users.is_banned` and its ban metadata,
              `users.registration_state`, `groups.approval_status` and
              `group_membership.is_group_admin` are not directly writable by
              the role, so a SQL-injection foothold in the Provider cannot
              mint a bot admin, unban itself, force a registration state,
              walk a group past the D47 approval gate, or grant group-admin.
              Every legitimate transition on those columns runs through a
              narrow, single-purpose `SECURITY DEFINER` routine the Provider
              holds `EXECUTE` on (V62)."
    GAP: Three of the four ungated "system-actor" routines are granted to
         infochat_provider and each re-opens, unconditionally, a transition
         the sentence above enumerates as closed:
         - V62__provider_identity_grants.sql:117-134 `bootstrap_ensure_admin
           (TEXT, TEXT)` — no actor gate AND no precondition of any kind. The
           `ON CONFLICT (adapter, contact_id) DO UPDATE SET is_admin = TRUE
           WHERE users.is_admin = FALSE` arm (V62:130-131) promotes ANY
           pre-existing users row to bot admin, at any time, in a deployment
           with any number of established admins. GRANT EXECUTE to
           infochat_provider at V62:534.
         - V62:217-235 `auto_promote_group_admin(UUID, UUID)` — no gate and
           no eligibility predicate; sets `is_group_admin = TRUE` for any
           (group, user). Every D47 constraint (registered, non-probation,
           non-banned, group currently has zero admins) lives only in Java
           (GroupAutoPromoteService.java:101-113). GRANT at V62:538.
         - V62:192-208 `insert_invited_user(TEXT, TEXT, TIMESTAMPTZ)` — no
           gate; mints a `users` row with `registration_state = 'invited'`
           and a caller-chosen `probation_until` (NULL ⇒ no probation at
           all). GRANT at V62:537.
         The fourth, `claim_simplex_admin` (V62:140-158), DOES carry a
         `WHERE NOT EXISTS (SELECT 1 FROM users WHERE adapter = p_adapter
         AND is_admin = TRUE)` precondition — proof that a narrowing guard
         was available and simply was not applied to the other three.
         The residual paragraph (security.md:1520-1533) does disclose that
         the four routines "carry no DB-side actor gate", but states the
         consequence only as "a foothold can still mint **the first** admin
         through that conduit", justified by "the bootstrap routine runs at
         every Provider start, before any admin need exist". That
         justification supports an *unauthenticated* routine; it does not
         support an *unconditional* one. The disclosure therefore understates
         the delivered surface on all three counts: (a) the bot-admin mint is
         any-time and any-contact, not first-admin-only; (b) group-admin
         grant is not mentioned at all in the residual, yet is named in the
         promise as prevented; (c) registration_state forcing is likewise
         named in the promise and absent from the residual.
    REPRO: Adversary holds a SQL-injection foothold in the Provider — the
           exact adversary V62's own header declares in-model
           (V62:1-15, "A SQL-injection foothold in the Provider could
           therefore mint a bot admin ... This migration applies the same
           treatment to the four identity tables"). After V62 the raw UPDATEs
           are indeed denied (42501), but the foothold instead issues:
           1. `SELECT bootstrap_ensure_admin('simplex', '<attacker's own
              contact id>');` → the attacker's own registered row flips to
              `is_admin = TRUE`. No `infochat.actor_id` needs to be set, no
              existing admin needs to be named, and no admin-count
              precondition applies. No BOOTSTRAP_ADMIN audit row is written
              either, because that INSERT lives in AdminBootstrap.java:246+,
              not in the routine. The attacker then drives /ban, /invite,
              /grant-admin, /audit, /approve-group from the normal messaging
              surface as a genuine bot admin.
           2. `SELECT auto_promote_group_admin('<any group id>', '<their user
              id>');` → group admin of any group whose slot is currently free,
              skipping every D47 eligibility rule.
           3. `SELECT insert_invited_user('signal', '<burner contact>',
              NULL);` → a registered, probation-free identity with no invite
              code ever presented, bypassing the D44 gate
              (security.md:993-1002, "An unknown DM contact's first message is
              checked against the invite table").
           The system should not have allowed these because the bullet the
           diff added claims precisely that these five transitions are
           unreachable for this adversary.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

  - CATEGORY: AUDIT-EVASION
    SEVERITY: low
    PROMISE: docs/spec/security.md:1517-1519: "Every legitimate transition on
              those columns runs through a narrow, single-purpose `SECURITY
              DEFINER` routine the Provider holds `EXECUTE` on (V62)."
              Paired with §Authorization model step 8 (security.md:812,
              "Audit-log the intent"), §Per-adapter admin threat profile
              (security.md:881-883, "the audit log records the bootstrap of
              the new admin contact"), and §Invite-code registration
              (security.md:999, "The invite-acceptance is audit-logged").
    GAP: V62:245-249 records the decision — "No routine writes an audit row.
         Every affected caller already pre-writes its row through
         AuditLogWriter + RedactionHook (Invariant 7)". V62 simultaneously
         makes those routines the ONLY write path to the privilege columns
         (V62:566-569 REVOKE INSERT, UPDATE on all four tables). The result:
         the newly-created chokepoint — the one place that now sees every
         privilege transition — is audit-free by construction, and the audit
         row remains entirely optional from the DB's point of view. Any
         holder of the EXECUTE grant (i.e. the entire Provider role) can flip
         is_admin (V62:294-311, 308-325), is_banned (V62:270-283), invite
         status (V62:427-443, 468-484), is_group_admin (V62:336-377) and
         approval_status (V62:488-503) with no row in audit_log. The
         admin-gated routines additionally take the audit-relevant actor as a
         *parameter* (`p_banned_by`, V62:253/270) that is never required to
         equal the GUC actor the gate checked, so a routine-level caller can
         also mis-attribute a ban. This is not a regression — before V62 a
         foothold's raw UPDATE was equally silent — but the bullet presents
         the routine funnel as the control, and the funnel was built without
         taking the audit property it uniquely enables.
    REPRO: Same foothold as Finding 1. `SELECT set_config('infochat.actor_id',
           '<any admin id, readable via the retained SELECT on users>', true);
           SELECT grant_bot_admin('<attacker user id>');` — the gate is
           satisfied (security.md:1526-1532 already concedes it "raises the
           bar ... without being a boundary"), the mutation commits, and
           audit_log gains nothing. An operator later reading /audit or
           `audit_log_view` sees a deployment whose admin set silently grew
           with no GRANT_ADMIN, BOOTSTRAP_ADMIN or ADMIN_CLAIM row explaining
           it, and no way to date the change. The spec concedes the weak actor
           gate; it does not concede the absent trail.
    SUGGESTED-FIX-CLASS: audit-log-coverage

  - CATEGORY: AUTH-BYPASS
    SEVERITY: low
    PROMISE: docs/spec/security.md:1526-1532: "the **admin-gated** routines
              resolve their actor from the `infochat.actor_id` GUC that the
              calling role sets itself, and check `is_admin` only, so against
              an attacker who already controls Provider SQL the gate raises
              the bar — they must name some admin's id".
    GAP: The diff's own regression suite pins that gate for 12 of the 14
         admin-gated routines and deliberately skips the two that matter most
         to credential issuance. ProviderIdentityGrantsIT.java:452-455 states
         it: "{@code insert_preban_user} and {@code mint_invite_code} are
         absent by necessity — they INSERT unconditionally, so they cannot be
         driven to a no-op; their gate is the same shared {@code
         require_bot_admin_actor()} call every routine here opens with." The
         probe list (ProviderIdentityGrantsIT.java:457-475) confirms the
         omission. The guards themselves are present today
         (V62:261 for insert_preban_user, V62:388 for mint_invite_code), but
         nothing in the suite fails if a future edit drops either PERFORM
         line, and `mint_invite_code` is the single routine whose product is a
         bearer credential: a PENDING invite code that registers a stranger on
         any adapter (security.md:978-997).
    REPRO: Not exploitable as shipped — the guard is in place. It becomes live
           on the first regression: a later migration or refactor deletes
           `PERFORM require_bot_admin_actor();` from V62:388 (or reissues the
           routine via CREATE OR REPLACE without it); `mvn verify` stays
           green, because ProviderIdentityGrantsIT never probes that routine
           and the handler tests only exercise the happy path with the GUC
           already bound. Any Provider-role SQL — including code paths that
           are not admin commands — can then run `SELECT
           mint_invite_code(gen_random_uuid(), 'OPEN_ADAPTER', 'simplex',
           NULL, NULL, NOW() + interval '7 days');` and read the code back via
           the retained SELECT on invite_code, minting DM access without a bot
           admin and outside the §Invite-code registration PENDING caps'
           intent. The same shape applies to insert_preban_user (mint a
           `preban` row for an arbitrary contact, silently denying them
           service).
    SUGGESTED-FIX-CLASS: other

OUT-OF-MODEL:
  - The 19 new routines are `SECURITY DEFINER` and therefore execute with the
    migration owner's rights (superuser in the shipped compose). Today every
    body is static SQL with `SET search_path = pg_catalog, public`
    (V62:77, 121, 144, 172, 196, 221, 257, 274, 289, 298, 312, 340, 355, 369,
    383, 411, 431, 452, 472, 492), so there is no dynamic-SQL or
    search-path-hijack path — noting it only because the owner-rights blast
    radius is now attached to 19 entry points instead of 3.
  - A hostile or compromised *operator* / direct psql access to the DB is
    explicitly out of model (security.md:24, "The **DB** is internal — only
    the two services and the operator reach it"), so the ability of the owner
    role and any future role to call these routines directly is not counted.
  - ProviderIdentityGrantsIT.java:498-506 deliberately leaves a permanent
    `is_admin = TRUE, is_banned = FALSE` row in the collector module's test
    cluster. Verified harmless today (no collector-module test asserts on the
    live-admin count, and existing collector ITs such as
    ApproveQuarantinePhantomNotifyIT:142-150 seed admins the same way), but it
    is exactly the fixture leak the provider-side helpers added in this same
    diff call out as "a permanent fixture leak that breaks the
    last-admin-protection tests" (GroupMembershipRepositoryTest.java:60-70).
    Test hygiene, not an attack path.

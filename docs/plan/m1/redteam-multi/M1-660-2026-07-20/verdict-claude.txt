    PROMISE: "It is bounded — read-only, capped in time (the pgvector probe by

    GAP: CommandIntentIndex.java:150-151 now arms
          `SET LOCAL hnsw.iterative_scan = strict_order` inside
          lookupCommand on EVERY caller's connection. On the tool path this
          stays time-capped: HelpLookupTool.java:169 runs
          CancellationService.armToolConnection → applyStatementTimeout
          (CancellationService.java:112-118), so the widened scan is bounded
          by `statement_timeout` and /stop's pg_cancel_backend. On the
          deterministic delivery-trigger path, ChatAgent.java:793 borrows a
          bare `dataSource.getConnection()` with NO statement_timeout and NO
          backend-pid registration — and the diff simultaneously removes the
          implicit work bound that previously protected that unarmed caller:
          the diff's own comment (CommandIntentIndex.java:165-176) states the
          pre-fix probe "stops after ef_search candidates," whereas the armed
          iterative scan "keeps walking" until a filter-surviving row emerges
          or `hnsw.max_scan_tuples` (a Postgres default, ~20k, nowhere
          spec-committed) exhausts. Result: the one per-turn pgvector probe
          that runs on an unarmed connection got strictly more expensive in
          the worst case, with no committed time cap and no /stop reach,
          while its sibling caller kept both. Asymmetric application of the
          spec's own bounding pattern — a defense-in-depth reduction, not a
          currently exploitable break.
    REPRO: A registered, post-probation user sends chat-mode messages whose
            embedded vector lands far from every visible command intent (any
            gibberish sentence). Each turn deterministically fires
            ChatAgent.lookupIntentForDelivery → lookupCommand (ChatAgent.java
            :443/:793-795 — it runs before the LLM call, so no tool-loop cap
            applies); because no row clears the distance threshold, the
            strict_order iterative scan walks the shared
            idx_doc_embedding_hnsw past every foreign-doc_kind row — the
            M1-649 topic corpus this ticket exists to prepare for — up to
            hnsw.max_scan_tuples per probe, on a connection nothing can
            time-cap or cancel. Exploitability today is negligible: the
            corpus is operator-written (attackers cannot crowd
            doc_embedding), small, and turns are metered by the per-user LLM
            bucket. The lever grows exactly as the shared index grows, and
            the failure would arrive with the data, not a code change — the
            same silent-arrival shape the diff's comment warns about for
            under-recall.

OUT-OF-MODEL:
  - The new javadoc/acceptance claim that the armed GUC and the never-committed
    read transaction "die at pool release, and never leak to another borrower"
    (CommandIntentIndex.java:103-113) rests on the connection pool's
    release-time rollback + autocommit-reset semantics (Agroal defaults), an
    infrastructure assumption outside security.md's documented boundaries. A
    deployment whose pool is configured without rollback-on-return would
    return a connection with an open snapshot-holding transaction. The
    codebase already relies on this pattern (CancellationService.java:104-110,
    SemanticSearchTool lineage), so this is a pre-existing assumption the diff
    extends, not introduces — flagged in case the user wants the pool
    contract written into the spec.
  - On a Postgres/pgvector older than 0.8, `SET LOCAL hnsw.iterative_scan`
    raises an error: the ChatAgent path catches SQLException and degrades to
    "no usage block" (ChatAgent.java:796-800), the tool path propagates to
    the dispatcher's typed error. Availability-only, fail-closed; deployment
    pinning of the pgvector version is operator territory.

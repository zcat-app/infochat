OUT-OF-MODEL:
  - DOS amplification on ChatAgent.lookupIntentForDelivery (no statement_timeout).
    M1-660 changes CommandIntentIndex.lookupCommand to arm
    hnsw.iterative_scan = strict_order inside a transaction it opens
    itself (setAutoCommit(false) → SET LOCAL → probe, no commit/rollback —
    relies on pool release-time rollback, matching SemanticSearchTool's
    shape). This correctly closes the silent-no-op trap the ticket
    targets, and on the HelpLookupTool caller it is fully bounded:
    HelpLookupTool.execute calls cancellationService.armToolConnection
    BEFORE lookupCommand (HelpLookupTool.java:169), which runs
    CancellationService.applyStatementTimeout (CancellationService.java:112)
    → setAutoCommit(false) + SET LOCAL statement_timeout. So lookupCommand's
    setAutoCommit(false) is a no-op, its SET LOCAL iterative_scan joins
    the same transaction, and the probe is statement_timeout-bounded
    AND /stop-cancellable (pid registered with the in-flight handle).

    ChatAgent.lookupIntentForDelivery (ChatAgent.java:793-800) takes a
    DIFFERENT shape: it borrows a bare dataSource.getConnection() inside
    try-with-resources and calls lookupCommand directly — it does NOT
    call armToolConnection, so statement_timeout is never armed on this
    path and the backend pid is never registered for /stop. Before
    M1-660 the probe was a non-iterative HNSW scan bounded by ef_search
    (default 40 candidates), so the missing time bound was a minor
    defense-in-depth gap. After M1-660 the same probe is iterative — it
    keeps walking the HNSW graph until a filter-surviving row emerges
    (bounded by hnsw.max_scan_tuples, default 20k), so the per-turn
    worst-case cost on this un-armed path is materially higher.

    Why this is OUT-OF-MODEL rather than a FINDING: the threat model's
    only statement_timeout-on-a-pre-fetch commitment (§Failure handling,
    "the deterministic digest-first semantic pre-fetch ... capped in
    time (the pgvector probe by `statement_timeout`...)") is explicitly
    scoped to the D28 semanticSearch pre-fetch. lookupIntentForDelivery
    is a separate M1-665 deterministic pre-fetch that the spec does not
    name and does not bind to statement_timeout. M1-660 neither creates
    the gap (lookupIntentForDelivery never armed statement_timeout, even
    before M1-660) nor violates a documented commitment by leaving it.
    The probe is still indirectly bounded by hnsw.max_scan_tuples and by
    the per-user LLM rate bucket (§Rate limiting), so the residual
    exposure is a quality / defense-in-depth degradation, not a
    threat-model breach. Flagging so the user can decide whether to
    extend the model: either (a) widen the §Failure handling pre-fetch
    bounding commitment to cover lookupIntentForDelivery and arm its
    connection via armToolConnection (the one-line fix that makes
    lookupIntentForDelivery byte-for-byte match HelpLookupTool's arming
    posture), or (b) accept the residual risk with the spec unchanged.
    Note the lookupCommand javadoc's claim that it mirrors
    "SemanticSearchTool's reference shape" is accurate for the
    HelpLookupTool caller (which arms statement_timeout externally) but
    papers over the fact that the lookupIntentForDelivery caller does
    not — a documentation accuracy issue worth a comment tweak if (b)
    is chosen.

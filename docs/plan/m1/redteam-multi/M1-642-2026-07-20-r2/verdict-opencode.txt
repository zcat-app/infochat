OUT-OF-MODEL:
  - deliverSequenceToGroup empty-sequence counter-increment trap.
    OutboundDelivery.deliverSequenceToGroup (new method,
    infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/OutboundDelivery.java,
    diff lines 1090-1115) loops `messages`, tracks `anyDelivered`, and after the
    loop applies a single aggregate: `if (anyDelivered) remove(groupId) else
    onPermanentGroupFailure(channel, groupId)`. When `messages` is empty the loop
    body never executes, `anyDelivered` stays false, and the else branch fires —
    the empty sequence contributes ONE increment to the per-group consecutive-
    permanent-failure counter (threshold 3, soft-removal trigger) even though no
    message was attempted and no failure was observed. Today's only caller
    (DigestDelivery.deliver, receiving DigestRenderer.renderSections output)
    cannot produce an empty list on this code path: DigestWorker enters the
    multi-section branch only when collection.posts() is non-empty, and
    renderSections emits at least the Other bucket when posts is non-empty, so
    no adversary input reaches deliverSequenceToGroup with an empty list today.
    The trap becomes reachable when M1-652 adds a filtering caller that could
    emit an empty list (e.g. "replay only undelivered categories" with all
    categories already delivered → empty list → silent counter increment toward
    soft-removal). The threat model is silent on the empty-sequence case: D63
    (added in this diff) and the messaging.md addition commit only to "any
    success resets the counter, all-permanent increments once, an interrupt
    that stops the sequence early attributes nothing" — none of the three
    covers zero messages. A future caller inheriting this method silently
    inherits the increment too. Not a current FINDING because no adversary path
    produces the input on the live call site; flagged so the user can decide
    whether to extend D63 with an explicit empty-sequence rule (e.g. "zero
    messages → no aggregate outcome") before M1-652 lands a filtering caller.

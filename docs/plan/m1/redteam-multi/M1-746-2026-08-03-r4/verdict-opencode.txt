RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: DOS
    SEVERITY: low
    PROMISE: "A SEPARATE hard retention ceiling (`MAX_CACHED_TRANSLATION_LENGTH` = 2048 ...) bounds what the cache may retain: a translation within the input cap but over the ceiling is served for the call but never cached, so a raised `input-max-length` cannot resurrect the amplification. Together they keep the 10,000-entry cache at ~20 MB worst case regardless of config, so a hostile endpoint's up-to-8-MiB response can never become tens of gigabytes of retained heap" (ticket M1-746, R1 re-audit r2/r3 text, part of this diff); threat-model trust boundary 9: "a pathological multi-GB reply cannot exhaust the JVM."
    GAP: The retention bound is delivered for the VALUE side only. `QueryTranslationCache.QueryKey` (infochat-provider/src/main/java/app/zcat/infochat/provider/translation/QueryTranslationCache.java:979) embeds the raw query as `sourceText`, and `keyFor` (lines 1022-1025) puts it in the key verbatim; the 2048 belt (QueryAnchorTranslator.java:616, checked only at lines 773-779) applies to the cached VALUE, never to the key. The key is length-bounded only by the operator-configured `infochat.chat.tool.input-max-length` injected at QueryAnchorTranslator.java:657-658 — the exact knob the belt claims to be "decoupled from". Retained heap is therefore `10,000 × (input-max-length + 2048)`, which is NOT "~20 MB ... regardless of config": at the 8 MiB transport-cap ceiling that is ~80 TB of key heap — the same order as the original R1 finding, now reachable through the key side the belt does not cover. The ticket's "regardless of config" claim is false as written (the endpoint-driven value-side amplification is genuinely closed; the residual needs the operator to raise the knob).
    REPRO: Operator raises `infochat.chat.tool.input-max-length` (the belt's own stated premise: "an operator raising the input cap must not silently resurrect the R1 heap-amplification"). A registered, non-probation user in a non-`en` scope (or a prompt-injected model emitting long tool-call `query` args, each accepted up to the raised cap by ChatToolDispatcher.validateInputLengths) issues 10,000 DISTINCT queries at the raised length; each `cache.put` (QueryAnchorTranslator.java:774) retains the full query in the key with no length bound of its own, so retained heap grows to `10,000 × input-max-length` regardless of the 2048 belt. With the cap at the 1-8 MiB operator ceiling, the cache holds tens of gigabytes — the amplification the R1 fix promised to make impossible "regardless of config".
    SUGGESTED-FIX-CLASS: input-sanitization

  - CATEGORY: DOS
    SEVERITY: low
    PROMISE: "the accepted translation is length-capped at the tool's CONFIGURED `input-max-length` — the same property the tool dispatcher enforces on the raw query, one knob, so the anchored string can never exceed what the raw path permits at ANY operator config" (ticket M1-746, R1 re-audit r2 text); QueryAnchorTranslator javadoc (line 592): "the anchored string may never exceed what the raw path permits at any operator config."
    GAP: The cap is re-validated only on the MISS path. `translate()` short-circuits at the cache lookup (QueryAnchorTranslator.java:703-706) and returns the stored translation without any `translated.length() <= inputMaxLength` re-check; `inputMaxLength` is frozen at construction (lines 657-663). A value accepted under a higher cap is served unchanged after the effective cap drops, so the anchored string can exceed what the raw path permits at the CURRENT config — the invariant is not delivered on the hit path. (Bounded impact: the belt keeps values ≤ 2048, so this is a longer-than-permitted query reaching the arms, not heap growth; and an in-memory cache means a restart clears stale values — but nothing in the code re-validates, so the guarantee rests on an operational accident, not on the code.)
    REPRO: Operator runs with `input-max-length = 500`; a `cs`-scope user searches text that translates to a 480-char string, which is cached (≤ 2048 belt, ≤ 500 cap). Operator lowers `input-max-length` to 200 without a restart (dev-mode reload, or a deployment that mutates config in place). The same query now hits the cache and is served at 480 chars — exceeding the 200-char bound the raw query path enforces at that config — while the miss path would have rejected it. The anchored string then reaches the embed and `plainto_tsquery('english', ?)` at a length the tool's own dispatcher would never admit for the raw query.
    SUGGESTED-FIX-CLASS: input-sanitization

Not an attack (the exception is disclosed and its bounds are delivered); flagging so the user can decide whether to schedule the revisit or amend the spec text.
  - The hard-coded `temperature: 0` lands on the shared `ModelTask.TRANSLATOR` key, silently changing the sampling behavior of the OTHER two translation legs (collector `IngestTranslationWorker` and provider `LlmTranslationProvider`/presentation pipeline), not just the query-anchoring leg. Disclosed in `docs/design/05-llm-and-embeddings.md` but absent from the `security.md` amendment; not an attack (more determinism), flagging for awareness that the security-model disclosure is narrower than the behavioral change.

RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: INFO-LEAK
    SEVERITY: low
    PROMISE: docs/spec/security.md §Secrets handling → "User content in
      exceptions" commits: "Exception messages and stack traces emitted
      via the application logger MUST NOT contain user-authored prose
      (chat-mode message bodies, post bodies, saved-post annotations,
      command arguments). The application provides a SafeLog utility
      that drops the exception message body, retains only the exception
      class name, and truncates the cause chain to class names
      (depth-capped at 5). The original Throwable is never passed to
      the underlying SLF4J logger."
    GAP: The diff introduces two new catch-and-log sites that pass the
      raw Throwable straight to the JBoss/SLF4J logger instead of
      routing through SafeLog:
        - DigestWorker.java:255 — `LOG.warnf(persistFailure, ...)`. The
          guarded call is `DigestSectionRepository.replaceSlotSections`
          (DigestWorker.java:251), whose batch INSERT binds the
          `digest_section.content` column to `RenderedSection.text()`
          (DigestSectionRepository.java, insert loop ~1003-1016 of the
          diff). That `content` byte string is the per-category render
          output: post titles, source display names, UIDs, and the
          LLM-generated per-cluster summary prose (DigestRenderer
          appends sanitized-but-still-post-derived prose). Post bodies
          / post-derived prose are exactly the class §Secrets handling
          names ("post bodies").
        - DigestDelivery.java:178 — `LOG.warnf(e, ...)` inside
          `RecordingAdapter.send`. The guarded call binds only
          (groupId, windowStart, categorySlug) — no user content — so
          this site's bind values are benign, but it still ships the
          Throwable to SLF4J against the literal "never passed" rule.
      This is not a theoretical-only drift: the codebase DOES enforce
      the SafeLog contract on content-touching exception paths in the
      same package and on the exact chokepoint this diff wraps —
      CategoryRollupGenerator.java:152 (`SafeLog.warn(LOG, ..., e)`,
      same digest prose family) and OutboundDelivery.java:312
      (`SafeLog.warn(log, ...)`, the class whose
      `deliverSequenceToGroup` the new RecordingAdapter delegates to).
      The diff's two new sites are the inconsistency, not the baseline.
    REPRO: Trigger a failure inside `replaceSlotSections` while a
      section list carrying post-derived prose is bound — e.g. a
      transient DB connectivity blip, a constraint/timeout on the
      batch INSERT, or a disk-full condition during the render-time
      persist. DigestWorker.java:250-258 catches the SQLException and
      hands `persistFailure` (message + full cause chain + stack
      trace) to `LOG.warnf`. The standard Postgres JDBC driver does
      not interpolate bind parameters into PSQLException text today,
      so no post body reaches the log on the default driver — but the
      threat-model commitment does not rest on driver behavior ("The
      original Throwable is never passed to the underlying SLF4J
      logger" is unconditional), batch-INSERT exceptions are the
      class most likely to grow parameter echo under driver
      rewrites/logging config, and a raised Hibernate trace level
      (the "Known framework-level logging risks" the spec already
      warns about) compounds the surface. An operator who lifts
      `org.hibernate.SQL`/`org.hibernate.type` to DEBUG for
      diagnosis during a persist-failure storm gets the section
      `content` bytes in the same log stream the un-SafeLog'd
      Throwable flows through.
    SUGGESTED-FIX-CLASS: other — route both catch blocks through
      `app.zcat.infochat.core.log.SafeLog` (e.g.
      `SafeLog.warn(LOG, "Section persist failed for group ...",
      persistFailure)`), matching CategoryRollupGenerator.java:152
      and OutboundDelivery.java:312. No behavior change; the
      throwable's class-name chain is retained, the message body and
      any embedded post-derived prose are dropped per the spec
      commitment.

OUT-OF-MODEL:
  - Fallback render-budget clamp is looser than its comment claims.
    DigestRetryService.fallbackRerun (diff ~811-825) sets
    `clampedWindowEnd = min(coords.expiresAt, now.plus(windowWidth))`
    and the comments (DigestRetryService + D65) assert the fallback's
    "render budget is bounded by the configured digest window width,
    never by the retention horizon." But the clamp bounds window-END,
    not window-WIDTH: `windowStart` stays pinned to the original
    slot's start, so a retry issued ~20h after a crash-stranded slot
    rebuilds a slot spanning (originalWindowStart .. now+30m) — a
    many-hours collection window, which is exactly what the comment
    says "never" happens. This is not elevated to a FINDING because
    (a) it only fires on the section-less fallback path (normal V61
    slots replay LLM-free), (b) the digest structure caps rendered
    clusters per-section so LLM call COUNT is structure-bounded
    regardless of window width, (c) the per-minute transport bucket +
    PT2M cooldown bound retry frequency, and (d) the threat model's
    DOS commitments are framed around rate caps / unbounded loops,
    which still hold. Flagged only because the spec/comment
    over-states the protection; the residual cost is bounded by
    other in-model mechanisms. Tightening the clamp to bound
    window-WIDTH (re-derive windowStart = clampedWindowEnd minus
    windowWidth) would make the comment true.

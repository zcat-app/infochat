  - Thread-confinement of the signal channel: PaginationSaturationTracker
    documents that fetch() runs synchronously on the dispatch thread; a
    paginating fetcher that ever paginated on a different thread (async
    internals) would silently LOSE its cap-hit/truncation signal (missed
    saturation alert), because the scheduler's consume reads the dispatch
    thread's ThreadLocal. That is a reliability/observability concern, not
    a security commitment in security.md, and no current fetcher does this.
    Unchanged by this diff; carried forward from the prior audit.
  - Failure-recording sub-path robustness: if the catch block's
    failure-recording sub-path itself throws an unchecked (non-SQLException)
    exception, the D42 ladder increment (recordFailure), the throttled
    'failed'-transition notification, and the streak-reset recordTick(false)
    are skipped for that tick. This is the leftover fragment of the closed
    finding, and it is now benign with respect to the finding's core harm:
    both thread-local drains have ALREADY run (FetchScheduler.java:527-528),
    so no flag survives to mis-attribute saturation to an innocent source,
    and the pending row is retried on the next heartbeat (the abort merely
    skips the remaining sources for that heartbeat). The residual is that a
    persistently-failing source may not transition to status='failed' while
    the repository itself is defective or the DB is down — an internal-fault
    precondition (DB is inside the trust boundary), not an adversary-reachable
    path, and pre-existing rather than introduced by this diff. Flagged as
    advisory so the user can decide whether robustness hardening warrants a
    ticket.

FINDINGS:
  - CATEGORY: INFO-LEAK
    SEVERITY: medium
    PROMISE: security.md §Secrets handling — "The post-setup `prod/switch-llm.sh` backend switcher records the LLM API key in `secrets.env` through the same dotenv-escaped channel and prints a per-task privacy disclosure naming exactly which generative tasks now call a remote provider and what each exposes — `chat` (private user messages) flagged loudest, the ingest tasks (`security`/`tagger`/`entity`/`classifier`) as topic-interest exposure over public posts".
    GAP: The diff routes VERBATIM inbound user chat text into `ModelTask.TRANSLATOR` but leaves the spec-committed per-task privacy disclosure describing the pre-M1-746 exposure.
      - infochat-provider/src/main/java/app/zcat/infochat/provider/chat/ChatAgent.java:689-694 (unchanged by the diff) dispatches the D28 pre-fetch with `query = userMessage` (first 500 chars of the user's raw message).
      - infochat-provider/src/main/java/app/zcat/infochat/provider/chat/tool/SemanticSearchTool.java:126-127 (new) hands that exact string to `QueryAnchorTranslator.translate(...)`.
      - infochat-provider/src/main/java/app/zcat/infochat/provider/chat/tool/QueryAnchorTranslator.java:236-251 (new) embeds the query verbatim in the prompt and calls `provider.generate(ModelTask.TRANSLATOR, "", prompt)`; the endpoint is whatever `LlmRouter.forTask(TRANSLATOR, lang)` resolves (per-task `infochat.llm.translator.base-url`, else the shared default) — nothing pins it local, and the diff itself extends the REMOTE path (infochat-llm-adapter/src/main/java/app/zcat/infochat/llm/impl/AnthropicProvider.java:421-423).
      - The disclosure surfaces the threat model names are untouched by the diff: prod/switch-llm.sh:403 and prod/scripts/4-llm.sh:493 still print "translator — translation of the bot's replies to you; exposes the bot-reply text (which can echo your queries)". The `chat` task alone carries the "!! YOUR PRIVATE MESSAGES" marker (prod/switch-llm.sh:394-395), and that block's own header comment states "A wrong claim here is a security defect".
      - The diff amends security.md (semanticSearch tool row, §Failure handling, §Rate limiting) and docs/design/05, but no hunk touches either disclosure script or the §Secrets handling exposure list.
    REPRO: 1) Operator keeps `chat` on the local backend and pins only the translation task remote (`infochat.llm.translator.base-url` + `infochat.llm.translator.api-key`) — a supported per-task routing shape, and the natural one for better `cs` quality. 2) Setup/switch output tells the operator that private messages stay local and that translator exposes only "the bot-reply text". 3) A registered user sets `/lang cs` and DMs the bot any private message. 4) On EVERY chat turn the deterministic pre-fetch ships the first 500 chars of that private message, verbatim, to the third-party endpoint (and again per distinct model-elected `semanticSearch` query). The operator was told this exposure did not exist; no operator- or user-facing surface discloses it.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

  - CATEGORY: DOS
    SEVERITY: low
    PROMISE: security.md §Rate limiting, the bullet this diff adds — "**Query-anchoring translation (M1-746, D58)** — a disclosed exception to the 'LLM-triggering operations' bucket: a non-English scope's retrieval issues generative `ModelTask.TRANSLATOR` calls — one per turn for the D28 pre-fetch, plus one per DISTINCT model-elected `semanticSearch` query — that draw NO per-user bucket token ... Accepted v1 posture, stated rather than hidden: the per-turn tool-call cap bounds model-elected volume, every call is a small (~100-token) prompt against the local translator model, the translation leg is cached per (scope, query, language) so repeated queries cost nothing, and the shared breaker bounds outage behaviour."
    GAP: The un-metered exception is disclosed, but three of the four bounds offered in exchange are not delivered by the code:
      - "local translator model": QueryAnchorTranslator.java:250 resolves the provider through `llmRouter.forTask(ModelTask.TRANSLATOR, sourceLanguage)`; LlmRouter applies no locality constraint (contrast the embedding leg, which the same tool row pins local under D54). The diff's own AnthropicProvider hunk (AnthropicProvider.java:421-423) exists precisely because TRANSLATOR can resolve to a remote endpoint.
      - "~100-token prompt": the prompt carries the caller's query up to the dispatcher's configured `infochat.chat.tool.input-max-length` (500 default, operator-raisable — injected in the `QueryAnchorTranslator` constructor), plus the template.
      - "cached ... so repeated queries cost nothing": QueryAnchorTranslator.java:216 (hit path skipped whenever the cached value exceeds the CURRENT cap), :253-262 (failure not cached), :270-274 (blank not cached), :284-289 (over-cap not cached), :297-303 (over-ceiling not cached). Trust boundary 9 puts a hostile or degraded endpoint in scope; an endpoint that answers over-cap or blank means the cache never populates, so every repeat of the same query re-issues a fresh un-metered generative call.
    REPRO: A registered, non-probation user sets `/lang cs` and chats normally. Each turn spends one token of the per-user LLM bucket but issues 1 (pre-fetch) + up to the per-turn tool-call cap generative TRANSLATOR calls that draw no token from any per-user or per-group bucket. With the translator pinned to a remote/paid endpoint (finding 1's config) and an endpoint whose replies exceed `input-max-length`, no cache entry is ever written, so N metered turns become N x (1 + tool-cap) unmetered outbound generative calls — the amplification the bucket exists to bound, resting on a "local" and "cached" argument the code does not enforce.
    SUGGESTED-FIX-CLASS: rate-limit

  - CATEGORY: INFO-LEAK
    SEVERITY: low
    PROMISE: security.md §What's intentionally NOT in v1 — "v1 relies on minimization (chat-memory TTL, `/forget`, `/export`) instead"; and, on what a translation cache may hold, the accepted-residual bullet in the same section: "v1 accepts this as a minor trade-off: the cached strings are presentation prose generated by the bot (cluster summaries, headers, status lines), **not user-authored content**".
    GAP: The diff introduces a second, user-content-bearing retention store that no minimization lever reaches. infochat-provider/src/main/java/app/zcat/infochat/provider/translation/QueryTranslationCache.java:92-95 builds a Caffeine cache with `expireAfterWrite(Duration.ofHours(24))` / `maximumSize(10_000)` whose VALUE is the English translation of the caller's query — and on the D28 pre-fetch path that query IS the user's chat message body (ChatAgent.java:689). Only the KEY is hashed (`keyFor`/`sha256` in the same class); the value is retained in plaintext. The class exposes only `get` and `put` — there is no invalidation entry point — so `/forget` (the D37 "user-initiated immediate purge") and the chat-memory TTL pruner, both DB-scoped, leave the derivative in place for up to 24h. The diff adds no purge hook and no `/export` coverage.
    REPRO: A user with `/lang cs` sends a sensitive message; its translated form is retained in provider heap for 24h keyed by the scope. The user then issues `/forget`, which the product presents as the immediate purge of the data held on their behalf — `chat_memory`, `chat_session`, `summary_anchor` and `saved_post` rows are deleted while the translated copy of the same message survives, unreachable by any user control, until the write-based TTL expires.
    SUGGESTED-FIX-CLASS: other

OUT-OF-MODEL:
  - Reading the plaintext translation values out of provider heap (debugger attach, core dump, host compromise) is out of the documented model — §Threat model scopes out side-channel attacks against the host and supply-chain/operator-infrastructure compromise. It is named only as the observation channel for finding 3, whose in-model substance is the retention-vs-`/forget` gap, not the heap read itself.
  - Considered and FALSIFIED, recorded so a later audit does not re-raise it: the query-translation cache is partitioned by (scope_kind, scope_id), so in GROUP scope the entry is shared by every member of that group and a cache hit is observable as a multi-second latency difference. This is not a leak — a group member's chat text is already visible to every other member of that group scope by construction, so the oracle discloses nothing the observer could not already read. DM scope keys on the caller's own id and shares nothing.

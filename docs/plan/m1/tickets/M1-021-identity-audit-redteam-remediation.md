# M1-021: Identity/audit redteam remediation (V6 — actor checks, search_path, ban-self trigger, audit-actor integrity)

## Context

Remediates the five `/redteam M1-008a` findings (frontmatter `redteam_findings:` on M1-008a — 2 high, 3 medium). Per the workflow's "never amend a passed commit" rule, the fix lands as a new migration on top of V5 rather than rewriting V5 in place. M1-008a's commit is immutable; M1-021 is the corrective unit.

The five findings cluster into three remediation surfaces, each landing as a CREATE OR REPLACE in the new migration:

1. **`delete_preban_user` hardening** (Findings 1, 3, 4 — one high + two medium). The M1-008a procedure (a) silently skips the audit row when `p_actor_id` does not match a `users` row (the `JOIN users a ON a.id = p_actor_id` returns zero rows, the `INSERT ... SELECT` inserts nothing, but the subsequent `DELETE FROM users WHERE id = p_user_id AND registration_state = 'preban'` proceeds — Finding 1, AUDIT-EVASION); (b) does not check that `p_actor_id` corresponds to a row with `is_admin = TRUE` (Finding 3, PERM-ESCAL); and (c) is `SECURITY DEFINER` without a pinned `search_path`, exposing it to the classic shadowing attack if `CREATE` is ever granted on `public` to an application role (Finding 4, PERM-ESCAL). The fix is a single `CREATE OR REPLACE PROCEDURE` that pins `search_path = pg_catalog, public` in the proc-level options block, performs an explicit `IF NOT EXISTS (SELECT 1 FROM users WHERE id = p_actor_id AND is_admin = TRUE) THEN RAISE EXCEPTION 'actor is not a bot admin'`, and only then proceeds to the audit INSERT and the DELETE. The audit INSERT must remain BEFORE the DELETE (Invariant 7 audit-before-effect). The schema fix subsumes the JOIN-returns-zero failure mode because the explicit existence check raises before reaching the INSERT.

2. **Trigger-layer ban-self prevention** (Finding 2 — high, PERM-ESCAL). The spec's `docs/spec/security.md` §Authorization model commits to "cannot ban self" being **enforced at the trigger layer, not just the command layer, so a buggy command cannot bypass it." The M1-008a `trg_last_admin_protection_update` only verifies "≥ 1 non-banned admin remains" — it does not know who the actor is and therefore cannot enforce "self ≠ target." The fix is the standard Postgres pattern for actor-aware triggers: the application sets a session-scoped GUC `infochat.actor_id` via `SET LOCAL infochat.actor_id = '<uuid>'` before issuing the privileged UPDATE; the trigger reads the GUC via `current_setting('infochat.actor_id', TRUE)` (the `TRUE` second-arg returns NULL on missing rather than raising) and, when set, compares to `NEW.id`. A self-ban attempt raises `cannot ban self`. The application side of this discipline (the actual `SET LOCAL` call site) lands in the later `/ban` / `/revoke-admin` command tickets; this ticket establishes the schema-side reader so the application-tier ticket can wire the call site as a one-line addition.

3. **Audit-row actor integrity** (Finding 5 — medium, AUDIT-EVASION). The Provider role has `INSERT` on `audit_log` with no consistency check between `actor_user_id` and the connection's effective actor. Combined with the role's `INSERT INTO audit_log` capability, any code path that reaches an `audit_log` write can mint rows attributing arbitrary actions (`GRANT_ADMIN`, `BAN`, `UNBAN_PREBAN_DELETE`) to arbitrary admins without performing those actions. The fix is a new BEFORE INSERT trigger `trg_audit_log_actor_check` that mirrors the GUC pattern from fix 2: when `current_setting('infochat.actor_id', TRUE)` is non-empty AND `NEW.actor_user_id IS NOT NULL` AND `NEW.actor_user_id IS DISTINCT FROM` the GUC, raise. The GUC-unset path is unchanged (preserves the bootstrap-admin and pre-application-wiring INSERT paths). The system-actor case (NEW.actor_user_id IS NULL) is preserved unconditionally.

The schema-only nature of the fix is preserved (no Java entity classes, no application-layer audit writer, no Provider startup). The application layer's wiring of `SET LOCAL infochat.actor_id` is owned by the later T1-D/E tickets that build `/ban`, `/revoke-admin`, `/grant-admin`, and the audit-write helper.

## Implementation notes

- **Migration version is the next free integer at start time.** V1..V5 are on disk; if M1-008b lands V6 first, this ticket takes V7; if not, V6. Concretely: at `/m1-tick start M1-021`, run `ls infochat-core/src/main/resources/db/migration/ | sort -V | tail -1` and pick the next integer. Update the file path in `files_scope` and the acceptance grep before implementation begins (refine if the version number changes; the integer choice is deterministic from on-disk state).
- **`SET search_path` lives in the procedure-options block, not the body.** Postgres syntax: `CREATE OR REPLACE PROCEDURE delete_preban_user(...) LANGUAGE plpgsql SECURITY DEFINER SET search_path = pg_catalog, public AS $$ BEGIN ... END $$;`. The `SET` clause MUST be at proc-declaration level (before `AS`), not as a body statement — placing `SET search_path` inside the body changes the session-level path for the rest of the transaction, which is the wrong semantics. The proc-level form scopes the override to the procedure invocation only.
- **The GUC name `infochat.actor_id` is namespaced.** Postgres requires custom GUCs to have a namespace prefix (a `.` in the name). `infochat.actor_id` follows the same convention as the request-id GUC the M1-008a `delete_preban_user` already reads (`current_setting('infochat.request_id', TRUE)`), keeping the application-layer GUC-set discipline coherent: the application sets `infochat.request_id` AND `infochat.actor_id` together at the start of every privileged-mutation transaction, and the schema reads both as appropriate.
- **The GUC reader uses `current_setting(name, TRUE)` not `current_setting(name)`.** The two-arg form returns NULL for an unset GUC; the one-arg form raises. The two-arg form is essential for backward compatibility with the M1-008a unit tests (which do not set the GUC) and for the bootstrap-admin path that runs without a session GUC.
- **Lock-then-read order in the trigger.** The M1-008a `LOCK TABLE users IN SHARE ROW EXCLUSIVE MODE` MUST remain at the very top of `trg_last_admin_protection_update`, before the `current_setting` read. The lock guarantees serialization of concurrent revocations (Invariant 2's serialization clause); reordering the GUC read above the lock would not break serialization (the GUC read is a session-local operation) but the spec-mandated ordering is "lock first, then proceed," and reviewers will look for it there.
- **The `cannot ban self` check fires only on the is_banned FALSE→TRUE transition.** A self-targeted UPDATE that does not change `is_banned` (e.g. updating `display_name`) must not raise. Likewise a self-targeted UPDATE that sets `is_banned = TRUE` when `OLD.is_banned` was already TRUE is a no-op transition and the trigger preserves the existing M1-008a behavior (no raise on no-op). The conjunction `OLD.is_banned = FALSE AND NEW.is_banned = TRUE AND v_actor::UUID = NEW.id` is the precise gate.
- **The audit-actor trigger does not enforce `actor_user_id IS NOT NULL`.** The system-actor case (no human caller) is real: BOOTSTRAP_ADMIN, BOOTSTRAP_SOURCE_LOAD, BOOTSTRAP_ASSET_LOAD, and the re-evaluation job all write audit rows with a NULL or system-typed actor. Constraining `NEW.actor_user_id IS NOT NULL` would break those paths. The trigger fires only when both the GUC is set AND `NEW.actor_user_id IS NOT NULL` AND they disagree.
- **Test fixture for GUC.** Tests open a JDBC connection, then issue `SET LOCAL infochat.actor_id = '<uuid>'` inside a transaction (autocommit OFF), then perform the UPDATE / INSERT, then assert. The M1-008a `PostgresSchemaTestBase` already exposes `newConnection()` and a `truncateAll()` between-tests reset; the new tests subclass it the same way the M1-008a tests do.
- **Search_path shadow attack test.** `DeletePrebanActorCheckTest` test (d) exercises the search_path pin by: (i) creating a temporary schema `attack_schema`, (ii) creating a fake `attack_schema.audit_log` table the test owns, (iii) `SET search_path = attack_schema, public` on the session, (iv) `CALL delete_preban_user(...)`. After the call, `SELECT count(*) FROM public.audit_log WHERE action = 'UNBAN_PREBAN_DELETE'` must be 1 (the procedure's pinned search_path resolved `audit_log` to `public.audit_log`, not the shadow). `SELECT count(*) FROM attack_schema.audit_log` must be 0 (the shadow was not written to). Cleanup: drop `attack_schema` after the test.
- **Audit row INSERT in the procedure no longer JOINs the actor.** With Finding 3's existence check raising before the INSERT, the audit row's `actor_contact_id` and `actor_adapter` need a different lookup — either (a) a second query against the actor row, or (b) drop those fields from the procedure-internal INSERT and rely on the application-layer audit writer to populate them when it lands. Option (b) is cleaner: the procedure-internal INSERT carries `actor_user_id, action, target_kind, target_id, target_contact_id, scope_id, request_id, details_json` (the actor's contact/adapter are derivable from `actor_user_id` by any later reader that needs them), avoiding a second SELECT round-trip. Choose option (b) inline; document the rationale in the migration comments. Option (a) is a fallback if a reviewer flags the column-loss.

## Big-picture notes

- **This ticket is the closing half of the M1-008a security commitment.** M1-008a established the schema; M1-021 closes the five gaps the redteam surfaced. The pair (M1-008a + M1-021) collectively delivers the spec's §Authorization model + §User ban + §DB roles trigger-layer enforcement. Subsequent application-tier tickets (the `/ban`, `/revoke-admin`, `/grant-admin`, and audit-write paths) build on top of this baseline and own the application-side `SET LOCAL infochat.actor_id` discipline.
- **The GUC pattern is a layered enforcement, not a defense in depth alternative.** The schema-side trigger only enforces "if the application set the GUC, the action must be consistent with it." The application-side discipline is "set the GUC before every privileged mutation." Both must hold for end-to-end safety. This ticket lands the schema half; the later T1-D/E tickets land the application half. Until the application half ships, the GUC-unset path is the legacy M1-008a behavior — no regression.
- **The redeclared procedure preserves Invariant 7 audit-before-effect.** The audit INSERT MUST come BEFORE the DELETE in the new procedure body, exactly as in M1-008a. Reversing the order would lose audit-before-effect on a transaction-aborted DELETE — the failure mode Invariant 7 exists to prevent. A reviewer should check this explicitly.
- **The M1-008a `trg_audit_log_no_update` and `trg_audit_log_no_delete` triggers remain in place.** This ticket only ADDS `trg_audit_log_actor_check` as a BEFORE INSERT trigger; it does not modify the append-only trigger guards. The append-only invariant continues to hold via the M1-008a triggers.
- **The audit_log_id_seq USAGE/SELECT grants and the operator-side hard-DELETE on users path are out-of-model per the redteam OUT-OF-MODEL note** and are not addressed here. If a future v2 amendment tightens the threat model to cover those, a separate remediation ticket lands then.

- **Other SECURITY DEFINER procedures.** This ticket touches only `delete_preban_user`. The future `approve_quarantine` / `reject_quarantine` procedures (per `docs/spec/security.md` §Quarantine workflow) land in their own ticket and MUST also pin `search_path` — the convention is established here for them to follow, not retro-applied (those procedures don't exist yet).

## Alternatives considered

- **Amend the M1-008a commit instead of a new migration.** Rejected: forbidden by the workflow (`CLAUDE.md` §M1 workflow — "Never amend a passed commit. Defects found after a passed review become a new ticket and a new commit"). Even though M1-008a hasn't been merged into `main` yet, the ticket is `status: done` and the commit on the per-ticket branch carries the APPROVE; amending would erase the immutable-canonical-commit invariant the workflow relies on.
- **Encode `actor_user_id` consistency as a CHECK constraint instead of a trigger.** Rejected: a CHECK constraint cannot read session GUCs (CHECK expressions are evaluated in a context that doesn't see `current_setting`). The GUC-aware enforcement requires a trigger; CHECK constraints are stateless and cannot cross-reference session state.
- **Forbid `NEW.actor_user_id IS NULL` audit rows.** Rejected: the spec's audit-action catalogue includes BOOTSTRAP_ADMIN, BOOTSTRAP_SOURCE_LOAD, BOOTSTRAP_ASSET_LOAD, and the re-evaluation job's RE_EVAL_RELEASED action — all legitimately run with no human actor. Constraining `actor_user_id IS NOT NULL` would break those paths. The system-actor case is preserved unconditionally.
- **Use a per-row CHECK that `actor_user_id` references a row with `is_admin = TRUE`.** Rejected: not all audit verbs are admin-only. `INVITE_CONSUME` is written when a non-admin user accepts an invite (the actor is the consuming user, not a bot admin). `FORGET`, `SET_LANG`, `SET_TIMEZONE` are user-level actions. Constraining the FK target to `is_admin = TRUE` would break those paths; the invariant the spec actually commits to is "audit row faithfully attributes the actor," not "actor must be admin."
- **Land the application-layer GUC-set discipline in the same ticket.** Rejected: the application-layer privileged-mutation paths don't exist yet (no `/ban`, `/revoke-admin`, `/grant-admin` handlers in the codebase). Adding application code here would balloon scope and require Java entity classes / Hibernate mappings / command-handler classes — exactly the surface M1-008a deliberately deferred. The schema-side reader is the slice that lands now; the application-side wiring is a one-line addition in each later command ticket.
- **Use `SET search_path` inside the procedure body instead of the proc-options block.** Rejected: a body-level `SET search_path = ...` mutates the session for the rest of the transaction, which is wrong for a `SECURITY DEFINER` procedure. The proc-level `SET` clause (in the declaration, before `AS $$`) scopes the override to the procedure invocation only and is the correct Postgres pattern. See https://www.postgresql.org/docs/current/sql-createprocedure.html (the `SET` clause is part of the procedure-level options).
- **Use a session-role switch (`SET LOCAL ROLE`) instead of `SET LOCAL infochat.actor_id`.** Rejected: roles in Postgres are coarse (per-DB-user); the actor we want to track is a per-application-user UUID, not a DB-role. The custom-GUC pattern is the standard PG idiom for application-side actor propagation, used widely (e.g. row-level-security policies that read `current_setting`).
- **Land all five fixes as separate tickets (one per finding).** Rejected: the five findings touch the same migration, the same procedure, and the same trigger function. Splitting them would multiply the migration count by 5 and force every test to be rewritten when the next finding's migration lands. Bundling into one V<N> migration is cleaner; the acceptance items still trace each finding individually.

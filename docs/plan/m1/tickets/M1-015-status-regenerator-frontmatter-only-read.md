# M1-015: Status-regenerator reads frontmatter only

## Context

M1-012 landed the STATUS.md regeneration delegation: a fresh-context
`status-regenerator` agent Globs ticket files, Reads each, computes
the aggregate view, and Writes the rendered STATUS.md. The
delegation works — STATUS regen no longer pulls N ticket bodies
into main-session transcript. But the *subagent's* fresh context
still over-reads.

The renderer needs, per ticket: `id`, `title`, `status`,
`blocked_by`, `deferred_on`, `deferred_reason`, `complexity`,
`risk`, `last_updated`, and the most recent entry under `reviews:`.
Every one of those keys lives in the YAML frontmatter between the
opening `---` and closing `---`. None of the body — Context,
Definition of Done, Implementation notes, Big-picture notes,
Out-of-scope expansion, Alternatives considered — is consulted by
the rendering algorithm.

The current contract (per M1-012's `status-regen-prompt.md` step 2)
says "Use the Read tool to load each ticket file from the Glob
result. Parse the YAML frontmatter between the opening `---` and
closing `---`." That instruction does not name a `limit:` argument,
so the agent's natural read pattern loads the whole file. For the
current 14-ticket set with frontmatter sizes roughly 35–98 lines
and bodies often 300–500 lines, the agent ingests ~5–7× more bytes
than it parses. The over-read scales linearly with milestone size:
at 50 M1 tickets the regenerator's fresh context could absorb
hundreds of KB it then ignores.

The fix is mechanical. The `Read` tool already supports `limit:`.
Instructing the agent to use `Read` with `limit: 150` (chosen to
clear the largest current frontmatter — M1-010's 98 lines — with
substantial headroom) loads only the prefix; the YAML parser sees
the same `---` ... `---` block; the rendered STATUS.md is
byte-identical. The 150-line cap is itself bounded — if a future
ticket has frontmatter exceeding it (a design smell on its own),
the agent re-Reads with a larger window. This is the simplest
possible tightening of the M1-012 contract and lands in two files.

## Definition of Done

- `docs/process/status-regen-prompt.md` instructs the agent to
  Read each ticket file with `limit: 150` so only the frontmatter
  prefix is loaded. The instruction explicitly names the cap
  (`limit: 150`) and explicitly states that the ticket body
  (Context, Definition of Done, Implementation notes, Alternatives
  considered) is not loaded. The instruction also documents the
  fallback: if the closing `---` is not found within the first 150
  lines, re-Read with `offset: 0, limit: 300` (or larger if still
  needed) and parse from the wider window.
- `.claude/agents/status-regenerator.md` persona body matches the
  same contract: the agent loads ONLY the frontmatter prefix of
  each ticket, not the body.
- The tool allowlist stays Read + Write + Glob (no Grep added).
  The frontmatter-only Read is achieved via `limit:`, which is a
  `Read` tool argument the M1-012 allowlist already permits.
- The prompt-template substitution wiring is unchanged. Same
  `{{TICKETS_GLOB}}` and `{{STATUS_FILE_PATH}}` placeholders, no
  new placeholder.
- The canonical STATUS.md output template body and placeholder
  rules are unchanged.
- A `/m1-tick status` run against the current M1 ticket set
  produces a STATUS.md byte-identical to the pre-edit version
  (the rendering contract is unchanged; only the load shape
  shrinks).
- `mvn -B verify` from the repo root exits 0.

## Implementation notes

- **The `limit: 150` choice.** The current largest M1 ticket
  frontmatter is M1-010 at 98 lines (closing `---` on line 98).
  150 is 50% headroom over that. Future tickets with significantly
  larger frontmatter blocks are a design smell — frontmatter is
  metadata, not narrative — but if one appears, the agent's
  fallback Read picks it up. The cap is a heuristic, not a hard
  contract.
- **The fallback shape.** If the agent's first Read returns 150
  lines and the closing `---` is not among them, the agent
  re-Reads the same file with `offset: 0, limit: 300`. If 300
  still isn't enough, re-Read with `offset: 0, limit: 600`. The
  doubling stops when the closing `---` is found OR when a single
  Read returns fewer lines than the limit (meaning the file
  itself is shorter — the closing `---` is missing, which is a
  malformed-ticket condition; the agent surfaces it in the
  structured short reply but proceeds with whatever frontmatter
  prefix it parsed).
- **Why not just Read with no limit and let the parser stop at
  the closing `---`?** That is the M1-012 status quo and the
  thing this ticket fixes. Without `limit:`, the Read returns the
  whole file regardless of where the YAML closes — the parser
  stops at `---`, but the *bytes* are already in the agent's
  context window. The whole point of the tightening is to load
  fewer bytes; the parser's stop point is irrelevant to the
  fresh-context cost.
- **Why not allow Grep instead and grep for the YAML block?**
  Three reasons. (a) Adding Grep widens the tool allowlist M1-012
  deliberately tightened. (b) Grep returns matched lines plus
  context lines, not a structured slice; the agent would still
  need to glue the matches back into a parseable YAML block,
  which is fragile. (c) `Read` with `limit:` is the mechanically
  simplest path — one argument, one tool, no parsing gymnastics.
- **What does NOT change.** The Glob pattern. The number of
  Reads (still one per ticket; this is per-Read bytes, not
  per-Read count). The aggregation algorithm. The rendered
  template body. The placeholder rules. The Write target. The
  structured short reply shape. The skill-side Write-scope guard
  around `git status --porcelain`. The agent's identity, model
  pinning, color, description.

## Big-picture notes

- **The structural win is per-invocation and milestone-scaling.**
  Today: ~13 tickets × ~400 lines avg = ~5200 lines per
  regeneration. After: ~13 tickets × ~80 lines avg (frontmatter
  is typically 50–98 lines; the cap of 150 means worst-case 150)
  = ~1100 lines per regeneration. ~5× reduction in the
  subagent's input-token cost. The win compounds as M1 grows;
  at 50 tickets the savings are ~16000 lines that never need to
  be loaded.
- **The cost is paid in the subagent's fresh context, not main
  session.** M1-012 already moved the regeneration out of main
  session. M1-015 doesn't change WHERE the cost is paid — it
  reduces the cost itself. So the operator's main-session
  transcript is unaffected; the bill is smaller.
- **The fix sits at the prompt + persona boundary, not the
  harness boundary.** The harness's `Read` tool already supports
  `limit:`. The ticket only changes the instruction the agent
  follows. No tool definition changes, no skill changes, no new
  placeholder, no allowlist change.

## Alternatives considered

- **Alt A: do nothing — the M1-012 contract is already
  out-of-main-session; the subagent cost is acceptable.**
  Rejected: subagent cost is still billed; the ~5× over-read
  scales linearly with milestone size; the fix is two-file,
  mechanical, and zero-risk.
- **Alt B: add Grep to the tool allowlist and have the agent
  grep the YAML block.** Rejected as enumerated in the
  Implementation notes (widens allowlist, Grep output shape is
  awkward for YAML reconstruction, simpler tool sufficient).
- **Alt C: split the ticket loader into a dedicated YAML
  helper (e.g., a `frontmatter-extractor` agent).** Rejected as
  premature abstraction. One Read with one `limit:` argument
  per ticket is the simplest mechanism. A helper would be
  bureaucracy.
- **Alt D: choose `limit: 100` instead of `limit: 150`.**
  Rejected: M1-010's frontmatter is 98 lines, leaving only 2
  lines of headroom. Future M1 tickets with similar acceptance
  complexity would routinely trip the fallback. 150 gives 50%
  headroom over the current worst case while still being a
  meaningful tightening.
- **Alt E: choose `limit: 300` to remove the fallback path
  entirely.** Rejected: 300 still loads more bytes than needed
  for every current ticket; the savings drop from ~5× to ~2×.
  The 150 + fallback shape keeps the common path tight while
  preserving correctness on the rare oversized ticket.
- **Alt F: bundle this with M1-013's anchor-range refinement
  for the code-reviewer.** Rejected: different agent, different
  prompt template, different files. Bundling would inflate the
  per-round diff stats and conflate two distinct fresh-context
  optimizations. Mirrors M1-012's own Alt D reasoning ("bundling
  any pair would inflate per-round diff stats").
- **Alt G: also add the frontmatter-only Read pattern to other
  agents that load ticket files (clarity-reviewer,
  code-reviewer).** Rejected: those agents need the ticket
  body. The clarity-reviewer needs it for ACCEPTANCE-RUNNABLE,
  OUT-OF-SCOPE-SPECIFIC, and post-M1-013 SELF-CONTAINED checks.
  The code-reviewer needs it for SCOPE-DRIFT and ACCEPTANCE
  checks. The frontmatter-only pattern applies only to
  status-regenerator because it is the only agent that
  consults zero ticket-body content.

RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - Unicode line/paragraph separators U+2028 (LINE SEPARATOR) and U+2029
    (PARAGRAPH SEPARATOR) survive IngestTextNormalizer.stripMetadataField
    (infochat-core/.../IngestTextNormalizer.java:369-380). The method strips
    bidi-control, zero-width, and ISO-control codepoints only — and
    Character.isISOControl covers exactly U+0000..U+001F and U+007F..U+009F,
    which does NOT include U+2028/U+2029 (Unicode categories Zl/Zp, not Cc).
    The diff's own stated goal (PostPersister.java:76-83, IngestTextNormalizer
    javadoc, IngestTextNormalizerTest.stripMetadataFieldRemovesEmbeddedNewline)
    is that "a newline cannot inject a misleading apparent line into a bare-
    emitted bot reply." A title or url carrying U+2028/U+2029 can still render
    as an apparent extra line on clients that honor those separators, so the
    newline-injection class the diff aims to close is only partially closed.
    This is flagged OUT-OF-MODEL rather than as a FINDING because the threat
    model (docs/spec/security.md §Ingest pipeline) commits only to NFKC +
    bidi-control + zero-width stripping on the post BODY; it makes no spec-level
    promise to normalize the single-line title/url metadata fields at all.
    Title/url normalization is net-new hardening introduced by this diff and
    is not a quoted threat-model commitment, so the residual U+2028/U+2029 gap
    sits below the audited promise surface. Surfaced so the user can decide
    whether to (a) extend stripMetadataField to also drop U+2028/U+2029 and
    other Zl/Zp separators, and/or (b) promote title/url metadata normalization
    to a spec-level commitment.

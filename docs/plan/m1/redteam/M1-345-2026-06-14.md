RED-TEAM VERDICT: CLEAN

The diff under audit (M1-345) is a narrow, defensive-tightening change to
the shared SSRF guard library. It touches three things, all of which
strengthen or are neutral to the threat-model commitments in
docs/spec/security.md §SSRF and outbound connections; none weakens a
promised defense.

Audit reasoning (falsified, not merely confirmed):

1. canonicalizeHost bracket-host validation
   (SsrfGuardedHttpClient.java:328-345). The change makes the bracketed-host
   branch REJECT any inner string that is not a real IPv6 literal via
   Inet6Address.ofLiteral, where the prior code re-bracketed any
   "[...]"-wrapped string unconditionally. This is strictly a tightening:
   it closes the asymmetry the spec's pin-key invariant relies on (the
   pin-map key must be "a real bracketed IPv6 literal or an
   IDN-normalized ASCII hostname"). Falsifier checked — could the
   rejection escape the wrapper's typed-exception contract and leak JDK
   internals? No: resolveAndValidate (lines 587-592) catches the
   IllegalArgumentException ofLiteral throws and wraps it as
   SsrfPolicyException(INVALID_HOST), the same path IDN.toASCII already
   used. Falsifier checked — does it newly reject a legitimate
   IPv4-mapped literal [::ffff:a.b.c.d] that URI.getHost() emits and that
   today flows to the IpBlocklist embedded-v4 decode? No: ofLiteral
   accepts IPv4-mapped literals (the diff's own no-regression test
   canonicalizeHostAcceptsBracketedIpv4MappedLiteral pins this), and the
   embedded-v4 decode in IpBlocklist.embeddedV4 still runs on the
   resolved bytes, so the §SSRF "embedded-v4 cannot be reached by
   spelling it as IPv6" defense is unchanged. ofLiteral performs no DNS,
   so no I/O is added to the hot path (no new DoS/timeout surface).

2. Redirect-cap-before-drain reorder (SsrfGuardedHttpClient.java:427-442).
   The over-cap hop now throws REDIRECT_CAP_EXCEEDED before draining the
   body it is about to discard, and explicitly closes the body
   (response.body().close()) to release the connection. Falsifier checked
   — does moving the drain skip any per-hop re-validation the spec's
   TOCTOU defense ("DNS is re-resolved after every redirect; the IP
   blocklist re-applies each hop") requires? No: resolveAndValidate runs
   at the top of every loop iteration (line 409) BEFORE the send and
   BEFORE the redirect/cap logic, so each followed hop is fully
   re-validated regardless of drain ordering. The drain on followed hops
   is still bodyCap-bounded (discardBounded, line 442). The change is
   correctness-neutral for the cap semantics and removes a wasted
   bodyCap-bounded read on the rejected hop — neutral-to-positive for the
   DoS budget.

3. isLoopbackV6 / isAllZeroV6 helper reuse (IpBlocklist.java:348-354).
   Verified byte-for-byte against the allZero(raw, fromInclusive,
   toExclusive) helper (lines 405-412): isAllZeroV6 -> allZero(raw,0,16)
   scans indices 0..15 (identical to the old i<16 loop); isLoopbackV6 ->
   allZero(raw,0,15) && raw[15]==1 scans 0..14 then checks index 15
   (identical to the old i<15 loop + raw[15]==1). The ::/:: and ::1
   blocklist behavior in isBlockedV6 is unchanged.

The remaining changed file is the ticket/STATUS bookkeeping (docs/plan),
which carries no runtime behavior.

No threat-model commitment is left undelivered by this diff. The
sensitive-surface inventory correctly reports auth, authorization, input
validation, ban handling, and audit-log surfaces as untouched, which
matches the diff.

RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: PERM-ESCAL
    SEVERITY: low
    PROMISE: docs/spec/security.md §Authorization model step 4.1-related
             timing-oracle commitment, recorded in the spec's step 3.5
             silent-drop rule and reflected in the prior router comment:
             "A missing row is the vanished-group race (concurrent removal
             after the step-3.5 approval read): silent drop ... throwing
             here was a timing oracle distinguishing removed-group state."
             The pre-diff router re-read groups WHERE removed_at IS NULL at
             step 4.1, so a group removed between the step-3.5 approval read
             and the membership write produced NO auto-promote, NO membership
             row, and NO command/chat processing.
    GAP: InboundRouter.java:613-623 — the step-4.1 path now does
         `dispatchScopeId = Objects.requireNonNull(approvedGroupId)` and
         immediately calls `groupAutoPromoteService.tryAutoPromote(...)` and
         `ensureGroupMembership(...)` with no re-validation of removed_at.
         The former `lookupGroupId` (SELECT ... AND removed_at IS NULL,
         deleted at InboundRouter.java:296-322 in the diff) is gone. The
         diff itself documents the new window at InboundRouter.java:597-607:
         "A group removed BETWEEN the step-3.5 approval read and this
         membership write now passes ... a benign membership INSERT for a
         just-removed group is tolerated rather than silently dropped."
         GroupApprovalCheck.dispatchByStatus only catches the
         already-removed-at-approval-read case (approved + removed_at !=
         null -> SilentDrop, GroupApprovalCheck.java:151-153); it cannot see
         a removal that lands AFTER its own SELECT.
    REPRO: An attacker @mentions the bot in an approved group at the same
           instant an admin (or the bot-removed cleanup path) soft-removes
           that group. If the removal commits after the step-3.5
           findApprovalRow SELECT but before step 4.1, the router writes an
           `is_group_admin = true` auto-promote row and a group_membership
           row against a removed group, and processes the inbound command /
           chat turn — operations the pre-diff code silent-dropped. The
           window is microseconds inside one synchronous handler and the
           attacker cannot reliably trigger or observe it; the resulting
           group-admin / membership rows are dormant because every
           subsequent @mention in the removed group resolves to SilentDrop
           (GroupApprovalCheck.java:151-153), so no command ever executes
           there again. Net effect is a defense-in-depth reduction (a write
           where there was previously none), not a reachable privilege gain.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

OUT-OF-MODEL:
  - The same step-3.5-to-step-4.1 window also lets one in-flight command /
    chat turn execute for a group removed in that microsecond window. The
    inbound message legitimately passed the approval gate when it arrived,
    and the spec models group removal as a soft-delete with no commitment
    about in-flight messages, so this is outside the documented threat model
    rather than a spec-promise gap. Flagged so the user can decide whether
    the spec should constrain in-flight handling across a concurrent removal.

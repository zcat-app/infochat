FINDINGS: (none)

The diff implements the §"Per-source UNKNOWN auto-disable" commitment that
auto-disable "stops the fetcher or stream-source worker from enqueueing new
posts" by firing a synchronous CDI SourceDisabled(sourceId) event from
PerSourceUnknownTracker.disableSource and observing it in the
NostrStreamSource.Registrar, which translates sourceId -> dispatchKey via a
Registrar-owned map and calls supervisor.stop(dispatchKey). Audited against
the threat model:

- Quarantine-exhaustion DoS defense (security.md §"Per-source UNKNOWN
  auto-disable", lines 947-969): the promise is delivered. The worker is
  stopped on disable; the residual in-flight buffer drains a bounded queue
  (INBOUND_CAPACITY) before exit, which the spec explicitly tolerates
  ("Posts already in the outbox or re-evaluation queue continue through
  their current evaluation stage unaffected").

- Keyspace-collision risk that the diff's own javadoc warns about
  (StreamSourceSupervisor.stop, NostrStreamSource:326-332): NOT reachable on
  this path. The observer only ever passes dispatchKeys it itself minted and
  stored in dispatchKeyBySource (NostrStreamSource:385); it never passes a
  FetchScheduler source key into supervisor.stop. remove() makes a repeated
  signal for an already-stopped source a no-op.

- Event ordering / admin notify (security.md §Failure handling throttled
  notifications): fire() is synchronous and precedes throttledAdminNotifier
  .notifyOnce, and both run only when the gated UPDATE
  (status='active' -> 'failed') actually transitioned a row (updated > 0,
  PerSourceUnknownTracker:139). An already-'failed' source produces no
  duplicate event and no double-notify. No audit_log write is promised for
  auto-disable, so no AUDIT-EVASION gap.

- DoS / event-loop blocking (threat-model DOS category): the synchronous
  source.stop() -> thread.join() chain runs on the Collector's scheduled
  re-eval onTick() thread, NOT the Provider messaging-adapter event loop the
  threat model calls out, and the join is bounded by draining a
  capacity-bounded queue. No unbounded loop.

- No new SQL is constructed from untrusted input; the disable UPDATE and the
  re-eval scan use parameterized statements. The JSONB-config readTree at
  NostrStreamSource:506/515 (flagged in the sensitive-surface inventory) is
  pre-existing code untouched by this diff (the diff only adds the
  dispatchKeyBySource map, the onSourceDisabled observer, and imports), so
  per the diff-only audit scope it is not a finding here.

OUT-OF-MODEL:
  - Multi-instance/HA assumption. The fix relies on the SourceDisabled CDI
    event reaching the StreamSourceSupervisor in the SAME JVM that holds the
    running Nostr worker. The system's single-active-instance advisory-lock
    enforcement (a separate, pre-existing mechanism) is what makes "the
    tracker and the worker are co-located in one JVM" true. If a future
    deployment ran multiple active Collector instances WITHOUT that lock, a
    source whose worker lives in instance B could be auto-disabled by
    instance A's tracker and keep enqueueing on B (the event never crosses
    the JVM boundary). This is outside the documented v1 threat model
    (single active instance is assumed), but flagged so the operator knows
    the worker-stop is intra-JVM only and does not survive a relaxation of
    the single-instance invariant.

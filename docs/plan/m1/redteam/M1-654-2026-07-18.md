RED-TEAM VERDICT: CLEAN

The diff closes a threat-model promise that was previously asserted but
unenforced. security.md §Prompt-injection defenses claims "Verification
(verification.md §Security) asserts the registry's name set equals the table
above byte-for-byte; CI fails on a mismatch in either direction." Before this
diff no test read the spec at all, and the drift the claim was meant to catch
had already occurred (verification.md enumerated five names while the registry
and security.md's table carried six, semanticSearch having been added by
M1-589). The diff makes the claim true.

Audit basis — the guard was checked against the REAL enforcement point, not
taken on faith:

- ChatToolRegistry.java:15-22 holds the static TOOL_NAMES set; toolNames()
  is the set the new test compares against the spec table.
- ChatToolDispatcher.java:140 rejects any name not in registry.toolNames()
  BEFORE any handler lookup or SQL. A handler present in the `tools` map but
  absent from the registry is therefore dead code, not a callable capability.
- ChatToolDispatcher.java:114-121 additionally fails construction (startup) if
  any registry name lacks a handler.
- ChatAgent.java:635 (model-initiated TOOL_CALL loop) and ChatAgent.java:535
  (the D28 deterministic semanticSearch pre-fetch) are the only tool-invocation
  paths in main/; both go through dispatch(), so the registry is the single
  gate on LLM capability. A repo-wide grep for langchain4j @Tool /
  ToolSpecification annotations returns no hits in main/ — the tool loop is
  hand-rolled, so there is no annotation-driven surface bypassing the registry.

Guard quality — the parser fails CLOSED in every direction that could widen
the LLM's capability:

- The assertion is SET EQUALITY (ChatToolAllowlistSpecParityTest.java:77-81),
  so a registry name with no spec row (capability widened without a spec
  amendment) and a spec row with no registry name both fail the build.
- Parsing is confined to the <!-- tool-allowlist:begin/end --> region
  (security.md:287, 298), so backticked tool names in surrounding prose cannot
  be miscounted as rows.
- Unrecognized lines inside the region FAIL rather than being skipped
  (:296-318). A skip-on-unrecognized parser would have been the real weakness:
  a spec restructure would silently shrink the parsed set and still compare
  equal to a correspondingly stale registry.
- A tool row relocated outside the markers, or a spec table restructure that
  defeats the row regex, produces a red build rather than a silent pass.
- parserIsNotVacuous (:243-251) is diagnostic rather than load-bearing (the
  parity assertion would already fail on an empty parse, since the registry is
  never empty), and it deliberately does not pin a count — so a future spec
  amendment adding a tool is covered automatically instead of requiring the
  guard to be edited first.
- Missing file or absent markers assert with an actionable message (:270-288);
  neither degrades to a pass.

The verification.md edit removes a stale second enumeration of the tool names
in favour of a pointer to the marker-delimited table. That is a reduction in
drift surface, not a weakening: the closed list remains stated at spec level in
security.md, which is the document the guard actually parses.

Remaining diff content (docs/plan/m1/STATUS.md, the ticket front-matter) is
process metadata with no runtime or trust-boundary effect.

OUT-OF-MODEL:
  - Third, unguarded enumeration of the tool names: ChatAgent.java:66-82 hard-
    codes the "Available tools:" block in the chat system prompt. This is a
    copy of the tool list that the new parity guard does not cover, so it can
    drift from the registry and the spec table. It is NOT a finding because it
    cannot widen capability in either direction: a name advertised in the
    prompt but absent from the registry is rejected at ChatToolDispatcher.java:140
    ("Unknown tool"), and a registry tool omitted from the prompt merely goes
    unadvertised. The threat model's commitment is scoped to "the agent's tool
    registry", not the prompt text, so extending the guard to a third surface
    would be a new commitment. Flagged so the user can decide whether the
    prompt block is worth folding into the same marker-parity mechanism as a
    usability/drift hardening.
  - Guard covers NAMES only, not the per-tool Notes column. The spec table's
    Notes carry security-relevant per-tool commitments (D59 world predicate and
    READY filtering on searchPosts/semanticSearch, getPost's
    existence-vs-no-access indistinguishability, listSaves "never returns
    another user's saves"). The threat model promises machine-checked parity of
    "the registry's name set" only, so name-only coverage delivers the stated
    promise in full. Those per-tool properties are behavioural and belong to
    per-tool tests rather than a spec-parity guard; noted only so the user is
    aware the guard's scope is names, not semantics.
  - Duplicate marker pair: the parser binds to the FIRST begin marker and the
    first end marker after it, so a hypothetical second marker block later in
    security.md would go unparsed. This cannot hide a registry name (extra
    registry names still fail set equality — the capability-widening direction
    stays fail-closed); it could only hide a spec-only row, the non-security
    direction. Requires a bizarre hand edit and is noted for completeness, not
    as an exploitable gap.

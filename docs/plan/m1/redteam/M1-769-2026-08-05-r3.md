ITEM 1 — Round-1 medium: a budget refusal burned the breaker's
HALF-OPEN recovery probe.

  Checked, not assumed:
  - CircuitBreakingLlmProvider.java:70-77 — the OPEN short-circuit
    throw happens BEFORE the try block, so a denied call never
    reaches the release arm and cannot return a probe it never
    earned. This is the first thing a "release" remediation can get
    wrong and it is right here.
  - CircuitBreakingLlmProvider.java:91-105 — the new
    `catch (RuntimeException e)` arm calls
    `breakerRegistry.releaseProbeForTask(task)` and rethrows. It is
    reached only by exceptions that escaped the two typed catches at
    :81 and :86, i.e. exactly where `LlmCallBudget.RefusedException`
    (declared `extends RuntimeException`, deliberately outside the
    `LlmCallFailedException` family) lands.
  - LlmCircuitBreakerRegistry.java:221 `releaseProbeForTask` →
    :261-269 private `releaseProbe` uses `breakersByKey.get(key)`
    (NOT `breakerFor`), so releasing against a key with no breaker
    entry allocates nothing — a refusal on a healthy endpoint cannot
    mint breaker state.
  - LlmCircuitBreakerRegistry.java:399-405
    `EndpointBreaker.releaseProbe` restores `state = OPEN;
    deadline = now;` — the probe is admissible again immediately,
    correct because the endpoint is exactly as overdue for a probe as
    it was before the acquisition. It does NOT close the breaker and
    does NOT zero the failure counter, so a refusal still asserts
    nothing about the endpoint (the separation the spec's "only
    transport failures trip it" sentence requires).
  - Non-vacuity of the pinning test:
    BudgetedLlmProviderTest.refusalReturnsTheBreakersRecoveryProbeInsteadOfBurningIt
    builds a SECOND registry on a SteppableClock and advances past
    the cooldown. Round 1's core complaint was that the existing test
    only exercised a CLOSED breaker, where `tryAcquire`
    (registry :358-373, `case CLOSED -> true`) does not mutate. The
    new leg drives OPEN → cooldown elapsed → HALF_OPEN, then asserts
    the probe is still on offer AND that a following unbound call
    reaches the stub and closes the breaker. Both assertions are
    needed; either alone would pass against the burning
    implementation.

  Judged closed because: the release is reached by construction (the
  refusal type is provably outside both typed catches), it cannot be
  reached from the short-circuit path, it does not manufacture
  breaker state, and the pinning test is non-vacuous against a
  steppable clock by explicit construction.

    LlmCircuitBreakerRegistryTest.interruptedCallDoesNotResetTheConsecutiveCount

    :309 `private enum TransportKind { LLM, EMBEDDINGS }`;
    :295 `llmKey(ModelTask)` and :299 `embeddingsKey()` are the only
    two constructors of a key. I checked that EVERY public entry
    point routes through one of them — :167/:172 wouldShortCircuit,
    :182 tryAcquireForTask, :221 releaseProbeForTask, :226

    record* pairs — so no residual endpoint-string path survives.
  - This makes the code match docs/spec/security.md §Failure handling

  - Checked the change does not weaken the chat-mode pre-fetch
    promise: the D28 skip is gated on `wouldShortCircuit(CHAT_AGENT)`
    (the LLM key). With embeddings separated, an embeddings-only
    outage no longer opens the chat breaker — but the pre-fetch's
    embed then short-circuits at its OWN breaker with no HTTP
    attempt, and the pgvector probe does not run on a failed embed.
    Net cost nil, so "bounded cost at most once per breaker cycle"

  (b) Probe ownership — checked, not assumed:
  - LlmCircuitBreakerRegistry.java:343
    `private @Nullable Thread probeOwner`; :369 set inside
    `tryAcquire` ONLY on the OPEN/HALF_OPEN branch — a CLOSED-branch
    acquisition (:360) never claims ownership, which is precisely the
    straggler class the finding described.
  - :399-405 `releaseProbe` requires
    `state == HALF_OPEN && probeOwner == Thread.currentThread()`.
  - I walked the four interleavings that could defeat it:
      * straggler admitted while CLOSED releases after a trip plus a
        cooldown while a newer caller holds the probe → owner
        mismatch → no-op. Correct.
      * probe holder's call succeeds → :427 `probeOwner = null` → a
        later stale release is a no-op. Safe direction.
      * a different thread's failure re-opens from HALF_OPEN → :446

  - Thread identity is sound here only because acquire and release

3. ATTACKS ATTEMPTED THAT DID NOT PAN OUT
----------------------------------------------------------------

The remediation surface is availability/cost, so these are the
boundaries probed and why each failed to yield a gap.

A. "The ScopedValue budget binding is absent on the threads that
   actually spend." — The binder is DigestRenderer.java:285
   (`LlmCallBudget.callWith(systemLlmBudget.forRender(groupId), ...)`)
   INSIDE `renderSections`, not around DigestWorker's
   `renderExecutor.submit`. If anything beneath it hopped threads,
   every draw would silently vanish and the deployment would look
   metered while being unmetered — the highest-value failure
   available here. Grepped the whole provider main tree for
   `parallel|CompletableFuture|ExecutorService|submit\(|Thread\.ofVirtual|supplyAsync|invokeAll`:
   the only hits are DigestScheduler:221 and DigestWorker:253 (both
   ABOVE the binder) and an unrelated PG listener. No fan-out exists
   beneath `renderSections`. No gap.

B. "A refused call escapes as an unhandled RuntimeException and drops
   the whole digest." — The spec's degrade-not-drop posture and the
   diff's own argument both rest on every generative caller under the
   binder catching RuntimeException. The headline display-hit leg is
   NEW to the budget in this diff (M1-767 excluded it), so it was the
   most likely uncovered caller. Checked all four:
   SummaryProseGenerator.java:113 and :144;
   CategoryRollupGenerator.java:215; TranslationPipeline.java:143 and
   :334 (`run` and `runForDisplayHit`, both falling back via
   `fallbackWithNote`). All catch RuntimeException. No gap.

C. "There is a provider call under the render the budget cannot see."
   — Grepped the digest package for
   `\.generate\(|translationPipeline\.|llmRouter\.`. Five live sites,
   all beneath `renderSections`, EXCEPT DigestRenderer.java:605,
   which I confirmed by reading :560-616 is inside
   `renderSummarySections` (the user-initiated `/summary` route that
   must NOT draw). Also confirmed LlmTranslationProvider.java:93-94
   reaches the budget by going through `LlmProvider.generate`, and
   LlmRouter.java:174 resolves providers from a CDI
   `Instance<LlmProvider>` so the decorator really applies. No gap.

D. "The new decorator is bypassable or mis-ordered." —
   BudgetedLlmProvider.java:60 is `APPLICATION + 200`, i.e. INSIDE
   CircuitBreakingLlmProvider's `APPLICATION + 100`. Verified the
   consequence that matters: a breaker-OPEN short-circuit throws at
   CircuitBreakingLlmProvider.java:74 one layer out and therefore
   never reaches the draw, so an outage charges nothing
   (DigestRenderCallAccountingTest.openBreakerRenderDrawsNothing
   asserts both `providerCalls()==0` and `callsInWindow()==0`).
   No gap.

E. "Concurrent renders overshoot the ceiling." —
   SystemLlmBudget.java:303 `tryDraw` is `synchronized`, and the
   check (:305) and the charge (:308) share that monitor, so the
   check-then-act window that exists across ADMISSIONS cannot exist
   across DRAWS. Pinned by
   SystemLlmBudgetFairnessTest.concurrentRendersCanNeverPushTheWindowPastTheCeiling
   (8 virtual threads, exact-equality assertion in both directions).
   No gap.

F. "An adversary arms the interrupt flag to stop the breaker ever
   tripping, so every turn pays a full timeout instead of failing
   fast." — Repeated `/stop` on chat turns does discard transport
   evidence at CircuitBreakingLlmProvider.java:82-84. But this is
   strictly BETTER than the pre-diff behaviour, which recorded such
   calls as REACHABLE and actively zeroed the counter
   (registry :424). Discarding beats un-tripping; an interrupted call
   sends no bytes, so the attacker's own calls cost nothing, and
   honest callers still advance the counter. Not a regression, so not
   a finding.

G. "The release path collapses the cooldown, so doomed HTTP attempts
   become unbounded during an outage." — Traced it: during a
   cooldown, `tryAcquire` (:362 `now.isBefore(deadline)`) denies, and
   the denial throws at :74 BEFORE the try, so a refused or
   interrupted call cannot release during the cooldown at all. Only
   the single caller that wins the probe can release, and if the next
   probe fails for real, :442-450 re-opens with a fresh cooldown.
   Steady state remains roughly one doomed attempt per cooldown,
   which is what the spec promises. No gap.

H. "A hostile endpoint reply (in scope per §Trust boundaries item 9)
   throws an untyped RuntimeException and steers the new release
   arm." — Read the embedding parser end to end
   (OpenAiCompatibleEmbeddingProvider.java:205-299): every divergence
   a hostile reply can produce — bad JSON, missing / duplicate /
   out-of-range `index`, non-array or non-numeric `embedding`, short
   reply — is raised as the typed `EmbeddingCallFailedException`. A
   throw-site census of that file returns typed exceptions only. The
   untyped class is not endpoint-steerable. No gap.

I. "The embedding decorator lacks the LLM twin's
   `catch (RuntimeException)` release arm, so the general invariant
   is asymmetric." — A real asymmetry
   (CircuitBreakingEmbeddingProvider has no third catch), but I
   checked reachability before writing it up: there is exactly ONE
   production `EmbeddingProvider` impl (grep for
   `implements EmbeddingProvider` — the rest are test doubles), the
   embedding side has no budget decorator and hence no
   RefusedException source, and per (H) a hostile reply cannot mint
   an untyped throw. Not currently reachable, so reporting it would
   be manufacturing. Recorded here as the boundary rather than as a
   finding.

J. "The retargeted DigestRendererTest methods dropped a control." —
   Tests are controls, so a retarget that silently removes coverage
   counts. Checked: both methods keep non-vacuity controls
   (`translatorCalls.get()==3`, `distinctProse.generateCalls()==1`,
   `proseGenerator.callCount()==3`), and the exact-count assertions
   moved to DigestRenderCallAccountingTest, which drives a REAL
   provider chain and asserts
   `chain.providerCalls() == budget.callsInWindow()` rather than a
   hand-computed literal. Coverage moved, not lost. No gap.

K. "Secrets or user content leak through the new log or exception
   text." — `RefusedException` (BudgetedLlmProvider.java:77) carries
   only `task.keySegment()`, no prompt and no endpoint. The breaker's
   new `label` (registry :315-321) is `endpoint + " (" + kind + ")"`;
   the endpoint was already logged pre-diff, and §Secrets handling
   puts console logs through the closed API-key catalogue redactor.
   No new exposure.

L. "Something the diff reroutes drops an incidental control." —
   DigestRenderer's old translation-cache probe in
   `appendClusterProse` was deleted, so I checked that the cache
   probe which ACTUALLY gates spend survives: DigestRenderer.java:939-948
   still probes `translationCache` and still decrements
   `translationMaxPerRender` (the M1-756 per-render headline budget).
   That control survives the reroute intact. No gap.

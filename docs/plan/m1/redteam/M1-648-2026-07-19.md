RED-TEAM VERDICT: CLEAN

Audited: M1-648 (working tree vs 6d99686e), diff target/redteam-diff-M1-648.diff
Threat model: docs/spec/security.md (read in full)

Surfaces probed and the evidence that closed each one:

1. Tool-allowlist closure (§Prompt-injection defenses, "The v1 list is closed at
   spec level"). ChatToolRegistry.java:14-27 adds "helpLookup"; the spec's marked
   table (docs/spec/security.md:297, between tool-allowlist:begin/end) gains the
   matching row in the same diff; ChatToolAllowlistSpecParityTest.java exists and
   is the CI parity guard the spec demands. ChatToolDispatcher.java:88-97 wires a
   handler, and requireHandlerForEveryAdvertisedTool (line 117) fails startup on
   registry/wiring drift. No name enters the registry without a spec row.

2. "All free-form string and list inputs ... are length-bounded ... rejected by
   the tool dispatcher before any SQL runs." Delivered generically, not per-tool:
   ChatToolDispatcher.validateInputLengths (line 207) walks EVERY arg entry and
   validateValue (line 221) caps any String at inputMaxLength before the cache
   key, the call-budget draw, or tool.execute. helpLookup's `query` inherits it
   with no per-tool opt-in required.

3. "Every argument is type-checked ... before the underlying SQL runs."
   HelpLookupTool.java:91 does an unchecked (String) cast, but the dispatcher
   catches ClassCastException (line 196) and returns a typed ValidationError with
   no Java exception text ("The Java exception text is not surfaced; it would leak
   internals"). A `{"query": null}` NPE escapes the dispatcher, but ChatAgent's
   catch-all (ChatAgent.java:278-292) converts it to the localized
   ERROR_CHAT_UNAVAILABLE via SafeLog with a null commit — turn discarded, no
   session advance, no stack trace to the user. Matches §Failure handling.

4. Tier-filter-before-return / no existence oracle (§Prompt-injection defenses,
   helpLookup row: "a hidden command's name never enters the LLM context").
   HelpLookupTool.java:107-111 resolves the tier and visible set BEFORE the SQL;
   DocEmbeddingDao.nearestVisible (line 1011 of diff) binds
   `target_ref = ANY(?)` inside the WHERE, so a non-visible doc can never rank.
   visibleCommandNames (HelpCommandHandler.java:1159) reuses the exact `visible`
   predicate (line 384) that bare /help and the M1-647 suggestion vocabulary use,
   including the probation delegation to
   CommandPermissions.allowedDuringProbation. Verified the filter is not merely a
   post-filter: the `ORDER BY ... , doc_id` tiebreak plus the in-WHERE ANY()
   restriction means a hidden name cannot appear even under a partial index scan
   (worst case is a false negative, never a false positive).

5. Tier-fact parity between the two entry points. resolveTierForChat
   (HelpCommandHandler.java:457) vs resolveTier (line 431): both read is_admin for
   the caller only, both gate groupAdmin on group scope, both consult
   probationCheck. scopeKind is "dm"/"group" from InboundRouter.chatModeScopeKindOf
   (line 1536) and scopeId in group scope is the approved groups.id
   (InboundRouter.java:735) — the same id resolveTier derives via
   findApprovalRow, so isGroupAdmin(scopeId, userId) is the identical lookup.
   lookupIsAdminById returns `rs.next() && rs.getBoolean(...)` — a missing row
   fails closed to non-admin.

6. Match-not-assert (§helpLookup row: "every byte of the returned help body comes
   from the runtime catalogue + bundles"). composeDetailIfVisible
   (HelpCommandHandler.java:1177) re-walks CATALOGUE and re-applies `visible`
   before composing; the DB supplies only target_ref, which by construction is a
   member of the visible set just bound into the query. Indexed text reaches the
   output on no path.

7. LLM trust boundary. Tool output is wrapped in the per-call random
   UNTRUSTED_CONTENT marker (ChatAgent.java:651-655) exactly as other tools are,
   and is never delivered to the user directly; the model's reply routes through
   the existing sanitize path (ChatAgent.java:461). Bodies are static bundle text
   with no inbound interpolation, and SearchPostsTool.jsonStr delegates to
   JsonEscaper, so no structural injection into the prompt.

8. Cancellation (§commands.md Conversation control, spec-load-bearing for /stop).
   HelpLookupTool.java:644 calls cancellationService.armToolConnection on the
   pooled connection before the single read-only pgvector query, matching the
   SemanticSearchTool precedent, and both commands.md and design/03 were amended
   to declare the primitive for the new tool.

9. SQL surface. Every DocEmbeddingDao statement is a PreparedStatement with bound
   parameters, including the two array binds via conn.createArrayOf and the vector
   literals via setString + ?::vector cast. No string-concatenated user or model
   input anywhere in main/ (the only concatenated SQL is in the two new *IT test
   fixtures, against constants).

10. DB least-privilege (§DB roles, "a SQL-injection bug in the Provider cannot
    ..."). V60__doc_embedding.sql grants only SELECT, INSERT, DELETE to
    infochat_provider and nothing to the collector; UPDATE is withheld and the
    DAO's upsert is DELETE-then-INSERT in one transaction to match, so the
    narrower grant is exercised rather than bypassed by a privileged DevServices
    role.

11. Rate limiting / DOS (§Rate limiting, "Tool calls per chat turn — fixed cap").
    helpLookup adds one embed round-trip plus one indexed query per call, inside
    the existing 25-call per-turn cap with identical-call caching
    (ChatToolDispatcher.java:170-183), inside the per-user LLM bucket that already
    meters the turn. Same cost shape as the already-allowlisted semanticSearch;
    no new unmetered surface.

12. Startup builder. CommandIntentIndexBuilder catches RuntimeException and
    logs+continues; EmbeddingProvider.embed declares no checked exceptions and the
    DAO wraps SQLException into IllegalStateException, so the fail-open posture
    D66/llm.md commit to is actually reachable. The build reads no
    attacker-controlled input — the corpus is derived from the compiled CATALOGUE
    and the immutable Map.ofEntries synonym seed (widened to public read-only
    access only).

No commitment in docs/spec/security.md is left undelivered by this diff.

OUT-OF-MODEL:
  - Recall shrinkage as a weak existence signal. HelpLookupTool omits the
    `SET LOCAL hnsw.iterative_scan = strict_order` that SemanticSearchTool arms
    (SemanticSearchTool.java:117-121) for the same filter-inside-the-index-query
    shape. If the planner does choose an HNSW scan with incremental sort, the
    ef_search candidate window is filtered by target_ref afterwards, so a visible
    doc within threshold could in principle be missed. I could not substantiate
    this as a finding: the direction is strictly fail-closed (false negatives
    only, never surfacing a hidden command), the corpus is ~41 rows against a
    default ef_search of 40, and the observable outcome — "no command matched" —
    is byte-identical to the designed below-threshold answer, so it carries no
    extra bit about hidden commands. Flagged only so the user can decide whether
    the threat model should state a recall-exactness requirement for the second
    corpus the way it does for the post corpus's world predicate.
  - Sanitizer-vs-helpLookup interaction (usability/audit-noise, not a weakening).
    §LLM output sanitizer strips or refuses LLM output containing admin command
    strings and audit-logs "every match ... per-occurrence, not throttled".
    helpLookup is the first tool that deliberately feeds bot-admin command syntax
    (/grant-admin, /ban usage bodies) into the LLM context for admin callers, so a
    bot admin asking a discovery question in chat will reliably produce a
    stripped/refused reply plus an untrottled audit row. The security property
    holds — this is the sanitizer working — but the threat model does not describe
    the resulting degraded admin-discovery UX or the audit volume, and the user may
    want to decide whether that interaction is intended.

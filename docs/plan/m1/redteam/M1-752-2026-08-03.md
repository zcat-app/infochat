RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: DOS
    SEVERITY: medium
    PROMISE: security.md §Failure handling — "**Per-source UNKNOWN auto-disable.** A source whose Stage 2 UNKNOWN
              rate exceeds a profile-driven threshold ... has its `source.status` transitioned to `'failed'` (the same
              status used for consecutive HTTP failures, decision D42 — but **excluded from D42's automatic re-probe
              rung**: this park is a security control, its park-reason discriminator marks it manual-only, and recovery
              happens only via `/source-enable`)" (docs/spec/security.md:1540-1546), and decisions.md:59 (D42 amended)
              — "`status='failed'` has two other writers whose recovery stays manual by design ... automatically
              re-enabling an adversary-influenced feed would defeat it ... re-probe eligibility is decided on that
              reason, never on bare `status='failed'`."
    GAP: The whole exclusion rests on one mutable column, and neither the amendment nor its implementing ticket says
         the reason write is guarded or that any writer has precedence. docs/spec/decisions.md:59 and
         docs/plan/m1/tickets/M1-754-parked-source-reprobe-ladder.md:62-67 require only that "All three park writers
         record their reason in the same statement that sets `status='failed'` (no two-step write)" — a same-statement
         requirement, not a same-condition one. The D42 ladder's existing statement
         (infochat-collector/src/main/java/app/zcat/infochat/collector/fetch/SourceRepository.java:65-75) guards ONLY
         the status flip behind `WHEN consecutive_failures + 1 >= ? AND status = 'active'`; every other SET term fires
         unconditionally, deliberately so ("The increment itself fires unconditionally — even on a 'failed' row",
         SourceRepository.java:62-64). The symmetric edit — adding `park_reason = 'fetch-failure'` to that SET list —
         therefore relabels a row parked seconds earlier by
         PerSourceUnknownTracker.java:148 (`UPDATE source SET status = 'failed' WHERE id = ? AND status = 'active'`),
         and the row silently becomes re-probe-eligible. The exclusion legs in
         M1-754...md:83-90 seed a static parked row and assert zero probes, so they cannot detect a reason written
         after the park.
    REPRO: Adversary controls (or can post into) an ingested feed. (1) Publish borderline content that Stage 2 labels
           UNKNOWN at a rate above the per-source threshold — the quarantine-exhaustion defense the spec says exists.
           (2) At the same time make the feed's HTTP endpoint hang: the fetch tick enumerates the source while it is
           still `active`, then blocks until the read timeout. (3) PerSourceUnknownTracker fires during the hang and
           parks the row with reason `unknown-rate`. (4) The hung fetch times out; the ladder's UPDATE runs against the
           now-`failed` row, leaves `status` alone (CASE-guarded) but rewrites `park_reason = 'fetch-failure'`.
           (5) Hours later the re-probe ladder selects the row, the adversary answers 200, and the feed is restored to
           `active` with `consecutive_failures = 0` — the security park is gone, no admin acted, and the adversary
           resumes flooding admin review capacity. Timing is adversary-chosen (they control both the UNKNOWN stream and
           the hang duration), so the race is steerable, not lucky.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

  - CATEGORY: DOS
    SEVERITY: medium
    PROMISE: decisions.md:59 (D42 as amended) — "The source row therefore records *why* it parked (park-reason
              discriminator, `schema.md` §Sources and tags), and re-probe eligibility is decided on that reason, never
              on bare `status='failed'`." Same commitment restated at docs/spec/security.md:1367-1371 and
              docs/spec/schema.md:262-273 ("UNKNOWN-rate and cycle-cap parks never recover automatically").
    GAP: The amendment defines no value for rows that are ALREADY parked when the discriminator ships, and states no
         fail-closed rule for an absent/unknown reason. M1-754's acceptance
         (docs/plan/m1/tickets/M1-754-parked-source-reprobe-ladder.md:58-67) specifies the column as "nullable, null
         when not parked" and says nothing about backfill; its selection predicate
         (M1-754...md:171-174, `status='failed' AND park_reason = 'fetch-failure' AND next probe due AND under cap`)
         is silent on NULL. The amendment's own motivating evidence — "16 of 79 sources (20%) sat parked, 11 of them
         healthy at probe time" (decisions.md:59) — is a direct incentive to backfill every existing `status='failed'`
         row to `fetch-failure` so the migration actually recovers those 11, which is precisely the
         "decided on bare `status='failed'`" behaviour the row forbids. The spec should have pinned the migration's
         disposition of pre-existing parked rows (fail-closed: no reason ⇒ never re-probed) rather than leaving it to
         the implementer under that pressure.
    REPRO: A source parked today by the UNKNOWN-rate control (or by D38's cycle cap) sits in `status='failed'` with no
           reason column. M1-754's migration lands; a backfill of `park_reason='fetch-failure'` for existing failed
           rows (or a re-probe predicate written as `park_reason IS DISTINCT FROM 'unknown-rate'`, equally permitted by
           the spec text) makes that row re-probe-eligible on the first ladder tick. The adversary who caused the
           original auto-disable simply keeps their endpoint answering; the feed is restored automatically and the
           quarantine-exhaustion defense is lifted with no admin action and no operator-visible statement that a
           security park was converted into a recoverable one.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

  - CATEGORY: AUDIT-EVASION
    SEVERITY: medium
    PROMISE: schema.md invariant 7 — "**Audit-before-effect.** Privileged actions write to `audit_log` *before* their
              side effects, so an interrupted command leaves a record of intent" (docs/spec/schema.md:787-796), and the
              directly analogous system-actor rule in security.md §Re-evaluation job: "**The transition is
              audit-logged** as `RE_EVAL_RELEASED` with `actor='re_eval_job'` ... Without this, posts auto-released
              from `QUARANTINED` ... reach users with no human reviewer ever having seen the row" (security.md:1514-1525).
    GAP: The amendment adds a NON-admin writer of the `failed → active` transition (docs/spec/schema.md:268-273,
         docs/spec/decisions.md:59, docs/spec/security.md:1363-1367) and commits only to "a throttled RECOVERED admin
         notification". No audit row is specified, and M1-754's acceptance
         (docs/plan/m1/tickets/M1-754-parked-source-reprobe-ladder.md:68-90) lists none. Until this diff, every
         `failed → active` transition was audit-logged: SourceEnableCommandHandler writes
         `AuditAction.SOURCE_ENABLE` (and a pre-write `SOURCE_ENABLE_INTENT` on the soft-deleted branch) in the same
         transaction as the UPDATE (SourceEnableCommandHandler.java:232, :257, :315). The replacement path drops that
         control. The only remaining signal is a notification the spec elsewhere allows to be coalesced —
         "Admin notifications are coalesced per `(channel, error_class)`" (security.md:1400-1402) and notifyOnce keyed
         per source UUID (FetchScheduler.java:516-519) — i.e. lossy and non-durable, whereas `audit_log` is
         append-only (schema.md invariant 10) and is the surface `/audit` reads.
    REPRO: Adversary owns a feed. They let it fail N times (park), sit out the backoff, then answer one probe (restore),
           then fail again — repeatedly. Each restore re-opens ingest from their feed. An operator investigating later
           ("was source X live on the 4th?") finds no audit row for any of the transitions; the RECOVERED notifications
           were coalesced into one summary or throttled away, and no record survives of when, how often, or on whose
           authority a globally-shared source row (D7) went back to `active`. Compare a bot admin doing the same thing
           by hand, which leaves a `SOURCE_ENABLE` row with actor and request_id.
    SUGGESTED-FIX-CLASS: audit-log-coverage

  - CATEGORY: INFO-LEAK
    SEVERITY: medium
    PROMISE: schema.md §Sources and tags — "Status is **orthogonal** to the soft-delete column `deleted_at`: the latter
              records 'user removed this from a scope and the source has no remaining subscribers' and hides the row
              from listings. The fetcher / StreamSource scheduler selects rows where `status = 'active'` AND
              `deleted_at IS NULL`" (docs/spec/schema.md:256-260). Also security.md §SSRF and outbound connections —
              "Every outbound connection from the Collector (feeds, redirects, and `StreamSource` connections) ... runs
              through a fail-closed allowlist (decision D20)" (security.md:196-207).
    GAP: The amendment creates a NEW outbound-fetch selection path — "run off the active fetch path so re-probes can
         never delay healthy sources" (docs/spec/decisions.md:59) — and enumerates none of the guards the path it
         parallels carries. The concrete selection recorded in the implementing ticket is
         `status='failed' AND park_reason = 'fetch-failure' AND next probe due AND under cap`
         (docs/plan/m1/tickets/M1-754-parked-source-reprobe-ladder.md:171-174): no `deleted_at IS NULL`, though every
         existing enumeration carries it (FetchScheduler.java:456, :714-719, :749-753), and no statement that the probe
         goes through the shared `infochat-ssrf` allowlist rather than a bespoke HTTP call on the new scheduling path.
         The human equivalent treats reviving a soft-deleted source as the higher-risk act: `/source-enable` on a
         soft-deleted row is confirm-gated with a pre-written `SOURCE_ENABLE_INTENT` audit row
         (SourceEnableCommandHandler.java:253-265). The automatic path as specified has no `deleted_at` notion at all.
    REPRO: A bot admin `/remove-source`s a feed that turned hostile (hard delete is forbidden by invariant 4, so removal
           == `deleted_at` set); the row's `status` stays `'failed'` from the earlier fetch ladder, because status and
           `deleted_at` are orthogonal. The re-probe ladder selects it on reason alone and keeps issuing outbound
           requests to that endpoint on the whole backoff schedule — telling a source the operator deliberately cut off
           that the deployment is still live and still polling it — and on the first 200 flips the row back to
           `status='active'`, resurrecting a state the admin's removal was meant to end (and re-arming the
           "an exclusion re-applies if the source is later revived" semantics at schema.md:290-292). If the probe is
           also implemented off the shared SSRF module, a parked source whose DNS has since been re-pointed at
           169.254.169.254 is probed without the blocklist/rebind checks the active path applies on every hop.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

OUT-OF-MODEL:
  - Lapsed-domain takeover of a parked source. A source parks precisely because its upstream is dead, and a dead domain
    can be re-registered by an adversary; the amendment revives it automatically with no re-validation that the
    identifier still belongs to whoever the operator originally approved. Noted rather than filed as a finding because
    v1 re-validates source ownership on NO path — a live source that changes hands has the same exposure — and ingested
    content still passes Stage 1/2, so the delta this diff introduces is the loss of a human checkpoint, not a new
    class of attack. Worth deciding explicitly if the operator considers "an admin looked at it before it came back"
    part of the source-approval story.

FINDINGS:
  - CATEGORY: AUDIT-EVASION
    SEVERITY: medium
    PROMISE: From `docs/spec/security.md` §Authorization model, evaluation order step 8: "Audit-log the intent." The spec lists audit-log as a deterministic step that runs after the permission check and before execution — applying to every inbound dispatched command, with privileged-tier reads explicitly covered by the corpus pattern (compare `ListSourcesCommandHandler` line 142–151 which writes a `privilegedReadAuditRow` precisely because "the unprivileged DM/group form intentionally leaves [the audit gap] open" — the privileged enumeration is audited because it discloses deployment-wide state).
    GAP: `infochat-provider/src/main/java/app/zcat/infochat/provider/command/ListGroupsCommandHandler.java` lines 71–125 (the entire `handle(...)` method) writes NO audit row. The class-level javadoc at line 642 ("Read-only handler: no audit row, no state mutation") declares the policy. The handler enumerates every `groups` row including each group's `id`, `approval_status`, `timezone`, `activated_by` contact id (redacted but identifiable by prefix/suffix), and active member count — global, deployment-wide state visible only to bot admins. The corpus precedent in `ListSourcesCommandHandler` (line 151 `writePrivilegedReadAuditRow`) audits an analogous privileged-tier admin enumeration; `/list-groups` is the same shape (admin-only, deployment-wide enumeration, contact ids surfaced) yet writes no row.
    REPRO: A compromised bot admin issues `/list-groups --page 1`, `/list-groups --page 2`, ..., enumerating every group's `(id, approval_status, redacted activator contact, member count, timezone)` across the deployment. No audit trail is written. A forensic investigator reviewing audit_log later cannot establish which admin enumerated the group inventory, when, or how often. The redacted activator contact id is reversible by anyone who already knows the contact id prefix/suffix (the redaction is identity-preserving for known contacts), so the disclosure scope is non-trivial — yet the operation is invisible in `/audit`.
    SUGGESTED-FIX-CLASS: audit-log-coverage

OUT-OF-MODEL:
  - The `escapeJson` helper in `ApproveGroupCommandHandler` / `RejectGroupCommandHandler` (constructed via string concatenation rather than a structured JSON builder) is correct under the current set of fields written (`adapter`, `upstream_group_id`, `approval_status` — DB-typed values with bounded shapes); if future details_json additions append free-form user-authored text, the closed-API-key catalogue redactor (§Secrets handling) would need to be applied to that text before insertion. Out of model for this diff because the current fields cannot carry user-authored prose.
  - The `RejectGroupCommandHandler.lookupActor` outside-transaction admin check (line 913) followed by an audit-row write (line 963) on a separate auto-commit connection has a small TOCTOU window where a concurrent `/revoke-admin` could land between the two; the resulting `REJECT_GROUP_INTENT` row would record an admin's intent that, at audit-write time, no longer holds is_admin. The confirm-leg in-tx `FOR UPDATE` re-check at line 994 prevents privilege-escalation execution, so the only artifact is audit-row pollution. Out of model because the threat model does not promise audit-row producer-side authorization revalidation; the inbound-side ban check + the in-tx re-check are the documented gates.

RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: DOS
    SEVERITY: high
    PROMISE: "A per-post attempt counter bounds retries; the infra-failure class and the UNKNOWN class carry separate, independent caps [...] INJECTION, MALWARE, or UNKNOWN on either class -> post stays QUARANTINED, the stage2_failed flag is preserved, and the attempt counter increments."
    GAP: In `infochat-collector/src/main/java/app/zcat/infochat/collector/eval/reeval/ReEvaluationJob.java:106-121`, the `processOne` method increments the attempt counter for ALL non-BENIGN verdicts including `INFRA_FAILURE`. The spec limits counter increments to `INJECTION`, `MALWARE`, or `UNKNOWN` verdicts only. `INFRA_FAILURE` is a transient condition (LLM unreachable) that should not consume an attempt. When `judgeBody()` returns `INFRA_FAILURE` (line 115 returning from `Stage2Worker.invokeWithRetryOnce` at line 179 of `Stage2Worker.java`), the code falls through to `incrementAttemptCounter` at line 120.
    REPRO: An attacker does not need to act; a temporary LLM outage during a re-eval tick is sufficient. If the LLM is unreachable for N consecutive re-eval ticks where N equals the cap (e.g., 3 for infra-failure class, 2 for UNKNOWN class), every post currently in the re-eval queue has its counter exhausted and transitions to NEEDS_REVIEW. The entire re-eval queue is permanently drained into the manual admin queue despite the LLM never having successfully evaluated any of those posts during re-eval. When the LLM recovers, there are no posts left to re-evaluate. This defeats the purpose of the re-eval job and shifts all triage burden to human admins for what could be hundreds of posts.
    SUGGESTED-FIX-CLASS: other

  - CATEGORY: AUDIT-EVASION
    SEVERITY: medium
    PROMISE: "approve and reject run as stored procedures [...] that internally read the original under the procedure's elevated rights and perform the restore + audit-log + NOTIFY in one transaction"
    GAP: `infochat-collector/src/main/java/app/zcat/infochat/collector/eval/reeval/AdminReviewTtlJob.java:96-121` transitions quarantine rows from PENDING to REJECTED and posts from NEEDS_REVIEW to QUARANTINED without writing any audit_log entry. The stored procedure `reject_quarantine` (V21__quarantine_admin.sql:112) writes an audit row for admin-initiated rejections, but the TTL auto-reject path bypasses the stored procedure and writes no audit. A quarantine row can permanently transition to REJECTED with no audit trail entry recording who or what caused the transition, when, or why.
    REPRO: A post enters NEEDS_REVIEW with a PENDING quarantine row. The admin-review TTL expires (24 hours in the test config). The TTL job runs `rejectExpired()` which transitions the quarantine to REJECTED and the post to QUARANTINED. An admin querying `audit_log` for this quarantine_id finds no REJECT row — the rejection is invisible in the audit trail. In a forensic review, the admin cannot distinguish a TTL-expired auto-reject from a database anomaly or a bug.
    SUGGESTED-FIX-CLASS: audit-log-coverage

  - CATEGORY: DOS
    SEVERITY: medium
    PROMISE: "Per-source UNKNOWN auto-disable. A source whose Stage 2 UNKNOWN rate exceeds a profile-driven threshold over a profile-driven rolling window has its source.status transitioned to 'failed'"
    GAP: `infochat-collector/src/main/java/app/zcat/infochat/collector/eval/reeval/PerSourceUnknownTracker.java:96-105`, the `checkAllSources` query counts ALL QUARANTINED posts with `stage2_done=TRUE AND stage2_failed=FALSE` as "UNKNOWN", but this filter also matches posts quarantined for INJECTION or MALWARE verdicts. The database schema stores no `stage2_verdict` column, so there is no way to distinguish UNKNOWN from INJECTION/MALWARE. A source with many legitimate INJECTION detections (e.g., a high-traffic feed that occasionally reposts injection-laden content) will have its "UNKNOWN rate" inflated by INJECTION verdicts it cannot control, leading to false-positive source disabling. The spec specifically says "UNKNOWN rate", not "hostile verdict rate" — the intent is to target the ambiguous verdict that signals judge degradation, not confirmed hostile content.
    REPRO: An RSS feed produces 10 posts per hour. 4 of them contain actual injection content and are correctly classified as INJECTION by Stage 2 (quarantined, stage2_done=true, stage2_failed=false). 6 are clean (BENIGN, released as READY). The UNKNOWN rate is 0%, but the tracker's query computes 4/10 = 40%. With a threshold of 0.5 this source stays active, but with a threshold of 0.3 it would be falsely disabled. The operator must then investigate and re-enable a source that has zero UNKNOWN verdicts.
    SUGGESTED-FIX-CLASS: other

OUT-OF-MODEL:
  - The `SECURITY DEFINER` stored procedures in V21__quarantine_admin.sql (lines 27, 86) do not include a `SET search_path = public` clause. PostgreSQL documentation warns that `SECURITY DEFINER` functions without a restricted `search_path` can be exploited if a caller can create objects in a schema that appears earlier in the search path. In this system the Provider role has no CREATE privilege and the DB is internal-only, so this is not exploitable under the current threat model, but it is a defense-in-depth gap if DB role grants ever widen. This pattern is pre-existing (V5 has the same gap) so it is not specific to this diff.

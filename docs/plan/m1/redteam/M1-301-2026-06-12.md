There is no code, SQL, auth logic, input-validation path, rate-limit, or
audit-log write in the diff. Nothing in the diff *delivers behavior*; it only
adjusts the system's stated commitments. The audit therefore reduces to: does
the amended threat model leave a self-inconsistency or a commitment that other
(untouched) spec text still promises but the amended text retracts in an
exploitable way?

Substance of the amendment: the per-adapter bot contact id (the value mention
recognition compares against) is downgraded from "derived from the adapter's
identity material at adapter startup; not an operator-typed property"
(deployment.md, old text) to "an operator-configured per-adapter property...
validated as non-blank at adapter startup" (deployment.md:138-146, new text).

Why this is not an in-model FINDING:
  - The threat model (security.md:27) classifies operator-set config
    (properties files, bootstrap JSON) as TRUSTED. An operator-typed bot
    contact id lands inside that trusted boundary; a "maliciously substituted"
    config value is an operator/host-compromise scenario, which security.md:29
    places out of scope for v1 (supply-chain attacks on operator
    infrastructure).
  - The amendment is self-consistent: it does not silently weaken a guarantee.
    security.md:537-548 ADDS an explicit §"Operator-typed bot-identity anchor"
    that discloses the exact residual risk (mistyped/substituted value silently
    misdirects mention recognition; no startup error beyond the non-blank
    check), assigns correctness to the operator, and flags auto-derivation as
    planned hardening. The CLAUDE.md engineering rule against silently trading
    away a spec security property is satisfied because the trade is documented,
    not silent.
  - The mention-recognition comparison itself is unchanged: messaging.md:46-60
    still mandates byte-equality of the cryptographic contact id and still
    forbids display-name matching. The amendment changes the *provenance* of the
    compared value (operator config vs. auto-derivation), not the comparison
    rule. An attacker who can only send arbitrary group text (the in-model
    adversary, security.md:16-19) still cannot forge a mention without matching
    the configured cryptographic anchor byte-for-byte.

No commitment in the threat model is left undelivered by this diff, because the
diff delivers no behavior — it is a coordinated spec amendment whose every
weakening is paired with an explicit disclosure inside the trusted-config
boundary.

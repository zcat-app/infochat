RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: INFO-LEAK
    SEVERITY: medium
    PROMISE: "LLMs (local or remote) are black boxes that can be coaxed into
              emitting attacker-chosen output. Local and remote LLMs have the
              same trust level." (security.md §Threat model) — remote LLM
              endpoints are NOT trusted parties; and §Secrets handling's
              posture treats the LLM API key as a secret whose exposure
              surfaces are enumerated and controlled ("LLM API keys are read
              from environment variables, not the DB"; closed redaction
              catalogue on every log/audit surface).
    GAP: The new shared api-key fallback resolves INDEPENDENTLY of the
         base-url axis. In OpenAiCompatibleProvider.java (~lines 166-185,
         diff hunk @@ -161,9 +166,27 @@) and AnthropicProvider.java (~lines
         133-155, hunk @@ -128,9 +133,26 @@), apiKey =
         per-task-key .or(infochat.llm.default.api-key) .orElse("") — so a
         task carrying a per-task base-url OVERRIDE but no per-task api-key
         inherits the deployment-wide credential and transmits it
         (Authorization: Bearer / x-api-key) to the OVERRIDDEN endpoint, not
         the endpoint the key was minted for. This cross-endpoint
         transmission is new in this diff (pre-D56, api-key never fell back
         across tasks; an unset per-task key meant empty). The hazard is
         actively advertised by the diff itself: LlmRouter.java's
         CONFIG_KEY_DEFAULT_API_KEY javadoc ("Split from the base-url key so
         a mixed deployment can still override one axis per task without
         restating the other"), prod/scripts/4-llm.sh remote-branch output
         ("a per-task infochat.llm.<task>.base-url override in the runtime
         application.properties can still pin one task by hand"), and
         prod/switch-llm.sh's header say to pin a task with a base-url line
         ONLY — none warns that the shared credential follows the pin. No
         guard covers the shape: LlmRouterStartupGuard scans only the
         base-url/provider/model axes; the off-host disclosure WARN names the
         route ("post bodies leave the host") but never that the shared
         api-key accompanies it. Mitigating context: operator-set config is
         trusted input in the threat model, so the trigger is operator
         action, not attacker input — but the receiving endpoint is a party
         the threat model explicitly classes as an untrusted black box, and
         the misconfiguration is the diff's own documented advice.
    REPRO: 1) Operator provisions remote backend via prod/scripts/4-llm.sh:
           wizard writes infochat.llm.default.base-url=https://provider-a/v1
           and infochat.llm.default.api-key=${INFOCHAT_LLM_API_KEY}
           (provider A's paid key in secrets.env).
           2) Following the wizard's printed advice, operator pins one task by
           hand with the single documented line, e.g.
           infochat.llm.chat.base-url=https://provider-b/v1 (a cheaper or
           experimental provider) — no per-task api-key, exactly as the text
           suggests.
           3) Boot succeeds; the disclosure WARN mentions only that chat's
           route is off-host. On the first chat call, apiKey falls back to
           the shared default and provider A's credential is sent in the
           Authorization header to provider B's server. Provider B — an
           endpoint the threat model treats as an untrusted black box — now
           holds a replayable billing/API credential for provider A. The same
           mechanism sends the remote key to the unauthenticated local Ollama
           (compose-network) when the pin target is local. The system gave no
           startup signal, no WARN, and no disclosure line about the
           credential's new destination.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

OUT-OF-MODEL:
  - switch-llm.sh mixed-config all-Enter is now a mutating run. Over an
    old-format MIXED file (e.g. chat remote, six tasks local — a shape the
    pre-M1-603 switcher itself created), the deployment-level default answer
    classifies as "remote" (chat.base-url fallback, prod/switch-llm.sh Phase
    1), so accepting all defaults sweeps every per-task line and routes all
    seven tasks to the remote provider — the deleted test
    allEnterIsByteIdenticalNoOpEvenWithARemoteTask pinned exactly this shape
    as a byte-identical no-op, and SwitchLlmWiringTest's javadoc still claims
    "an operator can inspect without fear of churn". Mitigations exist (the
    prompt says "for ALL generative tasks", a backup is written, the privacy
    disclosure fires and is accurate), and security.md's only commitment here
    — per-task disclosure correctness — is delivered, so this is a consent/
    expectation regression rather than a threat-model violation. Flagged for
    the user to decide whether the no-op guarantee should be re-committed for
    mixed files.
  - Boot-time DNS TOCTOU on the local-only guard, now extended to the shared
    default key: LlmRouterStartupGuard resolves the default base-url's
    loopback-ness once at boot (perTaskRoutes: "Resolve the shared default's
    loopback-ness ONCE"), while live calls re-resolve at request time — a
    hostname flipping from loopback to remote after boot would bypass
    local-only. Pre-existing mechanism (identical semantics for per-task
    URLs), and it requires control of the operator's DNS for an
    operator-configured host, which the threat model places out of scope
    (operator infrastructure / supply chain).

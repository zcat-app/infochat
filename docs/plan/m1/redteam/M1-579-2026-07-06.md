RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - Zero-width boundary mismatch between the D45 promotion predicate and the
    /pending listing predicate: security.md §Slow-start tier promotes a user
    when `NOW() > probation_until` (strict), while the new ACTIONABLE_WHERE
    lists users when `probation_until > now` (strict). At the exact instant
    `now == probation_until` a user is neither promoted nor listed. The window
    is a single instant, unreachable by an adversary and unactionable by an
    admin within it — informational only; the threat model specifies inclusive
    boundaries for invite-code TTL but makes no boundary commitment for the
    probation window, so this is not a delivered-promise gap.
  - Deliberate discoverability trade-off, not a gap: once a user's probation
    window elapses, their contact_id disappears from /pending permanently, and
    the only other discovery surface (/audit via audit_log_view) is
    redaction-masked by design (security.md §Secrets handling). An admin who
    later wants to /ban a settled user must obtain the contact id from
    conversation context. This is exactly the narrow-complement posture the
    amended D55 commits to (full-roster omission stands); flagged only so the
    user can confirm the operational cost is accepted.
  - PendingCommandHandlerIT disables the audit_log append-only triggers
    (trg_audit_log_no_update / trg_audit_log_no_delete) during test cleanup.
    This is test-fixture code in the failsafe IT phase, not shipped behavior,
    and predates this diff; it does not weaken the runtime append-only
    guarantee enforced by DB roles and triggers.

Audit notes (why CLEAN): the diff strictly narrows /pending's disclosure
surface. The removed `registration_state = 'invited'` OR-arm made /pending a
permanent roster of every post-D47 registered user — the reversal of the
no-/list-users privacy posture D55 forbids; the corrected predicate
(`adapter = ? AND is_banned = FALSE AND probation_until IS NOT NULL AND
probation_until > ?`, PendingUsersDao.java:53-55) matches the amended D55 /
commands.md / design text landed in the same diff. Both the count and list
queries share the single ACTIONABLE_WHERE constant (PendingUsersDao.java:100,
117) so no divergent second predicate exists; all SQL is parameterized; the
adapter key is bound to the inbound adapter (cross-adapter isolation, now
pinned by pending_actionableUserOnDifferentAdapterNotListed); the DM-only and
bot-admin gates and the audit-before-effect PENDING_LIST write
(PendingCommandHandler.java:78-126) are untouched and remain intact; the
probation cutoff reads the injected Clock. Tests were strengthened, not
weakened: the settled-user fixture moved from the unreachable 'vouched' shape
to the reachable ('invited', NULL) shape that would have caught the original
roster bug, and a vouch-shrinks-queue regression test was added.

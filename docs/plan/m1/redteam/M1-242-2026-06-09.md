# Red-team audit — M1-242 (pre-commit, --in-progress)

Target: M1-242
Base: df83e13 (merge-base with main)
Head: working tree (m1/M1-242-signal-inbound-decode-hardening, uncommitted)

Diff fed to adversary: the 3 Signal source files (SignalMessageCodec,
SignalGroupHandler, SignalJsonRpcClient), the 3 new tests, and the
docs/design/06-messaging.md §6.3.10 behavior change. Ticket body and STATUS.md
excluded (no ticket bodies / no implementer rationale to the adversary).

## Verbatim verdict

The Signal byte cap (16_384) mirrors SimpleX exactly, and matches the declared
`maxInboundMessageBytes` capability. The change is a consistent hardening of the
adapter inbound trust boundary.

The diff:
- Tightens the Signal inbound identity gate to canonical-UUID-only (consistent
  with D10 cryptographic-identity anchoring) on both DM and group
  message-sender paths.
- Adds a decoded-body UTF-8 byte cap on both paths, mirroring SimpleX and
  enforcing the declared `maxInboundMessageBytes` capability.
- Makes the oversize-line adapter-boundary drop silent (removing the prior
  friendly reply), which aligns adapter behavior with §Authorization model step
  1.5 (over-cap inbound must not produce a friendly-error reply, closing a
  DoS-amplification surface).

All three are hardening moves that close, not open, gaps. The regex is anchored
(`.matches()`) and linear (no ReDoS). Byte/char caps bound allocation. I found
no place where the diff fails a threat-model promise.

One inconsistency I noticed but verified is NOT introduced by the diff: the
group `MembershipEvent` path (`dispatchMembership` / `aciFromArrayEntry`,
SignalGroupHandler.java:239-285) feeds arbitrary lowercased strings as
`(adapter, contact_id)` join keys without the new `isAcceptableAci` gate. Those
lines are untouched context in the diff (the gate was added only to the
inbound-message sender branch). Per diff-only scope this is pre-existing, not a
delivered-gap of this change, so it is advisory only.

RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - Identity-gate asymmetry (advisory, pre-existing, NOT introduced by this
    diff): the new canonical-UUID `isAcceptableAci` gate is applied only to the
    inbound *message* sender path (DM `extractDm`, group message branch). The
    group `MembershipEvent` dispatch path (SignalGroupHandler.java:239-285,
    `aciFromArrayEntry`) still maps arbitrary `memberJoined`/`memberLeft` array
    strings to `UserJoined`/`UserLeft` events with `aci` lowercased only — no
    UUID assertion — so a non-canonical string could still become a
    `(adapter, contact_id)` join key via the membership surface. These lines are
    unmodified context in the diff (the gate was added only to the
    message-sender branch), so this is not a gap delivered by the change under
    audit; flagging it so the user can decide whether the UUID-only join-key
    policy should also cover the membership path in a follow-up.

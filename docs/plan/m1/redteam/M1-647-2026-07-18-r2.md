    PROMISE: docs/spec/security.md §LLM output sanitizer: "Before any
              LLM-generated text is delivered to a user, the candidate output is
              passed through a deterministic outbound regex pass that strips or
              refuses output containing admin command strings (`/grant-admin`,
              `/ban`, `/promote`, `/remove-source`, etc.). ... It does **not**
              apply to deterministic command output (`/help`, `/status`,
              `/list-sources`, etc.) because that text never passes through an
              LLM. ... the sanitizer closes the social-engineering surface where
              a small LLM emits plausible-looking admin commands across any of
              the surfaces above. Every match is audit-logged (per-occurrence,
              not throttled)."
              The exemption for deterministic output rests on the premise that
              such output is bot-authored and carries no attacker-chosen bytes.
              The diff itself restates that premise as the justification for its
              remediation (docs/spec/commands.md, added §Discovery paragraph:
              "A requested name is **echoed back only when it is command-shaped**
              ... This keeps inbound text from being reflected into bot output:
              without it a body such as `/summary/grant-admin` ... the reply
              would reproduce the literal string `/grant-admin` to a whole
              group"), and the ticket's new acceptance item asserts "no
              attacker-chosen bytes reach outbound text ... This closes both the
              new bare-slash path AND the pre-existing /help <arg> echo."
    GAP: The remediation is an ALPHABET-AND-LENGTH filter, not a CONTENT filter,
          and every admin command string the sanitizer enumerates is itself
          inside the permitted alphabet, so the guard passes them unchanged.

    REPRO: Precondition: an ordinary registered, non-probation, non-banned user
            in an approved group (or in DM). No admin rights needed.
            1. Attacker @mentions the bot with `/help grant-admin`.
            2. `detailBody` normalizes to `grant-admin`; the CATALOGUE lookup

            `isEchoSafe` passes -> `similarity("ban-source","add-source")` = 0.7

            /add-source? ..." — bot output carrying a `/ban`-prefixed token.
            Why the system shouldn't have allowed it: the prior audit's finding
            was that deterministic output now relays attacker-chosen bytes,
            voiding the premise behind the sanitizer's deterministic-output
            exemption. The remediation narrows WHICH bytes (no spaces, no
            slashes, no 8KB relay — all genuine improvements) but leaves intact
            precisely the byte sequences the sanitizer exists to suppress. The
            acceptance criterion "no attacker-chosen bytes reach outbound text"
            and the new commands.md sentence naming `/grant-admin` as the string
            the guard prevents are both stronger than what the code delivers.
            Note on provenance: for the `/help <arg>` surface this echo predates
            the diff; the diff does not widen it there. It is reported because
            the diff explicitly claims to have closed it (ticket acceptance item
            and new spec text), and because the diff extends the same guard —
            with the same shortfall — onto the newly-created bare-slash surface.

    now calls `slashMissSuggestion`, which calls `resolveTier`

    unrecognized slash command. security.md §Authorization model step 1.5
    commits the per-(adapter, contact_id) transport cap as bounding inbound
    "regardless of cost", and §Rate limiting adds the per-group reply cap, so
    this is bounded by an existing spec commitment rather than a violation of
    one. Flagged so the user can decide whether a 4x read amplification behind
    those caps is acceptable. Incidentally, the echo guard also bounds the
    Levenshtein cost: `isEchoSafe` runs BEFORE `suggestionList` on both call
    paths, capping the query at 32 chars, so the O(query x candidate) scan over
    the whole catalogue can no longer be driven with a body-cap-sized query.
  - Whether security.md §LLM output sanitizer's deterministic-output exemption
    should be narrowed at spec level from "deterministic command output" to
    "deterministic output that interpolates no inbound-derived text". That is
    the root cause of the finding above; closing it in code alone leaves the
    spec asserting a premise the code does not guarantee. A spec amendment
    decision, not an implementation defect.
  - Latent oracle risk in the intent map's fail-closed branch.
    CommandIntentSynonyms.java:464-467: an intent word resolving to a command
    outside the caller's vocabulary returns empty and deliberately does NOT fall
    through to the similarity pass. That is the safe direction today, and it is
    genuinely airtight at present: the only admin-targeting entry is
    "makeadmin" -> "grant-admin", and "makeadmin" scores below 0.6 against every
    visible command, so a non-admin cannot distinguish it from an unmapped word.
    But the property is unpinned: if a future synonym targeting a hidden command
    also scores >= 0.6 against a visible one, the suppressed fallback becomes an
    observable difference (mapped-to-hidden yields nothing where a comparable
    unmapped word yields a suggestion) — an existence oracle for the admin
    surface, which commands.md §Discovery calls "a security property, not a UX
    detail". No test in CommandIntentSynonymsTest pins the absence of that
    overlap.

FINDINGS:
  - CATEGORY: INFO-LEAK
    SEVERITY: high
    PROMISE: "Stdout console logs pass through the closed API-key catalogue redactor, fail-closed on regex timeout (whole message replaced with a fixed sentinel). The audit_log writer consumes the same Redactor utility so the two cannot drift."
    GAP: The diff amends security.md (line 1025-1026) to promise that the audit_log writer consumes the same Redactor utility. But DefaultRedactionHook (infochat-core/src/main/java/app/zcat/infochat/core/audit/DefaultRedactionHook.java:80-97) maintains its own independent CATALOGUE (7 regex patterns), its own InterruptibleCharSequence (line 175-206), and its own RegexInterruptedException (line 214-218). The new Redactor class (infochat-core/src/main/java/app/zcat/infochat/core/log/Redactor.java:45-54) duplicates all of these. Neither class imports or references the other. The catalogues are textually identical today but are structurally independent and can drift silently when a future edit adds or modifies a pattern in one but not the other.
    REPRO: A developer adds a new API-key shape (e.g., a new cloud provider prefix) to Redactor.CATALOGUE for stdout redaction but forgets to update DefaultRedactionHook.CATALOGUE. The audit_log writer now fails to redact the new shape in details_json. Alternatively, the reverse: a pattern is updated in DefaultRedactionHook but not in Redactor, and the key shape leaks to stdout. The spec amendment promised this scenario is structurally impossible ("cannot drift"), but the implementation does not deliver this structural guarantee.
    SUGGESTED-FIX-CLASS: other

  - CATEGORY: INFO-LEAK
    SEVERITY: high
    PROMISE: "Stdout console logs pass through the closed API-key catalogue redactor, fail-closed on regex timeout (whole message replaced with a fixed sentinel)."
    GAP: Redactor.isLoggable() (infochat-core/src/main/java/app/zcat/infochat/core/log/Redactor.java:92-123) processes only LogRecord.getMessage() and String elements of LogRecord.getParameters(). It does not process LogRecord.getThrown(). In JUL/JBoss LogManager, the formatter renders the full exception stack trace (including the exception message) AFTER the filter runs. An API key embedded in an exception message will appear unredacted in console output.
    REPRO: An LLM HTTP client throws an exception whose message includes the API key (e.g., "401 Unauthorized for POST https://api.anthropic.com/v1/messages, Authorization: Bearer sk-ant-api03-aBcDeFg..."). Application code logs this via logger.log(Level.SEVERE, "LLM call failed", thrownException). The filter's isLoggable() redacts the message template ("LLM call failed") but the thrown exception's message containing "sk-ant-api03-..." passes through unredacted because getThrown() is never inspected. The formatted console output includes the full stack trace with the raw key.
    SUGGESTED-FIX-CLASS: input-sanitization

  - CATEGORY: INFO-LEAK
    SEVERITY: medium
    PROMISE: "Stdout console logs pass through the closed API-key catalogue redactor, fail-closed on regex timeout (whole message replaced with a fixed sentinel)."
    GAP: Redactor.isLoggable() (infochat-core/src/main/java/app/zcat/infochat/core/log/Redactor.java:108-119) only redacts parameters that are instanceof String. Non-String objects whose toString() contains an API-key-shaped string will be rendered unredacted by the formatter after the filter runs.
    REPRO: Application code logs a request context object as a parameter: logger.log(Level.WARNING, "Request failed: {0}", contextObject) where contextObject.toString() returns "RequestContext{url=https://api.openai.com/v1/chat, auth=sk-proj-aBcDeFgHiJkLmNoPqRsTuVwX}". The filter checks params[0] instanceof String, finds it is not a String, skips it. The formatter calls toString() on the object and renders the raw key in console output.
    SUGGESTED-FIX-CLASS: input-sanitization

OUT-OF-MODEL:
  - The Redactor's InterruptibleCharSequence.toString() (line 159) delegates directly to the underlying string without a deadline check. During Matcher.replaceAll()'s appendTail phase, toString() is called, bypassing the watchdog. This is not exploitable for catastrophic backtracking (appendTail is linear), but it means the watchdog budget is not truly enforced end-to-end. Same pattern exists in DefaultRedactionHook. Not a finding because the spec's watchdog commitment targets regex matching, and appendTail is not regex matching.

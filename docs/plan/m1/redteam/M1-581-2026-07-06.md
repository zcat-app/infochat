OUT-OF-MODEL: (flagged for user decision; none count as findings under the documented threat model)
  - Malicious/tampered restore bundle as a root-write vector. The bundle's secrets.env
    INFOCHAT_*_DATA_DIR values drive root-privileged bind mounts and an in-container
    root untar (prod/scripts/restore.sh:389-394: `-v "/$rel:/$rel"` + `tar -C / -xzpf`),
    and the new M1-581 exact-line gate (restore.sh:298-309, `grep -qxF -- "$rel/"`)
    only checks path CONSISTENCY, not path SANITY: a hand-crafted bundle that sets
    INFOCHAT_SIGNAL_DATA_DIR=/etc and carries an exact `etc/` tar member passes the
    gate and overwrites /etc as root on the target host; the new printed
    return-to-fresh recipe (restore.sh:130-133) additionally has the operator run a
    root `rm -rf` on those same bundle-supplied paths. This stays out of model because
    security.md scopes the bundle as operator-trusted config / supply-chain
    ("Operator-set config ... is trusted"; supply-chain attacks on operator
    infrastructure out of scope), restore.sh itself codifies this
    (restore.sh:377 "tampered bundle stays an out-of-model, supply-chain concern"),
    and the diff's own STATUS.md hunk shows pending ticket M1-584 ("refuse
    system-prefix and colon data-dirs") already tracks closing exactly this. Note the
    M1-581 exact-line tightening is a strict improvement over the prior substring
    match — it narrows, never widens, what a bundle can get past the gate.
  - Secret-material disposal is plain-delete, not shred. The new partial-restore
    remediation (restore.sh:125-137) advises removing the placed secrets.env and
    root-owned identity key dirs with `rm` / `rm -rf`, and the EXIT hook
    (restore.sh:344, pre-existing shape at :243) plain-`rm -rf`s a staging tree
    holding a secrets.env copy and identities.tgz (adapter private keys). Disk-forensic
    recovery of deleted secrets is not covered by security.md (no at-rest-encryption
    or disposal commitment — DB-at-rest encryption is explicitly the operator's
    responsibility), and pending ticket M1-583 ("close the secret-disposal gaps",
    visible in the diff's STATUS.md hunk) plus the existing prod/scripts/shred-bundle.sh
    already track the shred story. The printed recipe could point at shred semantics
    instead of `rm -rf` when M1-583 lands.
  - Printed volume-removal recipe can select foreign volumes. Recipe step 3
    (restore.sh:134-135) tells the operator to `docker volume rm` the result of a
    NAME-SUBSTRING filter (`--filter name=infochat-pgdata`); on a host running a
    second compose project whose volume name contains the substring, the printed
    command targets that project's data too. Operator-executed advice on the
    operator's own host with no adversary input — availability hazard for co-located
    deployments, not a threat-model violation (the pre-existing fresh-DB gate at
    restore.sh:271 uses the same filter, so this is also not diff-introduced logic,
    only diff-introduced printed advice).

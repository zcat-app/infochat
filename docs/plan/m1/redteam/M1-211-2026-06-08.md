RED-TEAM VERDICT: CLEAN

The diff is a pure SPI-narrowing design decision plus documentation rewording and a test-double sweep. It removes `MessagingAdapter.assertIdentity(InboundMessage)` — which had zero production callers (confirmed: no `.assertIdentity(` in any `*/src/main/`) and whose three production implementations were no-op passthroughs (`return msg.sender();`) performing no cryptographic verification. No production routing, authorization, ban, audit, rate-limit, LLM-tool, or SQL code is altered.

Every threat-model commitment that touches this surface remains delivered:

- **Trust boundary 1** ("the adapter asserts identity via a stable, cryptographically anchored ID"): identity still flows to the Provider via `InboundMessage.sender()`, an unchanged path. The removed method only echoed that same value back; deleting it loses no verification step (the actual anchoring lives in each adapter's wire-decode codec, which this diff does not touch).

- **New spec sentence** "Provider rejects a `LOW`-trust adapter at registration ... unless ... `infochat.adapters.<name>.allow-low-trust`": already implemented and unchanged at `infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/AdapterRegistry.java:217-226` (Gate 6), reading the property at `:390-394`. The amended prose matches the existing gate; not a new undelivered promise.

- **New spec sentence** "A message whose identity cannot be asserted is dropped at decode ... carried on every inbound message": structurally enforced by the non-null `Identity sender` field on the `InboundMessage` record (`infochat-messaging-adapter/src/main/java/app/zcat/infochat/messaging/InboundMessage.java:24`) under the package's NullAway null-marked default — an InboundMessage cannot be constructed without a sender. The decode paths that build it are unchanged by this diff.

Falsifier checked and failed to break the verdict: the only way removal could weaken a defense is if a live caller relied on `assertIdentity` as a verification hook — but there are no production callers, and both the old and new spec describe the method as a passthrough with no verification, so no defense-in-depth layer is removed.

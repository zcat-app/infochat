# Red-team audit: M1-030 (provider catch-up hardening backlog)

RED-TEAM VERDICT: CLEAN

No FINDINGS against the documented threat model in `docs/spec/security.md`.
The diff lives entirely inside the DB-internal trust zone the threat
model carves out ("The DB is internal — only the two services and the
operator reach it"). None of the user-facing trust surfaces (auth,
authz, ban, audit, LLM tool surface, messaging adapter inbound) are
touched. The three hardening additions are pure defense-in-depth:

- `NewPostHandler.handle()` rejects NOTIFY payloads whose
  `(post_id, ready_at)` does not match a real `READY` row before
  advancing the cursor.
- `NewPostReconciler.runCatchUp` pages the catch-up scan
  (configurable `infochat.provider.catchup.page-size`, default 500)
  so a long-outage backlog cannot block `@Startup` arbitrarily.
- `NewPostListener.runLoop` detects a closed listenConnection in the
  `SQLException` catch branch, re-acquires the connection via
  `dataSource.getConnection()`, re-issues `LISTEN new_post`, and uses
  bounded exponential backoff (1s → 30s cap) on persistent failure.

## OUT-OF-MODEL (advisory; not spec violations)

1. **Existence-check ↔ cursor-advance atomicity.**
   `NewPostHandler.handle()` opens a separate `try-with-resources`
   `Connection` for the existence-check `SELECT` inside the
   `@Transactional` method (file:
   `infochat-provider/src/main/java/io/infochat/provider/outbox/NewPostHandler.java`).
   That `Connection` is closed before `ProviderStateDao.advanceCursor`
   runs on its own connection. Even with Agroal JTA enrollment, the
   `SELECT`'s snapshot is not preserved past the close, so the
   "same transactional boundary" javadoc claim is weaker than stated.
   No in-model adversary inside the DB trust boundary, so advisory
   only — but a stronger atomicity guarantee (single connection,
   single transaction; or `SELECT … FOR SHARE` joined with the
   subsequent update) is the conservative fix.

2. **Broad test-helper `DELETE`.** The three new IT classes'
   `clearAllItPosts()` helpers issue
   `DELETE FROM post WHERE uid LIKE '%-it/%'` (files:
   `NewPostHandlerHardeningIT.java`, `NewPostReconcilerPagingIT.java`,
   `NewPostListenerReconnectIT.java`). Test-only under DevServices, but
   the pattern would be unsafe if ever copy-pasted into prod tooling.

3. **NOTIFY events dropped during listener disconnect.** Postgres
   `LISTEN/NOTIFY` does not buffer for absent sessions; the catch-up
   reconciler only runs at `@Startup`, not after a transient
   disconnect. A post made `READY` during a Postgres restart stays
   user-invisible until the next Provider restart. The threat model
   does not commit to NOTIFY delivery during DB blips; a
   missed-NOTIFY catch-up trigger after listener reconnect is a
   candidate future hardening item.

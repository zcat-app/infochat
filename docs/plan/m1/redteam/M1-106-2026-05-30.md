# Red-team audit — M1-106 (Signal adapter skeleton)

Verbatim verdict returned by the threat-actor subagent (fresh context;
threat model + diff only).

---

RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - `SignalConfig.validate()` (infochat-messaging-adapter/.../signal/SignalConfig.java:62-78)
    embeds the operator-supplied `binary` path, `data-dir` path, and (implicitly,
    via the ACCOUNT_KEY message) the `account` phone number into
    `IllegalStateException` messages thrown at startup. If those exceptions
    propagate to a log sink, the operator's Signal phone number / filesystem
    layout appears in logs. This is outside the documented threat model —
    operator-set config is explicitly trusted ("Operator-set config (properties
    files, bootstrap JSON) is trusted"), and §Secrets handling / §User content
    in exceptions scope the redaction obligation to API-key shapes and
    user-authored prose, not operator config values. Flagged only so the user
    can decide whether operator-PII-in-startup-logs warrants extending the
    model; not counted as a finding.
  - The capability defaults `maxMessageBytes=2000`, `maxSendsPerSecond=8`,
    `maxInflightSends=4`, and `maxInboundMessageBytes=16384` are hard-coded
    constants (SignalAdapter.java:30-44) rather than profile-driven values. The
    spec's transport-level caps are "profile-driven" (§Rate limiting), and the
    in-code comment concedes these are "best-guess defaults not fixed by
    spec... expected to be tuned against a live signal-cli." This is a skeleton
    with no live transport (all send/receive throws), so the constants are
    inert and unreachable in this diff; whether they must become profile-driven
    before M1-107 wires the live subprocess is a planning question outside this
    diff's threat surface.

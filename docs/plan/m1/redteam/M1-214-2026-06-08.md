# Red-team audit: M1-214 (pre-commit)

RED-TEAM VERDICT: CLEAN

Audit notes (why each changed surface holds against the threat model):

- **fec0::/10 addition** (`infochat-ssrf/src/main/java/app/zcat/infochat/ssrf/IpBlocklist.java:217-220`): the mask `b0 == 0xFE && (b1 & 0xC0) == 0xC0` correctly covers `fec0::`–`feff::`; combined with the existing `fe80::/10` check the full `fe80::/9` legacy-local space is blocked with no gap between the two ranges. Transition-form embedding (6to4/Teredo/NAT64/IPv4-compatible) cannot smuggle a v6 site-local (those forms embed IPv4 only, and embedded IPv4 routes through `isBlockedV4` plus the host-interface re-check). Delivers the spec's "IPv6 equivalents" of private ranges.
- **Scheme case-fold** (`SsrfGuardedHttpClient.java:468-471`): widens acceptance only — an upper-cased scheme that previously failed closed now proceeds, but every accepted URI still runs the full pipeline (userinfo gate, host canonicalization, DNS resolution, blocklist, pinning) per hop. No Unicode case-fold collision is reachable: `java.net.URI` restricts scheme characters to ASCII alpha/digit/`+-.`, so `toLowerCase(Locale.ROOT)` cannot be fed a homoglyph that folds into `http`/`ws`. `isCrossOrigin` and `effectivePort` already compare case-insensitively, so credential scrubbing and port defaulting stay consistent with the gate. `Locale` was already imported (line 20).
- **Location-resolve wrapping** (`SsrfGuardedHttpClient.java:398-405`): closes a real contract escape (raw `IllegalArgumentException` from attacker-controlled `Location` previously left the documented `SsrfPolicyException`/`IOException` boundary). The wrap throws inside the hop loop, so the `finally` at line 416-420 still releases the DNS pin — no stale pin on the new path. An empty or self-referential `Location` degenerates into the redirect-cap path, which is bounded. The exception message embeds the attacker-controlled header value, matching the pre-existing `"blocked IP: "`/`"invalid host: "` pattern; CR/LF cannot survive JDK header parsing, so log injection via this string is not reachable, and the spec's `SafeLog` mechanism drops exception message bodies before logging.
- **Test rewrites** (`SsrfGuardedHttpClientTest.java`, `IpBlocklistTest.java`): assertion strength is preserved or increased — message-substring assertions became typed `reason()` assertions; the deleted `rejectsWebsocketSchemeForNow` is replaced by an equivalent `get()`-rejects-wss test plus a positive wss-acceptance test on the dedicated WebSocket entrypoint (which uses a test-seam resolver and a loopback-permitting blocklist, both established test patterns, not production behavior changes). No promised negative test was weakened or removed.

OUT-OF-MODEL:
  - The IPv4 blocklist does not cover 192.0.0.0/24 (IETF protocol assignments, incl. the 192.0.0.170/171 DNS64 discovery addresses), 198.18.0.0/15 (benchmarking), or 240.0.0.0/4 (reserved). The spec's committed category list ("private, loopback, link-local, multicast, CGNAT, and cloud-metadata ranges") does not name these, so this is advisory hardening, not a broken promise — extending the catalogue would be a design-note edit per the spec's own framing.
  - `SsrfPolicyException` messages embed attacker-controlled strings (redirect `Location`, hostnames) bounded only by the JDK's ~384 KiB header-size limit. The spec's `SafeLog` discipline neutralizes the logging surface, but any future caller that logs `ex.getMessage()` directly via SLF4J would re-open it; the typed `reason()` contract the diff strengthens is the right caller-side habit.

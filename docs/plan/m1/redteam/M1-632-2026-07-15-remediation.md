RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - Residual `--contact=` (empty-equals) parse shape is NOT covered by the
    fix's new malformed gate, but is non-exploitable and does NOT re-open the
    remediated medium finding. The amended threat model now promises
    (security.md:759-761): "Malformed issuance input — an unrecognized token,
    a value-less `--contact`, or a stray bare argument — is rejected with an
    explicit error; no code is created and no confirm is armed." The new
    `malformed` tracking in CreateArgs.parse catches the *space* form of a
    value-less `--contact` (falls into the else branch at
    InviteCommandHandler.java:864-870 → malformed=true → rejected at :325-327).
    It does NOT catch the *equals* form: token `--contact=` matches the
    `startsWith("--contact=")` branch at InviteCommandHandler.java:858-859 and
    sets `contact=""` (non-null, malformed=false). Input
    `/invite create --adapter <valid> --contact=` therefore skips the malformed
    gate, skips the bare→open normalization (contact != null), and reaches
    createContactBound(:371-374) with targetContactId="", minting a CONTACT_BOUND
    invite bound to an empty contact id — a code IS created and shown, contradicting
    the letter of the amended "value-less --contact is rejected; no code is created"
    promise.
    Why this is NOT a categorized finding: (1) It stays in the SAFE direction. The
    remediated medium finding was strict-intent silently widened to the
    broadest-blast-radius OPEN class; here the botched input stays in the
    bounded-risk CONTACT class, never normalized to OPEN, so the dangerous widening
    the fix targeted does not recur. (2) The minted invite is un-consumable: the
    intake consume (InviteCodeConsumer.java:98-104) binds `expected_contact_id = ?`
    to the inbound contact id, and that id is the adapter-assigned cryptographic
    identity (security.md Trust boundary 1) — never empty and never attacker-chosen —
    so no contact can ever match "". No AUTH-BYPASS (nobody reaches authenticated
    functionality), and it maps to no closed category's threat. (3) It is
    pre-existing parse behavior (the `--contact=` branch is unchanged by this diff),
    surfaced only because the diff's own new spec wording ("value-less --contact")
    can be read to cover it. Impact is confined to a dead invite that consumes one
    global `--contact` cap slot and writes one INVITE_CREATE audit row per admin
    invocation — self-inflicted, admin-only, not adversary-reachable.
    Flagged so the user can decide whether to (a) extend the malformed gate to the
    equals-empty `--contact=`/`--adapter=` shapes and (b) reject an empty
    expected_contact_id at issuance, closing the letter-of-spec gap. No action is
    required for the remediation to stand: both prior AUTH-BYPASS findings are
    closed and the fix introduces no new adversary-reachable gap on the invite/auth
    admission path.

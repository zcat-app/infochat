OUT-OF-MODEL:
  - Migration runbook (docs/design/07-deployment.md, "Migrate a pre-M1-506
    SimpleX by-address bootstrap", step 2) instructs the operator to
    `ALTER TABLE users DISABLE TRIGGER trg_last_admin_protection_delete`,
    delete the phantom admin row, then re-enable. If an operator forgets the
    re-enable, last-admin protection (a trigger-layer invariant per
    security.md §Authorization model) is silently absent until the next
    deploy/restart re-runs migrations. This is a trusted-operator break-glass
    action under the table-owner role (security.md §Threat model:
    "Operator-set config ... is trusted"), executed deliberately, with an
    explicit re-enable step in the same runbook — not an adversary-reachable
    path. Noted only so the user can decide whether the runbook should add a
    post-recovery verification step ("confirm the trigger is re-enabled").

  - The re-arm-after-revoke gap for the SimpleX claim-token
    (a still-configured `admin-token` re-arms if the claimed admin is later
    /revoke-admin'd) is described accurately by this diff's docs and is
    already an accepted, documented residual risk in security.md
    §Per-adapter admin threat profile, mitigated by the operator-hygiene
    "unset the token after claim" guidance. The diff strengthens, not
    weakens, this guidance. Not a finding; the underlying claim/gate logic
    (M1-506) is outside this diff.

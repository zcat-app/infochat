    over-audit (defense-in-depth) rather than under-audit (evasion); it does

    "an audit row records the threshold breach" as strictly singular under
    concurrency is a design call for the user.
  - The breach-branch audit insert and the conn.commit() are followed by
    breachAudited.add(key) on the same thread; if the JVM is killed (SIGKILL,
    crash) between commit and add, the durable audit row survives and the
    in-memory sentinel does not, so the next call would write a second audit
    row on restart. The existing class-level Javadoc already documents that a
    Provider restart resets the set and tolerates a second audit, so this
    matches the documented behavior — but the user may want to note that the
    new ordering subtly widens the duplicate-audit window from "restart-only"
    to "restart-or-crash-between-commit-and-add."
  - The trade-off comment at InviteCodeConsumer.java:148-154 asserts "if
    insertAudit succeeds but commit throws (rare), no DB row survives." This
    relies on the JDBC/PostgreSQL guarantee that a failed COMMIT rolls back
    the transaction. The outer catch (SQLException e) { conn.rollback(); ... }
    is also invoked, which is correct, but worth confirming the chosen JDBC
    driver behaves as the comment claims.

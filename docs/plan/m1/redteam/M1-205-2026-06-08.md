RED-TEAM VERDICT: FINDINGS

FINDINGS:

  - CATEGORY: DOS
    SEVERITY: high
    PROMISE: §Threat model — "The Provider is exposed to the internet through every enabled messaging adapter ... Adversaries can send arbitrary text on any of them"; §Rate limiting — "Chat-mode message rate (transport-level) — bounds inbound message volume regardless of cost"; §Authorization step 1.5 — "Apply the per-(adapter, contact_id) inbound rate cap ... Over-cap inbound is dropped silently ... before every application-level check below, so a hostile flood cannot drive outbound cost." The DOS category explicitly covers "Resource exhaustion ... blocking-the-event-loop in the messaging adapter."
    GAP: The diff removes the previously-spec'd bounded inbound queue (default 1000) + drop-newest eviction (docs/design/06-messaging.md §6.3.7; E4007 retired in 09-reference.md) and substitutes the claim that "the dispatch backlog is bounded by (rate-cap survivors × in-flight handler time)" using "the JDK default unbounded LinkedBlockingQueue." That claim is false for the queue itself: the step-1.5 rate cap (RateCapBucket.tryAcquire) runs inside InboundRouter.route() at InboundRouter.java:359, which executes on the adapter's single-thread dispatchExecutor (SimpleXWebSocketClient.java:105/:430 dispatchExecutor.execute(delivery); SignalJsonRpcClient.java:226/:579). The read loop enqueues every decoded inbound frame onto the unbounded executor queue (SimpleXWebSocketClient.dispatchAsync, line 428-437) and never blocks. The rate cap is therefore consumed strictly downstream of the unbounded queue, so it cannot bound queue depth — it only governs work done after an item is already dequeued.
    REPRO: An attacker (a single registered contact, or a flood across rotating unregistered contact ids — both reach the adapter read loop before any auth) sends in-spec-size messages on a connected adapter faster than the single dispatch thread can drain onMessage (each onMessage does a DB read for identity resolution plus normalization, so drain rate is modest). Because the read loop enqueues every frame onto the unbounded LinkedBlockingQueue without back-pressure, the queue — each entry retaining a full InboundMessage body — grows without bound, exhausting Provider heap and OOM-killing the only user-facing service. The step-1.5 rate cap drops each message cheaply when finally dequeued, but that is too late: the unbounded queue has already absorbed the flood. The maxContactBuckets ceiling added by this diff bounds the bucket-map key space but does nothing to bound the upstream dispatch queue.
    SUGGESTED-FIX-CLASS: rate-limit

OUT-OF-MODEL:
  - Outbound concurrency/rate-cap downgrade (maxInflightSends/maxSendsPerSecond -> ADVISORY/RESERVED): outbound volume is bot-generated and bounded upstream by the per-user/per-group reply caps and LlmRateCap; the threat model does not commit to an adapter-level OUTBOUND rate cap as a security boundary, so this downgrade is not a threat-model gap. Flagged only so the user can confirm no operator-cost guarantee depended on it.
  - maxContactBuckets "benign bounded overshoot under concurrent inserts": the size-check-then-computeIfAbsent is non-atomic and RateCapBucket is a singleton shared across the SimpleX and Signal dispatch threads, so the comment's "single-thread per adapter" justification understates concurrency — but the overshoot is bounded by the small number of concurrent adapter threads (2-3), so it is genuinely benign and not a finding.

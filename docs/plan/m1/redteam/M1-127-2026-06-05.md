FINDINGS:

  - CATEGORY: INFO-LEAK
    SEVERITY: low
    PROMISE: "Contact IDs are logged in redacted form (prefix + ellipsis + suffix)" and "`audit_log_view` is a Postgres view that exposes the same columns as `audit_log` minus any redacted fields (raw secrets, full contact ids — replaced with the redacted form per §Secrets handling)." (docs/spec/security.md §Secrets handling, §DB roles)
    GAP: `infochat-core/src/main/resources/db/migration/V31__service_role_login_and_audit_redaction.sql:65-75` — `redact_contact_id` masks fully only when `char_length(input) < 10`, otherwise returns `left(input, 6) || '…' || right(input, 4)`. For a contact id of length exactly 10, the 6-char prefix and the 4-char suffix are disjoint and contiguous (6+4 = 10), so they tile the entire string: every character is emitted with only a cosmetic `…` inserted in the middle, hiding nothing. The function comment reasons only about the overlap case (`< 10`) and misses that the no-hidden-middle case extends through length 10; the threshold should be `<= 10`.
    REPRO: A user whose adapter-assigned contact id is exactly 10 characters (e.g. a short custom-adapter or in-memory-adapter id) is involved in any audited action (BAN, INVITE_CREATE --contact, GRANT_ADMIN target, etc.). A bot admin runs `/audit`, which reads through `audit_log_view`; the `actor_contact_id` / `target_contact_id` columns render the full 10-character contact id rather than a partially-masked form. The view is the path specifically designed to withhold full contact ids from the Provider-role read surface, and for this length it discloses them completely.
    SUGGESTED-FIX-CLASS: input-sanitization

  - CATEGORY: INFO-LEAK
    SEVERITY: low
    PROMISE: "The audit_log writer consumes the same Redactor utility so the two cannot drift." / "mirrors `app.zcat.infochat.core.log.Redactor.CATALOGUE` so the read-side SQL mask cannot drift from the write-side Java filter." The spec elsewhere makes anti-drift a structural (CI-enforced) property (tool registry byte-for-byte; sanitizer match-set derivation). (docs/spec/security.md §Secrets handling, §LLM output sanitizer)
    GAP: `infochat-core/src/main/resources/db/migration/V31__service_role_login_and_audit_redaction.sql:88-100` hand-duplicates the seven-family catalogue from `infochat-core/.../log/Redactor.java:45-54` as PL/pgSQL `regexp_replace` calls. The "cannot drift" guarantee in the spec is delivered by both the console filter and the audit-write hook (`DefaultRedactionHook`) calling the *same* Java `Redactor.redact`; this new SQL function is a third, independent copy of the catalogue kept in sync only by a comment. There is no CI check binding the SQL bodies to `Redactor.CATALOGUE` (unlike the registry/sanitizer mismatch checks the spec mandates). If a key family is later added to the Java catalogue (a design-note edit per §Secrets handling), the read-side `audit_log_view` mask silently lags and would surface a secret the write hook missed (the read-side mask exists precisely as that backstop).
    GAP-NOTE: The SQL and Java catalogues match today; the finding is the absence of a mechanical guard against future drift, not a present divergence. Additionally, `redact_secrets_jsonb` (V31:88) runs Postgres `regexp_replace` with no per-input watchdog, unlike the §Ingest/§Secrets "java.util.regex-plus-watchdog, fail-closed" discipline applied to the write-side and console paths; it is labeled defense-in-depth, so this is a hardening gap rather than a primary-path failure.
    SUGGESTED-FIX-CLASS: audit-log-coverage

OUT-OF-MODEL:
  - Default fallback passwords (`INFOCHAT_COLLECTOR_PASSWORD:infochat-dev`, `INFOCHAT_PROVIDER_PASSWORD:infochat-dev`, `INFOCHAT_DB_PASSWORD:infochat-dev` in both `application.properties`) mean a service connects with a known weak password if the operator forgets to set the env var. Operator-set config is trusted per the threat model, so this is operator-infrastructure responsibility, not a modeled threat. Worth an operator-facing note nonetheless.
  - The production Collector process now holds the bootstrap `infochat` owner (superuser) credentials via the named `owner` datasource (`infochat-collector/.../application.properties` owner block; `PartitionCreator.java:46-48`). I confirmed the owner connection is used only for deterministic, non-attacker-controlled DDL: `PartitionCreator.provision` builds statements from `YearMonth.now()` via `PartitionDdl.createPartitions(month)` (no untrusted input), and ingest writes go through the weak default `infochat_collector` role. So there is no injection vector onto the owner connection. It is a least-privilege erosion (a 4th high-privilege principal living in a service exposed to untrusted feed content), but it is bounded and the user-facing Provider deliberately carries no owner credentials in production — consistent with the spec's Provider-focused least-privilege guarantee.

FINDINGS:

  - CATEGORY: INJECTION
    SEVERITY: critical
    PROMISE: docs/spec/security.md §Per-source trust boundaries / Nostr: "**Signature verification.** Every received event MUST pass signature verification against its claimed pubkey before reaching Stage 1. ... Failed verification → drop, increment a counter, never enqueue. Never released as `READY`, never visible to users." And: "**Ordering at the StreamSource trust boundary:** signature verification → kind allowlist → outbox write."
    GAP: infochat-collector/src/main/java/app/zcat/infochat/collector/stream/nostr/NostrStreamSource.java:132-141 — `deliverOne(NostrEvent event)` directly calls `deliver.accept(event.toNormalizedPost(...))`, which the Registrar wires to `postPersister.persist(...)` at NostrStreamSource.java:202. There is no `sig`/`pubkey` check anywhere in the diff; NostrRelayConnection.handleFrame (NostrRelayConnection.java:170-179) hands every parsed `Event` straight to the sink. The `NostrEvent` record carries `sig`/`pubkey` fields but they are never validated. The class-level javadoc explicitly admits "recomputing it from the canonical serialization and checking it against the signature is M1-097 (verification), out of scope here" — but the Registrar (NostrStreamSource.java:154-207) is `@Startup @Priority(460) @ApplicationScoped` and so wires the pipeline live on every Collector boot the moment this diff lands on main, well before M1-097 ships.
    REPRO: (1) Operator (or attacker who has compromised the operator's bootstrap-sources.json or talked an admin into adding a relay) configures a `kind='nostr'` source row with `config.relays` pointing at any attacker-controlled relay. (2) Attacker stands up a tiny NIP-01 relay that serves `["EVENT","sub",{ "id":"...", "pubkey":"<any public figure's hex pubkey>", "created_at":..., "kind":1, "tags":[], "content":"<arbitrary content attributed to victim>", "sig":"<garbage>" }]`. (3) The Collector parses the frame, drops it on the inbound queue, the delivery loop calls `toNormalizedPost`, and PostPersister writes a RAW post whose `upstream_identifier` is the attacker-chosen event id and whose body is the attacker-chosen content. (4) After Stage 1/Stage 2 BENIGN it becomes a user-visible post that the bot will surface in `/summary`, `getPost`, etc. attributed to the impersonated pubkey. The spec promises the relay is "not a trust anchor" and only the pubkey is — this diff inverts that contract.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

  - CATEGORY: INJECTION
    SEVERITY: high
    PROMISE: docs/spec/security.md §Per-source trust boundaries / Nostr: "**Kind allowlist.** Only kinds 1 (text notes) and 6 (reposts) are parsed in v1. All other kinds — including kind 4 (DMs), kind 7 (reactions), and any encrypted-content NIPs — are dropped without parsing." And: "an event of a disallowed kind is dropped at the kind filter and never reaches the outbox".
    GAP: infochat-collector/src/main/java/app/zcat/infochat/collector/stream/nostr/NostrStreamSource.java:132-141 — `deliverOne` ignores `event.kind()` entirely. NostrEvent.toNormalizedPost (NostrEvent.java:42-52) maps every event regardless of kind. There is no filter on the kind field anywhere in NostrRelayConnection.handleFrame, NostrStreamSource.deliveryLoop, or NostrStreamSource.deliverOne. Kind 4 (encrypted DMs), kind 7 (reactions), kind 5 (deletion requests), and arbitrary future/encrypted kinds are all persisted as posts.
    REPRO: A hostile relay (or any relay carrying ambient traffic that matches the subscriber's `kinds:[*]` filter, since this diff has no client-side kind filter to fall back on either) delivers `["EVENT","sub",{"kind":4,...,"content":"<encrypted DM ciphertext that decrypts to attacker-controlled prompt>"}]`. The Collector writes the DM ciphertext as a post body, which then flows into Stage 1/Stage 2 and the LLM pipeline. The spec explicitly names "encrypted-content NIPs" as the surface this rule defends against — they must never reach the parser.
    SUGGESTED-FIX-CLASS: input-sanitization

  - CATEGORY: INJECTION
    SEVERITY: high
    PROMISE: docs/spec/security.md §SSRF and outbound connections: "Every outbound connection from the Collector (feeds, redirects, and `StreamSource` connections) ... runs through a fail-closed allowlist (decision D20). ... The IP-blocklist and DNS-rebind defenses are **transport-agnostic** — a `wss://` relay connection is gated by the same checks as an `https://` feed fetch (decision D38). DNS-resolved IPs are checked against a blocklist of private, loopback, link-local, multicast, CGNAT, and cloud-metadata ranges (notably `169.254.169.254` and IPv6 equivalents) plus the host's own non-loopback interfaces. ... For long-lived `StreamSource` connections the IP check applies on every reconnect, and **any peer-IP change observed at the socket layer is a hard close**".
    GAP: infochat-collector/src/main/java/app/zcat/infochat/collector/stream/nostr/NostrRelayConnection.java:152-160 — `connectAndSubscribe()` dials with `httpClient.newWebSocketBuilder()...buildAsync(relayUri, ...)` directly. No allowlist, no DNS resolution-and-check, no peer-IP-change detection on reconnect. The diff's class-level javadoc explicitly defers this to M1-101 ("SSRF guarding of the wss:// target is M1-101 — this connection dials with a plain HttpClient"). Registrar.parseRelays (NostrStreamSource.java:228-247) also doesn't validate the scheme — `URI.create(relay.asText())` accepts any string parseable as a URI.
    REPRO: (1) Operator (or compromised admin) adds a nostr source whose `config.relays` includes `ws://169.254.169.254/latest/meta-data/iam/security-credentials/` or `ws://localhost:5432/` (Postgres) or `ws://127.0.0.1:8080/internal-admin-api`. (2) On Collector boot the Registrar dials these targets via the plain HttpClient, opening a WebSocket handshake to internal infrastructure. Even when the handshake fails (the target isn't a WebSocket), the connection itself has already probed/touched the target, leaking presence info and (for some targets) triggering metadata-service / cloud-IAM disclosure. (3) On reconnect with DNS rebinding (an attacker-controlled domain that flips its A-record between the allowed-IP first lookup and the actual TCP connect on reconnect), the Collector connects to whatever IP DNS now returns — no peer-IP-change hard-close exists.
    SUGGESTED-FIX-CLASS: missing-auth-check

  - CATEGORY: DOS
    SEVERITY: high
    PROMISE: docs/spec/security.md threat model: "Resource exhaustion, unbounded loops" (DOS category). And §SSRF / outbound: "Redirect, body-size, connect-timeout, and read-timeout caps are enforced; an unset timeout is a configuration error." And §Per-source trust boundaries: "the relay that delivered it is *not* a trust anchor" (relays are untrusted; "a hostile or buggy relay can produce many" events).
    GAP: Two unbounded buffers downstream of an untrusted relay:
      (a) infochat-collector/src/main/java/app/zcat/infochat/collector/stream/nostr/NostrStreamSource.java:68 — `private final BlockingQueue<NostrEvent> inbound = new LinkedBlockingQueue<>();` is unbounded; NostrStreamSource.start passes `inbound::offer` as the per-relay event sink (line 95), and `offer` on an unbounded LinkedBlockingQueue never rejects.
      (b) infochat-collector/src/main/java/app/zcat/infochat/collector/stream/nostr/NostrRelayConnection.java RelayListener.onText — accumulates `data` into `StringBuilder buffer` with no size cap until `last=true`. A relay that streams an infinitely-fragmented text frame without ever signalling `last=true` exhausts heap.
      Additionally, the WebSocket has only a connect timeout; no read timeout — a silent socket is held forever.
    REPRO: (a) A hostile or compromised relay flushes millions of small EVENT frames as fast as the WebSocket flow control allows. The delivery loop is bottlenecked on PostPersister DB writes (~ms each); `inbound` grows without bound until the Collector OOMs. (b) A hostile relay streams a single text frame in 1KB fragments, never sending the final fragment; `buffer` grows to GBs and OOMs the Collector. Either kills ingest for every other source on the Collector since a single JVM crash takes everything down.
    SUGGESTED-FIX-CLASS: rate-limit

  - CATEGORY: INFO-LEAK
    SEVERITY: medium
    PROMISE: docs/spec/security.md §Secrets handling / User content in exceptions: "Exception messages and stack traces emitted via the application logger MUST NOT contain user-authored prose (chat-mode message bodies, post bodies, saved-post annotations, command arguments). The application provides a `SafeLog` utility that drops the exception message body, retains only the exception class name, and truncates the cause chain to class names ... The original `Throwable` is never passed to the underlying SLF4J logger."
    GAP: infochat-collector/src/main/java/app/zcat/infochat/collector/stream/nostr/NostrStreamSource.java:139 — `LOG.warnf(e, "Nostr outbox delivery failed for event %s", event.id());` passes the raw Throwable to the JBoss logger. If the underlying `PostPersister.persist` throws `IllegalStateException` wrapping a `SQLException` whose message echoes the bind parameter (PostgreSQL JDBC error messages occasionally include the offending parameter row), the exception's message will include the post body (relay-supplied content, treated by Stage 1 as untrusted). NostrStreamSource.java:187 (`LOG.error("Failed to enumerate nostr sources; none registered", e)`), :243, :265 (Registrar) have the same shape, as does NostrRelayConnection.java connect-failure path. The spec is absolute ("The original `Throwable` is never passed to the underlying SLF4J logger") and `SafeLog` exists at infochat-core/src/main/java/app/zcat/infochat/core/log/SafeLog.java to enforce it.
    REPRO: A relay delivers an event whose `content` contains an API-key-shaped substring or admin contact id. PostPersister fails to write (transient JDBC error) and the wrapped SQLException's message includes the bound parameter row. The throwable is handed to LOG.warnf, which prints the full stack trace including the parameter value into operator stdout — bypassing both the user-content rule and the Redactor pass that SafeLog would have applied.
    SUGGESTED-FIX-CLASS: audit-log-coverage

OUT-OF-MODEL:
  - The malformed-frame log line `LOG.warnf("Nostr relay %s sent a malformed frame, skipping: %s", relayUri, e.getMessage())` (NostrRelayConnection.java:165) emits up to 120 chars of the raw relay frame (the `summarize(frame)` prefix included in MalformedFrameException's message). For a malformed `["EVENT", "sub", {"content":"...]"}]` this prints relay-supplied content into operator logs. Strictly, relay-authored prose is not "user-authored prose" under §Secrets handling, but a hostile relay could choose to craft frames that leak DM ciphertext or other relay-internal content into the operator stdout — flagged so the user can decide whether the spec's user-content rule should extend to all upstream-untrusted content.
  - The shared application-scoped `HttpClient httpClient = HttpClient.newHttpClient()` in `Registrar` (NostrStreamSource.java:179) shares one TCP/TLS connection pool across every relay of every nostr source. If a malicious relay is configured alongside legitimate ones, an attacker who can compromise that relay's TLS endpoint could potentially observe shared connection state (HTTP/2 multiplexing is moot for ws:// upgrades, but the executor and DNS-cache are shared). Not in the documented threat model; flagged for completeness.

RED-TEAM VERDICT: CLEAN

The diff adds a single audit-coverage seam: the permanent-delivery-failure
group soft-removal path (OutboundDelivery.onPermanentGroupFailure →
GroupRepository.markRemovedAudited) now writes a BOT_REMOVED system-actor
audit row in the same transaction as the removed_at mutation. Audited
against docs/spec/security.md.

Checked and found NOT in violation:

- AUDIT-EVASION (audit-before-effect, Invariant 7). markRemovedAudited
  INSERTs the BOT_REMOVED row via AuditLogWriter BEFORE markRemoved(conn,
  groupId) and commits both atomically; an audit-write SQLException calls
  conn.rollback() and rethrows, so no group is left removed_at-set without
  its audit row. GroupRepositoryAuditedRemovalIT pins the rollback
  (asserts removed_at stays NULL and no BOT_REMOVED row survives).
  Falsifier checked: is there a remaining production caller of the bare
  unaudited markRemoved(UUID)? Grep of infochat-provider/src/main shows
  the only invocations of markRemoved(conn, …) are inside markRemovedAudited
  and MembershipEventHandler.handleBotRemoved (both audited); the single-arg
  markRemoved(UUID) at GroupRepository.java:184 has no production caller.
  No evasion path.

- Column-shape parity with the native path. The new row mirrors
  MembershipEventHandler.handleBotRemoved (MembershipEventHandler.java:149)
  byte-for-byte on the audited columns: actor_user_id NULL, actor_contact_id
  NULL, actor_adapter = failing channel, target_kind="group", target_id /
  scope_id = group id. OutboundDeliveryCleanupIT asserts each column value.
  /audit and audit_log_view render system- and native-initiated removals
  identically.

- Redaction / sole-writer. The write routes through the CDI AuditLogWriter
  (AuditLogWriter.java:96-97) whose redact() hook runs before INSERT;
  field injection ensures production always binds the real redacting writer
  (no non-redacting default-writer constructor introduced). actor_adapter is
  the operator/system-controlled adapter.name() (channel), not attacker text
  — no log/SQL injection surface.

- INFO-LEAK in exceptions (security.md §User content in exceptions).
  GroupRepository.java:404-409 uses SafeLog.error + sanitizedFailure, which
  emit the SQLException class name only — no message body, no cause —
  matching the existing MembershipEventHandler convention. A Postgres
  constraint-violation DETAIL line (which can echo bound audit values) is
  not propagated.

- DOS / determinism. No new unbounded loop; requestId is one
  UUID.randomUUID() per removal; the threshold (> 1) is unchanged
  (M1-284, out of scope). The diff touches no authorization gate, ban
  path, invite gate, or LLM tool surface. The is_group_admin assertions
  flagged in the sensitive-surface inventory are pre-existing test code in
  OutboundDeliveryCleanupIT, untouched in intent by this change.

No threat-model commitment is left undelivered by this diff.

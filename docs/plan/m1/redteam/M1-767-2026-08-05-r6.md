OUT-OF-MODEL:
  - In-memory, per-JVM budget window. `SystemLlmBudget.callTimestamps` is a
    process-local ArrayDeque (SystemLlmBudget.java:120), so a restart, redeploy
    or crash-loop resets a 24-hour control to zero, and a multi-instance
    Provider would multiply the effective ceiling by the instance count. The
    threat model already accepts in-memory state for the analogous control
    ("State is in-memory only — a restart resets to CLOSED", §Failure
    handling); restarts and deployment topology are operator actions, not
    external-adversary levers in this model. Re-flagged from prior rounds for
    the spec owner, not filed.
  - The distinct refusal string `error.retry.digest_system_budget` is a
    cross-tenant load oracle: a group admin polling `/retry --digest` learns
    whether the DEPLOYMENT-wide window (filled largely by other groups'
    system-initiated renders) is at its ceiling. §Rate limiting accepts an
    analogous disclosure for the per-user concurrency reply on the grounds
    "metadata-only, self-triggered — no third party can probe another user's
    count", which is exactly the property this reply lacks. Admin-tier,
    metadata-only, and dispositioned in rounds 3-5; noted, not filed.
  - Pre-cap DB work on the refusal path. Because the gate sits above
    `llmRateCap.tryAcquire` (RetryCommandHandler.java:595) and
    `tryAcquireGroupLlm` (:598), a refused `/retry --digest` now costs one
    audit-row transaction (:555), `retryLeg`'s three SELECTs
    (DigestRetryService.java:336-342) and one `ThrottledAdminNotifier`
    `admin_notification_state` UPSERT, while drawing NO per-minute LLM token —
    an attempt that previously always spent one. Verified bounded rather than
    filed: `InboundRouter.java:1114` draws the D47 per-group command
    sub-bucket (`infochat.ratelimit.group-commands-per-15min`, default 20)
    before dispatch, and step 1.5's transport cap bounds the sender, so the
    residual is a handful of cheap statements per group per 15 minutes on an
    admin-only surface.
  - Scope note (not an attack): the accounting and fairness residuals carried
    from rounds 1-5 are unchanged in this diff and ship as documented residual
    risk under the filed follow-up M1-769 — the admission-only gate with no
    intra-render bound; the over-count legs (unresolvable SUMMARIZER router,
    OPEN breaker, empty-prompt roll-up skip, M1-763 slot-window cancellation
    charging ~211 phantom calls); the under-count legs (non-`en` roll-up's
    second provider leg, the `appendClusterProse` cache-eviction race); and
    the absence of a per-group share of the deployment-wide ceiling. All are
    named in `SystemLlmBudget`'s class javadoc, in the `application.properties`
    operator block and in the ticket's `out_of_scope`. Deliberately NOT
    re-reported as findings.

NOTES (audit record, not findings):

Round-6 surface — the three changes the brief flags as new, audited hardest:

  - GATE ORDERING REVERTED TO PROBE-FIRST. `RetryCommandHandler.java:578-583`
    evaluates `digestRetryService.retryLeg(groupDbId) == RetryLeg.FALLBACK
    && !systemLlmBudget.canStartRender()`. The stated rationale checks out
    against the code: `canStartRender()` (SystemLlmBudget.java:185-193) is not
    a pure predicate — its false branch calls
    `adminNotifier.notifyOnce(BREACH_KEY, "llm-budget-exhausted", "scheduled
    digest degraded: ...")`, whose coalescing suppresses the emission but not
    the JDBC round-trip. With the budget read ordered first, Java's `&&`
    short-circuit would evaluate it on EVERY `/retry --digest`, so during an
    exhausted window a REPLAY-leg retry — zero provider calls, zero render,
    nothing degraded — would emit the operator "scheduled digest degraded"
    signal and a DB write per attempt. Probe-first eliminates that on the
    REPLAY and NO_PRIOR legs. The revert introduces no new gap: the FALLBACK
    leg's behaviour is byte-identical under either order, and the probe's
    three SELECTs already ran in the healthy case under both orders.

  - THE NEW TEST ASSERTION PINS WHAT IT CLAIMS.
    `RetryDigestCommandTest.retryDigest_replayLegProceedsWithoutConsultingThe
    SystemBudget` sets `StubDigestRetryService.nextLeg = REPLAY` and installs
    `CountingSystemLlmBudget` (which counts and returns false), then asserts
    `canStartRenderCalls == 0` and `digestRetryService.callCount == 1`.
    Because the stub counts on the overridden method rather than being
    stubbed wholesale, a re-flip to budget-first ordering makes the count 1
    and the test red. The assertion is load-bearing, not decorative — it is
    exactly the coverage whose absence let the 01:08 regression through.

  - COMMENT/DOC QUALIFICATION. The "never gated" → "never gated in steady
    state" qualification was checked at each live site
    (RetryCommandHandler.java:150-153 and :561, DigestRetryService.java:49-50
    and :327-329, DigestWorker.java:92-95, SystemLlmBudget.java:56-57,
    DigestRenderer.java:104-107, application.properties M1-767 block). Every
    one now carries the residual and points at the canonical anchor
    (`DigestRetryService.retryLeg`). No executable line changed with them.

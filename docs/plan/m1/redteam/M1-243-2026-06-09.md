## Verbatim verdict

RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - Startup-time-only loopback resolution leaves a DNS-rebind window (host
    resolves all-loopback at boot but to a remote IP at call time). This is
    unchanged by the diff and is explicitly accepted in the threat model:
    docs/spec/llm.md §Per-task routing rules ("checked once at startup, not per
    call"), with the per-call SSRF defense delegated to infochat-ssrf's
    SsrfGuardedHttpClient rather than the LLM-call path (see
    LlmRouterStartupGuard.java:66-78). Flagged only so the user can confirm the
    LLM base-url call path is in fact routed through SsrfGuardedHttpClient
    per-call; if it is not, the startup-only check is the sole defense and the
    rebind window is a real residual — but that is a property of code outside
    this diff, not a gap this diff introduces.

## Adversary reasoning (verbatim)

The diff's purpose: harden the startup loopback check so a multi-A-record host
where only the first record is loopback no longer passes. This is a strict
tightening — getByName returned only the first record; getAllByName +
everyAddressLoopback requires ALL records loopback. The change strictly narrows
what counts as loopback (fewer hosts pass), which is the correct direction for a
fail-closed guard.

Adversarial probes:
1. DNS-rebind / TOCTOU — applies to infochat-ssrf, not this startup guard;
   spec-sanctioned residual, untouched by this diff. Not a finding (OUT-OF-MODEL).
2. everyAddressLoopback empty-array → false: correct fail-closed.
3. Mixed loopback+public → false: correct, now blocks the leak.
4. Does the change weaken anything? No — strictly more restrictive.
5. getAllByName ordering/caching gap? No — every record checked, no ordering
   dependency.
6. uri.getHost() null for malformed authority → treated non-loopback
   (fail-closed). Correct.

The diff is a pure hardening fix that closes a previously-existing first-IP-only
gap. It introduces no new gap against any threat-model commitment.

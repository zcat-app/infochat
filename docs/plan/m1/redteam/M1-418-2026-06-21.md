RED-TEAM VERDICT: CLEAN

No findings against the documented threat model.

The diff under audit (M1-418) introduces `prod/switch-llm.sh`, a post-setup
operator maintenance tool that re-routes per-task LLM backends, plus a JUnit
ProcessBuilder harness pinning it, a one-bullet `security.md` §Secrets handling
addition documenting it, a `SETUP_GUIDE.md` section, and ticket/STATUS
bookkeeping. The sensitive-surface inventory correctly reports that
authentication, authorization, input validation, ban handling, and audit-log
writes are all untouched.

Threat-model reasoning:

- The threat model's trust boundaries (§Threat model) name three untrusted
  actors: untrusted feed content (Collector), untrusted messaging-app users on
  every adapter (Provider), and black-box LLMs. NONE of these actors can invoke
  `prod/switch-llm.sh` — it is a host-shell maintenance tool requiring an
  interactive terminal session and write access to `prod/runtime/`. That access
  is operator-tier, and "Operator-set config (properties files, bootstrap JSON)
  is trusted" is an explicit threat-model assumption. The script is not on any
  in-model adversary's reachable surface.

- The single security-relevant spec commitment the diff ADDS (§Secrets handling,
  diff lines 222-227) is delivered:
  * The LLM API key is read with `read -rsp` (silent, no echo), never printed.
  * The key is written ONLY to `secrets.env` via `set_secret`, dotenv-escaped
    (`dotenv_escape`: backslash, then quote, then `$`), with `chmod 600` and
    `umask 077` — byte-identical to the audited `4-llm.sh` channel (M1-397).
  * `application.properties` references the key as the literal
    `${INFOCHAT_LLM_API_KEY}` (switch-llm.sh:790), never an inlined secret; the
    test `routeTaskToRemoteWritesBaseUrlApiKeyRefAndModel` asserts exactly this.
  * Routing a task to a local backend CLEARS the api-key line (`del_prop`,
    switch-llm.sh:802), preventing a stale remote key reference surviving.

- The "per-task privacy disclosure naming exactly which generative tasks now
  call a remote provider" promise is delivered accurately: the disclosure is
  driven by the FINAL `chosen[$task] == remote` set (Phase 4,
  switch-llm.sh:818-840), `chat` carries the loudest private-message warning,
  the ingest tasks are framed as public-post topic-interest exposure, and a run
  leaving zero remote tasks prints no disclosure at all (asserted by
  `privacyDisclosureNamesOnlyRemoteTasksWithCorrectExposure`). All six
  generative tasks are covered (chat in the first loop, the other five in the
  case statement); none is silently dropped.

- The spec's stdout API-key catalogue redactor (§Secrets handling) is a property
  of the Java application logger, not of operator shell tooling; the script
  never emits the key to stdout, so there is nothing for that mechanism to
  catch and no gap.

- The locked-embeddings invariant (embeddings block never touched) is a
  data-integrity / availability property, not a defended-against-adversary
  commitment in the threat model; the script excludes `infochat.embeddings.*`
  from its task list and the test
  `embeddingsBlockUnchangedEvenWhenReRoutingAGenerativeTask` pins it. No gap.

No SQL, no DB access, no LLM tool surface, no command-router code, no
audit-log path, and no adapter-intake path is touched by the diff. There is no
promise in the threat model that this diff fails to deliver.

OUT-OF-MODEL:
  - `prod/switch-llm.sh` copies `secrets.env` to a timestamped
    `secrets.env.bak.<ts>` (switch-llm.sh:750-752) on every mutating run, each
    containing the plaintext API key. Over many runs these accumulate plaintext
    secrets in `prod/runtime/`. The backups inherit 600 via `cp`/`umask 077`,
    but there is no GC and no operator prompt to remove them. This is a
    host-filesystem residual-secret concern; the host filesystem and operator
    config are trusted in the v1 threat model (same tier as "physical access to
    the server"), so it is not a FINDING. Flagged so the user can decide whether
    to add backup pruning or surface the residual-secret note to operators — the
    pre-existing wizard `4-llm.sh` has the identical pattern, so this is not a
    regression the diff introduces.

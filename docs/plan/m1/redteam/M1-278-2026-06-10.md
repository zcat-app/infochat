RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - Unauthenticated readiness-endpoint info leak widened by the diff. The
    threat model (docs/spec/security.md) makes NO commitment about the health
    endpoint at all — its contents and authentication live entirely in
    design-tier docs/design/07-deployment.md, which already documents the
    adapter-name enumeration as a known "mild information leak" mitigated by
    operator-side loopback-bind guidance (quarkus.management.host=127.0.0.1).
    This diff adds two new data items to that same unauthenticated payload:
    per-adapter up/down booleans folding the supervisor-terminal-failure
    signal (AdapterReadinessCheck.evaluate, infochat-provider/.../health/
    AdapterReadinessCheck.java:779-798) and a cumulative <adapter>.dropped-inbound
    count (same method, line ~791; MessagingAdapter.droppedInboundCount()).
    An unauthenticated caller that can reach the management port now learns
    not just which adapters are activated but whether each is alive and how
    saturated its inbound queue is — a marginally richer fingerprint of
    operational state. It stays OUT-OF-MODEL because: (a) security.md never
    promises the endpoint is authenticated or content-restricted; (b) the
    mitigation (loopback bind / host-firewall) is the same documented control
    that already covers the pre-existing adapter-name leak; and (c) nothing
    leaked crosses the per-adapter isolation boundary or discloses user/admin
    state. Flag for the user only to decide whether to elevate the
    health-endpoint posture (auth or content trimming) into the spec-level
    threat model, since the leaked surface grew.

  - signal-cli endpoint loopback gate relies on boot-time DNS resolution.
    ProductionAdapterBeans.parseEndpoint (infochat-provider/.../messaging/
    ProductionAdapterBeans.java:198-228) resolves the configured host via
    new InetSocketAddress(host, port) and checks resolved.isLoopbackAddress()
    once, at Producer @PostConstruct time. A hostname that resolves to a
    loopback IP at boot but later re-resolves to a non-loopback IP (DNS
    rebind) would not be re-checked. This is OUT-OF-MODEL because the endpoint
    host is operator-set config, which the threat model explicitly trusts
    ("Operator-set config (properties files, bootstrap JSON) is trusted"),
    and signal-cli is the operator's own daemon — not an attacker-influenced
    SSRF target governed by the §SSRF re-resolve-after-redirect rule. The
    check is also fail-closed for the unresolvable/null-address case
    (loopback=false → reject without opt-in), so the new gate only ever
    tightens the prior behavior. Noted so the user can confirm the operator-
    config trust assumption holds for this property and need not be hardened
    to a re-resolution-at-connect model.

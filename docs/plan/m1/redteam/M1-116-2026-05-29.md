## Verbatim threat-actor verdict

RED-TEAM VERDICT: CLEAN

The diff under audit (M1-116) is a Flyway migration (`V27__d47_remove_group_only.sql`) plus STATUS/ticket bookkeeping. It changes the legacy-row disposition for D47: instead of mapping pre-D47 `registration_state='group_only'` rows to `'invited'`, it maps them to the canonical pre-ban shape (`registration_state='preban'` + `is_banned=TRUE` + `banned_at` + `ban_reason`).

I audited this against every relevant threat-model commitment and found no promise-vs-delivery gap:

- AUTH-BYPASS / "there is no group-side registration bypass" (§Invite-code registration): The prior `→ 'invited'` mapping was the actual bypass — it would have granted DM access these group-auto-registered contacts never earned. The new `→ 'preban' + is_banned=TRUE` mapping closes that bypass. Cross-checking the auth evaluation order: a converted row exists, so DM step 2 (fires only on row absence) is skipped and the contact hits the step-4 ban check; in groups, `registration_state='preban'` triggers the step-3 silent drop. Both scopes are blocked, exactly as the file's lines 21-25 claim. Faithful to the spec.

- "Pre-ban → unban does NOT grant DM access" (§User ban): the spec ties the row-deletion-on-`/unban` behavior to `registration_state='preban'`. The migration produces precisely that state, so the deletion path will correctly fire and force a fresh invite. Consistent.

- Last-admin / PERM-ESCAL: `group_only` rows are by construction non-admin (auto-registered via group @mention, never bootstrap-seeded). Setting `is_banned=TRUE` touches no `is_admin=true` row, so the global last-admin counter is unaffected. No lockout, no escalation.

- AUDIT-EVASION (§Authorization model step 8; §DB roles `INSERT`-only on `audit_log`): the bulk transition writes a `D47_GROUP_ONLY_PREBAN_CONVERSION` audit row with `target_kind='system'` and an `affected_rows` count, gated by `HAVING count(*) > 0` (no spurious row when zero rows match). NULL `actor_user_id`/`banned_by` is correct for a system migration with no admin actor and is documented. The operation leaves an audit trail.

- INJECTION: the migration runs under the trusted Admin role (operator-set config is in-trust per the threat model); the `group_only` rows it consumes were minted by the prior trusted system, not by attacker-controlled input. No untrusted-input surface, no dynamic SQL.

The migration does the spec-faithful, defense-tightening thing. Nothing in the threat model is left undelivered.

Relevant file: infochat-core/src/main/resources/db/migration/V27__d47_remove_group_only.sql

OUT-OF-MODEL:
- An operator could, before this migration runs, manually have edited `group_only` rows or run a competing migration; pre-existing-DB tampering by the operator is out of model ("Operator-set config is trusted"). Advisory only, not a finding.

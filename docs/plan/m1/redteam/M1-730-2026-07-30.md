RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: DOS
    SEVERITY: medium
    PROMISE: docs/spec/security.md §Rate limiting — "Parser-only + DB-read
             paginated commands — `/help`, `/status`, `/list-sources`,
             `/get-sources`, `/get-tags`, `/saved`, `/audit`, `/export`,
             `/quarantine list` and similar. One bucket; high cap; cheap."
             §LLM output sanitizer — "Every match is audit-logged
             (per-occurrence, not throttled)." §Trust boundaries item 9
             establishes the pattern that untrusted-source payloads are
             "read under an operator-configurable cap ... before parsing, so
             a pathological multi-GB reply cannot exhaust the JVM."
    GAP: `/saved` was cheap because every attacker-influenceable field it
         sanitized carried a WRITE-boundary cap: `post.title` is truncated to
         `IngestTextNormalizer.TITLE_MAX_LENGTH` (200) at ingest, and personal
         tags are count/length-capped at the `/save` parse boundary. The diff
         adds `body` to the row read
         (SavedCommandHandler.java:87-89 SELECT_ROWS_BASE_SQL) and feeds it to
         the sanitizer via DisplayHeadline
         (SavedCommandHandler.java:292). `post.body` has NO write-path cap at
         all — DisplayHeadline.java:64-71 states this explicitly — so the only
         bound is the render-time `BODY_SCAN_LIMIT = MAX_LENGTH * 10` = 2000
         (DisplayHeadline.java:79), applied in Java AFTER the whole column is
         materialised (DisplayHeadline.java:150-152), not at the SQL boundary.
         Two costs scale with that 10x-wider sanitize unit, once per row and
         20 rows per page:
         (a) LlmOutputSanitizer.emitAuditRows
         (LlmOutputSanitizer.java:635-652) writes ONE `audit_log` INSERT per
         closed-list occurrence with no cap. A 2000-char body of repeated
         `/ban ` tokens yields ~400 occurrences; 20 rows yields ~8,000 INSERTs
         across 20 transactions for a single `/saved`, against ~800 before the
         diff. `/saved` remains in the "high cap; cheap" bucket, so the bucket
         no longer matches the command's cost profile, and the audit-write
         flood also buries genuine `LLM_OUTPUT_SANITIZED` rows in noise.
         (b) The un-truncated `body` column for 20 rows crosses the JDBC
         boundary in full before the 2000-char cut is applied, so per-request
         heap/network is bounded only by the feed body-size cap, not by
         anything `/saved` controls.
    REPRO: 1. Register (invite), let probation elapse. 2. `/add-source` a feed
           the attacker controls (open to any non-banned user per commands.md
           §Source management). 3. Publish 20 items whose bodies are ~2000
           chars of `/ban /ban /ban …` (no slash-reject applies to a post
           body; PostPersister stores it with no gate — see the handler's own
           comment at SavedCommandHandler.java:107-109) and whose titles are
           the ingest `untitled` sentinel, so DisplayHeadline promotes the
           body. 4. `/save` all 20. 5. Loop `/saved`. Each invocation costs the
           deployment ~8,000 audit_log INSERTs plus 20 full-body column reads,
           at the rate the cheapest read-command bucket permits. The system
           should not let a read-only paginated listing convert one cheap
           inbound message into thousands of unbounded DB writes.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

  - CATEGORY: INFO-LEAK
    SEVERITY: medium
    PROMISE: docs/spec/security.md §Ingest pipeline / §Quarantine workflow —
             "A Stage 2 `INJECTION`, `MALWARE`, or `UNKNOWN` verdict hides the
             entire post (`QUARANTINED` status)"; §Failure handling — "Stage 2
             verdict of `INJECTION`, `MALWARE`, or `UNKNOWN` → post stays
             `QUARANTINED` until admin review"; §Trust boundaries item 4 — "No
             post becomes user-visible without passing the layered ingest
             checks."
    GAP: `saved_post` is a frozen snapshot with no join back to `post`
         (SavedCommandHandler.java:87-89: `SELECT ... FROM saved_post WHERE
         user_id = ?` — no `post.status` predicate anywhere in the handler),
         so nothing in the read path observes a later quarantine decision.
         Before this diff the only snapshot field that escaped a post-hide was
         the `title` (write-capped at 200 chars). The diff promotes the
         `body` — the field an injection payload actually lives in — into the
         same un-status-checked render path (SavedCommandHandler.java:248,
         292; DisplayHeadline.java:117-124, 141-153). A post the system has
         since decided must not be shown to anyone therefore keeps delivering
         up to 200 chars of its body to a reader, and in group scope to every
         member of the group (the handler's own M1-675 comment,
         SavedCommandHandler.java:100-104, confirms `/saved` is
         group-broadcast; `error.saved.group_not_in_v1` exists in the bundles
         but is referenced by no code path). Post-hide re-quarantine is a real,
         implemented transition, not a hypothetical: ReEvaluationJob.java:363
         runs `UPDATE post SET status = 'QUARANTINED' ... WHERE ... status <>
         'QUARANTINED'`, and AdminReviewTtlJob.java:140 does the same for
         NEEDS_REVIEW expiry.
    REPRO: 1. An untrusted publisher (any feed; any non-banned user can point
           the bot at one via `/add-source`) posts an item whose body carries
           an injection/abuse payload the Stage 1 regex set does not flag and
           whose title is the `untitled` sentinel. 2. During a Stage 2 outage
           the post is released `READY` with Stage 1 redactions retained (spec
           §Failure handling), so it is briefly visible and saveable.
           3. A user `/save`s it — SaveCommandHandler copies `post.body` into
           `saved_post.body`. 4. The re-evaluation job runs against a recovered
           judge, returns `INJECTION`, and re-hides the post to `QUARANTINED`;
           it is now invisible via `/summary`, `searchPosts`, `semanticSearch`,
           `getPost` and every other surface. 5. The saver runs `/saved` in an
           approved group: the bot broadcasts the first 200 chars of that same
           quarantined body to every member. The same holds after an admin
           `/quarantine reject` or an admin-review TTL expiry. The quarantine
           decision is supposed to be the point at which that content stops
           reaching readers.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

OUT-OF-MODEL:
  - `[REDACTED:<id>]` placeholder integrity on the new `/saved` caller. The
    body pre-cut at `BODY_SCAN_LIMIT` (DisplayHeadline.java:150-152) applies
    only `codePointSafeCut` — unlike `truncate`, it has no
    `stage1PlaceholderSafeCut` — so a body cut at char 2000 can end in a half
    marker (`[REDACTED:ab`). Normally the later 200-char `truncate` discards
    that tail, but a flag-bearing closed-list hit collapses a long span to
    `[redacted command]`, which can bring the string back under `MAX_LENGTH`
    and deliver the half marker verbatim. This is pre-existing M1-729 code
    (already labelled out-of-model by the 2026-07-30 redteam at
    DisplayHeadline.java:183) that the diff merely gives a fourth caller; the
    impact is that a fragment reads as content rather than as a redaction, not
    a disclosure of redacted bytes.
  - Privileged command split across the headline field and the tags field of
    the SAME rendered `/saved` line (e.g. body `/list-sources`, personal tag
    `--all` — no slash, so the `/save` write-side slash reject does not stop
    it) is neither redacted nor audited, because the two tokens never share
    one sanitize input. This is the residual security.md §"Flag position
    mirrors the parser's own scan" explicitly accepts ("bounded by dispatch
    still requiring `is_admin=true`"), and it was equally reachable pre-diff
    via the title, so the diff does not widen it. Flagged only so the user can
    decide whether the accepted residual should still be accepted now that a
    2000-char body is one of the two fields.
  - Cross-scope widening of the D13 per-user-global save disclosure: a post
    saved in DM (whose world predicate was the DM's subscriptions) now
    exposes up to 200 chars of BODY, not just its title, when the user runs
    `/saved` in a group. User-initiated and disclosed by
    `reply.saved.header.global`, so not a threat-model violation — but the
    quantity of DM-world content a single group invocation reveals grew.

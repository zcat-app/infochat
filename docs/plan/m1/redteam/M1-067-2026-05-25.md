# Red-team verdict: M1-067 (2026-05-25)

RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: DOS
    SEVERITY: medium
    PROMISE: "Per-user token buckets bound [...] Parser-only + DB-read paginated commands — /help, /status, /list-sources, /get-sources, /get-tags, /saved, /audit, /export, /quarantine list and similar. One bucket; high cap; cheap." (security.md §Rate limiting)
    GAP: Every SQL query in ExportDataCollector (infochat-provider/src/main/java/app/zcat/infochat/provider/command/ExportDataCollector.java:69-118) lacks a LIMIT clause. The audit_log_view query and saved_post query can return unbounded result sets. All rows are loaded into memory as List<String>, serialized to JSON by collectRows(), then concatenated into a single reply String by ExportCommandHandler.formatPages(). The rate-limit bucket is labeled "high cap; cheap" — an unbounded full-table scan per user is not cheap for a power user with thousands of audit rows. Multiple concurrent /export requests from different users under the high-cap bucket can exhaust heap.
    REPRO: A bot admin who has been active for months accumulates thousands of audit_log rows. The admin sends `/export` in DM. The handler queries all their audit rows with no LIMIT, serializes each to a JSON string, paginates them into potentially hundreds of pages, then concatenates all pages into a single String reply. If 3-4 active admins do this concurrently, the Provider's heap is consumed by multiple large in-flight String objects.
    SUGGESTED-FIX-CLASS: rate-limit

  - CATEGORY: INFO-LEAK
    SEVERITY: low
    PROMISE: "the caller's own audit_log rows (rows where actor = self); audit rows that mention the caller as a target without being authored by them are not included." and "audit_log_view is a Postgres view that exposes the same columns as audit_log minus any redacted fields" (commands.md §/export, security.md §DB roles)
    GAP: The ExportDataCollector queries audit_log_view which includes `target_contact_id`. While the view applies `redact_contact_id()`, the current database implementation (V5__identity_audit.sql) has this as a stub function that returns its input unchanged. A bot admin exporting their own audit rows will receive other users' full contact_ids in the `target_contact_id` column of every admin action they performed. The export code does not apply any application-level redaction as a second line of defense.
    REPRO: A bot admin who has banned, vouched, or granted other users sends `/export`. The reply includes their audit_log_view rows, each containing `target_contact_id` with the full unredacted contact_id of the target user. Until the `redact_contact_id` database function is implemented with real redaction logic, the export leaks full contact identifiers of other users.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

OUT-OF-MODEL:
  - The `isJsonLike` shortcut in ExportDataCollector.appendValue() inlines Types.OTHER values that start with `{` or `[` directly into the JSON output without escaping. PostgreSQL guarantees JSONB values are well-formed JSON, so this is safe for JSONB columns. However, if a future schema change introduces a non-JSONB Types.OTHER column whose value coincidentally starts with `{` or `[`, the raw text would be inlined and could break JSON structure. Not currently exploitable since all Types.OTHER columns in the positive list are either UUID or JSONB.

RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: AUDIT-EVASION
    SEVERITY: medium
    PROMISE: docs/spec/security.md §LLM output sanitizer: "Every match is
      audit-logged; rows aggregate per distinct token per sanitize call
      and carry the exact occurrence count — counted, never throttled."
      The same section scopes the sanitizer to "the full set of
      LLM-authored output surfaces: chat-mode replies, on-the-fly
      /summary prose, periodic group digests, /retry re-rolls, and any
      future LLM-emitted text." The spec's re-eval precedent
      (RE_EVAL_RELEASED, §Re-evaluation job) shows the same posture on
      the ingest side: automated security-relevant transitions carry a
      committed audit row precisely so attacker probing at feed scale is
      not invisible to operators.
    GAP: Re-audit round 2 — verified NOT closed in the new diff (the
      round-2 change was the renderPrompt substitution-order hardening
      only). IngestTranslationWorker.sanitize (infochat-collector/src/
      main/java/app/zcat/infochat/collector/eval/translation/
      IngestTranslationWorker.java:429-440) runs the shared
      LlmOutputSanitizerCore closed-list strip over translator output
      before storage but emits only one WARN per distinct token; the
      class javadoc (:112-116) states explicitly that the collector-side
      application emits no audit_log rows, and LlmOutputSanitizerCore is
      declared pure, so no audit path exists anywhere for this surface.
      Not a capability constraint: the collector DB role is INSERT-only
      on audit_log (security.md §DB roles), so the spec-committed
      LLM_OUTPUT_SANITIZED row was deliverable from this call site.
      Scope re-examination (independent, per the round-2 framing): the
      "delivered to a user" anchor cuts toward exclusion, but the diff
      itself concedes the surface is inside the sanitizer's mandate by
      applying the redaction half to it ("the SAME sanitization
      pipeline"), and the spec attaches the audit row to every match of
      that sanitizer, per sanitize call — a surface cannot be inside the
      mandate for the strip and outside it for the audit row. If the
      user judges the anchor excludes retrieval-only fields, the correct
      resolution is a spec amendment stating that boundary, not a silent
      half-application of the control.
    REPRO: An adversary publishing to a subscribed non-English feed
      laces posts with privileged-command tokens (the translator is
      instructed to translate faithfully, so its output carries them).
      The worker's sanitize pass redacts the tokens from title_en/
      body_en before storage — the preventive control fires — but the
      only record is a WARN in collector stdout; /audit shows nothing,
      so translation-laundering probes at feed scale leave zero
      operator-visible audit trail, unlike every provider-side sanitizer
      hit and unlike the ingest-side RE_EVAL_RELEASED transitions.
    SUGGESTED-FIX-CLASS: audit-log-coverage

OUT-OF-MODEL:
  - Semantic-pollution via the translation channel: a hostile feed can
    shape its own English anchor text (crafted source prose that the
    translator faithfully renders) to influence search_tsv/embedding
    retrieval ranking of its own posts. Retrieval-integrity commitments
    are not in the documented threat model; flagged so the user can
    decide whether to extend it. (Carried over from round 1; still
    applicable to the shipped design.)

OUT-OF-MODEL:
  - Snapshot-served ban TOCTOU: the step-4 ban predicate now reads `is_banned`
    from the step-1 `UserSnapshot` (InboundRouter.java step-1 lookup → step-4
    check) instead of a fresh live query. A ban committed by an admin in the
    microsecond window between the step-1 SELECT and the step-4 check will let
    the single in-flight message through, taking effect only on the next
    inbound. This is explicitly within the spec's ban model ("Banned-user check
    is the first thing after identity resolution"; ban "takes effect on the next
    inbound") — the prior live-query carried an identical read-to-reply window,
    and the spec mandates ordering, not a dedicated second query. Noted only so
    the user can decide whether the spec should commit to a stronger
    "freshest-state ban read" guarantee; not a gap against the current threat
    model.
  - Command-body-cap value surface: `infochat.command.body-cap` (8192 default,
    256 in `%test`) is an additive character bound on normalized slash bodies
    layered above the existing `maxInboundBodyBytes` byte cap. Profile values are
    operator/design-tier config, not a spec commitment, so a too-permissive value
    is an operator-tuning concern outside the threat model rather than a delivery
    gap.

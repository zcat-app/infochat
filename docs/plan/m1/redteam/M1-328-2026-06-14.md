OUT-OF-MODEL:
  - Unbounded pre-validation tag list in parseTags(). TaggerWorker.parseTags()
    (infochat-collector/.../TaggerWorker.java:416-422) builds an ArrayList from
    every textual element of the LLM's "tags" array (or every comma-split token
    in the "TAGS:" fallback) with no length cap before validate() applies
    MAX_TAGS_PER_POST. A model coaxed into emitting an enormous tag array would
    have the whole list materialised and normalized before the cap drops the
    overflow. This is not a threat-model gap: the threat model's bounded-input
    commitments are the LLM TOOL surface (§Prompt-injection defenses — "All
    free-form string and list inputs across every tool below are length-bounded
    by a profile-driven cap"), which governs the Provider's LLM tool dispatcher,
    NOT the Collector ingest tagger. The spec makes no commitment to a
    parse-time tag-list cap on Stage-1/2 tagger output; the practical bound is
    the LLM's own generation token budget, and the work is O(n) over already
    received bytes. The diff under audit (the post.tags storage cap) is itself a
    hardening addition beyond any spec-level promise — the threat model's only
    tagger commitment is "Tagger failure -> fall back to source.bootstrap_tags"
    (§Failure handling), which the diff leaves intact (the zero-valid bootstrap
    path is unchanged). Flagged so the user can decide whether to extend the
    model with an explicit ingest-side parse cap; not counted as a FINDING.

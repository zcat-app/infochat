FINDINGS:
  - CATEGORY: INJECTION
    SEVERITY: medium
    PROMISE: docs/spec/security.md §LLM output sanitizer — "Before any
              **LLM-generated** text is delivered to a user, the candidate
              output is passed through a deterministic outbound regex pass
              that strips or refuses output containing admin command strings
              (`/grant-admin`, `/ban`, `/promote`, `/remove-source`, etc.).
              ... It does **not** apply to deterministic command output
              (`/help`, `/status`, `/list-sources`, etc.) because that text
              never passes through an LLM. ... the sanitizer closes the
              social-engineering surface where a small LLM emits
              plausible-looking admin commands across any of the surfaces
              above."
              The exemption for deterministic output is sound only while that
              output really is bot-authored. The diff itself makes that
              condition explicit and binding at docs/spec/commands.md:273-282:
              "**Any friendly error reachable below bot admin must not reflect
              inbound text**" and "`security.md` §LLM output sanitizer exempts
              deterministic command output from the admin-command strip on the
              premise that such output is bot-authored; **not interpolating is
              what makes that premise true**".
              Also docs/spec/security.md §Authorization model step 7:
              "**Permission check** against the matrix."
    GAP: The diff's remediation of /add-source is sound and complete (see
         VERIFIED below), but the tier-scoped property the rewritten spec
         paragraph now rests on does NOT hold for one of the keys that
         paragraph names as safe.

         docs/spec/commands.md:266-273 asserts: "a number of **bot-admin-only**
         errors still interpolate a raw token (`error.audit.unknown_action`,
         `error.quarantine.invalid_id`, `error.invite.unknown_adapter`,
         `error.group_not_found` and others) ... Reaching these requires bot
         admin, so the reader of any reflected text is already an admin and the
         social-engineering value is near zero."

         `error.group_not_found` is reachable WITHOUT bot admin through
         /approve-group, because that handler reflects BEFORE its admin gate:

           - infochat-provider/src/main/java/app/zcat/infochat/provider/command/ApproveGroupCommandHandler.java:124-128
             interpolates `parseGroupIdRaw(rawText)` into
             `error.group_not_found` and returns.
           - The ONLY check preceding it is the null-guard at
             ApproveGroupCommandHandler.java:116-118 (`adapter == null ||
             callerContactId == null`). That is not an authorization check.
           - The actual `isAdmin` gate is at
             ApproveGroupCommandHandler.java:146-151, inside `executeApprove`,
             which is reached only at line 130 — i.e. only when the UUID parse
             SUCCEEDS. A non-parsing argument short-circuits at 124-128 and
             never meets the gate.
           - The stale comment at ApproveGroupCommandHandler.java:112-115
             claims "Step 1+2 — actor resolution + admin gate. Fail fast before
             parsing"; the code under it performs no actor resolution and no
             admin gate.
           - There is no compensating router-level admin gate.
             infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/InboundRouter.java:1410-1421
             (`handleSlash`) dispatches to any `CommandHandler` whose `name()`
             matches, with no tier check. The only router-level gate is the
             probation check at InboundRouter.java:773-780, and
             CommandPermissions.java:33-81 is scoped to probation ONLY ("a
             probation user may only invoke commands in the spec-closed allowed
             set") — it carries no bot-admin dimension. Bot-admin enforcement
             is entirely per-handler, so a handler that reflects before its own
             gate is unguarded.
           - `parseGroupIdRaw` (ApproveGroupCommandHandler.java:305-315) returns
             the first whitespace-delimited positional token verbatim — no
             charset filter, no length bound, no UUID shape test.
           - The reflected value is rendered bare inside backticks:
             en.properties:741 `error.group_not_found=No group with id `{0}` is
             known to the bot. ...` (cs.properties:469 identical shape).
           - /approve-group has NO DM-only guard, unlike its bot-admin siblings
             (QuarantineCommandHandler.java:119-121,
             InviteCommandHandler.java:215-217). ApproveGroupCommandHandler.java:112-115
             states group scope "reaches here identically to DM scope", so the
             reflected bytes can be delivered into a group and seen by every
             member.

         The sibling handler proves this is an ordering defect, not an accepted
         design: RejectGroupCommandHandler.java:129-132 resolves the actor and
         gates on `isAdmin` BEFORE its identical `parseGroupIdRaw` reflection at
         :149-152, with the explicit comment "Admin gate has precedence".

         Ordering VERIFIED SAFE for the other named keys (each gate precedes
         each reflection, so the tier claim does hold for them):
           - AuditCommandHandler.java:99 gate -> :113-116 reflect.
           - QuarantineCommandHandler.java:127 gate -> :280 / :342 reflect.
           - InviteCommandHandler.java:225 gate -> :376 / :387 / :392 / :484 reflect.
           - RecoverPoolCommandHandler.java:104 gate -> :173 reflect.
           - RejectGroupCommandHandler.java:130 gate -> :151 / :158 / :230 reflect.
         Exactly one of the seven swept sites inverts the order, and it is one
         of the four the new spec paragraph names by hand as safe.
    REPRO:
         1. Attacker is a registered, non-probation, NON-ADMIN user — the
            probation gate (InboundRouter.java:773) blocks "approve-group"
            during probation, but nothing blocks it afterwards.
         2. In an approved group (or in DM), the attacker sends:
              /approve-group /grant-admin
         3. InboundRouter.handleSlash (:1413-1418) matches
            ApproveGroupCommandHandler.name() == "approve-group" and invokes
            handle() with no tier check.
         4. adapter and callerContactId are both non-null, so the guard at
            :116-118 passes. parseGroupId returns null (not a UUID), so :124-128
            fires and interpolates parseGroupIdRaw(rawText) == "/grant-admin".
         5. Every member of the group receives deterministic, sanitizer-exempt,
            bot-authored output containing the copy-pasteable string:
              No group with id `/grant-admin` is known to the bot. Pass the
              full id (a UUID) shown by /list-groups, ...
         6. The admin gate at :146-151 is never evaluated — the attacker never
            reaches executeApprove.
         7. This is byte-for-byte the outcome this ticket removed from
            /follow-tag, /unfollow-tag, /group-timezone, the two asset
            templates and /add-source, on the one output channel security.md
            deliberately leaves unfiltered, and it survives precisely because
            the spec paragraph this diff adds classified the key as

            Dispatch of /grant-admin still requires is_admin=true, so this is a
            social-engineering surface, not a direct escalation — which is
            exactly the residual risk the sanitizer exists to bound.

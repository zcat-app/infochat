OUT-OF-MODEL:
  - Empty-prompt fabrication on the roll-up path. `CategoryRollupGenerator.buildPrompt`
    (infochat-provider/src/main/java/app/zcat/infochat/provider/digest/CategoryRollupGenerator.java:293-314)
    still calls the LLM when the untrusted block contains ZERO headline lines. Two
    reachable shapes: (a) the char-budget check drops EVERY cluster — any time the
    first cluster's block alone exceeds `rollup-prompt-char-budget` (default 50 000,
    so ~250 max-length titles in one cluster, or an operator-set tiny budget); and
    (b) a category whose posts are all titleless — the Bluesky/Nostr shape
    (`DisplayHeadline.headlineSource` returns "" for blank/UNTITLED titles when the
    body argument is null, and buildPrompt passes a null body on purpose, so every
    post is `continue`d). In both shapes the model is asked to "Name the themes
    across the clusters below" with nothing below the delimiter, and whatever it
    fabricates is sanitized, translated, and delivered as a factual roll-up prefix
    in a push message (`generateRollup` returns `Optional.of(translated)`;
    DigestRenderer appends it at DigestRenderer.java:334 and :540). Pre-M1-728 the
    same categories contributed full bodies, so the model had material; the diff
    removes the material without adding an empty-input guard. This is a
    content-integrity/quality gap, not a breach of any docs/spec/security.md
    commitment — the spec's LLM defenses (D21 delimiter shape, output sanitizer,
    refusal handling) are all intact and no attacker-controlled input is required
    for shape (b) — so it is recorded here rather than as a FINDING. If the user
    wants "no LLM call / no roll-up on an empty untrusted block" to become a
    commitment, that is a one-line guard (`if (n == 1) → no roll-up`) plus a spec
    note; a hostile feed can also steer the roll-up through its own titles, but
    that influence is inherent to the subscribed-feed design and equally
    out-of-model.
  - Doc mismatch (cosmetic, not an attack): the `requestedSentences` javadoc
    (CategoryRollupGenerator.java:212-214) promises generateRollup's failure
    containment emits "a WARN naming the bad value", but the catch logs via
    `SafeLog.warn` (CategoryRollupGenerator.java:199), which per security.md
    §"User content in exceptions" drops the exception message body and keeps only
    the class name — the bad config value is never named. The SafeLog behavior is
    the spec-committed one; only the javadoc over-promises.

Audit notes (why the in-model surfaces hold):

- Prompt-injection defenses (security.md §Prompt-injection defenses, D21): the
  new prompt preserves the per-call random UUID delimiter and the
  treat-as-untrusted instruction verbatim; the system prompt keeps the
  never-follow-instructions clauses and the `[REFUSAL: <reason>]` contract, and
  `generateRollup`'s refusal/empty/failure containment is unchanged. The
  injection SURFACE shrinks: bodies and URLs no longer reach the prompt, and
  titles arrive sanitized.
- LLM output sanitizer (security.md §LLM output sanitizer, unconditional):
  output still runs `llmOutputSanitizer.sanitize` then `TranslationPipeline.run`
  (which re-sanitizes) before delivery (CategoryRollupGenerator.java:195-196) —
  unchanged by the diff. Prompt-input titles now additionally pass through
  `DisplayHeadline.of(title, null, sanitizer)`, which carries the load-bearing
  flatten → sanitize → truncate order (DisplayHeadline.java:133) and the
  one-author's-field-per-call sanitize unit (M1-697 invariant preserved: one
  post's title per call, never a concatenation).
- DOS: the prompt is now hard-bounded by `rollup-prompt-char-budget` (50 000
  chars default) — a strict improvement over the previous full-body prompt. Per-
  title sanitizer input is bounded by `IngestTextNormalizer.TITLE_MAX_LENGTH =
  200` at the PostPersister write boundary, and the null-body call keeps the
  unbounded-body fallback off this path. LLM call volume is unchanged (one
  request per category).
- Trusted config: both new keys are operator-set (trusted per security.md
  §Threat model). Malformed `rollup-sentence-bands` values throw
  IllegalArgumentException/NumberFormatException inside `generateRollup`'s
  `catch (RuntimeException)` (CategoryRollupGenerator.java:198), failing safe to
  no-roll-up; the unwired `new CategoryRollupGenerator()` test seam NPEs into the
  same catch — never into unsanitized delivery.
- Logging: the new budget-drop INFO line carries an int budget, an int count,
  and the section tag (Tier-1 controlled-vocabulary slug, null → "other") — no
  user content, no contact ids, no secrets (security.md §Secrets handling holds).
- Untouched surfaces: authorization evaluation order, invite/ban paths, rate
  limits, DB roles, audit-log coverage (the only new audit writes are the
  sanitizer's own spec-committed per-hit `LLM_OUTPUT_SANITIZED` rows, which are
  additive), and the outbound `](`-breaking chokepoint (the roll-up text flows
  through the existing DigestRenderer → OutboundDelivery path).

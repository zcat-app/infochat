# /redteam M1-222 — verbatim verdict (2026-06-07, second audit: commit 563563f)

RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: DOS
    SEVERITY: low
    PROMISE: "Per-group command rate (D47) — a sub-bucket per approved group bounding total command volume from all members within a sliding window. Only meaningful for approved groups (pending/rejected groups never reach command dispatch). When the cap fires, the reply is a fixed 'this group has reached its command rate limit' message. Profile-driven." (security.md §Rate limiting)
    GAP: The diff completes the D47 rate-cap family in `RateCapBucket` (group-reply bucket pre-existing at `infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/RateCapBucket.java:199`, group-LLM bucket added at line 232) but the third promised sub-bucket — per-group command rate — has no implementation anywhere in the Provider. Grep for `tryAcquireGroupCommand`-shaped methods, any `command.rate`/`command_rate` bundle key, or the spec's fixed "this group has reached its command rate limit" reply returns nothing in `infochat-provider/src/main`. `RateCapBucket` is the natural home (it now hosts the other two D47 sub-buckets and the M1-222 work touched its constructor seams, eviction sweep, and config block at `infochat-provider/src/main/resources/application.properties:372-380`), so the absence is structural, not a different-file placement. Residual exposure is bounded: the per-user transport cap (InboundRouter.java:359) and the per-group reply bucket (GroupApprovalCheck.java:122, which fires for every existing group row before dispatch and silently drops over-cap) cap the same inbound/outbound volume, which is why this is low rather than medium — but the spec's distinct fixed-reply overflow semantics for command volume are undelivered, and aggregate per-group DB-read cost from many members each under their personal transport cap is gated only by the reply bucket's silent-drop budget.
    REPRO: An approved group with N registered, post-probation members; each member sends slash commands (e.g. `/summary`, `/list-sources --page k`) at just under their individual transport cap. No per-group command bucket exists to bound the aggregate, so total command dispatch (and the DB queries behind each) scales linearly with N until the per-group reply bucket starts silently dropping replies — at which point command processing cost has already been paid per-inbound and the spec-promised fixed "command rate limit" reply is never produced. The spec promised a per-group aggregate command bound with an explicit overflow message; neither exists.
    SUGGESTED-FIX-CLASS: rate-limit

OUT-OF-MODEL:
  - All rate-cap state (`LlmRateCap` timestamp deques, all three `RateCapBucket` maps) is in-process memory: a Provider restart re-mints full allotments for every user and group. The spec never promises persistence for rate buckets and operator infrastructure is trusted, so a restart-coinciding flood window is outside the documented model — flagged in case the user wants the spec to state the in-memory trade-off explicitly.
  - Theoretical race between `tryAcquireGroupLlm`'s `computeIfAbsent` and the eviction sweep can let one acquire decrement an already-evicted bucket while the next acquire recreates a full one (≤1 surplus token, only after a full idle refill window, requires sweep-coinciding timing). Same pre-existing shape as the contact and group-reply buckets; not meaningfully exploitable, noted for completeness only.

Audit notes supporting the CLEAN-elsewhere conclusion (verified, not assumed): the per-group LLM bucket's two call sites cover every group-scope LLM surface that exists in v1 — group `/summary` returns `no_posts_yet` before any LLM work (`SummaryCommandHandler.java:148-151`) and non-digest `/retry` rejects non-DM scopes (`RetryCommandHandler.java:348-353`), so "chat replies + /summary + /retry re-rolls" is delivered positionally; the per-user-cap-fires-first ordering matches spec at both sites; the `refund` path conserves token counts under all interleavings I traced (one `pollLast` per one `tryAcquire`, keyed per-user, only on the no-LLM rejection path, so it cannot be leveraged to exceed personal budget); the fixed `group.llm_rate_limit` overflow reply is bounded outbound by the step-3.5 per-group reply bucket which fires for every existing group row regardless of approval state; the eviction-threshold widening (`max(evictionThreshold, refillWindow)`) closes the rebirth-at-full hole for the 15-minute windows without changing contact-bucket behavior; both existing locale bundles (`en`, `cs`) carry the new key; digest paths have no bucket call site, matching the "periodic digests do NOT count" exclusion; and `/retry --digest` audit rows are written before the cap gates, keeping rate-capped attempts audit-visible (audit-log coverage preserved).

FINDINGS:
  - CATEGORY: INJECTION
    SEVERITY: low
    PROMISE: docs/spec/security.md §Threat model — "The **Collector** is
              exposed to arbitrary feed content. Every RSS publisher,
              Reddit poster, Bluesky user, etc. is untrusted." The
              in-model standard for a wire-derived NUMERIC crossing a
              trust boundary is stated at §Trust boundaries item 9:
              "Provider-reported **numeric usage** (token counts) is
              checked at that same boundary before it reaches the
              counters: a count is impossible, and the report discarded
              whole rather than clamped, when it is negative … so … no
              counter can be driven backwards or inflated to a
              magnitude that swamps later honest increments". The diff
              introduces the ingest-side mirror of that boundary and
              states the same bound in its own contract
              (NormalizedPost.java:60-64: "clamped to
              ±MAX_ENGAGEMENT_COUNT before the multiply, so an
              upstream-supplied count cannot overflow 2 * reposts +
              likes into a negative score").
    GAP: The clamp is applied to an `int` that has already lost its
         magnitude and its SIGN. Both parsers admit any JSON numeric
         node and narrow it with `asInt()`:
         infochat-collector/.../fetcher/bluesky/BlueskyResponseParser.java:131-137
         (`if (!child.isNumber()) return null; return child.asInt();`)
         and infochat-collector/.../fetcher/reddit/RedditResponseParser.java:159-165
         (identical helper). Jackson's `LongNode.asInt()` /
         `BigIntegerNode.asInt()` are truncating narrowing conversions,
         not saturating ones, so a JSON integer outside the `int` range
         wraps modulo 2^32 BEFORE
         infochat-core/.../ingest/NormalizedPost.java:97-103 (compact
         constructor) and :146-157 (`clampCount`) ever see it. Two
         concrete consequences:
         (a) `likeCount: 2147483648` becomes `-2147483648`, is clamped
             to `-MAX_ENGAGEMENT_COUNT`, and — with `repostCount` set
             the same way — `deriveSocialScore` yields -1610612733, the
             most negative value the design permits. The javadoc's
             "cannot … overflow into a negative score" holds only for
             values that already fit in a Java `int`; the negative
             arrives by narrowing rather than by the multiply, but the
             stored result is the one the bound exists to forbid.
         (b) `likeCount: 4294967296` becomes exactly `0`, which is
             persisted by PostPersister.java:215-217 as a non-NULL `0`.
             That is the precise null-vs-zero conflation the whole
             boundary exists to prevent (NormalizedPost.java:38-42,
             BlueskyResponseParser.java:124-129, PostPersister.java:58-62):
             the row now asserts "seen and ignored" for an observation
             the upstream never made. The diff's own tests stop at
             2147483647 (BlueskyResponseParserTest
             `hugeRepostCountIsClampedSoTheScoreStaysPositive`,
             RedditResponseParserSocialSignalTest
             `hugeScoreIsClampedSoTheScoreStaysBounded`), i.e. exactly
             one below the first wrapping value, so no test pins the
             out-of-range case.
         Not currently exploitable for user-visible harm: grep shows no
         main-source reader of `likes` / `reposts` / `social_score`
         anywhere (only V7__joins_post.sql:160-162 declares them and
         PostPersister writes them), and the intended consumers — the
         `{{#has_social}}social score: {{score}}{{/has_social}}`
         summarizer-prompt block (docs/design/05-llm-and-embeddings.md
         §5.4) and the M1-724 prominence ordering — are not wired yet.
         Hence low: the stored value is corrupt at rest, and the first
         consumer inherits the corruption rather than the documented
         bound.
    REPRO: 1. Any non-banned user runs `/add-source` for a
              bluesky-kind source whose identifier is a getAuthorFeed
              URL on a host the adversary controls (BlueskyFetcher.java:25-31,
              :113-121 request the source identifier verbatim; the SSRF
              allowlist gates IP ranges, not who owns the host, per
              §SSRF and outbound connections). The same works for a
              reddit-kind source (RedditFetcher.java:117-124 appends
              `.json` to the supplied URL). A hostile or compromised
              upstream API reaches the same code path with no
              `/add-source` step at all, which is the case the threat
              model names directly.
           2. The host answers with a well-formed feed page whose entry
              carries `"likeCount": 2147483648, "repostCount":
              2147483648` (both in-range for JSON, out of range for a
              Java `int`).
           3. `intOrNull` accepts them (`isNumber()` is true),
              `asInt()` wraps each to `-2147483648`, `clampCount`
              floors each at `-536870911`, and PostPersister stores
              `likes = -536870911`, `reposts = -536870911`,
              `social_score = -1610612733`.
           4. Repeat with `"likeCount": 4294967296` to store a
              fabricated `likes = 0` / `social_score = 0` — a
              "seen and ignored" observation the upstream never
              reported — on a row that should have carried either a
              clamped magnitude or SQL NULL.
           The system should not have allowed it because this record is,
           by its own javadoc, "where an untrusted JSON number first
           becomes a typed domain value" and is the single place the
           project chose to carry the bound for "every present and
           future fetcher".
    SUGGESTED-FIX-CLASS: input-sanitization

OUT-OF-MODEL:
  - In-range engagement inflation. Even with the wrap fixed, a
    source-controlled `likeCount` of 536870911 (exactly
    MAX_ENGAGEMENT_COUNT) is accepted verbatim and yields the maximum
    permitted `social_score`. security.md commits to a specific,
    reproducible ordering for `searchPosts`
    (`COALESCE(published_at, fetched_at)` DESC, with an explicit
    argument about why an undated post cannot seize the head) but makes
    no commitment at all about engagement-derived ranking, so a feed
    that simply claims enormous counts to dominate any future
    social-signal ordering — and thereby to occupy the positions
    re-injected first into the chat prompt via the D28 pre-fetch — is
    outside the documented model today. If M1-724 or any later ticket
    wires `social_score` into ranking or into the
    `{{#has_social}}` prompt block, the model should be extended with
    the same kind of adversarial-ordering argument security.md already
    writes for `published_at` / `ready_at` / `fetched_at`.
  - Fidelity loss from Jackson number coercion generally: a
    floating-point `likeCount` (e.g. `1e300`) saturates to
    Integer.MAX_VALUE and a fractional value truncates. This is
    data-fidelity rather than a security commitment, and is noted only
    because it shares the `asInt()` call site with the finding above.

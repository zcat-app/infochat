Audit summary:

The diff under audit (M1-470) is a single, self-contained DoS-hardening
change to the shared SSRF library (`infochat-ssrf`
`SsrfGuardedHttpClient.java`) plus its test. It moves the
`bodyReadStartNanos` sample out of `supervisedDrain` and up into
`get(URI, Map)`, captured ONCE before the redirect loop
(SsrfGuardedHttpClient.java:414), then threads that single origin into:
  - every followed-hop drain `discardBounded(body, bodyReadStartNanos)`
    (line 463),
  - the terminal `readBounded(terminalResponse, bodyReadStartNanos)`
    (line 504),
  - and through `supervisedDrain` into the per-chunk deadline check in
    `supervisedReadChunk` (lines 706-712 and 730-735).

Threat-model bearing (security.md §"SSRF and outbound connections":
"Redirect, body-size, connect-timeout, and read-timeout caps are
enforced"): the change STRENGTHENS the read-timeout/body-read-deadline
cap. Before the fix, `supervisedDrain` re-sampled the deadline origin at
every body-read phase, so a self-redirecting host obtained
(redirectCap + 1) independent full `bodyReadDeadline` budgets and could
hold a fetcher virtual thread far past the documented bound while each
individual read stayed under the per-read watchdog. After the fix the
cumulative body-read wall-clock across all hops is bounded by ONE
`bodyReadDeadline`. This delivers MORE of the threat model's promise, not
less. No commitment in the threat model is weakened or left unmet by the
diff.

Adversarial checks performed and cleared:
  - Deadline-sharing data path verified end to end (capture site,
    every call site, and the two enforcement points in
    supervisedReadChunk). The shared start time is correctly used; no
    hop receives a fresh budget. No TOCTOU gap introduced — the existing
    B-DEADLINE-TOCTOU clamp (lines 714-722) still bounds per-read
    overshoot.
  - Test integrity: the new `redirectChainSharesOneBodyReadDeadline`
    test asserts the abort is BODY_READ_DEADLINE_EXCEEDED mid-chain
    (distinguishing fix from the pre-fix REDIRECT_CAP_EXCEEDED outcome)
    and that >1 hop is traversed; it is a genuine behavioral test, not a
    weakened/disabled one. The two pre-existing tests were edited only to
    pass `System.nanoTime()` to the new `discardBounded` signature,
    preserving their original assertions (BODY_CAP_EXCEEDED,
    BODY_READ_TIMEOUT/DEADLINE). No assertion was loosened.
  - No new input-validation, auth, isolation, audit, or admin-tier
    surface is touched. The mechanically-extracted "ban handling" hit in
    the inventory is a false positive: it points at a test-comment line
    about close()-drain semantics, unrelated to ban handling.

OUT-OF-MODEL:
  - The body-read deadline (now anchored at get() entry) bounds
    body-read + inter-hop time, but the overall worst-case wall-clock of
    a multi-redirect call is still approximately
    redirectCap x requestTimeout (slow per-hop header responses) + one
    bodyReadDeadline, because each hop's connection/header phase is
    governed by the separate per-request `requestTimeout`, not the shared
    body-read deadline. The threat model promises connect/read-timeout
    caps "are enforced" (they are, per hop) but does NOT commit to a
    single aggregate wall-clock bound for an entire redirect chain. This
    is a pre-existing design property unchanged by this diff, not a gap
    the diff introduces; flagged only so the user can decide whether a
    whole-call wall-clock cap is worth a future spec amendment.

FINDINGS:
  - CATEGORY: INFO-LEAK
    SEVERITY: medium
    PROMISE: "Stage 2 — LLM judge... is the actual security boundary"
      (docs/spec/security.md §Ingest pipeline: "Stage 1 is a coarse
      filter, not a complete defense... Stage 2 is the actual security
      boundary"), and §Failure handling: "Stage 2 verdict of INJECTION,
      MALWARE, or UNKNOWN → post stays QUARANTINED until admin review...
      a degraded judge must never auto-release." The V69 migration's own
      header restates the commitment this guard exists to deliver:
      "An admin working the review queue can approve a Stage 1 row while
      the post's first-pass Stage 2 verdict is still in flight (seconds
      normally, longer under semaphore queue-wait + retry backoff in
      Stage2Worker): the post is then READY and announced to users until
      the verdict transaction commits and re-hides it"
      (V69__approve_quarantine_verdict_owed_guard.sql:1-13) — i.e. the
      guard must refuse exactly that approve.
    GAP: The new predicate is `stage1_flagged = TRUE AND
      stage2_verdict IS NULL AND status = 'QUARANTINED'`
      (V69__approve_quarantine_verdict_owed_guard.sql:107-111, the
      `IF EXISTS (SELECT 1 FROM post ... AND status = 'QUARANTINED')`
      guard). The added `status = 'QUARANTINED'` conjunct re-opens the
      first-pass in-flight window the ticket was written to close: a
      Stage-1-flagged post owed its first-pass verdict is **RAW**, not
      QUARANTINED — "A regex match scrubs the body and records a
      quarantine row but leaves post.status='RAW' so Stage 2 can judge"
      (Stage1Pipeline.java:128-135; also :82-88 "post.status stays
      'RAW'... The ONLY exceptions are the watchdog and
      sanitizer-exception fail-closed paths"), and Stage1Worker.java:
      191-194 states the bitmap outright: "(stage1_flagged &&
      !stage2_done implies status='RAW': the only QUARANTINED posts with
      stage2_done=FALSE are the Stage-1 fail-closed paths, which leave
      stage1_flagged=FALSE)". So while the judge call is queued or in
      flight the guard's third conjunct is false and the approve sails
      through: span restored, status='READY', new_post NOTIFY fired,
      stage2_failed cleared — before any judgment exists. The round-1
      predicate (`stage2_done = FALSE`, no status conjunct) DID refuse
      this window; the remediation traded first-pass coverage for
      re-eval coverage while its header and the ticket acceptance text
      ("covering both the first-pass-in-flight window and the
      re-eval-queue window") claim both. The new pin tests make the
      regression invisible: `approveRaisesWhenStage2VerdictOwed` seeds
      `(stage1_flagged=true, stage2_done=false, status="QUARANTINED")`
      via the convenience seed (QuarantineProcedureNotifyIT, new
      seedFixture default `"QUARANTINED"`) — a bitmap Stage1Worker
      documents as impossible for a flagged post — and
      QuarantineCommandHandlerTest.approve_verdictOwed does the same via
      `UPDATE post SET stage1_flagged = TRUE, stage2_done = FALSE` on a
      QUARANTINED fixture. No test seeds the production in-flight state
      (RAW), so the suite is green while the guard never fires there.
      Two consequences of the same root cause: (a) common case — the
      exposure is transient (an INJECTION verdict re-hides per M1-739),
      but the new_post NOTIFY and the unredacted render already
      happened, which is precisely the "judge-condemned content is
      user-visible for the remainder of the window" outcome the guard
      exists to prevent; (b) stranded-verdict case — if the verdict
      never lands (crash between the Stage 1 commit and Stage 2
      completion, the orphan bitmap of Stage1Worker.java:170-199), the
      approved post is READY and never re-enters any recovery path: the
      orphan rescue re-selects stale RAW posts only, and the re-eval
      enumeration requires stage2_failed=TRUE or QUARANTINED
      (ReEvaluationJob.java:679-683), so the post is permanently
      released unjudged with Stage 1 redactions lifted. (Related, same
      conjunct, documented as deliberate in the ticket: the fail-open
      re-eval-queue class — RAW, stage2_failed=TRUE, verdict NULL —
      also passes the guard and approve's stage2_failed clear permanently
      cancels the owed re-evaluation; the ticket accepts this as the
      V41-pinned admin-approve lifecycle, so it is noted here for the
      user's weighing rather than counted as a separate finding.)
    REPRO: (1) A feed adversary publishes content that trips a Stage 1
      regex; Stage 1 redacts the spans, writes a PENDING quarantine row,
      and leaves the post RAW; the Stage 2 judge call queues behind the
      semaphore (window: seconds to minutes under queue-wait + retry
      backoff; unbounded if the worker crashes before the verdict
      commit). (2) An admin working `/quarantine list` — normal
      operation — sees the ordinary PENDING row and runs
      `/quarantine approve <id>`. (3) The guard evaluates
      `status = 'QUARANTINED'` against a RAW post, passes, restores the
      original (injection-shaped) span, sets status='READY', and fires
      the new_post NOTIFY: content no judge has ever seen is announced
      to users with redactions lifted. (4a) If the judge later returns
      INJECTION the post is re-hidden, but the announcement and
      unredacted render already occurred — the transient exposure M1-741
      exists to eliminate. (4b) If the verdict never lands, no path
      ever re-judges or re-hides the READY post: the release is
      permanent. The system shouldn't have allowed (3) because the
      ticket's own premise — and §Failure handling's "a degraded judge
      must never auto-release" — requires the guard to refuse while the
      first-pass verdict is owed, and the shipped predicate cannot see
      the state that obligation actually has.

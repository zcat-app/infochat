# Red-team audit: M1-151 (post-commit re-run, committed range)

Verbatim threat-actor verdict:

RED-TEAM VERDICT: FINDINGS

FINDINGS:

  - CATEGORY: AUDIT-EVASION
    SEVERITY: low
    PROMISE: "Authorization evaluation order on every inbound message. ... 7. **Permission check** against the matrix. ... 8. Audit-log the intent. 9. Execute." (security.md §Authorization model) — the diff itself cites this step-8 promise as the rationale for the new `REVOKE_ADMIN_INTENT` row ("the row's job is to survive the last-admin trigger rollback, so a refused attempt still leaves an operator-visible audit record", AuditAction.java:9-17).
    GAP: The intent row is gated by non-locking pre-checks that deliberately exclude two refusal paths that occur AFTER the permission check passes: target-unknown (step 5c) and target-not-admin (step 5d). `infochat-provider/src/main/java/app/zcat/infochat/provider/command/RevokeAdminCommandHandler.java:214-218` writes the intent only when `targetPre.isPresent() && targetPre.get().isAdmin`; the in-transaction 5c/5d branches (lines ~265-277 in the same file) roll back with no audit insert. So a fully-authorized bot admin who runs `/revoke-admin <contact>` against unknown or non-admin contacts passes step 7 (permission), reaches step 9 (execution attempt), receives a distinguishing reply (unknown vs. not-admin), and leaves zero rows in `audit_log` — the same class of "refused attempt invisible to operators" the ticket closes for the last-admin path, codified as intentional in the comment at RevokeAdminCommandHandler.java:205-208 ("guard-failing probes and no-op paths write no row").
    REPRO: As a bot admin on adapter A, issue `/revoke-admin <c1>`, `/revoke-admin <c2>`, ... across many contact ids. The reply distinguishes "unknown contact" from "not an admin" from "last admin", letting the admin enumerate which contacts are registered and which hold the admin bit, with no `REVOKE_ADMIN_INTENT` or `REVOKE_ADMIN` row ever written. An operator later auditing admin behavior sees nothing for the probing session.
    SUGGESTED-FIX-CLASS: audit-log-coverage

  - CATEGORY: AUDIT-EVASION
    SEVERITY: low
    PROMISE: Same step-8 commitment ("Audit-log the intent" precedes "Execute"), plus the diff's own stated invariant that a trigger-refused `/revoke-admin` "still leaves an operator-visible audit record" (AuditAction.java:14-17; RevokeAdminCommandHandlerTest.java assertion "the REVOKE_ADMIN_INTENT row ... must survive the trigger-raised rollback so the refused attempt stays operator-visible").
    GAP: The intent pre-checks are plain MVCC reads outside the transaction (`lookupUser`, RevokeAdminCommandHandler.java:382-385), while the authoritative state is read later under `FOR UPDATE` inside `executeRevoke`. The two can diverge (the comment at RevokeAdminCommandHandler.java:209-212 acknowledges races but only in the spurious-row direction). The inverse race breaks the invariant: if the target's `is_admin` is FALSE at pre-check time but TRUE by the time step 5c/5f runs (concurrent `/grant-admin` landing in the window), the intent row is skipped, the transaction proceeds, and a `trg_last_admin_protection_update` refusal (SQLSTATE IC001) rolls back the in-tx `REVOKE_ADMIN` row — leaving the refused attempt with NO surviving audit record, exactly the failure mode V35/this diff exists to eliminate. Similarly, an executed revoke in that race window commits with a `REVOKE_ADMIN` effect row but no paired `REVOKE_ADMIN_INTENT`, breaking the intent+effect `request_id` correlation the class javadoc promises (RevokeAdminCommandHandler.java:245-247).
    REPRO: Admin A issues `/revoke-admin C` while C is not yet admin; concurrently admin B issues `/grant-admin C` and admin-state elsewhere shifts so C becomes the revoke target whose removal would trip the last-admin guard. A's pre-check sees `C.isAdmin=false` → no intent row; A's transaction then sees `C.isAdmin=true`, proceeds, trigger raises IC001, everything rolls back. The audit log carries no trace of A's refused revocation attempt.
    SUGGESTED-FIX-CLASS: audit-log-coverage

OUT-OF-MODEL:
  - The `REVOKE_ADMIN_INTENT` row is inserted on a separate auto-commit connection that never sets the `infochat.actor_id` GUC (insertIntentAudit, RevokeAdminCommandHandler.java:400-412), so the V24 `trg_audit_log_actor_check` actor-integrity trigger passes it through its GUC-unset carve-out — the intent row's claimed actor is unverified at the DB layer. This mirrors the pre-existing `BAN_INTENT` pattern (BanCommandHandler.java:216-222) and the actor-integrity GUC is a migration-level remediation, not a security.md commitment, so it is flagged here as a hardening note rather than a finding: setting the session GUC before the intent INSERT would extend the V24 protection to intent rows at no cost.
  - Distinguishing `BLOCKED_SSRF` from `TIMEOUT`/`UNREACHABLE` in `/add-source` probe replies (UrlProbe.java:436-444) gives a registered, post-probation user a low-rate oracle for whether a hostname resolves into the blocked (internal/metadata) ranges. The user could usually learn the same from public DNS, and the spec does not promise to hide the failure class, so this stays advisory. The diff's typed-reason mapping is otherwise a strict tightening (default arm → BLOCKED_SSRF is conservative; the old message-prefix match is gone), and V35's trigger bodies are byte-equivalent to V24 (update) and V5 (delete) apart from the added `USING ERRCODE = 'IC001'` — no logic weakening found.

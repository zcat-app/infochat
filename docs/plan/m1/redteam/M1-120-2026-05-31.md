## Verbatim verdict

```
RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: AUTH-BYPASS
    SEVERITY: high
    PROMISE: From security.md §Trust boundaries (1): "The adapter asserts identity via a stable, cryptographically anchored ID. Display names are informational and never used for authorization (decision D10)." And from §"What's intentionally NOT in v1": "Display-name-based @mention recognition. v1 mention recognition is anchored to the cryptographic contact id only ... string-matching the bot's display name in inbound message bodies is forever out of v1 because an attacker who spoofs or impersonates the bot's display name could otherwise suppress or fake mentions."
    GAP: `infochat-provider/.../ProductionAdapterBeans.java:127` constructs the bot's SimpleX D10 trust anchor as `new SimpleXIdentity(simplexAdmin.orElse(""))`. (a) When `infochat.adapters.simplex.admin` is not set (gate 7 only requires the union across adapters to be non-empty — a deployment running `simplex,signal` with admin configured only on Signal passes gate 7), the bot's queue address becomes the empty string. `SimpleXMentionParser.botMentioned` (lines 62-69 of SimpleXMentionParser.java) calls `Arrays.equals(botBytes, mentionBytes)` where `botBytes` decodes from "" to an empty byte array; any mention entry that base64-decodes to empty bytes, or any literal "" that falls through both base64 decoders to `getBytes(UTF_8)` (also empty), matches the bot. The forged-mention class of attack the spec forever excludes is reintroduced. (b) Even when `simplex.admin` IS set, it carries the operator's bootstrap admin queue address (the human admin), NOT the bot's own queue address — these are two distinct identities under §Per-adapter admin threat profile. The bot's identity recognition is wired to the operator's contact id, so `@admin` mentions are misinterpreted as bot mentions and vice versa.
    REPRO: Operator deploys `infochat.adapters=simplex,signal` with only `infochat.adapters.signal.admin` configured (recommended high-assurance placement per §Per-adapter admin threat profile, which lets operators omit admin per individual adapter). SimpleX bean wires `botIdentity=""`. Attacker in any SimpleX group sends a `newChatItem` whose mention list contains an empty-string entry, or any mention entry whose base64 decode yields 0 bytes. `SimpleXMentionParser.botMentioned` returns true; the group-scope message reaches Provider through `SimpleXGroupHandler.onGroupCandidate` as if the bot had been mentioned. The attacker can drive bot responses in groups without ever using a real mention. In configuration (b) where simplex.admin is set to the admin's queue address, the attacker mentions the admin in a group and the bot processes the message as if it were the addressee, conflating admin↔bot identity at the trust-anchor layer.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

  - CATEGORY: AUTH-BYPASS
    SEVERITY: medium
    PROMISE: From security.md §Per-adapter admin threat profile: "Each enabled adapter has a different real-world compromise surface, and admin rows are per-(adapter, contact_id) ... Cross-adapter elevation is impossible by design (/grant-admin is inbound-adapter-scoped)." The per-adapter admin contact id is a separate, security-critical operator input; conflating it with the bot's own identity erases the per-adapter scoping that bounds blast radius.
    GAP: `infochat-provider/.../ProductionAdapterBeans.java:96-98, 111, 127, 234-241` reuses the single config key `infochat.adapters.<adapter>.admin` as BOTH (1) the bootstrap admin's contact id (consumed by AdapterRegistry gate 7 — `AdapterRegistry.java:221-243`) and (2) the bot's own per-adapter identity passed into `SimpleXAdapter`/`SignalAdapter`. These are distinct security primitives. An operator rotating the admin contact id (the documented "SimpleX queue rotation" mitigation in §Per-adapter admin threat profile) will inadvertently change the bot's identity at the same time, breaking mention recognition across all groups. Conversely, any future feature that surfaces the bot's identity (e.g., a `/whoami` for users to verify the bot's queue address) would leak the bootstrap admin's queue address to every user.
    REPRO: Operator follows the spec-recommended rotation procedure ("operator generates a fresh queue, updates the bootstrap property, restarts; the prior admin row is left in place per deployment.md §Bootstrap admin drift") — they rotate `infochat.adapters.simplex.admin` to a fresh queue. The bot's group-mention recognition silently switches to the new value: every existing group's @mention of the bot (which still references the bot's actual old queue address surfaced by simplex-chat) now misses; the bot goes silent in all groups. Worse, the new value (the new admin's private queue address) is now compared against every inbound mention list — exposing a side-channel where group members can probe whether their messages "match" the admin's queue without ever seeing the address directly.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

  - CATEGORY: DOS
    SEVERITY: medium
    PROMISE: From security.md §Trust boundaries (assumption): "Operator-set config (properties files, bootstrap JSON) is trusted" — i.e. operator inputs are validated at config-boundary before any traffic is served. The Producer's own javadoc at `ProductionAdapterBeans.java:251` acknowledges: "fail-fast with IllegalStateException naming the offending value so an operator can fix the exact property — this runs at Producer @PostConstruct time, before any traffic, satisfying the 'validation at system boundaries' carve-out from the No-defensive-code rule (config parsing is a system boundary)." `SimpleXConfig.validate()` (`SimpleXConfig.java:73-88`) is the documented validation entry point ("Provider invokes this during its startup gates; a failure here fails Provider startup") for filesystem/port checks.
    GAP: `infochat-provider/.../ProductionAdapterBeans.java:42-44` documents and intends: "The Producer does NOT call `SimpleXConfig#validate()`; validation runs only when `SimpleXAdapter#start()` is invoked." But `SimpleXAdapter.start()` (`SimpleXAdapter.java:155-198`) DOES NOT call `cfg.validate()` either — it goes straight to `SimpleXSubprocess.commandFor(cfg)` and `waitForWebSocketReady(cfg.wsPort())`. So the spec-mandated filesystem and port-range checks (binary exists+executable, dataDir exists+writable, wsPort in 1..65535) never run on the production path. An operator who configures `infochat.adapters.simplex.binary=/path/that/does/not/exist` or `simplex.ws-port=99999` (out of range) does not see a fail-fast startup error — the failure surfaces deep inside subprocess launch with an opaque ProcessBuilder/IOException, which `MessagingStartup.startAllAdapters()` (per the §6.7 resilience invariant) now SILENTLY ABSORBS via the broadened `catch (Throwable t)` clause. The deployment boots cleanly and serves traffic on the other adapters with the SimpleX path inert — no operator-visible signal that SimpleX is dead beyond a single ERROR log line whose exception message body is stripped by `SafeLog`.
    REPRO: Operator mis-types `infochat.adapters.simplex.ws-port=722654` (typo for 7265). Provider boots; AdapterRegistry passes all gates (no port-range check in the gates either); MessagingStartup invokes `simpleXAdapter.start()`; subprocess.start() succeeds or fails depending on environment; `waitForWebSocketReady(722654)` eventually throws (e.g. IllegalArgumentException from socket binding); the catch on line 86 logs via SafeLog with the exception class name only ("IllegalArgumentException"). Operator sees no actionable signal; SimpleX is silently inert. Equivalent for a non-executable binary path or non-writable data-dir — both intentional security-critical operator inputs that the spec wired to a validate() the diff never calls.
    SUGGESTED-FIX-CLASS: input-sanitization

  - CATEGORY: INFO-LEAK
    SEVERITY: low
    PROMISE: From security.md §"User content in exceptions": "Exception messages and stack traces emitted via the application logger MUST NOT contain user-authored prose ... The original Throwable is never passed to the underlying SLF4J logger." From §"Known framework-level logging risks": logger-level baseline keeps Hibernate parameter trace etc. at WARN — but this rule explicitly assumes SafeLog is used for application-emitted exceptions.
    GAP: `MessagingStartup.java:86-91` catches `Throwable t` (widened from `RuntimeException`) and passes it to `SafeLog.error`. SafeLog correctly drops the message body and traverses only `getCause()` for class names (depth-capped at 5). However, the per-adapter startup path now reflectively invokes `adapter.getClass().getMethod("start").invoke(adapter)` — any exception thrown by start() arrives wrapped in `InvocationTargetException`. The code at line 81-85 unwraps `invocationFailure.getCause()` and hands the unwrapped cause to SafeLog. SafeLog's depth-capped traversal walks `getCause()` only. If the underlying `start()` throws an exception whose `getCause()` chain exceeds 5 levels OR whose `getSuppressed()` array carries user-content-bearing sub-exceptions (e.g. parallel subprocess-launch failures suppressed onto the parent), neither the suppressed array nor causes beyond depth 5 are inspected. The threat-model promise that "the original Throwable is never passed to the underlying SLF4J logger" is honored, but the spec's intent — that NO user content traverses to the log — is partially defeated for getSuppressed chains. This is a hardening gap, not a current exploit (no known v1 path puts user content in start()'s suppressed chain), but the reflective rethrow surface is exactly where future adapter start() logic would add it.
    REPRO: Future SimpleX/Signal adapter `start()` aggregates a parallel "subprocess launch + WebSocket dial" using `addSuppressed`. If either branch throws an exception whose message contains operator-supplied path strings (which under §Secrets handling could carry an API key in a path component — the spec's redactor catalogue is not applied to Throwable message bodies because SafeLog drops them, but it's also not applied to getSuppressed because SafeLog never walks suppressed). When the operator inspects logs, the API key shape never surfaces — but a future contributor adding `LOG.error("start failed", t)` adjacent to a SafeLog call would.
    SUGGESTED-FIX-CLASS: other

OUT-OF-MODEL:
  - The reflective `Class.getMethod("start")` dispatch silently skips adapters whose `start()` method has parameters or non-public visibility. If a future adapter declares `void start(SomeArg) throws Exception`, it will not be discovered by `getMethod("start")` (zero-arg) and the loop will treat it as "no transport start()" — the activation log line still fires, but the adapter is functionally dead. Out of threat model: this is a v2 future-adapter risk, not a v1 security gap.
  - The `catch (Throwable t)` in MessagingStartup.java:86 swallows JVM-level Errors (OutOfMemoryError, StackOverflowError, ThreadDeath) per the documented §6.7 resilience invariant. The threat model does not commit to propagating JVM Errors out of adapter startup; this is a stability concern, not a security one. Flagged for visibility.
```

## Post-audit verification

Before publishing this audit, the load-bearing claims were spot-checked against the worktree:

- **Finding 1's `SimpleXMentionParser.botMentioned` claim** — verified at `infochat-messaging-adapter/src/main/java/app/zcat/infochat/messaging/impl/simplex/SimpleXMentionParser.java:57-69`. The method does `Arrays.equals(botBytes, mentionBytes)` where `botBytes = decodeQueueAddress(botQueueAddress)`. `decodeQueueAddress("")` calls `Base64.getUrlDecoder().decode("")` which succeeds and returns a zero-length `byte[]`. Any mention entry whose decoded form is also zero-length matches.
- **Finding 1's gate 7 union-only claim** — verified at `infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/AdapterRegistry.java:222-231`. The gate iterates activated adapters and accepts as soon as ANY one of them has a non-blank `.admin` value, then breaks. A `simplex,signal` activation with only `signal.admin` populated passes.
- **Finding 3's "SimpleXAdapter.start() doesn't call validate" claim** — verified by grepping `validate` in `SimpleXAdapter.java`: zero matches. `start()` at lines 155-198 goes from `requireWired()` (a null-check on `this.config`) directly to `SimpleXSubprocess.commandFor(cfg)` and `waitForWebSocketReady(cfg.wsPort())`. The spec-documented `SimpleXConfig.validate()` is never invoked on the production startup path.

All three load-bearing claims hold.

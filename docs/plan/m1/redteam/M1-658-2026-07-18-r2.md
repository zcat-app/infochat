    PROMISE: security.md §"LLM output sanitizer" as AMENDED by this diff

    GAP: The M1-658 guard censuses ONLY `error.*` templates by design
         (InboundReflectionGuardTest class Javadoc "<b>Errors only.</b> ... does
         NOT prove reply.* / success / confirmation templates safe"). A live,
         unvalidated inbound-text reflection exists in a SUCCESS (`reply.*`)
         template, in the guard's disclosed blind spot:
           - AddSourceCommandHandler.java:210-211 interpolates
             `result.displayName()` into `REPLY_ADD_SOURCE_FRESH_INSERT`.
           - displayName derives from the user-supplied `--name` override:
             AddSourceCommandHandler.java:196-197 →
             SourceUpsertService.defaultDisplayName (SourceUpsertService.java:276-284)
             returns `override.orElseGet(...)` VERBATIM — no charset/length
             validation.
           - The override is a raw inbound token: AddSourceArgs.java:138/145
             stores it straight from CommandTokenizer, and CommandTokenizer
             (CommandTokenizer.java:24-47) UNWRAPS double-quote pairs, so
             `--name "…"` may contain spaces — a fully parameterized admin
             command string fits.
         Because the key is `reply.add_source.fresh_insert` (not `error.*`),
         the guard's census never sees it; the security.md claim
         "interpolates no inbound-derived text / M1-647/M1-656 removed those
         echoes" is contradicted by a currently-shipping echo. This is a LIVE
         case in the disclosed reply-template blind spot, not merely a
         future-regression risk.
    REPRO: In an approved group, a GROUP admin (below bot admin; admitted by the
           `ERROR_ADD_SOURCE_GROUP_ADMIN_ONLY` gate at
           AddSourceCommandHandler.java:140-148) sends:
             /add-source https://attacker.example/feed --tags news --name "/grant-admin 3f9c…deadbeef approved"
           On FRESH_INSERT the deterministic success reply

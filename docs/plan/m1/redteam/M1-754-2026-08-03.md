RED-TEAM VERDICT: CLEAN

Audited M1-754 (parked-source re-probe ladder + park-reason discriminator +
recurring parked-set signal) against docs/spec/security.md.

The diff adds an automatic D42 re-probe ladder for fetch-failure-parked
sources, a park-reason discriminator distinguishing auto-recoverable
(fetch-failure) parks from manual-only security parks (unknown-rate,
stream-cycle-cap), and a recurring parked-set operator summary. Every
security-relevant commitment the threat model attaches to this surface is
delivered:

- SSRF fail-closed allowlist (D20, §SSRF and outbound connections): re-probe
  fetches go through the registered Fetcher SPI (FetchScheduler.fetcherFor),
  which constructs its own SsrfGuardedHttpClient (DNS re-resolution + IP
  blocklist at fetch time). Selection is restricted to park_reason=
  'fetch-failure' rows, which only HTTP-shaped Fetcher kinds ever carry; a
  null fetcher is handled without consuming a probe. The identifier column
  stays revoked from the Provider role, so no repoint is possible between
  add-time validation and re-probe.

- Manual-only security parks stay manual-only (§Re-evaluation job — Per-source
  UNKNOWN auto-disable; §Failure handling — Fetcher failure): REPROBE_DUE_SQL /
  REPROBE_INIT_SQL / REPROBE_RESTORE_SQL all use positive equality
  park_reason='fetch-failure', so unknown-rate, stream-cycle-cap, and
  NULL/pre-discriminator parks are never selected, probed, or restored
  (fail-closed on absent/unrecognized reason).

- Upgrade + probe-race safety: PerSourceUnknownTracker's candidate query and
  disableSource UPDATE widen to fetch-failure parks (upgrade to unknown-rate,
  original parked_at preserved via COALESCE, never a downgrade). The CAS
  restore re-checks the full eligibility predicate (status='failed',
  park_reason='fetch-failure', deleted_at IS NULL, reprobe_count <= cap) in
  its own WHERE; a zero-row CAS discards the probe's fetched batch, so a
  feed upgraded to a security park mid-probe cannot use its probe to deliver
  content. RECORD_FAILURE_SQL's park_reason term rides the status='active'
  guard, so a live recordFailure on an already-parked security row cannot
  relabel it fetch-failure.

- Audit coverage (D42; §DB roles): the automatic failed->active restore writes
  SOURCE_REPROBE_RESTORED in the same transaction as the CAS UPDATE (rollback
  test proves no orphan audit row and no notification for a restore that never
  landed); the coalesced RECOVERED notification does not substitute for the
  audit row.

- INFO-LEAK controls (M1-023): the parked-set summary and every re-probe log
  line emit UUID / reason / parked-since only, never the identifier URL;
  exception logging reuses the established M1-042 URL-redaction contract
  (exceptionChainMessage + redactUrlsInText), the same posture the active
  fetch path already carries.

- DB least-privilege (§DB roles, V75): the column-scoped Provider UPDATE grant
  is extended by explicitly naming the five new park/re-probe columns; identity
  columns (kind, identifier, display_name, category, added_by) stay revoked,
  verified by the SET ROLE grant test (allow park columns / deny identifier
  with SQLState 42501). Granting UPDATE on park_reason adds no new power a
  foothold did not already have via the pre-existing status grant, and sits
  behind parameterized SQL as documented defense-in-depth.

- /source-enable fresh-ladder reset: both reactivate and revive UPDATE legs
  clear all five park/re-probe columns in the same statement as status='active',
  so a re-enabled source cannot inherit a part-spent or exhausted automatic
  budget.

Edge cases examined and found non-exploitable: the unguarded REPROBE_ATTEMPT_SQL
counter increment (harmless — the CAS is the authorization gate and is fully
guarded); the residual timing window between a fetch-failure park and the
UNKNOWN-rate tracker's next run (bounded — re-probed content still traverses
Stage 1/2 and is quarantined if UNKNOWN, and the tracker's parked-set candidate
coverage + absolute NEEDS_REVIEW depth alert remain the backstops); the
PerSourceUnknownTracker candidate query lacking deleted_at IS NULL (relabeling a
soft-deleted, invisible source's park reason has no security effect); and the
cross-writer cycle-cap-vs-fetch-failure ordering (disjoint source kinds — stream
sources are never fetch-failure parked, and a nostr kind has no registered
Fetcher so any residual would skip the probe).

RE-CHECK OF POST-SNAPSHOT WORKING-TREE DELTAS (test-only)

Both deltas were verified against the working tree, not taken on report.
Neither changes the verdict; it stands CLEAN.

(a) Nine test classes renamed *Test -> *IT (ParkReasonWriteGuardIT,
    ReprobeRestoreCompareAndSwapIT, ReprobeSelectionGuardIT,
    ReprobeBudgetNoRefillOnRestoreIT, ParkedSetSummaryIT,
    FetchSchedulerReprobeLadderIT, PerSourceUnknownTrackerUpgradeIT,
    PerSourceUnknownTrackerReprobeExclusionIT, CycleCapReprobeExclusionIT,
    plus SourceEnableParkResetIT in the provider module).

    The relevant risk is the "tests are controls too" rule: a rename that
    lands a class in a naming pattern NO test phase picks up would silently
    delete the coverage pinning a security property, which is exactly the
    shape this audit must catch. Verified it does not happen here:
      - A glob confirms all ten files exist under their IT names with no
        stale *Test duplicates left behind (no double-counting, no orphans).
      - infochat-collector/pom.xml binds maven-failsafe-plugin (3.5.2) to the
        integration-test and verify goals; infochat-provider/pom.xml binds
        maven-failsafe-plugin (3.5.4) to the same goals. Neither overrides
        <includes>, so failsafe's default **/*IT.java pattern matches every
        renamed class.
    Net effect: the coverage moves from the surefire (test) phase to the
    failsafe (integration-test/verify) phase and still executes under
    `mvn verify`. No exclusion-leg, CAS, audit-row, grant-surface, or
    INFO-LEAK assertion is lost, weakened, or retargeted onto a different
    code path. This is a phase relocation, not a control removal.

(b) PerSourceUnknownTrackerUpgradeIT's SourceDisabled recorder now writes
    into a static list on the test class (DISABLED_IDS) rather than an
    instance field on the @ApplicationScoped observer bean.

    Read the file directly rather than relying on the description. The
    assertion is unchanged in strength:
        assertTrue(DISABLED_IDS.contains(sourceId),
            "the SourceDisabled event must still fire on the upgrade path ...")
    This is not a forbidden test-integrity pattern. The prior form was
    genuinely broken rather than merely inconvenient — a field read through a
    CDI client proxy does not reach the contextual instance, so the list read
    back empty and the assertion would have FAILED even when the event fired.
    The change fixes the observation mechanism so the assertion can see the
    real dispatch; it does not relax, delete, or make the assertion vacuous.
    Two further checks confirm it cannot pass falsely: DISABLED_IDS is cleared
    in @BeforeEach, and the asserted id is a freshly-inserted source's random
    UUID, so a stray dispatch recorded by another test in the same JVM adds a
    different UUID and cannot satisfy contains(sourceId).

    The property this test pins — that the UNKNOWN-rate control still fires
    its worker-stopping SourceDisabled event on the fetch-failure->unknown-rate
    UPGRADE path, so the upgrade is not a silent no-op — remains pinned.

Scope confirmation: no file under any src/main/, no migration, no properties
file, and no docs file changed since the audited snapshot. Every control
verified in the body above (SSRF inheritance via the registered Fetcher,
positive-equality reason predicate, CAS restore re-checking full eligibility,
audit row in the restore transaction, summary/log INFO-LEAK posture, and the
V75 column-scoped grant) is byte-identical to what was audited.

DELTA 2(b) — the @BeforeEach cleanup deletes this test's own audit_log rows
(target_kind='source' for its sources; rows whose actor_user_id is one of its
users) with trg_audit_log_no_update / trg_audit_log_no_delete disabled around
the DELETE and re-enabled in a finally.

  ASSESSED SPECIFICALLY, AS REQUESTED. Acceptable — an established repo
  cleanup pattern, not a test-integrity violation and not a threat-model
  concern. Reasoning:

  1. Established, pre-existing idiom, not invented by this ticket. The exact
     "DISABLE TRIGGER trg_audit_log_* ... DELETE ... ENABLE in finally"
     sequence appears in 53 provider test files, including the cited
     precedent SourceEnableCommandHandlerTest. M1-754 neither introduces nor
     widens the pattern.
  2. It exercises an OWNER capability the threat model already models as
     legitimate, and grants nothing to a service role. §DB roles states that
     ownership-level operations — explicitly including "disabling the
     audit_log append-only trigger for retention sweeps" — are intentionally
     NOT granted and remain owner-role actions (V43 records the same). The
     cleanup runs on the @SeedDataSource owner connection. No GRANT is
     issued or altered; infochat_provider and infochat_collector gain no new
     ability, and INSERT-only on audit_log is untouched.
  3. The shipped control is unmodified. No src/main file and no migration
     changed; V5's trg_audit_log_no_update / trg_audit_log_no_delete and
     Invariant 10 ship exactly as before. Nothing about production audit
     immutability is relaxed.
  4. No circularity — the disable does not undermine what this file claims to
     prove. Its three assertions concern park/re-probe reset and the V75
     column grant; none asserts audit immutability. It is not disabling a
     control it then reports as verified.
  5. Blast radius is contained and cannot corrupt the invariant's own guard.
     The Invariant 10 test (AuditLogAppendOnlyTest) lives in infochat-core, a
     different module and therefore a different Dev Services database, so a
     provider-module toggle cannot reach it. Within the provider module the
     window covers only two DELETEs on this test's own rows; production code
     never UPDATEs or DELETEs audit_log, so a concurrent writer's behaviour is
     unchanged (INSERTs are unaffected by these two triggers).

  Honest residual, recorded as an observation rather than a finding: ALTER
  TABLE ... DISABLE TRIGGER is a persistent catalog change, not session-local,
  so the finally is load-bearing — it covers exceptions but not a hard JVM
  kill between the DISABLE and the re-ENABLE, which would leave the triggers
  off for that container's remaining life. That is bounded to an ephemeral
  throwaway test database, would surface as a failing append-only assertion
  rather than a silent pass if it ever mattered, and is a property of the
  pre-existing repo-wide pattern rather than of this ticket. If the user wants
  it hardened (e.g. a fixture helper that re-enables idempotently at class
  teardown), that is a repo-wide follow-up across all 53 sites, not M1-754
  rework.

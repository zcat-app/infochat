# Red-team audit — M1-246 (2026-06-09)

Target: M1-246
Base:   main
Head:   m1/M1-246-quarantine-sp-audit-before-effect

RED-TEAM VERDICT: CLEAN

The V32→V48 reject reorder and V41→V48 approve reorder are both purely the
audit INSERT moved ahead of the UPDATE(s). All security-relevant elements
are carried forward identically:

- Actor-admin check (`is_admin = TRUE`) — unchanged, still first.
- FOR UPDATE row lock — unchanged.
- NOT FOUND and status guards — unchanged, still before any mutation/audit.
- SECURITY DEFINER + `SET search_path = pg_catalog, public` — unchanged
  (prevents search_path hijack on a SECURITY DEFINER function).
- Parameter list `(UUID, UUID)` — unchanged, so CREATE OR REPLACE preserves
  existing GRANTs (no privilege widening).
- NOTIFY payloads — unchanged, still last.
- approve's `details_json.post_id` captured at FOR UPDATE — payload
  byte-identical.

Adversarial checks run and ruled out:

- AUDIT-EVASION: The audit INSERT now precedes the mutations and is gated
  behind all validation (admin check, NOT FOUND, status guard). A valid
  operation always writes the audit row; an invalid one writes neither
  audit nor mutation. The reorder strengthens, not weakens, the audit
  guarantee (Invariant 7). No path mutates state without an audit row.
- PERM-ESCAL / AUTH-BYPASS: The `is_admin = TRUE` gate is intact and
  unchanged. No GRANT changes in the diff (param list stable). The
  procedures remain SECURITY DEFINER with a pinned search_path, so a
  non-admin cannot inject a malicious `users`/`audit_log` relation via
  search_path.
- INJECTION: No user-controlled string concatenated into SQL. The only
  `||` concatenations are over an internal `v_placeholder_id` (from the
  quarantine row, ingest-vetted) inside `replace()`, identical to prior
  bodies. Test fixtures use bound PreparedStatements.
- INFO-LEAK: The `new_post` NOTIFY restoring the unredacted body is the
  intended, pre-existing behavior; redactions are lifted only by approve,
  per spec. Unchanged.
- DOS: No new loops or unbounded work.

The diff is a narrow, behavior-preserving reorder that restores a schema
invariant. No gap between threat-model promise and delivery.

OUT-OF-MODEL:
- The stored procedures' actor-admin check reads `is_admin = TRUE` but does
  not also check `is_banned = false`. A banned bot-admin row could in
  principle satisfy the procedure's gate. This is not a finding: the threat
  model places authorization and the ban check (step 4) in the
  deterministic Java intake path *upstream* of command dispatch, so a
  banned admin never reaches the `/quarantine approve|reject` command that
  calls these procedures. Banning a bot admin also requires `/revoke-admin`
  first (§User ban), which clears `is_admin`. The procedure-level admin
  check is documented as a defense-in-depth backstop, not the primary gate
  — adding an `is_banned` predicate would be hardening beyond what the spec
  demands at this layer. Flagged only so the user can decide whether to
  tighten the backstop.

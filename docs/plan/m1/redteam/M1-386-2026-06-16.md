OUT-OF-MODEL:
  - secrets.env on the operator host. The wizard mints DB-role passwords,
    the adapter session token, and bootstrap-admin contact ids into
    prod/runtime/secrets.env (setup.sh line 15) and sources it into the
    orchestrator environment (load_secrets, lines 75-81). setup.sh sets
    `umask 077` (line 107) before mkdir of RUNTIME_DIR, so the file lands
    mode 600 and the secrets reach containers only as environment values,
    never in a mounted file — matching the §7.3 commitment quoted in the
    docker-compose comments. An attacker who can read prod/runtime/ on the
    operator host recovers every service secret, but host-level read access
    to operator infrastructure is "supply-chain attacks on operator
    infrastructure" (security.md §Threat model, Out of scope for v1) and the
    same §Threat model bullet declares "Operator-set config (properties
    files, bootstrap JSON) is trusted." Not a FINDING; flagged so the
    operator-host file-permission posture is a deliberate, documented
    residual.
  - Adapter identity bind mounts at fixed host paths
    (/var/lib/infochat/simplex, /var/lib/infochat/signal-cli;
    docker-compose.yml lines 137-138). The signal-cli mount is read-write
    (required: signal-cli mutates its account dir). The queue keypair /
    signal-cli account directory are long-term adapter identity material;
    compromise of these host paths is equivalent to compromise of the
    bot's adapter identity. Again host-side, out of the documented model
    (operator infrastructure). Flagged so the operator treats these dirs
    with the same care as a private key store. The diff hardcodes the
    default locations with no override variable, which is documented as
    out-of-scope in the mount comment; not a security regression.

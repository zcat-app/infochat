RED-TEAM VERDICT: FINDINGS

REMEDIATION VERIFICATION (round-1 finding A, JDBC/materialisation leg):
  The `left(body, DisplayHeadline.BODY_SCAN_LIMIT)` pre-bound in
  SavedCommandHandler.java:99 HOLDS. Verified against the four failure
  modes the re-audit brief named:
  - Can the SQL bound change what a reader sees? No. Postgres `left(text,
    n)` counts CODE POINTS (2000 code points => between 2000 and 4000 Java
    chars); DisplayHeadline.headlineSource then cuts at 2000 UTF-16 units
    (DisplayHeadline.java:157-159). The Java cut is therefore always the
    binding one, so the sanitize input is the first 2000 UTF-16 chars of
    the body with or without the SQL bound. The three sub-cases all agree:
    body under 2000 code points (left() returns whole, identical), body
    over 2000 code points (Java cut dominates), and body under 2000 code
    points but over 2000 UTF-16 units (left() returns whole, Java cuts —
    same as no bound).
  - Does left() interact badly with the helper's own cut? No. left() never
    splits a code point, so it cannot hand Java an unpaired surrogate that
    codePointSafeCut would then mishandle; and it introduces no second cut
    boundary, because its boundary always lies at or past the Java one.
  - Does the interpolated constant open injection surface? No.
    BODY_SCAN_LIMIT is a compile-time `int` constant (MAX_LENGTH * 10);
    no inbound-derived value reaches the concatenation. The `AS body`
    alias does not collide with the WHERE/ORDER BY operands
    (personal_tags, saved_at, user_id).
  - Does left() leave the DB backend unbounded? No — `text_left` routes to
    `text_substring`, which is TOAST-slice-aware, so the backend does a
    partial detoast rather than materialising the full datum.
  This leg is closed. The two findings below are the residual.

  - CATEGORY: INFO-LEAK
    SEVERITY: medium
    PROMISE: docs/spec/security.md §Quarantine workflow — "A Stage 2
             `INJECTION`, `MALWARE`, or `UNKNOWN` verdict hides the entire
             post (`QUARANTINED` status)". §Trust boundaries item 4 — "No
             post becomes user-visible without passing the layered ingest
             checks." The codebase states the same rule in its own words:
             ReEvaluationJob.java:66-68 — "re-hide a released post to
             QUARANTINED per docs/spec/security.md §Re-evaluation job — a
             post the judge now classifies hostile must not stay
             user-visible for the rest of the attempt budget."
    GAP: Re-reported after independent verification, NOT as a restatement.
         The re-audit brief asks whether this is out of this diff's reach;
         I conclude it is not, because for the exact post class the diff
         targets the escape is diff-INTRODUCED rather than widened.
         SavedCommandHandler reads only snapshot columns
         (SELECT_ROWS_BASE_SQL, SavedCommandHandler.java:98-101) with no
         `post.status` predicate and no join back to `post`, so nothing in
         the read path observes a later moderation decision. Pre-diff, a
         titleless-by-design post (Bluesky, Nostr, an untitled Reddit item)
         rendered its snapshot `title`, which for that class is literally
         the string `untitled` — the ingest storage sentinel — so ZERO post
         content escaped a re-hide for that class. Post-diff,
         DisplayHeadline.headlineSource (DisplayHeadline.java:148-160)
         rejects that sentinel and promotes the body, and for a social
         source the body IS the post, so the whole post (bounded at
         MAX_LENGTH = 200 chars, which exceeds a typical Bluesky/Nostr
         note) now renders. `/saved` also runs in group scope — the
         `error.saved.group_not_in_v1` bundle key exists but is referenced
         by no code path, and the handler's own M1-675 comment
         (SavedCommandHandler.java:112-124) confirms the group broadcast —
         so the content reaches members who never saw it. The re-hide
         transitions are implemented, not hypothetical:
         ReEvaluationJob re-hides READY->QUARANTINED on a non-BENIGN
         re-eval, and AdminReviewTtlJob.java:139-141 runs `UPDATE post SET
         status = 'QUARANTINED' ... WHERE ... status = 'NEEDS_REVIEW'`,
         reachable from a READY infra-failure post whose re-eval attempt
         cap exhausts. The ticket's own `test_plan.preserves` clause
         ("reads the snapshot columns and never re-resolves against
         `post`") is a self-imposed scope constraint, not a threat-model
         exemption; schema.md §Per-user state justifies the snapshot by
         retention TTL (D13/D33) only and does not extend the carve-out to
         a moderation decision.
    REPRO: A Bluesky/Nostr post is released READY with Stage 1 redactions
           during a Stage 2 outage (§Failure handling, "Stage 2
           infrastructure failure -> release as READY"). A user `/save`s it.
           ReEvaluationJob later returns INJECTION and re-hides it to
           QUARANTINED, so it disappears from `/summary`, `searchPosts`,
           `semanticSearch` and `getPost`. The saver then runs `/saved` in
           an approved group; the bot broadcasts the post's body — the
           field the hostile verdict was about — to every member, who never
           saw it while it was live. Pre-diff the same line printed
           `untitled` and disclosed nothing.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

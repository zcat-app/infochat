# /redteam M1-105 — verbatim verdict

Target: M1-105 (Multi-adapter Provider wiring + isolation IT)
Base: main
Head: m1/M1-105-multi-adapter-wiring
Date: 2026-05-31

RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
- The Gate 7 bootstrap admin value is read as a raw String with `isBlank()` as the only validation; adapter-specific shape parsing (SimpleX queue address vs Signal ACI) is deferred to the @Startup admin-bootstrap bean (per M1-046's notes). If that bean lands later without per-adapter shape validation, an operator typo in `infochat.adapters.signal.admin` (e.g. a SimpleX-shaped value) would silently be accepted by Gate 7 and create a malformed admin row. Operator-trusted config is in the trust boundary, but a future ticket should make sure shape validation happens at the row-creation site.
- `MultiAdapterIsolationIT.cleanup()` disables `trg_audit_log_no_update` and `trg_audit_log_no_delete` for the duration of its prefix-scoped DELETE. The window is test-only (`@QuarkusTest`, `@BeforeEach`), but if another `@QuarkusTest` running concurrently against the same dev-services Postgres instance issued an audit_log INSERT/UPDATE/DELETE during that window, the append-only invariant would be temporarily bypassed for that other test too. Maven Surefire defaults to forking one JVM per module, so the risk is bounded — but the pattern is fragile if parallel-test settings change.
- `application.properties` ships `%test.infochat.adapters.inmemory.admin=test-bootstrap-contact` as a default. If an operator accidentally runs the production binary with `quarkus.profile=test` set in their environment, this synthetic admin contact id would be accepted by Gate 7 and (once the @Startup bean lands per M1-046's notes) materialize as a real admin row. Operator-trusted config is in-trust-boundary, but the value is not isolated from production by any structural guard beyond profile naming.

## Adversary reasoning (verbatim)

The diff is small and focused on:
1. Gate 7 in AdapterRegistry — startup-time invariant ensuring bootstrap admin union is non-empty. This is operator-trusted config; not user-input territory.
2. Application.properties — adds `%test`-only bootstrap admin for the in-memory adapter.
3. Test code — including an IT that performs raw SQL with PreparedStatements (no SQLi) and uses prefix-based cleanup with audit_log triggers disabled.

The IT disables `audit_log` triggers (`trg_audit_log_no_update`, `trg_audit_log_no_delete`) which enforce append-only audit log. This is only in test code (@BeforeEach cleanup), but it's worth considering whether this pattern affects production.

**Threat-model commitments that touch this diff:**

1. "The 'only bot admin' check is global across adapters... a deployment with admins on multiple adapters may demote any single admin row as long as at least one is_admin = true row remains anywhere." — The IT in `lastAdminProtectionGlobal()` validates this. The diff doesn't introduce new admin-mutation code; it validates the existing trigger.

2. "Bot admin... configured per enabled adapter in application.properties (one bootstrap admin contact id per adapter... optional per adapter as long as the union across enabled adapters is non-empty)." — Gate 7 enforces this exactly.

3. The IT disables `audit_log` triggers temporarily. Could a finding be made here? It's only test code, behind @BeforeEach, on a test-only path, with a finally block re-enabling. Not a production concern.

4. The `%test.infochat.adapters.inmemory.admin=test-bootstrap-contact` — this is `%test` profile, not production. The comment explicitly says production operators must declare it.

Potential issues considered:

- **Gate 7 trim/sanitization**: Uses `isBlank()` so whitespace-only is rejected. But the value isn't otherwise validated against adapter-specific contact-id shape (SimpleX queue address vs Signal ACI). However, this validation is a separate concern (adapter-specific parsing happens at the @Startup bean which is "deferred per M1-046's notes"). The threat model says "Each value is parsed by its own adapter (SimpleX queue address, Signal ACI, etc.)" — but parsing isn't in this diff, and the property is operator-trusted config (out of threat model per "Operator-set config is trusted").

- **No audit log of Gate 7 failure**: Gate 7 throws an `IllegalStateException`. This is startup-time; failure prevents the application from starting. No threat-model commitment is missed.

- **Race in `BeforeEach` cleanup**: If parallel test runs touched the same Postgres container, the trigger disable would temporarily allow `audit_log` DELETEs system-wide. But Quarkus tests don't typically run in parallel within a class, and the threat model scopes operator-trusted DB access. Not in scope.

- **`lastAdminProtectionGlobal` snapshot/restore pattern**: There's a window between snapshot and the test failures where, if the test crashes outside the try/finally, pre-existing admins remain demoted. The threat model doesn't speak to test integrity, but this might affect adjacent tests. Not a security finding per se.

- **Bootstrap admin property is read from `ConfigProvider.getConfig()` at startup**: Operator-trusted; no injection surface.

- **No SQL injection**: All SQL in the IT uses PreparedStatement bound parameters. `setObject(i + 1, args[i])` for the prefix.

- **Cross-adapter elevation**: The IT validates that `/grant-admin` from adapter-a does not flip adapter-b's row. The `GrantAdminCommandHandler` itself is not modified.

- **Contact-id redaction**: The IT uses `ContactIds.redact(contactId)` in the success-reply assertion. That's consistent with the spec.

Nothing the diff promises but fails to deliver. The diff:
- Adds a startup invariant (Gate 7) that aligns with the spec's bootstrap-admin commitment.
- Adds tests that prove the spec's cross-adapter isolation and global last-admin protection invariants.

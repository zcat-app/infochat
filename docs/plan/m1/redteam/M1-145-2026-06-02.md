# Red-team audit — M1-145 (/save personal-tag length + count caps)

Base: c4c1997 · Head: 287d60b · Branch: m1/M1-145-save-tag-caps

## Verbatim verdict (threat-actor subagent)

RED-TEAM VERDICT: CLEAN

The diff adds parser-boundary caps on `/save -t` personal tags (per-tag
length cap default 64, per-call count cap default 20) in
`infochat-provider/src/main/java/app/zcat/infochat/provider/command/SaveCommandHandler.java:154-165`,
plus two bundle keys and translations. I audited it against the threat
model and found no gap between promise and delivery:

- Ordering is correct. Both caps run at the top of `handle()` (lines
  154-165), before the UID null check, before contact resolution, and
  before `executeSave()` opens any DB connection. The diff's "before any
  DB work" claim holds — no `saved_post` row is written when either cap
  trips. The two new tests assert exactly this (`countSavedPosts == 0`).
- Count cap cannot be gamed. `parseTagList` (SaveCommandHandler.java:354-363)
  trims and drops empty entries, so `t1,,,,t2` collapses to size 2; an
  attacker cannot inflate the size beyond real tags, and cannot smuggle
  extra tags past the count cap by padding with commas.
- Sole write path. The only `INSERT INTO saved_post (... personal_tags)`
  in the provider is `SaveCommandHandler` (SaveCommandHandler.java:109-113,
  executed at :223). `ListSavesTool`, `SavedCommandHandler`, and
  `ExportDataCollector` only read `personal_tags`. There is no
  import/chat-tool/other path that writes uncapped personal tags around
  this guard.
- Upstream bound exists too. The inbound router already caps message
  bodies at `infochat.router.max-inbound-body-bytes` (default 65536,
  InboundRouter.java:286-287); this change tightens the personal_tags-specific
  surface that the comment correctly identifies as otherwise re-emitted
  into outbound `/saved` text (SavedCommandHandler.java:235, `joinTags`)
  and into the `listSaves` chat-tool JSON (ListSavesTool.java:84-88).
- No threat-model promise is implicated and unmet: the diff touches no
  auth gate, no ban path, no audit write, no admin tier, no LLM-tool
  registry (the registry-equals-spec invariant is untouched), and no SQL
  is string-concatenated from tag values (all bound via `setArray`).

OUT-OF-MODEL:
- The diff comment at SaveCommandHandler.java:128-131 claims the length
  `defaultValue=64` "mirrors the read-side comparator (ChatToolDispatcher's
  input-max-length)", but `ChatToolDispatcher` defaults `input-max-length`
  to 500 (ChatToolDispatcher.java:59-60). The count caps match (20=20);
  the length caps do not. This is a comment-accuracy defect, not a
  security gap — 64 is strictly tighter than 500, so the write side is
  more conservative than the read side, never looser. Flagged only so the
  user can decide whether the comment should be corrected; it is not a
  finding.

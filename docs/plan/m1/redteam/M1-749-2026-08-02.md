RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: AUDIT-EVASION
    SEVERITY: medium
    PROMISE: docs/spec/security.md §LLM output sanitizer: "Every match is
      audit-logged; rows aggregate per distinct token per sanitize call
      and carry the exact occurrence count — counted, never throttled."
      The same section scopes the sanitizer to "the full set of
      LLM-authored output surfaces: chat-mode replies, on-the-fly
      /summary prose, periodic group digests, /retry re-rolls, and any
      future LLM-emitted text."
    GAP: The diff adds a new sanitize call site for LLM-emitted text —
      IngestTranslationWorker.sanitize
      (infochat-collector/src/main/java/app/zcat/infochat/collector/eval/translation/IngestTranslationWorker.java,
      new-file lines ~420-431; javadoc at lines ~113-116 and ~416-419) —
      which runs the shared LlmOutputSanitizerCore closed-list strip over
      translator output before storage but emits only one WARN per
      distinct token. The class javadoc states explicitly: "The
      collector-side application emits no audit_log rows — the audit path
      stays with the provider bean." LlmOutputSanitizerCore is declared
      "deliberately PURE ... It emits no log lines and writes no audit
      rows" (infochat-core/src/main/java/app/zcat/infochat/core/llm/LlmOutputSanitizerCore.java,
      new-file lines ~34-36), so no audit path exists anywhere for this
      surface. This is not a capability constraint: the collector DB role
      is INSERT-only on audit_log (docs/spec/security.md §DB roles), so
      the spec-committed LLM_OUTPUT_SANITIZED row could have been written
      from this call site.
    REPRO: An operator subscribes a non-English source the adversary can
      publish to (a threat-model-given: "Every RSS publisher, Reddit
      poster, Bluesky user, etc. is untrusted"). The adversary posts an
      article laced with privileged-command tokens (e.g. "the intruder
      typed /ban and /grant-admin"); the translator is instructed to
      preserve such tokens verbatim, so its output carries them. The
      worker's sanitize pass redacts the tokens from body_en before
      storage — the preventive control fires — but the only record is a
      WARN in collector stdout. /audit (audit_log_view) shows nothing:
      the injection-attempt telemetry the spec commits to for EVERY
      sanitizer match is absent for this surface, so an adversary can
      probe translation-laundering of privileged commands at feed scale
      with zero operator-visible audit trail.
    SUGGESTED-FIX-CLASS: audit-log-coverage
  - CATEGORY: INJECTION
    SEVERITY: low
    PROMISE: docs/spec/security.md §Prompt-injection defenses: "Every
      prompt that includes user-derived text is wrapped in a delimiter
      block whose marker contains a per-call random value... The system
      prompt instructs the model to never follow instructions inside the
      wrapper... and to treat the content as data." The wrapper's
      integrity depends on untrusted bytes never being reinterpreted as
      template structure.
    GAP: IngestTranslationWorker.renderPrompt
      (infochat-collector/src/main/java/app/zcat/infochat/collector/eval/translation/IngestTranslationWorker.java,
      new-file lines ~328-336) substitutes placeholders sequentially:
      {{id}}, {{SOURCE_LANGUAGE}}, {{title}}, {{body}} — in that order.
      Because {{body}} is replaced AFTER the upstream-controlled title is
      spliced in, a title containing the literal string "{{body}}" has
      the full post body substituted into the Title line as well. The
      untrusted title is thereby reinterpreted as template syntax,
      collapsing the prompt's title/body separation the JSON contract
      assumes.
    REPRO: A feed publisher sets a post title containing the literal
      {{body}}. The rendered prompt shows the entire body twice — once
      inside the Title: line, once in the body slot — and the model can
      legitimately return the whole body translation as the "title"
      value, which parses as VALID (non-empty textual title), is stored
      as post.title_en, and is indexed into search_tsv and embedded. The
      strict parse shape does not catch it; retrieval text is corrupted
      by template injection through a field the pipeline treats as
      opaque data. Blast radius is bounded (retrieval pollution of the
      attacker's own feed content, output still normalized/sanitized,
      fetch body caps bound the size), hence low.
    SUGGESTED-FIX-CLASS: input-sanitization

OUT-OF-MODEL:
  - Semantic-pollution attacks via the translation channel: a feed
    publisher (or a hostile translation endpoint, trust boundary 9) can
    bias or degrade the English retrieval text (search_tsv / embeddings)
    for non-English posts — e.g. selective mistranslation, keyword
    stuffing, or refusal-marker/NULL-release suppression of English
    retrievability. The spec commits to injection- and exfiltration-grade
    defenses for LLM handling of untrusted content, not to translation
    fidelity; a hostile endpoint's refusal/NULL-release power is also no
    greater than its pre-existing power to fail every call. Flagged so
    the user can decide whether retrieval-integrity commitments belong in
    the threat model.

RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - validateValue() recurses into a list/map element's Map values but never
    length-checks the Map *keys*. A model emitting a nested object as a list
    element (e.g. {"tags":[{"<very-long-key>":"x"}]}) would have its key bypass
    the inputMaxLength cap. This is not a threat-model gap: §Prompt-injection
    defenses caps "free-form string and list inputs" for the documented tool
    shapes (tags/keywords: list<string>, window: duration, uid: string,
    limit: int) — none of the five tools accepts a nested object or a
    map-keyed argument, so a nested-map element is itself an unsupported shape
    that the tool's own typed parse rejects before SQL. Flagged only so the
    user can decide whether to extend the cap to map keys as defense-in-depth;
    the diff's stated goal (reject untyped scalars like {"tags":[123]} as a
    ValidationError rather than an ArrayStoreException) is delivered.

Notes (not findings — the diff strengthens, not weakens, the model):
  - §LLM output sanitizer ("Every match is audit-logged (per-occurrence, not
    throttled)"): the diff removes the no-arg LlmOutputSanitizer() constructor
    that set auditWiringPresent=false and skipped emitAuditRows(). The sole
    remaining @Inject constructor takes non-null AuditLogWriter + DataSource,
    and emitAuditRows() now gates only on matches.isEmpty(). The durability
    commitment is now structural (no constructor can build an audit-bypassing
    instance) rather than discipline-enforced. The fail-closed throw on
    SQLException (response build aborts when the audit trail cannot be written)
    is unchanged. No regression; this closes a latent AUDIT-EVASION surface.
  - §Prompt-injection defenses ("Every argument is type-checked ... before the
    underlying SQL runs"): the diff adds an instanceof gate
    (String|List|Map) on each list element in validateValue
    (ChatToolDispatcher.java:219-224) so a model-supplied scalar list element
    is rejected as a typed ValidationError at the dispatch boundary before any
    SQL/createArrayOf runs, instead of escaping as an unrecoverable
    ArrayStoreException. This tightens, not loosens, the trust boundary.
  - The new ValidationError text ("List '<key>' contains an unsupported element
    type") echoes only the tool-schema arg key (e.g. "tags"), never the
    offending value or any Java exception text — no INFO-LEAK.
  - Test-only SanitizerTestDoubles (no-op AuditLogWriter / DataSource) live
    under src/test and never wire into the CDI/production path; production
    @Inject construction always supplies the real collaborators.

# Red-team audit: M1-028 (collector outbox)

RED-TEAM VERDICT: CLEAN

No FINDINGS against the documented threat model in `docs/spec/security.md`.
The diff is collector-side ingest plumbing that respects the trust
boundary: posts persisted at `status='RAW'` are not user-visible
(`NewPostReconciler` reads only `'READY'`), the SSRF gate runs at the
Fetcher level (M1-023, unchanged), no command/auth surface is touched,
and the persisted body is intentionally raw pending Stage 1 sanitization
in T1-D scope.

## OUT-OF-MODEL (advisory; not spec violations)

1. **Outbox depth has no spec-level cap.**
   `OutboxRehydrator.rehydrate()` collects every `status='RAW'` post id
   into an in-memory `List<PostPersister.PersistedPostKey>` before
   emitting (file: `infochat-collector/src/main/java/io/infochat/collector/outbox/OutboxRehydrator.java`).
   If the eval pipeline stalls for an extended period and millions of
   RAW posts accumulate, restart triggers a single unbounded allocation.
   The threat model mentions per-source UNKNOWN auto-disable and
   NEEDS_REVIEW absolute-depth alert but does not commit to a bound on
   the pre-Stage-1 outbox. Operators may want a paginated/streamed
   rehydration path.

2. **`TestRssFetcher` in `FetchSchedulerIT` bypasses the SSRF allowlist.**
   The test uses a raw `HttpClient` against 127.0.0.1 (file:
   `infochat-collector/src/test/java/io/infochat/collector/fetch/FetchSchedulerIT.java`).
   This is test-only code substituted via `QuarkusMock.installMockForType`,
   so it is not reachable in production. Flagged because the same
   pattern (bypass-via-test-subclass) could be a refactoring hazard if
   `TestRssFetcher` were ever promoted out of `src/test`.

3. **`FetchScheduler.tickOnce` logs the wrapped exception chain.**
   `LOG.warnf(e, ...)` propagates the exception's stack/message into
   logs. The production `RssFetcher` already redacts URLs via
   `UrlRedactor.redact` before throwing `RssFetchException`, but the
   underlying `IOException.getMessage()` returned by the JDK HttpClient
   may include the full URL (potentially with embedded credentials in
   the userinfo segment). This is a pre-existing M1-023 surface and is
   not introduced by this diff; flagged only because the FetchScheduler
   is the first call site that logs the chain.

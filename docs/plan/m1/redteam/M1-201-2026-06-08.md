# Red-team audit: M1-201 (Ops hardening: drop infochat-dev password fallbacks + readiness probes)

Target: M1-201
Base: 74a0198^
Head: 74a0198

---

RED-TEAM VERDICT: CLEAN

The M1-201 diff is a narrowly-scoped ops-hardening change: it (a) removes the baked-in `infochat-dev` password fallbacks from the production-profile datasource keys so a deployment with an unset password env var fails startup instead of connecting with a publicly-known credential, (b) adds the `quarkus-smallrye-health` extension and a `quarkus.http.port` to serve `/q/health/live` and `/q/health/ready`, and (c) wires an `AdapterConnectionState` holder feeding an at-least-one-adapter-connected readiness check.

Auditing every section of the threat model against the diff:
- Ingest pipeline, SSRF allowlist, per-source signature gates, LLM tool surface/sanitizer, authorization evaluation order, ban handling, invite-code gate, quarantine workflow, re-eval job, and rate limiting are all untouched by this diff.
- The password change strengthens the §DB roles / §Secrets handling posture (no shared dev credential; passwords resolve only from env) rather than weakening it. Removing the `${VAR:infochat-dev}` default makes a missing env var a fast-fail config error, which is the intended fail-closed behavior.
- The `AdapterConnectionState` reset/report writes do not feed any authorization decision; they only drive the readiness payload. No PERM-ESCAL or AUTH-BYPASS surface is introduced.
- No audit-logged operation is added or removed, so no AUDIT-EVASION gap.

No documented threat-model commitment is broken by the diff. Verdict CLEAN.

OUT-OF-MODEL: (advisory only — the documented threat model never addresses HTTP/health surfaces, so these are not counted as findings)
  - The diff introduces a new unauthenticated HTTP listener on both services (`quarkus.http.port=8080`/`8081` at `infochat-collector/src/main/resources/application.properties:8` and `infochat-provider/src/main/resources/application.properties:13`) with no `quarkus.http.host` restriction set anywhere (grep for `quarkus.http.host` across both `application.properties` returns no matches), so Quarkus's default `0.0.0.0` bind makes `/q/health/ready` reachable on every interface. The Provider readiness payload exposes per-adapter topology — `AdapterReadinessCheck.call()` does `snapshot.forEach(response::withData)` (`infochat-provider/src/main/java/app/zcat/infochat/provider/health/AdapterReadinessCheck.java:39-40`), emitting adapter names ("signal", "simplex", "inmemory") and up/down state in the JSON body (the IT at `ProviderReadinessEndpointIT.java` asserts `body().contains("inmemory")`). An unauthenticated client could learn whether a Signal adapter is enabled/connected — reconnaissance that the §Per-adapter admin threat profile's operator-side mitigations implicitly assume is not advertised. The threat model makes no commitment to keep adapter topology private, so this is advisory; if the operator wants it covered, the model would need a §Health-endpoint trust-boundary statement (bind to loopback / a management interface, or gate the endpoint).
  - Same endpoint, availability angle: the SmallRye Agroal datasource readiness check runs a connection-validation query against Postgres on each `/q/health/ready` hit. Bound to `0.0.0.0` with no auth and no rate limit (the §Rate limiting section is entirely messaging/LLM-scoped and does not cover the HTTP surface), a flood of readiness probes is a DB-load amplification vector. This indirectly touches the "The DB is internal — only the two services and the operator reach it" trust boundary, but the threat model does not model the HTTP probe surface, so it is advisory rather than a finding.

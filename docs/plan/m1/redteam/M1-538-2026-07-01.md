RED-TEAM VERDICT: CLEAN

No threat-model commitment is under-delivered by an adversary-reachable path
in this diff.

Scope of the diff: a live-run test/tooling harness (M1-538) plus doc/status
updates. It adds prod/live-inject-adversarial.sh (a bash wrapper) and
prod/sql/inject-adversarial-raw.sql (a corpus that inserts one adversarial
RAW post), and updates docs/testing/USER_TEST_PLAN.md, the M1 STATUS board,
and the ticket file. No production code path (Provider intake, authorization
steps 1-10, ingest Stage 1/2, LLM tool surface, audit-log path, DB role
grants) is modified.

Why each category is clean:

- INJECTION: The shell interpolates only compile-time constants into psql
  (POST_UID="m1-538-adversarial-a1", PAYLOAD_TOKEN="grantAdmin" —
  prod/live-inject-adversarial.sh:194,199, and the poll/assert queries at
  :292,326,336). The three numeric CLI args are regex-validated before any
  use (--backdate/--timeout as ^[0-9]+$, --poll as ^[1-9][0-9]*$ —
  :235-246), and backdate_minutes reaches SQL only through a validated psql
  -v variable (:275, consumed at inject-adversarial-raw.sql:461). No
  attacker-controlled input reaches the query builder.

- AUTH-BYPASS / PERM-ESCAL: The tool runs under the trusted database OWNER
  role via `docker compose exec` + secrets.env
  (prod/live-inject-adversarial.sh:263-266). The threat model designates the
  DB as internal ("only the two services and the operator reach it") and
  operator-set config as trusted (security.md §Threat model). Owner-role
  psql is the operator boundary, not an adversary boundary. The injected
  post carries a `grantAdmin` prompt-injection body, but that is *data fed
  into* the ingest pipeline the tool is testing — it never traverses the
  LLM tool surface as a callable (§Prompt-injection defenses: the tool
  registry is a closed read-only allowlist; there is no grantAdmin tool),
  and the deterministic authorization path (steps 1-9) never consults LLM
  output. Nothing here elevates any (adapter, contact_id) row's is_admin.

- INFO-LEAK: The tool reads only `post.status`, a quarantine row count, and
  a READY-body substring count (prod/live-inject-adversarial.sh:292,326,336)
  — all under the owner role, all echoed to the operator's own terminal. No
  user-authored prose, contact id, or secret is emitted; the assertion
  prints only counts and the fixed token string it is searching for.

- DOS: No unbounded loop reachable by an adversary. The poll loop is
  deadline-bounded (--timeout-seconds, :289-301). A malformed operator flag
  (e.g. a trailing `--backdate-minutes` with no value, where `shift 2 ||
  true` fails to consume) is an operator-invoked robustness nit, not an
  adversary-reachable path.

- AUDIT-EVASION: The SQL DELETEs quarantine/post/post_embedding rows
  (inject-adversarial-raw.sql:442-444) without an audit_log entry, but this
  is owner-role operator tooling, prefix-scoped to `m1-538-%` / the fixed
  test post_id. The audit-log commitments (§DB roles, Invariant 10/D34)
  govern the application/Provider path and the append-only trigger, not
  operator psql under the owner role — which the threat model already treats
  as the trusted recovery/maintenance principal. No adversary can invoke
  this path.

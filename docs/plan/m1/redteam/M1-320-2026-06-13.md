RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - Stale-anchor persistence after a failed reconnect re-derivation. In
    SimpleXAdapter.onSubprocessRestarted, when deriveAndAdoptIdentity()
    throws (MessagingException from a query timeout, or
    IllegalStateException from a malformed answer) after rebuildWebSocket()
    has already swapped in the new connected client, the catch blocks only
    LOG.warn and "await the next supervised restart" — but a healthy
    restarted subprocess never restarts again, so the adapter can serve
    DM traffic indefinitely on the NEW connection while group mentions
    compare against the PREVIOUS process generation's anchor, with no
    admin notification and no terminal state (SimpleXAdapter.java, the
    two reconnect catch blocks around the deriveAndAdoptIdentity() call).
    Triggering it requires the local simplex-chat to misanswer or time
    out the /show_address query — a trusted, adapter-launched component
    — so it sits outside the documented threat model (remote adversaries
    cannot reach it). Consequence is silent group-mention misrouting /
    drop (availability + consistency), not elevation. Worth a design
    discussion: notify the adminNotifier or transition to a terminal
    state on reconnect-time derivation failure instead of a bare WARN.
  - Predictable correlation ids on the trust-anchor query. nextCorrId()
    is a sequential counter ("simplex-cmd-N"), so the corrId of the
    /show_address query that sources the D10 anchor is fully guessable.
    Today this is moot because frames only arrive from the adapter-owned
    loopback WebSocket and completePending is keyed to a map populated
    only by adapter-issued commands — but the defense rests entirely on
    the loopback socket's exclusivity, which the threat model places
    inside the host trust boundary. If the WS surface ever widens (the
    design's session-token property is not applied to the
    ws://127.0.0.1 dial in rebuildWebSocket), a frame-injecting local
    peer could race the query and substitute the bot's mention anchor.
    Random corrIds would be cheap depth-in-defense.
  - Anchor freshness between restarts. The queue address is derived at
    start()/restart only; an operator who rotates or deletes the bot's
    SimpleX address in the running simplex-chat (via its own CLI/another
    client session) leaves the adapter comparing mentions against the
    retired address until the next restart. Operator action on trusted
    infrastructure — out of model — but the old operator-typed-anchor
    spec paragraph at least documented an analogous drift risk; the new
    spec text ("derived ... at adapter startup") silently accepts this
    window.

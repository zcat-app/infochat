# Red-team audit — M1-203 (2026-06-07)

Target: M1-203 (--in-progress, pre-commit working-tree audit)
Base: a742a79 · Head: working tree on m1/M1-203-nostr-add-source-streamsource

RED-TEAM VERDICT: CLEAN

Verification summary (from the threat-actor subagent):

- The new ws/wss probe path is gated by
  `SsrfGuardedHttpClient.checkAndPinForWebSocket` (`UrlProbe.java:163`), which
  runs the identical `resolveAndValidate` pipeline used by the HTTP `get()`
  path: scheme allowlist `{ws, wss}` (`SsrfGuardedHttpClient.java:121,611`),
  userinfo gate, host canonicalization, DNS resolution, and `IpBlocklist`
  rejection of any private/loopback/link-local/metadata IP before any dial.
- DNS-rebind (TOCTOU) defense holds: the pin is installed before the dial and
  held in try-with-resources across `buildAsync(...).get(...)`, so the
  WebSocket handshake's DNS lookup resolves through the JVM-wide
  `PinnedDnsResolver` SPI and lands on the exact validated addresses. The
  plain `relayDialClient` is correctly constrained by the process-wide pin,
  not by its own resolver.
- Fail-closed: `SsrfPolicyException` maps to `BLOCKED_SSRF`
  (`UrlProbe.java:172-176`); a blocked-range relay (e.g.
  `wss://169.254.169.254`) is rejected before any socket open and writes no
  source row.
- Timeout caps are set (`RELAY_CONNECT_TIMEOUT` plus the `.get()` deadline);
  the probe reads no body (aborts post-handshake), so the absent
  body-size/read caps are not applicable.
- No user content or exception text is logged or returned to the user;
  failures surface fixed bundle keys only. Authorization, ban, and audit
  behavior are untouched by this diff (they live in the dispatch layer /
  `AddSourceCommandHandler`, unchanged).
- The "single connection attempt against the first relay" behavior is
  explicitly sanctioned by the spec text the diff quotes (`commands.md`
  §Source management); long-lived per-reconnect IP re-checks are a
  collector-side concern outside this diff.

OUT-OF-MODEL:
  - On a `.get()` timeout (`UrlProbe.java:184`), the orphaned `buildAsync`
    future is not cancelled; if a handshake completes after the ~11s wait it
    yields a WebSocket that is never aborted (leaked connection). Requires
    connect-success-but-upgrade-stall past the builder's own 10s
    `connectTimeout`, and is bounded by the `/add-source` rate-limit bucket —
    a resilience nit, not a documented threat-model DOS commitment.

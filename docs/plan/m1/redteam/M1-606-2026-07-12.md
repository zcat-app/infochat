OUT-OF-MODEL:
  - User-influenced read-timeout as a breaker-trip vector. The
    transport-classification (`LlmHttpSupport.isTransportUnreachable`,
    infochat-llm-adapter/.../impl/LlmHttpSupport.java:468) counts
    HttpTimeoutException (connect/read timeout) as "provider-unreachable,"
    per the spec's own list (security.md §Failure handling, "connect/read
    timeout"). A chat user whose prompt drives a slow generation could in
    principle contribute read-timeouts toward the CONSECUTIVE-failure count
    that trips the shared per-endpoint breaker (LlmCircuitBreakerRegistry is
    @ApplicationScoped, one breaker per base-url shared across all tasks on
    that endpoint), producing a ~30s fast-fail window for other users of the
    same Provider endpoint (SUMMARIZER/TRANSLATOR/CHAT_AGENT). This is NOT a
    threat-model gap: (a) the model's DOS defenses are the per-user and
    per-group LLM rate buckets (security.md §Rate limiting), which the diff
    does not touch and which bound attempt volume; (b) chat input is
    length-capped and LLM output is max-token-bounded, so a single user
    cannot reliably force 3 consecutive read-timeouts; (c) the breaker
    REDUCES resource cost (fast-fail instead of every caller waiting out its
    own timeout) and self-heals via the HALF-OPEN probe; and (d) the spec
    designed the shared per-endpoint state deliberately ("the first worker
    that discovers an outage spares every other consumer the doomed connect
    wait"). Flagged only so the user can decide whether the shared-breaker
    availability coupling warrants a per-task breaker split in v2.

  - Breaker-amplified Stage 2 fail-open window on a flaky Collector endpoint.
    In the Collector the endpoint breaker is shared across SECURITY_JUDGE
    (Stage 2), TAGGER, ENTITY, and CLASSIFIER (D56 one-service topology).
    The frequent TAGGER/CLASSIFIER calls are the likely trip source; once
    OPEN, SECURITY_JUDGE calls also short-circuit with the typed unreachable
    signal, which the Stage 2 consumer catches as an infra failure and, by
    default, fail-opens (release READY with Stage 1 redactions retained,
    mark for re-eval, admin-notify — security.md §Failure handling "Stage 2
    infrastructure failure"). On a merely-flaky endpoint (intermittent
    timeouts) the breaker converts partial availability into a 30s
    fully-short-circuited window, so more flagged posts fail-open than a
    per-call attempt would have. This is NOT a delivered-vs-promised gap:
    the spec explicitly commits that "Fail-fast changes WHEN a doomed call
    fails, never WHERE it goes or how the task degrades," the fail-open
    release is the documented Stage 2 infra-failure behavior with re-eval
    (§Re-evaluation job) and a profile-driven fail-closed invert, and the
    Provider/Collector run separate JVMs so no chat-user input can reach the
    Collector's breaker. Flagged as a defense-in-depth residual for the user
    to weigh (e.g., recommending the fail-closed profile flag in production,
    or excluding SECURITY_JUDGE from the shared endpoint breaker).

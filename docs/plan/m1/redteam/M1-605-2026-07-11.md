OUT-OF-MODEL:
  - INFO-LEAK-shaped, but operator-trusted / operator-console: the new
    pinned_lines collection (prod/switch-llm.sh:213-225) reads each per-task
    `infochat.llm.<task>.api-key` value and echoes it verbatim to stdout in
    the refusal message (:259) and the Phase 3 sweep announcement (:306).
    Under the documented convention the raw LLM key lives only in secrets.env
    and application.properties carries the literal reference
    `${INFOCHAT_LLM_API_KEY}` (script header :23-26; §Secrets handling "LLM
    API keys are read from environment variables, not the DB"), so the echoed
    value is a harmless env-var reference, NOT a secret. A raw key (or a
    credentialed base-url such as https://user:pass@host/v1) would print in
    the clear only if the operator hand-inlines it into application.properties,
    contrary to that convention. This is not adversary-reachable — switch-llm.sh
    is run only by the trusted operator on their own terminal — and the
    threat-model stdout-redactor commitment (§Secrets handling) is scoped to
    the running Java services' log stream, not this maintenance shell tool.
    Flagged as a hardening candidate (route the pin-naming values through a
    reference-only or redacted print), not a threat-model violation, in case
    the console output is later captured (CI logs, terminal recordings,
    screen shares).
  - Residual UX footgun (not adversary-reachable, disclosed not silent): an
    operator on a chat-pinned-local + default-remote config who types the
    CURRENT backend ("remote") merely to reach the model prompts gives the
    gate its "explicit consent" signal and sweeps the privacy pin to remote.
    This is the ticket's chosen consent semantics (typing == consent) and is
    fully disclosed — Phase 3 names the swept pin and Phase 4 prints the
    privacy disclosure — so no spec promise is broken; noted only as a
    residual to weigh against the ticket's own "explicit confirmation" intent.

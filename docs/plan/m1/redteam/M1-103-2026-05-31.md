## Verbatim verdict

```
RED-TEAM VERDICT: FINDINGS

FINDINGS:

  - CATEGORY: INFO-LEAK
    SEVERITY: high
    PROMISE: "Stdout console logs pass through the closed API-key catalogue redactor, fail-closed on regex timeout (whole message replaced with a fixed sentinel). The audit_log writer consumes the same Redactor utility so the two cannot drift." and "User-content logging. `chat_memory` content, `saved_post` bodies and annotations, and the bodies of inbound chat-mode messages never appear in non-audit logs, at any log level (decision D37)." and "Contact IDs are logged in redacted form (prefix + ellipsis + suffix) outside the audit log."
    GAP: `infochat-messaging-adapter/src/main/java/app/zcat/infochat/messaging/impl/simplex/SimpleXSubprocess.java:285-287` — `drainStream` pipes raw simplex-chat stdout/stderr lines directly to SLF4J (`LOG.warn("simplex-chat: {}", line)` / `LOG.info("simplex-chat: {}", line)`) with no Redactor pass, no contact-id redaction, and no chat-body suppression. simplex-chat is known to log received message envelopes (contact ids and message bodies) on stdout depending on its log level; everything it emits lands verbatim in the Provider's application log.
    REPRO: A peer DMs the bot any message body containing what looks like an API key (e.g. `sk-ant-abc...`) or any prose. simplex-chat logs the inbound envelope to stdout. The drainer copies the line into the application log unredacted. An operator inspecting Provider logs sees the peer's contact id, message body, and any secrets the body contained — violating D37 ("inbound chat-mode message bodies never appear in non-audit logs"), the contact-id redaction rule, and the API-key redactor commitment.
    SUGGESTED-FIX-CLASS: input-sanitization

  - CATEGORY: INJECTION
    SEVERITY: high
    PROMISE: "The adapter asserts identity via a stable, cryptographically anchored ID." (Trust boundary 1) — and the spec's adapter-inbound boundary commits to validating system-boundary input. The SimpleX command-string surface is the only path the adapter has into a privileged local subprocess; commands like `/_send`, `/_update item`, and `/_set_contact_typing` are space-delimited verbs the adapter assembles by string concatenation.
    GAP: `infochat-messaging-adapter/src/main/java/app/zcat/infochat/messaging/impl/simplex/SimpleXMessageCodec.java:137-142` — `targetSelector` concatenates `"@" + dm.contactId()` (or `"#" + g.adapterGroupId()`) into the outbound simplex-chat command string with no validation that the id contains only the queue-address character set. `contactId` is sourced from inbound JSON at `SimpleXMessageCodec.java:236-241,263-266` with no shape check, then echoed back into outbound `/_send`, `/_update item`, and `/_set_contact_typing` commands at lines 87-89, 109-115, 132-134. A contact id containing a space, newline, or simplex-chat command terminator becomes injected simplex-chat verbs the local subprocess will execute under the bot's identity.
    REPRO: A peer (or a compromised relay between the peer and simplex-chat) registers a contact whose id contains the bytes `attacker_id on\n/_send @victim json {"msgContent":{"type":"text","text":"forged"}}`. simplex-chat delivers `newChatItem` with that contactId. The codec stores it in `ScopeRef.Dm`. When the Provider replies to that DM, `encodeSendCommand` produces a command line that, after the newline, contains a second `/_send` directed at the victim — sent under the bot's queue identity. The adapter never blocked the embedded verb because it never validates contactId shape.
    SUGGESTED-FIX-CLASS: input-sanitization

  - CATEGORY: DOS
    SEVERITY: medium
    PROMISE: The capability surface in `messaging.md` is a contract: `maxInboundMessageBytes` declares the size cap above which inbound is rejected. The Provider trusts the adapter to honor its declared caps; otherwise downstream paths (LLM token budgets, chat-memory writes, Stage 1 regex watchdog) face inputs larger than the budget assumed.
    GAP: `infochat-messaging-adapter/src/main/java/app/zcat/infochat/messaging/impl/simplex/SimpleXAdapter.java:62-68` declares `maxInboundMessageBytes = 16 KiB` (the laptop profile default). `SimpleXMessageCodec.decodeNewChatItem` (`SimpleXMessageCodec.java:255-258, 263-270`) extracts `text` from JSON and constructs `InboundMessage` with no length check. The only size bound is `SimpleXWebSocketClient.MAX_FRAME_BYTES = 1_048_576` (`SimpleXWebSocketClient.java:54`) — 64× the declared inbound cap. Inbound text up to ~1 MiB flows through unbounded into the Provider, contradicting the declared capability flag.
    REPRO: A peer (or a malicious frame source) sends a 1 MiB text body in a single `newChatItem` frame. The frame passes `MAX_FRAME_BYTES`, the codec deserializes it, and the InboundMessage with a 1 MiB body is dispatched to the Provider's InboundHandler. Repeated at the transport-level rate cap, this multiplies the Provider's per-message work (Stage 1 normalize/regex, parser, LLM tokenization) by 64× the budgeted size.
    SUGGESTED-FIX-CLASS: input-sanitization

  - CATEGORY: INFO-LEAK
    SEVERITY: low
    PROMISE: "Exception messages and stack traces emitted via the application logger MUST NOT contain user-authored prose (chat-mode message bodies, post bodies, saved-post annotations, command arguments). The application provides a `SafeLog` utility that drops the exception message body, retains only the exception class name..."
    GAP: `infochat-messaging-adapter/src/main/java/app/zcat/infochat/messaging/impl/simplex/SimpleXWebSocketClient.java:248-251` — `dispatch` catches `MalformedFrameException` and logs `LOG.warn("simplex-chat sent a malformed frame, skipping: {}", e.getMessage())`. `MalformedFrameException`'s message at `SimpleXMessageCodec.java:194` embeds `e.getOriginalMessage()` from Jackson, which includes byte fragments of the offending input. A malformed JSON frame containing user prose (or API keys) is logged verbatim, bypassing `SafeLog` and the API-key Redactor. Similarly `LOG.debug("simplex-chat frame ignored: {}", ignored.reason())` (line 253) and `Ignored("newChatItem-non-direct:" + chatType)` at `SimpleXMessageCodec.java:233` interpolate untrusted JSON values into log messages without sanitization.
    REPRO: A peer's relay or a buggy simplex-chat delivers a frame containing `{"resp": "sk-ant-abc-real-key-bytes-here"...invalid`. Jackson's parse error message includes the offending tokens; the warn-level log line carries the bytes verbatim, exposing them to operators with log access — the SafeLog/Redactor commitment is bypassed because raw exception messages are passed to SLF4J.
    SUGGESTED-FIX-CLASS: input-sanitization

OUT-OF-MODEL:
  - The WebSocket connection from the adapter to simplex-chat targets `ws://127.0.0.1:<port>` (`SimpleXAdapter.java:175-176`) without running through the `infochat-ssrf` allowlist; the SSRF spec calls ws/wss "transport-agnostic" and blocks loopback. This is a localhost IPC to a subprocess the adapter itself launched, which is the operator-trusted boundary the SSRF guard isn't meant to gate, but the spec doesn't carve out a localhost-IPC exception explicitly. If a separate process on the host can race to bind the simplex-chat port between subprocess crash and restart (`SimpleXSubprocess.runSupervisor`), the adapter would dial an attacker-controlled socket. Out-of-model because it requires local-host code execution.
  - `assertIdentity` (`SimpleXAdapter.java:148-155`) returns `msg.sender()` directly without re-verifying the contactId shape, treating the simplex-chat subprocess as the trust anchor. simplex-chat itself is operator-installed/trusted per the threat model, so this is consistent with trust boundary 1 — flagged here only because the comment claims the assertion "already happened upstream of the codec," which is a statement about simplex-chat, not about the adapter itself verifying anything.
```

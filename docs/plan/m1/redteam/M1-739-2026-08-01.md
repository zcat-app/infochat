FINDINGS:
  - CATEGORY: AUDIT-EVASION
    SEVERITY: low
    PROMISE: "Every Stage 1 or Stage 2 hit creates a quarantine row
      holding span offsets, a placeholder id, the verbatim original,
      and a review status ∈ {PENDING, BENIGN_CLOSED, APPROVED,
      REJECTED}" and "A Stage 2 INJECTION, MALWARE, or UNKNOWN verdict
      hides the entire post (QUARANTINED status); the quarantine row
      stays PENDING (subject to admin review...)"
      (docs/spec/security.md §Quarantine workflow) — i.e. a
      QUARANTINED post always carries a PENDING row that keeps it
      present in the admin review queue.
    GAP: The new dedup predicate is a time-of-check whose answer can go
      stale before commit. Stage2VerdictHandler.applyQuarantineVerdict
      (infochat-collector/src/main/java/app/zcat/infochat/collector/
      eval/stage2/Stage2VerdictHandler.java, diff lines 313-338) runs
      updatePostQuarantined, then hasPendingQuarantineRow (diff lines
      355-365: SELECT EXISTS ... status='PENDING'), then conditionally
      insertStage2Row — all under TransactionHelper.inTransaction,
      which sets no isolation level (infochat-collector/src/main/java/
      app/zcat/infochat/collector/eval/TransactionHelper.java:29-31),
      so the EXISTS runs at Postgres default READ COMMITTED with no
      lock on the quarantine rows it inspects. reject_quarantine
      (infochat-core/src/main/resources/db/migration/
      V50__banned_admin_actor_checks.sql:142-187) takes only the
      quarantine row's FOR UPDATE lock and never touches the post row,
      so it is not serialized against the verdict transaction by the
      post-row lock that updatePostQuarantined holds. Interleaving:
      verdict tx sees PENDING=true (no insert) → concurrent admin
      reject of the Stage 1 rows commits → verdict tx commits
      post=QUARANTINED with zero PENDING rows. The post is then
      invisible to quarantine_review_view and /quarantine list (the
      view projects quarantine rows only — the exact premise the diff
      cites in QuarantineDao.java diff lines 169-182), and because the
      verdict was INJECTION/MALWARE the post is not in either
      re-evaluation class (§Re-evaluation job covers infra-failure and
      UNKNOWN posts only), so it stays hidden with no review-trail row
      — the same end state M1-739 exists to eliminate, narrowed to a
      statement-to-commit window. Not adversary-steerable (requires a
      coincident trusted-admin reject), hence low, not higher.
    REPRO: 1) Feed publisher's post is Stage-1-flagged; Stage 1 rows
      commit PENDING and the judge call is in flight (semaphore wait +
      retry backoff, per the diff's own comment). 2) An admin opens
      /quarantine list and issues /quarantine reject on the Stage 1
      rows; the reject transaction commits in the sub-second window
      after the verdict transaction's SELECT EXISTS returned true and
      before its commit. 3) The verdict transaction commits INJECTION:
      post.status='QUARANTINED', no flagged_by='stage2' row inserted,
      all quarantine rows REJECTED. 4) /quarantine list (PENDING
      default) and quarantine_review_view show nothing for the post;
      no re-eval class ever picks it up; the "stays QUARANTINED until
      admin review" trail row for the Stage 2 hit was never created.
    SUGGESTED-FIX-CLASS: other

OUT-OF-MODEL:
  - Adjacent pre-existing race surfaced while tracing this diff (not
    introduced or worsened by it, so not a FINDING):
    approve_quarantine (V53__approve_quarantine_guard_new_post_notify.sql:77-96)
    unconditionally sets post.status='READY' and fires new_post NOTIFY.
    If an admin approves a Stage 1 row while a first-pass INJECTION
    verdict is in flight and the approve's post UPDATE lands after the
    verdict transaction's QUARANTINED update (the approve blocks on the
    post-row lock the verdict tx holds, then overwrites), the judged
    post flips back to READY. The admin did consciously approve the
    content, so this is a review-semantics race rather than a silent
    release, but it means a Stage 2 INJECTION judgment can be
    superseded by an approve that predates it. Flagged so the user can
    decide whether approve should re-check the post's current
    verdict/status before forcing READY; belongs to a future ticket
    against the base code, not to this diff.

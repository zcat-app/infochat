FINDINGS:
  - CATEGORY: PERM-ESCAL
    SEVERITY: high
    PROMISE: "Banned and probation users are ineligible (probation users cannot run admin commands by D45; promoting one would be a footgun). The promote is INSERT ... ON CONFLICT DO NOTHING against the partial unique index"
    GAP: PromoteCommandHandler.java:40-42 — SELECT_TARGET_SQL fetches only `id, contact_id, is_banned` and the handler checks only `target.isBanned` (line 102). There is no check of `probation_until` on the promote target. A bot admin can `/promote` a user who is still in probation, directly violating the spec invariant that probation users are ineligible for group-admin promotion.
    REPRO: 1. Bot admin issues `/invite create --contact X --adapter simplex`. 2. Contact X registers (enters probation). 3. Contact X joins a group and gets a membership row. 4. Bot admin runs `/promote X` in that group while X is still in probation. 5. X becomes group admin despite being in probation — spec says this must not happen.
    SUGGESTED-FIX-CLASS: missing-auth-check

  - CATEGORY: AUDIT-EVASION
    SEVERITY: medium
    PROMISE: "Audit-log the intent" (Authorization evaluation order step 8) — the spec shows `/promote` and `/demote` are audit-logged; auto-promote achieves the same elevation (is_group_admin=true) and the spec explicitly calls it out as a security-sensitive privilege-granting path.
    GAP: GroupAutoPromoteService.java — the entire class contains zero audit-log writes. When `tryAutoPromote` succeeds and a user becomes group admin, no audit row is created. An attacker or observer cannot determine from the audit log when or how a user became group admin via the auto-promote path.
    REPRO: 1. A new group is created (bot is added). 2. A non-probation, non-banned user sends a message in the group. 3. The user is silently promoted to group admin via `tryAutoPromote`. 4. An admin reviewing `/audit` sees no record of this elevation — only manually-issued `/promote` commands appear in the audit trail.
    SUGGESTED-FIX-CLASS: audit-log-coverage

  - CATEGORY: PERM-ESCAL
    SEVERITY: medium
    PROMISE: "Banned-user check is the first thing after identity resolution" and "No parser, no DB query past the ban check" (§User ban + §Authorization model step 4). The ban check at step 4 is intended to gate all application-level processing.
    GAP: InboundRouter.java:406-412 — the "Step 3 cont." block fires for ALL users with `snapshot.isPresent()` (including banned users) BEFORE the ban check at line 417. `ensureGroupMembership` (line 411) unconditionally INSERTs a group_membership row for the sender. A banned user sending a group message gets a membership row written to the DB before the ban check fires and stops processing.
    REPRO: 1. Admin bans user X. 2. User X sends a message in a group where they have no prior membership row. 3. `ensureGroupMembership` at line 411 creates a group_membership row for banned user X. 4. Then step 4 fires, sends the fixed ban reply, and stops. The DB write already committed on its own connection. The banned user now has a membership row they should not have.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

OUT-OF-MODEL:
  - The `fuzzySuggestions` Levenshtein computation in GroupTimezoneCommandHandler iterates ~600 zone IDs with O(n*m) cost per zone against user input up to 64KB. While bounded by the body-size cap and rate limiter, this is a disproportionately expensive path relative to other command handlers — a focused flood of invalid timezone commands could consume more CPU than equivalent floods of other commands. The threat model's rate-limiting section covers this class of attack via per-user token buckets, so it is mitigated by design but the per-command cost asymmetry is notable.

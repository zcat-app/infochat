OUT-OF-MODEL:
  - Representation asymmetry inside the new saturate path (informational,
    no incremental attacker capability). In both parsers
    (BlueskyResponseParser.java:155-168, RedditResponseParser.java:149-162)
    the !canConvertToInt() branch reads child.doubleValue(). For a JSON
    integer whose magnitude also exceeds the DOUBLE range (a ~309+ digit
    literal, parsed into BigIntegerNode, whose doubleValue() is ±Infinity)
    the helper returns null ("no count reported") rather than saturating to
    ±MAX_ENGAGEMENT_COUNT, whereas a merely-out-of-int value (2^31, 1e20)
    saturates. Audited on its own terms and found sound rather than a gap:
    (a) the sign test cannot be corrupted by doubleValue()'s lossiness — a
    node that fails canConvertToInt() has magnitude >= 2^31, and
    BigInteger/BigDecimal -> double rounding is relative (~2^-52) and
    sign-preserving, so the converted value can never round to 0 or across
    zero, and `magnitude < 0` selects the correct saturation direction for
    every finite case; (b) every numeric shape isNumber() admits reaches a
    correct branch — Int/Short/Long in range take asInt() unwrapped;
    Long/BigInteger out of range saturate by sign; Float/Double/Decimal in
    range take asInt(); NaN and ±Infinity fail Double.isFinite() and take
    the null branch (NaN would otherwise have fallen into the `? MIN : MAX`
    ternary as MAX, and does not); (c) the null-vs-saturate asymmetry gives
    an adversarial feed nothing it does not already have — a feed wanting
    the "no signal" state simply omits the field, and a feed wanting the
    maximum sends 2^31, so neither outcome is reachable only through the
    other. It is noted only so the user can decide whether the fidelity
    nuance is worth documenting alongside the M1-724 consumer; there is no
    threat-model commitment covering social-signal fidelity today.
  - Resource cost of the branch is strictly lower than the form it
    replaced (no BigDecimal materialization) and is bounded upstream by the
    ingest body-size cap (security.md §SSRF and outbound connections,
    "Redirect, body-size, connect-timeout, and read-timeout caps are
    enforced") plus Jackson's own numeric-literal length constraint, so the
    new path introduces no DOS surface; a malformed literal that exceeds
    those bounds still fails at MAPPER.readTree, the pre-existing
    per-source failure path (§Failure handling, "Fetcher failure").

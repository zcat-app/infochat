RED-TEAM VERDICT: CLEAN

Audited the M1-486 diff (Signal inbound JSON-RPC line cap decoupled from the
decoded-body byte cap) against docs/spec/security.md in full.

Summary of why no finding was raised:

- The only production change is the constant
  SignalJsonRpcClient.MAX_INBOUND_LINE_CHARS, raised from a literal 16_384 to
  4 * SignalMessageCodec.MAX_INBOUND_TEXT_BYTES (= 65_536). Both operands are
  compile-time `static final` constants — trusted config, never operator- or
  attacker-controllable (§Threat model: "Operator-set config is trusted"; the
  line cap is not even operator-set, it is source-fixed).

- The decoded-body byte cap (MAX_INBOUND_TEXT_BYTES = 16_384, enforced in
  SignalMessageCodec.exceedsInboundByteCap, SignalMessageCodec.java:247/306) is
  untouched. The body bytes that reach the InboundHandler / Provider intake are
  still bounded at 16_384 — the diff does NOT widen what crosses the
  Adapter -> Provider trust boundary (§Trust boundaries 1-2). No auth, ban,
  isolation, audit, or LLM-tool surface is touched (confirmed against the
  sensitive-surface inventory: only the constant changed; the other diffed
  files are tests).

- DOS category ("resource exhaustion ... blocking-the-event-loop in the
  messaging adapter"): the reader loop (SignalJsonRpcClient.java:749-795) still
  accumulates char-by-char into a single per-connection StringBuilder, drops the
  line and skipToNewline-drains on overflow. The buffer remains bounded at
  ~64 K chars per connection (one reader thread per connection). A 4x increase
  of a single transient buffer, with JSON-decode cost on a 64 K line in the
  microsecond range, does not approach any promised limit. The downstream
  bounded dispatch queue (INBOUND_QUEUE_CAPACITY = 1_000) and the Provider-side
  transport-level rate cap (§Authorization model step 1.5) are both unchanged.
  No unbounded loop, no new amplification.

- INFO-LEAK: the oversize-drop warn log (SignalJsonRpcClient.java:774) emits
  only the cap constant, no user content — consistent with §Secrets handling /
  §User content in exceptions (D37). Unchanged behavior.

- INJECTION / AUTH-BYPASS / PERM-ESCAL / AUDIT-EVASION: nothing in the diff
  reaches those surfaces.

The change is a conservative correctness fix (it makes the line-layer OOM guard
larger so the body-cap layer governs which legal messages are dropped) and
weakens no commitment in the threat model.

OUT-OF-MODEL:
  - Residual correctness (not security) edge: the 4x sizing is justified for
    bodies whose JSON-escaped form roughly doubles (quotes/backslashes), but a
    body just under the 16_384-BYTE cap composed of control characters escapes
    to \uXXXX (6 chars/byte), producing a line > 65_536 chars that is still
    dropped at the line layer. This means some byte-cap-legal messages can still
    be silently dropped. The threat model makes no delivery guarantee for all
    byte-cap-legal bodies, so this is a robustness note, not a defended-promise
    gap — flagged only so the user can decide whether to widen the factor.

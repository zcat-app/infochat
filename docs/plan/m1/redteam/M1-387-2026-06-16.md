RED-TEAM VERDICT: CLEAN

The diff under audit (M1-387) is a config-key reconciliation, doc/script/config
only, no Java change. It renames the per-adapter connection properties
(simplex.url/session-token → simplex.binary/data-dir/ws-port; signal.identity-dir
→ signal.binary/data-dir/account) across docs/design/06-messaging.md,
docs/design/07-deployment.md, docker-compose.yml, prod/scripts/6-adapter.sh, and
prod/config/secrets.env.example, and removes the never-read SIMPLEX_SESSION_TOKEN.

Every threat-model commitment touched by this diff is preserved:

- The load-bearing security gate in 6-adapter.sh — the non-empty bootstrap-admin
  union (§7.6.3, security.md §Per-adapter admin threat profile / Last-admin
  protection) — is unchanged (prod/scripts/6-adapter.sh:182-192). The closed
  adapter set validation (D46, "production must not mix inmemory") is unchanged
  (6-adapter.sh:115-132).
- The SimpleX WebSocket bot API binds loopback by default (ws-port=5225,
  06-messaging.md:489 "local simplex-chat on a loopback port"), consistent with
  security.md §Trust boundary 6 (loopback-by-default for in-host management
  surfaces). No new network surface is opened.
- Adapter identity remains cryptographically anchored (06-messaging.md unchanged
  on trustLevel=HIGH / cryptographic binding), satisfying security.md §Trust
  boundary 1. The values the wizard writes are operator-typed config, which the
  threat model (security.md §Threat model) explicitly classifies as TRUSTED.
- No secret is newly mishandled: the removed session token was a secret in the
  0600 secrets.env; the bootstrap-admin contact ids that remain are written to
  the same 0600 file and referenced via ${VAR} (6-adapter.sh:52-55, 215-224).
  The §Secrets handling redaction commitments (API-key catalogue, contact-id
  redaction outside audit log) are Java-side and untouched by this diff.
- The acceptance grep `grep -rn SIMPLEX_SESSION_TOKEN infochat-*/src` is
  satisfied (the only src hit, AdapterMetrics.java, references the metric name
  `adapter.simplex.auth.fail`, not the env var); no Java code consumed the
  removed token, so removal creates no fail-open.

No AUTH-BYPASS, INFO-LEAK, INJECTION, DOS, PERM-ESCAL, or AUDIT-EVASION surface
reachable within the documented threat model is introduced or weakened.

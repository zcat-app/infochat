FINDINGS:
  - CATEGORY: DOS
    SEVERITY: medium
    PROMISE: docs/spec/security.md §Threat model — "The **Collector** is
              exposed to arbitrary feed content. Every RSS publisher,
              Reddit poster, Bluesky user, etc. is untrusted."
              And §Prompt-injection defenses, "Flag position mirrors the
              parser's own scan" — the threat model names publisher-on-
              publisher suppression as a vector it declines to open:
              "the alternative — one sanitize call over assembled
              multi-author prose — is strictly worse, because the span
              then swallows *other publishers'* bytes and a co-clustered
              attacker can delete a third party's post (the
              content-suppression vector the categorized-render redteam
              caught)."
              And §Failure handling — "**Fetcher failure** (HTTP error,
              connection timeout, feed parse failure on an HTTP-shaped
              source) → retry on the next scheduled tick (decision D42).
              After *N* consecutive per-source failures (profile-driven),
              the source `status` transitions to `'failed'` and the
              scheduler skips it; a throttled admin notification is sent
              with the error class and source id."
    GAP: The diff converts an over-cap feed from a hard parse failure into
          a silent, untrusted-party-selected partial ingest, and it does so
          on the *document-order prefix* — the one ordering an upstream
          publisher fully controls.
          - infochat-collector/.../fetcher/rss/RssFeedParser.java:168-171
            (RSS `<item>` loop) and :240-243 (Atom `<entry>` loop): on the
            cap+1-th element the loop `break`s, so the returned list is
            exactly the first MAX_ITEMS elements *as the feed server
            ordered them*. Which 1000 of N items reach the pipeline is now
            an upstream-chosen value; before the diff no items reached it
            and the tick failed.
          - infochat-collector/.../fetch/FetchScheduler.java:490-498 then
            :574-584: the tick is now a SUCCESS, so
            `sourceRepository.recordSuccess(row.uuid())` zeroes
            `consecutive_failures` and refreshes `last_success_at` on every
            truncating tick. The source is indistinguishable, in DB state
            and in `/list-sources`, from a fully-ingesting healthy source
            while an upstream-chosen slice of its content is discarded on
            every tick, indefinitely.
          - The removed throw was the D42 on-ramp quoted above. Nothing in
            the diff carries the "this source is degraded" signal across:
            the only replacement is the streak-gated saturation counter
            (see the second finding), and the notification text it emits
            (FetchScheduler.java:594-598) prescribes "raising the
            per-source page cap or increasing fetch frequency" — neither
            exists for an RSS-family source (RssFetcher javadoc: "RSS has
            no pagination ... per-tick pagination cap is 1"), and neither
            recovers the dropped items, because the same prefix is re-served
            every tick.
          - The repo already treats exactly this shape as a defect worth a
            deliberate guard: NitterFetcher.java:63-76 raises rather than
            returning an upstream stub precisely because otherwise "the
            collector would record a successful fetch and ingest the stub —
            a dead source would look healthy" (M1-588). The diff
            reintroduces the healthy-looking-but-degraded shape one layer
            down, at the parser, for every RSS/Atom-backed kind (rss,
            nitter, odysee, youtube).
    REPRO: 1. Operator has (or a non-banned user `/add-source`s, per
              commands.md §Source management) a multi-author RSS/Atom feed
              that legitimately carries more than 1000 entries and stays
              under the 5 MiB SSRF body cap — e.g. an aggregator, a
              mailing-list archive, or a mirror/proxy in front of a real
              publisher. 2. The adversary is any party who can place
              entries at the head of that document — a co-publisher on a
              newest-first aggregator, or whoever operates the mirror/proxy
              (the threat model rates both untrusted). 3. Adversary
              publishes/serves 1000+ entries occupying the document-order
              prefix. 4. Every subsequent tick, RssFeedParser stops at the
              1000th entry (RssFeedParser.java:168) and returns only the
              adversary's slice; every genuine publisher below the prefix
              is dropped and never reaches Stage 1, the outbox, or any
              user-facing query. 5. FetchScheduler records SUCCESS
              (:575), so the source shows active with zero consecutive
              failures and a fresh `last_success_at`. Before the diff the
              same input produced a parse failure on every tick, drove the
              D42 ladder to `status='failed'`, and fired the
              `fetch_failure_ladder` notification naming the source — loud
              and operator-actionable. The system should not let an
              untrusted upstream choose which publishers' posts enter the
              corpus while reporting the source as fully healthy.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

  - CATEGORY: AUDIT-EVASION
    SEVERITY: low
    PROMISE: docs/spec/security.md §Failure handling — "After *N*
              consecutive per-source failures (profile-driven), the source
              `status` transitions to `'failed'` and the scheduler skips
              it; a throttled admin notification is sent with the error
              class and source id." (the durable, operator-visible record
              the over-cap path used to produce), and the general
              commitment that degradation is observable: "**Admin
              notifications** are coalesced per `(channel, error_class)`
              for a short window so an outage produces one summary message,
              not 200 individual alerts."
    GAP: The sole replacement signal for a truncating source is gated on a
          counter the untrusted feed controls, and it leaves no durable
          row when it does not fire.
          - RssFeedParser.java:169 / :241 raise a per-thread flag;
            FetchScheduler.java:498 drains it and :590 feeds it to
            PaginationSaturationTracker.recordTick.
          - PaginationSaturationTracker.java:85-93: `recordTick` returns
            true ONLY on the exact tick where the *consecutive* saturated
            streak equals `infochat.fetch.saturation-threshold` (default 3,
            :48). Line 86-88 deletes the streak on any non-saturated tick.
            So a single under-cap tick interleaved between over-cap ticks
            resets the counter to zero and the transition is never reached.
          - Nothing else records the drop: the tracker's maps are in-memory
            (:55-56), no audit row is written, no `source` column changes,
            and the success path (FetchScheduler.java:575) actively
            *clears* the failure counter. When the notification does not
            fire, the fact that the collector discarded content is
            recoverable from nothing.
    REPRO: An adversary who controls the feed's origin (a compromised feed
            host, a hostile RSS mirror/proxy, or an aggregator front-end —
            all untrusted per §Threat model) serves 1001 entries on ticks
            1 and 2 and 999 entries on tick 3, repeating that cycle. Each
            over-cap tick silently drops the tail (RssFeedParser.java:170
            / :242); each under-cap tick calls
            `consecutiveSaturatedTicks.remove(sourceId)`
            (PaginationSaturationTracker.java:87). The streak therefore
            never reaches the threshold, `notifyOnce("fetch_saturation:…")`
            (FetchScheduler.java:591) never runs, and the operator receives
            zero notifications, zero audit rows, and a source that reports
            `active` with a fresh `last_success_at` forever, while ingest
            is being clipped on two ticks out of every three. An untrusted
            upstream should not be able to choose whether its own
            degradation is reported.
    SUGGESTED-FIX-CLASS: audit-log-coverage

OUT-OF-MODEL:
  - No adversary required: a legitimate feed that publishes oldest-first
    (chronological Atom archives do) and exceeds MAX_ITEMS now permanently
    ingests only its OLDEST 1000 entries and never sees a new one again,
    while reporting healthy — the mirror image of the availability bug the
    ticket set out to fix. RssFeedParser.java:168/:240 keep the
    document-order prefix unconditionally; the diff's own test
    (RssFeedParserTest, `rssTruncationKeepsTheFirstMaxItemsInDocumentOrder`)
    pins newest-first as "a convention, not a guarantee". This is a
    correctness/availability concern with no attacker, so it is not counted
    as a FINDING, but it is the same code path as finding 1 and the user
    may want it weighed alongside.
  - The static `ThreadLocal` cap-hit flag (PaginationSaturationTracker:41)
    is drained only on FetchScheduler's success path (:498); the catch path
    (:499-534) does not drain it, so a fetcher that signals and then throws
    would leak the flag onto the next source ticked on that thread and
    mis-attribute saturation. Audited and NOT reachable from this diff: of
    the four RSS-family fetchers only NitterFetcher throws after parse
    (NitterFetcher.java:72), and its guard requires `posts.size() == 1`,
    which cannot co-occur with a 1000-post cap hit. Noted so the
    non-finding is on record rather than silently assumed.

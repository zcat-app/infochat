OUT-OF-MODEL:
  - Stale group_membership / is_group_admin after a Signal member leaves.
    With supportsMembershipEvents flipped to false
    (infochat-messaging-adapter/src/main/java/app/zcat/infochat/messaging/impl/signal/SignalAdapter.java:313)
    the Provider's MembershipEventHandler.handleUserLeft path
    (infochat-provider/src/main/java/app/zcat/infochat/provider/group/MembershipEventHandler.java:79)
    never fires for Signal, and the documented fallback — permanent-
    delivery-failure cleanup (GroupRepository.java:214-256) — only covers
    BOT-removal, not per-user leaves. A group member (including the group
    admin) who leaves the Signal group retains their membership row and
    is_group_admin flag indefinitely; leave-then-rejoin silently resumes
    group-admin, and a departed admin's stale row blocks the zero-rows
    auto-promote path. This is NOT a threat-model violation:
    docs/spec/security.md §Authorization model only commits to refilling
    the slot after "demotion or ban" (leave is not listed), the /promote
    escape hatch remains available, spec/messaging.md mandates
    supportsMembershipEvents=false absent a native wire signal, and the
    identical posture is already accepted for SimpleX. Note also that the
    pre-diff Signal membership events were built against a wire shape
    that never existed live (F-live-10: fakes only), so no working
    security behavior is removed — but the user may want the model
    extended to state a commitment (or an explicit non-commitment) about
    leave-driven membership/admin cleanup on membership-event-less
    adapters, since both v1 adapters are now in that class.
  - Unvalidated group-id string as the per-group scope key.
    SignalGroupHandler.extractGroupId
    (infochat-messaging-adapter/src/main/java/app/zcat/infochat/messaging/impl/signal/SignalGroupHandler.java:283-293)
    accepts any JSON string (no base64-shape or length check) as the
    ScopeRef.Group id, unlike the sender ACI which passes
    isAcceptableAci. Pre-existing behavior (the old groupV2.id path was
    equally unvalidated) and not adversary-reachable in-model: the value
    is produced by the co-located signal-cli subprocess from the
    protocol-level 32-byte group identifier, and the daemon channel is a
    loopback-only trust boundary per security.md §Trust boundaries. Flagged
    only because the diff widens the accepted stanza spellings; a shape
    gate here would be cheap defense-in-depth if the model is ever
    extended to treat the daemon stream as fully hostile.

# Red-team audit: M1-160 (2026-06-06)

Verbatim threat-actor verdict:

```
RED-TEAM VERDICT: CLEAN

Audit notes (evidence trail for the verdict):

1. **Promise under test.** The relevant threat-model commitments are
   per-(user, scope) isolation ("Never leak across users or between DM
   and group", schema Invariant 1 as referenced by the diff) and the
   authorization step-4.6 anchor-clear rule ("any non-/retry input from
   the same (user, scope) clears the anchor"). The diff is itself an
   isolation fix: adding the `scope_kind` discriminator to
   `summary_anchor` so a `users.id`/`groups.id` UUID collision can no
   longer alias a user's DM and group anchors (`/forget` cross-scope
   delete, `/summary` overwrite, `/retry` cross-boundary replay).

2. **Write-path consistency verified.** The only main-code anchor writer
   is `SummaryCommandHandler.handle`
   (infochat-provider/src/main/java/app/zcat/infochat/provider/command/SummaryCommandHandler.java:174).
   Its `resolveScopeId` (line 262) returns empty for non-DM scopes, so
   `write(scopeId.get(), scopeKind, scopeId.get(), …)` only ever runs
   with `scopeKind="dm"` and `user_id = scope_id` — exactly the
   derivation the V37 backfill (`CASE WHEN user_id IS NOT NULL AND
   scope_id = user_id THEN 'dm' ELSE 'group' END`) assumes. The backfill
   is therefore exact for every production-reachable row shape (DM
   personal rows and `user_id IS NULL` digest rows); falsification
   attempt (a group personal anchor with `user_id != scope_id` reaching
   the backfill) found no producing code path.

3. **Read/clear/key parity verified.** All five `SummaryAnchorRepository`
   operations (UPSERT/SELECT/DELETE/retry-count increment/clear) now
   carry `scope_kind`, including the in-memory `RetryKey`.
   `InboundRouter` step-4.6 pairs `chatModeScopeKindOf(msg.scope())`
   with `resolveChatScopeId(msg.scope(), …)` from the same `ScopeRef`
   (InboundRouter.java:582-584), so kind and id cannot disagree.
   `RetryCommandHandler`'s hardcoded `"dm"` (line 147) is guarded:
   `resolveUserId` (line 328-333) rejects non-DM scopes before the read,
   confirmed in source.

4. **No stale call sites.** Grep over `src/main` shows every
   `summary_anchor` SQL touchpoint is either updated
   (`SummaryAnchorRepository`, `ForgetPurgeService`,
   `ExportDataCollector`) or genuinely discriminator-independent
   (`ChatMemoryPruner.java:45`, age-only DELETE).
   `ForgetPurgeService.countRemainingScopes` binds all nine parameters
   in the correct (userId, scopeKind, scopeId)×3 order
   (ForgetPurgeService.java:128-136).

5. **DB-level backstop.** V37 adds `NOT NULL` plus
   `summary_anchor_scope_kind_chk CHECK (scope_kind IN ('dm','group'))`
   and rebuilds both partial unique indexes with the discriminator, so a
   future caller passing a bogus or missing `scope_kind` fails
   structurally rather than silently aliasing — consistent with the
   trigger-layer-enforcement philosophy in §Authorization model.

6. **Residuals considered and rejected as findings.** (a) Backfill
   misclassification of a hypothetical pre-existing colliding row:
   probability ~2⁻¹²² per pair, UUIDs are server-generated
   (`gen_random_uuid()` / `UUID.randomUUID()`) with no attacker
   influence, anchors are ephemeral replay state, and the residual is
   explicitly documented in the migration and design note — not an
   exploitable gap. (b) In-memory `retryCounts` growth: one entry per
   registered DM user, cleared on write/clear — bounded, pre-existing.
   (c) `scopeKind` as an unvalidated `String` parameter:
   internal-to-internal call with switch-derived constants at every site
   plus the DB CHECK backstop — inside the trust boundary per the
   project's stated validation placement.

OUT-OF-MODEL: (none)
```

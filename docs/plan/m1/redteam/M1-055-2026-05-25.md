RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: AUDIT-EVASION
    SEVERITY: medium
    PROMISE: "Authorization evaluation order on every inbound message: ... 8. Audit-log the intent. 9. Execute." (security.md, Authorization model, steps 8-9). The threat model commits that every successfully dispatched command is audit-logged before execution.
    GAP: `infochat-provider/src/test/java/app/zcat/infochat/provider/command/asset/AssetCommandsRoundtripIT.java` -- the test `bannedUserHitsBanCheckBeforeDispatch()` (line 281-288) asserts that a banned user produces zero `SLASH_DISPATCH` audit rows, but the two successful-dispatch tests `zcashCommandReturnsRenderedReply()` (line 186-217) and `probationUserCanInvokeAssetCommand()` (line 238-257) make no assertion that a `SLASH_DISPATCH` audit row IS created. The asymmetry means a regression that silently drops audit logging for asset commands would pass this test suite. Since this is the umbrella roundtrip IT (the cross-cutting test that validates the full vertical), this is the expected location for such an assertion and no other test in the diff covers it.
    REPRO: (1) A future code change accidentally removes the audit-log write from the asset-command dispatch path (e.g., a refactor of the command dispatcher skips step 8 for the asset-command family). (2) This roundtrip IT continues to pass because it never checks for the presence of the audit row on the happy path. (3) Asset commands execute without audit trail, violating the step-8 commitment. An adversary with a compromised user account could invoke asset commands repeatedly with no audit record.
    SUGGESTED-FIX-CLASS: audit-log-coverage

OUT-OF-MODEL:
  - The test suite runs with the `infochat` superuser database role (per `application.properties` line 18: `quarkus.datasource.username=infochat`), not the least-privilege `infochat_provider` role defined in the threat model (security.md, DB roles). The `@BeforeEach` cleanup executes `DELETE FROM audit_log` (line 83), which would be denied under the Provider role's `INSERT`-only grant. This means the test does not validate the DB-role constraint that "a SQL-injection bug in the Provider cannot ... alter quarantine entries, read unredacted audit rows." This is outside the diff's scope (it predates this ticket) but means no integration test currently validates the least-privilege DB role separation.

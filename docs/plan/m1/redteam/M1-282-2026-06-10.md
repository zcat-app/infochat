Audit summary (no findings against the documented threat model):

The diff extends Redactor.redactThrownChain to walk the full thrown
*graph* (cause chain + suppressed throwables, recursively) where the
pre-diff code (M1-272) walked only the cause chain and disabled
suppression on the RedactedThrown replacement. This remediates the
M1-272 leak shape: a secret-bearing suppressed throwable (e.g. a
try-with-resources close() failure) that previously rode RAW into the
console formatter on the clean pass-through path.

The relevant threat-model commitments (docs/spec/security.md §Secrets
handling and §"User content in exceptions") require that stdout console
logs and exception cause chains pass through the closed API-key catalogue
redactor, fail-closed on timeout, with nothing unscanned reaching the
formatter. The diff delivers this for the newly-covered suppressed surface:

- Secret in a suppressed message / suppressed-node's-own-cause / nested
  suppressed -> scanGraph (Redactor.java:208) flags CHANGED -> rebuildGraph
  (Redactor.java:255) emits the memoized REDACTED form; raw never used
  (text built from redactedByNode at :261-264). Pinned by
  RedactorSuppressedChainTest.

- Timeout fail-closed preserved: redact() returning TIMEOUT_SENTINEL inside
  scanGraph propagates TIMED_OUT -> redactThrownChain returns null ->
  isLoggable (Redactor.java:147-154) wipes message/params/thrown to the
  fixed sentinel, identical to the message/param fail-closed arms.

- Budget overflow fail-closed: a graph exceeding MAX_THROWN_CHAIN_DEPTH (16)
  returns CHANGED at budget==0 (Redactor.java:210-214), forcing the rebuild
  arm; rebuildGraph truncates a cut cause to a marker node and DROPS a cut
  suppressed entry (Redactor.java:276-280). No past-cap (unscanned) node
  reaches the formatter. A large CLEAN graph past the cap is still
  truncated, not passed through raw.

- Cycle termination: scan and rebuild share an identical pre-order
  traversal and an identical per-visit budget decrement (memoization
  changes only whether redact() re-runs, never whether a node is
  visited/decremented), so the two phases stay in lockstep and a
  mutually-suppressing pair terminates at the budget cliff with the
  cyclic node's secret already memoized in redacted form. A rebuild
  node is never reached that scan did not reach, so the "missing map
  entry == null message, never == unscanned" invariant holds; no node
  is ever emitted class-name-only while secretly carrying an unscanned
  message. Pinned by mutuallySuppressingPairTerminatesWithoutRawLeak.

- RedactedThrown now constructs with enableSuppression=true
  (Redactor.java:295); each rebuilt suppressed is a fresh copy (never
  `this`), so addSuppressed cannot throw on self/null.

I attempted to break the scan/rebuild budget lockstep with DAG (shared
node reachable twice) and cyclic shapes; in every case both phases
consume budget identically and truncation/redaction is fail-closed
(dropping or redacting, never emitting raw). The remediation is complete
for the suppressed-throwable surface the ticket targets.

OUT-OF-MODEL:
  - toString()-override leak on the CLEAN pass-through path (pre-existing,
    NOT introduced or touched by this diff; lives in M1-272's design).
    The redactor scans only Throwable.getMessage() per node. A custom
    Throwable subclass whose toString() embeds detail NOT present in
    getMessage() (e.g. a framework exception appending bind parameters or
    a URL) would be declared CLEAN, and on the clean path the ORIGINAL
    object is returned to the formatter, whose header line calls the
    original toString() — emitting the unscanned extra text. The rebuilt
    path is safe (RedactedThrown uses default toString over the redacted
    message). This diff neither creates nor widens this gap (the clean-path
    pass-through and getMessage()-only scan both predate M1-282); the
    catalogue backstop's design contract is getMessage(), and the §"User
    content in exceptions" promise is delivered by the separate SafeLog
    call-site utility, not by this console filter. Flagged only so the
    user can decide whether a future ticket should make the catalogue scan
    a node's toString() rather than getMessage() on the clean path.

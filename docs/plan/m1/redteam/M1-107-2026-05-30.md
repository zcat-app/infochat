RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: INFO-LEAK
    SEVERITY: medium
    PROMISE: "`chat_memory` content, `saved_post` bodies and annotations, and the bodies of inbound chat-mode messages never appear in non-audit logs, at any log level (decision D37). Stage events, request IDs, scope IDs, and counts are loggable; the prose itself is not." — security.md §Secrets handling / User-content logging. Also: "Stdout console logs pass through the closed API-key catalogue redactor, fail-closed on regex timeout".
    GAP: `infochat-messaging-adapter/src/main/java/app/zcat/infochat/messaging/impl/signal/SignalJsonRpcClient.java:315` — `LOG.warnf(e, "ignoring malformed JSON-RPC line: %s", line)` logs the entire raw inbound line at WARN level. The `line` is read from the TCP socket and on a parse failure can contain arbitrary text including a user's chat-mode message body, recipient identifiers, or API-key shapes. No Redactor is applied to the log argument. The Throwable is also passed to SLF4J which §"User content in exceptions" mandates "MUST NOT" be done — the spec requires going through SafeLog which "drops the exception message body, retains only the exception class name".
    REPRO: Any party able to inject a malformed JSON-RPC envelope on the localhost TCP channel (the threat-model section explicitly notes "any local-loopback process can connect") sends a single line of the form `{"method":"receive","params":{"envelope":{"sourceUuid":"AAAA-...","dataMessage":{"message":"sk-ant-api03-REDACTEDLOOKINGSECRET..."}}` with a trailing JSON-syntax error so `SignalMessageCodec.decode` throws `IllegalArgumentException`. The raw line — including the API-key-shaped substring and the message body — is then logged verbatim at WARN. Even legitimate signal-cli output that hits the codec's malformed path (e.g. a protocol version drift) flows the user-content body into the log stream without the closed-catalogue redactor.
    SUGGESTED-FIX-CLASS: audit-log-coverage

  - CATEGORY: DOS
    SEVERITY: medium
    PROMISE: security.md §Threat model places "DOS — Resource exhaustion, unbounded loops, unbounded LLM calls" under enforced categories, and the adapter publishes `maxInboundMessageBytes` as a capability flag in `CapabilityFlags` (security-relevant per messaging.md / §Trust boundary 1, where the adapter is the system boundary that "asserts identity via a stable, cryptographically anchored ID" — the boundary owns inbound size enforcement).
    GAP: `infochat-messaging-adapter/src/main/java/app/zcat/infochat/messaging/impl/signal/SignalAdapter.java:77` declares `maxInboundMessageBytes=16_384`, but `infochat-messaging-adapter/src/main/java/app/zcat/infochat/messaging/impl/signal/SignalJsonRpcClient.java:302` reads inbound lines via `BufferedReader.readLine()` with no length cap. The codec's `JsonReader` then materializes the full line into a `JsonObject` in heap. The declared capability is a non-binding documentation value; the reader does not enforce it.
    REPRO: A local process — or a buggy / compromised signal-cli — connects to (or IS) the daemon TCP endpoint and writes a single line of `{"method":"receive","params":"AAAAA…"}` repeated until OOM. Each call to `readLine()` accumulates the line into a char buffer with no cap; the JVM heap is exhausted long before any application-level size check fires. Cross-reference: `SignalSubprocess`'s Javadoc explicitly accepts "any local-loopback process can connect" as the trust posture; this finding bites when that posture is the threat surface.
    SUGGESTED-FIX-CLASS: input-sanitization

  - CATEGORY: DOS
    SEVERITY: medium
    PROMISE: security.md §Threat model commits to bounding "Resource exhaustion, unbounded loops" — adapter classes must not retain per-message state indefinitely or a sustained workload exhausts memory.
    GAP: `infochat-messaging-adapter/src/main/java/app/zcat/infochat/messaging/impl/signal/SignalJsonRpcClient.java:84-85` declares `handles` and `finalized` as `ConcurrentHashMap`s without bounds; lines 152 and 164 `put` entries on every `send()` / `finalizeHandle()`; no path ever removes entries (no TTL, no eviction on `update`, no removal on `finalize`, no cleanup on `disconnect`). A Provider running 24/7 with sustained outbound traffic accumulates one `SignalMessageHandle` per sent message forever. `disconnect()` (line 120-141) clears `pending` but NOT `handles`/`finalized` — even a reconnect cycle does not free this state.
    REPRO: Provider sends N outbound messages over a long uptime (legitimate digest traffic + chat replies). After ~N entries, the JVM heap fills with `SignalMessageHandle` records holding the entire original `OutboundMessage` (including the message text, per the record's `original` field — line 152). Heap-exhaustion DoS on the longest-running deployment, with the message text amplifying the per-entry cost.
    SUGGESTED-FIX-CLASS: rate-limit

  - CATEGORY: INFO-LEAK
    SEVERITY: low
    PROMISE: "Contact IDs are logged in redacted form (prefix + ellipsis + suffix) outside the audit log" and §"User content in exceptions": "Exception messages and stack traces emitted via the application logger MUST NOT contain user-authored prose ... command arguments". `SafeLog` is the spec-mandated utility for this.
    GAP: `infochat-messaging-adapter/src/main/java/app/zcat/infochat/messaging/impl/signal/SignalJsonRpcClient.java:264-265` constructs `MessagingException` with raw `signal-cli error " + err.code() + ": " + err.message()`. signal-cli's error messages routinely embed the destination contact id (e.g. `"recipient +15551234567 is blocked"` or `"identity for AAAA-... revoked"`). The exception flows to the Provider; if any upstream caller does `LOG.error("send failed", e)` the unredacted contact-id text reaches non-audit logs. The adapter does not pre-redact. Same shape at `SignalJsonRpcClient.java:204` ("Unknown handle: " + opaqueValue — low risk) and at the `editMessage`/`call` exception messages.
    REPRO: A bot admin issues `/ban <contact-id>` after that contact's Signal identity has rotated. Provider's send to the contact returns signal-cli error `-32602 "identity for aabbccdd-1111-... revoked"`. The constructed `MessagingException.getMessage()` contains the full ACI; the Provider's standard error-path logging (assuming SafeLog is not in the exact chain) leaks the targeted contact id to operator logs in cleartext, defeating §Secrets handling's prefix-ellipsis-suffix redaction commitment.
    SUGGESTED-FIX-CLASS: audit-log-coverage

  - CATEGORY: INFO-LEAK
    SEVERITY: low
    PROMISE: "the bodies of inbound chat-mode messages never appear in non-audit logs, at any log level (decision D37)" — security.md §Secrets handling.
    GAP: `infochat-messaging-adapter/src/main/java/app/zcat/infochat/messaging/impl/signal/SignalSubprocess.java` `drainAndLog` — `LOG.debugf("signal-cli: %s", line)` logs the merged stdout+stderr stream of signal-cli verbatim at DEBUG. signal-cli is known to emit message-related metadata (recipient addresses, timestamp echoes, sometimes message-body excerpts at INFO/DEBUG modes). No Redactor is applied. Spec says "at any log level"; the DEBUG cushion is not a defense.
    REPRO: An operator enables DEBUG logging on `app.zcat.infochat.messaging.impl.signal` for any reason. signal-cli's own logger emits a line referencing the destination phone number / ACI of a recently sent message; the wrapper passes it straight through `LOG.debugf` and the redactor is never invoked.
    SUGGESTED-FIX-CLASS: audit-log-coverage

OUT-OF-MODEL:
  - The signal-cli daemon TCP endpoint is unauthenticated. Anyone with local-loopback access can connect and either inject `receive` notifications (impersonating any ACI to the Provider) or read outbound traffic. `SignalSubprocess`'s own Javadoc explicitly accepts this: "any local-loopback process can connect; for v1 single-user deployments per docs/spec/security.md's operator-trust boundary this is accepted". This is a documented operator-trust delegation, not a finding against the threat model, but worth surfacing: the spec's threat model does NOT itself enumerate "local process compromise" as out-of-scope — the carve-out is added by the implementation. If a future deployment hosts the Provider on a multi-tenant box, the spec's "cryptographically anchored ID" promise (Trust boundary 1) is silently downgraded because any local process can forge ACIs over this socket.
  - If the operator sets `infochat.adapters.signal.daemon-host` to `0.0.0.0` or a non-loopback interface, the unauthenticated JSON-RPC port becomes network-reachable. `SignalAdapter.start()` does not constrain the configured host to loopback. Per the threat model "Operator-set config (properties files, bootstrap JSON) is trusted" — so this is out-of-model, but the trusted-config posture means a single property typo silently exposes a full Signal-impersonation control plane.

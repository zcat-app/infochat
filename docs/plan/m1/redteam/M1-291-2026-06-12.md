RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: DOS
    SEVERITY: high
    PROMISE: docs/spec/security.md §SSRF and outbound connections:
             "Redirect, body-size, connect-timeout, and read-timeout caps
             are enforced; an unset timeout is a configuration error."
             The read-timeout cap exists specifically because (per the
             readBounded watchdog rationale, SsrfGuardedHttpClient.java:607-622,
             M1-025 Finding 4) "a malicious upstream can dribble body bytes one
             per minute and hold a fetcher thread for hours"; the terminal-hop
             body read defends this with a per-read wall-clock watchdog plus a
             total bodyReadDeadline.
    GAP: The new redirect-hop drain discardBounded
         (SsrfGuardedHttpClient.java:735-748, called at :413) enforces only a
         SIZE cap (loop `while (total <= cap)`), NOT a time cap. It calls
         `in.read(buf)` directly on the fetcher thread with no per-read
         watchdog and no total deadline — unlike readBounded
         (SsrfGuardedHttpClient.java:634-700) which supervises every read on a
         virtual thread bounded by min(readTimeout, remaining-to-deadline). The
         per-hop `request.timeout(requestTimeout)` only bounds receipt of
         response HEADERS (stated at :607-610), not reads from the
         ofInputStream() body, so the redirect-body drain has no wall-clock
         bound. U-40 delivered the size half of the cap but dropped the
         read-timeout/deadline half the spec commits to.
    REPRO: Adversary controls (or can inject a redirect into) a Collector feed
           URL or a /add-source probe target — both are spec-untrusted
           (§Threat model: "Collector is exposed to arbitrary feed content").
           The malicious server answers the first hop with a 30x + Location
           header (so the wrapper enters discardBounded), then trickles the
           redirect response body at ~1 byte per minute, staying just under
           bodyCap total bytes. discardBounded blocks in `in.read(buf)` on the
           fetcher thread with no timeout, holding that thread for up to
           bodyCap minutes (hours). Repeating across the fetch concurrency pool
           starves the Collector's ingest workers — the exact slow-dribble
           hold the per-read watchdog was built to prevent, reintroduced on the
           redirect path.
    SUGGESTED-FIX-CLASS: other

  does NFKC + bidi/zero-width only, and LlmOutputSanitizer is a byte-identical
  passthrough for a value carrying no closed-list token. So a post titled
  `[redacted command]` already renders byte-identically to a real redaction
  today, for a post that was never redacted.

  The diff's actual delta is that the RENDERER now supplies the brackets, so
  the attacker's title need only be `redacted command` rather than
  `[redacted command]` — a two-character reduction in attacker effort on an
  existing class, not a new one. That does not make it a non-finding: the
  bracket now also carries semantic meaning (the subordinate line is the
  publisher's original), so a collision is newly ambiguous between "original
  headline" and "a redaction happened here". The severity (low) and the
  bounded blast radius the verdict states both hold: nothing dispatches on
  either literal, no data is disclosed, and is_admin is still required for any
  privileged command.

    PROMISE: docs/spec/security.md §Ingest pipeline — "Matches are recorded as
              quarantine spans and replaced in the body with a **structured
              placeholder committed at spec level**: the literal sequence
              `[REDACTED:<id>]` ... The brackets and `REDACTED:` literal are
              byte-identical across every implementation so user-facing prose,
              snapshot bodies, and tests recognise the marker by exact-match;
              the per-row `<id>` randomization is what stops attackers from
              pre-crafting a fake placeholder". And §LLM output sanitizer —
              "the group-visible echo surfaces (`/saved` reply, `/summary`, and
              the degraded group digest) are additionally passed through the
              closed-list `LlmOutputSanitizer` at **render**, where a title or
              tag whose canonical form is a privileged command renders as
              `[redacted command]`."
    GAP: The diff introduces a render-time wrapper that puts square brackets
         around wholly publisher-controlled text, on the same user-facing
         surfaces where the two spec-committed bracketed markers live, with no
         collision check.
         - infochat-provider/src/main/java/app/zcat/infochat/provider/render/DisplayHeadline.java:375-377
           `bracketed(line)` returns `"[" + line + "]"` over an arbitrary
           rendered feed field.
         - Same file:355-357 (`primaryFor`) and :363-367 (`subordinateFor`) are
           the two callers; :331-342 (`anchorBlock`) composes them.
         - Reached from the group-broadcast and reply surfaces:
           infochat-provider/src/main/java/app/zcat/infochat/provider/digest/DigestRenderer.java:920-925
           (periodic digest, NORMAL mode),
           infochat-provider/src/main/java/app/zcat/infochat/provider/command/ClusterBlockRenderer.java:144-150
           (`/summary --flat`, `/retry --flat`),
           infochat-provider/src/main/java/app/zcat/infochat/provider/command/SavedCommandHandler.java:481-501
           (`/saved`).
         The bracket characters are supplied by the renderer, so an attacker no
         longer has to produce them — only the bracket CONTENTS. That defeats
         the specific defense the threat model names: the per-row `<id>`
         randomization stops a pre-crafted `[REDACTED:<id>]` only while the
         attacker must also supply the brackets. `DisplayHeadline` itself
         declares both collidable literals it now cannot distinguish from feed
         text — `STAGE1_REDACTION_PREFIX = "[REDACTED:"` (same file:458) and
         `LlmOutputSanitizerCore.REDACTED_COMMAND_REPLACEMENT = "[redacted
         command]"` (infochat-core/src/main/java/app/zcat/infochat/core/llm/LlmOutputSanitizerCore.java:81)
         — and `sanitize` is a byte-identical passthrough for a value carrying
         no closed-list token, so neither string is altered on its way out.
         Nothing downstream neutralizes it either: the outbound chokepoint only
         breaks `](` adjacency
         (infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/OutboundDelivery.java:219,232,265).
    REPRO: `cs` is an enabled reader language today and the corpus is
           English, so no operator config change is needed.
           1. Attacker publishes to any ingested source a post whose `title` is
              exactly `redacted command` (or `REDACTED:9f3a2c11`). The title is
              within `TITLE_MAX_LENGTH`, carries no leading `/`, and therefore
              survives Stage 1, `IngestTextNormalizer`, and
              `LlmOutputSanitizer.sanitize` byte-for-byte.
           2. Any group on `/lang cs` (or any reader whose language differs
              from the post's declared `source.language`) renders the post.
              `DisplayHeadline.subordinateFor` emits the original beneath the
              primary line, wrapped by `bracketed`.
           3. The delivered digest line reads
              `· Přeložený titulek` / `[redacted command]` / `https://…` —
              byte-identical to what the closed-list sanitizer emits when it
              actually strips a privileged command, for a post that was never
              flagged and that produced no `LLM_OUTPUT_SANITIZED` audit row.
              The `REDACTED:` variant renders `[REDACTED:9f3a2c11]`,
              byte-identical to a Stage 1 quarantine placeholder for a post
              with no quarantine row.
           4. Why the system shouldn't have allowed it: the threat model makes
              these two literals byte-exact precisely so a reader (and an
              operator triaging output) can recognise them by exact match, and
              it reasons explicitly about attackers pre-crafting a fake
              placeholder. An operator correlating rendered redaction markers
              against `audit_log` now sees phantom redactions with no matching
              row — the "counted, never throttled" audit trail and the rendered
              evidence no longer agree, in the direction that reads as missing
              audit coverage. Symmetrically, a forged `[redacted command]` lets
              a hostile publisher make the bot appear to have suppressed
              content it never saw.
           Bounded: no data is disclosed, nothing dispatches on either marker,
           and `is_admin=true` is still required for any privileged command,
           so the effect is confined to forged system annotations in bot
           output.

OUT-OF-MODEL:
  - The bracket invariant the diff introduces ("an UNBRACKETED line always
    means this is already in your language") is enforced on three of the five
    surfaces that render feed headlines. Two still render them bare through the
    pre-diff entry point: `DegradedDigestRenderer.java:78` and
    `SummaryProseGenerator.java:233` both call `DisplayHeadline.of(...)`, so on
    the degraded periodic digest and degraded `/summary` prose a foreign-language
    headline is delivered unbracketed. A reader trained by the three correct
    surfaces is misled on exactly the surfaces that appear when the LLM path has
    failed. This is a D29 (docs/spec/decisions.md) invariant, not a
    docs/spec/security.md commitment, so it is not scored as a finding — flagged
    so the user can decide whether the invariant should be promoted into the
    threat model (a follow-up, M1-766, appears to be filed for the parity work).
  - `post.title_en` / `post.body_en` are LLM-authored and have no write-boundary
    length cap: `IngestTranslationWorker.cleanTitle`
    (infochat-collector/src/main/java/app/zcat/infochat/collector/eval/translation/IngestTranslationWorker.java:422-426)
    applies `IngestTextNormalizer.stripMetadataField` but not

    This diff is the first to project those two columns into the Provider

    `DisplayHeadline.BODY_SCAN_LIMIT` before any scanning, and `post.body` /
    `body_en` were already uncapped and already projected, so the change is a
    constant-factor increase on an accepted profile rather than a new class.
    Flagged in case the model should state a retained-size bound for

# /redteam M1-109 — verbatim verdict

Target: M1-109 (Multi-adapter production shape IT)
Base: 5f6300f (M1-120: SimpleX + Signal CDI activation (D46))
Head: a374907 (M1-109: Multi-adapter production shape IT)
Date: 2026-06-01

RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
- **Fake-vs-production behavioral drift.** `FakeSimpleXProcess.runAccept` and `FakeSignalCli.acceptLoop` now silently absorb handshake failures and loop accepting further client connections (diff lines 442-484 for SimpleX, 322-363 for Signal). The real `simplex-chat` and `signal-cli` subprocesses are not modeled to accept multiple client connections per supervisor lifetime; a production adapter bug that spuriously double-connects would be invisible to these fakes (latest `clientWriter` simply overwrites the prior one). This weakens the IT's ability to detect a "leaked-socket double-connect" production regression. Not a production security gap — only a test-fidelity ceiling — and the threat model makes no commitment about test fidelity itself.
- **Audit-log trigger disable during `@BeforeEach` cleanup** (MultiAdapterProductionIT.java:173-189). Same pattern already flagged OUT-OF-MODEL on M1-105's redteam (docs/plan/m1/redteam/M1-105-2026-05-31.md). The window is bounded by Surefire's per-module JVM forking but would weaken the append-only invariant for any other `@QuarkusTest` running concurrently against the same DevServices container if Maven test forking changes in the future. Test-side, in-trust-boundary; not a finding here either.
- **Acceptance item asymmetry.** Ticket line 41 commits to `grantAdminIsAdapterScoped` verifying "SimpleX → Signal AND vice versa", but the test (MultiAdapterProductionIT.java:316-336) only exercises SimpleX-inbound flipping the SimpleX-target and leaving Signal untouched. The reverse direction (Signal-inbound, SimpleX-target untouched) is not separately asserted. The production code path is symmetric (one handler reads `inboundContext.adapterName()` for both adapters) so the omission is a test-coverage gap rather than a security gap, but a future refactor that branches per-adapter inside the handler would not be caught by this IT. Negative-space gap, not a spec/diff break.
- **Test profile bootstrap admin properties persist across IT lifetime** (MultiAdapterProductionIT.Profile lines 1148-1156 of the diff). `m1-109-simplex-bootstrap-admin` and `00000000-0000-0000-0000-000000000001` do not match the `m1-109-prod-%` cleanup prefix, so if M1-120's `@Startup` admin-bootstrap bean materializes rows from these properties, those admin rows survive `@BeforeEach` cleanup and persist for the JVM lifetime. Other ITs in the same Maven invocation sharing the Quarkus DevServices container would inherit these as "pre-existing admins". Test-isolation concern, not a security gap.

OUT-OF-MODEL:
  - Levenshtein input is no longer 32-char-bounded. The round-2 remediation's
    `isEchoSafe` guard, which the r2 audit credited with capping the fuzzy
    query at 32 characters, is deleted in this revision. The query is now
    bounded only by `infochat.command.body-cap` (application.properties:499-504;
    8192 default, 16384 on remote-llm), enforced at InboundRouter.java:698
    before dispatch. Honest arithmetic: a 16384-char query against ~45
    catalogue candidates of ~13 chars costs ~9.6M inner iterations in
    `editDistance` plus a comparable `contains` scan — roughly 20-30ms,
    inline on the transport thread (an unrecognized slash is
    non-interruptible per `isInterruptible`, InboundRouter.java:1026-1043).
    Bounded by the step-1.5 per-(adapter, contact_id) cap of 60/min, that is
    ~3% of one thread per hostile contact, and registration is invite-gated
    (D44). security.md §Authorization model step 1.5 names the transport cap
    as the committed bound for inbound "regardless of cost", so this is
    within model — flagged only because a reader tracking the r2 note may
    assume the 32-char bound still exists. It does not.
  - DB-read amplification on the unknown-slash path persists in this
    revision: InboundRouter.java:1442-1451 calls `slashMissSuggestion` ->
    `resolveTier`, i.e. one users-row SELECT plus a probation check, plus
    `findApprovalRow` + `isGroupAdmin` in group scope, where the pre-diff
    path issued zero. Within model for the same step-1.5 reason. The diff
    does now document it honestly in InboundRouter's class javadoc
    (InboundRouter.java:171-179), which the earlier revisions did not.
  - The intent map's fail-closed branch remains structurally unpinned.
    CommandIntentSynonyms.java:147-150 suppresses the similarity fallback
    when an intent word resolves to a command outside the caller's
    vocabulary. I re-verified this is not currently observable: `makeadmin`
    is the only admin-targeting entry, and it scores below MATCH_THRESHOLD
    against every non-admin-visible command (no containment hit, edit
    distance <=0.22 against the nearest), so a non-admin cannot distinguish
    it from an unmapped word. The property is safe today but rests on that
    coincidence — a future synonym that both maps to a hidden command AND
    scores >=0.6 against a visible one would make the suppression observable.
    No test in CommandIntentSynonymsTest pins the absence of that overlap.
    Hardening opportunity, not a current gap, and security.md states no
    command-existence commitment (the no-existence-leak property lives in
    commands.md §Permission model).
  - Group-scope tier disclosure via suggestions. In a group the reply is
    delivered to the whole group, so a bot admin whose near-miss resolves to
    a bot-admin name (e.g. `/makeadmin`) has their admin status disclosed to
    co-members. This is metadata-only and self-triggered — the same class
    security.md §Rate limiting already accepts explicitly for the per-user
    concurrency-cap reply ("in a group it necessarily reveals that the sender
    has concurrent bot activity in other scopes (accepted: metadata-only,
    self-triggered)") — and it is pre-existing: bare `/help` in a group
    already renders the tier-filtered catalogue into group-visible output.
    Noted for completeness, not proposed as a change.
  - Confirming the scope exclusion given in the task: the tag/timezone/asset
    friendly errors (FollowTagCommandHandler, UnfollowTagCommandHandler,
    GroupTimezoneCommandHandler, AssetHandler) still echo raw inbound text.
    This diff touches none of those files. I note only that the distinction
    the new spec text draws — those templates render `{0}` bare while the
    command template supplied the slash — is factually correct as a severity
    argument, but it is an argument about copy-pasteability, not about
    reflection: those surfaces do still reflect inbound bytes into bot
    output. The separate ticket is the right vehicle.

RED-TEAM VERDICT: CLEAN

Audited the M1-262 diff (chat agent includes prior conversation history in
the prompt) against docs/spec/security.md in full. The diff adds
ChatSessionRepository.readTurns + ChatPromptBuilder history-block folding +
a token-budget trimmer, plus tests. The security-relevant commitments that
this change touches are all delivered:

1. Per-(user, scope) isolation (CLAUDE.md §Key conventions; spec authorization
   model). ChatSessionRepository.SELECT_TURNS filters
   `WHERE user_id = ? AND scope_kind = ? AND scope_id = ?`
   (ChatSessionRepository.java:210-213). The query is parameterized — no SQL
   injection surface. readTurnsReturnsOnlyOwnUserAndScopeInSeqOrder and
   turnsFromDifferentUserOrScopeNeverAppear pin the WHERE clause against
   other-user, other-scope-id, and other-scope-kind rows. No cross-scope or
   cross-user leak.

2. Prompt-injection defense (spec §Prompt-injection defenses: "Every prompt
   that includes user-derived text is wrapped in a delimiter block whose
   marker contains a per-call random value"). The history block gets its own
   fresh UUID marker per call (ChatPromptBuilder.java:96-98), distinct from the
   memory-block marker and the current-message marker. An attacker cannot
   pre-store a matching close tag because the marker is random per build().
   historyWrappedInUntrustedContentDelimiters pins this.

3. Content already vetted before it re-enters as history. The persisted user
   turn is the normalized body (spec authorization step 1.7: "The normalized
   body replaces the raw body for all downstream processing") and the persisted
   assistant turn is the LlmOutputSanitizer output (ChatAgent.java:168-174,
   sanitize-before-persist). History is LLM *input*, wrapped untrusted; the
   outbound sanitizer still runs on each new reply. No admin-command leak path
   is opened.

4. No new LLM tool, mutation path, admin gate, ban path, or audit write is
   introduced or altered. The LLM tool surface (spec §Prompt-injection
   defenses tool table) is untouched; trust boundary 5 (LLM ↔ system state)
   is unchanged.

5. The token-budget trimmer (ChatPromptBuilder.newestTurnsWithinBudget) uses
   the operator-trusted `infochat.context-window` config value (application
   .properties:378, trusted per spec §Threat model "Operator-set config ...
   is trusted"). It drops oldest turns first, bounding the history slice. The
   rate-limit commitments (spec §Rate limiting: transport cap, LLM cap, tool
   calls per turn) are unchanged.

No promise in the threat model that this diff touches is left undelivered.

FINDINGS: (none)

OUT-OF-MODEL:
  - readTurns reads the entire (user, scope) session into memory with no SQL
    LIMIT before newestTurnsWithinBudget trims it. A session held at the
    ceiling after a compress failure could be large. This is a sizing/cost
    concern bounded by the upstream auto-compress / ceiling gate (spec
    §Failure handling: "the chat session is held at the ceiling ... the user's
    next chat-mode message returns a localized friendly error"), which lives
    outside this diff and is not removed by it. No spec bullet promises an
    absolute prompt-size bound beyond the unchanged rate limits, so this is
    not a threat-model gap — flagged only so the user can decide whether to
    add a defensive SQL-side LIMIT.
  - The history budget consumes the full context window for history alone,
    so history + memory block + tool results + current message can collectively
    exceed the model's actual context window. This is a prompt-quality / LLM-cost
    trade-off, not a spec-promised security property.

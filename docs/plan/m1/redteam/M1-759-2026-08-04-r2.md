              Stage 1 `<<<UNTRUSTED>>>` marker strip." And §LLM output

              reply, `/summary`, and the degraded group digest) are

              `LlmOutputSanitizer` at **render**, where a title or tag
              whose canonical form is a privileged command renders as
              `[redacted command]`."
    GAP: The round-1 remediation is present but is a WHOLE-STRING check,
         so it closes only the exact payload round 1 named and not the
         class. `DisplayHeadline.bracketed`
         (infochat-provider/src/main/java/app/zcat/infochat/provider/render/DisplayHeadline.java:402-405)
         builds `wrapped = "[" + line + "]"` and defers to
         `impersonatesASystemMarker` (same file, :415-418), which tests
         `wrapped.equals(LlmOutputSanitizer.REDACTED_COMMAND_REPLACEMENT)`
         and `STAGE1_PLACEHOLDER_SHAPE.matcher(wrapped).matches()` — the
         pattern at :508-509 is anchored by `Matcher.matches()`, i.e.
         whole-string. Neither test asks whether the renderer's own
         opening `[` has SYNTHESIZED a committed literal as a SUBSTRING.
         A feed value that carries its own closing `]` followed by any
         trailing byte therefore pairs with the renderer-supplied `[`,
         produces the byte-exact literal inside the delivered line, and
         takes the non-colliding branch: no leading-space break, no
         `LLM_OUTPUT_SANITIZED` audit row.
         `REDACTED_COMMAND_REPLACEMENT` is `"[redacted command]"`
         (infochat-core/src/main/java/app/zcat/infochat/core/llm/LlmOutputSanitizerCore.java:81),
         so `bracketed("redacted command] x")` returns
         `"[redacted command] x]"` — containing the literal — and
         `bracketed("REDACTED:9f3a2c11] x")` returns
         `"[REDACTED:9f3a2c11] x]"` — containing a well-formed Stage 1
         placeholder. Both spec-committed literals are affected.
         The wrap is reached on every render surface the diff touches:
         ClusterBlockRenderer.java:144-150 (`/summary --flat`,
         `/retry --flat`), DigestRenderer.java:920 (periodic digest,
         normal-mode headline block), SavedCommandHandler.java:481 and
         :497 (`/saved` primary and subordinate slots). The two new
         regression tests
         (`aFeedTitleImpersonatingTheRedactedCommandMarkerCannotForgeIt`,
         `aFeedTitleImpersonatingTheStage1PlaceholderCannotForgeIt` in
         ClusterBlockRendererTest) pin only the bare payloads
         `redacted command` and `REDACTED:9f3a2c11`, so they pass while
         the class stays open.

         an approximation: DisplayHeadline.java:392-400 asserts the wrap
         "must not complete a system-marker impersonation" and the
         ticket's acceptance item asserts "neither literal can be
         forged". As implemented, the narrower true statement is "neither
         literal can be forged by a payload that supplies no closing
         bracket of its own".
         Verified NOT broken by the remediation, for the record: a
         genuine redaction still renders byte-exact (a real
         `[redacted command]` or `[REDACTED:<id>]` inside a headline
         wraps to `[[redacted command]]` / `[[REDACTED:<id>]]`, which

         for operator `audit_log` correlation); `truncate` cannot

OUT-OF-MODEL: (optional, omit if empty)
  - No write-boundary length cap on the anchor columns this diff is the
    first to project. V74 declares `post.title_en TEXT` /
    `post.body_en TEXT` with no cap
    (infochat-core/src/main/resources/db/migration/V74__post_english_anchor.sql:49-50),
    and IngestTranslationWorker's `cleanTitle`/`cleanBody` apply NFKC,
    the metadata/bidi strip and the shared sanitizer but no length bound,
    so a hostile or compromised translator endpoint (in scope per
    §Trust boundaries item 9) can persist up to the full 1-8 MiB reply
    cap per post. This diff adds `p.title_en, p.body_en` to three bulk
    SELECTs (EligiblePostQuery, both DigestPostCollector post queries,
    RetryCommandHandler.SELECT_POSTS_BY_UIDS) with no SQL-side bound, so
    a render materializes them raw for every row in the page. CPU is
    bounded — `DisplayHeadline.renderLine` applies `boundForScan`
    (BODY_SCAN_LIMIT, 2000 chars) before the sanitizer — so the exposure
    is heap, and item 9's stated guarantee is per-reply
    ("a pathological multi-GB reply cannot exhaust the JVM"), not
    aggregate-across-stored-replies. Flagged out-of-model rather than as
    a finding because `p.body` is already uncapped at write and already
    projected raw in the same queries, so the class pre-exists the diff;
    the delta is that `p.title` WAS capped at 200 at its write boundary
    and its anchor is not. Worth deciding whether §Trust boundaries item
    9 should extend its bound to persisted derived text.
  - The collision check is an enumeration of exactly the two literals
    `docs/spec/security.md` commits, but the diff introduces
    renderer-supplied brackets onto blocks that render OTHER
    renderer-authored bracketed structural tokens the check does not
    know about. ClusterBlockRenderer.java:103 emits
    `[topic_id=<id>]` as the block header, and the new subordinate line
    renders `[<feed title>]` at line start immediately beneath the
    primary — so a post titled `topic_id=t-fake` now renders a line
    byte-identical in shape to a real block header. `reply.saved.line`
    (`- [{0}] {1} — saved {2} — tags: {3}`) is the same pattern for the
    uid slot. Not reported as a finding because neither token appears in
    the threat model and neither is parsed back by any handler (the
    `covered by:` line still names the real sources and uids), so the
    consequence is display spoofing only. Flagged so the user can decide
    whether the bracket-collision rule should be derived from "every
    renderer-authored bracketed token on the surface" rather than from a
    hand-maintained pair.

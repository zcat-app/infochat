RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - Per-source ingest-window monopolisation on a shared multi-author feed.
    A publisher who can post to an aggregator RSS/Atom source (a planet
    feed, a combined-account nitter/xcancel endpoint, any user-added
    `/add-source` URL) can occupy the whole per-parse window by emitting
    >= MAX_ITEMS newest-first items, starving every co-publisher on that
    same source indefinitely. This looks like the round-1 DOS finding, and
    it is NOT carried as a finding here, for two independently-checked
    reasons. (1) The diff grants no new capability: the identical monopoly
    is achievable — pre-diff and post-diff — by serving EXACTLY MAX_ITEMS
    items, which parses cleanly, records SUCCESS, and produces no
    notification of any kind. The over-cap shape is strictly noisier than
    the at-cap shape, so an adversary optimising for silence would never
    choose it. (2) `docs/spec/security.md` carries no ingest-fairness or
    per-publisher-availability commitment. Its ingest commitments are
    safety-shaped (§Ingest pipeline Stage 1/2, §Per-source trust
    boundaries, §SSRF and outbound connections) plus the D42
    fetcher-failure ladder; "which items a healthy source yields" is
    unconstrained. The named content-suppression vector in §"Flag position
    mirrors the parser's own scan" is render-time sanitize-span
    granularity over assembled multi-author prose, a different layer.
    Surfaced so the user can decide whether to extend the model with an
    ingest-fairness commitment (e.g. a per-source item-cap alert threshold
    below MAX_ITEMS, or per-author quotas within one source); it is not a
    gap against the model as written.

  - Cross-source truncation misattribution via an Error escaping fetch().
    `PaginationSaturationTracker.TRUNCATED` is a static ThreadLocal and
    `FetchScheduler.drainPending` ticks many sources sequentially on one
    heartbeat thread, so a flag left set would be read as the NEXT
    source's truncation and notify against the wrong uuid. The diff drains
    it on both exits — `FetchScheduler.java:513` (success) and
    `FetchScheduler.java:556` (the `catch (Exception)` path, added by this
    remediation with an explicit rationale comment). The only undrained
    exit is a `Throwable`/`Error` propagating out of `fetcher.fetch()`,
    which `catch (Exception e)` does not catch. I checked reachability and
    it is not a live path: `RssFeedParser.java:172` / `:244` call
    `signalTruncation()` immediately followed by `break`, after which the
    only code executed before the scheduler's drain is the return
    unwinding, `reader.close()` in the `finally`, and
    `NitterFetcher.isXcancelWhitelistPlaceholder`'s size check — no
    allocation-heavy or recursive work sits between the raise and the
    drain. Deliberate JVM-state manipulation to force an Error at that
    instant is outside this threat model's external-adversary scope.
    Noted only because the sibling flag is asymmetric: the same catch path
    does NOT drain `CAP_HIT`. That asymmetry is pre-existing (not
    introduced or widened by this diff) and equally unreachable —
    `BlueskyFetcher.java:107` and `RedditFetcher.java:113` both call
    `signalCapHit()` after their page loop, with only `return` between the
    raise and the scheduler's `consumeCapHit()`. Hardening opportunity for
    a future ticket, not a finding against this one.

VERIFICATION NOTES (why the two round-1 findings are treated as closed,
and what else was checked and rejected — recorded so a later reader can
falsify this CLEAN rather than take it on trust):

  - Round-1 finding 2 (AUDIT-EVASION / low) is CLOSED. Truncation now
    raises its own flag, independent of the streak-gated pagination
    signal: `PaginationSaturationTracker.java:64` (`TRUNCATED`), `:107`
    (`signalTruncation`), `:119` (`consumeTruncation`). `recordTick` and
    its streak-reset at `:133-141` are byte-unchanged, so the
    `architecture.md:301-305` pagination-saturation commitment is intact.
    `FetchScheduler.java:577-588` fires `notifyOnce` on EVERY truncating
    tick with no streak gate. `ThrottledAdminNotifier.runNotify`
    (`:331-364`) persists an `admin_notification_state` row on the first
    call for the key and bumps `suppressed_count` on every subsequent
    within-window call, so the record is durable AND carries an occurrence
    count. The 1001/1001/999 oscillation that defeated the streak now
    notifies on tick 1; pinned by
    `FetchSchedulerSaturationIT.truncationNotifiesEvenWhenNoConsecutiveStreakEverForms`,
    which interleaves a clean tick so no streak of `threshold` ever forms
    — it discriminates against the rejected design, plus a negative
    control and an independence guard.

  - Round-1 finding 1 (DOS / medium) is CLOSED on the half that mapped to
    a threat-model promise. §Failure handling's D42 remedy is "a throttled
    admin notification is sent with the error class and source id"; the
    truncation path now delivers exactly that shape — error class
    `feed_truncated`, key `feed_truncated:<source uuid>`. The residual
    (the tick still calls `recordSuccess`, so `consecutive_failures` is
    zeroed and the source stays `status='active'`) no longer makes a
    truncating source indistinguishable from a healthy one, because the
    durable row plus the ADMIN-NOTIFY WARN line name the source and the
    condition. Delivery being "WARN log + persisted row" is the
    system-wide notifier posture (identical for `fetch_failure_ladder`,
    `fetch_saturation`, `fetch_persist_failure`), not a truncation-specific
    weakening.

  - The cap's actual security purpose — bounding allocation against a
    hostile unbounded item list — is preserved and slightly strengthened.
    The check moved BEFORE the parse of the cap+1-th item
    (`RssFeedParser.java:171`, `:243`) and `break`s, so the reader stops
    and the remaining bytes are never walked; the old code allocated
    MAX_ITEMS+1 posts before throwing. Pinned by
    `rssTruncationStopsConsumingTheStreamAtTheCap` /
    `atomTruncationStopsConsumingTheStreamAtTheCap`, which place a
    malformed item past the cap that a parse-everything-then-trim
    implementation would choke on.

  - No new DOS capability. Per-tick cost of an over-cap source
    post-diff (one <=5 MiB GET, 1000 parsed items, 1000 dedup-INSERTs,
    one notifier upsert) equals the cost of a legitimate exactly-at-cap
    source, which was always reachable and never self-parked. The
    notifier's per-(key, window) coalescing (default 1h) bounds WARN
    volume; the suppressed path is two statements against one row.

  - No new INFO-LEAK. The notification interpolates `row.uuid()`,
    `row.kind()` and `posts.size()` only — never `row.identifier()`,
    preserving the M1-023 URL-redaction precedent that the removed throw
    path carried via `logFetchFailure`/`UrlRedactor`, and never any feed
    content. `ThrottledAdminNotifier.sanitize` strips C0/C1/DEL and caps
    the message at 2048, so the ADMIN-NOTIFY scrape contract cannot be
    forged.

  - No unbounded key growth. `feed_truncated:<uuid>` is one key per
    source row — the same cardinality class as the three existing
    per-source keys — not a per-tick-unique key. Length is 51 chars
    against MAX_KEY_LENGTH 256.

  - No INJECTION surface. `row.kind()` reached the message only after
    `fetchersByKind.get(row.kind())` returned non-null, so it is one of
    the registered kind literals; all notifier SQL is parameterized.

  - Blast radius of the reject->truncate change is confined to the four
    RSS-family kinds. `BlueskyResponseParser.java:73-74` and
    `RedditResponseParser` still REJECT over-cap (comment-only edits in
    both), and `BlueskyResponseParserTest` /
    `RedditResponseParserItemCapTest` still pin those rejections.

  - Test integrity: nothing weakened, disabled, retargeted, or deleted.
    `RssFeedParserTest` gains a `@BeforeEach` drain and eight cases with
    all 15 pre-existing cases intact; `FetchSchedulerSaturationIT`'s
    existing streak assertions are untouched, its fixture cleanup only
    widened to delete the second key prefix.

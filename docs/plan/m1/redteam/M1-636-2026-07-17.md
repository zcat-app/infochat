RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: DOS
    SEVERITY: low
    PROMISE: "Per-user interruptible concurrency (M1-636) — not a rate
              bucket: a ceiling on one sender's CONCURRENT interruptible
              requests (the same three surfaces as the LLM bucket above,
              queued + running) across all scopes ... Checked at intake
              before any token draw or slot acquisition" (docs/spec/security.md:1218-1227).
              The referenced LLM bucket's surface list is "chat replies +
              on-demand `/summary` + `/retry` re-rolls" (docs/spec/security.md:1213-1214),
              and security.md:1031 explicitly names "`/retry --digest`" as a
              summarizer-invoking surface of that family.
    GAP: The cap check runs only inside the isInterruptible branch
         (infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/InboundRouter.java:855-878),
         and isInterruptible deliberately classifies `/retry --digest` as
         non-interruptible (InboundRouter.java:1018-1025), so that
         LLM-triggering re-roll is dispatched inline with no
         countNonTerminalTurns admission check and is never counted
         against the sender's ceiling. Delivery therefore covers only
         two-and-a-half of the "same three surfaces" the new spec bullet
         claims: a sender already at their concurrency cap can still
         originate one additional concurrent LLM-triggering request.
         Bounded in practice — the inline dispatch serializes on the
         adapter's single transport thread (at most one at a time, and it
         can never take a pool worker, so the "cannot occupy every
         dispatch worker" clause itself holds) and the per-user LLM rate
         bucket still meters it — hence low, but the spec text as amended
         promises more than the code enforces.
    REPRO: 1) Attacker (registered user) sends a chat message in their DM
           and a group @mention in an approved group; both turns are
           admitted and hold LLM calls (cap = 2 reached, both slots
           RUNNING). 2) Having previously run `/summary` in a third scope
           (a frozen digest anchor exists), the attacker now sends
           `/retry --digest` there. 3) InboundRouter.isInterruptible
           returns false, the M1-636 check at InboundRouter.java:871 never
           executes, and the summarizer LLM call runs inline — the sender
           now drives cap+1 concurrent LLM-triggering requests, which the
           amended §Rate limiting bullet says the ceiling was supposed to
           bound. The inline call additionally occupies the adapter's
           single dispatch thread for its full duration (pre-existing
           M1-634 design, but the new cap was sold as bounding exactly
           this sender-share class).
    SUGGESTED-FIX-CLASS: rate-limit

OUT-OF-MODEL:
  - Cross-scope activity disclosure in the reject text: the fixed reply
    ("You already have several requests in progress across your chats...",
    bundles/en.properties:556) is delivered into the scope the over-cap
    request arrived in — in a group, all members see that the sender has
    concurrent bot activity in OTHER scopes (possibly their private DM).
    Metadata-only, self-triggered (only the sender's own over-cap message
    fires it; no third party can probe another user's count), and the same
    class of cross-scope signal as the pre-existing per-user
    error.chat.llm_rate_cap reply and the explicitly accepted
    translation-cache side channel — but unlike the latter it is
    undocumented. Flagged for a decision on whether to accept-and-document
    or soften the wording.
  - No boot-time sanity coupling between infochat.chat.dispatch.per-user-cap
    and infochat.chat.dispatch.max-concurrency (InterruptibleDispatcher
    validates only perUserCap >= 1): an operator setting per-user-cap >=
    max-concurrency silently voids the "single sender cannot occupy every
    dispatch worker" property the spec bullet states. Operator-set config
    is trusted per the threat model (out of model), but the existing
    max-concurrency >= 2 boot check shows the project already guards
    config footguns of exactly this shape.

RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - Operator misconfiguration can void the single-sender property: nothing
    couples infochat.chat.dispatch.per-user-cap to
    infochat.chat.dispatch.max-concurrency at boot
    (InterruptibleDispatcher.java:154 validates only >= 1), so an operator
    setting per-user-cap >= max-concurrency re-opens "one sender occupies
    every worker." Operator-set config is trusted per the threat model
    (§Threat model, "Operator-set config ... is trusted"), so this stays
    out-of-model; the ticket records it as deliberately routed to a
    post-merge follow-up. Re-flagged so the follow-up is not silently
    dropped.
  - Colluding-identity pool saturation survives the cap by design: with the
    shipped defaults (per-user-cap 2, max-concurrency 4), two registered
    identities can jointly hold every pool worker. The promise is scoped to
    ONE sender's share ("one sender's CONCURRENT interruptible requests"),
    per-user fairness is an explicit v1 non-commitment
    (docs/design/06-messaging.md §6.3.7), and every extra identity costs an
    admin-issued invite (documented Sybil non-commitment,
    docs/spec/security.md §What's intentionally NOT in v1) — a documented
    residual, not a delivery gap; noted for the residual-risk ledger.

Re-audit verification trail (no findings):
  - The prior 2026-07-17 low DOS finding (spec-text overpromise: "same

  - "Checked at intake before any token draw or slot acquisition; a

RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: AUDIT-EVASION
    SEVERITY: medium
    PROMISE: docs/spec/security.md §Trust boundaries entry 9 (as amended by this
             diff): "Provider-reported **numeric usage** (token counts) is
             checked at that same boundary before it reaches the counters: a
             negative count, or an output count above the generation cap the
             request itself carried, is impossible for an honest endpoint, and
             such a report is discarded whole rather than clamped — the call
             then counts as reporting no usage, so the tampering shows up as a
             gap between the call counter and the token counters rather than as
             a plausible figure."
             Mirrored in docs/spec/llm.md §Bounded concurrency and
             observability: "an output count above the generation cap the
             request carried ... is discarded whole".
    GAP: The delivered upper bound is NOT "the generation cap the request itself
         carried"; it is "the per-task config key, if the operator set one",
         and in every shipped configuration that key is unset, so the
         upper-bound half of the promised check never fires.
         - infochat-llm-adapter/.../metrics/MeteredLlmProvider.java:202-213
           (`configuredOutputBound`) reads only
           `infochat.llm.<task>.max-tokens`; an absent key returns
           `NO_OUTPUT_BOUND` = `Long.MAX_VALUE` (declared at
           MeteredLlmProvider.java:65-69).
         - MeteredLlmProvider.java:174-176 is therefore reduced to the sign
           check alone for any task without that key.
         - The request nevertheless always carries a cap:
           infochat-llm-adapter/.../impl/OpenAiCompatibleProvider.java:207
           (`config.getOptionalValue(prefix + "max-tokens", Integer.class)
           .orElse(1024)`) and :225 (`root.put("max_tokens", cfg.maxTokens())`);
           docs/design/05-llm-and-embeddings.md:172-176 states "Every request
           carries `max_tokens` ... (optional, default 1024 ...). The default is
           a cap, not absent-means-uncapped".
         - No `.properties` file in the repository sets `max-tokens` for any
           task (repo-wide grep for `max-tokens` over `*.properties` returns no
           matches); infochat-collector/src/main/resources/application.properties
           and infochat-provider/src/main/resources/application.properties carry
           only per-task `model` keys (collector :415-:512, provider :362-:379).
           The setup wizard writes the key for `chat` and `summarizer` only
           (prod/scripts/4-llm.sh:647-653), leaving security, tagger, entity,
           classifier and translator permanently unbounded.
         - The gap is enshrined by the new test
           infochat-llm-adapter/src/test/java/.../LlmObservabilityTest.java:207-219
           (`reportedCountsStillRecordForATaskThatConfiguresNoMaxTokens`): a
           TAGGER reply reporting 4,000 output tokens is asserted to be RECORDED
           — yet that request carried `max_tokens=1024`, so 4,000 is exactly the
           "impossible for an honest endpoint" report the spec bullet says is
           discarded.
    REPRO: 1. Deploy with the shipped `application.properties` (no `max-tokens`
              key anywhere) — i.e. the default v1 deployment; the wizard-written
              overrides cover only chat/summarizer.
           2. Point `infochat.llm.default.base-url` (or any per-task base-url) at
              a hostile or compromised OpenAI-compatible endpoint — in scope per
              §Threat model ("LLMs ... are black boxes that can be coaxed into
              emitting attacker-chosen output. Local and remote LLMs have the
              same trust level") and entry 9 ("whatever answers on the
              configured base-url picks every field of the reply").
           3. Answer any SECURITY_JUDGE / TAGGER / ENTITY / CLASSIFIER /
              TRANSLATOR call with a well-formed body whose
              `usage.completion_tokens` is 9_000_000_000 (or any value above the
              1024 the request sent).
           4. `MeteredLlmProvider.plausibleUsage` accepts it (bound =
              Long.MAX_VALUE) and `LlmMetrics.recordLlmCall`
              (LlmMetrics.java:92-94) increments `llm.tokens.out` by it.
           5. Result: the endpoint writes an arbitrary figure into the
              observability record, and the promised tamper-evidence signal
              ("llm.calls.total outrunning the token counters") never appears —
              the operator sees a plausible-looking, monotonically-inflated
              series instead. The spec promised this exact report class would be
              discarded whole.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

  - CATEGORY: AUDIT-EVASION
    SEVERITY: low
    PROMISE: docs/spec/security.md §Trust boundaries entry 9 (as amended by this
             diff): "The residual is the in-range lie: a reply reporting a
             wrong-but-possible count is indistinguishable from an honest one,
             and no v1 decision reads these counters, so its blast radius stays
             inside usage observability."
    GAP: The delivered check bounds the INPUT count only by sign
         (MeteredLlmProvider.java:174 — `usage.inputTokens() >= 0`), with no
         upper bound of any kind and no relation to the prompt actually sent, so
         the admitted residual is far wider than "wrong-but-possible": an
         endpoint may report `prompt_tokens = 9223372036854775807` and it is
         recorded verbatim by LlmMetrics.java:89-91. That figure is not
         "indistinguishable from an honest one" — it is as impossible as the
         over-cap output count the same method rejects — yet it passes the
         boundary the spec bullet says usage is "checked at ... before it reaches
         the counters".
         Secondary vector on the same boundary: the value the check sees for
         Anthropic is a THREE-field wire-controlled sum computed upstream at
         infochat-llm-adapter/.../impl/AnthropicProvider.java:267-271
         (`input_tokens + cache_read_input_tokens +
         cache_creation_input_tokens`), so an endpoint can choose three values
         whose 64-bit sum wraps to a small positive number that the boundary
         then reads as honest; the check runs after the overflow, not on the
         reported fields.
         Because Micrometer counters are monotonic and only reset on process
         restart, a single such reply permanently destroys the
         `llm.tokens.in{task,provider,model}` series for the JVM lifetime — the
         same "poisoned for the process lifetime" property M1-673 closed for the
         `model` tag is left open for the counter magnitude.
    REPRO: 1. Same hostile-endpoint setup as finding 1 (in scope per entry 9).
           2. Return one well-formed reply with
              `"usage":{"prompt_tokens":9223372036854775807,
              "completion_tokens":1}` for any task (no config key required — the
              input side has no bound in ANY configuration, not just the default
              one). Anthropic variant: `input_tokens` /
              `cache_read_input_tokens` / `cache_creation_input_tokens` chosen so
              the sum wraps.
           3. `llm.tokens.in` jumps to ~9.2e18 and can never come back down; all
              later honest increments are invisible against it, and every
              `rate()`/`increase()` over the series is meaningless for the rest
              of the process lifetime, with no discarded-report gap to signal
              that anything happened.
    SUGGESTED-FIX-CLASS: input-sanitization

OUT-OF-MODEL:
  - An operator who configures an absurd `infochat.llm.<task>.max-tokens` (e.g.
    10_000_000) makes the upper bound vacuous. Operator-set config is trusted
    per §Threat model ("Operator-set config (properties files, bootstrap JSON)
    is trusted"), so this is not an adversary-reachable path — but it is worth
    noting that the bound's strength is entirely an operator-config property.
  - An unresolvable config expression in `max-tokens` would make
    `config.get(...)` throw inside `plausibleUsage`, converting an already
    successful LLM call into a FAIL-metered exception. The delegate's own
    `configFor` reads the same key first and fails earlier, and operator config
    is trusted, so this is not reachable by an adversary in the documented model.

AUDIT NOTES (no finding; recorded so a re-audit does not redo the work)

Checked against the commitments this diff itself adds to docs/spec/security.md
§Trust boundaries entry 9 and docs/spec/llm.md §Bounded concurrency and
observability. Note: the verdict file previously at this path was from an
earlier revision of the working tree — it cited
INPUT_OVERHEAD_SLACK_TOKENS = 65_536 and "neither spec file mentions the
slack". Both are now false: the constant is 1024 (MeteredLlmProvider.java:102),
security.md discloses "a small fixed allowance for the provider's own
chat-template overhead" and names it in the residual ("including one inside
the input side's bounded template-overhead allowance"), llm.md mirrors it
("which is bounded but not zero"), and
`inputCountJustAboveTheOverheadAllowanceIsNotRecorded` pins the allowance as
bounded rather than blanket. That finding is remediated.

  1. "checked at that same boundary before it reaches the counters" —
     `recordLlmCall` has exactly two call sites, both in MeteredLlmProvider
     (:142-143 OK path via `plausibleUsage`, :149 FAIL path with a literal
     null). No other production caller anywhere in the repo. HOLDS.

  2. "the generation cap the request carried (the effective cap, default
     included — an absent per-task max-tokens does not mean uncapped)" —
     there are exactly three production LlmProvider impls.
     OpenAiCompatibleProvider.java:207 resolves an absent key to 1024 and
     :225 sends it; DeepSeekProvider extends it and adds only the
     thinking/reasoning_effort field (DeepSeekProvider.java:182-190),
     inheriting the same cap; AnthropicProvider.java:168 reads it with
     `config.getValue` (no default) so an absent key fails the startup scan
     before any call. Decorator and providers read the byte-identical key
     expression `task.configPrefix() + "max-tokens"` off the same injected
     `Config`, so profile keys, env-var mappings, and config expressions
     resolve identically on both sides — no divergence is constructible in
     a booted deployment. No properties file in the repo sets the key
     (verified by grep) and prod/scripts/4-llm.sh writes it for chat +
     summarizer only, so 1024 is the real effective cap everywhere else.
     HOLDS.

  3. "input count exceeds a ceiling derived from the size of the prompt sent
     plus a small fixed allowance" and "it never discards an honest reply" —
     the bound is 3 * (systemPrompt.length() + userPrompt.length()) + 1024
     (MeteredLlmProvider.java:242-245). A Java char is at most 3 UTF-8 bytes
     (a surrogate pair is 2 chars for 4 bytes), and no byte-level BPE token
     consumes fewer than one byte, so this is a genuine upper bound on any
     tokenization of that prompt. Both v1 request bodies carry only
     model/max_tokens/system+user with no tool or function schemas
     (OpenAiCompatibleProvider.java:223-232, AnthropicProvider.java:180-199),
     so the 1024 slack covers chat-template overhead with room to spare.
     Anthropic's three input fields are disjoint per the Messages API
     (input_tokens excludes cached tokens), so folding them cannot
     double-count an honest reply into a false discard — the pre-existing
     AnthropicProviderCacheTokenTest pins the sum. No arithmetic overflow:
     max promptChars is ~4.3e9, times 3 is ~1.3e10, far inside long. HOLDS.

  4. "no counter can be driven backwards" — a negative on either field
     discards the whole record (MeteredLlmProvider.java:217-221), so no
     negative reaches `Counter.increment`. HOLDS.

  5. "discarded whole rather than clamped" / "the call then counts as
     reporting no usage" — returns null, which LlmMetrics.java:88 reads as
     no-usage while still incrementing llm.calls.total, producing exactly
     the promised gap. HOLDS.

  6. Residual accuracy. The Anthropic three-field 64-bit sum
     (AnthropicProvider.java:267-271) can wrap; a wrap to negative is caught
     by the sign check, a wrap to a small positive is admitted — exactly
     what the amended spec names ("since the boundary sees only the wrapped
     total"). `cache_read_input_tokens` / `cache_creation_input_tokens` use
     `asLong(0L)` with no `canConvertToLong` gate, so a JSON double like
     1e30 saturates to Long.MAX_VALUE before the addition; the resulting sum
     still lands in the disclosed wrap case. The residual is stated, not
     understated.

  7. Embedding side (entry 9 covers "LLM/embeddings provider response").
     LlmMetrics records no token counters for embeddings;
     `embedding.dimension` is a gauge whose value is re-settable
     (LlmMetrics.java:123-130), so it carries no monotonic-poisoning
     property, and its provider/model tags come from `providerName()` and
     `infochat.embeddings.model`, never the wire
     (MeteredEmbeddingProvider.java:46-52, :62-64). No wire-derived metric
     label exists on either side. Unaffected by this diff and still
     satisfied.

  8. Log hygiene (§Secrets handling, §User content in exceptions). The new
     discard log (MeteredLlmProvider.java:222-225) emits only the task key
     segment, the constant provider name, and four integers — no prompt or
     response content, and no attacker-controlled string reaches a format
     argument, so there is no log-injection surface. Prompt length is
     inferable from the logged `inBound`; that is a count, which §Secrets
     handling explicitly permits ("Stage events, request IDs, scope IDs, and
     counts are loggable; the prose itself is not").

  9. No test weakening. The added `max-tokens=256` in the shared setup and
     the stub's new mutable `wireUsage` field leave every pre-existing
     assertion — including M1-673's wire-model-tag absence checks —
     reachable and unchanged; the honest (10, 5) default sits inside both
     new bounds, and the negative-count test seeds an honest call first so
     it asserts against non-zero baselines.

 10. Untouched surfaces confirmed untouched: no authentication,
     authorization, admin-tier, ban-path, invite-code, per-(user, scope)
     isolation, or audit_log write is reached by this diff. The only
     non-code changes are STATUS.md bookkeeping and the ticket file.

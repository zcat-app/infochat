FINDINGS:
  - CATEGORY: DOS
    SEVERITY: medium
    PROMISE: security.md §Failure handling, per-source UNKNOWN auto-disable (docs/spec/security.md:1547-1553, as
              amended by this diff) — "A source whose Stage 2 UNKNOWN rate exceeds a profile-driven threshold ... has
              its `source.status` transitioned to `'failed'` (the same status used for consecutive HTTP failures,
              decision D42 — but **excluded from D42's automatic re-probe rung**: this park is a security control, its
              park-reason discriminator marks it manual-only, and recovery happens only via `/source-enable`)". Same
              commitment at security.md:1363-1379 ("Parks written by the per-source UNKNOWN-rate auto-disable (below)
              and by D38's cycle cap are excluded from re-probe — they recover only by admin action, distinguished via
              the park-reason discriminator") and at decisions.md:59 (D42 amended) — "`status='failed'` has two other
              writers whose recovery stays manual by design ... automatically re-enabling an adversary-influenced feed
              would defeat it". The control's stated purpose (security.md:1556-1572) is the quarantine-exhaustion
              defense: "the system shifts the cost from 'admins must triage every post indefinitely' to 'admins
              re-enable a single source after diagnosis.'"
    GAP: The exclusion is delivered only when the security control is the writer that PARKS the row, and the amendment
         makes it structurally impossible for that control to claim a row another writer parked first. D42 property (a)
         (docs/spec/decisions.md:59) is normative and one-way: "a park reason is written by the same guarded condition
         that performs the `active → failed` transition ... a writer that does not park the row does not write the
         reason"; schema.md:268-271 restates it. Both manual-only writers are guarded on the row still being active —
         `PerSourceUnknownTracker.java:148` (`UPDATE source SET status = 'failed' WHERE id = ? AND status = 'active'`)
         and `NostrStreamSource.java:558` (identical guard) — and the UNKNOWN tracker's *selection* also filters
         `WHERE s.status = 'active'` (`PerSourceUnknownTracker.java:114`), so it never even evaluates a parked source.
         Consequently a row already parked `fetch-failure` by the D42 ladder can never be relabelled `unknown-rate`, no
         matter how far its UNKNOWN rate later exceeds the threshold: the security control's write is a silent no-op and
         the row keeps the one reason that IS re-probe-eligible. Property (b) ("Manual-only wins — a fetch-failure
         reason may never overwrite a manual-only reason; the precedence is one-directional and is a property of the
         write") reads as if it covers this, but it only constrains the fetch writer; it states no obligation on the
         manual-only writer to upgrade an existing reason, and property (a) forbids exactly that upgrade. M1-754's
         acceptance pins the losing side of the tension and not the winning one: "All three park writers record their
         reason in the same statement that sets `status='failed'`" (M1-754-parked-source-reprobe-ladder.md:69-73) —
         for the tracker that statement is the `status = 'active'`-guarded UPDATE — and the exclusion legs
         (M1-754...md:124-130) "seed a parked row with its reason", i.e. they only exercise the ordering where the
         security control won the race. Before this amendment the no-op was harmless (`failed` was terminal for every
         writer, so which control got there first did not matter); the amendment makes recovery rights depend on write
         order and does not carry the control across.
    REPRO: Adversary controls, or can post into, an ingested HTTP-shaped feed (in-model: "The Collector is exposed to
           arbitrary feed content. Every RSS publisher ... is untrusted", security.md:22-23).
           (1) Publish a burst of borderline content that Stage 2 labels UNKNOWN — the quarantine-exhaustion payload
               the per-source control exists to stop. Stage 2 verdicts land over the following hours (bounded eval
               concurrency); the UNKNOWN rate is computed on verdict time (`status_changed_at`), not fetch time
               (PerSourceUnknownTracker.java:108-125).
           (2) Immediately after the burst, make the endpoint fail (refuse connections). At the profile default of five
               consecutive failures on a 30-minute poll (decisions.md:59), the D42 ladder parks the row ~2.5h later
               with reason `fetch-failure`.
           (3) The UNKNOWN rate crosses the threshold after that park. `checkAllSources` filters `s.status = 'active'`,
               so the source is not even a candidate; `disableSource`'s UPDATE would be a no-op anyway. No
               `unknown-rate` reason is ever written, no admin notification about the UNKNOWN rate fires, and the row
               stays labelled `fetch-failure`.
           (4) The re-probe ladder selects it (reason matches, `deleted_at IS NULL`, backoff due, under cap). The
               adversary answers one probe with 200. The row is restored to `active`, `consecutive_failures` zeroed,
               and — per M1-754...md:114-117 — the park reason AND re-probe state are cleared, so the absolute
               re-probe cap counter resets too.
           (5) Repeat from (1). Each cycle re-opens ingest from the feed and refills the quarantine review queue with
               no admin ever diagnosing anything, and because step (4) resets the ladder the absolute cap never bites.
           The system should not have allowed this: the spec says an UNKNOWN-rate park "recover[s] only by admin
           action", and here the very feed the control was measuring is auto-readmitted on a timer.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

OUT-OF-MODEL:
  - Lapsed-domain takeover of a parked source. A source parks precisely because its upstream is dead, and a dead domain
    can be re-registered; the amendment revives it automatically with no re-validation that the identifier still
    belongs to whoever the operator originally approved. Still unaddressed in the remediated text. Noted rather than
    filed because v1 re-validates source ownership on NO path (a live source that changes hands has the same exposure)
    and ingested content still passes Stage 1/2 — the delta this amendment introduces is the loss of a human
    checkpoint, not a new class of attack. Worth an explicit operator decision if "an admin looked at it before it came
    back" is considered part of the source-approval story.

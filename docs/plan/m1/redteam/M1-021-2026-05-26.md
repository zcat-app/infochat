RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: AUDIT-EVASION
    SEVERITY: high
    PROMISE: "any code with INSERT on audit_log can mint rows attributing arbitrary actions to arbitrary actors" (Finding 5 this diff claims to fix); spec §Authorization model step 8: "Audit-log the intent"; the combined promise is that audit rows faithfully attribute actions to the correct actor.
    GAP: V24__identity_audit_remediation.sql:98-108 — trg_audit_log_actor_check guards actor consistency only when current_setting('infochat.actor_id', TRUE) is non-NULL and non-empty. No application-layer Java code in the codebase ever executes SET LOCAL infochat.actor_id before writing audit rows. The AuditLogWriter performs direct INSERT without setting the GUC. Consequently, every audit INSERT in production takes the GUC-unset path and the trigger's actor-consistency check is bypassed.
    REPRO: (1) SQL injection in any Provider-side code with INSERT on audit_log crafts INSERT INTO audit_log (actor_user_id, action, ...) VALUES ('<victim-admin-uuid>', 'BAN', ...). (2) The trigger reads current_setting('infochat.actor_id', TRUE) which returns NULL (no application code sets it). (3) The trigger's IF v_actor IS NOT NULL check is false, so the INSERT succeeds. (4) The audit log now contains a forged row attributing a BAN action to an innocent admin, with no integrity check having fired.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

  - CATEGORY: PERM-ESCAL
    SEVERITY: high
    PROMISE: Spec §Authorization model: "cannot ban self" enforced at the trigger layer, not just the command layer, so a buggy command cannot bypass it.
    GAP: V24__identity_audit_remediation.sql:68-76 — trg_last_admin_protection_update reads current_setting('infochat.actor_id', TRUE) for the ban-self check. No application-layer Java code sets this GUC before UPDATE operations on the users table. The trigger's IF v_actor IS NOT NULL AND v_actor <> '' guard evaluates to false, so the ban-self check is skipped entirely. The application-layer self-ban guard is the sole defense; a bug in that check or a direct SQL path from any other handler that sets is_banned = TRUE would not be caught at the trigger layer.
    REPRO: (1) An admin issues /ban targeting themselves. (2) Suppose the BanCommandHandler's application-layer self-ban check has a bug. (3) The UPDATE reaches the trigger. (4) The trigger reads infochat.actor_id = NULL (never set). (5) The IF v_actor IS NOT NULL check is false; the ban-self prevention is skipped. (6) The admin has banned themselves, violating the spec invariant.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

  - CATEGORY: PERM-ESCAL
    SEVERITY: medium
    PROMISE: Spec §DB roles: "The Provider role has EXECUTE on these procedures, never SELECT on the underlying raw-original quarantine column"; spec §Quarantine workflow: "approve and reject run as stored procedures that internally read the original under the procedure's elevated rights."
    GAP: V21__quarantine_admin.sql:24-77 (approve_quarantine) and V21__quarantine_admin.sql:83-115 (reject_quarantine) are both SECURITY DEFINER without SET search_path = pg_catalog, public. This is the identical vulnerability class that V24 fixes for delete_preban_user (Finding 4). The ticket's out-of-scope note incorrectly states "those procedures don't exist yet" — V21 was committed on 2026-05-25 (M1-081a), before M1-021 was implemented. A Provider-role session that manipulates search_path before calling these procedures can shadow the quarantine, post, or audit_log tables.
    REPRO: (1) SQL injection via the Provider role. (2) SET search_path = attack_schema, public; CREATE TABLE attack_schema.audit_log (...); then SELECT approve_quarantine(...). (3) The procedure runs as the migration superuser (SECURITY DEFINER) without a pinned search_path. (4) The procedure's INSERT INTO audit_log resolves to attack_schema.audit_log — the real audit row is never written.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

  - CATEGORY: PERM-ESCAL
    SEVERITY: medium
    PROMISE: Spec §Quarantine workflow: "Admins review via /quarantine list and /quarantine approve|reject"; spec §Authorization model: "Permission checks run in deterministic Java."
    GAP: V21__quarantine_admin.sql:24 (approve_quarantine) and V21__quarantine_admin.sql:83 (reject_quarantine) accept a p_actor_id parameter but never verify that the actor exists or is an admin. This is the identical vulnerability class that V24 fixes for delete_preban_user (Findings 1+3). Any caller with EXECUTE privilege (the Provider role) can pass an arbitrary UUID as the actor.
    REPRO: (1) SQL injection via the Provider role. (2) SELECT approve_quarantine('<quarantine-id>', '<non-admin-user-id>'). (3) The procedure performs the quarantine approval attributed to a non-admin user, bypassing the admin authorization requirement. (4) A quarantined post is restored to READY status.
    SUGGESTED-FIX-CLASS: missing-auth-check

OUT-OF-MODEL:
  - The audit_log_id_seq USAGE/SELECT grants to both service roles allow either service to probe the sequence value and infer the total number of audit rows ever written. The ticket and prior redteam acknowledge this is outside the documented threat model.
  - The tests connect as the container's bootstrap superuser, not as the application roles (infochat_provider / infochat_collector). A test that connects as the Provider role and attempts the search_path shadow attack would be a stronger validation. This is a test-hardening opportunity, not a production vulnerability.

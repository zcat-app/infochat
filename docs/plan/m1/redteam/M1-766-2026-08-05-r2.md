OUT-OF-MODEL:
  - Zero-width-only anchor can drop the whole headline block on the match
    path (new behaviour introduced BY the round-1 fix, not by the feature).
    `DisplayHeadline.derive` (DisplayHeadline.java:299-321) guards the
    anchor with `anchor.isBlank()`, which uses `Character.isWhitespace` and
    therefore does NOT catch an anchor made only of zero-width codepoints
    (U+200B/C/D, U+FEFF) — those are non-blank, survive `flattenToOneLine`'s
    `strip()`, and are stripped only later, inside
    `LlmOutputSanitizerCore.canonicalizeForMatching`. On the no-match path
    the sanitizer returns the caller's ORIGINAL bytes, so nothing changes.
    But when a closed-list token appears anywhere ELSE in the pair (e.g. in
    the publisher's own title), the canonical form IS returned, the anchor
    portion canonicalizes to the empty string, `sanitized.split("\n", 2)`
    yields `lines[0] == ""`, and the record is built as
    `AnchoredHeadline("", <original>, true)` — whose `isEmpty()` keys off
    `readerLine` alone (DisplayHeadline.java:207-209), so every caller
    (DegradedDigestRenderer.java:101, SummaryProseGenerator.java:253,
    ClusterBlockRenderer, SavedCommandHandler) drops the primary AND the
    surviving original together. Reachability needs a translator-authored
    anchor of only zero-width bytes, which `IngestTranslationWorker`'s
    "non-empty translated title" test admits and which trust-boundary item 9
    (hostile/coaxed endpoint) puts in scope. Not filed as a FINDING: the
    suppression reaches only that one post's own headline (never another
    publisher's — the unit is still one post), the post still renders with
    its source name / url / uid, no unredacted token is delivered, and the
    `LLM_OUTPUT_SANITIZED` row still fires with the exact count. No
    security.md clause commits to per-post headline availability, so this
    is a robustness gap rather than a threat-model violation — but it is a
    new failure mode the pair-join created, and a `lines[0].isEmpty()` fold
    into the existing collapse branch would close it.
  - The `--name` flag reject is going-forward only, while the spec sentence
    it leans on reads as total. `SourceUpsertService.containsFlagToken`
    (SourceUpsertService.java:443-450) sits at the write boundary and the
    ticket states the residual explicitly, but security.md §"LLM output
    sanitizer" justifies the write-boundary-alone posture with "constraining
    the single produced value covers every surface that later renders it" —
    which is a property of values produced AFTER the guard exists. Any
    `source.display_name` already stored with a `--x` token (added before
    this change, on a deployment with data) keeps rendering unsanitized
    beside a sanitized headline. Noted for the user to decide whether a
    one-shot re-validation of stored display names is owed alongside the
    guard.
  - The PRESENTATION translation is a third derivation the widened "pair"
    wording does not name. On `ClusterBlockRenderer` and
    `SavedCommandHandler` the primary line is handed to the display-hit
    leg and its reply is sanitized by itself via
    `DisplayHeadline.prepareTranslatedHeadline` (DisplayHeadline.java:538-541),
    a separate call from the pair call in `derive`. So a command word
    introduced by the presentation translator, plus a flag in the bracketed
    original delivered directly beneath it, share no sanitize input and
    neither redacts. This is PRE-EXISTING (both files are untouched by this
    diff) and it is arguably already scoped out: security.md now says the
    guarantee holds "within one author's field (or its pair)" and that a
    flag entry "redacts only when its command word and flag appear in the
    same field or its translation", where "its translation" is the INGEST
    anchor. Flagged only because the spec paragraph this diff rewrote is the
    natural place a reader would expect the display-hit derivation to be
    named or excluded, and it is neither.

VERIFICATION OF THE TWO ROUND-1 FINDINGS (both genuinely CLOSED — recorded
here so the pass is auditable, not as findings):

  - Round-1 finding 1 (pair straddle) — CLOSED. `derive`
    (DisplayHeadline.java:299-321) now issues ONE
    `LlmOutputSanitizer.sanitize` over
    `flattenToOneLine(boundForScan(anchor)) + '\n' +
     flattenToOneLine(boundForScan(original))`, anchor first, which is the
    same direction the block is delivered in on every caller
    (`anchorBlock`/`primaryFor`+`subordinateFor` always put the primary
    above the original, and the primary is never the original when the
    anchor is used). Attacks tried and failed:
      * Forging the separator from feed bytes: `flattenToOneLine`
        (DisplayHeadline.java:564-566) collapses `(?:\R|\s)+` — which covers
        \n, \r, \f, \x0B, \t, space, U+0085, U+2028, U+2029 — to one space
        and strips the ends, so neither operand can carry a `\n` into the
        join.
      * Manufacturing a SECOND newline inside the sanitizer, which would
        desynchronise the split: NFKC never emits U+000A;
        `stripBidiAndZeroWidth` only deletes; `breakLinkAdjacency` inserts a
        space; `REDACTED_COMMAND_REPLACEMENT` carries none; and
        `MARKDOWN_LINK` (`\[([^\]]+)\]\(([^)]+)\)`) is newline-preserving —
        its label and target groups both match `\n` but the replacement
        re-emits group(1) and group(2) verbatim, and the only characters it
        deletes are `[`, `]`, `(`. Output therefore carries 0 or 1 `\n`, so
        `split("\n", 2)` cannot return 3 parts or mis-pair the lines.
      * Losing the separator: it can only be consumed by a redaction span
        that crosses it (`redactFlagEntry`, and the `\s+` in a multi-word
        regex entry such as `/invite create`). That is the documented
        collapse branch (DisplayHeadline.java:313-319), which reports the
        pair UNANCHORED with both slots equal so `subordinateFor` suppresses
        the duplicate — fail-safe, no half-deleted line, no dangling
        bracket.
      * Reaching bytes it should not: the sanitize input is exactly the two
        operands of ONE post's ONE chosen field, so the flag-span deletion
        cannot touch another post or another author. Pinned by
        `render_keepsTheUnitAtONEPostSoOneTitleCannotEraseAnother` and
        `degradedProseKeepsTheUnitAtOnePostSoOneTitleCannotEraseAnother`.
      * Audit coverage: one call instead of two aggregates per distinct
        token per call and carries the exact occurrence count, so the
        `LLM_OUTPUT_SANITIZED` signal is lossless
        (LlmOutputSanitizer.java:236-289).
      * The round-1 tests that PINNED the gap as intended behaviour are
        gone, replaced by tests asserting redaction
        (DegradedDigestRendererTest.render_redactsAClosedListEntry...,
        SummaryProseGeneratorTest.degradedProseRedacts...,
        DisplayHeadlineTest.anchorFirstRedactsAClosedListEntryStraddlingThePair
        and .feedTextCannotForgeTheSeparatorThatJoinsThePair). No
        pre-existing security assertion was deleted, weakened or retargeted.

  - Round-1 finding 2 (`--name` supplies the flag half) — CLOSED.
    `containsFlagToken` (SourceUpsertService.java:443-450) is applied at the
    same write boundary as `containsSlash`, and critically it runs on
    `stripped` — the value AFTER `Normalizer.normalize(..., NFKC)` and
    `IngestTextNormalizer.stripMetadataField` (SourceUpsertService.java:397-405)
    — which is also the exact value that gets stored. Representation
    bypasses attempted and all closed: fullwidth `－－all` (U+FF0D folds to
    `-` under NFKC), NBSP / U+2000-200A / U+202F / U+205F / U+3000 as the
    token separator (all fold to U+0020, so `split("\\s+")` splits there),
    `-<ZWSP>-all` and bidi-wrapped hyphens (stripped by
    `stripMetadataField`), tab/control-separated forms (ISO controls
    stripped, so the token merges into the preceding word and no longer
    starts with `--`). The residues that DO survive the guard — U+1680 as a
    separator, U+2010/U+2011/U+2212 as the hyphens — survive intake
    normalization identically and are therefore invisible to
    `ListSourcesArgs.parse`'s own `split("\\s+")` / exact `--all`
    comparison, so they do not dispatch either: the guard and the parser
    read the same canonical form with the same tokenizer, which is the
    right symmetry. Punctuation-wrapped forms (`(--all)`) are not caught but
    are not dispatchable either. Over-rejection is bounded to tokens opening
    with two ASCII hyphens and degrades to the host-derived name; the em-dash
    case is pinned by `ordinaryNameWithAnEmDashIsStillReflected`.
    `SourceUpsertService.defaultDisplayName` is the single producer of the
    stored value and `AddSourceCommandHandler:216-217` is its only caller,
    so there is no second write path around the guard.

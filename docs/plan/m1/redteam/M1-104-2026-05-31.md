disposition: |
  Two findings against the SimpleX group-message codec's memberId fallback
  (SimpleXMessageCodec.java:117-125). Both have the same root cause: when
  simplex-chat surfaces a group sender without `memberContactId` (a normal-
  operation path for members not yet bidirectionally contact-established),
  the codec falls back to `memberId` as the Identity contactId. memberId is
  a per-group identifier, not a cryptographically-anchored account id, which
  (1) lets a globally-banned user evade the ban check by appearing in a
  group via memberId only (AUTH-BYPASS/high), and (2) collides across
  distinct (user, group) pairs because memberId is a per-group counter
  (PERM-ESCAL/medium — cross-user state leak via shared `(adapter,
  contact_id)` join key).

  FIXED IN-BRANCH (2026-05-31) at user direction: rather than route through
  a new remediation ticket, the fix lands as a second commit on the M1-104
  branch BEFORE the squash-merge to main, so the merged commit on main
  presents the trust-boundary-tight code only. The fix removes the memberId
  fallback entirely (chosen Option A from the disposition above) and adds a
  regression test `memberIdOnlyGroupFrame_dropped` in
  SimpleXGroupHandlerTest that asserts a group frame missing
  `memberContactId` decodes as Ignored("newChatItem-group-without-sender")
  and is never delivered to the handler. The javadoc bullet on the
  group-frame conventions is updated to document the rejection contract.
  Functional impact: pre-contact group members (who simplex-chat surfaces
  without a memberContactId) are silently ignored at the adapter boundary
  rather than delivered with a non-cryptographic identifier; the trade-off
  preserves the D10 trust anchor at the cost of group-message
  responsiveness to such members until they DM-establish contact.
  Verified: SimpleXGroupHandlerTest grew 6→7 tests, all green;
  `mvn -B clean verify` exit 0 (log: target/m1-tick-test-M1-104-rfix.log).

  Two OUT-OF-MODEL observations recorded (cross-encoding mention collision
  + log-injection via chatType); neither is reachable in v1.

RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: AUTH-BYPASS
    SEVERITY: high
    PROMISE: "The adapter asserts identity via a stable, cryptographically anchored ID. Display names are informational and never used for authorization (decision D10)." (§Trust boundaries 1) — paired with "Banned-user check is the first thing after identity resolution" and "Banned user receives one fixed reply per inbound message" (§User ban).
    GAP: infochat-messaging-adapter/src/main/java/app/zcat/infochat/messaging/impl/simplex/SimpleXMessageCodec.java:411-419 (sender fallback: `senderContactId = optText(groupMember, "memberId")` when `memberContactId` is absent), surfaced into `Identity.contactId` via SimpleXGroupHandler.java:77 (`new Identity(gc.senderContactId(), ...)`). The codec's own comment on lines 413-418 calls out that simplex-chat surfaces only `memberId` for "members whose contact has not yet been established bidirectionally" — i.e., a normal-operation path. `memberId` is a per-group identifier, not a cryptographic contact id, so it is neither a stable account anchor (the same user has different memberId values across different groups) nor a reliable cross-message join key. Provider's ban check uses `(adapter, contact_id)` as the join key, so a user banned by their real queue-address `contactId` who later sends a group message that surfaces only via `memberId` produces a `contact_id` value that does not match the banned row.
    REPRO: 1) Bot admin bans Alice by her real SimpleX queue address (`/ban alice-queue-addr`). The `users` row carries `is_banned=true` for `(adapter=simplex, contact_id='alice-queue-addr')`. 2) Alice joins an approved group with the bot, but Alice has never DM-established a bidirectional contact with the bot. 3) Alice posts in the group with an `@bot` mention. The simplex-chat build surfaces the message with `chatItem.chatDir.groupMember.memberContactId` absent (because contact-direction isn't established) and only `memberId='group-7-member-3'` populated. 4) The codec falls back to `memberId`, builds `GroupCandidate.senderContactId='group-7-member-3'`. 5) SimpleXGroupHandler delivers `InboundMessage` whose `sender.contactId='group-7-member-3'`. 6) Provider's authorization step 4 looks up `users WHERE adapter='simplex' AND contact_id='group-7-member-3'` — no match. The ban is bypassed; the message reaches step 6 (parse) and beyond as if Alice were an unknown contact (which then short-circuits silent-drop per step 3 since unknown contacts in groups are invisible — but if Alice ever gets a row created under that memberId via any path, she has a clean second identity that the global ban does not track).
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

  - CATEGORY: PERM-ESCAL
    SEVERITY: medium
    PROMISE: "Per-adapter trust level: the adapter asserts identity via a stable, cryptographically anchored ID" (§Trust boundaries 1) and the per-(user, scope) isolation invariant (CLAUDE.md "Per-(user, scope) isolation for state, memory, saves. Never leak across users").
    GAP: infochat-messaging-adapter/src/main/java/app/zcat/infochat/messaging/impl/simplex/SimpleXMessageCodec.java:411-419. The same memberId fallback above also breaks per-user isolation in the other direction: two distinct users in two distinct groups can independently surface with the same `memberId` (memberId is a per-group counter in simplex-chat, not a global identifier), so the codec can assign the same `senderContactId` to two different real users. Provider then routes both into the same `(adapter, contact_id)` row — sharing chat memory, saves, follow-tag preferences, and probation state across users. Conversely, the same real user appearing across two groups with no established contact gets two different `senderContactId` values, fragmenting their state.
    REPRO: 1) Alice joins group G1; simplex-chat surfaces her without `memberContactId` and assigns `memberId='m-1'`. 2) Bob joins group G2; simplex-chat independently surfaces Bob without `memberContactId` and assigns `memberId='m-1'` (the counter is per-group, so collisions across groups are routine). 3) Alice @mentions the bot in G1; Provider creates/finds a row keyed `(simplex, 'm-1')` for Alice. 4) Bob @mentions the bot in G2; Provider finds the same `(simplex, 'm-1')` row, treats Bob's message as Alice's, applies Alice's probation state, writes Bob's group activity into Alice's audit footprint.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

OUT-OF-MODEL:
  - Mention-parser cross-encoding collision (an attacker-controlled queue address that base64-decodes to the same bytes as the bot's queue-address literal) is theoretically possible against a short non-base64 bot address but not exploitable against realistic SimpleX cryptographic queue addresses, where the attacker cannot choose the decoded bytes of their own contact id (the protocol assigns it).
  - Log-injection via attacker-controlled `chatType` field landing in DEBUG `Ignored` reason strings — only reachable when production lowers SimpleX logger below the baseline; out-of-model per "production logger-level baseline MUST keep these categories at WARN or above."

RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: PERM-ESCAL
    SEVERITY: medium
    PROMISE: "Authorization → execution. Permission checks run in deterministic Java." (§Trust boundaries §3) + "**Last-admin protection (bot admin only).** ... Enforced at the trigger layer, not just the command layer, so a buggy command cannot bypass it." (§Authorization model). The handler-layer admin check is the spec's deterministic-Java permission gate; the trigger only enforces the last-admin floor, not the general "actor must still be admin at execution time" property.
    GAP: GrantAdminCommandHandler reads the actor row via lookupUser() at infochat-provider/src/main/java/app/zcat/infochat/provider/command/GrantAdminCommandHandler.java line 113 (outside any transaction; each lookupUser opens its own short-lived Connection per lines 209-228). The executeGrant transaction (line 167) wraps only the audit INSERT + UPDATE on the target; the actor row is never re-read and never row-locked. RevokeAdminCommandHandler has the identical shape (file infochat-provider/src/main/java/app/zcat/infochat/provider/command/RevokeAdminCommandHandler.java lines 121-127 for the admin gate, lines 170-189 for the unlocked executeRevoke transaction). The repo's VouchCommandHandler precedent (M1-045 redteam-fix round 2) closed this exact TOCTOU with a `SELECT id, is_admin FROM users WHERE ... FOR UPDATE` on the actor row INSIDE the transaction so concurrent /revoke-admin against the actor serializes on the row lock. The new handlers do not adopt this pattern. The V5 trg_last_admin_protection_update trigger only checks the post-update count of qualifying admins, not the actor's current admin state, so it does not close this gap.
    REPRO: Admin A and admin B are both online. B sends /revoke-admin A at T0. A — racing the demote — sends /grant-admin <accomplice> at T0+ε. A's handler executes lookupUser(adapter, A.contactId) and reads is_admin=true (no row lock). B's executeRevoke transaction commits, flipping A.is_admin=false. A's executeGrant transaction then commits, flipping accomplice.is_admin=true. The trigger does not fire because B remains is_admin=true. A is now demoted but successfully promoted an accomplice AFTER their own demotion landed in the DB. The same shape applies to A issuing /revoke-admin <co-admin>: A revokes co-admin after being demoted, leaving the deployment with one fewer admin than the audit log's "B revoked A" + "A revoked co-admin" sequence implies was intended. Both surfaces defeat the spec's deterministic-Java permission gate by letting a stale "is_admin=true" snapshot drive a mutation the actor's current state forbids.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

OUT-OF-MODEL:
  - The handler's admin gate accepts `actor.is_admin=true` regardless of `actor.is_banned`. In normal operation the intake-side step-4 ban check blocks banned users before any handler, so a banned admin cannot reach the handler. The M1-039 in-handler-ban defense-in-depth precedent is NOT applied here (the handlers add only a probation defense-in-depth check, not a ban defense-in-depth check). Currently unreachable per intake-side gate, but inconsistent with the established repo pattern.
  - parseTargetContact() does not run the chat-input fenced-code carve-out — it just trims and splits on whitespace. A homoglyph/zero-width-formatted contact id in the body is normalized at intake step 1.7 to its semantic form before reaching the handler, so this is benign in practice; documented here only because the handler reads the body again rather than a pre-parsed token.

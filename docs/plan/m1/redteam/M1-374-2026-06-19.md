RED-TEAM VERDICT: CLEAN

Audit summary (not part of the parsed verdict — the line above is the verdict):

Scope of the diff: M1-374 reworks the *test-only* loopback carve-out for the
SSRF IP blocklist. The security-relevant production change is confined to
infochat-ssrf/src/main/java/app/zcat/infochat/ssrf/IpBlocklist.java; everything
else is test-source conversion (deleting ~18 `extends IpBlocklist` doubles and
repointing construction sites to a shared `LoopbackPermittingBlocklist.create()`
factory in ssrf TEST sources, exported via a Maven test-jar) plus three pom
test-jar wirings and STATUS/ticket bookkeeping.

Threat-model commitment audited (security.md §SSRF and outbound connections):
"DNS-resolved IPs are checked against a blocklist of private, loopback,
link-local, multicast, CGNAT, and cloud-metadata ranges ... plus the host's own
non-loopback interfaces" and "The allowlist is not user-configurable."

Why the diff still delivers it (each falsifier checked against the file, not
just the diff hunk):

1. Carve-out cannot reach production. The `permitLoopback=true` path is
   reachable ONLY through the package-private `IpBlocklist(boolean, Supplier)`
   constructor (IpBlocklist.java:141). Both production constructors — the public
   no-arg (line 115) and the M1-026 package-private Supplier overload (line 126)
   — delegate with `false`. The sole caller of the boolean constructor is
   `LoopbackPermittingBlocklist.create()` (LoopbackPermittingBlocklist.java:1456),
   which lives in ssrf TEST sources and is pulled into the collector/provider
   modules only via a `<type>test-jar</type> <scope>test</scope>` dependency
   (infochat-collector/pom.xml:996-1002, infochat-provider/pom.xml:996-1002), so
   it is on no production classpath. No `src/main` tree contains a call to the
   boolean constructor. This is strictly STRONGER than the prior convention-only
   guard (don't subclass): the class is now `final` and `isBlockedAgainst` is now
   `private`, so the former protected-override seam is closed.

2. Even the test carve-out is scoped to loopback only. The branch is
   `if (permitLoopback && addr.isLoopbackAddress()) return false;`
   (IpBlocklist.java:197). `isLoopbackAddress()` matches 127.0.0.0/8 and ::1
   only — it does NOT match 169.254.169.254, 0.0.0.0 (anyLocal), CGNAT, RFC1918,
   IMDS, or any other blocked range, all of which still fall through to the
   unchanged `isBlockedV4`/`isBlockedV6` logic. The carve-out is byte-for-byte
   equivalent to the deleted subclasses (permit loopback first, then defer to the
   strict range check). No additional range is re-opened.

3. No test weakening. The strict-mode / SSRF-rejection tests still construct the
   blocklist via the no-arg `new IpBlocklist()` strict constructor (e.g.
   UrlProbeTest swaps in the strict production blocklist for its rejection assert,
   per the retained class comment). The `firstBlocked` batch path and per-call
   host-interface re-enumeration (TOCTOU/DNS-rebind defense) are untouched.

4. Out-of-model build risk only: the noted Quarkus split-package / test-indexing
   concern for the shared factory is a build-correctness matter gated by `mvn
   verify`, not a threat-model commitment; if it failed it would break tests, not
   widen the SSRF surface.

No gap between the documented threat model and the delivered behavior was found.

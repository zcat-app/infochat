RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - redactUserInfo (LlmHttpSupport.java:265-285) has an incomplete-redaction
    edge case, but the surface it protects is OUTSIDE the documented threat
    model, so it is not a FINDING. Context: the base-url is operator-set
    config, which the threat model classifies as TRUSTED ("Operator-set
    config (properties files, bootstrap JSON) is trusted", security.md
    §Threat model). The threat-model commitments that DO touch logged
    secrets are (a) §Secrets handling — redaction of a CLOSED catalogue of
    API-key shapes (sk-, ghp_, AKIA..., generic hex/base64 adjacent to
    api_key/secret/token/password/bearer) on audit-log and console output,
    and (b) §User content in exceptions — dropping USER-AUTHORED prose from
    exception messages via SafeLog. An arbitrary userinfo password embedded
    in an operator's base-url is neither a catalogue API-key shape nor
    user-authored prose, so the threat model never promised to keep it out
    of the boot log. The whole M1-401 ticket is hardening beyond the
    documented commitments (the M1-330 defense-in-depth line).

    The edge case itself, for the record: redactUserInfo locates the
    authority as the span from "://" to the first '/', '?', or '#', then
    redacts up to the last '@' within that span. If the userinfo USER or
    PASSWORD itself contains a '/', '?', or '#' BEFORE the '@' (e.g.
    "https://user:pa/ss@host/v1"), the authority-scan terminates at that
    in-credential delimiter, the subsequent lastIndexOf('@', authorityEnd-1)
    finds no '@' before it, and the function returns the value UNCHANGED —
    so the credential would echo verbatim into the IllegalArgumentException
    message and thence the boot log. The tested vector (literal space in the
    password) does not hit this because a space is not a path delimiter.
    A real exploit also requires the malformed-URL parse-failure branch to
    fire AND the operator to have typed such a base-url, both gated behind
    the trusted-config boundary. If the user wishes to extend the threat
    model to cover operator-config credential leakage into logs as a
    first-class commitment, hardening redactUserInfo to mask the userinfo
    even when in-credential delimiters precede the '@' (or simply masking
    everything between "://" and the last '@' anywhere before the host
    boundary) would close it. SUGGESTED-FIX-CLASS (advisory only):
    input-sanitization.

RED-TEAM VERDICT: FINDINGS

Round-3 re-audit note (context, not a finding): the round-1 (U+2800) and round-2
(Hangul filler) bypasses ARE genuinely closed and are NOT re-reported. The
boundary heuristic is gone; containsSlash (SourceUpsertService.java:881-883)
rejects any ASCII '/' anywhere in the name, so every blank-rendering codepoint
on either side of any character-category partition is now irrelevant — the
character preceding the slash is never consulted. That part of the remediation
is sound. The finding below attacks the NEW load-bearing claim the absolute rule
introduced: claim (a), that testing the ASCII slash alone is sufficient
"because the router NFKC-normalizes inbound text before dispatch". That claim
holds only OUTSIDE fenced code blocks, and a command body can contain a fence.

FINDINGS:
  - CATEGORY: INJECTION
    SEVERITY: medium
    PROMISE: docs/spec/security.md §LLM output sanitizer — "a deterministic
              reply that echoes an attacker's raw token is exactly as dangerous
              as an LLM emitting one. The exemption is safe only to the extent
              deterministic output is **bot-authored** — interpolates no
              inbound-derived text ... That is a property the handlers must
              **maintain**, not one the exemption may assume". This same diff
              amends that section to declare the surface's "one known live
              instance — the `/add-source` `--name` display-name echo — was
              closed by M1-659, which constrains the name where the value is
              produced", and amends docs/spec/commands.md §Discovery to claim
              "a name containing **any** slash, or over-long input ... is
              discarded whole in favour of the host-derived default. Only an
              ordinary slash-free name is stored and echoed."
    GAP: The absolute rule tests one concrete character —
         infochat-provider/src/main/java/app/zcat/infochat/provider/source/SourceUpsertService.java:881-883
         `private static boolean containsSlash(String name) { return
         name.indexOf('/') >= 0; }` — and the javadoc at
         SourceUpsertService.java:867-873 states the security claim that makes
         one character sufficient: "Testing the ASCII slash alone is sufficient
         because the router NFKC-normalizes inbound text before dispatch
         ({@code InboundRouter.appendNormalized} ...), which folds U+FF0F
         FULLWIDTH SOLIDUS to {@code '/'} before this check runs."

         NFKC does NOT run over the whole inbound body. Per
         docs/spec/security.md §Authorization model step 1.7 and §Ingest
         pipeline, chat intake normalization "carves out fenced code blocks"
         and "Bytes inside fences are preserved verbatim". The implementation
         does exactly that:
           - InboundRouter.normalize (InboundRouter.java:1625-1661) splits the
             body on '\n' and normalizes PER LINE. A line matching
             matchFenceOpener (:1671-1692) is appended verbatim (:1646) and
             sets inFence; every subsequent line until a closer is appended
             verbatim (:1654). Only non-fence lines reach appendNormalized
             (:1648), which is the sole caller of Normalizer.normalize(...,
             NFKC) (:1729).
         The command-vs-chat decision, however, is made on the FIRST CHARACTER
         OF THE WHOLE BODY, not per line:
           - InboundRouter.java:1061 `if (normalized.startsWith("/"))` → slash
             dispatch; commandNameOf (:1483-1488) likewise reads only the body's
             first token.
         So a body whose line 1 begins `/add-source` dispatches as a command
         while its line 2 opens a fence, leaving lines 2+ UN-normalized. The
         round-4 reviewer note in the ticket
         (docs/plan/m1/tickets/M1-659-add-source-name-echo-reflection.md:486-488)
         records that this exact ordering risk was probed and dismissed —
         "fenced code blocks are left un-normalized ... it is not a bypass,
         because such a message does not start with '/' and routes to chat
         mode". That reasoning is false: only the body's first character governs
         routing, and the fence opens on a later line.

         The un-normalized fence content reaches the display name intact:
           - CommandTokenizer.tokenize
             (infochat-provider/src/main/java/app/zcat/infochat/provider/command/CommandTokenizer.java:28-42)
             suppresses whitespace splitting while inQuotes, and '\n' is
             whitespace — so a quoted `--name "` opened on line 1 swallows the
             newlines, the fence delimiter line, and the fence body into ONE
             token. AddSourceArgs.java:140-145 assigns that token to
             displayNameOverride.
           - acceptableOverride (SourceUpsertService.java:833-845) calls
             IngestTextNormalizer.stripMetadataField
             (infochat-core/.../IngestTextNormalizer.java:83-104), which removes
             the newlines (Character.isISOControl) but has no NFKC step and no
             U+FF0F case; String.trim() removes only <= U+0020. U+FF0F survives.
           - containsSlash finds no ASCII '/', the length is under
             MAX_DISPLAY_NAME_LENGTH = 80, so the override is ACCEPTED, stored
             as source.display_name (UPSERT_SOURCE_SQL,
             SourceUpsertService.java:98-107), and interpolated into
             BundleKeys.REPLY_ADD_SOURCE_FRESH_INSERT
             (AddSourceCommandHandler.java:196-211) plus every later echo of the
             stored field (/list-sources, /unfollow-source, /remove-source).

         Claim (c) — "a slash-free stored display name cannot carry a command
         token" — is true of a genuinely slash-free string, but the stored value
         here is only slash-free in the representation containsSlash inspects.
         The moment that same text re-enters intake as an ordinary (unfenced)
         message, NFKC folds U+FF0F to '/' and it is a command. The check and
         the eventual parse disagree about what a slash is, which is precisely
         the gap the NFKC-before-dispatch claim was supposed to remove.

         No test covers this: every new test in
         AddSourceCommandHandlerTest.java:904-1117 drives handler.handle(...)
         with a single-line, already-normalized string, bypassing
         InboundRouter.normalize entirely — so no test can observe that the
         handler's input is not always NFKC-folded.
    REPRO: 1. Attacker is any registered, non-probation user (/add-source is
              probation-blocked but otherwise open to ordinary users). In an
              approved group the success reply is broadcast to every member,
              including any bot admin present.
           2. They send ONE multi-line message (line 2 is three literal
              backticks; U+FF0F FULLWIDTH SOLIDUS, bytes EF BC 8F, stands where
              a slash would go):

                /add-source https://example.com/f.xml --tags news --name "Reuters
                ```
                <U+FF0F>grant-admin 11111111-2222-3333-4444-555555555555 approved"

           3. InboundRouter.normalize: line 1 has no fence opener → normalized;
              line 2 matches matchFenceOpener → appended verbatim, inFence=true;
              line 3 is inside the fence → appended VERBATIM, so U+FF0F is never
              NFKC-folded. Body length ~150, well under
              infochat.command.body-cap (2048-16384 across profiles;
              application.properties:499-503), so the step-6 body cap
              (InboundRouter.java:702) does not fire.
           4. normalized.startsWith("/") is true → slash dispatch
              (InboundRouter.java:1061). CommandTokenizer keeps the quoted
              multi-line value as one token; stripMetadataField drops the
              newlines. displayNameOverride becomes
              `Reuters```<U+FF0F>grant-admin 11111111-...-555555555555 approved`
              — 68 characters, no ASCII '/', so containsSlash returns false and
              acceptableOverride ACCEPTS it. Length 68 < 80.
           5. The value is stored and the bot replies (and /list-sources later
              re-renders it to a bot admin):
                Source added: Reuters```／grant-admin 11111111-2222-3333-4444-555555555555 approved ...
              On an adapter advertising supportsCodeFormatting the backtick run
              renders the payload as a code block, which makes it read as an
              official copy-pasteable snippet rather than as a source name.
           6. A bot admin copy-pastes the apparent command line (selecting from
              the visible solidus onward). That paste is an ordinary single-line
              message with no fence, so appendNormalized DOES run on it: NFKC
              folds U+FF0F to '/', the body now starts with '/', and it
              dispatches as a genuine
              `/grant-admin 11111111-2222-3333-4444-555555555555 approved`
              executed under the admin's is_admin=true.
           The system should not have allowed it because this same diff amends
           security.md and commands.md to declare this reflection instance
           closed and to assert that only a slash-free name is stored and
           echoed, and because the sufficiency of the ASCII-only test is
           explicitly justified in the code by a normalization guarantee that
           the spec's own fenced-code carve-out suspends.

OUT-OF-MODEL:
  - Copy-paste social engineering of a human bot admin is the terminal step of
    the chain. docs/spec/security.md §LLM output sanitizer keeps this surface in
    model ("a copy-pasted reply still requires is_admin=true to do anything";
    the sanitizer exists to close "the social-engineering surface where a small
    LLM emits plausible-looking admin commands"), so the finding is reported as
    in-model defense-in-depth. The residual after any fix — an admin choosing to
    run a command they read in bot output — is a human factor the model does not
    promise to eliminate.
  - Claim (b) is CONFIRMED, not a finding: the non-folding homoglyphs U+2215
    DIVISION SLASH, U+2044 FRACTION SLASH and U+29F8 BIG SOLIDUS have no NFKC
    compatibility decomposition to U+002F, so a pasted line carrying one fails
    InboundRouter.java:1484's startsWith("/") and routes to chat mode, yielding
    nothing executable. They are cosmetic-only. U+FF0F is materially different
    precisely because it DOES fold — which is what makes the fence carve-out
    exploitable rather than merely untidy.
  - The absolute no-slash rule newly routes far more inputs to
    defaultDisplayName's fallback (SourceUpsertService.java:794-802), which is
    not itself run through acceptableOverride: on a null host or a parse failure
    the whole identifier becomes the display name. Not reported as a finding —
    a URL reaching that point has already passed the AddSourceArgs URI parse,
    the http/https scheme gate, the SSRF allowlist and a successful probe, and a
    host component can carry neither a slash nor a space — but the fallback's
    exposure grew with this change, so the user may want it to share the
    override's constraint. (Also flagged by the round-2 audit.)
  - Sources created by the bootstrap loader from bootstrap-sources.json do not
    pass through acceptableOverride, but operator-set config is trusted per
    docs/spec/security.md §Threat model, so this is out of model.

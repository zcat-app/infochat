RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: DOS
    SEVERITY: medium
    PROMISE: "Rate limiting... `/quarantine approve` — per-admin bucket." (security.md §Rate limiting)
    GAP: QuarantineCommandHandler.java:148-165 (`handleApprove`) calls the `approve_quarantine` stored procedure with no command-level rate limiting. The only rate limiting is the transport-level `RateCapBucket` at the `InboundRouter` level, which is a generic per-contact bucket shared across all commands and is not the command-specific per-admin bucket the spec requires.
    REPRO: A compromised bot-admin account (or an admin under social-engineering pressure) sends `/quarantine approve <id1>`, `/quarantine approve <id2>`, ..., `/quarantine approve <idN>` in rapid succession. Each call executes the stored procedure, which reads `original_html`, restores it into the post body, writes an audit row, and fires `NOTIFY new_post` -- all within a full Postgres transaction with row locks. Without a command-specific rate cap, an attacker can (a) mass-approve quarantine entries faster than the operator can react, restoring potentially malicious content; (b) drive transactional DB load via the `FOR UPDATE` lock + body replace + audit INSERT + NOTIFY per invocation, bounded only by the generic transport rate (default 60/min).
    SUGGESTED-FIX-CLASS: rate-limit

  - CATEGORY: AUDIT-EVASION
    SEVERITY: medium
    PROMISE: "Authorization evaluation order on every inbound message: ... 8. Audit-log the intent. 9. Execute." (security.md §Authorization model) and "Any new command added to the system goes through the same permission matrix and the same audit-before-effect rule." (commands.md §Permission model)
    GAP: AuditCommandHandler.java (entire file) and QuarantineCommandHandler.java:97-134 (`handleList`) perform privileged admin-only read operations without writing any audit row. The established codebase pattern audits admin-only reads: `ListSourcesCommandHandler.java:208-218` writes `LIST_SOURCES_ALL` for the privileged `/list-sources --all` read; `AuditAction.java:36-46` Javadoc explicitly describes this as closing "the gap... specifically the privileged-read enumeration." Neither `/audit` nor `/quarantine list` follows this pattern -- a bot admin can read the deployment-wide audit history and the quarantine review queue without leaving any trace in the audit log.
    REPRO: A compromised bot-admin issues `/audit --action BAN` to enumerate all ban events (learning which contacts were banned and by which admin), or `/quarantine list --all` to enumerate all quarantine entries (learning post UIDs, flagged content patterns, and rule IDs). No audit row records this reconnaissance. An operator performing a post-incident review of the audit log has no signal that the compromised admin account was used for read-side reconnaissance before an attack.
    SUGGESTED-FIX-CLASS: audit-log-coverage

  - CATEGORY: AUDIT-EVASION
    SEVERITY: low
    PROMISE: "Admins review via `/quarantine list` and `/quarantine approve|reject`. `/quarantine list` defaults to `PENDING` rows only; `BENIGN_CLOSED` rows are not surfaced unless `--all`." (security.md §Quarantine workflow) and the command signature `/quarantine list [-w ...] [--all] [--page N]` (commands.md §Admin)
    GAP: QuarantineCommandHandler.java:97-134 (`handleList`) hardcodes `page = 1` and `pageSize = 20` with no `--page` parsing. The BundleKeys header template (`REPLY_QUARANTINE_LIST_HEADER`) shows `page {1}/{2}` but the handler always returns page 1. When the quarantine queue exceeds 20 entries, entries beyond index 20 are invisible to the admin through the chat interface. This degrades the quarantine review workflow's effectiveness: an attacker who can produce a sustained flow of quarantine-triggering content can push earlier (potentially more dangerous) entries off the visible first page, causing them to be missed during admin triage. The `-w` (time window) flag specified in the command catalogue is also not implemented.
    REPRO: An adversary controlling a feed injects 25+ posts that trigger Stage 1 quarantine hits. The admin issues `/quarantine list` and sees only the 20 most recent entries (page 1 of 2). The 5 oldest quarantine entries -- which may include the adversary's initial, more carefully crafted injection attempts -- are hidden. The admin cannot issue `/quarantine list --page 2` to see them because the handler ignores `--page`. The admin must use `psql` to discover the hidden entries.
    SUGGESTED-FIX-CLASS: other

OUT-OF-MODEL:
  - The `lookupActor` method in both `AuditCommandHandler.java:185-212` and `QuarantineCommandHandler.java:229-247` swallows `SQLException` and returns `Optional.empty()`, which maps to `ERROR_ADMIN_ONLY`. While this is fail-closed (correct), a persistent DB failure would cause a legitimate admin to be locked out of quarantine review and audit access with no indication that the issue is a DB failure rather than a permissions problem. The `LOG.errorf` captures the exception but the admin-facing reply is indistinguishable from a real permissions denial.
  - The `mapStoredProcError` method at `QuarantineCommandHandler.java:213-227` uses fragile `contains("not found")` substring matching on `SQLException` messages. A different PostgreSQL error that coincidentally contains "not found" in its message would be misclassified as a quarantine-not-found error rather than surfacing as an internal error. This is mitigated by the DB being internal/trusted and the stored procedure message format being controlled, but it is a brittle coupling.

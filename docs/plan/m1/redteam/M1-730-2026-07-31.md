RED-TEAM VERDICT: CLEAN

REMEDIATION VERIFICATION (round-2 finding B, INFO-LEAK leg — the
VISIBILITY_INTERLOCK_SQL added to both listing SELECTs in
SavedCommandHandler.java:96-125). Attacked per the re-audit brief,
against the live file (not just the diff):

  - Count/rows split: CLOSED. The predicate is compiled into BOTH
    SELECT_COUNT_BASE_SQL (SavedCommandHandler.java:101-102) and
    SELECT_ROWS_BASE_SQL (:122-125) via the shared constant, so the
    header total cannot disagree with the rendered rows in the hiding
    direction. Test savedHidesSaveWhosePostIsQuarantined pins "1 of 1".
  - Tag/window filter path: CLOSED. appendFilters (:251-261) appends
    `AND personal_tags @> ?` / `AND saved_at > ?` AFTER the parenthesized
    interlock; the AND chain keeps the interlock conjunctive for every
    filter combination. No filter disables it.
  - Pagination: CLOSED. ORDER BY/LIMIT/OFFSET are appended after the
    WHERE (:237-238); a page boundary cannot resurrect a hidden row.
  - Operator precedence / NULL handling: CLOSED. The OR is fully
    parenthesized inside the AND chain. saved_post.post_uid is part of
    the PK (NOT NULL); if post.status were ever NULL the EXISTS(READY)
    branch fails and the row is hidden — the failure direction is
    fail-closed, never fail-open.
  - Second code path bypass: CLOSED for this surface. Grep over
    provider main shows exactly two saved_post listing SELECTs, both in
    this handler, both carrying the predicate. UnsaveCommandHandler is
    DELETE-only; ExportDataCollector exports to the owning caller only
    (D37 self-disclosure); ListSavesTool is a separate pre-existing
    surface — see OUT-OF-MODEL.
  - Post CONTENT columns crossing the predicate: CLOSED. Both probes
    are `SELECT 1` correlated on uid only; the reply renders snapshot
    columns exclusively (SELECT list at :122-125). Test asserts the
    seeded post's title never appears.
  - Multi-window "any READY window" rule vs other surfaces: CONSISTENT.
    Verified the actual read paths: GetPostTool.java:62-65
    (`WHERE p.uid = ? AND p.status = 'READY'` + world — any READY
    window resolves), RetryCommandHandler.java:93 (`p.uid = ANY(?) AND
    p.status = 'READY'`), EligiblePostQuery.java:225/344,
    SearchPostsTool.java:149, SemanticSearchTool.java:167/182 — all are
    bare `status = 'READY'` predicates with no latest-window qualifier,
    so a uid with one QUARANTINED and one READY window is visible on
    every one of them, exactly as the interlock decides. getPost adds
    the D59 world predicate /saved deliberately lacks, but that is the
    documented D13 per-user-global carve-out, disclosed in the reply
    header, and it can only ever re-show the saver's own snapshot.
  - Hiding rows a legit user should see: consistent, not a gap. A save
    whose post sits in RAW/NEEDS_REVIEW is now hidden, but those
    statuses are invisible on every other surface too, and the bookmark
    reappears on any READY transition (pinned by
    savedReappearsWhenHiddenPostReturnsToReady). Nothing is destroyed.
  - Round-1 finding A (DOS, audit-INSERT leg): NOT re-reported per the
    brief — accepted as M1-737. The new predicate only shrinks the set
    of rows reaching the sanitizer; it does not widen the 2000-char
    unit, the 20-row page, or the bucket. Not materially worse.

No new findings on the diff's other surfaces: the `left(body,
BODY_SCAN_LIMIT)` bound remains headline-invisible (r2's four-mode
verification stands and the new test pins it with an emoji-bearing
body); the constant is a compile-time int with no inbound-derived

DisplayHeadline (title XOR body), tags keep their own call, and the
new no-headline template sanitizes its tag token the same way.

OUT-OF-MODEL:
  - Aged-out-QUARANTINED revival. PartitionPruner drops post partitions
    wholesale on the retention horizon with no status discriminator
    (PartitionDdl.java:102-143), so a post re-hidden to QUARANTINED
    loses its row ~30 days later, the interlock's NOT EXISTS branch
    then passes, and the saved snapshot — including up to 200 chars of
    the body the judge classified hostile — renders through /saved
    again, group-broadcast included. The remediation narrows the leak
    from "forever" to "until retention drop", which matches the
    documented contract (schema.md §Per-user state justifies the
    snapshot by retention TTL only; Invariant 6 exempts saved_post from
    partition aging), but the spec is silent on whether a hostile
    moderation verdict should outlive the post row. Flagging so the
    user can decide whether security.md §Quarantine workflow should be
    extended to bind the snapshot to the verdict, not just to live
    post.status (e.g. consult the quarantine table once the post row is
    gone).
  - ListSavesTool (the LLM chat tool) reads saved_post with no
    visibility predicate (ListSavesTool.java:88-103), so a QUARANTINED
    post's snapshot_title and URL still reach the chat prompt and can
    surface in a group-scope chat reply. Title/URL only — never the
    body — so this is pre-diff parity, not a diff-introduced escape,
    and the ticket scoped the interlock to /saved. Noted because the
    remediation comment's "same rule /summary, search and getPost
    apply" does not extend to this fourth saved-post read path; if the
    interlock is the rule, listSaves is the remaining exception.
  - PRE-EXISTING, unchanged (carried from the r2 audit so it is not
    mistaken for a diff regression): `/saved --page 2147483647`
    overflows `(args.page - 1) * PAGE_SIZE` (SavedCommandHandler.java:238)
    to a negative OFFSET, Postgres rejects it, and the SQLException
    surfaces as the IllegalStateException at :176-181. One failed
    request, no persistent effect.

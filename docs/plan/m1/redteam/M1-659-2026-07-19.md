    GAP: The remediation inverts the boundary test to an ACCEPT predicate:
         infochat-provider/src/main/java/app/zcat/infochat/provider/source/SourceUpsertService.java:365-378
         `if (!Character.isLetterOrDigit(name.charAt(i - 1))) return true;`
         — a '/' is accepted only when preceded by a letter or digit. The
         method javadoc (SourceUpsertService.java:351-363) states the security
         claim this rests on: "Inverting the test makes every such codepoint —
         present and future — a rejection by default."

         That claim does not hold, because the accept side is not free of
         blank-rendering codepoints. Unicode contains blank/zero-rendering
         characters in the LETTER category (Lo), which satisfy
         Character.isLetterOrDigit and are therefore ACCEPTED as
         word-continuing:
           - U+115F HANGUL CHOSEONG FILLER  (category Lo)
           - U+1160 HANGUL JUNGSEONG FILLER (category Lo)
           - U+3164 HANGUL FILLER           (category Lo, NFKC → U+1160)
         These are the well-known "blank character" codepoints used to create
         empty display names on chat platforms precisely because they render as
         a blank gap while defeating whitespace-based validators.

         Nothing upstream removes them:
           - InboundRouter.appendNormalized (InboundRouter.java:1728-1755)
             applies NFKC then strips ONLY bidi controls and
             {U+200B, U+200C, U+200D, U+FEFF}. U+115F/U+1160 survive; U+3164
             NFKC-folds to U+1160, which also survives. (Neither composes with
             a preceding Latin letter, so the Hangul LV composition step in
             NFKC leaves the filler standalone.)
           - IngestTextNormalizer.stripMetadataField
             (infochat-core/src/main/java/app/zcat/infochat/core/ingest/IngestTextNormalizer.java:83-104)
             removes bidi controls, U+200B/C/D, U+FEFF, Character.isISOControl,
             U+2028, U+2029 — none of which match a Hangul filler.
           - String.trim() at SourceUpsertService.java:332 removes only
             codepoints <= U+0020.
         So acceptableOverride (SourceUpsertService.java:327-339) returns the
         value unchanged, it is stored as source.display_name (UPSERT_SOURCE_SQL,
         SourceUpsertService.java:98-107), read back via RETURNING display_name,
         and interpolated into BundleKeys.REPLY_ADD_SOURCE_FRESH_INSERT
         (AddSourceCommandHandler.java:196-211) plus every later echo of the
         stored field (/list-sources, /unfollow-source, /remove-source).

         The new test blankRenderingNonSeparatorCodepointBeforeACommandTokenIsRejected
         (AddSourceCommandHandlerTest.java:723-748) exercises only U+2800 — a
         NON-letter blank, i.e. the rejected side of the predicate. No test
         exercises a blank that is itself a letter, which is the side that
         still admits the payload.
    REPRO: 1. Attacker is any registered, non-probation user (/add-source is
              probation-blocked but otherwise open to ordinary users); in an
              approved group the success reply is broadcast to every member,
              including bot admins.
           2. They send (U+3164, U+1160 or U+115F as the byte sequence in place

OUT-OF-MODEL:
  - Copy-paste social engineering of a human bot admin is the terminal step of
    the chain. security.md §LLM output sanitizer keeps this surface in model
    ("a copy-pasted reply still requires is_admin=true to do anything"; the
    sanitizer exists to close "the social-engineering surface where a small LLM
    emits plausible-looking admin commands"), so the finding is reported as
    in-model defense-in-depth. The residual after any fix — an admin choosing to
    run a command they read in bot output — is a human factor the model does not
    promise to eliminate.
  - Homoglyph slashes (U+2215 DIVISION SLASH, U+2044 FRACTION SLASH) still pass
    containsCommandToken, which tests only the ASCII '/'. They are NOT counted
    as a finding: neither has an NFKC compatibility decomposition to U+002F, so
    a pasted line carrying them does not parse as a command at intake step 1.7
    and yields nothing executable. (U+FF0F FULLWIDTH SOLIDUS does NFKC-fold to
    '/', but that fold happens at intake before the check, so the stored name
    contains a real '/' and is caught correctly.)
  - defaultDisplayName's fallback path (SourceUpsertService.java:288-297) is not
    run through acceptableOverride: when the URI has a null host or fails to
    parse, the whole identifier string becomes the display name. Not reported as
    a finding because a URL reaching that point must already have passed the
    AddSourceArgs URI parse, the http/https scheme gate, the SSRF allowlist and
    a successful probe, and no command-token-bearing value that satisfies all
    four was demonstrable. Flagged so the user can decide whether the fallback
    should share the same constraint as the override.

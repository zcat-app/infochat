FINDINGS:
  - CATEGORY: AUDIT-EVASION
    SEVERITY: low
    PROMISE: docs/spec/security.md §Re-evaluation job — "BENIGN on an
      UNKNOWN post → post transitions QUARANTINED → READY with Stage 1
      redactions retained and the quarantine row transitions
      PENDING → BENIGN_CLOSED"; and §Quarantine workflow — "Every
      Stage 1 or Stage 2 hit creates a quarantine row holding span
      offsets, a placeholder id, the verbatim original, and a review
      status ∈ {PENDING, BENIGN_CLOSED, APPROVED, REJECTED}" with
      BENIGN_CLOSED as "the durable signal for 'Stage 2 cleared this'".
      The admin review queue (/quarantine list, PENDING rows only) is
      the system's committed durable signal of what still awaits human
      review.
    GAP: The new insert path
      (infochat-collector/.../eval/reeval/ReEvaluationJob.java:351-356,
      QuarantineDao.java insertReEvalRow, diff lines 253-283) creates a
      flagged_by='stage2' PENDING row on re-hide, but the BENIGN-release
      close path is stage1-scoped:
      ReEvaluationJob.java:513-516 closeQuarantineRows filters
      "WHERE post_id = ? AND flagged_by = 'stage1' AND status = 'PENDING'".
      So a post re-hidden with this new row that a later re-eval rolls
      BENIGN is auto-released (QUARANTINED→RAW→READY, correctly audited
      RE_EVAL_RELEASED + throttled page via the wasHeld branch,
      ReEvaluationJob.java:240-264) while its stage2 row stays PENDING in
      the admin review queue until TTL auto-reject. The review queue —
      the surface admins triage from — now asserts "awaiting review,
      judge said hostile" about a post the system has already released
      as BENIGN, and the stale-row comment in closeQuarantineRows
      ("a future non-stage1 quarantine writer (none in M1) must not be
      auto-closed", ReEvaluationJob.java:508-512) is now factually
      wrong: this diff IS the non-stage1 writer. The ticket's own
      clarity_check (docs/plan/m1/tickets/M1-738, diff lines 70-76)
      admits the gap and records a user decision to defer the stage2-row
      lifecycle to a follow-up ticket; the residual stands until that
      lands.
    REPRO: An adversary controlling a feed published during a Stage 2
      outage gets posts released READY with no quarantine row. They
      craft content that flips the judge: re-eval 1 returns INJECTION →
      post re-hidden, new stage2 PENDING row inserted (the fix working
      as intended); re-eval 2 (after a model swap / warm-up / borderline
      content) returns BENIGN → post auto-released to users. The admin
      queue still lists the post PENDING under rule_id
      'reeval_injection'. Repeated across the adversary's catalog this
      dilutes the PENDING review queue with rows pointing at live,
      already-released posts; an admin acting on a stale row either
      approves (harmless no-op splice + new_post re-notify) or rejects
      (no placeholder exists, post stays READY) — neither matches the
      queue's claim, and genuine PENDING rows compete with phantom ones
      until TTL expiry. Bounded by one stuck row per post and the
      admin-review TTL, hence low.
    SUGGESTED-FIX-CLASS: audit-log-coverage

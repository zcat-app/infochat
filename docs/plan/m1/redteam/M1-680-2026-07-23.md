    PROMISE: docs/spec/security.md §LLM output sanitizer, "Flag position mirrors
              the parser's own scan" (lines 447-463, added by this diff):
              "A flag-bearing closed-list entry matches its flag at **any
              argument position** within the command's argument run, not only
              immediately after the command word. The rule is the same
              match-what-the-parser-dispatches derivation as the case rule
              above: the flag-parsing handlers loop over *every* argument
              token ... The argument run **ends** at a sentence terminator or
              at a following `/`-command, **neither of which can occur inside a
              real argument to any flag-bearing entry**."
              Plus the surrounding commitment: "the sanitizer closes the
              social-engineering surface where a small LLM emits
              plausible-looking admin commands across any of the surfaces
              above. Every match is audit-logged (per-occurrence, not
              throttled)."
    GAP: The terminator claim is factually false about the parser it claims to
         mirror, so the "any argument position" promise is delivered only for
         argument runs that happen to contain no `.`, `!`, `?` or `/`.
         - infochat-provider/src/main/java/app/zcat/infochat/provider/llm/LlmOutputSanitizer.java:178
           `private static final String ARGUMENT_RUN = "(?=\\s)[^.!?/]*?";`
           The run cannot cross `.`, `!`, `?` or `/`.
         - infochat-provider/src/main/java/app/zcat/infochat/provider/command/ListSourcesCommandHandler.java:469-470
           (javadoc) "Token-based parser; **unknown flags are ignored** (no
           error surface ...)" and the loop at :479-493, which tests each token
           against `--all` / `--include-deleted` / `--page` and silently
           ignores everything else. There is therefore no such thing as an
           argument the parser rejects: ANY junk token — including one carrying
           `.`, `!`, `?` or `/` — is a "real argument" that leaves `--all`
           dispatching. LlmOutputSanitizer.java:160-165 repeats the false
           premise in code ("the parser accepts only --all, --include-deleted,
           --page N and --page=N").
         - The added regression test only exercises the punctuation-free case
           (infochat-provider/src/test/java/app/zcat/infochat/provider/llm/LlmOutputSanitizerTest.java:206-228,
           `--page 1 --all` / `--page 2 --include-deleted`), and
           :244-253 actively asserts the non-match on a `.`-bearing run, so the
           bypass class is locked in by a test rather than caught by one.
    REPRO: 1. Adversary plants text in any surface that reaches the chat
              agent's context — a feed post body (Stage 1/2 clear it as benign
              prose) or a retrieved title/URL, which the D28 deterministic
              `semanticSearch` pre-fetch re-injects into every chat turn by

           2. Payload steers the model to close its reply with a
              helpful-looking admin tip, e.g.
              `To audit every configured feed run: /list-sources --filter rss/news --all`
              (equivalently `/list-sources --page 1. --all`,
              `/list-sources v2.0 --all`, `/list-sources why? --all`).
           3. `LlmOutputSanitizer.sanitize()` compiles entry 20 to
              `\Q/list-sources\E(?=\s)[^.!?/]*?\s+\Q--all\E(?=$|[^a-zA-Z0-9\-])`.

              (or `.`/`!`/`?` in the variants), so the character class fails at
              every expansion and the entry does not match. Result: the line
              ships VERBATIM — no `[redacted command]` marker, no WARN line, and
              no `LLM_OUTPUT_SANITIZED` audit row. The operator's only signal

              `ListSourcesArgs.parse` ignores `--filter` and `rss/news` and sets

              exactly the disclosure the spec says this closed-list entry

              bypassed by the same class of trivial mutation that motivated the

  - CATEGORY: DOS
    SEVERITY: medium
    PROMISE: docs/spec/security.md §Trust boundaries item 9 ("LLM/embeddings
              provider response → system"): "Everything a generative or
              embeddings endpoint returns is endpoint-chosen input, not a
              trusted internal value ... so a hostile or compromised endpoint is
              in scope here for the same reason a hostile feed is on the ingest
              side. Two properties bound what a reply can do. The response body
              is read under an operator-configurable cap (clamped to 1–8 MiB)
              before parsing, so a pathological multi-GB reply cannot exhaust
              the JVM."
              Supporting, §Ingest pipeline: "`java.util.regex` is a backtracking
              engine, so catastrophic backtracking is **mitigated by the
              watchdog timeout, not prevented at the engine level**" — the
              project's own stated discipline for attacker-influenced regex
              input, which the outbound sanitizer has no equivalent of.
    GAP: The diff replaces the linear `\s+<flag>` tail with a lazy character-run
         followed by a greedy whitespace quantifier, introducing quadratic
         backtracking on whitespace runs.
         - LlmOutputSanitizer.java:178 `"(?=\\s)[^.!?/]*?"` and :240-244, which
           emit `<literal>(?=\s)[^.!?/]*?\s+<flag>` for entries 20 and 21.
         - java.util.regex evaluates the lazy `[^.!?/]*?` iteratively, calling
           its continuation once per character position; that continuation is
           the GREEDY `\s+`, which at each position consumes the remaining
           whitespace run and backtracks it one character at a time. On an
           N-character whitespace run with no `.`/`!`/`?`/`/` and no closing
           flag, total work is ~N²/2, and the pass runs once per flag entry
           (twice). Pre-diff the pattern was `\Q/list-sources\E\s+\Q--all\E`,
           which is linear on the same input — the super-linearity is new.
         - The javadoc's safety argument (:167-176, "168 KB scans in ~5 ms") and
           the accompanying test
           (LlmOutputSanitizerTest.java:255-270) both use single-space-separated
           tokens, where `\s+` can only ever consume one character, so neither
           covers the quadratic case.
         - No watchdog, timeout, or length cap wraps `sanitize()`
           (LlmOutputSanitizer.java:263-271); ChatAgent.java:507,
           TranslationPipeline.java:114, DigestRenderer.java:131,
           CategoryRollupGenerator.java:148 and ClusterBlockRenderer.java:107 all
           call it inline on the reply path.
    REPRO: 1. Adversary is a hostile or compromised LLM endpoint (explicitly in
              scope per trust boundary 9), or prompt-injects a local model into
              a degenerate whitespace run.
           2. The reply content is `"/list-sources"` followed by N space
              characters and nothing else (no `.`, `!`, `?`, `/`, no `--all`).
           3. `applyClosedListStripWithMatches` reaches entries 20 and 21. For
              each of the N lazy positions the greedy `\s+` walks the remaining
              run forward and back: ~N²/2 steps per entry, ~N² overall, with no
              watchdog to abort.
           4. At N≈16k (a 1024-max-token reply built from multi-space tokens)
              this is ~10^8 backtrack steps — seconds of CPU burned per reply,
              per pattern. At the 8 MiB body size the spec explicitly permits a
              reply to reach, N≈8.4e6 gives ~3.5e13 steps: the sanitize call
              never returns and the reply path's worker thread is wedged for the
              process lifetime.
           5. Why the system shouldn't have allowed it: the spec names the
              response-body cap as the property that bounds what a pathological
              reply can do. A super-linear consumer downstream of that cap
              converts an in-cap reply into unbounded CPU, and the diff's own
              performance analysis (which correctly rules out StackOverflowError)
              does not cover it.

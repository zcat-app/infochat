RED-TEAM VERDICT: CLEAN

Audited diff M1-510 (SimpleX codec: align DM inbound/outbound/error decode
with live v6.5.4.1 wire format) against docs/spec/security.md.

The diff is a wire-format field-mapping bugfix confined to SimpleXMessageCodec.java
plus migrated test fixtures. Every security-relevant change preserves (and in one
case improves) the threat-model commitments:

- Adapter->Provider trust boundary / D10 identity anchor (§Trust boundaries item 1):
  The contactId field path is UNCHANGED; identity is still the transport-assigned
  per-connection contactId, validated through isValidQueueAddressId before any
  InboundMessage is built (SimpleXMessageCodec.java:412-423). A numeric connection
  id (e.g. 5) is exactly the "per-connection contact id the transport assigns" the
  spec names as the anchor, and is assigned by the trusted local simplex-chat
  subprocess, not attacker-forgeable. The displayName -> localDisplayName change
  keeps the display name informational-only and explicitly does NOT read the
  self-asserted contact.profile.displayName (line 424-429), matching D10.

- Command-injection boundary (design §6.4.4): firstScalarText (line 905-912)
  widens the send-ack chat-item id to accept JSON numbers, but that id is round-
  tripped only into /_update item and is re-gated by
  requireValidQueueAddressId(chatItemId,...) at encode time (line 153) before
  being pasted into the command verb. A numeric id carries no command terminator
  ([' ', '@', '#'] are outside the value), so the widening does not loosen the
  boundary. Inbound contactId / adapterGroupId / memberContactId / mention
  memberRef all remain charset-validated.

- §User content in exceptions: the error-tag decode now reads ONLY the enum-like
  nested .type (chatError.errorType.type / chatError.storeError.type, line ~847)
  and deliberately never reads the sibling free-form "message" field. This
  strictly REDUCES the prose-leak surface versus the prior firstTextual(chatError,
  errorType) read; a test asserts the echoed "Failed reading: empty" prose cannot
  reach CommandError.detail(). Ignored.reason() sentinels remain fixed strings and
  do not embed attacker-controlled chatType bytes (line 392-401).

- Fail-closed failure classification (§Failure handling): classifyError is
  unchanged and still defaults absent/unknown tags to PERMANENT.

- DoS: the plural newChatItems path decodes the first element only
  (chatItems.get(0), line 368); no unbounded iteration is introduced.

- No authentication, invite-code, ban, admin-tier, authorization, LLM-tool, or
  audit-log surface is touched by the diff (consistent with the sensitive-surface
  inventory).

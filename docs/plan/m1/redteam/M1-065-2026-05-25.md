RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: DOS
    SEVERITY: medium
    PROMISE: "every interruptible read-only query (chat-mode tool calls, on-demand `/summary`) runs under a profile-driven `statement_timeout` that bounds the worst case even when `pg_cancel_backend` fails" (docs/spec/commands.md line 710-712, mirrored in security.md via the /stop spec)
    GAP: `CancellationService.applyStatementTimeout()` is defined at infochat-provider/src/main/java/app/zcat/infochat/provider/chat/CancellationService.java:77 but has zero callers anywhere in the codebase (`Grep` for `applyStatementTimeout` across the provider module returns only the definition site). Neither `/retry`'s `fetchReadyPosts` queries (RetryCommandHandler.java:262) nor `/summary`'s `EligiblePostQuery`, nor the chat-agent tool-call path apply the statement timeout. The spec's defense-in-depth safety net for long-running queries (the timeout that bounds the worst case independent of `pg_cancel_backend`) is dead code.
    REPRO: 1. A user issues a chat-mode message that triggers a tool call with a complex query (e.g., `searchPosts` with a large tag set). 2. The query runs against a large `post` table and takes longer than the profile-driven cap. 3. Another user (or the same user) issues `/stop`. 4. `pg_cancel_backend` is issued but Postgres is mid-I/O and the cancel signal is delayed. 5. Without `statement_timeout`, the query runs unbounded until Postgres completes it, defeating the "bounds the worst case" promise.
    SUGGESTED-FIX-CLASS: other

  - CATEGORY: DOS
    SEVERITY: low
    PROMISE: "Bounded by a small fixed retry cap (value in design notes) anchored to that most-recent summary-producing command. When the retry cap is exhausted, a friendly error is returned" (docs/spec/commands.md line 726-729)
    GAP: RetryCommandHandler.java:125 increments the retry counter (`summaryAnchorRepository.incrementAndGetRetryCount`) BEFORE validating that the frozen UIDs still resolve to READY posts (line 133) and BEFORE acquiring the in-flight slot (line 143). If all posts are quarantined, or if the in-flight slot is occupied, the retry attempt fails with a friendly error but the counter is already consumed. Repeating this wastes all cap slots without a single LLM call.
    REPRO: 1. User runs `/summary` (anchor written, counter at 0). 2. An admin quarantines all posts that were in the summary. 3. User issues `/retry` three times; each time counter increments (1, 2, 3) but the handler returns "no eligible posts" because all UIDs are filtered. 4. When the admin un-quarantines the posts, the user issues `/retry` again; counter is now 4 > cap(3), so the cap-exhausted error fires even though no LLM call was ever made. The user must issue a non-`/retry` command and re-run `/summary` to reset, even though the original anchor is still valid.
    SUGGESTED-FIX-CLASS: other

OUT-OF-MODEL:
  - The `serializeClusterMap` method in SummaryCommandHandler.java:345-360 builds JSON by string concatenation without escaping `topicId` or `uid` values. Currently these are deterministic hex-based identifiers (safe), but if a future change allows richer identifiers, a specially crafted value containing `"` could break the JSON structure stored in `summary_anchor.cluster_map`, which is later parsed by `RetryCommandHandler.reconstructClusters`. The DB is internal and the values are system-generated, so this is not in the current threat model, but a `jakarta.json` builder would be more resilient.

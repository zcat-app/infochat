No findings. The diff scopes the RE_EVAL_RELEASED audit row and the throttled
admin page in ReEvaluationJob.applyBenignReEval to the genuine hidden->visible
release (post status='QUARANTINED' at re-eval time) and changes the audit
target_id from the internal post.id surrogate to candidate.postUid().

Both changes match docs/spec/security.md §Re-evaluation job:

- The spec mandates the audit + throttled notification only for the
  UNKNOWN->BENIGN release ("The transition is audit-logged as RE_EVAL_RELEASED
  with actor='re_eval_job', target_kind='post', target_id=<post_uid>,
  details_json={prior_verdict, new_verdict='BENIGN', attempt}, and a throttled
  admin notification fires"). An UNKNOWN verdict always implies QUARANTINED
  status, so the wasHeld gate (postIsQuarantined) is always true for that class
  and the spec-mandated audit + page always fire. The QUARANTINED infra-failure
  release is additionally covered. Only the READY (already user-visible) and RAW
  (in-pipeline, never in the admin review queue) infra-failure sub-cases are
  dropped — neither is the QUARANTINED->released exposure the spec's audit
  rationale ("posts auto-released from QUARANTINED ... with no human reviewer
  ever having seen the row") is written to defend, so no spec-required audit is
  lost. The gate keys on the live pre-transition status and the status read
  shares the release UPDATE's transaction (ReEvaluationJob.java:232-249), so
  audit and release are atomic — no genuine hidden->visible release of a
  review-held post can evade the audit, and a failed status read fails closed
  (rolls back the release too).

- target_id=candidate.postUid() (ReEvaluationJob.java:506) satisfies the
  spec's explicit "target_id=<post_uid>" requirement, replacing the prior
  post.id deviation. post.uid is non-null (selected at
  ReEvaluationJob.java:649; schema NOT NULL).

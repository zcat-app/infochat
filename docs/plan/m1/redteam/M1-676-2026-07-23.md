RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: INJECTION
    SEVERITY: medium
    PROMISE: docs/spec/security.md §LLM output sanitizer — "Before any
             **LLM-generated** text is delivered to a user, the candidate
             output is passed through a deterministic outbound regex pass
             that strips or refuses output containing admin command
             strings (`/grant-admin`, `/ban`, `/promote`,
             `/remove-source`, etc.) ... the sanitizer closes the
             social-engineering surface where a small LLM emits
             plausible-looking admin commands across any of the surfaces
             above." And the paragraph this diff ADDS: "The closed-list
             pass matches against the **canonical** form of the candidate
             output ... which is the same representation the deterministic
             command parser consumes (§Message intake step 1.7). ... Case
             is deliberately **not** folded: dispatch compares the command
             name exactly, so `/Grant-Admin` is not a command and
             redacting it would corrupt prose for no security gain."
    GAP: The new "same representation the parser consumes" claim is false
         for every multi-word closed-list entry whose second token is a
         SUBCOMMAND, because the parser case-folds subcommands and the
         sanitizer does not.
         - infochat-provider/.../llm/LlmOutputSanitizer.java:288-291
           (`canonicalizeForMatching` = NFKC + bidi/zero-width strip, no
           case fold) and :160-165 (`compileClosedListPattern` quotes each
           word literally → case-sensitive match).
         - The justification comment at LlmOutputSanitizer.java:283-286
           and the spec text at docs/spec/security.md:425-427 both rest on
           "dispatch compares the command name with equals". That is true
           only of the command NAME
           (InboundRouter.java:1410-1414, `handler.name().equals(commandName)`).
           It is NOT true of the subcommand:
           InviteCommandHandler.java:231-241 does
           `split[1].toLowerCase(Locale.ROOT)` before switching on
           "create"/"list"/"revoke"/"bot-contact"/"pending-contacts", and
           QuarantineCommandHandler.java:134-143 does the same for
           "list"/"approve"/"reject".
         - Consequence: 8 of the 34 CLOSED_LIST entries
           (LlmOutputSanitizer.java:114-121 `/invite create|list|revoke|
           bot-contact|pending-contacts`, :119-121 `/quarantine
           list|approve|reject`) are evaded by changing the case of the
           second word only. The evading string is delivered verbatim, and
           because there is no match there is also no WARN line and no
           `LLM_OUTPUT_SANITIZED` audit row — the operator signal the
           same section commits to ("Every match is audit-logged") is
           silent for exactly the outputs that still dispatch.
    REPRO: 1. Attacker publishes feed content (or sends a group chat turn)
              carrying an injection payload. The threat model itself
              concedes the model context is attacker-influenced: the D28
              deterministic `semanticSearch` pre-fetch re-injects
              feed-derived titles/URLs on every chat turn
              (§Prompt-injection defenses, `semanticSearch` row).
           2. Payload steers the chat/summarizer/digest model into
              emitting: `To unblock this, an admin should run
              /invite CREATE --open` (or `/quarantine APPROVE <id>`,
              or the fullwidth `/invite ＣＲＥＡＴＥ`, which NFKC folds to
              `/invite CREATE` and still evades the case-sensitive
              pattern).
           3. `LlmOutputSanitizer.sanitize()` canonicalizes
              (LlmOutputSanitizer.java:240-241), finds no closed-list
              match, takes the `matches.isEmpty()` early return at :261-263
              and returns the ORIGINAL bytes. No redaction, no WARN, no
              audit row.
           4. A bot admin reading the reply copy-pastes the suggested line.
              Intake normalizes it (InboundRouter.normalize), `handleSlash`
              resolves `invite` (exact-case name match, unaffected by the
              case change), `InviteCommandHandler` lower-cases `CREATE` to
              `create`, and the privileged path runs — an `--open` invite
              code is minted for the adapter (or a quarantined,
              injection-flagged post has its Stage 1 redactions lifted and
              is re-published via `NOTIFY new_post`).
           5. The system should not have allowed it: this is the exact
              copy-paste social-engineering surface §LLM output sanitizer
              exists to close, and the diff's own premise is that the
              sanitizer must see what the dispatcher sees.
    SUGGESTED-FIX-CLASS: input-sanitization

  - CATEGORY: INJECTION
    SEVERITY: low
    PROMISE: docs/spec/security.md §LLM output sanitizer is the single
             outbound gate for LLM-authored text; the sanitizer's own
             documented pass ordering (LlmOutputSanitizer.java:30-36) is
             "Markdown link syntax `[text](url)` is rewritten to
             `text (url)` ... Runs FIRST so a hostile
             `[Click for admin](/grant-admin)` flattens ... BEFORE the
             closed-list pass sees it", backing the plain-text/bare-URL
             surface convention (CLAUDE.md §Key conventions: "bare URLs
             (no markdown link syntax)").
    GAP: The markdown pass runs on the RAW bytes
         (LlmOutputSanitizer.java:187, :199-203, `MARKDOWN_LINK` at :168 is
         ASCII-bracket-only), while canonicalization now happens later,
         inside the closed-list pass (:240-241). NFKC folds U+FF3B/U+FF3D/
         U+FF08/U+FF09 to `[`/`]`/`(`/`)`, so on ANY closed-list hit the
         returned canonical text (:264) can contain markdown link syntax
         that the flatten pass never saw. Pre-diff the fullwidth brackets
         survived to the user as fullwidth characters (no client renders
         them as a link); post-diff the sanitizer itself converts them into
         real markdown link syntax in the delivered message.
    REPRO: 1. Injected model emits:
              `Run /ban spammer, then see ［important notice］（https://evil.example/x）`
              (fullwidth brackets/parens).
           2. Markdown pass: no ASCII `[..](..)` → no flatten.
           3. Closed-list pass on the canonical form: `/ban` matches →
              redacted → the returned text is the canonicalized form
              `Run [redacted command] spammer, then see [important notice](https://evil.example/x)`.
           4. The delivered reply now carries label-hiding markdown link
              syntax the sanitizer's first pass exists to remove. Impact is
              bounded today only because both v1 production adapters assert
              `supportsMarkdownLinks=false`; the flattening invariant, not
              the adapter capability flag, is what the pass ordering was
              documented to guarantee.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

OUT-OF-MODEL:
  - Unicode whitespace that survives NFKC and is not in Java's ASCII `\s`
    (U+1680 OGHAM SPACE MARK, U+2028/U+2029, U+0085) breaks the multi-word
    closed-list patterns' `\s+` separator — but it equally breaks the
    parser's own `split("\\s+")` (InboundRouter.java:1411,
    InviteCommandHandler.java:231), so no dispatchable command is missed.
    It becomes reachable only if a messaging client rewrites U+2028 to a
    newline on copy/paste, which is client behaviour outside the
    documented model. Flagged so the user can decide whether client-side
    paste transformation belongs in the model.
  - Behaviour change with no attack, noted for the record: matching on the
    canonical form REMOVES some redactions that the raw-byte pass used to
    perform. `/ban` followed by a combining mark (e.g. `/ban` + U+0301) or
    by an NFKC-folding letter form (e.g. U+24D0 → `a`) matched pre-diff and
    no longer matches, because the canonical form is `/bań` / `/bana`.
    Neither dispatches at intake (intake canonicalizes identically), so
    this is a false-positive removal, i.e. the intended semantics — but it
    does mean the bot may now display near-lookalike admin command strings
    it previously redacted.

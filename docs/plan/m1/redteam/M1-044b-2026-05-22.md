## Verbatim verdict (threat-actor subagent output)

RED-TEAM VERDICT: FINDINGS

FINDINGS:

  - CATEGORY: AUTH-BYPASS
    SEVERITY: high
    PROMISE: spec/security.md §Invite-code registration ("Group-registered users do not get free DM access"): "the permission step (step 7) adds a DM-only gate that rejects any DM from a `group_only` user with the same fixed `Access requires an invitation.` reply as step 2's invalid path." Combined with spec/security.md §Authorization model step 7 ("Permission check against the matrix. ... blocked commands return a friendly ... reply and never reach execution") and step 9 ("Execute"), the spec orders Permission BEFORE Execute, i.e., a blocked DM from a `group_only` user must "never reach execution."
    GAP: infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/InboundRouter.java lines 319-345. The DM-gate carve-out fires AFTER `handleSlash` (line 322) has already executed the command handler. The body is overwritten (line 342) but the handler's side effects already occurred. For example, `AddSourceCommandHandler.handle()` (infochat-provider/src/main/java/app/zcat/infochat/provider/command/AddSourceCommandHandler.java lines 107-184) performs a URL probe (outbound HTTP) and a `sourceUpsertService.upsert(...)` (DB write) before returning. `SummaryCommandHandler.handle()` performs an LLM call before returning. The comment at InboundRouter.java line 336-338 acknowledges "The handler's SELECT (e.g. /help) is wasted work for a group_only DM, but bounded" — but this dismisses the issue assuming only read-only handlers; the actual handler registry includes mutating handlers.
    REPRO: 1) Alice is auto-registered in Group G via `@mention` → her users row gets `registration_state='group_only'`. 2) Alice DMs the bot: `/add-source https://attacker.example/feed.rss --tags news`. 3) InboundRouter step 1.5 admits her (under rate cap), normalize runs, lookupUser returns a snapshot with `registration_state='group_only'`. 4) Steps 2,3,4 do not fire (snapshot.isEmpty()==false, scope!=Group, not banned). 5) `handleSlash` dispatches to `AddSourceCommandHandler`, which does NOT see Alice's `group_only` flag (its `lookupActor` only checks `is_banned`/`is_admin`), runs URL probe, and calls `sourceUpsertService.upsert` — the source is added to the DB. 6) Step 7 then overrides `body` to "Access requires an invitation." Alice sees the rejection literal but the source row exists in the DB. She has driven outbound SSRF-guarded HTTP probes and DB writes from a state the spec explicitly bars from DM dispatch.
    SUGGESTED-FIX-CLASS: missing-auth-check

  - CATEGORY: DOS
    SEVERITY: medium
    PROMISE: spec/security.md §Authorization model step 1.5: "Over-cap inbound is dropped silently for the rest of the cap window — no reply (including no fixed ban reply, no fixed invite-required reply, no friendly error). The cap runs after step 1 ... and before every application-level check below, so a hostile flood cannot drive outbound cost via the per-inbound fixed-reply paths."
    GAP: infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/InboundRouter.java lines 243-255. The body-size cap fires BEFORE the rate cap (`tryAcquire`) and sends a `MESSAGE_TOO_LARGE_REPLY` for every oversize inbound. Oversize-inbound flow never consumes a token from `RateCapBucket`, so an adversary can sustain unbounded `MESSAGE_TOO_LARGE_REPLY` outbound at line rate by always shipping bodies above `infochat.router.max-inbound-body-bytes`. The class-level Javadoc at line 88-95 justifies the ordering ("adversarial bodies cannot drive bucket arithmetic"), but the trade-off violates the spec's explicit promise that step 1.5 fires before "every application-level check" and that no friendly-error reply is emitted under flood.
    REPRO: 1) Attacker scripts inbound messages of 65,537 bytes each (one byte above the default cap) at 10 messages/second. 2) Each inbound bypasses the rate cap and triggers `sendReply(MESSAGE_TOO_LARGE_REPLY)` → 10 outbound/second indefinitely. 3) Over a sustained flood this is a 10× outbound amplification compared to the under-cap inbound rate (60/min = 1/s). The bot's outbound budget is exhausted without the bucket ever decrementing — the rate-cap signal the operator monitors stays "healthy" while outbound is saturated.
    SUGGESTED-FIX-CLASS: rate-limit

  - CATEGORY: INFO-LEAK
    SEVERITY: low
    PROMISE: spec/security.md §Secrets handling: "Contact IDs are logged in redacted form (prefix + ellipsis + suffix) outside the audit log."
    GAP: infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/InboundRouter.java lines 379-383. When `lookupUser` catches a `SQLException`, the wrapping `IllegalStateException`'s message embeds the raw `contactId` ("InboundRouter.lookupUser failed for adapter=" + adapter + " contact_id=" + contactId). The `lookupUser` call at line 267 is not inside a try/catch in `onMessage`, so this exception bubbles up to whoever invoked the inbound handler (the adapter's InboundHandler lambda set in AdapterRegistry line 216). When that surface logs an uncaught dispatch failure, the unredacted contact id will appear in operator logs — the same surface that the M1-038 redaction pass was meant to lock down at the three explicit log sites in this same method.
    REPRO: 1) Operator transient DB outage during dispatch causes `lookupUser` to throw. 2) The IllegalStateException bubbles to the adapter dispatch surface (Quarkus default uncaught-exception logger, or any future adapter-level catch-and-log). 3) The exception's `getMessage()` is logged, including the raw contact id. 4) An operator-log reader sees the unredacted id.
    SUGGESTED-FIX-CLASS: input-sanitization

  - CATEGORY: AUDIT-EVASION
    SEVERITY: low
    PROMISE: spec/security.md §Invite-code registration: "**Brute-force rate limit.** A per-`(adapter, contact_id)` rate limit applies to invite-code attempts. Failed attempts increment a counter; when the counter exceeds a profile-driven threshold within a profile-driven window, further attempts from that `(adapter, contact_id)` are rejected without checking the code, and an audit row records the threshold breach."
    GAP: infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/InboundRouter.java lines 277-293. A DM from an unknown contact whose normalized body is not parseable as a UUID short-circuits at line 280 (parseInviteCode returns null → ERROR_INVITE_REQUIRED reply, return) WITHOUT calling `inviteCodeConsumer.consume`. The brute-force counter (per `InviteCodeConsumer`) therefore does not increment on non-UUID attempts. An adversary searching the invite-code namespace can prefix-filter their guesses: only valid-UUID-shaped guesses ever reach the counter, so the effective search budget is "threshold × non-trivial-guesses-per-window" rather than "threshold × total-inbound-per-window." This is a defense-in-depth shortfall: the brute-force limit's value as an audit signal (the threshold-breach audit row) is also weakened — the breach row never fires for adversaries who issue many non-UUID probes mixed with a few UUID-shaped guesses below threshold.
    REPRO: 1) Attacker enumerates a target contact_id by alternating: send 9 UUID-shaped guesses (under the threshold-of-10), then send 1000 non-UUID-shaped probe payloads. 2) The 9 UUID guesses increment the counter to 9; the 1000 non-UUID probes are short-circuited without incrementing. 3) Wait for the window to roll over, repeat. 4) The audit row "threshold-breach" never fires, and the attacker has performed >1000 invite-related probes per window without operator visibility.
    SUGGESTED-FIX-CLASS: rate-limit

OUT-OF-MODEL:
  - The `lookupUser` SQL uses parameterized binding (`PreparedStatement.setString`), so SQL injection at this site is not exploitable; flagged only to note that the `IllegalStateException` message at line 380-382 concatenates `adapter` and `contactId` from the raw inbound — if this surface is ever re-used as an audit-log details_json field via a stringly-typed plumbing, the redaction hook would need to apply there too.
  - The `MESSAGE_TOO_LARGE_REPLY` literal does not pass through the LLM sanitizer (it's a fixed deterministic literal), so this is not an LLM-output exfiltration channel. Listed for completeness because oversize handling sits next to LLM-output surfaces in the threat model.

## Verbatim threat-actor verdict

```
RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: AUDIT-EVASION
    SEVERITY: low
    PROMISE: docs/spec/security.md §Authorization model: "Authorization
      evaluation order on every inbound message: ... 7. Permission
      check ... 8. Audit-log the intent. 9. Execute. 10. LLM only
      enters for chat-mode replies, summary prose, and the eval
      pipeline."
    GAP: For confirmable destructive commands (`/ban`, `/invite create
      --open`, `/invite revoke`), the first-call path passes the admin
      gate and self-ban guard (the spec's step-7 permission check),
      then stores the validated intent in `ConfirmStateService.remember`
      and returns a prompt — but writes NO `audit_log` row.
      - infochat-provider/src/main/java/app/zcat/infochat/provider/command/BanCommandHandler.java:170-178
        — first-call path: parse + self-ban guard +
        `confirmStateService.remember(...)` + return prompt. No
        `auditLogWriter` / `insertAudit` invocation.
      - infochat-provider/src/main/java/app/zcat/infochat/provider/command/InviteCommandHandler.java:254-264
        — `/invite create --open` first-call: validate adapter,
        `confirmStateService.remember`, return prompt. No audit row.
      - infochat-provider/src/main/java/app/zcat/infochat/provider/command/InviteCommandHandler.java:506-516
        — `/invite revoke` first-call: UUID-parse,
        `confirmStateService.remember`, return prompt. No audit row.
      - Existing tests `banAndInviteRevokeAuditRowsShareRequestId`
        (BanCommandHandlerTest, around line 317) and
        `banFirstCallReturnsPromptAndWritesNoStateChange` explicitly
        assert "first /ban must write no audit rows" — i.e., the
        absence of an audit row is a deliberate, tested invariant.
    REPRO: A bot-admin who has passed admin-gate issues `/ban
      target-contact` in DM. The router writes pending state to
      in-memory `ConfirmStateService`, sends the prompt, and returns.
      The admin then drops the connection, restarts their client, or
      simply never types `/ban confirm`. The 60-second timeout lapses,
      lazy-expiry removes the pending entry on the next `peek`/`take`,
      and no `audit_log` row exists for the attempted ban. Effect: an
      admin can probe-and-abandon `/ban target` repeatedly (within
      transport-rate-cap) to determine that the system would proceed
      to the confirm step against any given target (e.g., to learn the
      target is registered + not the last admin) without leaving an
      audit trail. Same shape for `/invite create --open` (probe
      whether the open-cap is met) and `/invite revoke` (probe whether
      the code-prefix would be accepted as a parsable UUID). The
      spec's step-8 "Audit-log the intent" is the trail that lets a
      second admin or an operator notice the probing; with no row
      written, that trail is missing.
    SUGGESTED-FIX-CLASS: audit-log-coverage

OUT-OF-MODEL:
  - The "args retyped" relaxation in `InboundRouter.isConfirmShape`
    (`infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/InboundRouter.java:484-490`)
    accepts any inbound that `startsWith("/" + sweepPrefix + " ")` AND
    `endsWith(" confirm")` as a matching confirm — but the args
    between the prefix and "confirm" are IGNORED; the handler's
    `takeMatching` pops the ORIGINAL stored args. An admin who issued
    `/ban alice` then types `/ban bob confirm` (typo or intent change)
    bans `alice`, not `bob`. The audit row is accurate (alice is
    banned), so this is a UX-footgun rather than an audit-evasion or
    privilege-escalation surface. Flagging here so the user can decide
    whether to tighten the matcher to the canonical-only form
    `"/" + sweepPrefix + " confirm"`.
  - A `peek`+`takeAny` pair in step 4.5
    (`infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/InboundRouter.java:356-374`)
    is not atomic across two `ConcurrentHashMap` operations. If the
    same admin's two inbounds race (a fresh `/ban target2` arriving
    on a different thread between the `peek` and `takeAny` of an
    unrelated cancellation), `takeAny` may pop the NEWER pending while
    the cancellation reply names the OLDER `commandName()`. The
    Provider intake path is normally serialized per-(adapter,
    contact_id) by the inbound channel ordering, so this race is
    unlikely in practice; noting it in case the messaging adapter or
    thread pool ever delivers concurrently from the same actor.
```

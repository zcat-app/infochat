OUT-OF-MODEL:
  - Round-1 finding re-verified as genuinely CLOSED, not merely "remediation
    attempted". Checked against the code, not the claim:
    (a) `Thread.interrupted()` (LlmOutputSanitizer.java:257) runs BEFORE the
        try-with-resources, so `dataSource.getConnection()` — the Agroal
        interruptible-acquisition leg round 1 named — and every pgjdbc socket
        operation run with the flag CLEAR.
    (b) The restore sits in a `finally` attached to the SAME try that owns the
        resource, so Java's ordering is body -> `conn.close()` -> catch ->
        finally. The connection's close (which triggers the pooled reset /
        rollback, itself socket I/O) therefore also runs with the flag clear —
        a `finally` placed inside the try-with-resources would have missed it.
    (c) The finally covers every exit: normal return, the
        SQLException->IllegalStateException throw at :282, and any unchecked
        throw out of `auditLogWriter.write`.
    (d) No swallow window. If the caller's flag was armed, `finally` re-arms
        unconditionally (idempotent against a second interrupt landing
        mid-write). If it was NOT armed, `callerWasInterrupted` is false and
        the finally does nothing, so an interrupt arriving mid-write stays on
        the thread and stays fail-loud — exactly what the inline comment
        claims.
    (e) The park is gated behind the `matches.isEmpty()` early return, so the
        no-match path (the overwhelming majority of sanitize calls, including
        every call on the transport dispatch thread) is byte-for-byte
        unchanged.
    (f) Cancellation survives: LlmHttpSupport.java:190-194 re-arms the flag and
        classifies the interrupt as NOT transport-unreachable, so an
        interrupted render neither resumes spend nor trips the shared
        per-endpoint circuit breaker into a deployment-wide outage.
    Audited the remediation as new surface across every caller of
    `sanitize()` — the D35 /stop path in particular. `InFlightTracker`
    .CancellationHandle decides discard on its own `cancelled` AtomicBoolean,
    not on the interrupt status (InFlightTracker.java:47-51), and
    `releaseWorker()` clears the flag under the handle monitor at the end of
    the in-flight section (:91-94). The park cannot leak a re-armed flag past
    that gate (a post-release `emitAuditRows` would read
    `callerWasInterrupted == false`), and it cannot suppress a /stop (the
    restore is unconditional). No control depends on the flag inside the
    parked window.
  - The park makes connection ACQUISITION uninterruptible for its duration.
    Under pool exhaustion that is bounded by Agroal's acquisition timeout —
    but neither `infochat-provider/src/main/resources/application.properties`
    nor the collector's sets `quarkus.datasource.jdbc.acquisition-timeout`, so
    the bound is the framework default rather than an operator-stated one.
    Judged NOT exploitable and therefore not filed: the interrupted render is
    a virtual thread holding no pool worker, its LLM spend has already stopped,
    the digest in-flight guard is released on the worker thread independently
    of the orphan, and the number of parked writes per render is bounded by
    the digest's post/cluster count at two slots per group per day. Flagged
    only so the user can decide whether that timeout deserves an explicit,
    spec-visible value now that a security-relevant path depends on it.

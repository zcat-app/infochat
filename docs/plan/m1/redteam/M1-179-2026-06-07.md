RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - The new `WHERE NOT EXISTS (SELECT 1 FROM post WHERE uid = ?)` pre-filter is, by the implementer's own comment (`PostPersister.java:112-124`), only *advisory* under concurrently-overlapping scheduler ticks — there is no table-level UNIQUE on `uid` alone because the partition key (`fetched_at`) must participate in every unique constraint, and the `ON CONFLICT (source_id, upstream_identifier, fetched_at)` backstop only catches same-partition races. If two ticks for the same item land in *different* `fetched_at` partitions concurrently, both can pass `NOT EXISTS` and both insert, yielding a duplicate post that is enqueued and runs Stage 1/Stage 2 twice (extra LLM/judge cost). This depends entirely on the single-instance, non-overlapping-tick guarantee of the Collector scheduler (M1-009 advisory lock), which this diff does not touch and which is an internal operational assumption, not an attacker-reachable surface. The threat model makes no dedup-as-security-control promise, and a duplicate row still passes the full ingest pipeline, so this is a correctness/cost concern rather than a violated commitment. Flagging only so the user can decide whether the "advisory under overlap" admission deserves a hardening ticket.

Notes on what was checked and found clean:
- SQL injection (INJECTION): the statement at `PostPersister.java:125-136` is fully static; every dynamic value (`uid`, `sourceUuid`, `upstreamIdentifier`, url/title/body, timestamps, and the uid probe at param 10) is bound via `PreparedStatement`. `uid` is lower-case sha256 hex. No untrusted concatenation. Clean.
- Cross-trust-boundary suppression (INFO-LEAK/integrity): the pre-filter only blocks INSERT, never UPDATE/DELETE, so a re-fetched colliding item is dropped and the existing row is preserved. `uid = sha256(source_id || '|' || upstream_identifier)` embeds the source UUID, so a cross-source uid collision to suppress another source's post requires a sha256 preimage collision (infeasible). Within a single feed the attacker already controls ordering, so no new boundary is crossed. Clean.
- Ingest-pipeline bypass (trust boundary 4): dedup returning `Optional.empty()` only prevents a second enqueue of an already-persisted item; it does not let any post reach users without Stage 1/Stage 2. Clean.
- Sensitive surfaces (auth, invite-code, ban, audit, LLM tool args) are untouched by the diff, consistent with the inventory.

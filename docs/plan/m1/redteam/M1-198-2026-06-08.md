RED-TEAM VERDICT: CLEAN

The diff adds a `ScopeRef.Group` guard to five bot-admin command handlers
(Ban, Invite, Unban, Vouch, ListSources `--all`/`--include-deleted`) so they
return `error.command_dm_only` before resolving the caller, opening a
transaction, or emitting any group-visible reply that would disclose invite
codes, audit data, quarantine state, cross-group admin roles, or
deployment-wide source URLs. This tightens, rather than loosens, the trust
boundary.

Verification of the adversary's primary hypotheses:

- Completeness of the DM-only set. The spec/diff enumerates the DM-only
  bot-admin commands as `/grant-admin`, `/revoke-admin`, `/ban`, `/unban`,
  `/vouch`, `/invite*`, `/quarantine*`, `/audit`, and
  `/list-sources --all/--include-deleted`. The diff touches only five handlers;
  the other four were the obvious gap to probe. Grep confirms the untouched
  handlers already carry the identical guard before any sensitive work:
  `GrantAdminCommandHandler.java:187`, `RevokeAdminCommandHandler.java:190`,
  `QuarantineCommandHandler.java:82`, `AuditCommandHandler.java:72`. No DM-only
  command lacks the guard. (Falsifier — "an admin command leaks in group scope
  because its handler skips the guard" — checked against all 13 handlers in the
  set and found false.)

- Guard ordering / confirm-fork bypass. `BanCommandHandler.java:155` places the
  guard ahead of both the admin gate and the `confirm`-token fork (`:178`), so
  `/ban confirm` in a group also short-circuits to `command_dm_only` rather than
  reaching `takeMatching`/`executeBan`. No partial-execution path survives.

- ListSources base path. The un-flagged group path
  (`ListSourcesCommandHandler.java:169`) returns only group-scoped subscriptions
  via `scopedPath(...,"group",...)`; the deployment-wide `selectAllSources`
  enumeration is reachable only after the group guard (`:133`) and the `isAdmin`
  gate (`:137`). No deployment-URL leak in group scope.

- Disclosure-ordering note (not a finding). The guard fires for all group
  callers, so a non-admin probing `/ban` in a group now sees `command_dm_only`
  instead of `admin_only`. This reveals only that the command is DM-scoped, not
  any privileged state, and the diff's own spec text
  (`docs/design/03-commands.md`, the "✅ DM only" block) commits to exactly this
  behavior. By design, not a gap.

No new input parsing, LLM calls, SQL, or audit-affecting paths are introduced,
so no INJECTION/DOS/AUDIT-EVASION surface is opened.

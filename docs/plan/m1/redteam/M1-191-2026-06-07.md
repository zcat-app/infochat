# Red-team audit: M1-191 (2026-06-07)

Verbatim threat-actor verdict follows.

```
RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL: (advisory notes — none rises to an in-model promise violation)
  - **Latest-wins same-host pin overlap can land a connection on a sibling
    caller's validated IP set.** `PinnedDnsResolver.Provider.pin`
    (infochat-ssrf/src/main/java/app/zcat/infochat/ssrf/PinnedDnsResolver.java:164-170)
    replaces the served address list on every overlapping pin of the same
    canonical host. A guarded call whose DNS lookup runs after a concurrent
    same-host pin connects to the *other* call's validated set, not its own,
    and `PinnedDial.addresses()` (SsrfGuardedHttpClient.java:677) then does
    not contain the actual socket peer. I traced every divergence path: each
    served set entered `PINS` only after passing `IpBlocklist` inside
    `resolveAndValidate` (SsrfGuardedHttpClient.java:485-490), the freshest
    set always wins, and the refcount-decrement arm
    (PinnedDnsResolver.java:229-232) keeps only already-validated addresses
    — so the spec's "the TCP connection lands on a validated IP" and "the IP
    blocklist re-applies each hop" promises hold under all interleavings,
    including a holder releasing while others remain. The residual is
    cosmetic: the javadoc claim "Every address served has passed the
    IpBlocklist in some *still-active* holder's validation"
    (PinnedDnsResolver.java:152-154) is technically false after the latest
    pinner releases first (the served set then belongs to a released holder,
    though it was validated during the overlap window). Worth a doc fix if
    the user cares about the comment's precision; no reachable blocked-IP
    path.
  - **Peer-IP-change watcher baseline vs. actual socket peer.** The spec
    promises "any peer-IP change observed at the socket layer is a hard
    close," but the documented watcher pattern (resolveForWebSocket javadoc,
    SsrfGuardedHttpClient.java:617-633) compares fresh DNS resolutions
    against `PinnedDial.addresses()`, i.e. DNS-vs-DNS, never the actual
    socket peer. Under latest-wins the actual peer may sit outside that
    baseline. This gap is **pre-existing caller-side design, not introduced
    by this diff** (the watcher never reads the socket peer in either the
    old locked design or the new map design), and every divergence outcome
    is either fail-closed (a thrown re-resolve hard-closes) or stays within
    blocklist-validated public IPs. Flagged so the user can decide whether
    the Nostr StreamSource watcher should compare the literal socket peer
    address rather than DNS baselines.
  - **JDK `InetAddress` positive cache sits above the resolver SPI**
    (acknowledged in the new test's own javadoc,
    PinnedDnsResolverConcurrencyTest preamble). Production validation
    resolves via `InetAddress.getAllByName`
    (SsrfGuardedHttpClient.java:228-235), which populates that cache with
    the just-validated answer, so a cache hit during connect serves the
    validated set and the pin is bypassed-but-equivalent. Pre-existing
    architecture, unchanged by this diff; noted only because the pin map is
    not the sole resolution path the connect can take.

Audit summary: the diff replaces the JVM-global `ReentrantLock` + single
pin slot with a per-host refcounted `ConcurrentHashMap` pin map. I checked:
release-on-throw for both the HTTP redirect loop (`finally` at
SsrfGuardedHttpClient.java:404-408) and the WebSocket path (validation
precedes pin install at SsrfGuardedHttpClient.java:610-615, so a policy
throw leaves no stale pin); per-hop release-then-pin preserves the
per-redirect re-resolve + re-blocklist promise; the `PINS.isEmpty()` fast
path cannot skip a caller's own pin (the pin install happens-before the
send's lookup, and the caller's own entry keeps the map non-empty);
idempotent release cannot decrement another holder's refcount
(`AtomicBoolean` CAS, PinnedDnsResolver.java:220-223); map growth is
bounded by in-flight guarded calls; the loopback-permitting blocklist is
test-scope only. The change also removes a real availability defect (a
slow adversarial host serializing the JVM's entire outbound plane),
strengthening the DOS posture rather than weakening it. No promise in
`docs/spec/security.md` §SSRF and outbound connections is undelivered by
this diff.
```

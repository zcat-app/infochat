RED-TEAM VERDICT: CLEAN

No finding rises to the bar of a threat-model commitment the diff fails to
deliver. The diff is a documentation/metric reconcile: it rewrites the SimpleX
adapter's auth-failure narrative (§6.4.1/§6.4.6/§6.4.7, §7.14 runbook, §6.12
catalogue) to match the shipped loopback-IPC reality, removes the
never-incremented adapter.simplex.auth.fail counter (AdapterMetrics.java:190 +
the SIMPLEX_NAME constant) and its registration-only test, and performs ticket
housekeeping (M1-372 deferred onto M1-396). The only Java behavior change is the
deletion of a dead meter and a test that asserted that dead meter's existence.

Commitments checked against docs/spec/security.md:

- Trust boundary 1 (Adapter -> Provider; cryptographic identity anchor, D10):
  unchanged. SimpleX still anchors identity on the cryptographic queue address;
  the SimpleXAdapter.java change is a javadoc block only (diff lines 359-368).

- SSRF / outbound connections (security.md SSRF section): the loopback WebSocket
  to the co-located simplex-chat subprocess is the adapter's own control-plane
  transport, not a Collector feed fetch or Provider /add-source probe. The
  allowlist's loopback block governs ingest/source-fetch egress, not the
  adapter's IPC to a process it spawned. No allowlist surface is widened.

- Health/management loopback posture (trust boundary 6): consistent. The model
  already relies on loopback binding for co-located services (Postgres
  127.0.0.1:5432); a loopback simplex-chat subprocess fits the identical posture
  the spec endorses, not a new exposure.

- Audit log (security.md DB roles / Secrets handling / Quarantine): the removed
  item is a Prometheus metric, not an audit_log row. The spec's audit
  commitments (admin actions, ban, quarantine, re-eval) are untouched. The
  metric catalogue lives in design notes, not spec, so its trim cannot violate a
  spec-level audit commitment. No AUDIT-EVASION.

- DOS (tight reconnect loop): the old prose justified a separate auth-failure
  backoff to avoid a futile retry loop. The new prose routes every close through
  the existing network-failure backoff plus the subprocess supervisor's
  crash-respawn; the diff changes no reconnect code (the auth path never existed
  in code per the ticket's verified-at-source finding), so no new unbounded-loop
  surface is introduced.

- Test integrity: the removed test (simplexAuthFailCounterIsRegisteredOnlyForThe
  SimplexAdapter) asserted only that the dead counter was registered for simplex
  and absent for signal. It pinned no security property -- it pinned the
  existence of a counter no production path increments. Removing it in lockstep
  with the metric is a consistent reconcile, not a weakened security test.

The threat model nowhere commits to SimpleX session-token / cookie
authentication or a SimpleX AUTH_FAILED terminal state; those were design-note
narrative describing behavior the code never implemented. Aligning the docs to
the shipped loopback-IPC transport removes a false claim, not a real defense.

OUT-OF-MODEL:
  - The security posture of the SimpleX loopback transport rests entirely on the
    "co-located subprocess on loopback, adapter-spawned" assumption. If an
    operator ever exposed the simplex-chat ws-port off-loopback (binding it to
    0.0.0.0 or forwarding it), the now-documented "no authentication" property
    would let any host that reaches the port drive the bot's SimpleX identity
    with no credential. This is an operator-misconfiguration / deployment-shape
    concern (parallel to the health-port and Postgres-port loopback caveats the
    spec already carries), not a gap in the diff under audit, and the diff does
    not change the bind. Flagged so the model owner can decide whether to add an
    explicit "ws-port MUST stay loopback" operator commitment alongside the
    existing health/Postgres loopback caveats.

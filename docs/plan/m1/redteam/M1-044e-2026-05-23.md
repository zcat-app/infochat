# Red-team audit — M1-044e

RED-TEAM VERDICT: CLEAN

## Threat-actor session notes (verbatim, prose preamble)

The subagent returned a verbose audit transcript ending in the structured
verdict line. The substantive observations recorded during the audit:

- **Brute-force counter applies to (adapter, contact_id).** Once a contact
  hits the brute-force threshold, even a later-presented VALID invite code
  returns `BruteForceThresholdBreached`. This is per-(adapter, contact_id)
  and the spec explicitly accepts the DOS-against-legitimate-user trade-off
  ("further attempts from that (adapter, contact_id) are rejected without
  checking the code"). Not a finding.

- **Rate-cap-first vs MESSAGE_TOO_LARGE_REPLY.** The spec §Authorization
  model step 1.5 says "no reply (including no fixed ban reply, no fixed
  invite-required reply, no friendly error)". `MESSAGE_TOO_LARGE_REPLY` is
  a friendly error reply, so the rate-cap-first ordering correctly
  suppresses it under flood. Matches spec promise. Closed.

- **`lookupUser` SELECT before ban check is OK.** The spec says banned
  users never reach "any DB query past the ban check" — "past" means after.
  A SELECT before the ban check is fine as long as nothing happens after
  the ban check returns true except the fixed reply. `if (banCheck.isBanned(...))
  { sendReply(...); return; }` — banned user stops there.

- **Pre-banned contact path.** Pre-ban creates a row with `is_banned=true`.
  A pre-banned contact sending a DM: snapshot non-empty → step 2 (unknown
  contact) doesn't fire → step 4 (ban check) fires → ban reply. Correct.

- **Snapshot ↔ ban-check TOCTOU.** A user banned between snapshot read and
  ban check is caught by the fresh ban check. A user banned between
  snapshot read and `inviteCodeConsumer.consume` (step 2, unknown contact)
  could have an attempt row written; narrow race window, not a spec
  violation, snapshot semantics accepted.

- **`InboundContext.setAdapterName` before rate-cap.** Just sets a string
  on a request-scoped CDI bean. No leak; no observable side effect for
  dropped inbound.

- **`@NonNull String body` on consume.** `parseUuid(body)` would NPE on
  null, but callers must pass non-null per contract; `normalize(raw)`
  never returns null (returns `out.toString().trim()`). Contract holds.

- **Brute-force-check-before-audit-insert.** When `attempts >= threshold`,
  the code short-circuits to `BruteForceThresholdBreached` without
  consuming. Below threshold but invalid → `Rejected` with attempt insert.
  Counter management is correct.

## Conclusion

All four M1-044b red-team findings (AUTH-BYPASS, DOS, INFO-LEAK,
AUDIT-EVASION) close cleanly. No new gaps against the spec. No
out-of-model concerns surfaced.

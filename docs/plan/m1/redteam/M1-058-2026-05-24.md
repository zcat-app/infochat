# Red-team audit — M1-058 (2026-05-24)

RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: INJECTION
    SEVERITY: low
    PROMISE: From threat model §Secrets handling: "Contact IDs are logged in redacted form (prefix + ellipsis + suffix) outside the audit log. User-content logging. `chat_memory` content, `saved_post` bodies and annotations, and the bodies of inbound chat-mode messages never appear in non-audit logs, at any log level (decision D37). Stage events, request IDs, scope IDs, and counts are loggable; the prose itself is not." Combined with the diff's own contract that the canonical `ADMIN-NOTIFY key=... error=... message=...` line is "pinned for operator log scraping" (ThrottledAdminNotifier.java:1525-1527), the format is a security-relevant interface whose integrity the notifier is responsible for.
    GAP: `ThrottledAdminNotifier.notifyOnce` at `infochat-collector/src/main/java/app/zcat/infochat/collector/notifier/ThrottledAdminNotifier.java:1527` formats `key`, `errorClass`, and `message` directly into the WARN log line with no newline/CR scrubbing, no length cap, and no character allowlist. The method signature accepts any `@NonNull String` for all three fields. The corresponding columns in V16 (`notification_key`, `error_class` TEXT) also have no `CHECK` constraint to bound length or forbid control characters at the DB layer.
    REPRO: A future caller — e.g., the Stage 1 infrastructure-failure path catching a parser exception whose `getMessage()` includes attacker-influenced bytes from a malformed feed body, or the D42 fetcher-failure path including a server-returned response excerpt — passes that text into `message` (or `errorClass`). A line like `LOG.warnf("ADMIN-NOTIFY key=%s error=%s message=%s", "k", "EC", "real-detail\nADMIN-NOTIFY key=spoofed error=spoofed message=fake")` writes two lines to the operator's log scrape: one genuine, one attacker-forged. Operator alerts driven by `grep ADMIN-NOTIFY` then see fabricated entries (or, with a long enough body, real lines are flooded out). The diff has no current callers, so this is currently unreachable; the gap manifests as soon as the next ticket wires `notifyOnce` to any caller that forwards externally-influenced text (exception messages, feed-derived bodies, URLs). The persisted `notification_key` is also unbounded, so a high-cardinality attacker-influenced key inflates the monotonic table without bound — spec acknowledges DBA TRUNCATE as the only recovery.
    SUGGESTED-FIX-CLASS: input-sanitization

OUT-OF-MODEL:
  - `SQLException` inside `notifyOnce` returns `NotifyOutcome.SUPPRESSED` and emits a `LOG.warnf` line that does NOT match the canonical `ADMIN-NOTIFY key=… error=… message=…` pattern (`ThrottledAdminNotifier.java:1545`). An operator-scrape rule keyed to `ADMIN-NOTIFY` would miss the original failure entirely when the DB is degraded. This is a reliability/observability concern (not in the documented threat model) — the spec acknowledges "the notifier IS the failure-visibility path" in the comment but does not commit to a degraded-DB fallback format.
  - The migration grants `SELECT, INSERT, UPDATE` only to `infochat_collector` and `SELECT` to `infochat_provider`. Several Provider-side failure paths in §Failure handling (compression failure, chat-mode LLM unreachable, summarizer unreachable) are spec-listed but cannot call `notifyOnce` from the Provider role because they lack `INSERT/UPDATE`. Spec does not explicitly require Provider-side admin notification to flow through this same table, so this is a feature-completeness concern rather than a spec violation.
  - Relevant files: `infochat-collector/src/main/java/app/zcat/infochat/collector/notifier/ThrottledAdminNotifier.java`, `infochat-core/src/main/resources/db/migration/V16__admin_notification_state.sql`.

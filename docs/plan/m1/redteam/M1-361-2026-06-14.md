RED-TEAM VERDICT: CLEAN

Audit scope: M1-361 splits the audit-verb closed set into a sealed
AuditVerb supertype permitting AuditAction (application-writable verbs)
and ProcedureOnlyAction (verbs written ONLY by SECURITY DEFINER stored
procedures / migrations), and renames the config-baked
STARTUP_RELEASE_ON_STAGE2_FAILURE_TRUE verb to the value-agnostic
STARTUP_RELEASE_ON_STAGE2_FAILURE (moving the observed config value into
details_json).

Threat-model promises checked and found delivered:

1. Audit-before-effect carve-out (security.md §Quarantine workflow,
   §User ban: APPROVE_QUARANTINE / REJECT_QUARANTINE / UNBAN_PREBAN_DELETE
   are written only by the SECURITY DEFINER procedures, never by an
   arbitrary Java caller). The diff STRENGTHENS this: RedactionHook.AuditRow.action
   is typed AuditAction (RedactionHook.java:91, builder action(AuditAction)
   at :149), and AuditLogWriter.write consumes AuditRow, so a Java caller
   now physically cannot route a ProcedureOnlyAction through the writer —
   the guarantee moves from comment-policing to compile-time refusal.
   Verified UnbanCommandHandler.java references UNBAN_PREBAN_DELETE only in
   comments; the row is written by the V5 delete_preban_user procedure in
   SQL, so the move to ProcedureOnlyAction breaks nothing and removes a
   Java path to forge that verb.

2. /audit bot-admin-only gate (security.md §Authorization model step 7;
   DB roles "/audit reads through audit_log_view"). Unchanged by the diff:
   AuditCommandHandler.java:86 still rejects non-admin, queries still hit
   audit_log_view (:168, :192), AUDIT_READ row still written (:132).

3. No audit verb dropped from the filterable/validated set
   (AUDIT-EVASION check). The /audit --action filter now resolves over the
   FULL catalogue via AuditVerb.values() (AuditCommandHandler.java:58, :99)
   and AuditVerb.valueOf, which unions AuditAction + ProcedureOnlyAction
   (AuditVerb.java:43-46, :58-65). The procedure-only verbs an admin must
   be able to filter for (APPROVE_QUARANTINE etc.) remain in ACCEPTED_ACTIONS
   and remain accepted by the parse-boundary validation. No verb became
   unfilterable or unvalidatable.

4. SQL injection on /audit filters (INJECTION check). --action is validated
   against AuditVerb.valueOf before use (AuditCommandHandler.java:99) AND
   bound as a parameter via setString (:163, bindParams :224-235); --actor
   is resolved to a UUID or a never-matching sentinel UUID (:111-115) and
   bound. The catch at :100 catches only IllegalArgumentException, which
   AuditVerb.valueOf throws explicitly (AuditVerb.java:64) — no uncaught
   exception / stack-trace leak introduced.

5. Verb rename consistency. STARTUP_RELEASE_ON_STAGE2_FAILURE is renamed
   consistently across all three code references (AuditAction.java,
   StartupReleaseOnStage2FailureWarn.java, Stage2VerdictHandler.java javadoc);
   remaining old-name occurrences are docs/design and ticket/plan files
   only. The verb is application-written via AuditLogWriter; there is no SQL
   CHECK on audit_log.action and no migration writes it (V5 §2.1.8 — the
   closure is application-layer), so no DB-side cross-check breaks and the
   boot-time posture audit row is still emitted.

6. details_json additions are non-injectable: profileLabel is run through
   JsonEscaper.escape (StartupReleaseOnStage2FailureWarn.java) and
   release_on_stage2_failure is a Java boolean literal, not user input. The
   posture value is intentionally audit-visible (it records observed config
   state) — no INFO-LEAK.

Conclusion: the diff is a refactor that preserves every audit, authorization,
and injection-defense promise in the threat model and tightens the
audit-before-effect guarantee from convention to compiler enforcement. No
gap between promise and delivery.

Scope note: M1-567 adds operator-tier migration tooling — prod/scripts/pack.sh
(host-clone bundler), prod/scripts/restore.sh (host-clone reconstructor), a
JUnit test that pins restore.sh's fail-loud precondition gates
(RestoreWiringTest.java), and docs (SETUP_GUIDE.md, docs/design/07-deployment.md
§7.10.1). No new Provider/Collector runtime code path is introduced: the only
non-doc, non-test artifacts are two shell scripts, and the only code reference to
them is the test (grep of *.java, *.sh, *.yml, *.properties confirms nothing in
the running system invokes pack.sh/restore.sh). The scripts are invoked manually
by the operator on the host; there is no path from a messaging adapter, a feed,
or the LLM to them. Per security.md §Threat model, operator-set config and
operator actions are trusted; the diff adds no adversary-reachable surface.

Checked against every threat-model commitment that touches the data these
scripts handle, and found no gap:

- INFO-LEAK / §Secrets handling. The scripts never echo secret values. The DB
  password is used only single-quoted inside an in-container `sh -c
  'PGPASSWORD="$INFOCHAT_DB_PASSWORD" ...'` (pack.sh:486-488, restore.sh:847-849,
  858-859) — expanded in the container from the compose --env-file, never on the
  host stdout. secrets.env is read via read_dotenv_value (never `source`d) — the
  M1-389/M1-397 discipline, verbatim from backup.sh. Every FAIL message names
  only file paths / a Docker volume name / a data-dir path / a base-URL
  (restore.sh:803, 887) — none of which is a secret. The bundle carrying all
  secrets in plaintext is consistent with the documented posture (written 0600
  under umask 077, loud WARNING block, encryption-for-transfer is the operator's
  responsibility per D34 and security.md §"What's intentionally NOT in v1":
  "DB-at-rest encryption — operator's responsibility").

- §DB roles / injection-containment. pg_dump/pg_restore run as `infochat`, which
  docker/postgres-init.sh:31 confirms is the DB OWNER role (LOGIN CREATEROLE, NOT
  superuser) — the operator/owner tier the threat model authorizes for full DB
  read incl. raw audit_log and raw quarantine originals. `pg_restore --no-owner`
  (restore.sh:848) assigns object ownership to `infochat`, never to a service
  role, so infochat_collector/infochat_provider never own objects and remain
  bound by the append-only trigger and their explicit grants. The core
  containment invariant ("a SQL-injection bug in the Provider cannot read
  unredacted audit rows or raw quarantine originals") relies on DEFAULT-DENY
  (absence of a grant), which a restore cannot accidentally add; any grant that
  fails to apply removes access, never adds it — fail-safe.

- PERM-ESCAL. The clone faithfully restores the users table (is_admin/is_banned
  unchanged) and the SimpleX single-use claim gate stays satisfied (the restored
  (simplex, is_admin=true) row keeps the token spent), consistent with §Per-
  adapter admin threat profile. restore.sh deliberately does NOT run
  6b-simplex-provision.sh (restore.sh:946-947) so no NEW SimpleX identity is
  minted. No path grants a service role or a chat user more than it had.

- AUDIT-EVASION. The audit log is dumped and restored faithfully by the owner;
  no app-tier write path is bypassed and no operation the threat model requires
  to be audit-logged is hidden. security.md commits to no audit row for a
  host-migration operator action, so none is owed.

- DOS. One-shot operator scripts; the only loops are bounded by
  OLLAMA_WAIT_TIMEOUT / COLLECTOR_WAIT_TIMEOUT. No adversary trigger.

OUT-OF-MODEL:
  - Tar-slip / arbitrary-file-overwrite on a tampered bundle. restore.sh:828
    extracts the bundle's identities.tgz with `tar -C / -xzpf`, reconstructing
    entries relative to the target host's root filesystem. The same-absolute-path
    precondition gate (restore.sh:797-809) only verifies that each configured
    INFOCHAT_<NAME>_DATA_DIR APPEARS as an entry in the tar; it does NOT restrict
    the archive to those entries, nor reject absolute or `../` traversal members.
    A hand-crafted/tampered bundle carrying extra members (e.g. `home/<user>/
    .ssh/...`, `etc/...`, a `../`-escaping path) would therefore be written onto
    the target with the restoring user's privileges — a classic tar-slip
    primitive. This is OUT-OF-MODEL: it requires supplying a malicious bundle,
    and bundle integrity depends on operator storage + transfer, which security.md
    §Threat model places out of scope ("supply-chain attacks on operator
    infrastructure ... out of scope"; TLS/MITM assumed handled; the operator is
    explicitly told to encrypt the bundle for transfer). pack.sh (pack.sh:519) is
    unaffected — it tars a trusted source. Flagged so the user can decide whether
    to extend the threat model to cover migration-bundle integrity (e.g. reject
    absolute/`..`/out-of-allowlist tar entries before the `-C /` extraction, or
    require a detached signature on the bundle).

(actorContactId, actorAdapter) to the CHAT_MODE audit row in
ChatAgent.writeAuditRow, sourced from the request-scoped InboundContext,
plus a unit test pinning the new attribution. This is a pure
audit-coverage improvement; it weakens no threat-model commitment.

Checks performed:

- INJECTION (SQL/JSON): The two new values are bound as PreparedStatement
  parameters (AuditLogWriter.write positions 2 and 3, both via
  setNullableString), never concatenated into SQL. The details_json
  string-concat path is unchanged and still routes scope_kind/scope_id
  through JsonEscaper.escape. No new injection surface.

- AUDIT-EVASION: The row is written by the system before the LLM call
  (ChatAgent.java:228), not authored by the actor. The added fields are
  the adapter-resolved cryptographic contact id and adapter name — the
  actor's own identity, which the actor cannot forge (set by
  InboundRouter.onMessage, not from message body). The change increases
  audit attribution rather than removing or exposing it.

- INFO-LEAK / D37: The added values are identity (contact id + adapter),
  not user-authored prose; consistent with §Secrets handling ("audit log
  records intent — command name, actor, scope, target — not user-authored
  prose"). Full contact ids in the raw audit_log are by-design; the
  Provider reads through the redacted audit_log_view (§DB roles), which
  this diff does not touch. Every row still passes RedactionHook.redact
  before INSERT.

- Trust boundary: senderContactId is the adapter-assigned per-connection
  id / ACI (§Trust boundaries 1), not the self-asserted profile address,
  so it is a trusted authorization-grade identity — appropriate as the
  audit actor key.

No promise in the threat model is left undelivered by this diff.

RED-TEAM VERDICT: CLEAN

The diff adds an orphan-rescue branch to Stage1Worker.processKey: a post
left at (status='RAW', stage1_done=TRUE, stage1_flagged=TRUE,
stage2_done=FALSE) — the state a crash or a failed Stage-2 verdict write
between the stage1_done commit and Stage 2 completion leaves behind — is
routed through the existing, spec-sanctioned Stage2VerdictHandler.apply(
INFRA_FAILURE) path instead of being stranded in RAW forever.

Audit against the threat model commitments:

1. §Failure handling — "Stage 2 infrastructure failure (... unparseable
   ... after retry) → release as READY with the Stage 1 redactions
   retained, mark the post for re-evaluation, notify admin via the
   throttled channel. A profile-driven flag lets production profiles
   invert this default and keep the post quarantined." The rescue reuses
   the canonical handler verbatim: fail-open sets stage2_done=TRUE,
   stage2_failed=TRUE, status stays RAW (the release path), fail-closed
   sets status='QUARANTINED'. stage2_failed=TRUE feeds the re-evaluation
   job (§Re-evaluation job item 1), which re-judges with a healthy
   judge. The WARN carries Stage2VerdictHandler.ERROR_CLASS_STAGE2_INFRA_FAILURE,
   the same string the throttled admin notifier coalesces on for a
   genuine outage. No commitment is re-implemented or weakened; the
   orphan inherits the existing path's behavior.

2. §Ingest pipeline — "release with Stage 1 redactions retained" /
   "[REDACTED:<id>]" placeholder. Verified load-bearing: Stage1Pipeline.
   handleSuccess (infochat-collector/.../eval/stage1/Stage1Pipeline.java:423-428)
   commits the quarantine-row inserts AND the redacted-body UPDATE (which
   sets stage1_done=TRUE and stage1_flagged=TRUE) in ONE transaction. So
   the orphan bitmap atomically implies post.body already holds the
   redaction placeholders and the quarantine rows exist. The crash that
   creates the orphan happens strictly after that commit, so the fail-open
   rescue release cannot expose unredacted (pre-Stage-2) content.

3. The branch-guard comment's claim ("stage1_flagged && !stage2_done
   implies status='RAW'; the only QUARANTINED posts with stage2_done=FALSE
   are the Stage-1 fail-closed paths, which leave stage1_flagged=FALSE")
   is verified against Stage1Pipeline: the watchdog / match-overflow /
   sanitizer-exception fail-closed writers (updatePostQuarantined,
   Stage1Pipeline.java:601-614) set status='QUARANTINED' but never set
   stage1_flagged, so those rows are excluded from the rescue. No
   non-RAW post is wrongly transitioned.

4. Idempotency: after the rescue stage2_done=TRUE, so a repeated worker
   pass (rehydrator or stale-RAW re-emit) no longer matches the orphan
   guard and short-circuits at the stage1_done skip. The rescue inserts
   no quarantine rows, so no duplicate-quarantine side effect. A
   concurrent double-delivery would at worst re-run an idempotent UPDATE
   and double-increment a non-security status counter; no quarantine,
   audit, or release double-effect.

5. DOS: the change REMOVES the pre-existing condition the ticket targets
   (orphan re-selected by reEmitStaleRaw every pass forever). It
   introduces no new unbounded loop; the stale-RAW sweep remains
   LIMIT-bounded and is not adversary-amplifiable.

No log-injection (only post UUIDs are logged, never the body — consistent
with §Secrets handling — User content in exceptions). No SQL injection
(all statements parameterized). No authorization, ban, invite, or
audit-write surface is touched. No threat-model commitment is left
undelivered by the diff.

OUT-OF-MODEL:
  - Under the fail-open posture (infochat.security.release-on-stage2-failure
    =true, the inherited base default), the orphan rescue makes a
    Stage-1-flagged post user-visible (with Stage 1 redactions) BEFORE any
    Stage 2 LLM judge has ever seen it, relying on the asynchronous
    re-evaluation job to eventually produce the real verdict. An adversary
    controlling a feed can craft Stage-1-flagging content, but cannot
    control whether the Collector crashes in the narrow window between the
    stage1_done commit and Stage 2 — so the trigger is not
    adversary-reachable. The resulting exposure window is identical in
    nature to the Stage-2-infra-failure degraded mode that §Failure
    handling and §"A complete LLM outage degrades quality, not safety"
    already accept, and re-eval supplies the eventual Stage 2 verdict.
    Flagged here only so the user can decide whether the crash-orphan
    case warrants a synchronous Stage-2 re-run (the judge is, after all,
    typically healthy when the rescue fires) rather than the asynchronous
    re-eval deferral the diff chose. This is a defense-in-depth design
    choice, not a spec violation.

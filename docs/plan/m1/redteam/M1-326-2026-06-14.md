RED-TEAM VERDICT: CLEAN

No findings. The diff is a hardening change that tightens an existing
trust boundary rather than relaxing one.

Summary of the audit:

- Scope of the diff: NostrRelayConnection's EVENT-handling arm in
  handleFrame is changed so that markProductive() (which fires
  RelayHealthTracker.recordSuccess and resets reconnect backoff) is
  credited only AFTER the event crosses the signature trust boundary.
  The eventSink type changes from Consumer<NostrEvent> to
  Predicate<NostrEvent>; the sink is NostrStreamSource::enqueueInbound,
  which runs verifier.verify() and returns false on a forged/invalid
  signature.

- Threat-model alignment: this closes a gap against
  architecture.md §Per-relay degradation and security.md
  §Per-source trust boundaries (D38). Before the change a relay could
  stream well-framed but signature-invalid EVENTs, score "productive,"
  reset its backoff every connect, and never enter cooldown — defeating
  the per-relay mark-bad / all-relays-bad / terminal-failed safety
  valve that bounds outbound connection cost. The change makes the
  per-relay degradation path reachable for a signature-flooding relay,
  which is the spec commitment. No DoS surface is opened: verify() was
  already invoked on this path before the change (the prior Consumer
  return value was simply discarded), so there is no new per-event cost.

- Trust-boundary ordering preserved: enqueueInbound still enforces
  signature verification -> kind allowlist -> dedup -> outbox write
  (NostrStreamSource.java:186-215), matching the spec's load-bearing
  ordering. The diff does not reorder or weaken it; an unverified event
  of any kind is still dropped at the signature step before reaching the
  kind filter.

- Liveness credit preserved: the EOSE arm still credits productivity
  unconditionally and independently of the sink
  (NostrRelayConnection.java:345). A healthy relay that sends EOSE after
  its initial dump is therefore never falsely marked unproductive, even
  if its EVENTs happen to be duplicates (cross-relay one-event-many-
  relays design), disallowed kinds, or overflow the bounded inbound
  queue. enqueueInbound returning false in those non-signature cases
  withholds only the EVENT-arm credit, not the EOSE-arm credit — a
  defense-in-depth posture consistent with "a spamming relay MUST be
  marked bad" (architecture.md:273-278), not a gap.

- Test changes are mechanical: NostrSsrfTest:148 and NostrSsrfIT:105
  swap a void-body `event -> {}` Consumer lambda for an `event -> true`
  Predicate to satisfy the signature change. These are SSRF tests whose
  assertions do not depend on the sink return value or on productivity
  state (newConnection uses a no-op RelayHealthTracker); no security
  assertion is weakened, disabled, or removed. The new
  NostrProductivityAfterVerifyTest adds positive coverage that a
  signature-invalid flood leaves productiveSinceConnect false and the
  primed cooldown intact.

- No authorization, ban-handling, audit-log, invite-code, admin-tier,
  LLM-tool-surface, or per-(user,scope) isolation surface is touched by
  the diff (consistent with the sensitive-surface inventory). The
  collector ingest path here is read-only at the Nostr protocol layer;
  no key-handling, signing, or publish path is introduced.

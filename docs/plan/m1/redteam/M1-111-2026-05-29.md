  legacy `registration_state='group_only'` rows to `'invited'` — the

  a non-interacting state. The adversary is correct that `group_only`
  rows were an attacker-reachable tier (minted by the now-removed group

  `'invited'` grants DM + full group access D47 promises is reachable

  context) rated this `high` on an "upgrade from a pre-D47 deployment"
  premise. M1 is greenfield (CLAUDE.md: "there is no prior version to be

  the authors anticipated non-zero rows. Real exploitability today is
  lower than `high`, but the migration encodes a security decision worth
  fixing before it can ever bite: prefer deleting `group_only` rows (so
  the contact re-enters through the invite gate) over promoting them.

FINDINGS:

  - CATEGORY: AUTH-BYPASS
    SEVERITY: high
    PROMISE: §Invite-code registration / §"What's intentionally NOT in v1": "Group interaction requires prior DM registration (D47). A user must have `registration_state IN ('invited', 'vouched')` to interact with the bot in any group... The DM invite gate is the universal registration path — there is no group-side registration bypass." And: "Group auto-registration. Removed by D47... only users who passed the DM invite gate can interact in groups. This is a hardening decision... the auto-registration path is permanently closed."
    GAP: `infochat-core/src/main/resources/db/migration/V27__d47_remove_group_only.sql:21-25` runs `UPDATE users SET registration_state = 'invited' WHERE registration_state = 'group_only'`. Every legacy row that the now-removed group auto-registration path minted for an untrusted contact (a user who was auto-created on a group `@mention` and never presented an admin-issued invite) is promoted to `'invited'` — the exact state that signifies "passed the DM invite gate." Downstream, `InboundRouter.java:347-356` (new step 3) drops a group sender only when `snapshot.isEmpty() || REGISTRATION_STATE_PREBAN.equals(...)`; `'invited'` passes. The old step-4.7 DM-gate that previously turned away `group_only` DM contacts with `error.invite.required` is deleted (`InboundRouter.java:390-405` removed). Step 2 (DM invite gate) fires only when no users row exists (`InboundRouter.java:318-347`), and these rows exist. Net effect: a contact who never received an invite is migrated into the post-invite-success state and gains both full DM access and full group interaction once their (temporary) probation window elapses.
    REPRO: 1) On a pre-D47 deployment, an attacker `@mention`s the bot in any group — the old auto-register path mints a `users` row with `registration_state='group_only'`, no invite ever required. 2) Operator upgrades and V27 runs, flipping that row to `'invited'`. 3) The attacker now DMs the bot: step 2 finds an existing row (skips the invite gate), there is no DM-gate carve-out anymore, ban/probation pass once probation elapses, and the attacker reaches command dispatch and chat mode as a fully registered user. They also interact freely in groups (step 3 no longer drops them). They obtained the access that D47 promised is reachable only via an admin-issued invite. The safe migration would delete `group_only` rows (forcing re-entry through the invite gate) or move them to a non-interacting state, not promote them to `'invited'`.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

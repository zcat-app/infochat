RED-TEAM VERDICT: FINDINGS

Prior-round disposition (verified against the current diff, not assumed):

  Prior finding 1 (INJECTION, medium) — CLOSED. DisplayHeadline.of
  (infochat-provider/src/main/java/app/zcat/infochat/provider/render/DisplayHeadline.java:217)
  is `truncate(sanitize(flattenToOneLine(source)))`. Flattening now precedes the
  sanitizer, so the bytes the closed-list pass inspects are the bytes delivered.
  I re-derived the evasion directly: `\R` matches U+0085/U+2028/U+2029 (the three
  line boundaries `\s` misses and that LlmOutputSanitizer.isTokenSeparator
  (LlmOutputSanitizer.java:392-394) and canonicalizeForMatching
  (LlmOutputSanitizer.java:618-621) both leave intact), the run is REPLACED with a
  space rather than deleted, and the only post-sanitize transform is `truncate`,
  which removes a suffix and appends the ellipsis — it cannot splice two
  fragments, cannot strip a leading prefix, and cannot complete a multi-word or
  flag-bearing closed-list entry. Delivered text is a prefix of sanitize(input),
  so every full token in it was seen and adjudicated by the sanitizer.

  Prior finding 2 (DOS, low) — CLOSED for the path the finding named.
  headlineSource (DisplayHeadline.java:239-241) bounds the body at
  BODY_SCAN_LIMIT = 2000 BEFORE the sanitizer is handed it, and
  DisplayHeadlineTest.overLongBodyIsBoundedBeforeItReachesTheSanitizer pins the
  bound on the sanitizer's INPUT via a recording subclass, not on its output.
  I checked that the pre-bound cannot itself be turned into an escape: a
  closed-list token straddling index 2000 is only half-present in the sanitize
  input and therefore only half-present in the delivered prefix, and text past
  2000 is discarded outright so a shrinking flag-entry redaction cannot pull it
  into the 200-char display window.

    PROMISE: docs/spec/security.md §LLM output sanitizer — "the group-visible
              echo surfaces (`/saved` reply, `/summary`, and the degraded group
              digest) are additionally passed through the closed-list
              `LlmOutputSanitizer` at **render**, where a title or tag whose
              canonical form is a privileged command renders as
              `[redacted command]`", and §"Canonical-form matching" — the pass
              matches "the **canonical** form of the candidate output ... which
              is the same representation the deterministic command parser
              consumes". Both commitments hold only if no transform runs between
              the sanitizer and delivery; that ordering is the control the round-1
              INJECTION finding was about.
    GAP: The remediation reordered the pipeline to flatten -> sanitize -> truncate
         (DisplayHeadline.java:25-37 and :217) but the diff simultaneously ADDS a
         javadoc line at one of the three call sites asserting the opposite,
         previously-vulnerable order as the design intent:
         infochat-provider/src/main/java/app/zcat/infochat/provider/command/ClusterBlockRenderer.java:46-47
         — "Deriving the headline is a deterministic pure function (sanitize,
         then flatten, then bound)". That is a direct contradiction of
         DisplayHeadline.java:25 ("Order is load-bearing: flatten -> sanitize ->
         truncate") in the same diff, and it is stated in the file that carries
         the M1-675 group-broadcast rationale a maintainer would read first. The
         security argument for the ordering — that the sanitizer's token
         separators are ASCII-only and its canonical form preserves
         U+0085/U+2028/U+2029, so a post-sanitize whitespace rewrite manufactures
         a dispatchable token the sanitizer never adjudicated and never audited —
         appears only in DisplayHeadline; the caller's javadoc records the wrong
         order with no WHY at all, so a reader reconciling the two has nothing to
         adjudicate with.
    REPRO: Not reachable against the code as it stands today — the ordering is
           behaviourally correct and pinned by
           DisplayHeadlineTest.unicodeSeparatorInsideAClosedListEntryIsRedactedNotRewrittenIntoACommand
           and ...unicodeSeparatorInsideAFlagEntryIsRedacted, so a reorder fails
           `mvn verify`. The exposure is a regression channel, not a live attack:
           a future change that "restores" the order this javadoc documents —
           e.g. moving flattenToOneLine into truncate, or applying it at the
           renderer after DisplayHeadline.of returns, which the caller's own
           javadoc describes as correct — re-arms the round-1 attack verbatim:
           publish a post whose headline text is

    remediation bounds the body (BODY_SCAN_LIMIT) but applies no bound to the
    title, on the premise stated at DisplayHeadline.java:62-63 that
    "`post.title` is capped at `IngestTextNormalizer.TITLE_MAX_LENGTH` (200) at

    (a) it is not adversary-reachable — PostPersister.normalizeTitle
    (infochat-collector/.../outbox/PostPersister.java:282-290) is the sole `post`

    every new title at 200, so no publisher can mint an over-cap title today;
    (b) it is not introduced by this diff — the pre-change call site was
    `llmOutputSanitizer.sanitize(first.title())`, equally unbounded. The residual
    is legacy pre-M1-693 rows only. Flagged so the user can decide whether the
    stale premise in the javadoc is worth correcting, since it is the stated
    justification for an asymmetric bound.
  - Self-inflicted display suppression via the Stage 1 placeholder guard.
    stage1PlaceholderSafeCut (DisplayHeadline.java:317-324) returns the opener
    index when no closing `]` is found (`close < 0 || close >= cut ? start : cut`),
    so a body beginning with a bare, never-closed `[REDACTED:` collapses the whole
    headline to `…`. That is one publisher shrinking their own post's headline —
    no other author's bytes are reachable, the url and uid operands still render,

    quirk, not a content-suppression vector of the kind the threat model's
    §"Flag position mirrors the parser's own scan" reserves the narrow sanitize
    unit against. Noted only so the behaviour is on the record.

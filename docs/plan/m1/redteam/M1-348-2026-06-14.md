RED-TEAM VERDICT: CLEAN

Audited diff M1-348 (base 579fb46c^, head 579fb46c) against the threat
model in docs/spec/security.md.

Scope of the change: DefaultRedactionHook.redact now adds a fail-closed
post-condition — after the Redactor catalogue pass and the existing
timeout-sentinel substitution, if the redacted details_json is not
JSON-shaped (per the new structural isJsonShaped heuristic) the value is
replaced with the REDACTED_FIELD_JSONB sentinel before it can reach
AuditLogWriter's `?::jsonb` cast. Plus the matching unit test and the
ticket/STATUS bookkeeping.

Threat-model commitments examined and why each holds:

- §Secrets handling ("Audit-log writes pass through a redaction hook ...
  The redactor is fail-closed on regex timeout ... a timed-out match
  treats the whole field as redacted rather than emitting it raw").
  The change strictly TIGHTENS this promise: the only new assignment is
  toward the sentinel (more redaction / fail-closed), never away from it.
  isJsonShaped can never cause a previously-redacted secret to be emitted
  raw — it only forces the whole field to the sentinel. No weakening of
  the redaction catalogue, no new emit-raw path.

- The unchanged `redacted.equals(detailsJson)` short-circuit (return the
  original row) still fires only when redaction produced no change, i.e.
  no secret was present to redact. The new check is correctly placed
  before this short-circuit, so a non-JSON value that the Redactor left
  unchanged is forced to the sentinel rather than passing through.

- AUDIT-EVASION considered: substituting the sentinel wipes only the
  details_json column. The audit row's intent-bearing columns
  (actor_user_id, actor_contact_id, action, target_kind, target_id,
  target_contact_id, scope_id, request_id) are untouched and still
  written. Per §Secrets handling the audit log records "intent (command
  name, actor, scope, target), not user-authored prose" — those live in
  the dedicated columns, not details_json, so the core audit trail is
  preserved. details_json is built by deterministic internal code (e.g.
  restored_group_admin UUID lists), not directly attacker-controlled, so
  there is no actor-driven path to force a non-JSON details_json and
  thereby suppress audit content.

- INJECTION considered: details_json still binds via PreparedStatement
  with the server-side `?::jsonb` cast (AuditLogWriter line 60/115); the
  heuristic explicitly defers the authoritative parse to that cast. No
  string concatenation into SQL is introduced.

- DOS considered: isJsonShaped is a single linear O(n) scan with no
  backtracking and no regex; it adds bounded cost on a path the Redactor
  watchdog already governs. No new unbounded loop or event-loop block.

- False-fail direction (a valid bare-scalar JSONB document being forced
  to the sentinel) is a fail-closed over-redaction, not an info-leak, and
  all code-built details_json values are objects; it does not break any
  threat-model commitment.

No gap found between a threat-model promise and the delivered diff.

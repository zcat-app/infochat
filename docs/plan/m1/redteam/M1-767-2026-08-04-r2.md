          `SystemLlmBudget.java:65-68` instructs the reader to "read them as a

          What is NOT named is the M1-763 slot-window cancellation.
          `DigestWorker.java:243-276`: on TimeoutException the worker degrades the
          digest and DISCARDS the render's result, but the render thread keeps
          running — the code says so at `DigestWorker.java:265-272` ("each remaining
          call in the render fails fast without opening a socket ... The render LOOP
          still runs to completion ... and its result is discarded here"). So every
          draw site still fires on a cancelled render: `DigestRenderer.java:377`
          `recordCalls(shownClusters.size())`, `DigestRenderer.java:393`
          `recordCalls(leadProse.size())`, and `DigestRenderer.java:455`
          `recordCalls(1)` per section. Every post-interrupt cluster is charged
          although, by M1-763's own design, it opened no socket. Magnitude: bounded by
          `infochat.summary.cluster-cap` (`DigestPostCollector.java:35`, default 200),
          so up to ~200 summarizer draws + up to 3 lead draws + up to 8 roll-up draws
          — roughly 7% of the shipped 3000-call ceiling charged for ONE render whose
          output nobody received. That is larger than any named leg, and unlike them
          its size is set by post volume rather than by nominal render cost. This is
          also the only over-count leg that fires while the endpoint is UP and
          answering, so the operator guidance derived from the named legs
          (`application.properties`: "It over-counts during an LLM outage") does not
          warn about it.
    REPRO: 1) The configured LLM endpoint answers every request successfully but
            slowly — latency under `read-timeout`, so no transport failure occurs and
            the circuit breaker never trips (§Failure handling: only transport
            failures trip it). A compromised or throttled remote provider is in-model
            per §Trust boundaries item 9; a saturated local backend does it equally

            drains on wall-clock. The operator's only recovery levers are a process

            transient latency event is thereby converted into a day-long,
            deployment-wide degradation of the very surface the budget exists to
            protect, and the code comment a future reader consults asserts the error
            legs are all named.

  - CATEGORY: DOS
    SEVERITY: medium
    PROMISE: security.md §Rate limiting — "**Per-group LLM rate (D47)** — a separate
              sub-bucket per approved group bounding LLM-triggering operations (chat
              replies + on-demand `/summary` + `/retry` re-rolls) across all group
              members. The per-user LLM cap fires first; the per-group cap is the
              backstop for groups with many active members. ... Periodic digests do
              NOT count against user-initiated per-group LLM budget (they are
              system-initiated; the aggregate system LLM budget is the backstop for
              digest cost)." The spec assigns `/retry` re-rolls to the per-user and
              per-group buckets and the aggregate budget to SYSTEM-initiated digest
              cost; the whole §Rate limiting section is built on per-consumer bounds.
    GAP: The load-bearing justification for the draw altitude is FALSE.
          `SystemLlmBudget.java:33-44` states: "These draw sites live in
          `DigestRenderer.renderSections` because that is the only
          scheduled-route-only entry point (`DigestWorker.executeSlot` is its sole
          caller) ... a draw moved down to where the provider call actually happens
          would meter the user-initiated routes into this system-initiated budget and
          break the split `LlmRateCap` (M1-183) and the D47 per-group sub-bucket
          exist to maintain. Correct SCOPE is bought here at the price of an inexact
          COUNT." `renderSections` is not scheduled-route-only.
          `DigestRetryService.java:220-234` (`fallbackRerun`) calls
          `digestWorker.execute(slot)` on the `/retry --digest` command path
          (`RetryCommandHandler.java:161`, `:559`), and `execute` →
          `executeSlot` (`DigestWorker.java:172`) → `renderSections`
          (`DigestWorker.java:240`). The SAME source file already documents this at
          `DigestRenderer.java:143-155` — "TWO ROUTES reach this render ... The
          USER-INITIATED route is `/retry --digest`, which reaches the very same
          render via `DigestRetryService.fallbackRerun` → `DigestWorker.execute`" —
          so the new javadoc contradicts the code beside it. Two consequences:
          (i) a user-initiated re-run draws the aggregate system budget ON TOP of the
          per-user LLM token and the D47 per-group sub-bucket `RetryCommandHandler`
          already spent (`RetryCommandHandler.java:549-559`) — precisely the
          double-metering the javadoc claims the altitude avoids, and precisely what
          the follow-up ticket's own out_of_scope calls "break the spec's
          system-vs-user-initiated split"; (ii) the admission gate at
          `DigestWorker.java:227-228` sits on the SHARED path, so a deployment-wide
          counter driven by OTHER tenants' system-initiated digests now refuses a
          group admin's user-initiated command. The inexact count was accepted as the
          price of a scope correctness the shipped code does not deliver, so the
          trade-off recorded in the javadoc, the ticket and `application.properties`
          is not the trade-off that shipped.
    REPRO: 1) Unrelated groups' scheduled slots drive the PT24H window to the 3000
            ceiling (nominal load reaches it at the ticket's own stated capacity of
            50 full-mode groups x 2 slots; finding 1 reaches it far sooner).
            2) A group admin in group B — whose group has never overrun anything,
            whose per-user LLM bucket is full and whose D47 per-group sub-bucket is
            full — issues `/retry --digest` for a slot whose sections were not
            persisted (any slot that previously degraded leaves `renderedSections`
            null at `DigestWorker.java:295`, so nothing is persisted and the retry
            takes the `fallbackRerun` branch). 3) `RetryCommandHandler` spends B's
            per-user LLM token and B's D47 per-group token, `DigestRetryService`
            stamps B's PT2M cooldown (`DigestRetryService.java:87`, `:232`), and the
            render is then refused by a counter B never touched. 4) B receives the
            headlines-only degraded form and has burned a token, a group token and a
            cooldown for it. Nothing in the threat model lets a third party's
            system-initiated activity consume the buckets the spec sizes per-user and
            per-group. The converse direction is equally reachable: a group admin's
            own `/retry --digest` full re-runs draw down the deployment-wide pool
            that backstops every OTHER group's scheduled digest, with no per-group
            share to bound it.
    SUGGESTED-FIX-CLASS: rate-limit

OUT-OF-MODEL:
  - The window is in-memory and per-JVM (`SystemLlmBudget.callTimestamps`), so a
    restart, redeploy or crash-loop resets a 24-hour control to zero, and a future
    multi-instance Provider would silently multiply the ceiling by the instance
    count. The spec already accepts in-memory state for the circuit breaker ("State
    is in-memory only — a restart resets to CLOSED") and process restarts are not an
    external-adversary lever here. Flagged for the spec owner, not filed.
  - Operator sizing guidance: `application.properties` says "The 100x headroom below
    is what absorbs that error", while the ticket's §Measurement sizes the same 3000
    at "~50 full-mode digest groups at two slots/day" — i.e. the 100x is headroom
    over ONE render, not over the deployment's daily load, so at the documented
    capacity there is none left to absorb a ~2x accounting error in either direction.
    Operator-configuration and documentation territory (operator config is trusted per
    §Threat model), so noted rather than filed — but it is what turns both findings
    above from margin-eating into ceiling-crossing.

RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: DOS
    SEVERITY: medium
    PROMISE: "**Per-group LLM rate (D47)** — a separate sub-bucket per approved group bounding LLM-triggering operations (chat replies + on-demand `/summary` + `/retry` re-rolls) across all group members. The per-user LLM cap fires first; the per-group cap is the backstop for groups with many active members."
    GAP: The diff routes every LLM-triggering surface through `LlmRateCap`, which is strictly per-`users.id` (key is `UUID userId`, `LlmRateCap.java:50` / `:34`). The group chat-mode LLM dispatch in `InboundRouter.java:592` gates the call with `llmRateCap.tryAcquire(actorId)` where `actorId = snapshot.get().id()` — the individual sender. No per-`groups`-row aggregate bucket is consulted on that path. `GroupApprovalCheck` (the step-3.5 per-group rate surface) contains no LLM-cap logic (grep for `llm`/`Llm`/`LLM` returns nothing there), and the only per-group LLM-cost control in the tree is `DigestRetryService`'s digest cooldown (`DigestRetryService.java:44`), which covers `/retry --digest` only, not member chat. The diff's whole subject is LLM-rate-cap coverage, yet the group-aggregate dimension the threat model names is absent: N registered members of one approved group can each spend their own per-user budget with no group-level ceiling.
    REPRO: An approved group has many registered (`invited`/`vouched`), non-banned members. Each member sends chat-mode `@mention` messages at or below the per-user cap (default 10/min). Each passes the per-user `llmRateCap.tryAcquire` at `InboundRouter.java:592` and reaches `chatAgent.handle` (line 605). Aggregate LLM invocations for that single group scale linearly with member count, bounded only by the sum of per-user caps and the transport cap — exactly the "groups with many active members" exhaustion case the per-group LLM backstop was specified to bound. No per-group LLM bucket ever rejects the flood.
    SUGGESTED-FIX-CLASS: rate-limit

OUT-OF-MODEL:
  - The per-group LLM backstop gap is reachable today only because group chat-mode (`InboundRouter.java:592`) is the lone group path that reaches the LLM; `/summary` and `/retry` personal re-rolls are DM-only (`SummaryCommandHandler.resolveScopeId` returns empty for group scope, `RetryCommandHandler.resolveUserId` rejects non-DM), so those two surfaces named in the per-group-LLM promise cannot currently exercise it. If group `/summary` is enabled later, the same missing per-group bucket would apply to them. Noting for completeness — the finding above already covers the live (chat) path.

Note: the per-user, multi-surface coverage that is the diff's actual subject is delivered soundly — `/summary` (`SummaryCommandHandler.java:190`), `/retry` (`RetryCommandHandler.java:183`), and chat (`InboundRouter.java:592`) all consult the one shared `LlmRateCap` keyed by the same `users.id`, so a caller cannot bypass the per-user cap by switching surfaces; rejection consumes no token (`LlmRateCap.tryAcquire` returns before `addLast`) and no in-flight slot leaks (the `finally` releases it). No AUTH/INFO-LEAK/cross-user-isolation gaps found in the refactor.

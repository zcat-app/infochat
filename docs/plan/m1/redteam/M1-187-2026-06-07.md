# Red-team audit — M1-187 (Strip bot-mention span in group inbound delivery)

RED-TEAM VERDICT: CLEAN

The diff implements the messaging.md §Required SPI surface promise ("the mention is stripped before delivery") and is correctly anchored to the D10 cryptographic trust anchor rather than display-name text search, which is the security-load-bearing property here.

Verification of the key threat-model commitments against the diff:

- Display-name spoofing forbidden (security.md "Display-name-based @mention recognition ... forever out of v1"; trust boundary 1 "Display names are informational and never used for authorization"): Both strippers iterate only protocol mention entries. Signal compares `mention.getString("uuid")` to `botAci` under canonical lowercase (`SignalGroupHandler.java:194`); SimpleX compares `span.queueAddress()` to `botIdentity.queueAddress()` (`SimpleXGroupHandler.java:104`). Neither does a substring search of the body. The `mentionByDisplayName_ignored` and `..._plainTextBotNameKept` tests confirm plain-text occurrences of the bot name survive. No bypass.

- Untrusted wire data at the adapter inbound boundary (threat model: "Adversaries can send arbitrary text on any [adapter]"): The new code validates attacker-controlled offsets. Signal checks `start < 0 || length <= 0 || start + length > body.length()` and skips bad entries (`SignalGroupHandler.java:199`). SimpleX gates spans behind a reconstruction guard in `extractMentionSpans` that returns `List.of()` unless every segment matches `text` at its computed offset and the segments cover the text exactly (`SimpleXMessageCodec.java:1474-1491`), and only accepts `memberRef` values passing `isValidQueueAddressId`. A non-reconstructing/hostile frame yields no spans and the text is delivered unstripped — recognition (D10) is unaffected because it reads the separate queue-address list.

- No exception path on the listener/reader thread: I traced the right-to-left delete with StringBuilder clamping (deletes sorted by descending start, `end` clamped to current length). Because all deletions occur at positions ≥ the current span's start, the running length never drops below any not-yet-processed span's start, so `delete(start, end)` cannot throw `StringIndexOutOfBoundsException`. The junction-whitespace step is guarded by `junction < stripped.length()`. No reader-thread crash.

- The strip is pure content transformation upstream of the Provider; it makes no authorization decision and does not move/bypass the ban check, invite gate, step-1.7 normalization, or command parse, all of which remain downstream at the Provider intake. Stripping the attacker's own mention from the attacker's own message confers no escalation.

OUT-OF-MODEL:
- Adapter-side compute on a single inbound frame: an attacker who controls both the body and the `mentions` array (Signal: unbounded array; SimpleX: bounded by reconstructing segments) can, with an alternating span/gap pattern, push the right-to-left StringBuilder deletion toward O(L²) arraycopy work on the reader thread, where L is the body length. The right-to-left ordering largely mitigates the contiguous case, and realistic per-message body size bounds keep this in the low-milliseconds range; the transport-level rate cap (step 1.5) bounds message frequency but only at the Provider, after the adapter has done this work. The threat model makes no spec-level commitment to adapter-side input-size bounds, so this is advisory rather than a finding — flagging it in case the user wants the adapter to cap mention-array length / body length before stripping.

RED-TEAM VERDICT: CLEAN

The diff wires a concrete `StageProgressNotifier` into `/summary` so the command self-delivers a placeholder-then-finalize "visibly-evolving message" instead of returning text to the router. I audited it against every threat-model commitment plausibly in reach of these code paths and found no gap.

What I checked and why it holds:

- LLM output sanitizer (threat model §"LLM output sanitizer": "Before any LLM-generated text is delivered to a user, the candidate output is passed through a deterministic outbound regex pass"). The sanitizer is NOT bypassed by the new delivery path: `llmOutputSanitizer.sanitize(cp.prose())` still runs in `appendClusterBlock` (SummaryCommandHandler.java:331), composing the sanitized prose into the `out` buffer before it is handed to `progressNotifier.complete(scope, out.toString().stripTrailing())` (line 281). The regression test at diff line 2242 pins that `/grant-admin` is stripped from the self-delivered body.

- No user-authored text in progress strings (threat model: stage strings must be deterministic-bundle lookups; D43). `StageProgressNotifier.publish` resolves every stage by enum via `bundleLoader.get(bundleKeyFor(stage))` with no interpolation; `fail()` uses the static `PROGRESS_FAILED` bundle key; only `complete()` carries caller-composed (already-sanitized) text. StageProgressNotifierTest pins that a hostile contact-id in the scope never surfaces in any sent/updated stage string.

- Cross-adapter isolation (trust boundary 1 / D46/D10). `resolveAdapter()` matches `inboundContext.adapterName()` against `activatedAdapters()` and throws if absent, so a `/summary` over one adapter is finalized only over that same adapter. `InboundContext` is `@RequestScoped` (one instance per dispatch), so concurrent inbound from different adapters cannot collide on `adapterName`, and the `StageProgressNotifier` reads it at call time within the request.

- No-double-send dispatch seam (no new INFO-LEAK / no second uncontrolled outbound). The `@Nullable` widening of `CommandHandler.handle` and the `if (body != null) sendReply(...)` guard in InboundRouter.java (diff lines 1722-1732) only suppress a router send when the handler self-delivered; non-null returns are unchanged.

- Authorization, ban, invite-code, audit-log, and rate-limit paths are untouched (consistent with the sensitive-surface inventory). The pre-existing in-flight slot and per-user LLM rate cap remain in force ahead of the notifier path.

OUT-OF-MODEL:
- StageProgressNotifier per-scope state leak under `Error` (not `RuntimeException`). If a `java.lang.Error` (e.g. OOM) escapes after `publish(STARTED)` created the scope state but before `complete`/`fail` runs, the `catch (RuntimeException)` does not fire, so the entry in `states` (with a stale `MessageHandle`) is never removed; a later `/summary` for the same scope would coalesce against the dead handle. This is a correctness/resource-cleanup concern under abnormal JVM conditions, not a violation of any documented threat-model promise (no notifier-state-cleanup or availability-under-Error guarantee exists in the model). Flagging so the user can decide whether to widen the catch to `finally`-based cleanup.

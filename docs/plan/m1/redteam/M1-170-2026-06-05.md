I have reviewed the full threat model, the complete diff, the sensitive-surface inventory, and the relevant source files (`SignalGroupHandler.java` dispatch loop and group-id origin, plus the `MembershipEventHandler`/`GroupMembershipRepository` changes).

Analysis summary of the audited surfaces:

- Audit-before-effect (MEMBER_LEFT): `writeAudit(...)` runs before `markMemberRemoved(...)` inside one transaction that commits atomically (MembershipEventHandler.java:117-120). No path removes a member without first writing the audit row. The `FOR UPDATE` lock (GroupMembershipRepository LOCK_MEMBERSHIP) serializes against concurrent `/promote`/`/demote`, so the recorded `was_group_admin` provenance cannot go stale between read and update.
- Verified-no-op suppression (state == null || state.removed() → rollback, no audit): only fires when the leave implies no mutation. There is no branch where an effective removal (active row → removed) skips the audit. This bounds attacker-repeatable leave events from growing `audit_log` without limit — a hardening, not a regression (the prior plain-SELECT path minted an audit row per repeat).
- Logging: all new log lines (SafeLog calls in MembershipEventHandler, the `LOG.errorf` in SignalGroupHandler, the `log.debug` no-op line) carry only internal UUIDs (groupId/userId), the exception class name, and a base64 group id — never the ACI/contact id, never user prose, never the exception message body. SafeLog truncates the cause chain to class names. The `TargetedFailingAuditLogWriter` test confirms the contact id and SQLException message text do not leak.
- Per-event isolation (SignalGroupHandler:187-198 and AdapterRegistry.dispatchMembershipEvent): catches `RuntimeException` (Errors propagate), swallows after safe-logging, so one failing event does not abort sibling dispatch and a failed transaction rolls back whole (member stays active, no orphan audit).

No gap between a security.md commitment and the delivered behavior was found. MEMBER_LEFT audit is not itself an enumerated security.md promise, and the diff strengthens (rather than weakens) audit-before-effect, bounded audit growth, and log hygiene.

RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - Membership-event authenticity: a `UserLeft` event for the current group admin clears `is_group_admin` (via the V5 trigger inside `markMemberRemoved`), freeing the one-admin-per-group slot for an attacker to claim via the first-`@mention` auto-promote path. The diff does not change who may emit membership events; their authenticity is an adapter/Signal-protocol concern (groupV2 member changes are authenticated group operations, and `groupId` originates from signal-cli, not free-form attacker text). security.md documents no trust commitment for inbound membership events, so this is advisory only — flag for the user if membership-event spoofing should be brought into the documented model.

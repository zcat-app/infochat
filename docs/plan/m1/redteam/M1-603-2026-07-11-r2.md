RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: INFO-LEAK
    SEVERITY: low
    PROMISE: "LLMs (local or remote) are black boxes that can be coaxed into
              emitting attacker-chosen output. Local and remote LLMs have the
              same trust level." (security.md §Threat model) — remote LLM
              endpoints are NOT trusted parties; §Secrets handling treats the
              LLM API key as a secret whose exposure surfaces are enumerated
              and controlled ("LLM API keys are read from environment
              variables, not the DB"; closed redaction catalogue on every
              log/audit surface). The diff's own remediated rule (D56,
              docs/spec/llm.md §Per-task routing rules) states the general
              principle: "the default credential travels only to the default
              endpoint ... the pinned endpoint is a party the key was not
              minted for."
    GAP: The 2026-07-11 remediation coupled the axes in ONE direction only.
         In OpenAiCompatibleProvider.java:195-199 and
         AnthropicProvider.java:160-164, the resolution is: per-task api-key
         wins UNCONDITIONALLY; the default api-key is inherited only when the
         base-url also came from the default. The mirror shape is not
         covered: a task with a per-task api-key but NO per-task base-url
         silently falls back to the shared default endpoint
         (infochat.llm.default.base-url) and transmits the PER-TASK
         credential (Authorization: Bearer / x-api-key) to the DEFAULT
         endpoint — a party that key was not minted for when the per-task
         key belongs to a previously pinned foreign provider. This
         cross-endpoint transmission is new in this diff: pre-D56 a missing
         per-task base-url resolved to the baked loopback
         (localhost:11434/v1, removed by this diff) or failed the eager
         startup resolution, so an orphan per-task key could at worst reach
         a loopback address, never the operator's live remote default. No
         guard covers the shape: LlmRouterStartupGuard scans base-url/
         provider/model axes only (LlmRouterStartupGuard.java:650-673,
         458-490); an orphan infochat.llm.<task>.api-key with no matching
         per-task base-url raises no startup signal, and the off-host
         disclosure WARN names only the route. Neither the switch-llm.sh
         header (prod/switch-llm.sh:12-17) nor the 4-llm.sh pin advice
         (prod/scripts/4-llm.sh:485-489) — which now correctly instruct the
         operator to ADD both lines when pinning — says the two lines must
         also be REMOVED together when unpinning.
    REPRO: 1) Wizard remote run writes
           infochat.llm.default.base-url=https://provider-a/v1 and
           infochat.llm.default.api-key=${INFOCHAT_LLM_API_KEY} (provider
           A's key).
           2) Following the diff's printed pin advice, the operator pins
           chat to provider B with BOTH lines:
           infochat.llm.chat.base-url=https://provider-b/v1 and
           infochat.llm.chat.api-key=<provider B's key> (the explicit
           per-task key the remediation now requires).
           3) Later the operator unpins chat by deleting the line the docs
           call "the override" — the base-url line — leaving the api-key
           line (no tool or doc removes them as a pair on a hand edit;
           switch-llm's sweep only runs on a full backend switch).
           4) Boot is clean — chat's base-url silently falls back to the
           shared default, no guard scans for orphan per-task api-keys. On
           the first chat call, provider B's credential is sent in the
           Authorization header to provider A's server — an endpoint the
           threat model classes as an untrusted black box, which now holds
           a replayable billing/API credential for provider B. No startup
           signal, no WARN, no disclosure line names the credential's new
           destination. Severity is low, not medium: unlike the remediated
           round-1 finding, no shipped tooling or printed advice produces
           the triggering shape (the pin advice creates both lines; the
           switcher sweeps both lines atomically) — it requires a partial
           manual unpin — but the damage class is identical, and the silent
           base-url fallback this diff introduces is what lets the stale
           key travel instead of failing loudly.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

OUT-OF-MODEL:
  - switch-llm.sh consent regression persists from round 1 (unchanged by
    the remediation): over an old-format MIXED file (e.g. chat remote, six
    tasks local — a shape the pre-M1-603 switcher itself created), the
    deployment-level default answer classifies as "remote" (chat.base-url
    fallback, prod/switch-llm.sh Phase 1), so an all-Enter run sweeps every
    per-task line and routes all seven tasks remote; the same sweep removes
    a deliberate hand-written per-task LOCAL pin (e.g. an operator keeping
    chat on-host for privacy) on any mutating run. security.md's only
    commitments here — per-task privacy-disclosure correctness and the
    local-only hard gate — are both delivered (the disclosure fires and is
    accurate; local-only=true still refuses boot), so this is a
    consent/expectation regression rather than a threat-model violation.
    Flagged again for the user to decide whether the byte-identical no-op
    guarantee should be re-committed for mixed files.
  - Boot-time DNS TOCTOU carried over from round 1, unchanged: the guard
    resolves the shared default base-url's loopback-ness ONCE at boot
    (LlmRouterStartupGuard.perTaskRoutes), while live calls re-resolve at
    request time — a hostname flipping loopback→remote after boot bypasses
    local-only. Pre-existing mechanism (identical semantics for per-task
    URLs) and requires control of the operator's DNS for an
    operator-configured host, which the threat model places out of scope.
  - The guard's config snapshot now copies the raw
    infochat.llm.default.api-key value into the snapshot map
    (LlmRouterStartupGuard.java:831-832) although no scan ever reads it —
    the diff's own comment asserts it is never echoed, and I verified no
    read exists today. Inert, but an unused secret held in a map the
    fatal/WARN paths iterate widens the surface a future snapshot-dump or
    debug-logging change could leak; dropping the unused entry would
    remove the hazard class.

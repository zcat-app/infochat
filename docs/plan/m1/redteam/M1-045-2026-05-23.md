RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: AUTH-BYPASS
    SEVERITY: medium
    PROMISE: docs/spec/security.md §Slow-start tier: "Every newly registered
      user enters a probation period (decision D45). ... Blocked operations
      return a friendly reply stating when full access unlocks; the reply
      never reaches the LLM or any write path." And §Authorization model
      step 7: "Probation restrictions (D45) are part of the permission
      matrix: blocked commands return a friendly 'probation period' reply
      and never reach execution."
    GAP: infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/InboundRouter.java
      lines 307, 341-343, 366 — `snapshot` is captured via `lookupUser`
      BEFORE step 3's `autoRegisterService.resolveOrRegisterGroup` insert;
      the step-5 probation gate then guards on `if (snapshot.isPresent())`
      (line 366). For a group `@mention` from an unknown contact, `snapshot`
      is empty at this point, so the probation check is skipped for the very
      message that triggered auto-registration. The router proceeds to step
      6 dispatch with no probation gate, even though `AutoRegisterService`
      inserted the row with `probation_until = NOW() + probationDuration`
      (AutoRegisterService.java line 87). The acceptance ticket explicitly
      documents this carve-out as intentional, but the spec promise is
      "every newly registered user" with no first-message carve-out.
    REPRO: An attacker joins a group the bot serves and sends `@bot /<command>`
      as their first message. Step 1 sets adapter; step 1.5 rate cap passes;
      step 1.7 normalizes; step 2 skipped (Group scope); step 3 auto-registers
      them with probation_until in the future; step 4 ban check (not banned);
      step 5 probation gate sees `snapshot.isEmpty()` and SKIPS; step 6
      dispatches the slash command. While today every group-scope-callable
      handler short-circuits (e.g.,
      `AddSourceCommandHandler.java:137` rejects group scope with
      `error.add-source.group_admin_only`), the security boundary the spec
      commits to is the probation gate itself — not the downstream handlers'
      independent rejection. Any future group-scope handler that adds side
      effects (T2-F's group_admin proceed path is named in
      `AddSourceCommandHandler.java:137`'s comment) silently inherits the
      bypass with no separate audit signal. The spec's "bounds early
      resource damage per identity" (§What's intentionally NOT in v1 —
      Sybil resistance) is precisely the property this gap erodes.
    SUGGESTED-FIX-CLASS: missing-auth-check

  - CATEGORY: INFO-LEAK
    SEVERITY: low
    PROMISE: docs/spec/security.md §Invite-code registration: "Group-registered
      users do not get free DM access. ... the permission step (step 7) adds
      a DM-only gate that rejects any DM from a `group_only` user with **the
      same fixed `Access requires an invitation.` reply as step 2's invalid
      path**."
    GAP: infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/InboundRouter.java
      lines 366-384 (step 5 probation gate) run BEFORE lines 426-431 (step 7
      DM-gate). A `group_only` user (registered via group `@mention`) who
      DMs the bot while still in probation receives `error.probation.blocked`
      (which enumerates "/help, /status, /summary, /saved, /get-tags,
      /get-sources, /list-sources, /export, /forget, /lang, /stop" as
      "Allowed during probation") instead of the spec-mandated
      `error.invite.required` reply. The reply text actively misleads the
      user: it lists commands they cannot actually invoke (the DM gate
      blocks all of them). It also creates a reply-content distinction
      between (a) unknown DM contacts (`error.invite.required`) and (b)
      registered `group_only` contacts (`error.probation.blocked`), letting
      a contact probe whether they have any registered presence the bot
      remembers — by sending a single DM and observing which fixed reply
      lands.
    REPRO: Attacker is auto-registered in a group as `group_only` (e.g.,
      during the auto-register first-mention). Within the probation window
      they open a DM and send `/help`. The bot replies with the
      probation-blocked text including the list of allegedly allowed
      commands. The spec promise is `Access requires an invitation.`; the
      user gets a different, longer text revealing internal classification.
      A second attacker DMs from a never-seen contact and gets the literal
      invite-required reply. The reply-text divergence is a confidentiality
      boundary the spec promised to keep flat.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

OUT-OF-MODEL:
  - The `VouchCommandHandler` does not check whether the target row's
    `is_banned = true`. A bot admin can `/vouch` a banned user, advancing
    `registration_state` from `group_only` to `vouched` and clearing
    `probation_until`, even though intake step 4 still blocks the user. No
    exploit follows because step 4 ban check fires before any access is
    granted, but operators who later `/unban` the contact will find them
    landed past probation with no separate probation grace period. This is
    a v1 operator-procedure consideration, not a documented threat-model
    commitment.
  - The `VouchCommandHandler` looks up the actor and target in separate
    non-transactional connections (`lookupUser` calls at lines 123 and
    138), then opens a transaction for the audit + UPDATE. A concurrent
    `/revoke-admin` between actor lookup and the audit/UPDATE would let a
    just-demoted admin's `/vouch` still land. The window is the duration
    of the second `lookupUser` call. The spec does not commit to
    serializing privilege changes against in-flight admin commands;
    flagged as out-of-model.

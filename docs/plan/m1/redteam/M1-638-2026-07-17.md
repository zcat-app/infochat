RED-TEAM VERDICT: CLEAN

Audited M1-638 (interruptible-turn lifecycle registry) against the
commitments in docs/spec/security.md. The diff refactors InFlightTracker
from a thread-keyed one-slot-per-scope map into a per-scope registry that
tracks QUEUED turns (pre-worker) plus the at-most-one RUNNING turn, so
/stop can cancel a turn still sitting in the InterruptibleDispatcher pool
queue. It touches CancellationService.cancel (sweep queued then running),
the three tryAcquire call sites (ChatAgent, RetryCommandHandler,
SummaryCommandHandler adopted-cancelled early returns), and
InboundRouter.runSeededDispatchStage (register-at-submit + discard leak
guard).

The threat-model commitments this change could plausibly weaken were
checked and hold:

- Per-(user, scope) isolation ("Never leak across users or between DM and
  group", CLAUDE.md key conventions; D28/D13). Every registry key embeds
  the message AUTHOR's userId: DM turns register as (userId,"dm",userId)
  (InboundRouter.java:866-868, dispatchScopeId=snapshot.get().id() for DM),
  group turns as (userId,"group",groupId). /stop's cancel key
  (StopCommandHandler.resolveScope, lines 121-128) is
  (stopSenderUserId,"dm",stopSenderUserId) / (stopSenderUserId,"group",
  groupId). Cross-user cancellation is structurally impossible because the
  author's userId is part of the key on both the register and cancel sides;
  cancelQueuedTurns/consumeIfCancelled use computeIfPresent on that exact
  ScopeKey (InFlightTracker.java:209-220, 187-199). The IT
  stopByUserANeverCancelsUserBsQueuedTurn pins this.

- Adoption context bleed. tryAcquire's seededTurnId() reads the thread-
  bound @RequestScoped InboundContext proxy (InFlightTracker.java:257-296,
  419-428). The worker seeds operationId=turnId at the top of
  runSeededDispatchStage (InboundRouter.java:951) before any tryAcquire, so
  the read always resolves THIS turn's UUID on THIS worker's fresh context;
  a foreign/absent context mints a fresh identity (safe fallback), and turn
  ids are per-turn UUIDs, so no cross-turn or cross-scope adoption collision
  exists.

- No RUNNING-slot leak / permanent lockout. Admission ("one RUNNING per
  key") derives from the running field only; a leaked QUEUED entry blocks no
  admission (isInFlight/getCancellationHandle report running only,
  InFlightTracker.java:313-336). All three acquirers release the slot in a
  finally, including on the new adopted-cancelled early returns
  (ChatAgent.java:290-295, RetryCommandHandler.java:271-276,
  SummaryCommandHandler.java:406-408). QUEUED entries are cleaned by
  runSeededDispatchStage's finally{ discard } (InboundRouter.java:966-972),
  and the dispatcher uses CallerRunsPolicy (never rejects), so the stage —
  and thus the discard — always runs.

- Rate limiting. The change strengthens, not weakens: adopted-cancelled
  turns short-circuit BEFORE the LLM bucket draw and retry-cap peek
  (RetryCommandHandler.java:201-204, SummaryCommandHandler.java:288-291,
  ChatAgent.java:237-239), so a cancelled turn burns no token. The
  transport rate cap (step 1.5) still gates inbound before registerQueued,
  and the interruptible pool stays bounded — no new resource-exhaustion
  amplification.

- Determinism boundary (steps 1-9 never call the LLM). Registration at
  submit is a cheap in-memory map write; no LLM call is introduced upstream
  of any authorization gate.

- No AUTH/PERM/INJECTION/AUDIT surface. /stop is conversation control, not
  a privileged-tier command; the threat model does not require it to be
  audit-logged, and no admin-tier gate, SQL string, or prompt path is
  changed. The IT's ALTER TABLE audit_log DISABLE TRIGGER is test-only
  cleanup on the seed datasource, matching 51 existing test files — not a
  production code path.

No gap between a documented threat-model promise and the delivered diff
was found.

RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - The injected `Clock clock` field in LlmRateCap is package-private and
    field-injected (`@Inject Clock clock = Clock.systemUTC();`). A test or any
    same-package code can overwrite it to skew the rate-cap window. This is
    not a finding: per the documented trust model, internal Java state set by
    CDI/co-located code is trusted (CLAUDE.md §No-defensive-code), the field is
    not reachable from any messaging-adapter, HTTP, or LLM-tool input surface,
    and the diff's sensitive-surface inventory confirms no auth/ban/isolation/
    input-validation/audit surface is touched. The chosen seam exactly mirrors
    the established convention used across ~18 other provider components
    (RateCapBucket, GroupAutoPromoteService, ListSavesTool, ProbationCheck,
    InviteCodeConsumer, etc.), so it introduces no new exposure. Flagged only
    so the user can confirm the package-private clock seam remains the accepted
    project-wide pattern.

Notes for the reviewer (not findings):
  - The change is a pure time-source refactor: `System.currentTimeMillis()` ->
    `clock.millis()` at three sites (tryAcquire window decision, the scheduled
    evictIdleEntries entrypoint). In production `Clock.systemUTC().millis()` is
    byte-for-byte equivalent to `System.currentTimeMillis()`, so the per-user
    LLM rate-cap commitment (security.md §Rate limiting, "LLM-triggering
    operations ... its own bucket, capped lower") is preserved unchanged: same
    60 s sliding window, same cap comparison (`size() >= capPerMinute`), same
    no-budget-on-reject semantics, same 120 s eviction cutoff.
  - Single-clock discipline (CLAUDE.md §9) is satisfied: both the decision read
    (tryAcquire) and the eviction read (evictIdleEntries) use the same injected
    clock; the component does not split across an app clock and a DB clock.
  - No DOS regression: the change neither raises the cap nor widens the window,
    and the refactor cannot be driven by adversary input.

RED-TEAM VERDICT: CLEAN

The diff (M1-342) adds a per-tick "provider-down" latch to ReEvaluationJob:
processOne now returns true iff the Stage-2 re-judge verdict is INFRA_FAILURE,
and onTick breaks the candidate loop on the first such verdict, bounding
outage-time provider-call fan-out to one judge call per tick. The remaining
change is a JUnit IT plus a counting Stage2Worker test double.

Audited against docs/spec/security.md §Re-evaluation job, §Failure handling,
§Quarantine workflow, and trust boundary 5 (LLM ↔ system state). No spec
commitment is broken:

- AUDIT-EVASION (checked, not a finding): the spec-mandated RE_EVAL_RELEASED
  audit row and throttled admin notification fire only on a BENIGN re-eval
  release (applyBenignReEval, ReEvaluationJob.java:197-225 / :415-427).
  processOne returns false on BENIGN (line 184), so the BENIGN branch never
  latches and every release still audits + notifies exactly as before. The
  latch fires only on INFRA_FAILURE (line 190), which performs no release and
  has no audit obligation.

- INFO-LEAK (checked, not a finding): non-BENIGN verdicts still re-hide a
  released post to QUARANTINED (applyNonBenignReEval, line 263) — unchanged,
  returns false, does not latch. INFRA_FAILURE-latched and cap-exhausted
  posts that are deferred during a sustained outage remain QUARANTINED
  (hidden) — strictly fail-closed. No user-visible exposure is introduced.

- DOS (checked, not a finding): the change REDUCES fan-out during an outage;
  it does not introduce an unbounded loop or new resource cost. judgeBody
  (Stage2Worker.java:248-261) catches provider RuntimeExceptions internally
  and returns INFRA_FAILURE rather than throwing, so the latch engages on a
  real outage; the onTick catch (lines 153-161) only handles body-reconstruction
  failures and correctly leaves providerDown unset for those.

Residual behavioral degradation considered and judged in-model: during a
sustained LLM outage, per-post cap-exhaustion -> NEEDS_REVIEW transitions for
candidates ordered after the first INFRA_FAILURE candidate are deferred to a
later tick (the latching candidate never advances, so it re-latches each tick
until the provider recovers). Those posts stay QUARANTINED (hidden) rather
than transitioning to NEEDS_REVIEW, and so are not counted by the NEEDS_REVIEW
depth alert (countNeedsReviewWithinScanWindow, line 606) for the outage
duration. This is consistent with the spec's explicit stance that "A complete
LLM outage degrades quality, not safety" (§Failure handling): the content most
needing review stays hidden (fail-closed), checkNeedsReviewDepth() still runs
unconditionally each tick (onTick line 163), and the deferred posts are
re-enumerated by the deterministic ORDER BY fetched_at, id scan once the
provider recovers and the latch releases. No confidentiality, integrity, or
availability commitment in the threat model is forfeited.

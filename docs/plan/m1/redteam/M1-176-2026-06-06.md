RED-TEAM VERDICT: CLEAN

The diff is a single, tightly-scoped availability hardening: `NostrEvent.toNormalizedPost` now sets `published_at = LEAST(created_at, fetchedAt)` instead of trusting the relay-supplied `created_at` verbatim (`infochat-collector/src/main/java/app/zcat/infochat/collector/stream/nostr/NostrEvent.java:87-88`).

I verified the threat it closes is real and that the fix lands at the right column:
- The Nostr reconnect `since` cursor is `SELECT MAX(published_at) FROM post WHERE source_id = ?` (`NostrStreamSource.java:461`, converted to epoch seconds at `:469`), fed into the relay REQ filter (`:329`, `NostrRelayConnection.java:395`). A single future-dated event would have pushed `MAX(published_at)` past now, making the `since` filter exclude every genuine event and silently blind the bot to that source — an availability/DoS gap. The clamp guarantees `published_at <= fetchedAt`, so the cursor can no longer be advanced past wall-clock receipt time.
- The clamp executes at outbox-write mapping, strictly downstream of the documented Nostr trust gates (signature verification → kind allowlist → dedup in `NostrStreamSource.enqueueInbound`, `:145-182`). The diff does not reorder or weaken any of those gates, consistent with security.md §Per-source trust boundaries.
- `fetchedAt` is wall-clock `Instant.now()` supplied at delivery time (`NostrStreamSource.java:222`), so the clamp ceiling is genuine receipt time, not relay-controlled.

No threat-model promise is touched-but-unfulfilled. The change strengthens availability and introduces no new auth, isolation, injection, audit, or leak surface. Tests (`NostrEventTest.java`) cover both the future-clamp and past-preserved branches.

OUT-OF-MODEL:
- The clamp bounds only the upper end; a far-past or negative `created_at` is preserved unchanged. This does not poison the `MAX(published_at)` cursor (it only moves the max upward) and is not a documented threat, so it is advisory only. The pre-existing `Instant.ofEpochSecond(createdAt)` overflow path (out-of-range `created_at` throwing `DateTimeException`) predates this diff and is already absorbed by the per-event `try/catch (RuntimeException)` in `NostrStreamSource.deliverOne` (`:223-230`); not introduced or worsened here.

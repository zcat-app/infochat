RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: INFO-LEAK
    SEVERITY: medium
    PROMISE: "Redactions are lifted only by `/quarantine approve`... An
      admin reviewing the quarantine row is the only path that restores
      the original span" (docs/spec/security.md §Quarantine workflow),
      and "a degraded judge must never auto-release" (§Failure handling).
      The ticket's own premise — the threat-model commitment the V69
      guard exists to deliver — is that approve must not release a post
      whose Stage 2 verdict is still owed, because the post is then
      "READY and announced to users" before the judgment exists
      (V69__approve_quarantine_verdict_owed_guard.sql:5-13).
    GAP: The guard predicate is `stage1_flagged = TRUE AND stage2_done =
      FALSE` (V69__approve_quarantine_verdict_owed_guard.sql:87-93). But
      the Stage 2 infra-failure path sets `stage2_done = TRUE,
      stage2_failed = TRUE` and leaves the verdict unrecorded —
      Stage2VerdictHandler.applyInfraFailure lines 218-236 (both the
      release-on-stage2-failure=true and =false branches call
      updatePostStage2DoneRaw / updatePostQuarantined with
      stage2Failed=true and stage2_done=TRUE, stage2Verdict=null). So a
      QUARANTINED post sitting in the re-evaluation queue awaiting the
      verdict it is still owed (release-on-stage2-failure=false profile —
      precisely the profile whose operator chose fail-closed because the
      judgment matters) PASSES the guard. The V69 header comment even
      asserts the opposite — "A post with stage2_failed = TRUE but
      stage2_done = FALSE is still owed the verdict (it sits in the
      re-eval queue), so the guard refuses it too" (lines 23-26) — which
      is factually wrong about the flag state: re-eval-queue posts carry
      stage2_done = TRUE. Worse, the approve body then clears
      `stage2_failed = FALSE` (V69:117-121, "drop the post out of the
      re-eval queue's infra-failure branch so it can never be
      re-hidden"), so the post permanently exits the re-evaluation
      queue: no verdict is ever recorded, no re-hide can ever fire, and
      the original span is restored + the new_post NOTIFY announces the
      unjudged content. The guard therefore closes only the
      first-pass-in-flight window (seconds) while leaving the
      infra-failure/re-eval window (minutes-to-forever under a judge
      outage) wide open, and converts a transient owe-verdict state into
      a permanent never-judged state.
    REPRO: (1) Operator runs the fail-closed profile
      (release-on-stage2-failure=false, the production posture the spec
      explicitly offers). (2) A feed adversary publishes content that
      trips a Stage 1 regex; the post is flagged, a PENDING quarantine
      row is created. (3) The judge endpoint is down or the adversary
      times the attack to a judge outage (§Trust boundaries item 9 puts
      hostile/flaky endpoints in scope; sustained UNKNOWN/infra-failure
      floods are an in-model attack shape per §Re-evaluation job); the
      Stage 2 call infra-fails, the post is set QUARANTINED with
      stage2_done=TRUE, stage2_failed=TRUE, no verdict, and queued for
      re-evaluation. (4) An admin working `/quarantine list` sees the
      ordinary PENDING row — indistinguishable from a judged row — and
      runs `/quarantine approve <id>`. (5) The guard passes
      (stage2_done=TRUE), the original span is restored, status flips to
      READY, the new_post NOTIFY announces the post to users, and
      stage2_failed is cleared so the re-evaluation job never picks the
      post up again. Content the judge never saw is permanently
      user-visible with redactions lifted — the exact outcome the guard
      was built to prevent — and no subsequent re-eval verdict can
      re-hide it.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

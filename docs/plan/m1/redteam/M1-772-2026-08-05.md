    SEVERITY: low
    PROMISE: docs/spec/security.md §Invite-code registration commits that the
             broad-blast-radius admin primitives are confirm-gated —
             "`--open` — adapter-bound invite ... Requires confirm (broader
             blast radius)" and "`/invite revoke` requires confirm" — and
             §Authorization model step 4.5 (as implemented per
             docs/spec/commands.md §Surface conventions, "any other input
             cancels") makes the armed window self-closing: the pending
             confirm is drained, and the user acknowledged, as soon as the
             same (user, scope) sends anything that is not the confirm shape.
             The same step also carries the §/retry anchor clear ("any
             non-/retry input from the same (user, scope) clears the anchor").
    GAP: infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/InboundRouter.java:740-745
         inserts a new unconditional `return` for any slash body containing a
         line boundary. That return sits at line 745, i.e. BEFORE the step-4.5
         confirm-cancel sweep (InboundRouter.java:834-855) and BEFORE the
         step-4.6 anchor clear (InboundRouter.java:859-869). A multi-line
         slash body therefore (a) leaves a pending destructive confirm armed
         for the remainder of its TTL, (b) emits no
         `REPLY_CONFIRM_CANCELLED` acknowledgement — the user sees only
         `error.command.multiline` — and (c) leaves the `/retry` summary
         anchor in place. The diff's own inline comment (InboundRouter.java:733,
         "before every DB write, including the step-4.5 confirm drain") records
         the skip as intended, and the ticket lists the drain as out-of-scope,
         but neither carries the control across nor argues it is no longer
         needed. This is the engineering-rules §10 "incidental obligations of a
         rerouted path" shape: the pre-existing body-cap branch
         (InboundRouter.java:722-727) has the same skip, but it is reachable
         only with an over-cap body, whereas the new branch is reachable with a
         two-character body, so the exception widens from a rare shape to a
         trivially-typed one.
    REPRO: 1. Bot admin DMs `/invite create --open` (or `/ban <contact>`); the
              handler arms a PendingConfirm under (actorId, DM scope) with a
              TTL and replies with the confirm prompt.
           2. The admin then sends any slash body carrying a line boundary,
              e.g. `/help\nnote to self` (or a client that emits CRLF-wrapped
              text). InboundRouter returns at :745 with
              `error.command.multiline`.
           3. The `/invite create --open` confirm is still armed and the admin
              received no cancellation acknowledgement — the spec's
              "any other input cancels" contract, which is what bounds the
              armed window for the primitive the spec singles out as having
              the "broader blast radius", did not fire. A later
              `/invite create --open confirm` (or, via the documented
              "args retyped" relaxation, any `/ban <other> ... confirm`
              body) still redeems the ORIGINAL armed payload.
           Not adversary-reachable across users: PendingConfirm is keyed by
           (actorUserId, scope) so no third party can arm, prolong, or redeem
           another actor's confirm. The exposure is the erosion of a
           defense-in-depth timer on the deployment's broadest admin
           primitives, not a cross-principal bypass — hence low.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

  - Spec prose overstates the closed defect (accuracy, not a hole).
    docs/spec/commands.md §Surface conventions (added lines) says the
    pre-change behaviour meant `/list-sources` with `--all` on a later line
    "dispatched the admin-only deployment-wide listing". Verified against
    infochat-provider/.../command/ListSourcesCommandHandler.java:159-184: the
    `--all` / `--include-deleted` branch re-checks `actor.isAdmin` inside the
    handler and refuses a non-admin caller, and RetryCommandHandler.java:538-548
    gates `--digest` on bot-admin-or-group-admin. So the pre-existing defect was
    a widened argument run reaching an authorization-gated branch, not an
    authorization bypass. Flagged so the user does not credit this change with
    closing an auth hole that the deterministic permission checks already held.
  - Availability trade-offs the change makes, all accepted-by-design but not
    threat-model items: (a) `/ban --reason="a\nb"` and any other double-quoted
    multi-line value (CommandTokenizer) are now rejected outright;
    (b) InboundRouter.isMultiLineCommand rejects a TRAILING U+0085 / U+2028 /
    U+2029 because normalize()'s `trim()` only strips codepoints <= U+0020, so a
    client that appends one of those to an otherwise-valid command makes it
    unusable; (c) in group scope the rejection reply renders in "en" rather than
    the group's `/lang`, because the group scope language resolves at step 4.1
    which the new return precedes — identical to the existing body-cap replies
    and already documented at InboundRouter.java:629-633.
  - Token separators outside ASCII `\s`. CommandTokenizer.java:34 splits on
    `Character.isWhitespace`, which includes U+001C–U+001F; those are neither
    line boundaries (so the new `\R` gate does not reject them) nor recognized
    by the sanitizer's separator set
    (LlmOutputSanitizerCore.isTokenSeparator, :378-380, ASCII `\s` only).
    Checked and NOT exploitable today: the only flag-bearing closed-list
    entries are `/list-sources --all` / `--include-deleted`, parsed by
    ListSourcesArgs with `split("\\s+")`, and the multi-word entries
    (`/invite create` etc.) resolve their subcommand via
    InviteCommandHandler.java:236 `split("\\s+", 3)` — so a U+001C-separated
    token dispatches nothing. Noted only because the amended spec paragraph
    re-states the ASCII-`\s` equivalence as a general property of "the parser",
    while several privileged handlers in fact tokenize on a wider set; a future
    closed-list entry whose flag is parsed by CommandTokenizer would silently
    inherit an evasion, exactly the shape the spec's own case-rule paragraph
    warns about.

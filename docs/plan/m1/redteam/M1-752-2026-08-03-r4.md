  - CATEGORY: DOS
    SEVERITY: low
    PROMISE: security.md §Failure handling, Per-source UNKNOWN auto-disable —
              "**Auto-disable only blocks new ingest** — it stops the fetcher or
              stream-source worker from enqueueing new posts from the source"
              (docs/spec/security.md:1572-1576), the mechanism that "bounds the
              **quarantine-exhaustion** attack surface: an adversary controlling a feed
              ... cannot drown admin review capacity by crafting borderline content that
              consistently triggers UNKNOWN" (security.md:1576-1581). Reinforced by
              property (e)'s own stated purpose: "an automatic restore must never clear a
              park reason a security control wrote during the probe window"
              (security.md:1382-1383).
    GAP: Property (e) makes the restore's STATUS WRITE a compare-and-swap, but the diff
         is silent on the probe's PAYLOAD — nothing gates the fetched posts on the same
         CAS result. The probe is a real fetch, not a liveness ping: M1-754's design
         constraints mandate "The probe itself MUST go through the existing `Fetcher` SPI
         (`Fetcher.fetch(dispatchKey, identifier)`)"
         (M1-754-parked-source-reprobe-ladder.md:755-760), which returns the parsed
         items. D42 ("automatically re-probed ... run off the active fetch path"),
         schema.md:279-286 and security.md:1363-1367 all describe only what happens to
         `status`, `consecutive_failures`, `park_reason` and the audit row. M1-754's
         acceptance item 3 specifies the no-op's effects exhaustively as "leaves the park
         intact, is not an error, and writes no audit row and no RECOVERED notification"
         (M1-754-parked-source-reprobe-ladder.md:568-582) — it does not say the probe's
         fetched posts are discarded. Acceptance item 9, which describes the successful
         restore, likewise says nothing about the items. The two natural implementations
         differ in exactly this respect: select -> fetch -> persist+enqueue -> restore
         (leaks) versus select -> fetch -> CAS -> persist only if the CAS updated a row
         (safe). Neither is mandated, and the persist-then-restore ordering is the one
         that falls out of reusing the existing tick body's persist-before-emit outbox
         discipline (FetchScheduler.java:67-70).
    REPRO: Adversary controls an ingested feed that is parked `fetch-failure` (they let
           it fail N consecutive ticks, which is cheap and adversary-timed). They wait
           out the backoff and watch for the probe. On the probe they answer 200 with a
           large batch of borderline content engineered to draw Stage 2 UNKNOWN verdicts.
           The batch is fetched and — under the persist-then-restore ordering the diff
           permits — persisted and enqueued. `PerSourceUnknownTracker` then crosses the
           per-source threshold and upgrades the row to the manual-only `unknown-rate`
           reason. The restoring UPDATE correctly no-ops (property (e) working as
           designed), the source stays parked and is never probed again — but the batch
           the control existed to keep out is already in the outbox and consumes admin
           review capacity, and the operator's only signal that the probe delivered
           anything is the absence of a RECOVERED notification. The same shape applies to
           the `/remove-source` leg: an admin soft-deletes a hostile feed during the
           probe window, the restore no-ops as specified, and one batch from the
           deliberately-cut-off endpoint is ingested anyway. The exposure is one batch per
           park (only the first successful probe reaches this path), which is why this is
           low and not medium — but it is a side effect of the probe that the CAS
           remediation does not cover and that no acceptance item pins either way.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: PERM-ESCAL
    SEVERITY: medium
    PROMISE: security.md §Per-adapter admin threat profile (SimpleX admin):
             "Single-use means a token that leaked and was then re-issued
             cannot be replayed once the real admin has claimed." And
             decisions.md D50 / security.md §Authorization model: "The token
             is single-use — once any contact has claimed SimpleX admin, a
             later presentation of the same token (same or different contact)
             grants nothing and yields the same fixed reply an invalid invite
             would."
    GAP: The implementation does NOT enforce single-use per-token. The
         single-use gate is row-existence-based, not token-spent-based.
         infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/SimpleXAdminClaim.java:619-626
         (CLAIM_ADMIN_SQL) gates the claim on
         "WHERE NOT EXISTS (SELECT 1 FROM users WHERE adapter = ? AND
         is_admin = TRUE)". "Used" therefore means "a SimpleX admin row
         currently exists," NOT "this token was ever presented." The token
         itself remains a live, long-lived config/env secret
         (SimpleXAdminClaim.java:628-629, @ConfigProperty admin-token) that is
         never marked spent. The class Javadoc admits the divergence
         (SimpleXAdminClaim.java:74-78, "Known v1 limitation: if the operator
         later /revoke-admins the only SimpleX admin, the token can
         re-establish one"). Consequence: the moment the SimpleX is_admin
         count drops to zero, the still-configured token re-arms and the next
         DM presenting it claims admin again — directly contradicting the
         spec's "a leaked token ... cannot be replayed once the real admin has
         claimed." Reaching zero SimpleX admins is a normal multi-adapter
         operation: last-admin protection is GLOBAL across adapters
         (security.md §Authorization model), so a deployment with a Signal
         admin can /revoke-admin the SimpleX admin and leave SimpleX with zero
         admin rows. (The same root cause also breaks the spec's documented
         rotation flow in the other direction — "issue a fresh token and the
         new first-DM claim establishes a new admin row; the prior admin row
         is left in place" is impossible here, because the prior row's
         is_admin=TRUE blocks every new claim regardless of token value.)
    REPRO: Precondition (the exact scenario the spec's single-use is designed
           to defend): the operator's admin-token leaks but is left in config.
           1. Operator runs SimpleX + Signal adapters. SimpleX admin claimed
              by the operator on first DM (token now "spent" per spec).
           2. Operator (or a compromised co-admin) /revoke-admin's the SimpleX
              admin row — permitted because the Signal admin keeps the global
              non-banned is_admin count >= 1.
           3. SimpleX is_admin count is now zero; the NOT EXISTS gate is true
              again. The attacker, who holds the leaked token, sends one DM to
              the SimpleX bot with the token body.
           4. SimpleXAdminClaim.claim inserts a fresh
              (simplex, attacker_contact_id) row with is_admin=true and
              returns Claimed; the attacker receives the welcome reply and now
              holds SimpleX bot-admin (invite issuance, ban, source mutation,
              audit access on that adapter). The spec promised the leaked
              token could not be replayed once the real admin had claimed.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

OUT-OF-MODEL:
  - Token-length side channel: constantTimeEquals
    (SimpleXAdminClaim.java:762-766) uses MessageDigest.isEqual on raw UTF-8
    bytes, which returns early on a length mismatch and so leaks the token
    byte-length to an attacker who can guess. The spec does not commit to
    hiding token length and the body length is attacker-chosen anyway; noted
    only so the user can decide whether token-length confidentiality is in
    scope.

RED-TEAM VERDICT: CLEAN

Round-5 audit note (context, not a finding): the three prior bypasses are
confirmed CLOSED and are not re-reported. The boundary heuristic is gone
entirely (neither side of any character-category partition is consulted), and
the round-3 NFKC-ordering dependency is removed — acceptableOverride
(infochat-provider/src/main/java/app/zcat/infochat/provider/source/SourceUpsertService.java:310-332)
now normalizes the value itself before the slash test, so correctness no longer
rests on how the value reached the handler.

Adversarial verification performed against the CURRENT code, along the four
axes the remediation's own claims stand on:

1. NFKC-then-strip-then-trim ORDERING. The order is
   Normalizer.normalize(NFKC) -> IngestTextNormalizer.stripMetadataField ->
   trim -> {empty | containsSlash | length} (SourceUpsertService.java:324-331).
   This is the safe order. The dangerous inversion would be strip-then-NFKC,
   where a compatibility decomposition could re-introduce a codepoint the strip
   had already removed; here the strip runs last, so nothing NFKC emits escapes
   it. The reverse direction — the strip creating a slash — is impossible:
   character removal never synthesises a character, and the only context-
   sensitive step in a later re-normalization is canonical composition, which
   can never yield U+002F because SOLIDUS has no canonical decomposition and is
   therefore not a composition target. Removing a composition-blocking
   Default_Ignorable (e.g. U+200D between a starter and a combining mark) does
   leave the stored string outside NFKC form, but the only thing a later NFKC
   can then do is compose base+mark into a precomposed letter — never a slash.

2. NON-U+002F CODEPOINTS YIELDING AN EXECUTABLE COMMAND ON PASTE-BACK. Every
   codepoint with a compatibility mapping that contains ASCII '/' is folded
   BEFORE the test and is therefore caught, including the multi-character
   expansions the earlier rounds did not exercise: U+FF0F -> '/', U+2105 -> "c/o",
   U+2100 -> "a/c", U+2101 -> "a/s", U+2106 -> "c/u", U+33A7 -> "m/s". The
   non-folding homoglyphs (U+2215, U+2044, U+29F8) survive into the stored
   name, but dispatch is gated on a literal ASCII '/' at index 0 — verified
   firsthand at InboundRouter.java:1061 `if (normalized.startsWith("/"))` — and
   NFKC is idempotent, so no surviving codepoint can become one on the paste-back
   pass. Combined with D12 (slash-prefix is the only command sigil), a
   slash-free stored name cannot carry a command token.

3. LENGTH BOUND vs NFKC EXPANSION. The bound is applied to the same string that
   is stored and echoed (`stripped`, SourceUpsertService.java:325-331), not to
   the raw input, so neither expansion (up to ~18x for e.g. U+FDFA) nor
   contraction (canonical composition) can put more than
   MAX_DISPLAY_NAME_LENGTH=80 units into the outbound reply.

4. WHAT THE ADDED NORMALIZATION NEWLY INTRODUCES. The new NFKC call runs on an
   argument that carries no parser-level length cap (the class comment at
   SourceUpsertService.java:79-86 states the 200-char design-tier --name
   guardrail is unimplemented), so it sees up to the inbound body cap. This is
   not a DOS: normalization is sub-millisecond at that size, it executes AFTER
   the network URL probe (AddSourceCommandHandler.java:178-197) which dominates
   cost by orders of magnitude, and /add-source carries its own rate bucket per
   security.md §Rate limiting.

Two further paths were checked and found closed rather than assumed:
  - The fallback branch prior audits flagged advisory — `host == null ?
    identifier : host` (SourceUpsertService.java:295-296), which would put a
    slash-bearing full URL into display_name — is UNREACHABLE from /add-source:
    AddSourceArgs.parseUri (AddSourceArgs.java:207-226) already returns null
    when `uri.getHost()` is null or blank, so the handler only ever passes an
    identifier with a non-null host. The fallback is always a bare host.
  - The reply templates were inspected for a bundle-supplied slash immediately
    preceding the interpolated name, which would have let attacker text follow a
    slash the name never had to contain. None exists: every display-name echo is
    a backtick-wrapped `{0}` (reply.add_source.fresh_insert,
    reply.list_sources.line, reply.unfollow_source.success,
    reply.remove_source.success, reply.confirm.prompt.remove_source in
    infochat-provider/src/main/resources/bundles/en.properties:174, 394, 424,
    416, 412), and the name is passed as a MessageFormat ARGUMENT, never as part
    of the pattern.

The spec amendments the diff makes are accurate rather than aspirational: the
security.md §LLM output sanitizer edit narrows only the exemplar's status and
preserves the residual-risk framing verbatim ("no mechanical guard", "other
reply.* echoes remain unreviewed", "not a proven-safe blanket"), so it claims no
guarantee the code does not deliver.

OUT-OF-MODEL:
  - Human copy-paste of a command an admin reads in bot output. security.md
    §LLM output sanitizer keeps the surface in model ("a copy-pasted reply still
    requires is_admin=true to do anything"), but the residual after any fix — an
    admin choosing to run what they read — is a human factor the model does not
    promise to eliminate. With the slash rule in place there is no longer a
    pasteable command token to begin with.
  - A display name may still contain backticks, so on an adapter advertising
    supportsCodeFormatting a name carrying a backtick run can break out of the
    inline-code span in `Source `{0}` added.` (en.properties:174) and alter how
    the rest of that one message renders — e.g. absorbing the
    reply.add_source.url_visibility_disclosure line into a code block. No
    threat-model bullet commits to reply-rendering integrity, and no command
    token is obtainable without a slash, so this is rendering cosmetics rather
    than a promise gap. The party whose disclosure line is obscured is the
    attacker themselves. Flagged so the user can decide whether the display-name
    constraint should also reject backticks.
  - /list-sources echoes the raw source identifier verbatim
    (reply.list_sources.line {1}, en.properties:394). That is inbound-derived
    text on a deterministic reply surface, but it is mandated by security.md
    §Source URL visibility, and a URI cannot carry whitespace (AddSourceArgs
    .parseUri rejects it), so no argument-bearing admin command can be embedded
    in one. Pre-existing and outside this diff.
  - Sources whose display_name is written by the collector-side bootstrap loader
    do not pass through acceptableOverride. Operator-set config is trusted per
    security.md §Threat model, so this is outside the model.
  - The design-tier 200-char --name parse guardrail remains unimplemented (per
    the diff's own comment at SourceUpsertService.java:79-86). Design notes are
    not the threat model, so this cannot be a finding; noted only because it is
    what leaves the new NFKC call reading up to the body cap.

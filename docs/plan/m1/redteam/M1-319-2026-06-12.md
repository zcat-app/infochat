RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - Local-filesystem write access to the signal-cli data dir now controls the
    D10 mention anchor: an attacker who can edit <data-dir>/data/accounts.json
    (swap the uuid for the configured account's entry) silently misdirects
    mention recognition at the next adapter start — the exact failure shape
    the removed operator-typed property had, relocated from properties file to
    data dir. This is the same trust tier as the Signal identity keys stored
    in the same directory (an attacker there already owns the account), and
    operator-infrastructure compromise is explicitly out of the documented
    threat model ("Operator-set config ... is trusted"; supply-chain /
    operator-infra attacks out of scope). Flagged so the user can decide
    whether docs/design/06-messaging.md §6.5.4 should state the data-dir
    filesystem-permission expectation explicitly.
  - Anchor staleness across a live re-registration: SignalAdapter.start()
    derives the ACI once, before the spawn; the supervised subprocess restart
    path (SignalSubprocess restartHung / onExit) re-spawns signal-cli without
    re-deriving. If the Signal account is re-registered or re-keyed while the
    Provider runs (ACI change), the cached anchor diverges until the next
    full adapter restart — mention recognition silently goes dark rather
    than failing loudly. Exploiting this requires compromise of the bot's
    own Signal account (carrier/recovery attacks on the bot's number), which
    the threat model treats as operator-side; the documented Signal-vs-SimpleX
    admin-placement guidance already covers the account-recovery surface.

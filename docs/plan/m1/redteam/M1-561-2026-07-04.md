RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: INFO-LEAK
    SEVERITY: medium
    PROMISE: security.md §Prompt-injection defenses — "The system prompt
             instructs the model to never follow instructions inside the
             wrapper, to refuse action requests with a **structured refusal
             marker** (the literal token used in v1 lives in design notes)".
             §What lives in design notes keeps "The structured refusal marker
             convention (literal token, prompt phrasing)" secret. The intercept
             the diff edits exists (per its own comment, ChatAgent.java:246-259)
             to enforce that the marker is protocol surface which must NOT be
             delivered verbatim, because "delivering it verbatim leaks the
             injection-defense convention to the counterparty it defends
             against, and lets the LLM author what looks like bot-authoritative
             bracketed status text."
    GAP: The diff reorders ChatAgent.doHandle so stripToolCalls (step 5,
         ChatAgent.java:244) runs BEFORE the refusal-marker intercept (step 6,
         ChatAgent.java:260-265). The intercept predicate is anchored on both
         ends: `trimmedFinalText.startsWith("[REFUSAL:") &&
         trimmedFinalText.endsWith("]")` (line 261). stripToolCalls, when it
         hits a `TOOL_CALL:` substring with no balanced brace, drops everything
         from that substring through end-of-text (lines 445-455, "Partial or
         unbalanced fragment: drop through end-of-text"). When the marker's
         closing `]` sits AFTER an embedded `TOOL_CALL:` fragment, strip
         deletes the `]`, leaving text that starts with `[REFUSAL:` but no
         longer ends with `]`. The post-strip intercept then fails to match and
         the mangled marker flows to sanitize/persist/deliver. Pre-diff (intercept
         before strip) the same input WAS caught, so this is a regression the
         reorder introduces, not a pre-existing gap.
    REPRO: Assume the black-box-LLM threat model (spec §Threat model: "LLMs ...
           can be coaxed into emitting attacker-chosen output"). An attacker
           uses prompt injection (via an untrusted post body surfaced in chat,
           a tool result, or their own chat message) to coax the CHAT_AGENT to
           emit the literal terminal text `[REFUSAL: TOOL_CALL: foo]`.
           TOOL_CALL_PATTERN requires an opening `{`, which is absent, so the
           tool loop does NOT dispatch and returns this text in-line
           (ChatAgent.java:315-317) — no iteration-cap needed. stripToolCalls
           finds the `TOOL_CALL:` substring, appends `[REFUSAL: `, finds no
           brace, and returns `[REFUSAL: ` (line 445-455). The intercept at
           line 261 sees a value that no longer ends with `]`, so it does not
           degrade the turn; the text is sanitized and delivered. The user
           (i.e. the injection counterparty) receives `[REFUSAL:` — the exact
           injection-defense convention the design notes keep secret and the
           intercept is meant to withhold — plus attacker-shaped
           bot-authoritative-looking bracketed text. The same class covers any
           marker whose closing `]` follows an embedded `TOOL_CALL:` fragment
           (balanced-brace variants surface via the post-iteration-cap path,
           ChatAgent.java:357-359).
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

OUT-OF-MODEL:
  - The anchored predicate has always leaked a refusal marker that lacks a
    trailing `]` entirely (e.g. the LLM emits `[REFUSAL: reason` with no closing
    bracket) — this held both before and after the diff and is a pre-existing
    limitation of the two-sided-anchor check, not introduced by M1-561. Flagged
    so the user can decide whether to harden the predicate to a prefix-only or
    normalized-scan form independent of this reorder.

# /redteam M1-222 — verbatim verdict (2026-06-07)

RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: DOS
    SEVERITY: medium
    PROMISE: "**Per-group LLM rate (D47)** — a separate sub-bucket per approved group bounding LLM-triggering operations (chat replies + on-demand `/summary` + `/retry` re-rolls) across all group members. The per-user LLM cap fires first; the per-group cap is the backstop for groups with many active members." (security.md §Rate limiting)
    GAP: The sub-bucket is consulted at exactly one production call site — the chat-mode branch (`infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/InboundRouter.java:617-618`). The only group-scope LLM-triggering re-roll that exists today, `/retry --digest` (`infochat-provider/src/main/java/app/zcat/infochat/provider/command/RetryCommandHandler.java:375-407` → `DigestRetryService.retryDigest`, `infochat-provider/src/main/java/app/zcat/infochat/provider/digest/DigestRetryService.java:61-68`), never calls `tryAcquireGroupLlm` — and it also never draws a per-user `LlmRateCap` token (its only bound is a standalone per-group cooldown in `lastRetryAt`). The new test `groupSlashDispatchDoesNotConsultGroupLlmBucket` (InboundRouterTest.java:633-656 in the diff) pins "no slash dispatch consults the bucket" as intended behavior, cementing the gap. The spec's bullet enumerates `/retry` re-rolls as inside the sub-bucket; the diff delivers the sub-bucket for chat replies only, so a group's aggregate user-initiated LLM consumption is the bucket budget PLUS an independent digest-re-roll budget the bucket never sees. (`/summary` in group scope is vacuously safe today — `SummaryCommandHandler.java:145-151` returns `no_posts_yet` for group scope before any LLM call — but the moment group `/summary` lands, nothing structural forces it through the group bucket.)
    REPRO: In an approved group, a hostile or compromised group admin (1) has members drain the group-LLM bucket with 5 chat messages, then (2) issues `/retry --digest` each time the `DigestRetryService` cooldown elapses. Every re-roll runs the full digest prose generation through the LLM while `tryAcquireGroupLlm` reports the group exhausted — the group's LLM cost exceeds the spec'd per-group budget on a cadence the new cap never observes, and no per-user LLM token is spent either.
    SUGGESTED-FIX-CLASS: rate-limit

  - CATEGORY: DOS
    SEVERITY: low
    PROMISE: "**Per-group LLM rate (D47)** — a separate sub-bucket per approved group bounding LLM-triggering operations ... Profile-driven." (security.md §Rate limiting — the cap value is the operator-configured bound)
    GAP: Eviction-recreation outpaces the refill schedule. `evictIdleBuckets` removes a group-LLM bucket once `lastRefillEpochMillis` is older than `infochat.rate-cap.eviction-threshold` (default `PT10M`, `infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/RateCapBucket.java:60`, sweep at lines 290-295), and `tryAcquireGroupLlm` recreates an evicted key with a FULL token allotment (`new Bucket(groupLlmCap, ...)`, RateCapBucket.java:232-233). Because the eviction threshold (10 min) is shorter than the group-LLM refill window (15 min), a drained-then-idle bucket is forgotten and reborn full at ~10 min, where the refill schedule would have granted only ~⅔ cap. Effective sustained rate ≈ cap per (eviction-threshold + sweep interval) instead of cap per refill window — roughly 1.5× the configured budget.
    REPRO: Members of an approved group drain the 5-token group-LLM bucket in a burst, then keep the group chat-silent for 10+ minutes (slash commands and other groups are unaffected). The sweep evicts the entry; the next burst gets a fresh 5 tokens. Repeating yields ~5 LLM calls per ~10-11 minutes against a configured 5-per-15-minutes cap.
    SUGGESTED-FIX-CLASS: rate-limit

  - CATEGORY: DOS
    SEVERITY: low
    PROMISE: "The per-user LLM cap fires first; the per-group cap is the backstop for groups with many active members." (security.md §Rate limiting) — the backstop should reject without spending the user's budget, the discipline the codebase itself applies elsewhere ("a rate-cap rejection records no timestamp, so the next permitted request still succeeds").
    GAP: In `InboundRouter.java:592-622`, `llmRateCap.tryAcquire(actorId)` consumes a per-user LLM token BEFORE the group bucket is checked; when `tryAcquireGroupLlm` then rejects (line 617-618), no LLM call happens but the sender's global per-user token stays spent. The per-user bucket is actor-keyed, not scope-keyed, so the wasted token also reduces the victim's DM chat / `/summary` / `/retry` budget. Contrast `SummaryCommandHandler.java:173-192` and `RetryCommandHandler.java:167-185`, which deliberately order checks so rejections consume nothing.
    REPRO: A hostile member of a busy approved group keeps the 5-token group-LLM bucket pinned empty (5 cheap chat messages per window). Every other member who tries to chat in that group burns one of their own scarce per-user LLM tokens per attempt and receives only the fixed `group.llm_rate_limit` reply — after a few attempts the victim is locked out of DM chat too, despite never receiving an LLM reply, amplifying one member's in-cap traffic into cross-member LLM-budget exhaustion.
    SUGGESTED-FIX-CLASS: rate-limit

OUT-OF-MODEL:
  - A `infochat.ratelimit.group-llm-refill-window` configured as `PT0S` causes division-by-zero in `tryAcquireGroupLlm` (RateCapBucket.java:238), turning every group chat message into the generic internal-error reply. Operator-set config is trusted per the threat model, so misconfiguration is out of model; a startup-time positive-duration assertion would be cheap hardening.

AUDIT NOTES (non-findings; rationale for CLEAN):

M1-336 is a behavior-preserving refactor that extracts the UTF-8
byte-length arithmetic used at the messaging-adapter ingest boundary
into a single shared class (infochat-messaging-adapter/.../Utf8.java)
and replaces three prior hand-copies / getBytes(UTF_8) allocations with
calls to it. Every threat-model surface the diff touches was checked
against the security.md commitments; no promise is weakened.

1. DOS — inbound body-size cap walk (security.md §Authorization model
   step 1.5/1.7, "the size-cap below still bounds NFKC cost").
   The cap moved from an early-exit walk (InboundRouter.exceedsUtf8ByteLength,
   removed) to a full walk computed once
   (InboundRouter.java:378 inboundByteLength = Utf8.byteLength(raw))
   reused by the cap test (line 410). This is NOT a regression: the
   old code ALSO performed a full walk every message for the
   adapter.message.bytes metric (old AdapterMetrics.utf8ByteLength,
   no early exit) in addition to the early-exit cap walk, so the body
   was walked up to twice; the new code walks it exactly once. Walk
   length is bounded upstream by the adapter codecs, which reject
   inbound bodies over MAX_INBOUND_TEXT_BYTES (16384) before
   constructing the InboundMessage (SignalMessageCodec.exceedsInboundByteCap,
   SimpleXMessageCodec.java:361/472), and the per-(adapter,contact_id)
   rate cap (InboundRouter.java:402) fires before the size check.
   Order/cost class unchanged; no amplification surface opened.

2. Correctness of byte accounting (no spec promise on exact arithmetic;
   design-notes territory). Utf8.byteLength/exceedsByteLength match
   getBytes(UTF_8).length across ASCII/2-byte/3-byte/4-byte-surrogate-
   pair classes (Utf8Test pins this against the getBytes reference).
   For unpaired surrogates the methods diverge from getBytes (which
   would emit a 1-byte '?'), counting a lone high surrogate as 4 and a
   lone low surrogate as 3 — but the Javadoc states this is verbatim
   the accounting both prior hand-copies used, so it is behavior-
   preserving, and over-counting only makes the size cap MORE
   conservative (rejects marginally earlier), never less. No bypass.

3. No auth / ban / invite / admin-tier / audit / isolation logic is
   touched. The diff does not alter any authorization step ordering,
   any DB query, any reply-bundle selection, or any audit write. The
   new metric overload records an integer byte count, never message
   content, so no INFO-LEAK surface is added.

The refactor delivers exactly what the threat model already promised
and changes no security-relevant behavior.

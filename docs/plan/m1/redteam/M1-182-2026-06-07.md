# Red-team audit: M1-182 (in-progress), 2026-06-07

Verbatim threat-actor verdict follows.

```
RED-TEAM VERDICT: FINDINGS

FINDINGS:

- CATEGORY: INJECTION
  SEVERITY: high
  PROMISE: "**Stage 2 verdict** of `INJECTION`, `MALWARE`, or `UNKNOWN` → post stays `QUARANTINED` until admin review." and "Two kinds of posts feed the re-evaluation queue: 1. Posts released with Stage 1 redactions retained because of a **Stage 2 infrastructure failure** … 2. Posts marked **UNKNOWN** by Stage 2" (docs/spec/security.md §Failure handling, §Re-evaluation job). The judge re-roll surface is promised for UNKNOWN posts only; definitively-hostile verdicts are admin-review-only.
  GAP: The "UNKNOWN class" enumeration predicate in infochat-collector/src/main/java/app/zcat/infochat/collector/eval/reeval/ReEvaluationJob.java:393-399 is `status='QUARANTINED' AND stage2_done=TRUE AND stage2_failed=FALSE` — it never checks `stage2_verdict`. A first-pass INJECTION or MALWARE verdict produces exactly that column state (`Stage2VerdictHandler.applyQuarantineVerdict`, infochat-collector/src/main/java/app/zcat/infochat/collector/eval/stage2/Stage2VerdictHandler.java:144-151 → `updatePostQuarantined` with `stage2Failed=false`). So INJECTION/MALWARE-classified posts are swept into the re-eval queue and re-judged every tick up to `unknownCap`. The diff's new BENIGN path (`applyBenignReEval` → `requeueForPipeline`, ReEvaluationJob.java:134-155, 286-296) then auto-releases them: RAW → tagger/entity/embedding → ReadyPromoter → READY + `new_post`. A single BENIGN flip on any re-roll releases content the judge had definitively classified hostile, with no admin ever reviewing it. (The enumeration SQL itself predates the diff, but the diff is the verdict-handling implementation and its requeue path is the concrete release vector; the diff's own javadoc at ReEvaluationJob.java:36-39 codifies the verdict-blind predicate as the UNKNOWN class.)
  REPRO: Adversary publishes a crafted post on any subscribed feed designed to be borderline for the judge model (small local models are noisy). Stage 1 flags it; Stage 2 first pass returns INJECTION → post QUARANTINED (correct). Every `infochat.reeval.poll-interval` tick, ReEvaluationJob re-submits the original (pre-redaction) body to the judge — up to `unknownCap` independent rolls. The first roll that returns BENIGN requeues the post to RAW; the pipeline completes and ReadyPromoter flips it READY and fires `new_post`. The injection payload is now in user-visible retrieval (`searchPosts`/`getPost`/digests/summarizer prompts). The spec says this content class never leaves quarantine without `/quarantine approve`.
  SUGGESTED-FIX-CLASS: trust-boundary-tightening

- CATEGORY: AUDIT-EVASION
  SEVERITY: high
  PROMISE: "**Redactions are lifted only by `/quarantine approve`.** … An admin reviewing the quarantine row is the only path that restores the original span." and "Approve transitions `PENDING → APPROVED` …, restores the original span, and **fires `NOTIFY new_post`**" (docs/spec/security.md §Quarantine workflow) — admin review is the terminal authority over a quarantined post, and the approve action is audit-logged.
  GAP: `approve_quarantine` (infochat-core/src/main/resources/db/migration/V25__quarantine_procedure_remediation.sql:51-56) sets the post READY and restores the original span but never clears `stage2_failed`. An approved infra-failure post therefore stays in the re-eval infra-class enumeration (`stage2_failed = TRUE AND status != 'NEEDS_REVIEW'`, ReEvaluationJob.java:396). The diff's NEW `reHideToQuarantined` (ReEvaluationJob.java:225-234, predicate `status <> 'QUARANTINED'`) will, on the next non-BENIGN judge roll, flip the admin-approved READY post back to QUARANTINED — silently reversing an audited admin action. No audit row records the reversal (the only writes are the verdict UPDATE and status flip, ReEvaluationJob.java:192-203), and `reAnnouncePendingQuarantineRows` matches nothing because the quarantine rows are `APPROVED`, not `PENDING` (ReEvaluationJob.java:245-248) — so the Provider's quarantine cursor never learns of the change either. Because approve restored the original span into `body`, `reconstructOriginalBody` feeds the judge the very content the admin overrode, making a non-BENIGN verdict — and thus the reversal — the likely outcome precisely in the false-positive cases admins approve.
  REPRO: During a Stage 2 outage window, a post is released READY with redactions (`stage2_failed=true`). An admin reviews it, decides the flagged span is a false positive, and runs `/quarantine approve` — span restored, `APPROVE_QUARANTINE` audited, `new_post` fired. On the next re-eval tick the job enumerates the post (flag never cleared), the judge sees the restored span, returns UNKNOWN or INJECTION, and the post is re-hidden to QUARANTINED. The admin's decision is undone with zero audit trail and zero notification; the post silently vanishes from every user-visible query until cap exhaustion lands it in NEEDS_REVIEW.
  SUGGESTED-FIX-CLASS: audit-log-coverage

- CATEGORY: AUDIT-EVASION
  SEVERITY: medium
  PROMISE: "**The transition is audit-logged** as `RE_EVAL_RELEASED` with … `details_json={ prior_verdict, new_verdict='BENIGN', attempt }`, and a throttled admin notification fires … Without this, posts auto-released from `QUARANTINED` after an UNKNOWN-then-BENIGN re-eval reach users with no human reviewer ever having seen the row" (docs/spec/security.md §Re-evaluation job).
  GAP: (a) `priorVerdict` is derived solely from the `stage2_failed` flag (`candidate.stage2Failed() ? "INFRA_FAILURE" : "UNKNOWN"`, ReEvaluationJob.java:135), never from the recorded `stage2_verdict`. The diff's own `recordVerdictAndIncrementCounter` (ReEvaluationJob.java:205-216) writes INJECTION/MALWARE into `stage2_verdict` on earlier attempts; when a later attempt flips BENIGN, the `RE_EVAL_RELEASED` row falsely reports `prior_verdict='UNKNOWN'`, masking exactly the "hostile-classified post auto-released" signal the spec added this audit for. (b) In the `clearStage2Failed` branch (ReEvaluationJob.java:137-152), the `RE_EVAL_RELEASED` audit row and the "Re-eval released post_id=…" admin notification fire even when the post remains QUARANTINED — which happens in the production profile (`release-on-stage2-failure=false`, post quarantined with `stage2_failed=true`) and after any diff-introduced re-hide. The post then needs a second BENIGN via the UNKNOWN-class branch to actually release, producing a duplicate `RE_EVAL_RELEASED` row; the audit trail records two releases, the first of which never happened.
  REPRO: Feed content gets first-pass UNKNOWN; re-eval attempt 1 returns INJECTION (recorded in `stage2_verdict`); attempt 2 returns BENIGN → post released via requeue, audit row says `prior_verdict='UNKNOWN'`. An admin auditing auto-releases for judge flip-flops on hostile classifications cannot see that an INJECTION-classified post was released. Separately, under `release-on-stage2-failure=false`, every quarantined infra-failure post that re-evals BENIGN generates a "released" audit row and admin notification while still hidden.
  SUGGESTED-FIX-CLASS: audit-log-coverage

OUT-OF-MODEL:
- Documented spec deviation, safe direction: docs/spec/security.md §Re-evaluation job says on a non-BENIGN re-eval the `stage2_failed` flag is "preserved **(or set, if the prior verdict was UNKNOWN)**"; the diff deliberately never sets it (javadoc at ReEvaluationJob.java:184-188 argues the spec contradicts its own lower-UNKNOWN-cap rationale). The implementation choice is strictly more conservative (UNKNOWN-class posts exhaust the lower cap faster and reach NEEDS_REVIEW sooner), so it is not an exploitable weakness — but it is an unamended divergence between spec text and code that should be resolved by a spec amendment rather than a code comment.
- The re-hide leaves `ready_at` non-NULL on QUARANTINED posts. I verified every Provider visibility path filters on `status='READY'` (GetPostTool, SearchPostsTool, GetReferencesTool, EligiblePostQuery, DigestPostCollector, NewPostReconciler, NewPostHandler), so no stale-visibility hole exists today — but any future query that keys on `ready_at IS NOT NULL` alone would resurrect re-hidden hostile posts. Hardening note only.
```

RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: DOS
    SEVERITY: medium
    PROMISE: §Authorization model step 1.5 (and §User ban): "Apply the
             per-(adapter, contact_id) inbound rate cap ... The cap runs
             after step 1 ... and before every application-level check
             below, so a hostile flood cannot drive outbound cost via the
             per-inbound fixed-reply paths in steps 2 and 4." §User ban:
             "Transport-level rate cap fires before the ban check (and
             before every other application-level check)." §Rate limiting
             commits a per-(adapter, contact_id) transport bucket and a
             per-group reply/command/LLM cap so all inbound-driven outbound
             cost is bounded.
    GAP: The new group-invitation inbound surface bypasses the step-1.5
         transport rate cap entirely. The cap (`rateCapBucket.tryAcquire`)
         is invoked only in InboundRouter.onMessage (the inbound *message*
         path). The invitation path is a parallel dispatch:
         SimpleXWebSocketClient dispatch case ReceivedGroupInvitation →
         dispatchAsync (diff lines 606-608) → SimpleXAdapter.onGroupInvitation
         → InvitationHandler → AdapterRegistry.dispatchGroupInvitation
         (no rate-cap call, diff lines 793-800) →
         GroupInvitationHandler.handle, which does an UNCONDITIONAL
         `findByAdapterAndContactId` DB lookup for every invitation
         (GroupInvitationHandler.java:66) before any cap is consulted. When
         the inviter is registered+non-banned, it calls
         source.joinGroup(...) → SimpleXAdapter.joinGroup, whose own comment
         states "/_join ... draws no rate token" (diff lines 304-312). The
         ReceivedGroupInvitation frames also share the single bounded
         dispatchQueue/dispatchExecutor with inbound messages
         (SimpleXWebSocketClient INBOUND_QUEUE_CAPACITY), so an invitation
         flood competes with — and can overflow-drop — legitimate inbound
         message processing. Auto-join also bypasses the §3.5 global
         max-groups / per-user group-activation caps, which only fire when a
         `groups` pending row is created at first @mention, not at join.
    REPRO: A registered (registration_state IN ('invited','vouched'),
           non-banned) user — i.e. a normally-onboarded user, no admin
           rights — scripts the creation of N SimpleX groups and invites the
           bot to each. The bot emits N `/_join` outbound commands with no
           per-(adapter, contact_id) bucket consumed, becoming a member of N
           attacker-chosen groups (no upper bound, no admin notification
           until/unless @mentioned). Concurrently the N invitation frames
           occupy the shared bounded dispatch queue; once full, inbound
           DM/group messages from other users hit the overflow-drop path.
           None of this debits the step-1.5 transport bucket because the
           invitation path never routes through InboundRouter.onMessage. The
           spec commits that "a hostile flood cannot drive outbound cost,"
           but this path drives both unbounded outbound `/_join` sends and
           unbounded DB lookups, and degrades the inbound dispatch lane.
    SUGGESTED-FIX-CLASS: rate-limit

OUT-OF-MODEL:
  - Silent group membership with no audit/admin signal. A registered
    inviter can make the bot a silent member of an arbitrary group that
    never gets an admin notification or audit_log row unless/until the bot
    is @mentioned (which creates the §3.5 pending row + throttled admin
    notify). The bot can therefore sit in groups operators are unaware of.
    The threat model's admin-awareness commitment is anchored to pending-row
    creation at @mention, not to the join itself, and §"Audit log writes:
    (none touched)" — so no spec bullet currently *requires* auditing the
    join. Flagged so the user can decide whether group joins warrant an
    audit row / admin notification at accept time.

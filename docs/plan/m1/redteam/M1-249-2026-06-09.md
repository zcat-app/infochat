# Red-team audit — M1-249 (provider lows) — 2026-06-09

Verbatim verdict returned by the threat-actor subagent (fresh context: threat
model `docs/spec/security.md` + the code-only diff of the three legs):

---

The dispatch path no longer echoes the raw payload anywhere: the catch logs a
shape-only message plus the exception (whose message is now content-free), and
the parse failure throws a content-free exception. No remaining sink
reintroduces the raw bytes. This closes an INFO-LEAK hardening gap; it
introduces none.

I've audited all three changes against the threat model:

1. **BanCommandHandler.lookupUser** — removal of an unreachable `adapter == null`
   branch (NullAway-proven non-null source, parameterized SQL). No AUTH-BYPASS /
   PERM-ESCAL / INJECTION regression; the admin-gate and self-ban resolution
   semantics are unchanged.
2. **RateCapBucket refactor** — behavior-preserving extraction. The
   contact-bucket key-space cap (the M1-044a DOS defense) is preserved before
   `computeIfAbsent`; bounded-keyspace buckets correctly omit it; refill math is
   identical. No DOS regression.
3. **NewPostListener** — strengthens info-leak hygiene at the NOTIFY boundary;
   no required signal or audit dropped.

No gap between threat-model promise and delivery. The diff only tightens or
preserves the documented commitments.

RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - The `new_post` NOTIFY channel is emitted by the Collector under its own DB
    role and is internal per the threat model ("The DB is internal — only the
    two services and the operator reach it"). An attacker forging arbitrary
    NOTIFY payloads would require already holding a DB connection with NOTIFY
    rights, which is outside the documented trust boundary. The diff's removal
    of raw-payload echoing is a defense-in-depth improvement on this internal
    boundary rather than a fix for an in-model threat; no model extension is
    warranted.

RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - Mid-prose refusal-marker leak (advisory, pre-existing, NOT introduced by
    this diff). The intercept at ChatAgent.java:265 is prefix-anchored
    (trimmed post-strip text startsWith "[REFUSAL:"), so an LLM reply of the
    shape "here is your answer [REFUSAL: reason]" is neither caught by the
    intercept nor removed by stripToolCalls (no TOOL_CALL substring), and the
    marker is delivered to the user verbatim. This is the deliberate
    "anchored, not substring" design M1-559 shipped (a substring scan would
    let injected content force turn degradation by quoting the token), and
    the diff explicitly preserves it. The documented threat model
    (security.md §Prompt-injection defenses) commits only that the system
    prompt *instructs* the model to emit the structured refusal marker and
    keeps the literal token in design notes; it does not commit that the
    ChatAgent intercept catches every occurrence of the marker in delivered
    text. Marker-interception completeness is therefore an implementation
    defense-in-depth choice, not a spec promise, so this residual falls
    outside the documented model. Flagging so the user can decide whether to
    promote "the refusal marker must never appear anywhere in delivered
    text" to a spec-level commitment (which would then also implicate the
    unchanged two-sided anchors in SummaryProseGenerator.java:119, which miss
    an unterminated "[REFUSAL: x" with no closing bracket).

  - LLM-output Unicode-evasion of the marker literal (advisory, pre-existing).
    The prefix check compares against the ASCII literal "[REFUSAL:"; LLM
    output is not Unicode-normalized before the check (step 1.7 normalization
    is inbound-user-text only). Injected content could in principle coax the
    model to emit a homoglyph/full-width lookalike that evades the prefix
    match. This does not leak the real ASCII convention token (the lookalike
    is attacker-chosen text, not the genuine marker) and applies equally to
    M1-559 and SummaryProseGenerator, so it is a pre-existing, low-value
    surface outside this diff and outside the documented model.

Rationale for CLEAN:
  The diff is a remediation of the prior /redteam M1-561 medium INFO-LEAK
  (post-strip-only two-sided anchor missing "[REFUSAL: TOOL_CALL: foo]" whose
  closing ']' the strip's unbalanced-fragment drop-through eats). The change
  from `startsWith && endsWith` to prefix-only, run after stripToolCalls,
  strictly widens the intercepted set and closes the reported gap without
  opening a new one:
    - stripToolCalls only deletes text and "[REFUSAL:" contains no
      "TOOL_CALL:" substring, so a genuine leading marker cannot be destroyed,
      and a mid-prose marker cannot be turned into a false prefix match.
    - The redteam repro and the unterminated-marker case are now both caught
      (verified against ChatAgent.stripToolCalls at ChatAgent.java:438-462 and
      the intercept at 264-269).
    - The chat-mode intent is audit-logged before the LLM call
      (ChatAgent.java:228 writeAuditRow), so a refused turn is not
      audit-evading; the refused path returns the deterministic bundle string
      with a null pendingCommit (ChatAgent.java:267-268), so no marker text,
      no admin string, and no chat_message rows are persisted or delivered.
    - The WARN log carries userId only, no LLM-authored reason text (D37),
      consistent with §Secrets handling / §User content in exceptions.
  No documented threat-model commitment is left undelivered by the diff.

# Red-team audit — M1-039

Verbatim threat-actor verdict (post-commit, pre-merge audit on
branch tip `m1/M1-039-add-source-handler-hardening`):

```
RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: INFO-LEAK
    SEVERITY: low
    PROMISE: §User ban — "Banned user receives one fixed reply per
              inbound message, regardless of input." §Authorization
              model — "Ban check. If `is_banned=true`: fixed reply,
              stop. No parser, no DB query past the ban check, no
              LLM."
    GAP: infochat-provider/src/main/java/app/zcat/infochat/provider/command/AddSourceCommandHandler.java:117-132
         — In group scope, `lookupActor` returns `Optional.empty()`
         (because `ScopeRef.Group` carries no contact id and
         `contactIdOf` returns `null` for Group), so the in-handler
         ban check at line 118 is a no-op. The `ScopeRef.Group`
         discriminator at line 130 then returns
         `error.add_source.group_admin_only` instead of the
         spec-mandated `error.add_source.banned` literal. The diff
         explicitly documents this as deferred to T2-A/T2-F
         (file:114-115; ticket out_of_scope at
         docs/plan/m1/tickets/M1-039-add-source-handler-hardening.md:84)
         but the threat-model commitment "one fixed reply regardless
         of input" remains unkept until those land. The reorder is
         structurally correct for when an actor identity becomes
         reachable, but no router-level intake gate ships with this
         diff to compensate.
    REPRO: Adversary already banned (`is_banned=TRUE`) on the current
            adapter sends `/add-source https://example.com/feed.xml
            --tags x` into a group scope. The handler responds with
            `error.add_source.group_admin_only` ("Only group admins
            can ...") instead of the fixed banned reply. The
            adversary thus learns (a) that the body was parsed
            beyond the ban check, and (b) the group_admin_only state
            in that scope, neither of which a banned user should
            observe per "regardless of input." Direct material impact
            is minor (no admin action succeeds), but the "one fixed
            reply" invariant is observably violated.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

OUT-OF-MODEL:
  - Cross-adapter contact-id collision in
    `SELECT id, is_admin, is_banned FROM users WHERE contact_id = ?`
    (AddSourceCommandHandler.java:76-77, 211-213) — the lookup is
    keyed on `contact_id` only, not `(adapter, contact_id)`, so two
    adapters minting the same contact-id string would conflate
    identities. This is documented as a known MVP single-adapter
    assumption (file:64-71) and is not new in this diff; M1 mandates
    SimpleX + Signal so a future ticket must widen the SPI before
    either of those adapters is enabled in production. Out-of-scope
    for M1-039 but worth surfacing because the deferral chain
    (T2-A → T3-A) leaves the lookup uncorrected longer than the
    diff's comment implies.

  - `ContactIds.redact` applied to a source URL
    (SourceUpsertService.java:169-171, 209-212) returns
    `https://...xml`-shape redaction for typical inputs, which
    exposes the scheme deterministically. Per §Source URL visibility
    the URL is bot-admin-visible anyway, so this is not a
    confidentiality leak; flagged only to note the helper is reused
    on a non-contact-id input shape and the redaction may not be
    ideal if exception messages leak to less-trusted channels.
```

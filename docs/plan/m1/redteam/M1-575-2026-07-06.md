# Scope audited: M1-575 — /pending admin-actionable-user list.
# Files under audit: PendingCommandHandler.java, PendingUsersDao.java,
# LlmOutputSanitizer.java (+/pending), AuditAction.java (+PENDING_LIST),
# en/cs bundles, PendingCommandHandlerIT.java, plus spec/decisions/design docs.
#
# Threat-model surfaces checked and how the diff satisfies each:
#
# 1. AUTH-BYPASS / PERM-ESCAL — /pending is DM-only + bot-admin-only.
#    PendingCommandHandler.handle rejects non-Dm scope with
#    error.command_dm_only BEFORE any query (mirrors AuditCommandHandler),
#    then lookupActor((adapter,contactId)) + isAdmin() gate. Upstream the
#    InboundRouter already applies the ban check (step 4, snapshot.isBanned)
#    and the probation gate (step 5): CommandPermissions.allowedDuringProbation
#    fails closed for "pending" (not in ALLOWED, not an asset), and
#    unregistered/preban group senders are silent-dropped at step 3. No
#    reachable path to the disclosure without is_admin=true on the inbound
#    (adapter, contact_id). Satisfies §Authorization model steps 3/4/5/7.
#
# 2. INFO-LEAK (cross-adapter / cross-user) — PendingUsersDao scopes every
#    query with "adapter = ?" bound to inboundContext.adapterName(); the
#    admin sees only pending users on their own inbound adapter (D55 intent).
#    Full contact-id disclosure is spec-sanctioned by D55 as an active
#    admin-only DM action surface; §Secrets handling redaction governs
#    passive log/audit channels, not this reply. OutboundDelivery does NOT
#    log reply bodies (channel name + byte-count metrics + SafeLog only), so
#    the unredacted ids never reach non-audit logs. The audit row stores only
#    the admin's own actor_contact_id (redacted by audit_log_view on read)
#    and details_json {"page":N} — no listed user's id is copied into audit.
#
# 3. INJECTION (SQL) — all predicates use PreparedStatement bound params;
#    ACTIONABLE_WHERE has only the literal 'invited' plus bound adapter/cutoff/
#    limit/offset. detailsJson is "{\"page\":" + page + "}" where page is a
#    validated Integer from parsePositiveInt (Integer.parseInt, non-numeric ->
#    usage error), so the JSON is always well-formed. No user prose in any SQL.
#
# 4. DOS — pagination is bounded: effectivePage = min(page, totalPages) caps
#    OFFSET to the real row count even for --page 2147483647; parseInt overflow
#    -> usage error (no ArithmeticException). Page size is config (default 20),
#    not attacker-controlled. The transport-level rate cap (router step 1.5)
#    bounds inbound volume regardless; DM-only + admin-only bounds the caller
#    set to trusted principals.
#
# 5. AUDIT-EVASION — audit-before-effect: the PENDING_LIST row is written and
#    committed in its own transaction BEFORE countActionable/listActionable.
#    Audit-write failure returns error.internal and performs NO disclosure
#    (fail-closed). audit_log is append-only (Provider role INSERT-only;
#    no-update/no-delete triggers), so the actor cannot alter its own row.
#    Every disclosure path is preceded by an audit write; the only paths that
#    skip the audit (group DM-only error, non-admin error, malformed-page
#    usage error) also disclose nothing. AuditAction.PENDING_LIST added.
#
# 6. Sanitizer structural mirror — LlmOutputSanitizer.CLOSED_LIST gains
#    "/pending", matching the commands.md §Permission model bot-admin closed
#    list; the CI equality test (matchSetEqualsSpecClosedList) stays green.
#    The compiled pattern \Q/pending\E(?=$|[^a-zA-Z0-9-]) strips the literal
#    admin token from LLM output without over-matching.
#
# 7. Exception logging — LOG.errorf(e, "/pending query failed") mirrors the
#    sibling AuditCommandHandler pattern; the SQLExceptions carry no
#    user-authored prose (params are adapter/cutoff/limit/offset), so
#    §"User content in exceptions" is not implicated.
#
# No commitment in docs/spec/security.md is left undelivered by this diff.

OUT-OF-MODEL:
  - PII-harvesting by a compromised bot admin: /pending lets any bot admin
    enumerate the full, dialable contact ids of every probation/awaiting-vouch
    user on their inbound adapter in one bounded read. This is the explicit
    D55 design intent (the full id is the functional payload for /vouch //ban),
    it requires an already-trusted admin principal (whose compromise is
    covered by §Per-adapter admin threat profile), and every invocation writes
    a PENDING_LIST audit row. It is therefore inside the "admins are trusted"
    assumption, not a threat-model violation — flagged only so the user can
    decide whether the enumeration surface warrants an explicit residual-risk
    note in §Secrets handling / §Per-adapter admin threat profile.

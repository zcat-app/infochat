OUT-OF-MODEL:
  - Unknown-adapter-name residue in AdminBootstrap.validateContactId
    (infochat-provider/.../startup/AdminBootstrap.java:183-198). The
    validator iterates configured adapter names from the CSV and, when a
    name resolves to NO discovered MessagingAdapter bean, returns silently
    without validating — then ensureAdmin (line 200) still writes a
    users(is_admin=true) row plus a BOOTSTRAP_ADMIN audit row and COMMITS
    its own transaction at line 158. AdminBootstrap is @Priority(200) and
    runs/commits BEFORE AdapterRegistry's gate-2 unknown-name rejection at
    @Priority(300), so a typo'd adapter name with a configured .admin value
    leaves a committed, never-reachable admin row + audit entry behind even
    though boot ultimately aborts at gate-2. This re-creates a weak form of
    the "malformed admin row survives the failed boot" residue the ticket
    exists to eliminate — but only for the adapter-NAME-mistyped case, not
    the contact-ID-mistyped case the validate-before-write order does close.
    It falls OUT-OF-MODEL because the adapter list and admin contact id come
    exclusively from operator-set config, which the threat model
    (security.md §Threat model: "Operator-set config ... is trusted")
    explicitly trusts; an adversary cannot set the adapter name or contact
    id, so this is an operator-footgun / boot-hygiene gap, not a reachable
    adversary escalation. Flagged so the user can decide whether to tighten
    AdminBootstrap to fail-fast on an unresolved adapter name (matching the
    registry's gate-2 semantics) before any write, rather than skipping it.

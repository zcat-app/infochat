OUT-OF-MODEL:
  - Future-regression note (not an attack): the fix's coverage rests on the
    comment-level claim in AdapterRegistry.java:378-381 that the three wiring
    lambdas are "the single provider-side boundary where adapter threads enter
    provider code." Today that is true — MessagingAdapter exposes exactly
    setInboundHandler / setMembershipEventHandler / setGroupInvitationHandler,
    and all three are pinned via runWithApplicationClassLoader
    (AdapterRegistry.java:382-390). But nothing structural (no test over the
    SPI setter set, no wrapper enforced by the interface) prevents a future
    SPI callback setter from being wired without the pin, silently
    re-introducing the F-live-1 silent-drop availability failure for that
    callback class. Flagged for awareness only; not exploitable in this diff.

Audit notes (why CLEAN):
  - The change is availability-restoring, not gate-altering: the D50
    admin-claim / D44 invite routing logic is untouched; only the thread
    context classloader environment around the existing dispatch changes.
    Pre-fix, every first inbound crashed at SimpleXAdminClaim ARC creation and
    was dropped per D37 — the diff closes that DoS-shaped gap rather than
    opening one.
  - Pin scope is correct: runWithApplicationClassLoader
    (AdapterRegistry.java:459-468) saves the adapter thread's loader, runs
    only provider-side code under the application loader, and restores in
    finally, so exceptions still propagate to the adapter's D37 catch
    (SimpleXAdapter.java:781-788, class+stack only, no message bodies) and the
    adapter thread never keeps a leaked application classloader. No
    adapter-controlled code executes under the pinned loader.
  - No new oracle: the test (InboundDispatchForeignContextClassLoaderTest.java:273-276)
    asserts the fixed error.invite.required reply for a body that is neither
    the admin token nor an invite UUID — consistent with security.md
    §Authorization model's "no validity oracle" commitment for the SimpleX
    claim token (invalid token gets the same fixed reply as an invalid
    invite).
  - Test config is profile-scoped: the admin-token value
    "m1-543-live-shape-token" lives only in a QuarkusTestProfile override
    (InboundDispatchForeignContextClassLoaderTest.java:339-345), never in
    shipped configuration; per-run-unique contact ids avoid polluting the
    invite brute-force counter rather than weakening it.

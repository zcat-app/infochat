RED-TEAM VERDICT: CLEAN

No production-reachable gap between the threat model's commitments and the
diff was found. M1-414 adds a dev-only message-injection harness
(DevTerminalHarness) that injects inbound under an arbitrary, attacker-chosen
contact id — a deliberate bypass of trust boundary 1 ("the adapter asserts
identity via a stable, cryptographically anchored ID"). The threat model's
governing requirement for such a seam is that it must NEVER be present in a
production build. That requirement is delivered:

- The harness bean is gated by @IfBuildProperty(name="infochat.dev.harness.
  enabled", stringValue="true") at DevTerminalHarness.java:320. @IfBuildProperty
  resolves at Quarkus augmentation (build) time and defaults enableIfMissing=
  false, so a build that does not set the flag excludes the bean from the jar
  entirely; a runtime property cannot re-enable it. The flag is set in no
  application.properties (only in the diff's own test profile + ticket), so the
  shipped default build does not contain the surface.
- DevTerminalHarnessAbsentTest empirically confirms the bean is unresolvable
  under the normal test profile without the flag (the build-time prod-absence
  proof the threat model relies on).
- Injected messages are not an authorization bypass: deliverDm/
  deliverGroupMention call the InMemoryAdapter's registered InboundHandler,
  which AdapterRegistry wires to InboundRouter.onMessage. So an injected
  directive still traverses the full intake chain (ban check, invite gate,
  probation, per-(user,scope) isolation). Only trust boundary 1 (cryptographic
  identity) is bypassed — consistent with the ticket's stated security note.

OUT-OF-MODEL:
  - Documentation imprecision (not an exploitable gap). The ticket and the
    DevTerminalHarness javadoc (lines 308-312 of the diff) describe a second,
    co-required gate: "it injects InMemoryAdapter, which AdapterRegistry only
    activates under infochat.adapters=inmemory ... Both must hold." The
    mechanism is mischaracterized: AdapterRegistry.inMemoryAdapter()
    (AdapterRegistry.java:112-116) is an @Produces @ApplicationScoped method
    with NO config gate, so the InMemoryAdapter *bean* exists regardless of the
    infochat.adapters value. The actual safety in a flag-enabled-but-non-
    inmemory deployment comes from a different fact: the InMemoryAdapter's
    InboundHandler is null unless AdapterRegistry activates it (handler is set
    only inside the activation loop), so deliverDm/deliverGroupMention throw
    IllegalStateException rather than injecting (InMemoryAdapter.java:176-182,
    253-256). The defense-in-depth therefore holds in effect, but for a
    different reason than documented. This does not weaken the production
    "never ships" guarantee — that rests solely on the build-time
    @IfBuildProperty gate, which is sound and tested — so it is flagged here
    for accuracy rather than as a FINDING. SUGGESTED-FIX-CLASS: other
    (doc/comment correction).

  - DoS via unbounded input file. readNewCompleteLines() calls
    Files.readAllBytes on the configured input file every poll
    (DevTerminalHarness.java:368-372); a very large file could exhaust heap,
    and I/O errors surface as UncheckedIOException from the scheduler thread.
    This is out of the documented threat model: the input file is an
    operator-local, trusted dev artifact ("Operator-set config ... is
    trusted"), the surface is build-time-gated out of production, and the
    threat model scopes adversaries to adapter-delivered text, not local
    files. Noted only so the user can decide whether to bound the read in the
    dev tool. SUGGESTED-FIX-CLASS: other.

RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - Group-admin-driven re-trigger of the widened first-run window
    (checked, does NOT reproduce — recorded so the next auditor does not
    re-derive it). `/group-timezone` lets a group admin move
    `groups.timezone`, which moves the slot's `windowStart`
    (DigestScheduler.java:137-140), and the new lookback fires whenever
    `SummaryCacheRepository.findPreviousBoundary` returns empty
    (DigestWorker.java:183-185). The attack would be: flip the timezone
    repeatedly so each new slot looks like a "first run" and each digest
    renders a full inter-slot post set (up to `infochat.summary.cluster-cap`
    = 200 posts and their per-cluster LLM prose), bypassing the per-user and
    per-group LLM buckets — periodic digests are explicitly exempt from the
    per-group LLM budget (security.md §Rate limiting, "Periodic digests do
    NOT count against user-initiated per-group LLM budget"). It does not
    reproduce: a slot only fires while `now` is inside its 30-minute window
    (DigestScheduler.java:146,156,185), so a firable `windowStart` is always
    within ~30 minutes of now, i.e. later than every already-written
    `summary_cache` row (real digests and missed-slot sentinels alike, both
    written at past instants). `findPreviousBoundary` (max(slot_fired_at) <
    windowStart, expiry-independent) therefore returns non-empty for every
    slot after the group's genuine first one, and the 12h/18h lookback is a
    one-time-per-group cost bounded by the same 200-row SQL LIMIT every
    steady-state digest already pays. Flagged only because a future change
    that prunes `summary_cache` rows, or that relaxes the live-window check,
    would turn this into a real LLM-cost amplifier.
  - First digest can broadcast pre-approval content. A newly approved
    group's opening digest now covers 12h (evening) or 18h (morning) before
    its slot, which can include posts published while the group was still
    `pending`/`rejected` or before the `groups` row existed
    (DigestWorker.java:185, 341-350). commands.md §Periodic group digests
    commits only that "Pending and rejected groups never receive periodic
    digests" and that no catch-up digest is emitted on approval — both still
    hold (no extra slot fires; only the content span of the first legitimate
    slot widens). No confidentiality boundary is crossed: the collector
    applies the D59 world predicate and `status='READY'` inside the SQL
    (DigestPostCollector.java:126-162), a fresh group's world is the
    operator-seeded bootstrap corpus only, and any registered member can
    already retrieve the identical rows in the same group scope with
    `/summary -w 24h` (EligiblePostQuery.java:190-253; the window flag
    accepts up to 168h/30d). Noted so the user can decide whether "first
    digest may predate approval" deserves an explicit spec line.
  - Increased likelihood of the degraded (headlines-only) digest on a
    group's first run. The first digest now carries a full inter-slot post
    set into the same ~30-minute render budget (DigestWorker.java:207-235),
    so it is more likely to blow the deadline and fall to
    `DegradedDigestRenderer`, which security.md §"Sanitizer output never
    contains `](`" records as a deliberate bypass surface with accepted
    residual risk (no translation, outside the `](` adjacency guarantee).
    This is a probability shift on an already-documented-and-accepted path,
    not a removed control — the closed-list protection still runs on that
    path (`llmOutputSanitizer.sanitize(p.title())`,
    DegradedDigestRenderer.java:38), and the same 200-post ceiling is
    already reachable on every steady-state digest.

RED-TEAM VERDICT: CLEAN

The diff (M1-189) is a narrowly-scoped DB grant-hardening migration plus
its integration test and two doc/spec sentence updates. Security-relevant
claims verified:

- `V39` `REVOKE ALL ON FUNCTION approve_quarantine/reject_quarantine FROM
  PUBLIC` correctly removes the Postgres-default PUBLIC EXECUTE that
  V21/V25/V32/V41 left in place. The explicit `infochat_provider` grant
  from V21 (line 118-119) survives a PUBLIC revoke, and `CREATE OR
  REPLACE` (V41) preserves the tightened ACL. The Collector — which the
  threat model declares is exposed to arbitrary untrusted feed content —
  loses its implicit EXECUTE on these `SECURITY DEFINER` functions,
  closing a path where a compromised Collector could call
  `approve_quarantine` to lift Stage-1 redactions. Confirmed by
  `DbGrantsRevocationIT` distinguishing 42501 (ACL denial) from P0001
  (in-body admin check).
- `REVOKE UPDATE ON price_snapshot FROM infochat_collector` restores the
  spec's "INSERT-only; no updates" immutability contract. Tables grant
  nothing to PUBLIC by default, Provider already holds SELECT-only, DELETE
  was already revoked in V17. Access is via the partitioned parent whose
  ACL is checked.
- Checked every `SECURITY DEFINER` function in the migration set:
  `delete_preban_user` (V5/V24) was already PUBLIC-revoked; the only ones
  left with default PUBLIC EXECUTE were the two quarantine functions this
  diff fixes. No other `SECURITY DEFINER` surface is left exposed.

No gap between threat-model promise and delivery.

OUT-OF-MODEL:
  - Flyway migration ordering (not a threat-model promise, not an attack —
    advisory only): V39 is being introduced with a version number *below*
    an already-committed migration (V41,
    `infochat-core/src/main/resources/db/migration/V41__approve_quarantine_clears_stage2_failed.sql`).
    Flyway runs with `migrate-at-start=true` and no `out-of-order=true`
    override (`infochat-collector/src/main/resources/application.properties:80`).
    On a fresh/greenfield database all migrations apply in version order,
    so the revocations land correctly and the test suite (DevServices
    fresh DB) passes. On any database that has already migrated through
    V41, Flyway's default validation rejects the lower-versioned V39 and
    `migrate-at-start` fails the boot — a fail-safe (the service refuses
    to start; it does not silently skip the revocation), so this is a
    deployment-correctness concern, not a silent privilege gap. Surfaced
    so the reviewer/operator can confirm M1 is still pre-deployment
    greenfield before this lands.

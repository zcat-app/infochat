OUT-OF-MODEL:
  - pg_cancel_backend cross-borrower cancellation residual (CancellationService.java:71-80).
    The remediation gates pg_cancel on `workerInterrupted` (the handle monitor's
    open-gate signal), which closes the common stale-cancel window. A narrow residual
    remains and is documented as inherent: between the gate check returning true and
    the cancel SQL reaching PostgreSQL, userA's worker can finish, release its pooled
    DB connection, and userB's worker can re-borrow that same backend pid and start a
    scope-filtered read. `pg_cancel_backend(pid)` then cancels userB's query, failing
    userB's turn (degrades to the chat-unavailable reply). This is a cross-user
    AVAILABILITY/liveness blip, not a data leak: no other-user state, memory, or saves
    are disclosed, and the query userB runs is already its own scope-filtered read. The
    documented per-(user,scope) isolation promise (CLAUDE.md §Key conventions;
    security.md §Trust boundaries) is about state/memory/saves not leaking across users —
    it does not commit that one user's /stop can never perturb another user's operation.
    The window is doubly bounded (Postgres discards cancels against idle backends; the
    connection must be re-borrowed AND mid-query within a microsecond window) and the
    impact is a single self-healing failed turn. Flagged so the user can decide whether
    to extend the model to cover cross-user spurious query cancellation; it is not a
    violation of any current spec commitment.

  - Stale-interrupt cross-user confinement (the prior-round remediation) is sound. The
    handle monitor makes interruptWorker()'s check-then-interrupt mutually atomic with

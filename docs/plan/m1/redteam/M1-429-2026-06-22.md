FINDINGS:
  - CATEGORY: AUTH-BYPASS
    SEVERITY: high
    PROMISE: Trust boundary #7 (security.md §Trust boundaries):
             "The SimpleX adapter speaks an unauthenticated WebSocket bot
             API to a co-located `simplex-chat` subprocess it spawns; there
             is no session, cookie, or token... That 'no authentication'
             property is sound only while the channel stays loopback: the
             shipped default binds the adapter's ws-port to loopback.
             Exposing it beyond the host — binding off-loopback or
             forwarding the port — is an explicit operator action, never a
             default, and voids the property: any host that reaches the
             port can then drive the bot's SimpleX identity with no
             credential." Design 06-messaging.md §6.4.1 line 492 restates
             "WebSocket to the local simplex-chat on a loopback port".
    GAP: SimpleXSubprocess.java:162-168 (commandFor). The prior invocation
         pinned the bind interface explicitly with
         `"--network", "ws://127.0.0.1:" + config.wsPort()` — the literal
         `127.0.0.1` host was the mechanism that delivered the "binds to
         loopback" promise. The diff replaces that with
         `"-p", Integer.toString(config.wsPort())`, which passes only a
         port and NO interface/host argument. The loopback bind now rests
         entirely on an undocumented default of the `simplex-chat -p` flag.
         Nothing in the diff, the changed file, the config object
         (SimpleXConfig exposes only binary/dataDir/wsPort — no bind-host),
         or a compose host-port mapping (the subprocess is spawned directly
         on the host, not in a port-mapped container) constrains the bind
         to loopback. The new unit test
         (SimpleXSubprocessTest.commandForUsesPortFlagAndInDirDbPrefix)
         asserts the `-p`/`-d` flag shape but does NOT assert that the
         resulting server binds to 127.0.0.1 only — the security-relevant
         property is untested. The javadoc at lines 159-160 documents only
         that `-p` "runs the chat server ... on the configured port" and
         is silent on the bind interface. If `simplex-chat -p` defaults to
         binding all interfaces (0.0.0.0 / `::`), the credential-free bot
         WebSocket is reachable from the host network BY DEFAULT, which is
         precisely the "never a default" state trust boundary #7 forbids.
    REPRO: Operator deploys with the shipped default (no extra firewalling,
           trusting the spec's "binds to loopback by default" promise) on a
           multi-tenant or LAN-reachable host. simplex-chat is launched as
           `simplex-chat -d <dir>/simplex_v1 -p 5225`. A co-located but
           untrusted process, a container neighbor, or any host on the same
           L2 segment connects to <host-ip>:5225, opens the WebSocket, and —
           with no token, cookie, or session required (boundary #7) — issues
           bot-API commands as the bot's SimpleX identity: read inbound DMs,
           send messages, drive the D10 trust anchor. The operator never
           took the "explicit action" the spec says is required to expose
           the port; the default invocation did it for them. The system
           should not have allowed the credential-free port to leave
           loopback without an explicit operator opt-in.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

## Follow-up disposition (2026-06-22): HIGH finding VERIFIED FALSE

The high AUTH-BYPASS finding's premise — "if `-p` defaults to all interfaces,
the credential-free bot WebSocket is host-reachable BY DEFAULT" — was tested
directly against the production binary and is **empirically refuted**.

Method: fetched the SHA-pinned `simplex-chat` v6.5.4 binary (sha256
`8c33b69e…ab655`, identical to `Dockerfile.jvm` and verified before execution),
started the chat server with `-p <port>`, and enumerated its listening sockets:

```
LISTEN 0  1024  127.0.0.1:5599  0.0.0.0:*  users:(("simplex-chat",pid=...))
```

Falsifier (any non-loopback listener, IPv4 OR IPv6): NONE — the only socket the
process opened was `127.0.0.1:<port>`. No `0.0.0.0`, no `::`.

Conclusion: `-p` binds **loopback only** by default, so trust boundary #7's
"shipped default binds the ws-port to loopback" holds. No auth-bypass exposure;
severity downgraded high → informational. The legitimate residual — the loopback
guarantee was implicit/undocumented in code (the old `--network ws://127.0.0.1`
made it explicit) — is closed on the M1-429 branch by a refine that documents
the verified default in the `commandFor` javadoc. The `-p` syntax has no host
argument, so a self-documenting comment is the strongest available anchor.

## Audit run 1 (commit 85c88c9 — M1-041 implementation tip)

RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: AUDIT-EVASION
    SEVERITY: medium
    PROMISE: docs/spec/security.md §LLM output sanitizer — "Every match is audit-logged (per-occurrence, not throttled)." Reinforced by §Secrets handling which frames "audit-logged" as a write to the durable `audit_log` table (redaction hook, audit_log_view, append-only trigger, role grants all reference that table). The promise is durability, not "best-effort log line."
    GAP: `infochat-provider/src/main/java/app/zcat/infochat/provider/llm/LlmOutputSanitizer.java:215-239` — `emitAuditRows` opens its own short-lived autoCommit connection per matched token (line 228), catches `SQLException` (line 230), logs `errorf`, and continues to the next token. The closed-list rewrite has already finished at line 134; the rewritten user-visible text is returned at line 136 regardless of whether the corresponding audit row reached the database. There is no retry, no in-memory queue, no surrounding transaction the caller could roll back, and the WARN log at line 190 is process-local — not the durable `audit_log` row the spec pins. The fail-soft choice is acknowledged in the inline comment ("we cannot fail the user-visible reply because the audit row failed") but it directly contradicts the spec's "every match" wording.
    REPRO: (1) Adversary triggers any LLM output flow whose model emits a closed-list token (e.g., a chat prompt that coaxes a small LLM into emitting `/ban …` or `/grant-admin …`). (2) Concurrently, the audit_log INSERT path is degraded — e.g., DB connection pool exhausted, a long-running admin query holding a lock that conflicts with the append-only INSERT, a network blip between pgjdbc and Postgres, or a Stage 1 watchdog redaction-loop in another thread saturating the pool. (3) `auditLogWriter.write(conn, row)` throws `SQLException`; the catch logs and returns. (4) The user receives the sanitized reply; no durable `audit_log` row exists. The bot-admin reviewing `/audit` later sees zero `LLM_OUTPUT_SANITIZED` rows for this incident, violating the per-occurrence durability commitment. A patient adversary can correlate prompt-injection probes with operator load windows to surface this gap.
    SUGGESTED-FIX-CLASS: audit-log-coverage

## Audit run 2 (commit e7c0c9b — fail-loud fixup on top of 85c88c9)

RED-TEAM VERDICT: CLEAN

The audit-1 medium AUDIT-EVASION finding is closed. End-to-end
verification:

  1. `LlmOutputSanitizer.emitAuditRows` now wraps all per-match writes
     in a single transaction (`setAutoCommit(false)` + `commit()`);
     on any `SQLException` it throws `IllegalStateException` wrapping
     the cause.
  2. `sanitize()`'s javadoc declares the throw; the method bubbles
     it unchecked.
  3. `SummaryCommandHandler.appendClusterBlock` (the production
     caller) does not catch — the exception propagates up.
  4. The `InboundRouter` runtime-exception handler logs and returns
     `INTERNAL_ERROR_REPLY` to the user; the sanitized text with
     stripped closed-list tokens is NOT sent.
  5. New IT `LlmOutputSanitizerAuditRowIT.auditWriteFailureAbortsSanitizeFailLoud`
     pins the fail-loud path with a `DataSource` that throws on
     `getConnection()`.

OUT-OF-MODEL:
  - `DefaultRedactionHook`'s watchdog fail-closed branch returns the
    literal string `"[REDACTED]"` (no quotes) for the entire
    `details_json` field. `AuditLogWriter` binds `details_json` with
    a `?::jsonb` cast (`infochat-core/.../AuditLogWriter.java:84`).
    PostgreSQL rejects `[REDACTED]` as invalid JSONB, so a
    watchdog-firing input causes the surrounding audit INSERT (and
    therefore the surrounding admin action, when audit is inside the
    dispatch transaction) to roll back. The spec's "fail-closed on
    regex timeout" intent is satisfied (raw value never emitted), but
    the placeholder shape would more reliably preserve the audit trail
    if it were valid JSONB (e.g. `"\"[REDACTED]\""` as a quoted string
    or `"{\"_redacted\":true}"` as an object). Triggering the watchdog
    with a 100ms cap against the seven well-bounded catalogue regexes
    is unlikely in practice and the only inputs into a redacted field
    today are operator-controlled (admin `/ban --reason`, bootstrap
    path) — so this is a defense-in-depth observation, not a current
    exploit. Flagged for the operator to decide whether to harden the
    placeholder to valid JSONB or accept the current shape.

## Audit run 3 (commit 72e9297 — JSONB-fallback fixup on top of e7c0c9b)

RED-TEAM VERDICT: CLEAN

The audit-2 OUT-OF-MODEL observation is closed end-to-end:

  1. New constant `REDACTED_FIELD_JSONB = '{"_redacted":true,"reason":"regex_watchdog_timeout"}'`
     replaces the bare `[REDACTED]` literal in the
     `RegexInterruptedException` catch branch of
     `DefaultRedactionHook.applyCatalogue`. The string is a valid
     JSONB document; the `?::jsonb` cast in `AuditLogWriter` accepts
     it; the surrounding dispatch transaction does NOT roll back.
  2. The per-match `REDACTED_PLACEHOLDER` stays `"[REDACTED]"` —
     it lives inside a JSON string context (e.g.
     `{"key":"[REDACTED]"}`), so it was always valid at the field
     level. Only the whole-field fallback needed the JSONB shape.
  3. `RedactionHookTest.watchdogFiringFailsClosed` now asserts
     against `REDACTED_FIELD_JSONB` and pins the JSONB-validity
     properties (starts with `{`, `_redacted=true` flag, `reason`
     key for operator triage).
  4. New IT `AuditLogWriterIT.watchdogFallbackIsValidJsonb` writes
     the fallback through the real `?::jsonb` cast against
     Testcontainers Postgres and asserts the row materializes with
     the expected keys after JSONB round-trip.

The spec's "fail-closed on regex timeout: a timed-out match treats
the whole field as redacted rather than emitting it raw" is now
delivered without the downstream JSONB-cast collateral that would
have rolled back the surrounding admin-action transaction. The
audit-1 medium AUDIT-EVASION finding remains resolved from
commit e7c0c9b.

No new gaps surface. M1-041 is ready for `/m1-tick merge`.

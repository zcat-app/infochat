RED-TEAM VERDICT: CLEAN

The diff replaces the former single last-registered-wins `replyTarget` with a `name()`-keyed `replyTargets` map and routes every outbound reply back through the exact adapter that delivered the inbound (resolved by the registry-supplied `adapterName`). This strengthens, rather than weakens, the cross-adapter isolation invariant (§Trust boundaries item 1; §Per-adapter admin threat profile "Cross-adapter elevation is impossible by design").

Key checks performed and why each promise holds:

- Cross-adapter identity-space bleed at the reply layer: the `adapterName` passed to `sendReply` originates from `adapter.name()` captured in the registry's activation loop (AdapterRegistry.java:279-280), not from any user-controllable field of `InboundMessage` — the comment confirms the SPI deliberately carries no adapter-identity field. A user on adapter A cannot spoof a reply onto adapter B. The bind key (`setReplyTarget` → `adapter.name()`, InboundRouter.java:304) and the resolve key (`replyTargets.get(adapterName)`, InboundRouter.java:627) are the same trusted value. The diff explicitly removes the old last-wins fallback (InboundRouter.java:631-637).

- User-ban fixed-reply commitment (§User ban "Banned user receives one fixed reply per inbound message"; step 4): the ban reply still fires once per inbound (InboundRouter.java:425) and now ships through the delivering adapter. The null-target drop branch is reachable only when no adapter is bound under that name — a test-wiring miss or teardown race, not a normal-operation state, since the registry binds every activated adapter's target before wiring its handler.

- Duplicate-name dedup gate (AdapterRegistry.java:153-160) operates on the `infochat.adapters` CSV, which the threat model classifies as trusted operator config; it fails fast on `"x,x"`. Two distinct beans sharing a `name()` would collapse map entries, but that is a deployment/code defect outside the documented threat model (operator config trusted), not an attacker-reachable condition.

- Log safety: the new error line (InboundRouter.java:636) logs the registry-canonical `adapterName` (no user-controlled bytes → no log injection) and redacts the scope id via `ContactIds.redact`, consistent with §Secrets handling.

- Concurrency: `replyTargets` is a `ConcurrentHashMap`; `resetReplyTargets()` clears before the rebind loop on idempotent restart, mirroring the existing `activatedAdapters.clear()`. No TOCTOU exposure introduced (start() is the @PostConstruct/test path, not concurrent with live dispatch in normal operation).

All `sendReply` call sites were migrated (no leftover single-target reference). The test-only changes rebind fakes' `name()` to match the inbound `adapterName` the tests deliver; assertion semantics are unchanged.

No findings. No out-of-model advisories beyond the two-beans-same-name deployment note above, which the trusted-config boundary already covers.

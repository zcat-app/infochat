RED-TEAM VERDICT: CLEAN

The diff is a narrow Signal-adapter hardening change (M1-293). Every
threat-model commitment its surfaces touch is upheld or strengthened.

Reviewed against the threat model (docs/spec/security.md):

1. Mention-span overflow DoS (DOS category). The central fix widens the
   bounds guard in SignalGroupHandler.stripBotMentions to do the addition
   in long before comparing:
     SignalGroupHandler.java:221
       if (start < 0 || length <= 0 || (long) start + (long) length > body.length())
   A hostile mention entry (start=Integer.MAX_VALUE, length=1) previously
   wrapped the 32-bit sum negative, slipped the ">" guard, and threw out of
   StringBuilder.delete, silently dropping the whole group message — a
   per-message DoS of group functionality. The widened guard skips the
   overflow span and still dispatches. Verified the test pins exactly this
   (SignalGroupHandlerTest.overflowMentionSpanSkipped_messageStillDispatched).
   Falsifier checked: a start value > Integer.MAX_VALUE would be truncated by
   Parsson getInt -> BigDecimal.intValue() wrap, but any resulting value is
   re-bounded by the same guard against body.length(); worst case strips a
   wrong in-bounds span, message still dispatches — no throw, no DoS.

2. D10 display-name-never-authoritative (PERM-ESCAL / INFO-LEAK). The diff
   threads attacker-controlled signal-cli sourceName into Identity.displayName
   on both DM (SignalMessageCodec.java:246-247, SignalJsonRpcClient.java:849-850)
   and group (SignalGroupHandler.java:177-178) paths. Falsifier checked:
   grepped infochat-provider/src/main for Identity.displayName() consumption —
   the provider never reads it for authorization, and the only .displayName()
   call sites are asset/source display names, not Identity. Identity.java:13-17
   documents contactId as the sole authorization anchor. No leak path: grepped
   infochat-messaging-adapter/src/main — sourceName is only stored into the
   Identity/ReceivedDm record, never interpolated into any log statement (the
   membership-dispatch log at SignalGroupHandler.java:274 logs class name +
   groupId only). No log-injection or INFO-LEAK surface introduced.

3. Mention-recognition trust anchor (AUTH-BYPASS). botMentioned
   (SignalMentionParser.java:57-78) is unchanged and remains a constant-time
   ACI byte compare with no display-name matching — consistent with the spec's
   "display-name-based @mention recognition is forever out of v1."

4. Rate caps (DOS). Capability values move maxSendsPerSecond 8->5 and
   minEditInterval ZERO->600ms (SignalAdapter.java:127-138). The threat model
   leaves these profile-driven (design notes); the change strengthens outbound
   DoS resistance, never weakens it.

5. Launch-failure classification. Doc-only change (docs/design/06-messaging.md)
   making an initial signal-cli launch IOException fail-fast as a deterministic
   operator-config error rather than burning the restart budget; per-adapter
   resilience and readiness rules are unchanged. No security commitment broken.

Inbound byte cap (SignalGroupHandler.java:150-154) and timestamp validation
(165-172) are untouched and still enforced before dispatch.

No gap found between threat-model promise and diff delivery.

RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - General-assistant framing turns the chat agent into an arbitrary-topic
    LLM responder. ChatPromptBuilder.CHAT_SYSTEM_PROMPT_TEMPLATE was rewritten
    from "Answer questions using only the tools provided and the conversation
    history" to "Answer any question the user asks ... answer from your own
    general knowledge." Any registered (post-invite, non-probation) user can
    now use the bot as a general LLM, not just a feed search surface. This is
    bounded by the existing per-user and per-group LLM rate caps
    (InboundRouter llmRateCap.tryAcquire / tryAcquireGroupLlm) and does not
    open a data-exfiltration path (every tool remains SQL-scope-filtered, so a
    coaxed LLM still cannot reach another user's data). The documented threat
    model commits no chat-topic restriction, so this is a product/cost decision
    outside the model — flagged so the user can decide whether a topic gate or
    a tighter aggregate LLM budget is wanted.
  - ivfflat future density side-channel. design/05-llm-and-embeddings.md and
    the SemanticSearchTool comment state that the iterative-scan exactness
    (which eliminates the recall-crowding density oracle) is an HNSW property:
    the deferred per-profile ivfflat design has no strict_order iterative-scan
    mode, so an un-deferred ivfflat profile would revert to a post-filtered
    top-k whose recall shrinks with unsubscribed-content density, re-opening a
    coarse density oracle. v1 ships HNSW on every profile (§5.5), so this is
    not currently reachable; flagged so it is re-audited if/when ivfflat is
    un-deferred. Subscription isolation (no unsubscribed post surfaces) holds
    on both paths regardless.
  - The deterministic pre-fetch's embedding HTTP round-trip
    (SemanticSearchTool.execute: embeddingProvider.embed(...)) now runs on the
    user-facing hot path on every chat turn, BEFORE the DB probe. The amended
    §Failure-handling "bounded" claim cites statement_timeout, which caps only
    the pgvector probe, not the embed HTTP call; the embed call's boundedness
    relies on the local embedding backend's own timeout config. Not
    adversary-reachable — the backend is trusted local infra (D54) and the
    query text cannot force a local embedder to hang — and turn concurrency is
    bounded by the per-user LLM rate cap; noted as a robustness observation
    only.

FINDINGS:
  - CATEGORY: DOS
    SEVERITY: low
    PROMISE: docs/spec/security.md §Rate limiting, Per-group LLM rate (D47):
             "Periodic digests do NOT count against user-initiated per-group
             LLM budget (they are system-initiated; the aggregate system LLM
             budget is the backstop for digest cost)." The digest render is
             therefore the one LLM-spending surface the threat model exempts
             from every per-user and per-group bucket, and it names a single
             backstop for it.
    GAP: The named backstop does not exist in code (grep for an aggregate /
         global / system LLM budget returns only prose in docs/spec,
         docs/design/04-security.md:692 and redteam notes; the only
         implemented ceilings are the per-user LlmRateCap, the D47 per-group
         bucket and per-task concurrency semaphores). This diff does not
         create that gap — it is pre-existing and explicitly recorded as
         awaiting a decision in
         docs/plan/m1/tickets/M1-758-...md:30-44, and two prior M1-756 audit
         rounds declined to attribute it. What this diff DOES is install the
         sole regression guard for the mechanism that actually stands in for
         the missing backstop — M1-763's interrupt-driven render cancel — and
         it installs it on the wrong thread type.
         - infochat-llm-adapter/src/test/java/app/zcat/infochat/llm/impl/HttpProviderSharedPipelineTest.java:219-253
           asserts the two-part contract (zero outbound requests on an
           already-armed interrupt; flag re-armed by
           LlmHttpSupport.sendForBody:190-194) on the JUnit **platform**
           thread.
         - The production path this guards runs on a **virtual** thread:
           infochat-provider/src/main/java/app/zcat/infochat/provider/digest/DigestWorker.java:59-60
           (`Executors.newVirtualThreadPerTaskExecutor()`), submitted at
           DigestWorker.java:222 and interrupted at DigestWorker.java:256
           (`renderFuture.cancel(true)`).
         - The diff asserts thread-type independence rather than testing it
           (HttpProviderSharedPipelineTest.java:233-235: "A platform thread is
           deliberate. The send() entry check is thread-type independent...").
           The repo's own countervailing evidence sits two modules away:
           infochat-provider/src/test/java/app/zcat/infochat/provider/llm/LlmOutputSanitizerAuditRowIT.java:169-178
           records that on a virtual thread an armed interrupt makes socket
           I/O fail with "Closed by interrupt" while "An interrupted PLATFORM
           thread completes socket I/O normally, so this same test run on the
           JUnit thread passes against the unfixed sanitizer and proves
           nothing." So interrupt-plus-socket semantics are already known, in
           this codebase, to diverge by thread type for the adjacent leg of
           the same cancellation path.
         - The diff itself states nothing else covers this
           (HttpProviderSharedPipelineTest.java:222-231: "which nothing else in
           the suite exercises... DigestWorkerTest asserts on a stub rather
           than the transport"), confirmed by grep: no other test in any module
           exercises an already-armed interrupt against the LLM transport, and
           none does so on a virtual thread.
         Net effect: the only volume ceiling on an orphaned digest render's
         generative spend is verified green by a test that does not execute the
         code path shape production uses, for a surface the threat model
         exempts from every other bucket.
    REPRO: 1. Operator routes SUMMARIZER/TRANSLATOR to a remote provider (the
              supported `remote-llm` / DeepSeek posture) and a group runs
              `digest_mode=full` with a large post set, so
              DigestRenderer.renderSections issues one generative call per
              cluster plus per-section roll-ups.
           2. An attacker-influenced condition that lengthens the render —
              feed volume the collector admitted, or provider latency — pushes
              the render past `slot.windowEnd()`. DigestWorker.java:227 times
              out, degrades, and calls `renderFuture.cancel(true)`.
           3. The render loop continues to completion by design
              (DigestWorker.java:252-255). Every remaining generative call is
              a no-op ONLY IF `HttpClient.send`'s already-armed-interrupt entry
              check fires identically on the virtual thread carrying the
              render. If it does not — a JDK upgrade, or a virtual-thread
              specific send path — each remaining cluster issues a real
              outbound request against a discarded result.
           4. Nothing fails: the guard added by this diff still passes (it runs
              on a platform thread), DigestWorkerTest asserts on a stub, and
              §Rate limiting's named aggregate backstop does not exist to cap
              the volume. The spend is unattended, per-slot, per-group, and
              repeats every digest slot. The system should not have a
              bucket-exempt LLM surface whose only ceiling is guarded off the
              execution shape it runs on.

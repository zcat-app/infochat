# Red-team verdict — M1-044c (2026-05-22)

RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: AUDIT-EVASION
    SEVERITY: high
    PROMISE: docs/spec/security.md §Secrets handling: "Audit-log writes pass through a redaction hook that masks values matching a **closed catalogue of API-key shapes**. The catalogue's v1 baseline (spec-level commitment) is: OpenAI-style `sk-…`... Generic 32+-character hex / base64 strings adjacent to the case-insensitive substrings `api[_-]?key`, `secret`, `token`, `password`, `bearer`."
    GAP: `BanCommandHandler.insertAudit` (infochat-provider/src/main/java/app/zcat/infochat/provider/command/BanCommandHandler.java:165-189) writes `details_json` via raw `ps.setString(9, detailsJson)` with no redaction hook applied. The `ban_reason` is JSON-escaped but never passed through the spec-promised API-key catalogue. Same gap in `InviteCommandHandler.insertAudit` (line ~357-381) and `UnbanCommandHandler.insertUnbanAudit` (line ~292-313). The implementation explicitly defers M1-041 ("the M1-041 AuditLogWriter consolidation is deferred").
    REPRO: A bot admin issues `/ban victim --reason "key=sk-ant-api03-abcd1234ABCD1234abcdEFGH5678ijklMNOP"`. The handler writes the API-key-shaped reason verbatim into `audit_log.details_json`. Any operator with audit-log SELECT rights now sees the key. Spec promises this surface is redacted at audit-write time, but no hook is on the write path.
    SUGGESTED-FIX-CLASS: audit-log-coverage

  - CATEGORY: AUTH-BYPASS
    SEVERITY: high
    PROMISE: docs/spec/security.md §What's intentionally NOT in v1: "Two-factor confirmation for ban — single-step confirm-within-window is enough for v1." (i.e., single-step confirm-within-window IS in v1.) docs/spec/security.md §Invite-code registration: "`--open` ... Requires confirm (broader blast radius)" and "`/invite revoke` requires confirm."
    GAP: `BanCommandHandler.handle` (infochat-provider/src/main/java/app/zcat/infochat/provider/command/BanCommandHandler.java:131-243) ships `/ban` with no confirm gate — the handler executes the BAN + INVITE_REVOKE transaction on the first inbound `/ban` message. `InviteCommandHandler` explicitly states "Confirm-gate deferred ... M1-044c ships without the confirm gate ... v1 is a deliberate temporary spec deviation" (lines 59-66), and `handleCreate`/`handleRevoke` execute their mutations directly.
    REPRO: An attacker who briefly gains the admin's chat session (shoulder-surf, unlocked phone, an open SimpleX client) types `/ban <legit-user>`, `/invite create --adapter signal --open`, or `/invite revoke <stale-code>` and the mutation commits immediately. Spec requires a confirm-within-window step to bound this exposure; the diff has none.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

  - CATEGORY: AUDIT-EVASION
    SEVERITY: medium
    PROMISE: docs/spec/security.md §Authorization model step 8: "Audit-log the intent." docs/spec/security.md §Per-adapter admin threat profile (admin actions on a single-adapter compromise must be auditable).
    GAP: `InviteCommandHandler.handleRevoke` (infochat-provider/src/main/java/app/zcat/infochat/provider/command/InviteCommandHandler.java:436-470) writes the INVITE_REVOKE audit row only AFTER `lockPendingInviteId` succeeds. When the code is absent or already-REVOKED, the function rolls back and returns `error.invite.revoke_not_pending` with NO audit row. Step 8 commits to logging the intent, not just the effect.
    REPRO: A bot admin (or attacker with the admin's session) issues `/invite revoke <random-uuid>` repeatedly to brute-force probe for valid PENDING codes. The success path writes one audit row; every failed attempt leaves zero audit trail. An offline review of the audit log cannot reconstruct the probe attempt.
    SUGGESTED-FIX-CLASS: audit-log-coverage

  - CATEGORY: PERM-ESCAL
    SEVERITY: medium
    PROMISE: docs/spec/security.md §Per-adapter admin threat profile: "Cross-adapter elevation is impossible by design (`/grant-admin` is inbound-adapter-scoped). A compromised Signal admin cannot grant admin on SimpleX without also compromising a SimpleX admin's chat session." Also §Per-adapter admin threat profile cautions that admin placement on the lower-trust adapter (Signal) carries SIM-swap and account-recovery risk.
    GAP: `InviteCommandHandler.handleCreate` (infochat-provider/src/main/java/app/zcat/infochat/provider/command/InviteCommandHandler.java:215-237) verifies the actor is admin **on the inbound adapter** (line 219-220), then mints an invite for **any** target adapter named in the `--adapter` flag (line 227-237). There is no requirement that the actor also holds admin on the target adapter. A compromised Signal admin can mint a SimpleX invite that the SimpleX adapter will honor on first DM, registering a fresh user under the attacker's control on the high-trust adapter.
    REPRO: Attacker compromises a Signal admin's session (SIM-swap, per spec §Per-adapter admin threat profile). From the Signal chat, attacker issues `/invite create --adapter simplex --open` (or `--contact <attacker-simplex-id>`). The InviteCommandHandler validates the actor is `is_admin=TRUE` (true, Signal admin row), validates `simplex` is in the enabled-adapters set (true), and mints the invite. The attacker now uses the code on SimpleX to register a new identity. While they don't gain admin on SimpleX directly, they have established a high-trust-adapter foothold the spec said cross-adapter elevation should not enable.
    SUGGESTED-FIX-CLASS: missing-auth-check

  - CATEGORY: INFO-LEAK
    SEVERITY: low
    PROMISE: docs/spec/security.md §Secrets handling: "Contact IDs are logged in redacted form (prefix + ellipsis + suffix) outside the audit log."
    GAP: `BanCommandHandler.lookupUser` (infochat-provider/src/main/java/app/zcat/infochat/provider/command/BanCommandHandler.java:255-271), `InviteCommandHandler.lookupUser` (line 540-556), `UnbanCommandHandler.lookupUser` (line 256-272), and several other catch-blocks wrap the SQLException into an `IllegalStateException` whose message contains `"contact_id=" + ContactIds.redact(...)`. That part is fine. However, the `cause` (original SQLException) is preserved with `, e` and PostgreSQL driver exception messages routinely include the raw bound parameter values for constraint violations. When the IllegalStateException is logged by an upstream handler, the wrapped cause's `e.getMessage()` (containing the un-redacted contact_id) may be written verbatim.
    REPRO: A `/ban <contact-with-DB-constraint-violation>` triggers a SQLException whose PG message embeds the raw contact_id (e.g. "duplicate key value violates unique constraint ... Detail: Key (adapter, contact_id)=(signal, +15551234567)"). The wrapping IllegalStateException carries the cause; default log handlers print `Caused by:` chains verbatim with the unredacted id.
    SUGGESTED-FIX-CLASS: input-sanitization

  - CATEGORY: DOS
    SEVERITY: low
    PROMISE: docs/spec/security.md §Prompt-injection defenses (LLM call sites) commits "**All free-form string and list inputs across every tool below are length-bounded by a profile-driven cap**" as the dispatcher-level discipline. The pattern generalizes: deterministic admin commands accept structured input from an authenticated admin tier, but the spec's overall posture is that all free-form text reaching deterministic command paths is bounded.
    GAP: `BanCommandHandler.BanArgs.parse` (infochat-provider/src/main/java/app/zcat/infochat/provider/command/BanCommandHandler.java:425-461) accepts `--reason "..."` of arbitrary length and writes it raw into `users.ban_reason` (TEXT) and into `audit_log.details_json` (JSONB). No length cap. A compromised admin session could push very large reason payloads to bloat the audit log and `users` table.
    REPRO: Attacker (with admin session) issues `/ban target --reason "<10MB of text>"`. The handler accepts and persists. Repeated calls grow the audit-log table without bound.
    SUGGESTED-FIX-CLASS: input-sanitization

  - CATEGORY: AUDIT-EVASION
    SEVERITY: low
    PROMISE: docs/spec/security.md §Authorization model step 8: "Audit-log the intent." (The intent is the parsed command, not only the executed mutation.)
    GAP: `BanCommandHandler.handle` (infochat-provider/src/main/java/app/zcat/infochat/provider/command/BanCommandHandler.java:138-157) short-circuits on the non-admin path (line 145-147), the no-args path (line 151-156), and the self-ban path (line 161-163) with NO audit row written. A non-admin probing whether `/ban <target>` is wired (reconnaissance) leaves no trail. The handler-level pattern is "audit-before-effect on the success path only," not "audit-the-intent." Same gap in `UnbanCommandHandler.handle` (admin gate + parse failure + unknown-contact) and `InviteCommandHandler.handle` (all admin-gate and validation rejections).
    REPRO: An attacker with a non-admin user row enumerates admin commands (`/ban x`, `/unban x`, `/invite create --adapter signal --open`, `/invite revoke any-uuid`). Each command returns `error.admin_only` and leaves zero audit rows. The operator has no signal that the account is probing the admin surface.
    SUGGESTED-FIX-CLASS: audit-log-coverage

OUT-OF-MODEL:
  - Admin running `/ban target --reason "..."` from a public location where the reason text shoulder-surfs to onlookers. Spec accepts physical-access threats as out of scope.
  - DB role enforcement (V2 roles in migrations) is the second line of defense for any of the audit-log writes; the diff assumes the provider role has INSERT on audit_log per spec §DB roles, and that's enforced by Postgres. If a future migration loosens that grant, the redaction-hook gap above becomes a direct disclosure path; flagged here as a defense-in-depth dependency that the spec already addresses.

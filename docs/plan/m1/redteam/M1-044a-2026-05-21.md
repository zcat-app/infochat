# Red-team audit: M1-044a (intake-step services)

## Scope

M1-044a lands the intake-step services (RateCapBucket,
InviteCodeConsumer, BanCheck) plus the V12 migration backing the
brute-force counter plus the AutoRegisterService rename-and-narrow. The
services are dead until M1-044b wires them into InboundRouter.onMessage;
this audit looks at the services in isolation against the threat-model
commitments they will be the load-bearing realization of (steps 1.5, 2,
3, 4 of §Authorization model).

## Structured verdict (verbatim from threat-actor)

RED-TEAM VERDICT: FINDINGS

FINDINGS:

  - CATEGORY: INFO-LEAK
    SEVERITY: medium
    PROMISE: "Contact IDs are logged in redacted form (prefix + ellipsis + suffix) outside the audit log." (docs/spec/security.md §Secrets handling)
    GAP: Raw `contactId` is concatenated into `IllegalStateException` messages in three new/modified files:
      - infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/InviteCodeConsumer.java:171-173 ("InviteCodeConsumer.consume failed for adapter=... contact_id=" + contactId)
      - infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/InviteCodeConsumer.java:176-178 ("InviteCodeConsumer.consume connection failed for adapter=... contact_id=" + contactId)
      - infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/InviteCodeConsumer.java:231-233 ("users row missing after invite-consume INSERT for adapter=... contact_id=" + contactId)
      - infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/BanCheck.java:57-59 ("BanCheck.isBanned failed for adapter=... contact_id=" + contactId)
      - infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/AutoRegisterService.java:79-82, 88-90 ("users row missing after upsert..." and "AutoRegisterService.resolveOrRegisterGroup failed...")
      None of these call the existing M1-038 `ContactIds.redact` helper that other handlers (per the M1-039 precedent) use for exception messages. When propagated through Quarkus default exception logging, the raw `contact_id` value (the cryptographic identity of an inbound contact) lands in non-audit logs.
    REPRO: Trigger any SQLException reachable from these paths (e.g., a transient DB connection blip during invite consume, or a schema mismatch). The Quarkus default error handler logs the full exception chain including these messages. An operator with read access to application logs (which is broader than the audit-log path) now sees plaintext contact IDs — the same data the audit-log redaction hook (V5 §2.1.9 `redact_contact_id`) was designed to keep out of routine log surfaces.
    SUGGESTED-FIX-CLASS: input-sanitization

  - CATEGORY: AUDIT-EVASION
    SEVERITY: medium
    PROMISE: "Failed attempts increment a counter; when the counter exceeds a profile-driven threshold within a profile-driven window, further attempts from that (adapter, contact_id) are rejected without checking the code, and an audit row records the threshold breach." (docs/spec/security.md §Invite-code registration)
    GAP: infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/InviteCodeConsumer.java:141-145. The in-memory `breachAudited.add(key)` is called BEFORE `insertAudit(...)` runs. If `insertAudit` throws (any SQL/DB error: FK constraint, role grant issue, network blip, append-only trigger misconfiguration, target_kind CHECK violation), the catch block at line 169 rolls back the DB transaction — but the in-memory Set mutation is NOT rolled back. Subsequent calls in the same JVM see `breachAudited.add(key)` return false and skip the audit insert entirely. The threshold breach is silently never audited until the breach event "ends" (counter drops below threshold), at which point `breachAudited.remove(key)` clears the sentinel — but by then the original breach has gone unaudited and the evidence trail is lost.
    REPRO: Adversary patient-brute-forces invite codes from a stable `(adapter, contact_id)`. Reaches threshold. Audit insert encounters any transient or persistent SQL fault (e.g., temporary connection issue, an admin running migrations, the new `INVITE_BRUTE_FORCE_BREACH` action verb not being whitelisted by a future audit-helper closure check). The IllegalStateException propagates; operator may or may not notice. The next breach attempt finds `breachAudited` already contains the key, so no audit row is ever written for this breach event. The brute-force evidence is missing from `audit_log`, defeating the spec's "an audit row records the threshold breach" commitment.
    SUGGESTED-FIX-CLASS: audit-log-coverage

  - CATEGORY: DOS
    SEVERITY: low
    PROMISE: "Per-user token buckets bound, grouped explicitly so commands that share a cost profile share a bucket... Chat-mode message rate (transport-level) — bounds inbound message volume regardless of cost." (docs/spec/security.md §Rate limiting) — the bucket is positioned as a defense, but its memory footprint must itself be bounded.
    GAP: infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/RateCapBucket.java:72-82. The `evictIdleBuckets` predicate requires `bucket.tokens == inboundPerMinute` (i.e., the bucket must be FULL) AND `lastRefillEpochMillis < thresholdEpochMillis`. But refill is lazy — `lastRefillEpochMillis` only advances inside `tryAcquire`. A bucket that has been drained (tokens < cap) and then abandoned (no further `tryAcquire` calls) will never refill back to `cap` on its own, so the eviction predicate never fires. The bucket is pinned in the ConcurrentHashMap indefinitely.
    REPRO: Any contact that drains its bucket and stops sending leaves a permanent entry. For an adversary on an adapter where cheap fresh contact IDs are obtainable (Sybil resistance is acknowledged out-of-v1 per §What's intentionally NOT in v1), this turns the bucket into an attacker-controlled memory-growth vector: send 1 message from each of N synthetic IDs to seed N permanent entries, then keep doing so. Map grows without bound; provider OOMs eventually. Even without an adversary, every legitimate user who hits the cap and goes silent leaves a residual bucket — over months of operation the map grows monotonically.
    SUGGESTED-FIX-CLASS: rate-limit

  - CATEGORY: AUTH-BYPASS
    SEVERITY: low
    PROMISE: "Pre-banned contact + invite. /invite create --contact <id> against a contact whose users row already has is_banned=true returns a friendly error pointing the admin at /unban; no invite is created. The intake-side ban check (authorization step 4) is the second line of defense — even if a stale invite exists, the ban check fires first..." AND "DM — unknown contact. If no user row exists for this (contact_id, adapter): check whether the full normalized message body is a valid PENDING invite code..." (docs/spec/security.md §Invite-code registration, §Authorization model)
    GAP: infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/InviteCodeConsumer.java:130-180 — the `consume` method does not itself verify that no `users` row exists for `(adapter, contactId)`. If the splice (M1-044b) ever routes a contact-with-existing-row (pre-banned, group-only, or vouched) to `consume`, the `INSERT_USER_SQL` runs with `ON CONFLICT DO NOTHING` and the subsequent `SELECT_USER_ID_SQL` happily returns the EXISTING row's id (including a `registration_state='preban'` or `is_banned=true` row). The function returns `Accepted(existingUserId)` and writes an `INVITE_CONSUME` audit row, even though the contact is banned or already registered. The building block defaults open; it relies entirely on the caller's gating.
    REPRO: A stale `PENDING` invite exists for `(adapter, contactId)` from before a `/ban` (race window between ban and pre-ban revoke). The contact has a `users` row with `is_banned=true`. If M1-044b's intake path (yet to be implemented) calls `InviteCodeConsumer.consume` before the ban check (or in the wrong order), the consume succeeds, the invite transitions to USED, and the caller receives `Accepted(userId)` pointing at the banned row. The defense-in-depth this building block could provide (refuse to consume when a users row already exists, regardless of ban state) is absent — the contract is enforced only at the call site, with no internal sanity check that the precondition holds.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

OUT-OF-MODEL:
  - The `invite_code_attempt` table grows unbounded forever per V12 migration's explicit "Rows accumulate forever in v1; no TTL" commitment. Long-term disk exhaustion is bounded by attacker patience but the spec's acceptance of append-only semantics defers this to operator-side TRUNCATE under the admin role. Not a finding under the v1 threat model.
  - Per-adapter Sybil identities (used in the DOS finding above) are explicitly out of v1 scope per §What's intentionally NOT in v1 "Sybil resistance across adapters." The DOS finding stands on the non-adversarial memory-leak shape; the Sybil-amplified version is advisory.

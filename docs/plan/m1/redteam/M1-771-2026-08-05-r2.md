FINDINGS:
  - CATEGORY: INJECTION
    SEVERITY: low
    PROMISE: docs/spec/security.md §Rate limiting (Periodic-digest headline
             translation, M1-756/M1-759, D29 (c)): "headlines beyond the
             budget render untranslated and, per D29 (c), BRACKETED, the same
             degraded shape the `/saved` page uses: an unbracketed line always
             means the reader's own language, so a budget exhaustion must not
             silently emit a bare foreign line (M1-759)." Backed by §Trust
             boundaries item 9: "Everything a generative or embeddings
             endpoint returns is endpoint-chosen input, not a trusted internal
             value: whatever answers on the configured base-url picks every
             field of the reply, so a hostile or compromised endpoint is in
             scope here for the same reason a hostile feed is on the ingest
             side."
    GAP: The remediation aligned the echo comparison with the value about to
         be STORED, but the value that carries the bracket promise is the
         value about to be RENDERED, and the render applies a strictly
         stronger reduction than the echo check does. The two reductions are
         not the same function, so the round-1 harm is still reachable.

         Echo side —
         infochat-collector/.../eval/translation/IngestTranslationWorker.java:667-676
         compares `normalize.apply(x).strip()` on both sides.
         `normalizeTitle` (same file:710-713) = NFKC +
         `IngestTextNormalizer.stripMetadataField`; `normalizeBody`
         (same file:722-725) = NFKC + `stripBidiAndZeroWidth`
         (infochat-core/.../ingest/IngestTextNormalizer.java:54-79, an
         explicit codepoint list). Neither collapses INTERNAL whitespace runs.
         `normalizeBody` additionally leaves U+0085 / U+2028 / U+2029 intact —
         the exact three codepoints
         infochat-provider/.../render/DisplayHeadline.java:36-43 already
         documents as surviving "NFKC + stripBidiAndZeroWidth". Java
         `String.strip()` only removes `Character.isWhitespace` codepoints, so
         it does not remove U+0085 either.

         Render side — DisplayHeadline.java:269-271 (`renderLine`) puts BOTH
         the anchor and the original through
         `flattenToOneLine` (same file:510-512), which is
         `replaceAll("(?:\\R|\\s)+", " ").strip()`: it collapses every
         whitespace RUN to one space and treats U+0085/U+2028/U+2029 as line
         boundaries. Two strings the echo check judged unequal therefore
         become byte-EQUAL at render. Then DisplayHeadline.java:266 sets
         `anchored = true` for any non-blank anchor;
         DisplayHeadline.java:365-369 (`subordinateFor`) SUPPRESSES the
         bracketed original because `originalLine.equals(primaryLine)`;
         DigestRenderer.java:1012-1019 makes the display-hit leg a no-op for
         an `en` scope; TranslationPipeline.java:306-307 turns NO_OP +
         `usesAnchor` + `en` into `primaryInReaderLanguage = true`; and
         DisplayHeadline.java:357-359 then renders that primary line
         UNBRACKETED.

         Net: an anchor that differs from the original only in whitespace
         RUN-LENGTH (or, in the body field, only in U+0085) is stored, and the
         reader is shown ONE unbracketed foreign line with no bracketed
         original beneath it — byte-for-byte the round-1 outcome, through a
         reduction the fix did not adopt. The trigger no longer needs an
         exotic codepoint: a translator asked to echo its input routinely
         normalizes whitespace, so this fires without adversarial precision.

         Secondary vector, same promise and same fix class: invisible format
         codepoints outside the `IngestTextNormalizer` enumeration and outside
         NFKC's removals — U+2060 WORD JOINER, U+00AD SOFT HYPHEN, U+034F
         COMBINING GRAPHEME JOINER, U+FE00..U+FE0F variation selectors — are
         stripped by nothing on either side and are not
         `Character.isWhitespace`, so `original + U+2060` clears the echo
         check and is stored. That one leaves the subordinate line visible
         (the strings are not equal at render), so it is weaker: the reader
         still gets a bracketed original, but the PRIMARY line is still
         foreign and still unbracketed, which is the letter of the invariant.
         This is NOT the "lightly-reworded original / fluent prose in the
         wrong language" residual the new class javadoc (same file:161-163)
         discloses — that residual is about text the model actually rewrote;
         these are verbatim echoes.

    REPRO: 1. Operator declares a `cs` source (e.g. a Bluesky/Nostr feed,
              whose posts carry the `untitled` sentinel so the BODY field is
              the rendered headline — DisplayHeadline.java:250-256).
           2. The attacker (a feed author steering the translator through the
              wrapped post body, or a hostile/compromised endpoint on the
              configured base-url per §Trust boundaries item 9) causes the
              TRANSLATOR reply for a post whose body is
              `"Povoden  zasahla Prahu."` (two spaces) to be
              `{"title":"...","body":"Povoden zasahla Prahu."}` (one space) —
              i.e. a verbatim echo with the whitespace run collapsed. The
              U+0085 variant works identically: reply
              `"Povodenzasahla Prahu."` against an original containing a
              plain space.
           3. `anchorField` computes
              `normalizeBody(reply).strip()` = `"Povoden zasahla Prahu."` vs
              `normalizeBody(original).strip()` = `"Povoden  zasahla Prahu."`
              — unequal. `sanitize` changes nothing (no closed-list token), so
              the second comparison is unequal too. No `reportEcho`, no
              `translator.echo` notification, no WARN. `body_en` is persisted
              as the Czech original.
           4. An English (`/lang en`) group receives the periodic digest.
              `DisplayHeadline.anchorFirst` derives
              `readerLine = renderLine(body_en)` and
              `originalLine = renderLine(body)`; `flattenToOneLine` collapses
              both to `"Povoden zasahla Prahu."` — now EQUAL.
              `usesAnchor` is true (source `cs` != scope `en`),
              `translatesUnderThisScope` is false for an `en` scope, so the
              display hit is NO_OP and `primaryInReaderLanguage` is true.
           5. The delivered digest entry is a single line:
              `· Povoden zasahla Prahu.` — unbracketed, with the subordinate
              original suppressed. The reader is told, by the absence of the
              bracket, that this line is in their own language. It is not.
              The system should not have allowed it: this is the exact
              non-translation the echo control was added to reject, and the
              only thing that saved it was a whitespace difference the render
              itself throws away.

OUT-OF-MODEL:
  - `reportEcho` (IngestTranslationWorker.java:690-699) runs BEFORE
    `persistTranslation`, and `ThrottledAdminNotifier.notifyOnce` writes to
    `admin_notification_state`. If that write throws, `processOne` aborts, the
    post keeps `translation_done = FALSE`, and the next tick re-picks it and
    re-spends a TRANSLATOR call — a post that reliably echoes plus a failing
    notifier is an unbounded per-post LLM re-spend. Not adversary-reachable
    (it needs a DB-side infrastructure failure the threat model puts inside
    the trusted DB boundary), and it fails in the safe direction for the
    anchor itself, so it is raised as an operational note rather than a
    finding. The sibling REFUSAL arm notifies AFTER its persist and does not
    have this shape.

RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: DOS
    SEVERITY: medium
    PROMISE: security.md §Authorization model / §Rate limiting commit that the
             D47 caps "bound the bot's TOTAL passive memberships" and that the
             global cap "stops the aggregate even when every inviter is
             individually under its own cap" (GroupInvitationHandler javadoc /
             code comment, restating the §3.5 commitment that step 3.5 must
             "Enforce the per-user group activation cap and the global
             max-groups cap"). The §Rate limiting model exists so no single set
             of actors can exhaust shared resources past the configured bound.
    GAP: The global-cap enforcement is a non-atomic check-then-act with no
         transaction, row lock, or advisory lock spanning the read and the
         insert. GroupInvitationHandler.java:153 reads
         groupJoinRepository.countJoins() (GroupJoinRepository.java:513, a bare
         SELECT COUNT(*)) and only later, at GroupInvitationHandler.java:166,
         issues tryRecordJoin (INSERT). The adapter dispatch
         (SimpleXWebSocketClient.java:524-526) keys FIFO ordering on the
         INVITER contactId only — so invitations from the SAME inviter
         serialize, but invitations from DISTINCT registered inviters run
         concurrently on different dispatch threads. Two or more distinct
         inviters whose invitations land in the window between the global
         COUNT and the INSERT each observe count < globalMaxGroups and each
         proceed to record + joinGroup, pushing the persisted total past
         globalMaxGroups. The per-inviter cap is safe (serialized per inviter);
         the GLOBAL cap — the exact backstop the spec says protects against
         "every inviter individually under its own cap" — is the one that
         races.
    REPRO: Attacker controls (or colludes across) N registered, non-banned
           inviters (each past the DM invite gate). With the global pool near
           full, all N send a group invitation to a distinct new group at the
           same instant. The per-inviter dispatch serializes nothing across
           the distinct inviter keys, so all N handle() calls evaluate
           countJoins() before any of them commits, all see count <
           globalMaxGroups, and all record + join. The bot ends up in
           globalMaxGroups + (N-1) passive groups, exceeding the configured
           ceiling the operator set. Overshoot is bounded by concurrency
           width, so the unbounded-growth DoS is still closed, but the
           specific "global cap is a hard aggregate ceiling" promise is not
           delivered.
    SUGGESTED-FIX-CLASS: other

  - CATEGORY: DOS
    SEVERITY: medium
    PROMISE: security.md §Rate limiting / DoS posture: caps exist so one set of
             actors cannot deny a shared capability to everyone else; the
             M1-519 change states the caps "close the unbounded-growth DoS"
             while keeping the bot able to serve legitimate auto-join traffic
             under the §3.5 D47 group machine.
    GAP: auto_joined_group has NO removed_at column and DELETE is revoked from
         every app role permanently (V55__auto_joined_group.sql:280-281,
         "REVOKE DELETE ... FROM infochat_provider / FROM PUBLIC"; the table
         comment at lines 252-258 confirms the count is "intentionally a
         one-way ratchet"). countJoins()/countJoinsByInviter() count every row
         ever inserted, including groups the bot has since left or never
         actually joined (record-then-join at GroupInvitationHandler.java:166
         records the slot even if source.joinGroup at :167 then throws —
         documented as an accepted over-count). Because the count never
         decreases and there is no in-band reclamation (slot-freeing deferred
         to the still-pending M1-522), the shared global slot pool is a
         lifetime sink. The per-inviter cap (default 3) limits a single inviter
         to 3 slots, but ceil(globalMaxGroups / perUserActivationCap) registered
         inviters (2 on the pi profile where global=5, 4 on laptop where
         global=10) suffice to fill the entire global pool with throwaway
         groups, after which the bot silently refuses ALL further auto-join
         invitations deployment-wide — permanently, with recovery only via
         out-of-band operator psql under the owner role (the app/admin roles
         cannot DELETE).
    REPRO: A small set of registered (invited/vouched) inviters each invite the
           bot into per-user-activation-cap distinct disposable groups until
           countJoins() reaches globalMaxGroups. They then have the bot leave
           every group (or the groups are deleted). The auto_joined_group rows
           remain (no removed_at, DELETE revoked), so countJoins() stays at the
           ceiling forever and GroupInvitationHandler.java:153 drops every
           subsequent legitimate invitation. The auto-accept feature is denied
           to all future users with no chat-surface or admin-command recovery.
           This is an anticipated/deferred trade-off (M1-522) but is surfaced
           here because the recovery ticket is not yet delivered and the
           lockout is reachable by a modest, invite-gated actor set.
    SUGGESTED-FIX-CLASS: other

OUT-OF-MODEL:
  - The auto-join surface and the §3.5 @mention surface (GroupApprovalService)
    SHARE the config keys infochat.groups.global-max-groups /
    per-user-activation-cap but COUNT DIFFERENT TABLES (auto_joined_group vs
    groups). The "no parallel cap surface / the two surfaces never diverge"
    comment (GroupInvitationHandler.java:65-68) is therefore inaccurate: the
    effective ceiling on the bot's total group footprint is up to the sum of
    the two independent counters (≈2× the configured value) rather than a
    single shared bound. Not a direct threat-model violation, but worth a
    decision on whether the operator-facing cap number means what an operator
    would assume.

RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - No explicit rate limit on `/grant-admin` and `/revoke-admin`. The spec §Rate limiting enumerates buckets (parser-only/DB-read, asset, /add-source, chat-mode, LLM, tool-calls, /quarantine approve) but does NOT list admin-tier mutating commands like `/grant-admin` / `/revoke-admin`. A compromised admin account could thrash the audit log via repeated grant/revoke cycles, but this is admin-tier abuse already inside the trust boundary, so spec doesn't promise to defend against it.
  - Defense-in-depth asymmetry: probation re-checked in handler, `is_banned` is not. The handler explicitly relies on the M1-044b intake-side ban gate (`InboundRouter` step 4) to block banned callers and adds an in-handler probation re-check as defense-in-depth, but does NOT add an analogous in-handler ban re-check on the actor row. If a future intake-side regression let a banned admin past step 4, the handler would proceed with grant/revoke. Test scenario (e) in `RevokeAdminCommandHandlerTest` deliberately exercises this path with `caller.is_banned=true` — only the V5 last-admin trigger stops the operation, and only because the test arranges for the target to be the sole qualifying admin. Per the no-defensive-code rule the current shape is defensible (intake is the system boundary), but the asymmetry with the probation check is worth surfacing.
  - No audit row for admin reject paths (`error.contact_not_registered`, `error.grant_admin.banned_target`, `error.grant_admin.already_admin`, `error.revoke_admin.not_admin`, `error.revoke_admin.cannot_revoke_self`). Spec §Authorization model step 8 says "Audit-log the intent" — the diff audits only on the successful UPDATE path (audit-before-effect inside the same tx). An admin can issue `/grant-admin <suspect>` against arbitrary contact ids to enumerate user state (registered? banned? already admin?) via the differential reply text with no trace in `audit_log`. Admin-tier is trusted, so the impact is low and the spec's "intent" phrasing is ambiguous (intent-to-execute vs intent-to-mutate), but flagging for the user to confirm which interpretation governs.

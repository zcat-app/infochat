RED-TEAM VERDICT: CLEAN

The diff is a focused remediation (M1-175) of the `/ban` handler that (a) moves the `BAN_INTENT` audit write ahead of the self-ban execution guard so a permission-passing-but-refused self-ban still leaves exactly one intent row, (b) threads the prompt-leg intent `request_id` through `BanConfirm` so the committed `BAN`/`INVITE_REVOKE` effect rows correlate with the authorizing intent, and (c) adds an in-transaction `SELECT ... FOR UPDATE` admin re-gate in `executeBan` to close the demote-between-prompt-and-confirm TOCTOU. I checked it against every relevant threat-model commitment and found no gap:

- Audit coverage (§Authorization model steps 7→8→9, AUDIT-EVASION): every committed `BAN` is necessarily preceded by a `BAN_INTENT` (the pending `BanConfirm` is only stored at `remember()` after the intent INSERT at `BanCommandHandler.java:219`), and the refused self-ban now also lands an intent row. No effect path bypasses the intent write. The intent write records the actor explicitly via `insertAudit`/`RedactionHook.AuditRow.actorUserId` (`:421-432`), so the separate autoCommit connection that lacks `SET LOCAL infochat.actor_id` does not lose actor attribution.
- Auth gate / TOCTOU (trust boundary 3, PERM-ESCAL): the confirm leg re-checks `is_admin` at dispatch (`:162`) and again under a row lock inside the transaction (`:281-286`); a demotion between prompt and commit yields `error.admin_only` with rollback and zero effect rows. `is_banned` is intentionally not re-checked here because the banned-user short-circuit is upstream at intake (spec step 4); that reliance is on a documented upstream boundary, not an inference about unshown code.
- Injection: the only string-concatenated SQL is `SET LOCAL infochat.actor_id = '<actor.id>'` (`:289`), where `actor.id` is a typed `UUID` resolved from the DB, not attacker-controlled; all target/reason/adapter values flow through `PreparedStatement` binds (`:441-479`).
- DOS / audit spam: the `BAN_INTENT` write is reachable only past the admin gate (`:162`), so a non-admin cannot drive audit-row growth or DB cost.
- Reply/leak surface: error replies are fixed bundle keys; the only contact id placed in exception text is `ContactIds.redact(...)` (`:357`, `:363`).

The supporting test changes (`ConfirmStateServiceTest`, `InboundRouterConfirmCancelTest`) are mechanical 2-arg→3-arg `BanConfirm` constructor updates with a fixed `"intent-req"` string and no weakened assertions; no test-integrity erosion.

OUT-OF-MODEL:
- The `--reason` flag value (admin-authored) is stored verbatim (JSON-escaped) in `audit_log.details_json` via `banDetailsJson` (`:499-505`), and `executeBan`'s catch wraps the `SQLException` cause and rethrows (`:355-364`). Both are pre-existing behaviors not introduced or altered by this diff, and the §"User content in exceptions" obligation binds the downstream logging site (SafeLog), not the throw site — flagged only so the user can confirm the eventual log sink uses SafeLog.

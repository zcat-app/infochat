RED-TEAM VERDICT: CLEAN

No service role is a member of `infochat_admin`. The only membership grant is
the documented operator example in a comment. So the Provider/Collector logins
cannot `SET ROLE infochat_admin` to reach the admin surface. The trust boundary
holds.

The diff is a clean, tightly-scoped privilege grant that delivers exactly the
documented operator surface, grants nothing beyond it, widens no service-role
privilege, and is covered by both positive (admin can) and negative (service
roles cannot) integration tests. No threat-model promise is left undelivered.

OUT-OF-MODEL:
  - The admin operator paths granted by V43 (`DELETE` on `heartbeat`,
    `TRUNCATE` on `invite_code_attempt`, hard-`DELETE` on `source`) execute as
    raw DML under the operator's psql session and leave no `audit_log` row —
    unlike the chat-tier admin commands, which are audit-logged at intake. This
    is consistent with the spec framing the admin role as trusted operator psql
    (`security.md` §Threat model: "Operator-set config ... is trusted"; §DB
    roles describes these as ungated "escape hatches"), so it is not a model
    violation. Flagging only so the user can decide whether operator-side
    destructive psql actions (notably `invite_code_attempt` purge and `source`
    hard-delete) warrant a forensic trail beyond Postgres server logs; if so,
    that is a spec extension, not a defect in this diff.

OUT-OF-MODEL:
  - Static 4000-token floor vs. model-controlled reasoning tail. The guard
    (DeepSeekProvider.java:158-173) forces a reasoning-enabled task to provision
    max-tokens >= REASONING_MIN_MAX_TOKENS (4000). The floor is derived from a
    30-item spike sample whose worst observed completion was 2063 tokens, and the
    spike doc itself caveats "a sample maximum under-estimates the true tail"
    (docs/plan/m1/spikes/M1-610-judge-reasoning.md:141-146,169-172). Reasoning
    token count is chosen by the model, so a longer/harder judge prompt could
    still consume >4000 completion tokens on a reasoning-ON call, truncate the
    verdict to empty (finish_reason=length, content=""), route to Stage 2
    INFRA_FAILURE, and release-as-READY. The guard's javadoc claim "so reasoning
    cannot truncate the verdict and fail-open" (DeepSeekProvider.java:168-169) is
    therefore a probabilistic mitigation, not a proof. This is OUT-OF-MODEL
    because (a) it is reachable ONLY when an operator opts into reasoning, and
    operator-set config is trusted per security.md §Threat model, and (b) the
    resulting behavior — release-as-READY on a Stage 2 infrastructure failure — is
    the DOCUMENTED default in security.md §Failure handling ("unparseable ...
    reply after retry -> release as READY ... A profile-driven flag lets
    production profiles invert this default"), so it is accepted behavior rather
    than a violated commitment. Flagged so the user can decide whether to (i) pair
    reasoning-ON with the invert-to-quarantine profile flag as a documented
    requirement, or (ii) size the floor from a larger corpus study.

  - Startup-scan-only enforcement of a per-call value. The coupling guard runs
    only in the startup config scan (LlmRouter.java:301-302 ->
    assertTaskConfigResolvable), but the effective max-tokens is re-read per call
    (OpenAiCompatibleProvider.configFor is deliberately un-cached and treated as
    "runtime-resolvable", OpenAiCompatibleProvider.java:152-162,207). If a runtime
    config source lowered max-tokens below the floor after boot while
    reasoning-effort stays set, the wire path (customizeRequestBody still emits
    reasoning_effort, DeepSeekProvider.java:182-190) would send reasoning with an
    under-provisioned budget and the guard would not re-fire. This is OUT-OF-MODEL:
    it requires trusted operator config to change at runtime, and it mirrors the
    identical startup-scan posture of the pre-existing parent max-tokens guard
    (requirePositiveMaxTokens, OpenAiCompatibleProvider.java:208) that the spec
    already accepts. Noted only so the user knows the coupling is a boot-time, not
    a per-call, invariant.

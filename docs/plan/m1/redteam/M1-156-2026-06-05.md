# Red-team audit: M1-156 (2026-06-05)

Verbatim threat-actor verdict follows.

```
RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: INFO-LEAK
    SEVERITY: low
    PROMISE: "Audit-log writes pass through a redaction hook that masks values matching a closed catalogue of API-key shapes … Generic 32+-character hex / base64 strings adjacent to the case-insensitive substrings `api[_-]?key`, `secret`, `token`, `password`, `bearer`." (§Secrets handling) and "Stdout console logs pass through the closed API-key catalogue redactor."
    GAP: The widening in infochat-core/src/main/java/app/zcat/infochat/core/log/Redactor.java:54-61 ({0,5} → {0,20}) and its SQL mirror in infochat-core/src/main/resources/db/migration/V31__service_role_login_and_audit_redaction.sql:101-106 moves the evasion cliff but keeps two finite escape hatches: (a) a separator run of 21+ characters still defeats the catch-all on both engines; (b) the separator class ["'\s:=] excludes common key/value punctuation (`,`, `|`, `>`, `->`, parentheses), so `password -> <32-char-secret>` or `token, <secret>` never matches at any quantifier. The new tests (RedactingLogFilterTest.redactsGenericWithLongSeparatorRun, 13-char run; RedactorSqlParityIT, 12-char run) only exercise inside-the-bound shapes, so the residual cliff is invisible to the suite.
    REPRO: An operator secret that reaches a log message or audit_log.details_json formatted as `api_key:                      <40-char-key>` (21+ separator chars, e.g. column-aligned config dumps or pretty-printed YAML) or `token -> <key>` passes both the console Redactor and redact_secrets_jsonb unredacted; a bot admin reading /audit (via audit_log_view) or anyone with log access sees the raw key. Exploitability is bounded because the attacker rarely controls the operator key's surrounding formatting — hence low.
    SUGGESTED-FIX-CLASS: input-sanitization

  - CATEGORY: INFO-LEAK
    SEVERITY: low
    PROMISE: "The audit_log writer consumes the same Redactor utility so the two cannot drift." (§Secrets handling) — the system's commitment that the Java-side and read-side redaction surfaces stay equivalent, which M1-169's parity guard exists to enforce.
    GAP: The ticket notes state that Java/SQL parity rests on the regex strings staying *textually identical*, and RedactorSqlParityIT verifies parity only with ASCII-only samples. Textual identity does not give semantic identity across engines: Java \s without UNICODE_CHARACTER_CLASS is ASCII-only ([ \t\n\x0B\f\r]), while PostgreSQL ARE \s is [[:space:]], which under an ICU/UTF-8 collation can include non-ASCII whitespace (e.g. U+00A0); (?i) case-folding scope likewise differs. A secret separated from its keyword by a non-breaking space is redacted on one engine and leaked on the other, and the parity IT cannot catch it because its corpus never carries non-ASCII separators.
    REPRO: A log/audit field containing `password<U+00A0><32-char-secret>` (NBSP is common in copy-pasted rich text) is left raw by the Java console Redactor and the audit-write hook while redact_secrets_jsonb may mask it on read — i.e. the console log stream leaks what the audit view hides, the exact drift class the parity guard was built to prevent. mvn verify stays green because every parity sample is ASCII.
    SUGGESTED-FIX-CLASS: other

  - CATEGORY: INFO-LEAK
    SEVERITY: low
    PROMISE: "**`audit_log_view`** is a Postgres view that exposes the same columns as `audit_log` minus any redacted fields … this is the path `/audit` uses." (§DB roles) — redaction on the Provider's audit read path must reflect the current catalogue.
    GAP: The widened SQL pattern lands via in-place edit of an already-numbered migration (V31__service_role_login_and_audit_redaction.sql:103, ticket out_of_scope: "V31 is edited in place per the M1-116 precedent"). Any database that already executed the original V31 keeps the old {0,5} redact_secrets_jsonb function while the Java side ships {0,20}: Flyway will flag a checksum mismatch on startup, but the standard operator response (`flyway repair`, which updates the checksum without re-running the migration) leaves the narrow SQL function in place permanently. RedactorSqlParityIT runs against a freshly-migrated schema, so it can never detect a stale deployed function.
    REPRO: Operator with a pre-existing dev/staging DB pulls this change, hits the V31 checksum-mismatch startup failure, runs `flyway repair` (the documented Flyway remedy), and restarts. From then on the console Redactor masks 6-20-char-separator secrets while audit_log_view (the /audit path) renders them raw to bot admins — silent, permanent drift between the two surfaces the spec says cannot drift. Greenfield M1 status keeps this low, but the in-place-edit precedent makes recurrence likely.
    SUGGESTED-FIX-CLASS: other

OUT-OF-MODEL:
  - Sybil-driven growth of breachAudited plus the new per-consume full-map sweep (InviteCodeConsumer.java:155, 240-243): an adapter with free identity minting (SimpleX queue addresses) lets an attacker breach the threshold from N fresh contact ids inside one window, growing the map to N entries and making every unknown-contact consume pay an O(N) removeIf scan. The eviction bounds growth to one window (a genuine improvement over the prior unbounded set), and per-identity Sybil resistance is explicitly out of scope for v1 (§Threat model, §What's intentionally NOT in v1), so this is advisory: cost is small (entries are tiny, sweep is in-memory) but the sweep could be made amortized (e.g. time-gated) if hostile-adapter load ever matters.
  - The BruteForceThresholdBreached outcome maps to a distinct "too many attempts" fixed reply (class javadoc, pre-existing, outside the diff hunks), while §Invite-code registration says the limit "does not change the per-failure user-visible reply." The distinct reply is an oracle telling a brute-forcer exactly when their probes stop being checked against the code table. Pre-existing behavior, not introduced by this diff — flagged for a follow-up spec-conformance check, not as a finding against M1-156.
```

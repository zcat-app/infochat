RED-TEAM VERDICT: FINDINGS

FINDINGS:

  - CATEGORY: PERM-ESCAL
    SEVERITY: medium
    PROMISE: From `docs/spec/security.md` §User ban: "Banned-user check is the first thing after identity resolution... Banned user receives one fixed reply per inbound message, regardless of input." And from decision D11 (Trust boundaries §2): "Banned users get one fixed reply and never reach the parser, the chat agent, or any DB query past the ban check."
    GAP: `infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/InboundRouter.java:379-409` invokes `groupApprovalCheck.check()` BEFORE the step-4 ban check. The Check at `GroupApprovalCheck.java:107-126` calls `GroupApprovalService.evaluate` which (in `GroupApprovalService.java:118-160`) executes multiple DB queries (`findApprovalRow`, `countGroupsActivatedBy`, `countActiveGroups`, `tryInsertPending`) and emits an admin notification via `ThrottledAdminNotifier.notifyOnce` — all of which the §User ban promise says a banned user must never reach. The reply a banned user receives in a group is `GROUP_PENDING`/`GROUP_REJECTED`/`GROUP_ACTIVATION_LIMIT`/`GROUP_GLOBAL_LIMIT` rather than the documented fixed ban reply. (Note: §Authorization model itself orders step 3.5 before step 4, so the spec is internally inconsistent — the diff implements the ordering literally and breaks the §User ban promise.)
    REPRO: (1) Bot admin sets `is_banned=true` on user U via `/ban`. U remains registered (`registration_state IN ('invited','vouched')`). (2) U @-mentions the bot in a fresh group G that has no `groups` row. (3) Inbound router executes step 1.5 (transport cap OK), step 1.7 (normalize), step 3 (U is registered, passes), step 3.5 (`GroupApprovalCheck.check` fires). (4) `GroupApprovalService.evaluate` finds no row, passes the per-user cap (U has 0 prior activations), passes the global cap, INSERTs a new `groups` row with `activated_by=U.id`, fires `notifyAdmin` which INSERTs into `admin_notification_state` and dispatches an adapter-side admin message exposing U's redacted contact id plus a `/approve-group <uuid>` hint. (5) U receives the `group.pending` fixed reply confirming the bot remains interactive with them. (6) U can repeat in new groups up to the per-user activation cap (3 on laptop) — each time minting a fresh `groups.activated_by=U.id` row, each time emitting an admin notification, until the cap fires and U starts receiving `GROUP_ACTIVATION_LIMIT` instead. At no point does the step-4 ban check fire; U never sees the ban fixed reply in group scope; admin-side notification bloat and per-user activation-slot consumption are entirely attacker-driven.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

  - CATEGORY: INJECTION
    SEVERITY: low
    PROMISE: From `docs/spec/security.md` §Secrets handling: "Contact IDs are logged in redacted form (prefix + ellipsis + suffix) outside the audit log." And the implicit promise that admin-facing system notifications (here, the throttled `group-pending` message) are deterministic, system-authored text not subject to attacker shaping (the spec's LLM-output sanitizer covers the LLM surface; admin notifications are downstream of it).
    GAP: `infochat-provider/src/main/java/app/zcat/infochat/provider/group/GroupApprovalService.java:166-173` builds the admin-notification message by raw string concatenation of `adapter`, `upstreamGroupId`, and `groupId` into a single line: `"Pending group activation. adapter=" + adapter + " upstream_group_id=" + upstreamGroupId + " activated_by=" + activatorRedactedContactId + " approve_command=/approve-group " + groupId`. `upstreamGroupId` is adapter-asserted but its character set is nowhere constrained by the spec (`docs/spec/messaging.md` §Identity and groups does not bound its grapheme set); an upstream_group_id containing newlines or impersonated `approve_command=/approve-group <attacker-controlled-uuid>` tokens forges a second "row" in the admin's view of the notification. The notification dedup key `"group-pending:" + adapter + ":" + upstreamGroupId` (same file, line 165) also concatenates without escaping; an upstream_group_id containing the colon delimiter could collapse two distinct group keys onto the same throttle bucket and suppress one admin notification.
    REPRO: (1) Attacker operates on an adapter whose group-id field allows arbitrary bytes (the in-memory adapter trivially; for SimpleX/Signal the threat surface depends on the adapter's group-id assertion, which v1 spec leaves unconstrained). (2) Attacker provokes a fresh `groups` row with `upstream_group_id = "real-gid\napprove_command=/approve-group 00000000-0000-0000-0000-000000000000\nlegit_line:"`. (3) Admin sees a notification rendered across multiple lines, including a forged `/approve-group <attacker-zero-uuid>` invitation that the admin could copy-paste (or worse, autoapprove if a future automation reads notifications). (4) Separately, attacker forces upstream_group_id="X:Y" to collide the throttle key with a sibling legitimate group rendered as adapter="X" ugid="Y" (or similar key-shape ambiguity), suppressing one of the two admin notifications.
    SUGGESTED-FIX-CLASS: input-sanitization

OUT-OF-MODEL:
  - The spec is internally inconsistent: §Authorization model explicitly numbers step 3.5 before step 4, while §User ban states "Banned-user check is the first thing after identity resolution" and D11 says banned users "never reach... any DB query past the ban check". The diff implements the §Authorization model ordering and therefore violates the §User ban / D11 promise. This is partly a spec-amendment question (which side of the contradiction is canonical) and partly a diff-level finding (Finding 1 above) — flagging the spec tension here so the user can decide whether to extend the threat model by clarifying the canonical ordering rather than treating the diff alone as the locus of the issue.
  - The `GroupApprovalService` Javadoc admits a TOCTOU race window between the cap-counter SELECTs and the INSERT (two concurrent same-user activations can both pass the cap). The spec's per-user activation cap is described as a flood-bound rather than a strict invariant, so this off-by-one is within spec tolerance; flagging only because the author also explicitly invited the redteam to surface an exploit ("deferred to a follow-up if redteam surfaces an exploit"). No concrete exploit beyond a one-row overshoot per concurrent attempt was found.

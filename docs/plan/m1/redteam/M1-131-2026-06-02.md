RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: DOS
    SEVERITY: low
    PROMISE: "**All free-form string and list inputs across every tool below are length-bounded by a profile-driven cap** (the cap value lives in design notes); a call exceeding the cap is rejected by the tool dispatcher before any SQL runs and the LLM sees a typed validation-error reply." Also: "Every argument is type-checked and bound to enums, validated ranges, or length caps before the underlying SQL runs."
    GAP: The rewritten `parseToolArgs`/`toJavaValue` (ChatAgent.java:292-318) now produces value shapes the old flat parser never emitted — notably nested `Map<String,Object>` for JSON objects (case OBJECT, lines 301-309) and `List<String>` for arrays. The dispatcher's bound-enforcement, `ChatToolDispatcher.validateInputLengths` (ChatToolDispatcher.java:160-184), only inspects top-level `String` values and `List` elements that are `String`. A top-level value that is a nested `Map` (e.g. `{"keywords":{"k":"<10kB string>"}}`) falls through every branch unchecked, so the "length-bounded ... rejected by the tool dispatcher before any SQL runs" guarantee is not enforced for that shape by the dispatcher. In practice the oversized payload does not reach SQL today only because the consuming tool's cast (e.g. `(List<String>) args.get("keywords")` in RecallMemoryTool.java:39) throws `ClassCastException`, which ChatToolDispatcher.java:149 now converts to a `ValidationError` — i.e. the bound is enforced incidentally by a downstream type cast, not by the dispatcher as the spec commits. The dispatcher contract ("rejected by the tool dispatcher before any SQL runs") is therefore delivered only as a side effect of cast failures, leaving no guarantee for any future tool that legitimately accepts a map/object argument or that defensively coerces rather than casts.
    REPRO: A prompt-injected post body (LLMs are in-scope untrusted per the threat model) coaxes the chat agent to emit `TOOL_CALL: recallMemory {"keywords":{"x":"AAAA…(50KB)…"}}`. `parseToolArgs` builds `{keywords -> Map{x -> 50KB String}}`; `validateInputLengths` sees a `Map` value, matches neither the `String` nor `List` branch, and returns null (passes). The 50KB string was never length-checked by the dispatcher. Today RecallMemoryTool's `(List<String>)` cast aborts the call, but the dispatcher's spec-committed pre-SQL length gate did not fire — defense-in-depth on the bound is absent for nested shapes the new parser now constructs.
    SUGGESTED-FIX-CLASS: input-sanitization

OUT-OF-MODEL:
  - Deeply-nested attacker-influenced JSON causing recursion/stack exhaustion in the recursive `toJavaValue` (ChatAgent.java:292) or in `Jackson readTree` over the unbalanced-brace tail (`text.substring(braceStart)`, ChatAgent.java:223): mitigated by Jackson's default `StreamReadConstraints` max-nesting-depth (1000), which raises a `StreamConstraintsException` caught at ChatAgent.java:274. Noted only so the residual risk is explicit if a future build relaxes the Jackson stream-read constraints; not a finding under the current framework default.

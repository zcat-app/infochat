# Red-team audit: M1-192 (2026-06-07)

Verbatim threat-actor verdict:

```
RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: INJECTION
    SEVERITY: medium
    PROMISE: "Collector ingest → user-visible store. No post becomes user-visible without passing the layered ingest checks (§ Ingest pipeline)." and "Stage 1 is a coarse filter, not a complete defense. ... Stage 2 is the actual security boundary."
    GAP: The diff replaces fail-at-boot config binding with lazy per-call resolution for the SECURITY_JUDGE task. Pre-diff, `OpenAiCompatibleProvider` used `@ConfigProperty(name = "infochat.llm.security.base-url")` / `...model` with no defaults, so a missing or typoed key refused startup (CDI injection failure). Post-diff, `configFor` (`infochat-llm-adapter/src/main/java/app/zcat/infochat/llm/impl/OpenAiCompatibleProvider.java`, new `configFor` body: `config.getValue(prefix + "base-url", String.class)` / `getValue(prefix + "model", ...)`) throws `NoSuchElementException` only at call time. The startup guard does not compensate: `LlmRouterStartupGuard.onStartup` calls `router.assertAllTasksResolve()` (`infochat-llm-adapter/src/main/java/app/zcat/infochat/llm/routing/LlmRouter.java:229-233`), which validates only that each task resolves to a registered *provider name*, never that the per-task `base-url`/`model` keys exist. Downstream, `Stage2Worker.tryOnce` catches bare `RuntimeException` (`infochat-collector/src/main/java/app/zcat/infochat/collector/eval/stage2/Stage2Worker.java:205`), so the config-missing exception is indistinguishable from a transient LLM outage: both retry attempts fail instantly, the verdict becomes `INFRA_FAILURE`, and the post follows the Stage-2-infra-failure path (release as `READY` with Stage 1 redactions only, on the default profile). The spec sanctions that path for *transient* infrastructure failure with re-eval recovery; the diff makes it the *permanent steady state* for a deployment with one typoed property — a state that before this diff was structurally impossible because the process would not boot. The Provider-side properties comment even acknowledges the new burden ("the library defaults nothing, so Provider must declare the keys for every task it routes") without any mechanism enforcing it.
    REPRO: Operator deploys the Collector with `infochat.llm.security.model` misspelled (e.g. `infochat.llm.securty.model`). The service boots cleanly — `LlmRouterStartupGuard` passes (provider names all resolve), no startup error. An adversary controlling any subscribed RSS/Bluesky/Nostr feed publishes posts whose injection payload is crafted to slip the Stage 1 regex catalogue (which the spec itself calls a coarse filter). Every Stage 2 invocation throws `NoSuchElementException` on both attempts → `INFRA_FAILURE` → the post is released `READY` and user-visible with only Stage 1 applied, indefinitely, for every post from every source. The judge — "the actual security boundary" — never runs for the lifetime of the deployment, where the pre-diff behavior was a refused boot that forced the operator to fix the key. (Throttled admin notifications and the re-eval/NEEDS_REVIEW cap soften but do not close this: posts are user-visible during the window and the re-eval job fails on the same missing key.)
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

  - CATEGORY: DOS
    SEVERITY: low
    PROMISE: "Schema-violating LLM output ... is treated identically to an unparseable reply at every stage: retry once, then apply the stage-specific failure path" together with "Stage 2 infrastructure failure (LLM unreachable, timeout, unparseable or schema-violating reply after retry) → release as READY with the Stage 1 redactions retained" — the single retry is the mechanism that keeps transient provider failures from converting posts into the degraded-security release path.
    GAP: The diff deletes the entire `Retry-After` machinery: `LlmHttpSupport.retryAfterMsFor`/`parseRetryAfterMs` removed (`infochat-llm-adapter/src/main/java/app/zcat/infochat/llm/impl/LlmHttpSupport.java`), and the `retryAfterMs` field/accessor removed from `LlmCallFailedException` and `EmbeddingCallFailedException` in all three providers. Grep confirms no production consumer ever slept on the value (only docs/review files reference `retryAfterMs`), so current behavior does not regress — but the deletion forecloses the only path by which the spec-mandated single retry could succeed against a rate-limited (429) or overloaded (503) endpoint: `Stage2Worker.invokeWithRetryOnce` (Stage2Worker.java:173-183) re-issues the call immediately, which against a provider that just advised `Retry-After: 2` is near-certain to fail again, converting every rate-limit burst into `INFRA_FAILURE` → degraded release (Stage 1 only) or, in production profiles that invert the default, quarantine backlog growth.
    REPRO: A burst of legitimate LLM-triggering load (or provider-side throttling of the operator's API account) causes the Stage 2 endpoint to return 429 with `Retry-After: 2`. Attempt 1 fails; the immediate attempt 2 fails milliseconds later; the post takes the Stage-2-infra-failure path even though waiting the advised 2 seconds would have produced a healthy verdict. An adversary who can correlate feed publishing with periods of provider rate-limiting gets their content judged by Stage 1 alone more often than the spec's retry-once design intends.
    SUGGESTED-FIX-CLASS: rate-limit

OUT-OF-MODEL:
  - TOCTOU between the startup-time local-only guard and the new per-call dynamic config reads: `LlmRouterStartupGuard` validates a config snapshot once at `@PostConstruct`, while `OpenAiCompatibleProvider.configFor` now re-reads `infochat.llm.<task>.base-url` on every call — the javadoc explicitly states caching was rejected because values are "runtime-resolvable." A config source whose values change after boot could route post bodies to a non-loopback host after the local-only check passed, with no re-check and no confirmation log. Out of model because (a) the local-only commitment lives in `llm.md`, not the supplied `security.md` threat model, and (b) "operator-set config is trusted" — but the guard's protection is now point-in-time rather than matching the actual resolution behavior, which the user may want a spec note or a per-call loopback assertion for.
  - The new test harness (`OpenAiCompatibleProviderTest`) binds `HttpServer.create(new InetSocketAddress(0), 0)` — the wildcard address, not loopback — exposing the mock LLM endpoint on all interfaces for the test's duration. Test-time only, mirrors the pre-existing `AnthropicProviderTest` pattern; flagged for hygiene, not exploitability.
```

RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: AUDIT-EVASION
    SEVERITY: high
    PROMISE: "Authorization evaluation order on every inbound message: ... 8. Audit-log the intent. 9. Execute."
    GAP: RetryCommandHandler.java:364-393 (`handleDigestRetry`) and DigestRetryService.java:54-76 (`retryDigest`) execute a mutating operation (DELETE from `summary_cache`, LLM invocation, INSERT into `summary_cache`) with no audit log write anywhere in the path. Neither the handler nor the service inject or call `AuditLogWriter`. By contrast, the spec requires step 8 (audit-log the intent) before step 9 (execute) on every inbound message. A group admin or bot admin can repeatedly replace digests with no audit trail.
    REPRO: A group admin sends `/retry --digest` in a group. The command succeeds (deletes old cache row, invokes LLM, inserts new cache row, delivers new digest to the group). No row is written to `audit_log`. An operator inspecting the audit log sees no record of who triggered digest replacements, when, or how many times. A compromised group admin could replace digests to alter what group members see, with no forensic trail.
    SUGGESTED-FIX-CLASS: audit-log-coverage

  - CATEGORY: DOS
    SEVERITY: medium
    PROMISE: "LLM-triggering operations (chat replies + on-demand `/summary` + `/retry` re-rolls) — its own bucket, capped lower, profile-driven."
    GAP: RetryCommandHandler.java:364-393 (`handleDigestRetry`) does not check any LLM rate-cap bucket before calling `digestRetryService.retryDigest()`, which invokes the LLM via `digestWorker.execute()`. The per-group ConcurrentHashMap serialization in DigestRetryService.java:55 prevents concurrent calls for the same group but does not limit frequency — once each call completes, the next can fire immediately. There is no per-user or per-admin LLM-triggering-operations rate bucket applied.
    REPRO: A group admin repeatedly sends `/retry --digest` in rapid succession. Each call is serialized (waits for the prior call to complete) but otherwise unbounded. After each LLM call completes (~seconds), the admin immediately triggers another. Over time this drives unbounded LLM cost with no rate-bucket rejection.
    SUGGESTED-FIX-CLASS: rate-limit

  - CATEGORY: PERM-ESCAL
    SEVERITY: low
    PROMISE: "Non-admin's `/retry --digest` -> friendly error (group-admin or bot-admin only for digest replacement)."
    GAP: RetryCommandHandler.java:129 routes on `rawText.contains("--digest")`, a loose substring match. Any input containing the substring `--digest` anywhere — e.g., `/retry foo--digest`, `/retry --digestive` — is routed to the digest-admin path instead of the personal-retry path.
    REPRO: A bot admin in a group sends `/retry something --digest-mode`. The substring `--digest` matches. The handler routes to `handleDigestRetry` instead of the personal-retry path, inadvertently triggering a digest replacement.
    SUGGESTED-FIX-CLASS: input-sanitization

OUT-OF-MODEL:
  - The `DigestRetryService.inFlight` ConcurrentHashMap is instance-local per the spec ("Provider-instance-local; a restart clears in-progress state per spec"). In a hypothetical multi-instance Provider deployment (not specified for v1), two Provider instances could accept concurrent `/retry --digest` for the same group, defeating the serialization guarantee. This is explicitly accepted by the spec for v1 but worth noting for future multi-instance deployments.

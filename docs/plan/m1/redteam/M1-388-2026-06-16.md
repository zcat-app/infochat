OUT-OF-MODEL:
  - Build-time binary acquisition is a supply-chain step, explicitly out
    of the v1 threat model ("Out of scope for v1: ... supply-chain attacks
    on operator infrastructure"). The diff fetches simplex-chat and
    signal-cli via `curl -fsSL` over HTTPS from pinned GitHub release tags
    and verifies each artifact with `sha256sum -c -`, failing the build
    non-zero on mismatch (Dockerfile.jvm:49-60). TLS/MITM is also out of
    model, and the pinned-tag + SHA256 check closes it regardless. No
    threat-model commitment governs `docker build`-time outbound fetches:
    the `infochat-ssrf` allowlist (security.md §SSRF) constrains *runtime*
    outbound connections from the Collector/Provider (feeds, redirects,
    StreamSource, `/add-source` probes), not build-stage artifact pulls.
    No gap between promise and delivery here; noting only so the operator
    can decide whether to extend the model to cover image-build provenance
    (e.g. cosign/attestation on the release artifacts).

  - The Provider container runs as root (pre-existing in Dockerfile.jvm;
    no USER directive added or removed by this diff) and now drives two
    third-party binaries as root OS subprocesses. A parsing/protocol bug
    in simplex-chat or signal-cli fed adversary-controlled inbound would
    execute with full container privileges. This subprocess execution
    model is pre-existing and frozen by decision D46 (the ticket's
    out_of_scope explicitly excludes changing it), and container OS-user
    privilege dropping is not a spec-level commitment in security.md, so
    it is not a finding against the documented model. Flagged so the
    operator can decide whether non-root container execution belongs in
    the threat model as defense-in-depth around the adapter trust boundary
    (security.md §Trust boundaries 1, Adapter → Provider).

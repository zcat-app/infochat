RED-TEAM VERDICT: CLEAN

The prior HIGH DOS finding (leave->re-join cap-laundering: tryRecordJoin's
ON CONFLICT DO NOTHING left a re-joined active group permanently uncounted by
both D47 caps) is remediated by this diff. tryRecordJoin now runs
ON CONFLICT (adapter, upstream_group_id) DO UPDATE SET removed_at = NULL,
inviter_user_id = EXCLUDED.inviter_user_id
(GroupJoinRepository.java INSERT_JOIN), reactivating the freed slot so it
re-counts against both COUNT_BY_INVITER and COUNT_ALL (both now carry
AND removed_at IS NULL). The cap check (GroupInvitationHandler.java:158-171)
runs before tryRecordJoin, so a re-join passes the cap while the slot is freed
and then re-consumes it on reactivation — bounded. A single attacker can never
exceed its per-inviter cap of k active groups (freeing requires an actual
departure on the native BotRemoved path); multi-identity laundering is Sybil,
explicitly deferred to v2 (security.md §"Sybil resistance across adapters").
Re-attribution between inviters cannot amplify the coalition's total active
groups beyond honest multi-identity capacity, which the global cap still binds.
The new GRANT keeps the (adapter, upstream_group_id) natural key out of the
column list, and a Provider SQLi foothold already controlled the caps via the
removed_at UPDATE grant, so no new injection power is conferred; the §DB-roles
injection promise (posts/snapshots/quarantine/audit) is untouched. The
remediation is covered by reJoinReactivatesFreedSlotAndReattributesInviter,
freedJoinIsExcludedFromBothCounts, botRemoved_freesJoinOnlyAutoJoinSlot, and
thresholdPermanentGroupFailuresFreeAutoJoinedSlot.

OUT-OF-MODEL:
  - SimpleX-path slot-freeing via permanent-delivery-failure inference
    (GroupRepository.markRemovedAudited -> GroupJoinRepository.markRemovedByGroupId)
    frees a D47 cap slot on INFERRED removal, not a confirmed BotRemoved event.
    If an adversary could force sustained PERMANENT send failures while keeping
    the bot joined to the group, the slot would free without an actual departure,
    letting the bot accumulate active-but-uncounted groups and partially eroding
    the global max-groups bound on the NUMBER of live groups. This is adapter-
    internal behavior not evidenced in the diff, the D47 group-count caps are
    documented as soft flood-bounds rather than strict invariants (M1-519 redteam
    Finding 1 resolution), per-group reply/command/LLM rate caps (security.md
    §Rate limiting) bound the cost of any single uncounted-active group, and
    M1-526 is the referenced in-band recovery path. Flagged only so the user can
    decide whether to harden the inference signal or audit auto-join slot churn.
  - markRemovedByNaturalKey / markRemovedByGroupId free a join-only group's slot
    with no audit_log row (log line only), matching the already-unaudited
    tryRecordJoin INSERT convention. The threat model commits to auditing command
    intent and the BOT_REMOVED/MEMBER_LEFT group-row events, not passive
    auto-join/leave bookkeeping, so this is not a promised audit surface. Advisory
    only (carried over from the prior audit).

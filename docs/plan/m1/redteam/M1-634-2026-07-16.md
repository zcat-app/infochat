RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: DOS
    SEVERITY: low
    PROMISE: "Per-(user, scope) isolation for state, memory, saves. Never leak
              across users or between DM and group." (CLAUDE.md §Key conventions,
              the isolation invariant security.md constrains) — combined with the
              D35 cancellation model that security.md §Slow-start / commands.md
              §Surface conventions build on: a /stop cancels only the issuing
              (user, scope)'s own in-flight turn.
    GAP: The new interruptible offload runs turns on a FIXED, reused pool of
         threads (InterruptibleDispatcher.dispatch → executor.execute,
         infochat-provider/.../messaging/InterruptibleDispatcher.java:183; pool
         built at :536). Cancellation targets a captured Thread, not the still-held
         slot: CancellationService.cancel
         (infochat-provider/.../chat/CancellationService.java:60-65) calls
         handle.markCancelled() then handle.workerThread().interrupt() with NO
         re-check that the slot is still held by that handle at interrupt time.
         The captured workerThread is the pool thread that was running turn A.
         The mitigation added for this exact hazard — Thread.interrupted() in
         InterruptibleDispatcher.runStage's finally (InterruptibleDispatcher.java:226,
         whose comment claims it "confines a cancellation to the task it targeted")
         — only covers the interleaving where the stale interrupt lands BEFORE the
         next task's first blocking call. It does NOT cover the interleaving where
         cancel()'s own interrupt() call at CancellationService.java:65 is delayed
         (the /stop thread descheduled between reading the handle at :48-49 and
         issuing the interrupt at :65) until after the pool thread has finished
         turn A, released slot A, run the finally, and recycled to turn B for a
         DIFFERENT (user, scope), entering turn B's blocking LLM/HTTP call. The
         interrupt then lands on turn B and raises ClosedByInterruptException in
         user Y's LLM call.
    REPRO: User X has a chat turn A in flight (pool thread T holds the
           InFlightTracker slot). User X sends /stop; CancellationService.cancel
           reads handle H for (X, scope) while the slot is still held, then is
           descheduled just before H.workerThread().interrupt(). In that window
           turn A completes, releases its slot, thread T is recycled by the pool
           to run turn B for user Y and enters Y's generate() HTTP call. cancel()
           resumes and interrupts T — now running Y's turn. Turn B's own
           cancelled flag (handle H_B) is false, so it is not treated as a /stop,
           but the interrupt has already broken Y's LLM call: Y's turn degrades to
           the failure terminal ("chat unavailable") instead of Y's answer. User X
           has thereby caused a different user's turn to fail — a cross-(user,
           scope) effect the isolation invariant forbids. The window is very tight
           and not reliably attacker-triggerable, hence low, but it is a genuine
           residual gap the code's own comment asserts is closed.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

OUT-OF-MODEL:
  - Under pool saturation, ThreadPoolExecutor.CallerRunsPolicy
    (InterruptibleDispatcher.java:541) runs an interruptible turn INLINE on the
    single transport dispatch thread, so the D35 "/stop cancels immediately"
    property degrades back to the pre-M1-634 unreachable state for the duration of
    that inline turn (a queued /stop on the same dispatch thread waits behind it).
    The diff documents this as the intentional pre-M1-634 fallback with the
    transport's bounded inbound queue (M1-224) as the memory bound, and no NEW drop
    path or unbounded LLM concurrency is introduced (max concurrent LLM calls stay
    bounded at pool size + a fixed per-adapter inline count). security.md commits
    to the bounded-queue memory guard, not to /stop reachability under all load, so
    this is a documented degradation rather than a threat-model violation — flagged
    so the user can decide whether D35 immediacy under saturation warrants a
    stronger guarantee.

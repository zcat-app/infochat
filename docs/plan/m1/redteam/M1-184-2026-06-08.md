RED-TEAM VERDICT: CLEAN

The diff hardens the Signal daemon-stream intake (`SignalMessageCodec.decode`/`extractDm` and `SignalJsonRpcClient.handleLine`) against malformed frames. Audited against every threat-model commitment that touches the changed surface (input validation / message intake, the Adapter→Provider trust boundary, D37 "User content in exceptions," and DOS "blocking-the-event-loop in the messaging adapter"), I found no gap between promise and delivery:

- DOS / reader-survival: `decode` and `extractDm` are now provably total over arbitrary frame shapes. Every JSON accessor uses `get()` + `instanceof` or the `getString/getInt(name, default)` total variants; `containsKey` and `canonicalizeAci` cannot throw; the only two `throw` sites in `decode` are caught by `handleLine`'s broadened `catch (RuntimeException e)`. The DM/group/handler dispatch paths (`handler.onMessage`, `dispatchGroupNotification`) are each wrapped, so no hostile frame can kill the reader or dispatch thread and leave a live-but-deaf adapter (`SignalMessageCodec.java:142-195`, `SignalJsonRpcClient.java:543-556, 637-647`).
- D37 / no user content in logs or exceptions: `decode` now throws fixed-text `IllegalArgumentException("Malformed JSON-RPC envelope")` with the raw line removed and the parser cause dropped entirely (`SignalMessageCodec.java:104, 117`). `handleLine` logs only `e.getClass().getSimpleName()`, never `getMessage()` (`SignalJsonRpcClient.java:553-554`). The cause-chain absence is pinned by `decodeExceptionMessagesCarryNoFrameContent`.
- Trust boundary / identity: `sourceUuid` is read via the total `getString(..,null)` accessor and dropped if absent or wrong-typed; display-name fields (`sourceName`) remain unused for identity. No change weakens the cryptographic-ID anchor.
- The attacker-influenced `timestamp` only feeds `Instant.ofEpochMilli` and the `"signal-"+ts` message id; `longValueExact` overflow/fractional inputs are caught and drop the frame (`integralLong`, lines 185-195). The id format is unchanged by this diff.

The remaining diff (`FakeRelayServer` Vert.x→JDK-socket rewrite, `CapturingLogHandler`, two new tests) is test-only and touches no production trust boundary.

OUT-OF-MODEL:
- Pre-existing (not introduced by this diff): `SignalJsonRpcClient` line assembly (lines ~520-537, outside the audited hunks) reads a daemon line until `\n` with no maximum-length bound, so a single oversized inbound line buffers unboundedly in `handleLine`'s `String line`. This is an in-model DOS shape but lives in untouched code; flagging only so the user can decide whether a separate ticket should cap inbound line length.
- `FakeRelayServer.handshake` reads request headers via an unbounded `readLine` loop and then byte-reads to EOF; this is a loopback test fixture dialed only by the probe under test, not a production attack surface.

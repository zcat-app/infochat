# Red-team verdict — M1-097

## Verbatim verdict (from the threat-actor subagent)

```
RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
- No persistent/Prometheus-style metric for the failed-signature counter.
  The diff exposes failedSigCount() as a package-private getter and logs
  the 1st + every-100th drop; the counter is otherwise in-memory per
  NostrStreamSource instance and is lost on restart. The spec calls the
  counter "the audit surface" but does not commit to durability or
  external scrape; the Prometheus counter shape lives in design notes
  (security.md §"What lives in design notes"). Flagging as advisory in
  case the user wants to elevate the counter to a Micrometer/Prometheus
  metric.

- Signature-valid events of disallowed kinds (e.g. kind 4 DMs, kind 7
  reactions) are silently dropped with no counter at all
  (NostrStreamSource.java:147-150 in the diff explicitly:
  "No counter — kind drops are noise"). The spec only requires a counter
  for failed verification, not for kind drops, so this matches the
  documented model. A hostile relay flooding signature-valid
  disallowed-kind events would burn verifier CPU per event with no
  operator-visible signal — but per-relay degradation / rate-cap is
  explicitly deferred to M1-099, so this falls inside a deferred ticket's
  scope.

- BIP-340 implementation uses BC's BigInteger/ECPoint math, which is not
  constant-time. The verifier holds no secrets (pubkey is public,
  signature is public, message hash is public), so timing leaks would
  expose nothing not already on the wire. Noted only because hand-rolled
  crypto in NostrEventVerifier.java:89-135 is a maintenance liability
  worth a periodic re-review against the BIP-340 reference vectors.

- The spec text "dropped without parsing" for disallowed kinds is met in
  spirit (no body extraction, no normalization, no outbox write) but not
  literally (Jackson does deserialize the event object before the kind
  gate fires, because the kind gate runs after signature verification per
  the spec's mandated ordering). The two clauses of the spec are in mild
  tension; the implementation chose the explicit ordering clause, which
  is the more security-relevant of the two.
```

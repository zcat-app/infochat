Assessment summary (threat-actor):
- concurrentExecution=SKIP on schedulers: hardening (DOS reduction), no regression.
- Bluesky timestamp parse (parseIndexedAtOrNull): correct boundary validation, no leak.
- PerSourceUnknownTracker per-source coalescing key: fixes a notification-suppression

- PerSourceUnknownTracker fetched_at partition bound: documented semantic narrowing;
  worst-case-lag argument holds for first-pass UNKNOWN verdicts (re-eval'd UNKNOWN
  posts carry stage2_failed=TRUE and are already excluded), so the auto-disable
  promise is not meaningfully weakened. Low/defensible.
- CDI SSRF producer + @Inject: SSRF guard wiring preserved, behavior identical, IT
  asserts it (assertSame to the CDI-produced bean).

No promise in the threat model is broken by this diff.

OUT-OF-MODEL:
  - The PerSourceUnknownTracker SQL gains a `fetched_at >= now() - (window + 2d slack)`
    bound. This narrows the per-source UNKNOWN auto-disable signal: a post whose
    Stage-2 UNKNOWN verdict lands now but whose fetched_at is older than window+slack
    is excluded from the rate (proven by the new test
    oldPartitionPost_excludedFromRate_sourceNotDisabled). The spec's
    quarantine-exhaustion defense (security.md §Per-source UNKNOWN auto-disable) is
    not meaningfully weakened because first-pass UNKNOWN verdicts — the ones this
    query counts (it requires stage2_failed=FALSE, and re-eval'd UNKNOWNs carry
    stage2_failed=TRUE per §Re-evaluation job, so they are already excluded) — occur
    within seconds/minutes of fetched_at, far inside the 2-day slack. Flagged only so
    the user can confirm the worst-case-eval-lag assumption (slack > max
    fetched_at→verdict lag) is one the spec is comfortable committing to; if a future
    pipeline backlog can exceed 2 days for a first-pass verdict, the auto-disable
    would silently undercount that source's UNKNOWN rate. Not a current finding given
    the documented drain-time argument.
  - Doc-vs-code inconsistency (not a security gap): CollectorSsrfClientProducer
    produces an @Singleton bean, but the ssrfClient() accessor javadoc
    (NostrStreamSource.java:371) and the wiring-IT javadoc claim dispatch goes
    "through the @ApplicationScoped client proxy." @Singleton is a pseudo-scope with
    no proxy. The assertSame in the IT still holds; no behavioral or trust-boundary
    impact.

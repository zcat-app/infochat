RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: DOS
    SEVERITY: low
    PROMISE: docs/spec/security.md §"User content in exceptions": "Exception
             messages and stack traces emitted via the application logger MUST
             NOT contain user-authored prose ... The application provides a
             SafeLog utility that drops the exception message body, retains only
             the exception class name, and truncates the cause chain to class
             names (depth-capped at 5)." The spec commits to a bounded cause-chain
             rendering (depth cap 5, class-names-only for causes).
    GAP: The rewritten stackWithoutMessage walks the FULL cause chain with no
         depth cap. The loop guard only prevents cyclic non-termination
         (IdentityHashMap `seen`), not unbounded depth on an acyclic chain, and
         it emits every level's full stack frames rather than the
         class-names-only, depth-5 form the spec commits to. See
         infochat-messaging-adapter/.../simplex/SimpleXAdapter.java:806-819 and
         infochat-messaging-adapter/.../signal/SignalJsonRpcClient.java:985-998
         (for (Throwable current = t; current != null && seen.add(current); ...)
         with no depth counter and a per-level getStackTrace() append).
    REPRO: A deep-but-acyclic wrapped-exception chain arising in the inbound
           handler renders every level's class name plus every level's full
           stack frames into a single log line, unbounded by the spec's depth-5
           cap. This bloats the log entry well beyond the committed bound. Not
           realistically attacker-driven (exception nesting depth is a function
           of internal call structure, not inbound message content, and the
           cycle guard prevents true infinite loops), so this is a
           defense-in-depth / resilience gap rather than a reachable exploit —
           but it is a stated spec commitment the diff does not deliver. The
           user-prose-suppression property itself IS delivered: getMessage() is
           never rendered at any level (verified by the added
           stackRenderingIncludesCauseChainFramesButNoMessages and
           stackRenderingTerminatesOnCyclicCause tests), so no user content
           leaks.
    SUGGESTED-FIX-CLASS: other

OUT-OF-MODEL:
  - Stack frames (StackTraceElement) and class names are content-free by
    construction, so the diff's decision to render full frames per cause level
    (vs the spec's class-names-only for causes) does not leak user-authored
    prose; it only affects log size, which is folded into the DOS finding above.

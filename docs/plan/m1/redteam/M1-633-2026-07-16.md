RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - Roster-binding race / social engineering via Sybil knocks. On SimpleX an
    attacker can mint fresh connections at will (Sybil resistance is explicitly
    out of v1 scope, security.md §What's intentionally NOT in v1) and knock
    immediately after a legitimate person connects, placing an attacker id at
    the top of the most-recent-first /invite pending-contacts roster. An admin
    expecting "Alice just connected" may bind a --contact code to the
    attacker's id. Residual risk is bounded: the mis-bound code fails for the
    legitimate contact (contact_id mismatch at consume) and grants the attacker
    nothing unless the admin also delivers the code to the attacker's own
    connection out-of-band. Worth a line in operator guidance (confirm the id
    with the person out-of-band before binding), not a threat-model breach.
  - Sybil-driven invite_code_attempt bloat now has an admin-facing read cost.
    The table is append-only with operator TRUNCATE as the only purge path
    (security.md §DB roles), and the new roster query
    (InviteCommandHandler.java SELECT_PENDING_CONTACTS_SQL) runs a per-adapter
    GROUP BY plus a NOT EXISTS anti-join over it on every admin invocation.
    An adapter-level Sybil flood (out of v1 scope) can both bury legitimate
    candidates behind pages of attacker ids and grow the scan cost unboundedly.
    Admin-only, rate-bucketed invocation and the pre-existing table-growth
    posture keep this outside the documented model; an index/retention story
    for invite_code_attempt is the hardening lever if it ever bites.
  - Lenient trailing-token parsing on the new subcommand. ListArgs.parse
    silently ignores unrecognized tokens, so `/invite pending-contacts
    --adapter signal` quietly lists the INBOUND adapter's roster instead of
    erroring (same posture as the existing /invite list). No commitment is
    breached — the security.md malformed-input rejection promise is scoped to
    issuance (`/invite create`), and the disclosure stays inbound-adapter-
    scoped regardless — but an admin typo can yield a roster from a different
    adapter than the admin believes they are viewing. Ids mis-copied across
    adapters fail safe at consume time (adapter is part of the match key).

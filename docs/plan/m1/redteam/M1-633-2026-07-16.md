RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - Roster-binding race / social engineering via Sybil knocks. On SimpleX an
    attacker can mint fresh connections at will (Sybil resistance is explicitly
    out of v1 scope, security.md §What's intentionally NOT in v1) and knock
    immediately after a legitimate person connects, placing an attacker id at
    the top of the most-recent-first /invite pending-contacts roster. An admin
    expecting "Alice just connected" may bind a --contact code to the
    attacker's id. Residual risk is bounded: the mis-bound code fails for the
    legitimate contact (contact_id mismatch at consume) and grants the attacker
    nothing unless the admin also delivers the code to the attacker's own
    connection out-of-band. Worth a line in operator guidance (confirm the id
    with the person out-of-band before binding), not a threat-model breach.
  - Sybil-driven invite_code_attempt bloat now has an admin-facing read cost.
    The table is append-only with operator TRUNCATE as the only purge path
    (security.md §DB roles), and the new roster query
    (InviteCommandHandler.java SELECT_PENDING_CONTACTS_SQL) runs a per-adapter
    GROUP BY plus a NOT EXISTS anti-join over it on every admin invocation.
    An adapter-level Sybil flood (out of v1 scope) can both bury legitimate
    candidates behind pages of attacker ids and grow the scan cost unboundedly.
    Admin-only, rate-bucketed invocation and the pre-existing table-growth
    posture keep this outside the documented model; an index/retention story
    for invite_code_attempt is the hardening lever if it ever bites.
  - Lenient trailing-token parsing on the new subcommand. ListArgs.parse
    silently ignores unrecognized tokens, so `/invite pending-contacts
    --adapter signal` quietly lists the INBOUND adapter's roster instead of
    erroring (same posture as the existing /invite list). No commitment is
    breached — the security.md malformed-input rejection promise is scoped to
    issuance (`/invite create`), and the disclosure stays inbound-adapter-
    scoped regardless — but an admin typo can yield a roster from a different
    adapter than the admin believes they are viewing. Ids mis-copied across
    adapters fail safe at consume time (adapter is part of the match key).

## Out-of-model disposition (2026-07-16, post-merge evaluation)

Everything above this line is the threat-actor's verbatim verdict. This
section is the operator-decision record for the three OUT-OF-MODEL items;
each claim below was re-verified against the code, not taken from the
audit's framing. Outcome: **all three closed, no ticket filed.**

**1. Sybil knock racing the roster — CLOSED, no code change.**
Fail-safe confirmed at `InviteCodeConsumer.java:103`
(`AND (invite_type = 'OPEN_ADAPTER' OR expected_contact_id = ?)`): a code
mis-bound to an attacker's id is unredeemable by the intended person AND
worthless to the attacker, who never receives it (the admin delivers the
code out-of-band to the intended person). A won race therefore costs a
confused retry, not access; the attacker profits only if they also control
the code-delivery channel, in which case the roster is irrelevant to the
outcome. Sybil resistance is out of v1 scope (security.md §What's
intentionally NOT in v1). Residual mitigation is operator behavior —
confirm the id out-of-band before binding — worth a sentence of onboarding
guidance whenever those docs are next touched, not a ticket.

**2. invite_code_attempt growth / roster read cost — CLOSED. The suggested
retention lever is REJECTED, not deferred.**
The audit suggests "an index/retention story for invite_code_attempt is the
hardening lever if it ever bites." Both halves fail on inspection:
  - *Retention would erode a deliberate security property.* V12's header
    states it explicitly: "Rows accumulate forever in v1; no TTL. The
    operator-side TRUNCATE under the admin role is the incident-response
    purge path — mirroring the audit-log append-only treatment so a
    misconfigured GRANT cannot delete the patient-brute-force evidence.
    DELETE is intentionally NOT granted to either service role."
    (security.md §DB roles, line ~1286, backs the TRUNCATE-only posture.)
    A TTL/purge sweep is precisely what V12 refuses. Do not file it as
    hardening; a future session proposing it should read V12 first.
  - *No index is missing.* `idx_invite_code_attempt_lookup
    (adapter, contact_id, attempted_at DESC)` already leads with the
    roster query's filter column and grouping key; the NOT EXISTS
    anti-join rides `users_adapter_contact_unique`. (No EXPLAIN was run —
    the claim here is only that no absent index was identified.)
True residual: M1-633 introduced the first query over this table that
scales with rows-per-adapter rather than a bounded window. Growth requires
many DISTINCT contact ids (the per-(adapter, contact_id) brute-force
limiter bounds per-contact growth) — i.e. Sybil, out of scope — and the
command is bot-admin-only, rarely invoked, and paged at 20.

**3. Lenient trailing-token parsing — CLOSED, no code change.**
The audit's "admin believes they are viewing a different adapter" risk is
largely self-correcting: `reply.invite.pending_contacts_header`
interpolates the INBOUND adapter, so `/invite pending-contacts --adapter
signal` sent from a SimpleX DM renders "Connected but unregistered contacts
on `simplex`" — the reply names the real adapter and visibly contradicts
the typo. Beyond that, `/invite list` has the identical posture (unknown
tokens ignored, page-1 fallback), so making pending-contacts strict alone
would leave the two read-only invite subcommands inconsistent; making both
strict changes shipped `/invite list` behavior and needs its own spec pass.
The spec scopes malformed-input rejection to `/invite create` deliberately:
that is the path that mints state, whereas reads are idempotent and
self-describing.

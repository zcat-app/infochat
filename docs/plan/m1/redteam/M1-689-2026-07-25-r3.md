         `/summary` result set for the first time (the window predicate
         moved from `published_at >= ?` to `ready_at >= ?` at
         infochat-provider/src/main/java/app/zcat/infochat/provider/summary/EligiblePostQuery.java:226).
         The column is nullable
         (infochat-core/src/main/resources/db/migration/V7__joins_post.sql:145)
         and PostPersister binds SQL NULL for a feed item with no usable
         date (infochat-collector/src/main/java/app/zcat/infochat/collector/outbox/PostPersister.java:193-195).

         readers of that column and guarded it —
         infochat-provider/src/main/java/app/zcat/infochat/provider/digest/DigestPostCollector.java:106,117-119
         ("Reachable here only since M1-689 moved the window predicate off
         this column"). It missed the third reader:
         infochat-provider/src/main/java/app/zcat/infochat/provider/command/RetryCommandHandler.java:353
         still does an unguarded `rs.getTimestamp("published_at").toInstant()`.
         That reader is on the `/retry` replay path, which is fed directly
         from the newly-widened `/summary` set:
         SummaryCommandHandler.java:322,325 freezes `result.posts()` uids
         into `summary_anchor.post_uids`, and RetryCommandHandler.java:175
         -> :322 -> :342 re-reads them with
         `WHERE p.uid = ANY(?) AND p.status = 'READY'` — no published_at
         predicate to filter the NULL row back out. The NPE is thrown at
         line 175, outside any try/catch in `handle`, so it escapes the
         command handler.
         Nothing catches this at build time or test time:
         `EligiblePostQuery.Post.publishedAt` is already `@Nullable`
         (EligiblePostQuery.java:124) so NullAway has no contract to
         violate on the Java side, and `java.sql.ResultSet.getTimestamp`
         is unannotated third-party, so the unguarded `.toInstant()`
         compiles clean. Neither retry test can express the case:
         RetryCommandHandlerGroupScopeIT (modified by this diff) seeds

OUT-OF-MODEL:
  - (advisory, not a finding) Sort-plan cost after V64 drops
    `idx_post_published`. No btree can serve `COALESCE(published_at,
    fetched_at) DESC`, so all four window queries now sort their window
    set per call instead of walking an ordered index to the LIMIT. The
    widest case is `searchPosts` with `window: P30D`. Bounded by the
    armed `statement_timeout`, the LIMIT/cluster-cap and the per-turn
    tool-call cap; no spec-level query-cost budget exists to measure it
    against, and the migration note and design notes state it explicitly.
    Same item the earlier rounds raised; recorded as dispositioned.
  - (advisory, not a finding) Prose precision in the newly-added
    security.md `searchPosts` bound: "It cannot outrank later fetches" is
    loose. An undated post fetched at T keys at T and therefore DOES
    outrank a post from a LATER fetch whose stated date is older than T.
    The operative clause immediately before it — "level with the ceiling
    a dated post from that same fetch could claim — and no higher" — is
    accurate, and it is the clause the defense rests on: I verified the
    ingest clamp's ceiling is exactly `fetched_at`
    (PostPersister.java:193-194, `publishedAt.isAfter(fetchedAt) ?
    fetchedAt : publishedAt`), so a dated attacker can already claim that
    same instant by asserting any future date. Omitting the date
    therefore buys no position a dated post could not already take, and
    no attacker capability follows from the loose sentence. Raising it as
    a finding would be a prose nit with no exploit behind it.

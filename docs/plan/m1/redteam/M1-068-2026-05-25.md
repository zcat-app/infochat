# Red-team audit: M1-068 (2026-05-25)

RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: DOS
    SEVERITY: low
    PROMISE: "Per-user token buckets bound [...] LLM-triggering operations
    (chat replies + on-demand /summary + /retry re-rolls) — its own bucket,
    capped lower, profile-driven."
    GAP: InboundRouter.java:267-268 — the llmCallTimestamps ConcurrentHashMap
    never evicts entries for users who stop sending messages. Each registered
    user who ever sends a chat-mode message leaves a permanent (UUID,
    ArrayDeque) entry. While individual deques are pruned of timestamps older
    than 60 s, the map keys persist for the JVM lifetime.
    REPRO: Over an extended deployment, many distinct registered users each
    send at least one chat-mode message. Each creates a permanent map entry.
    After months, the map holds thousands of entries for inactive users,
    consuming heap proportional to total registered-user population rather
    than active population. Per-entry cost is ~80 bytes, so this requires a
    large user population to matter.
    SUGGESTED-FIX-CLASS: other

  - CATEGORY: INFO-LEAK
    SEVERITY: low
    PROMISE: "Before any LLM-generated text is delivered to a user, the
    candidate output is passed through a deterministic outbound regex pass
    that strips or refuses output containing admin command strings [...].
    The sanitizer applies to the full set of LLM-authored output surfaces:
    chat-mode replies [...]"
    GAP: ChatAgent.java:41-42,141 — the TOOL_CALL_PATTERN regex requires
    both a tool name AND a JSON body ({.*?}) to match. A partial tool call
    emitted by the LLM (e.g. "TOOL_CALL: searchPosts" without JSON args,
    or "TOOL_CALL: searchPosts {broken" with no closing brace) will not
    match and will pass through to the user. The output sanitizer only
    strips privileged-tier command tokens, not internal tool protocol.
    REPRO: User sends a chat-mode message. LLM runs through
    MAX_TOOL_ITERATIONS. The final forced LLM call still includes
    TOOL_INSTRUCTIONS in the system prompt. LLM emits "Here is your
    answer. TOOL_CALL: searchPosts" (no JSON body). The regex does not
    match. The user sees the internal protocol text.
    SUGGESTED-FIX-CLASS: input-sanitization

  - CATEGORY: AUDIT-EVASION
    SEVERITY: low
    PROMISE: "Audit-log the intent." (security.md §Authorization model
    step 8) and "The audit log records intent (command name, actor, scope,
    target), not user-authored prose." (security.md §Secrets handling)
    GAP: ChatAgent.java:281-294 — writeAuditRow records scope_kind
    ("dm"/"group") in detailsJson but does not record scopeId. For
    group-scope chat-mode requests, the audit row does not identify WHICH
    group. For DM scope, scopeId == userId so it's derivable from
    actorUserId, but for group scope this is a gap.
    REPRO: User A sends a chat-mode message in Group X. The audit row
    records action=CHAT_MODE, actor_user_id=A, target_kind=user,
    target_id=A, details_json={"scope_kind":"group"}. An auditor cannot
    determine which group was targeted without cross-referencing
    chat_session. If the user is in multiple groups, the row is ambiguous.
    SUGGESTED-FIX-CLASS: audit-log-coverage

OUT-OF-MODEL:
  - The per-user LLM rate cap covers only chat-mode, not the full
    "LLM-triggering operations" bucket (chat + /summary + /retry) the
    spec envisions. The ticket explicitly marks the shared-bucket
    infrastructure as a follow-up. An attacker who discovers the chat-mode
    cap can pivot to /summary for unbounded LLM calls. This is a
    pre-existing gap not introduced by this diff.

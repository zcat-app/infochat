    SEVERITY: low
    PROMISE: docs/spec/security.md §Trust boundaries item 3 — "**Authorization →
             execution.** Permission checks run in deterministic Java. The LLM is
             downstream of every authorization decision" — and §What's
             intentionally NOT in v1 — "Two-factor confirmation for ban —
             single-step confirm-within-window is enough for v1", i.e. the
             confirm-within-window IS the v1 control that binds a destructive
             admin primitive to the target the admin named. The diff's own spec
             amendment (docs/spec/commands.md §Surface conventions, added lines)
             states a confirm leg "is a confirmation **only when that argument
             names the very action awaiting confirmation**".
    GAP: The newly-stated identity binding is enforced in exactly ONE place — the
         router's cancel-vs-leave-alone sweep
         (infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/InboundRouter.java:1707-1733,
         called from InboundRouter.java:970). The handler-side pop that the same
         method's javadoc calls "the authoritative {@code takeMatching} call"
         (InboundRouter.java:1685-1687) was NOT changed and remains
         target-blind: every confirmable handler forks on a bare suffix test and
         then executes the STORED payload with no comparison against the body
         that triggered it —
         BanCommandHandler.java:190-199 (`rawText.trim().endsWith(" confirm")` →
         `takeMatching` → `executeBan(pendingBan.targetContactId(), …)`),
         RejectGroupCommandHandler.java:136-143,
         QuarantineCommandHandler.java:333-341,
         InviteCommandHandler.java:422-433 and :762-770,
         UnfollowTagCommandHandler.java:199-205. So the property "a confirm leg
         may not execute against a target it did not name" is a router
         invariant, not a property of the primitive. I verified there is no
         dispatch path today that reaches a handler while skipping step 4.5 —
         `runDispatchStage` has a single call site (InboundRouter.java:1095) and
         the interruptible fork (InboundRouter.java:1028-1094) carries no
         confirm-arming command — which is why this is low and not high. But the
         defence is one refactor deep: any future early-dispatch shortcut, or a
         new confirmable handler whose `sweepPrefix()` does not exactly prefix
         the body its own fork accepts, silently re-opens M1-775's original
         wrong-target execution with no test failing (the four new router tests
         all drive the full `onMessage` funnel, so none of them would notice).
    REPRO: Today (post-fix) the sequence is contained, and the repro is the
           dependency, not an exploit:
           1. Bot admin DMs `/ban alice-contact` → BanConfirm("alice-contact")
              armed, BAN_INTENT audited.
           2. Admin (or an admin whose client auto-completes) sends
              `/ban bob-contact confirm`.
           3. Router step 4.5 calls isConfirmShape → retyped segment
              "bob-contact" ≠ "alice-contact" → takeAny drains the entry and
              replies "Pending `ban` cancelled." Only because of that drain does
              BanCommandHandler's `takeMatching` come back empty.
           4. Remove step 3 from the picture — i.e. any code path that dispatches
              a slash body without step 4.5 — and BanCommandHandler.java:190-199
              pops BanConfirm("alice-contact") and bans alice from a message
              that names only bob, with the BAN effect row correlating to
              alice's intent. The primitive itself cannot tell the two bodies
              apart.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

OUT-OF-MODEL:
  - Write-triggered-only expiry of the pending-confirm map
    (ConfirmStateService.java:113). The sweep runs inside `remember()`, so in a
    deployment where no further confirm is ever armed, the last expired entries
    persist for the process lifetime holding their payload — for BanConfirm that
    is a full, un-redacted target `contact_id` plus the admin-authored `reason`
    string. Steady-state map SIZE is genuinely bounded (any `remember` prunes
    every past-deadline entry, so live entries ≤ the set of (user, scope) pairs
    that armed within one TTL, itself bounded by the §Rate limiting caps), so
    this is not a DOS. It is a data-minimisation residual only, and reading
    Provider process memory is outside the documented adversary model.
    security.md discloses the analogous in-memory residual for the translation
    cache under §Secrets handling ("process-local, never persisted, and
    bounded"; "`/forget` clears chat memory, not this cache"); this one carries
    no equivalent disclosure. Flagging so the user can decide whether the
    §Secrets handling enumeration should name it.
  - Concurrency of the new sweep: `pending.values().removeIf(...)` on a
    ConcurrentHashMap was checked for the "removes by key, not by value" hazard
    that would make it a cross-user cancel of a concurrently re-armed entry.
    `ConcurrentHashMap.ValuesView.removeIf` delegates to `removeValueIf`, whose
    `replaceNode(k, null, v)` is value-conditional, and `Stored` is a record
    with value equality — so a freshly re-armed entry is not removed. Verified,
    NOT a finding; recorded so a future reader does not re-derive it.

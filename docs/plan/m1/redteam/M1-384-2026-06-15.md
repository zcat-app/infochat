RED-TEAM VERDICT: CLEAN

FINDINGS: (none)

The diff under audit adds one operator-facing deployment wizard subscript
(prod/scripts/6-adapter.sh) plus ticket/STATUS bookkeeping. No runtime
service code, no adapter intake path, no authorization/ban/audit Java, and
no SQL is touched. The script's only inputs are interactively typed by the
operator at deploy time.

Audited against every commitment in docs/spec/security.md; the relevant
ones and why each holds:

- "Operator-set config (properties files, bootstrap JSON) is trusted"
  (threat model, line 27). Every value this script reads (adapter list,
  SimpleX URL, identity dirs, session token, per-adapter admin contact id)
  is operator-supplied at an interactive prompt. The operator is the
  trusted principal; there is no adversary on this input path within the
  documented model. Supply-chain attacks on operator infrastructure are
  explicitly out of scope (line 29-33).

- Non-empty admin union (§7.6.3 / Authorization model "Last-admin
  protection" + "Operator-side mitigations"): the spec requires the union
  of bootstrap admins across enabled adapters to be non-empty. The script
  delivers exactly this — admin_union is tallied across chosen adapters
  (6-adapter.sh:254-256, 265-267) and the load-bearing gate refuses to
  write config and exits non-zero when it is zero (6-adapter.sh:277-282),
  BEFORE any config side effect, so a refused run leaves no half-written
  block (6-adapter.sh:284-290). The per-adapter property is correctly kept
  optional: the bootstrap-admin line is emitted only when that adapter has
  a contact set (6-adapter.sh:305-307, 311-313), matching "optional per
  adapter as long as the union is non-empty" (§Per-adapter admin threat
  profile).

- Idempotent/resumable contract: capture_secret and collect_admin skip a
  key already present in secrets.env (6-adapter.sh:172-174, 192-194), and a
  prior-run admin still counts toward the union via collect_admin's
  already-set return-0 path, so a resume does not spuriously fail the gate
  or overwrite captured secrets. The config rewrite strips prior
  infochat.adapters lines first (6-adapter.sh:288-290) so a re-run with a
  changed selection cannot leave stale per-adapter properties — no
  authorization-relevant residue.

- Secrets handling: the captured SimpleX session token is written to a
  umask-077 + chmod-600 secrets.env (6-adapter.sh:148-151, 170-185) and
  referenced from application.properties only as ${SIMPLEX_SESSION_TOKEN}
  (6-adapter.sh:303), never inlined into the world-readable properties
  file. Hidden (-s) input is used for the token. This is consistent with
  §Secrets handling (keys/secrets out of plaintext config).

- Closed adapter set (D46): the in-memory test adapter is never offered and
  free-text selection is validated against the closed {simplex, signal} set
  at the system boundary (6-adapter.sh:218-232), so production cannot mix in
  the test adapter — consistent with the cross-adapter trust-level model.

No threat-model commitment is left undelivered by this diff.

OUT-OF-MODEL:
  - application.properties config injection via operator-typed values: the
    SimpleX URL and identity-dir strings are written verbatim into
    application.properties with printf '...=%s\n' (6-adapter.sh:302-310). An
    operator who types a value containing an embedded newline could inject
    additional property lines (e.g. a spoofed bootstrap-admin-contact-id).
    This is self-injection by the trusted operator, not an adversary-reachable
    surface — "Operator-set config is trusted" (threat model line 27) places
    it outside the documented model. Flagged only so the user can decide
    whether deploy-time input hardening is worth adding; it is not a
    threat-model violation.

RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: AUDIT-EVASION
    SEVERITY: medium
    PROMISE: "The audit log records *intent* (command name, actor, scope, target), not user-authored prose." (docs/spec/security.md §Secrets handling) and "Audit-log the intent." (docs/spec/security.md §Authorization model step 8)
    GAP: ForgetCommandHandler.java:227-237 — the `insertAudit` method builds the `RedactionHook.AuditRow` without calling `.scopeId(scopeId)` on the builder, even though the `scopeId` variable (the DM user UUID or the group UUID identifying which scope was purged) is available at the call site in `executeForget` at line 103. The spec explicitly lists "scope" as a required component of the audit intent. An operator reviewing the audit log after a `/forget` cannot determine which scope was purged — was it the user's DM, or a specific group? This matters because `/forget` is a per-scope destructive operation (it purges different data sets depending on the scope), and the remaining-scopes disclosure means multiple `/forget` invocations for the same user can target different scopes. Without the scope_id the audit trail conflates all of them into a single undifferentiated "user purged something."
    REPRO: (1) User A runs `/forget` then `/forget confirm` from DM scope. (2) User A runs `/forget` then `/forget confirm` from Group-X scope. (3) Operator queries `SELECT * FROM audit_log WHERE action = 'FORGET' AND actor_user_id = <A>`. (4) Both rows have `scope_id = NULL`; the operator cannot distinguish which row corresponds to which scope purge. The spec promises the audit row records "scope" but the diff does not deliver it.
    SUGGESTED-FIX-CLASS: audit-log-coverage

OUT-OF-MODEL:
  - The `ForgetCommandHandler.contactIdOf(ScopeRef)` method returns `null` for `ScopeRef.Group`, which means `lookupUser(adapter, null)` returns empty and the handler returns `ERROR_INTERNAL` for any group-scope invocation. This is a pre-existing pattern across all command handlers (the group dispatch path is deferred per the `InboundRouter` comments). It is not a security finding because the group-scope dispatch path is not yet wired end-to-end in v1, but it is worth noting that if/when group scope is enabled, the `ForgetCommandHandler` will need a mechanism to resolve the caller's contact_id from the group-scope `InboundMessage.sender()` (which is available in the router but not propagated to handlers via the current `CommandHandler.handle(ScopeRef, String)` signature).

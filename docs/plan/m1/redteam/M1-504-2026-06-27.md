OUT-OF-MODEL:
  - Fail-fast regression on operator-mistyped SimpleX admin config. The diff
    lowers SimpleXIdentity.MIN_QUEUE_ADDRESS_LENGTH from 43 to 32
    (infochat-messaging-adapter/.../simplex/SimpleXIdentity.java:34), which the
    diff itself documents as now ACCEPTING a 36-char Signal ACI pasted into the
    SimpleX admin slot (SimpleXIdentityTest.java:46-56,
    wellFormedNoLongerRejectsSignalAciByLength). This weakens the startup
    fail-fast that M1-208 added: an operator who mistypes a Signal ACI into
    infochat.adapters.simplex.admin no longer fails Provider startup and instead
    seeds a "phantom" SimpleX admin row that no real inbound contact can ever
    claim. This is NOT a threat-model finding for two reasons rooted in
    security.md: (1) §Trust boundaries states "Operator-set config (properties
    files, bootstrap JSON) is trusted" — the value gated here flows only through
    the bootstrap-admin parse gate (AdapterRegistry.java:318,
    AdminBootstrap.java:198) and the bot's own subprocess-derived identity
    adoption (SimpleXAdapter.java:400), never through any adversary-controlled
    intake path (inbound parsing uses charset-only isValidQueueAddressId, which
    is unchanged); and (2) §Authorization model "Last-admin protection — Blind
    spot" explicitly pre-classifies the phantom-admin-from-mistyped-contact-id
    scenario as "an operator-misconfiguration risk, not an adversary-reachable
    path — the seeded contact id is trusted operator config (§Trust boundaries),
    never attacker-controlled." The new floor of 32 also exactly equals the
    documented real wire width (24-byte SMP recipient queue id -> 32 URL-safe
    base64 chars), so it does not admit any value shorter than a genuine queue
    address. The reduced floor opens no cross-adapter identity bleed: the
    accepted ACI-shaped value is still stored as a SimpleX contact_id and the
    adapter field remains part of every identity/invite match key
    (§Invite-code registration "Cross-adapter isolation"). Flagged only so the
    user can decide whether the lost fail-fast warrants restoring a stricter
    SimpleX-specific format check (e.g. rejecting the UUID hyphen shape) as
    defense-in-depth on trusted config; it is not an exploitable gap against the
    documented threat model.

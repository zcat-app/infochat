      The remediation targets only round-1 finding 2. The new catch in
      Stage2VerdictHandler.applyQuarantineVerdict
      (infochat-collector/src/main/java/app/zcat/infochat/collector/eval/stage2/Stage2VerdictHandler.java,
      diff lines 326–349) classifies SQLState 23505 from
      idx_quarantine_one_pending_stage2_row
      (infochat-core/src/main/resources/db/migration/V70__quarantine_one_pending_stage2_row.sql,
      diff lines 766–768) as a benign duplicate and returns normally —
      but, as the diff's own comment states, "a statement error aborts
      the PostgreSQL transaction — only rollback can follow": the
      ENTIRE verdict transaction (the post UPDATE plus the colliding
      insert) still rolls back. On the re-eval path that post UPDATE
      carries the new verdict and the attempt-counter increment, and
      the collision is guaranteed, not racy: M1-742 inserts a PENDING
      flagged_by='stage2' row UNCONDITIONALLY on every first-pass
      non-BENIGN verdict (diff lines 300–325), including UNKNOWN, and
      UNKNOWN posts are exactly what feeds the re-eval queue. Every
      re-eval verdict therefore collides with the still-pending
      first-pass row, rolls back, and the counter never increments — so
      the spec's retry bound never engages. The remediation makes this
      strictly quieter than round 1: apply() now returns normally, so
      the re-eval job believes the verdict was applied; the only signal
      is an INFO log line, and no stage2_failed stamp, no NEEDS_REVIEW
      transition, and no admin notifier ever fires. (Round-1 finding 2
      — the unclassified escape reaching the fail-open infra-failure
      path — IS genuinely closed by this same catch and is not
      re-reported.)
    REPRO: |
      Attacker publishes borderline content the judge first scores
      UNKNOWN. Under M1-742 the first-pass verdict inserts a PENDING
      stage2 row unconditionally; the post is QUARANTINED with
      stage2_done=true, stage2_failed=false, so it enters the re-eval
      queue. Each re-eval tick spends a judge LLM call; the verdict
      (UNKNOWN/INJECTION/MALWARE) enters applyQuarantineVerdict; the
      stage2-row INSERT collides with the first-pass row under V70's
      partial unique index; the transaction rolls back; the new catch
      swallows the 23505 and apply() returns normally. The attempt
      counter stays at 0 forever — every subsequent tick repeats the
      LLM spend and the silent rollback until a human reviews the
      first-pass row, with no cap exhaustion, no NEEDS_REVIEW
      escalation, and no admin notification, exactly the bound the spec
      promises. The per-source UNKNOWN auto-disable bounds future
      ingest from the attacker's source but the spec keeps
      already-queued posts flowing ("Posts already in the outbox or
      re-evaluation queue continue through their current evaluation
      stage unaffected"), so the queued posts keep burning judge calls.

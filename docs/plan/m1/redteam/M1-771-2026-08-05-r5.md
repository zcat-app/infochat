    GAP: The word walk is evaluated on the POST-TRUNCATE strings, so on any

         bound says padding at either end is caught, visible or not. For an
         over-cut headline, padding at the leading end is not caught, and
         neither is an INVISIBLE pad there — the case the diff's own tests
         claim to close.

         - infochat-provider/.../render/DisplayHeadline.java:263-274
           (`derive` / `renderLine`) builds BOTH operands as
           `truncate(sanitize(flattenToOneLine(boundForScan(x))))`, so each
           line is at most `MAX_LENGTH` (200) chars plus `ELLIPSIS`

           + "…"`).
         - DisplayHeadline.java:381-395 (`displaysAsTheOriginal`) then walks
           the ORIGINAL LINE's whitespace-split tokens against the ANCHOR
           LINE with `indexOf(word, from)` and returns false on the first
           token it cannot find.
         - DisplayHeadline.java:420-429 (`displayForm`) runs AFTER that
           truncation, so dropping the Cf/Mn categories cannot undo a cut the
           padded code point already shifted. The invisible-pad protection the

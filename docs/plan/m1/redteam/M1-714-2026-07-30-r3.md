Round-1 finding 1 (INJECTION, medium) — CLOSED, re-verified against code, not
against the remediation claim.
  - LlmOutputSanitizer.isTokenSeparator (LlmOutputSanitizer.java:392-394) is
    exactly {' ', '\t', '\n', '\r', '\f', ''} — the ASCII \s set, as the
    DisplayHeadline javadoc states.
  - canonicalizeForMatching (LlmOutputSanitizer.java:618-621) is
    NFKC + IngestTextNormalizer.stripBidiAndZeroWidth; that strip deliberately
    excludes U+2028/U+2029 (IngestTextNormalizer.java:97-105), so those three
    code points do reach the matcher intact — the premise of the round-1
    attack is real.
  - flattenToOneLine's "(?:\R|\s)+" covers exactly the gap set (\R adds
    U+0085/U+2028/U+2029 on top of ASCII \s) and runs BEFORE sanitize, so the
    bytes the matcher inspects are the bytes delivered. The reverse direction
    was also checked: the parser's split("\\s+") consumes the SAME step-1.7
    canonical form the sanitizer matches on (NFKC + the same strip), so a
    separator the sanitizer misses is not a separator the parser honours
    (NFKC-to-space characters such as U+00A0/U+3000/U+2000-200A fold in the
    canonical form and are matched there). Pinned by
    DisplayHeadlineTest.unicodeSeparatorInsideAClosedListEntry... and
    ...InsideAFlagEntryIsRedacted.
  - Post-sanitize steps cannot re-arm it: truncate only removes a suffix,
    stripTrailing only touches the string end, and the appended "…" glues onto
    the last token ("/ban…" is not "/ban"; NFKC folds it to "/ban...").

RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - No runtime interlock distinguishes a disposable live-test deployment from
    production. prod/live-reset.sh (prod/live-reset.sh:1-130) and
    prod/sql/reset-control-plane.sql (prod/sql/reset-control-plane.sql:1-92)
    wipe the append-only audit_log (Invariant 10 / D34) and DELETE every user
    (including all bot admins) with the last-admin DELETE trigger disabled,
    guarded only by documentation ("TEST-loop only — never a production
    procedure"). There is no environment assertion, no typed confirmation, and
    no --force flag. This matters because security.md commits audit_log to
    append-only "in production" and withholds audit-trigger-disable / audit
    DELETE even from the operator Admin role (§DB roles). However, the script
    requires the DB OWNER password from runtime/secrets.env plus host + docker
    access — all trusted-operator surface. The threat model explicitly scopes
    out operator infrastructure and host access ("Operator-set config is
    trusted"; §Threat model "Out of scope for v1"), and the spec itself frames
    analogous mistakes (the phantom-admin blind spot) as
    "operator-misconfiguration risk, not an adversary-reachable path." No
    inbound-message / adapter path reaches this tooling, so no in-model
    adversary gains a new capability. Flagged so the user can decide whether to
    add a production-guard interlock (e.g. refuse unless an
    INFOCHAT_ALLOW_LIVE_RESET marker or a non-prod profile is set) as
    defense-in-depth.
  - The audit_log append-only guard (trg_audit_log_no_delete/_update, FOR EACH
    ROW) is bypassed by TRUNCATE at prod/sql/reset-control-plane.sql:64-82. This
    is inherent to Postgres owner/superuser privilege and is consistent with
    §DB roles, which already reserves audit-trigger-disable and unredacted audit
    operations to the owner role (superuser psql). The Provider and Admin roles'
    constraints are untouched, so the D34 commitment ("a SQL-injection bug in
    the Provider cannot ... delete posts ... read unredacted audit rows") still
    holds. Noted only because the TRUNCATE-vs-DISABLE-TRIGGER path lets an owner
    erase audit_log without ever toggling the append-only trigger; this is not a
    regression the diff introduces to any in-model principal.

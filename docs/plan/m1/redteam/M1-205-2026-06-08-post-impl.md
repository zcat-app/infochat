# Red-team verdict — M1-205 (post-reopen implementation), 2026-06-08

Target: M1-205 --in-progress
Base:   main
Head:   m1/M1-205-adapter-rate-limit-enforcement-decision (869adf7)

RED-TEAM VERDICT: FINDINGS

FINDINGS:

  - CATEGORY: DOS
    SEVERITY: medium
    PROMISE: §Authorization model step 1.5 — "Apply the per-`(adapter, contact_id)` inbound rate cap ... before every application-level check below, so a hostile flood cannot drive outbound cost via the per-inbound fixed-reply paths." §Rate limiting commits to bounding flood while the invite-code gate (step 2) remains the working entry path for new contacts.
    GAP: `infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/RateCapBucket.java:234-236`. The new hard cap rejects ANY new `(adapter, contactId)` key once `buckets.size() >= maxContactBuckets` (default 100_000, line 73). The eviction sweep (`evictIdleBuckets`, line 391; predicate at 403-409) only removes keys idle longer than `max(evictionThreshold=PT10M, refillWindow)` and runs every 5m. There is no eviction of live keys to admit a new one (intentional, comment line 71), so a map saturated with attacker keys is a closed door to every subsequent distinct contact until those attacker keys age out.
    REPRO: On an adapter with no Sybil signal (spec §"Sybil resistance across adapters" acknowledges fresh identities are free), the attacker emits one inbound from each of 100_000 distinct attacker-chosen contact ids, then re-touches each id once per <10 minutes (~167 inbound/sec aggregate, well under transport inbound capacity and each id stays under the 60/min per-key cap). The map stays pinned at the cap with attacker keys; every legitimate brand-new contact's first DM now hits `buckets.size() >= maxContactBuckets` and is silent-dropped at step 1.5 — it never reaches step 2's invite-code check. Legitimate users cannot register for as long as the flood is sustained. The prior code grew memory unbounded; this fix swaps an unbounded-memory DoS for a sustainable registration-availability DoS that the spec's flood-bounding promise did not anticipate.
    SUGGESTED-FIX-CLASS: rate-limit

OUT-OF-MODEL:
  - Per-adapter shared `OutboundRateLimiter` (`OutboundRateLimiter.java`, wired at `SimpleXAdapter.java:394/415/426`, `SignalAdapter.java:317/322/328`) means one user's sustained outbound paces all users' outbound on that adapter via `Thread.sleep` in `acquire()`. The spec (§6.3.6 / design) explicitly designates this as transport self-protection beneath the per-user limiter and concurrency is one-frame-per-connection, so cross-user pacing latency is an accepted design property, not a broken promise. Flagged only so the user can confirm the shared-pacer latency coupling is acceptable.
  - The key-space cap is reset on Provider restart (buckets are in-memory, `RateCapBucket.java:44-49` documents this). An attacker's saturation evaporates on restart; conversely the lock-out in the finding above also clears on restart. Restart cadence is operator infrastructure, out of the documented threat model.

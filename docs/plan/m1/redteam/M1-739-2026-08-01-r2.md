RE-AUDIT VERIFICATION (round-1 finding: AUDIT-EVASION, low — TOCTOU on
the dedup predicate; docs/plan/m1/redteam/M1-739-2026-08-01.md):

The finding is genuinely closed; it is NOT re-reported.

- The dedup check is now
  `SELECT 1 FROM quarantine WHERE post_id = ? AND status = 'PENDING'
  FOR UPDATE` (Stage2VerdictHandler.lockPendingQuarantineRows, diff
  hunk at Stage2VerdictHandler.java:421-430), executed inside the
  verdict transaction BEFORE updatePostQuarantined. A concurrent
  reject_quarantine takes the same row lock (verified against the live
  procedure body, V50__banned_admin_actor_checks.sql:156-159), so the
  finding's interleaving now serializes: the verdict tx blocks on the
  lock, and at READ COMMITTED the unblocked FOR UPDATE re-evaluates
  the predicate against post-reject row versions — the REJECTED row no
  longer matches status='PENDING', the check returns zero rows, and
  the stage2 PENDING row is inserted in the same transaction as the
  post UPDATE. The new serialization IT
  (Stage2FirstPassQuarantineRowIT.rejectCommittingBeforeTheCheckCannotSuppressInsert)
  pins exactly this interleaving with a two-connection lock/await
  harness and final-state assertions.
- Deadlock-order angle: the verdict tx takes quarantine row locks
  first, then the post row lock via updatePostQuarantined.
  approve_quarantine (V53__approve_quarantine_guard_new_post_notify.sql)
  takes the quarantine row FOR UPDATE (lines 46-50) and only then
  UPDATEs post (lines 77-85) — the same order. reject_quarantine locks
  only the quarantine row and never touches post. No lock cycle exists
  between the verdict tx and either procedure.
- Phantom-insert angle: a zero-row FOR UPDATE locks nothing, but no
  writer can conjure a PENDING row mid-first-pass — Stage 1 rows
  commit before Stage 2 runs, and the re-eval job (the only other
  PENDING-insert writer, QuarantineDao.insertStage2Row) cannot
  enumerate a post with stage2_done=false.
- Reverse-order interleaving (verdict tx locks first, reject lands
  after the verdict commit) leaves the post QUARANTINED with rows that
  were genuinely PENDING and queue-visible at verdict-commit time; the
  subsequent reject is then a serialized terminal admin review of a
  hidden post, not the finding's stranded state (an admin
  pre-hide review of a visible post silently becoming a post-hide
  close). The harmful case is the one the lock now orders away.
- approve-race angle: an admin approve committing before the verdict
  check flips the Stage 1 rows to APPROVED, so the check reads zero
  PENDING rows and the insert fires — the re-hidden post re-enters the
  queue with a fresh stage2 PENDING row (approve-after-verdict remains
  the designed admin release path; the round-1 out-of-model note on
  the pre-existing READY-over-in-flight-verdict window stands, see
  OUT-OF-MODEL).

OUT-OF-MODEL:
  - Duplicate-verdict phantom insert (not adversary-steerable, fails
    visible): if the same post is evaluated by Stage 2 twice
    concurrently (e.g. an Invariant-5 re-emission while the first
    judge call is still in flight), both verdict txs can read zero
    PENDING rows — there is nothing to lock, so FOR UPDATE cannot
    serialize them — the second tx blocks only on the post row lock,
    and both insert a stage2 PENDING row. The result is a duplicate
    queue entry, not a hidden post: the queue over-reports rather than
    under-reports, and an admin closing one row leaves the other
    PENDING with the post still listed. No threat-model promise is
    broken; a partial unique index or an idempotency key on
    (post_id, flagged_by, rule_id) would be a hardening ticket if the
    duplicate-eval race is deemed reachable in practice.
  - Pre-existing, carried over from round 1 unchanged: an admin
    approve_quarantine landing while a first-pass verdict is in flight
    sets the post READY and fires new_post; the in-flight non-BENIGN
    verdict then re-hides it. The remediation improves the end state
    (the re-hidden post now always carries a PENDING queue row, so the
    flip is admin-visible) but the transient READY window and its
    NOTIFY are base-code behavior this diff does not own; recorded for
    the previously-suggested base-code ticket.

RED-TEAM VERDICT: CLEAN

No findings. The diff hardens the deployment by reducing the migration-owner
DB role (`infochat`) from `SUPERUSER` to `CREATEROLE` and adds two
`GRANT infochat_collector/infochat_provider TO infochat WITH ADMIN OPTION`
grants so the now-non-superuser owner can still run V4/V31's `ALTER ROLE …
LOGIN/NOLOGIN`. Audited against docs/spec/security.md §DB roles (D34) and the
trust-boundary commitments; every relevant promise is preserved or strengthened.

Audit reasoning (why the changed surface does NOT breach the threat model):

1. §DB roles (lines 1096-1098) promises a SQL-injection bug in the Provider
   "cannot delete posts, mutate price snapshots, alter quarantine entries, read
   unredacted audit rows, or read raw quarantine originals." That promise binds
   the `infochat_provider` service role. The new grants flow owner→service
   (`infochat` becomes a member of the service roles), NOT service→owner. A
   Provider SQLi foothold connecting as `infochat_provider` gains no membership
   in the owner and inherits no owner privilege. Promise intact.
   (docker/postgres-init.sh:29-30 / :86-87)

2. The owner credential (held by the Collector for Flyway, deployment.md §7.7)
   already OWNS every table created by V1..V51, so it already has full DML/DDL on
   the whole `infochat` database. Moving it from SUPERUSER to CREATEROLE is a
   strict reduction: a leaked owner credential can no longer take over the
   cluster, read other databases, gain OS access via COPY … FROM PROGRAM, or
   carry BYPASSRLS. The `WITH ADMIN OPTION` membership adds only the ability to
   SET ROLE to the two service roles (no new data reach — owner already owns
   everything) and to re-grant those memberships; both stay inside this one
   database. Net blast-radius reduction, consistent with D34's least-privilege
   intent. security.md makes no commitment about the owner role's attribute level
   that this diff could violate.

3. Privilege determination verified at source, not from the diff's attestation:
   - grep of all V*.sql migrations shows the ONLY privilege-sensitive operation
     is V1__init.sql:15 `CREATE EXTENSION IF NOT EXISTS vector`. The extension is
     pre-installed by the image's bootstrap superuser before Flyway runs, so the
     IF NOT EXISTS clause makes it a no-op under the CREATEROLE owner. No
     ALTER SYSTEM, no COPY … FROM PROGRAM, no event trigger, no CREATEDB, no
     second CREATE EXTENSION exists in the migration set.
   - V4__nologin.sql:10-12 and V31:22-23 perform `ALTER ROLE infochat_collector
     /infochat_provider LOGIN/NOLOGIN` on roles the bootstrap superuser created;
     on PG16 a non-superuser CREATEROLE role can only ALTER roles it administers,
     so ADMIN OPTION on exactly those two roles is the minimum required. The
     diff grants ADMIN OPTION on precisely those two and nothing else.
   - infochat_admin (V2-created by the owner via Flyway, V4:12 ALTER NOLOGIN) is
     administered by the owner automatically; the diff correctly grants nothing
     extra for it.

4. SECURITY DEFINER functions (approve_quarantine / reject_quarantine, V21/V25
   etc.) are owned by the migration owner and previously ran in a SUPERUSER
   definer context; they now run in a CREATEROLE definer context. They only
   read/write tables the owner owns, which it still does. This is a reduction in
   definer privilege, not a regression. grep confirms the schema uses GRANT/REVOKE
   + SECURITY DEFINER and no ROW LEVEL SECURITY / CREATE POLICY, so there is no
   RLS for the dropped SUPERUSER to have been silently bypassing.

5. No application trust-path code changed: the diff is a docker init shell script
   plus design-doc and STATUS/ticket bookkeeping. No change to identity
   resolution, ban check, authorization steps, LLM tool surface, ingest pipeline,
   audit-log writes, or rate limiting. None of the sensitive-surface inventory
   entries are reachable through behavior introduced by this diff (they are
   doc-line matches in 07-deployment.md, not code changes).

OUT-OF-MODEL:
  - Trust of operator-set config and the image's bootstrap superuser is assumed
    by security.md §Threat model ("Operator-set config … is trusted"). The
    bootstrap-superuser pre-installing the vector/pgcrypto extensions and holding
    the cluster superuser credential for admin psql (deployment.md §7.7) sits
    inside that trusted boundary, so a compromise of the bootstrap superuser
    itself is out of model — not a finding, noted only so the operator knows the
    residual cluster-takeover path now routes exclusively through the bootstrap
    superuser credential rather than the (now CREATEROLE) owner credential.

RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - GGUF model-binary integrity / supply-chain trust. The diff adds an
    *optional* operator-supplied SHA-256 check (blank input skips it) on a
    model binary downloaded from an operator-chosen URL in the interactive
    setup wizard (prod/scripts/4-llm.sh:182, 199-208). The commit comment
    frames this as "closing the tamper window," but the only tamper window
    it addresses (compromised mirror / MITM of the GGUF download despite
    TLS) sits squarely in the categories the threat model declares out of
    scope: docs/spec/security.md lines 27 ("Operator-set config ... is
    trusted") and 29-30 ("Out of scope for v1: ... supply-chain attacks on
    operator infrastructure, TLS/MITM"). The actor supplying both the URL
    and the checksum is the operator — the trusted principal — running the
    script on their own host. There is no spec commitment that model-binary
    integrity is verified, so "the check is optional / can be skipped" is
    not a gap against any promise. Flagged only so the user can decide
    whether v1 should make GGUF integrity a model-tier commitment; today it
    correctly is not.

  - Operator input flowing into docker invocations. $gguf_url, $gguf_file
    (derived via basename of the query/fragment-stripped URL), and
    $gguf_sha256 are read at interactive prompts and passed to docker as
    argv (--entrypoint sha256sum/ls/rm/curl, no shell-string interpolation),
    and the checksum comparison runs in bash, not in a shell command. So
    even an adversarially crafted value cannot achieve command injection
    here. But this is moot under the threat model regardless: the operator
    is the trusted actor (security.md:27), and command-injection-via-own-
    input on a host you already control is not an escalation. No FINDING.

# Red-team audit: M1-020 — 2026-05-26

RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: INFO-LEAK
    SEVERITY: high
    PROMISE: "Exception messages and stack traces emitted via the application
      logger MUST NOT contain user-authored prose (chat-mode message bodies,
      post bodies, saved-post annotations, command arguments). The application
      provides a SafeLog utility that drops the exception message body, retains
      only the exception class name, and truncates the cause chain to class
      names (depth-capped at 5). The original Throwable is never passed to the
      underlying SLF4J logger." (docs/spec/security.md §User content in
      exceptions)
    GAP: The diff introduces SafeLog and applies it to 3 call sites
      (InboundRouter.java:533, InboundRouter.java:613, MessagingStartup.java:62)
      but leaves at least 2 high-risk call sites in the Provider that pass full
      Throwable objects directly to SLF4J: (1) ChatAgent.java:127 —
      log.error("ChatAgent.handle failed for userId={}", userId, e) catches
      exceptions from doHandle() which processes the user's chat message through
      prompt building, LLM calls, and JSON parsing; any of these can embed the
      user's chat-mode message body in the exception text. (2)
      CompressCommandHandler.java:163 — log.warn("Compression LLM call failed
      for userId={}", userId, e) catches exceptions from the LLM generate call
      that received the full conversation text including user-authored
      chat_memory content. The Redactor console filter (Redactor.isLoggable at
      Redactor.java:92-125) processes record.getMessage() and
      record.getParameters() but never touches record.getThrown(), so the
      throwable's message and stack trace (which may contain user prose) are
      rendered to stdout unredacted.
    REPRO: (1) A user sends a chat-mode message containing sensitive content.
      (2) The LLM provider throws an exception whose message includes the user
      prompt (e.g., a JSON parse error, an HTTP client error with the request
      body, or a timeout error that includes the prompt fragment). (3)
      ChatAgent.handle catches the exception at line 127 and passes the full
      throwable to log.error. (4) SLF4J renders the exception message and full
      stack trace to stdout. (5) The Redactor console filter processes the log
      record's message template but NOT the thrown exception, so the user's
      sensitive content appears in the operator log stream.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

  - CATEGORY: INFO-LEAK
    SEVERITY: medium
    PROMISE: "Exception messages and stack traces emitted via the application
      logger MUST NOT contain user-authored prose." (docs/spec/security.md
      §User content in exceptions)
    GAP: MembershipEventHandler.java:124 passes a SQLException directly to
      log.error: log.error("failed to write audit row action={} scope={}",
      action, scopeId, e). JDBC drivers can include bind parameter values in
      SQLException messages, particularly when constraint violations include
      the violating value. The audit_log table's details_json column carries
      structured data derived from user actions.
    REPRO: (1) A user triggers a membership event. (2) The audit_log INSERT
      produces a constraint violation whose exception message includes the bind
      parameter text. (3) MembershipEventHandler catches the SQLException at
      line 124 and passes the full throwable to log.error. (4) User-influenced
      content appears in the operator log stream. Requires a specific DB-side
      constraint violation to trigger, hence medium severity.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

OUT-OF-MODEL:
  - The Redactor console filter (applied as a JUL Filter) does not redact the
    Throwable attached to the log record (record.getThrown()). Even for call
    sites that already use SafeLog (which never passes the Throwable to SLF4J),
    any future regression that re-introduces a direct log.error(..., throwable)
    call would bypass the Redactor filter's API-key catalogue for keys embedded
    in exception messages. The Redactor could be extended to also process
    record.getThrown().getMessage() through the API-key catalogue as a
    defense-in-depth measure.
  - SafeLog's cause-chain walker follows getCause() pointers and is depth-capped
    at 5, which correctly prevents infinite loops from cyclic cause chains.
    Throwable.toString() (which SafeLog deliberately avoids) and some logging
    frameworks can be tricked by cyclic causes into infinite recursion. SafeLog's
    design sidesteps this by using getClass().getName() only.

OUT-OF-MODEL:
  - Non-canonical base64 acceptance / scope-key malleability. The gate's javadoc
    (SignalMessageCodec.java:324) claims the id "strict-Base64 decodes", but
    java.util.Base64.getDecoder() is not strict in two ways: it accepts input
    with missing final-quantum padding, and it does not reject non-zero
    trailing pad bits. Consequently many distinct string spellings of the same
    underlying group bytes pass isAcceptableGroupId
    (SignalMessageCodec.java:339-347), and extractGroupId returns the RAW
    string (SignalGroupHandler.java:317), which becomes the ScopeRef.Group key
    verbatim (SignalGroupHandler.java:148, 180) — no canonicalization
    (decode-then-re-encode) is applied, unlike the sender-ACI path which pairs
    its gate with canonicalizeAci. Unreachable today: signal-cli itself
    base64-encodes the protocol-derived group id, so the spelling is canonical
    and stable, and the loopback signal-cli channel is trusted by the current
    threat model. But under the exact "if that boundary is ever redrawn"
    hypothetical the gate cites as its own motivation, spelling malleability
    would let one physical group fragment into multiple distinct scope keys —
    multiplying per-group reply/command/LLM rate-cap buckets (security.md
    §Rate limiting), groups rows, pending-approval slots, and per-group
    isolation partitions. If the model is ever extended to distrust the
    signal-cli channel, the gate should canonicalize, not just validate.
  - Unthrottled WARN per rejected frame. The shape-gate WARN
    (SignalGroupHandler.java:311-314) fires before sender-identity assertion
    (the isAcceptableAci check at SignalGroupHandler.java:126 runs after
    extractGroupId) and before every Provider-side rate cap (step 1.5 is
    downstream of adapter dispatch), with no coalescing — contrast the
    threat model's coalesced admin-notification discipline (security.md
    §Failure handling). If the gate ever became peer-reachable, each hostile
    frame would yield one WARN line (log-volume amplification / disk
    pressure). Unreachable today for the same reason as above: a hostile
    Signal peer cannot make signal-cli emit invalid or out-of-band base64,
    so the WARN path is operator-diagnostic, not adversary-drivable. Noted
    so a future trust-boundary redraw also revisits log-rate bounding on
    this path (the pre-existing oversize-drop WARN at
    SignalGroupHandler.java:149 shares the shape).

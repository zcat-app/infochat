RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - The entire diff hardens the on-disk encoding of operator-pasted values
    written to secrets.env by the first-run setup wizard (prod/scripts/2-secrets.sh,
    4-llm.sh, 6-adapter.sh). The values escaped are: INFOCHAT_LLM_API_KEY (read
    via `read -rsp` from the operator console) and the per-adapter bootstrap-admin
    contact id (read via `read -rp` in collect_admin). All inputs originate from
    interactive operator prompts. docs/spec/security.md §Threat model states
    "Operator-set config (properties files, bootstrap JSON) is trusted" and lists
    only messaging-app users, feed publishers, and LLMs as in-model adversaries.
    No in-model adversary can influence secrets.env content, so a corrupted/
    interpolated value is an operator-accident-resistance concern, not an
    attacker-reachable surface. The ticket itself documents this classification.
    Flagged only so the user can confirm the trust boundary is as stated.

  - The bootstrap-admin contact id escaped here ultimately resolves into
    infochat.adapters.<name>.bootstrap-admin-contact-id and mints an is_admin=true
    row (CLAUDE.md §Bootstrap admin). A wrong escape could in principle resolve a
    DIFFERENT contact id and grant admin to an unintended contact. Reviewed the
    escape (dotenv_escape: backslash first, then '"', then '$') against
    double-quoted dotenv semantics — the ordering is correct, '#' correctly needs
    no escaping inside double quotes, and the value round-trips byte-for-byte.
    Even if it were wrong, the trigger is an operator mistyping their own admin id
    into their own console — still inside the trusted operator-config boundary, not
    an in-model adversary. Noted for completeness, not a finding.

  - prod/scripts/6-adapter.sh:230-231 writes INFOCHAT_SIMPLEX_DATA_DIR /
    INFOCHAT_SIGNAL_DATA_DIR from operator-typed paths WITHOUT dotenv_escape,
    an inconsistency with the three writes this ticket hardens. Same trust
    boundary (operator-typed, trusted) and explicitly out of this ticket's
    files-scope/acceptance, so out-of-model and out-of-scope; flagged only so the
    user can decide whether a follow-up ticket should unify the encoding.

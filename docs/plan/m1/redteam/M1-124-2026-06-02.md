RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - Pre-existing (NOT introduced by this diff) logging path at
    infochat-llm-adapter/src/main/java/app/zcat/infochat/llm/impl/AnthropicProvider.java:159-160:
    `LOG.warnf("AnthropicProvider: non-2xx %d from %s; error: %s", ..., errorMsg)`
    logs `errorMsg` — text derived from an untrusted remote-LLM error
    response body (per the threat model, "LLMs (local or remote) are black
    boxes that can be coaxed into emitting attacker-chosen output") —
    directly through the JBoss `Logger` rather than through the spec-mandated
    closed API-key catalogue console redactor / `SafeLog` utility
    (§Secrets handling: "Stdout console logs pass through the closed API-key
    catalogue redactor"; "Exception messages and stack traces emitted via the
    application logger MUST NOT contain user-authored prose"). A hostile or
    misconfigured upstream that echoes a secret-shaped string into
    `error.message` could surface it in stdout unredacted. This diff does not
    touch that line and does not regress it (the new `preview()` wrap actually
    caps the logged length at 200 bytes), so it is not a finding against this
    diff — flagged only so the user can decide whether the redactor coverage
    of this provider's warn-log path is tracked by a separate ticket.

Summary of the audited diff:
1. Anthropic auth header names corrected to the real API names
   (anthropic-version, x-api-key) — no user/attacker-controlled header
   values, no header-injection surface (values are a compile-time constant
   and trusted config).
2. Removal of an unused import.
3. extractErrorMessage now wraps its output in preview(...), length-bounding
   the diagnostic to 200 bytes — a net reduction in any leak/log surface.
4. Catch narrowed from Exception to IOException around JSON.readTree, which
   is the only throwing call in that block (JsonNode.path(...).asText(...)
   does not throw), so no exception path is silently swallowed or newly
   leaked.

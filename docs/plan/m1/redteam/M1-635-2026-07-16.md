RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - Saturation oracle: the submit-time acknowledgement placeholder appears
    if and only if the interruptible pool is saturated at submit
    (InboundRouter.java:854-856, InterruptibleDispatcher.wouldQueue), so any
    registered user gains a deterministic, low-noise signal that
    >= max-concurrency LLM turns from OTHER users/scopes are in flight
    system-wide — a cross-user aggregate-activity inference channel. The
    threat model promises per-(user, scope) isolation of state/memory/saves,
    not concealment of aggregate load (it explicitly accepts the weaker
    translation-cache timing side-channel as a v1 trade-off), and the same
    signal already leaked pre-diff via queueing latency; the ack merely makes
    it explicit and cheap to probe. Flagging so the user can decide whether
    aggregate-load observability belongs in the model.
  - Error-class strand window: publishQueuedPlaceholder deliberately
    registers NO request-end cleanup (StageProgressNotifier.java:201-246),
    and every worker-side safety net catches RuntimeException only
    (InterruptibleDispatcher.runStage:214, InboundRouter.dispatchSlashOrChat:1030,
    dispatchChatSelfDelivering:1092). A non-RuntimeException Throwable
    (StackOverflowError/OOM) thrown in the worker's window between
    setOperationId (InboundRouter.java:915) and the first notifier publish
    (which is what registers the M1-334 drain, StageProgressNotifier.java:149)
    leaves the acknowledgement placeholder stranded forever: "working on it"
    never finalized, typing indicator stuck ON for that scope, and the
    states-map entry leaked. Pre-diff, the M1-334 request-end drain covered
    the equivalent window because no placeholder existed before first publish.
    Not adversary-triggerable on demand (requires an Error, not an exception,
    in a few in-memory checks), so it maps to no threat-model commitment —
    recorded as a hardening observation only.
  - /stop cannot reach a queued-but-not-started turn: the InFlightTracker
    slot is acquired on the worker inside ChatAgent.dispatch
    (ChatAgent.java:225-226), so a turn sitting in the pool queue holds no
    slot and CancellationService finds nothing to cancel — the user who just
    received the new "working on it" acknowledgement gets an idempotent
    no-op from /stop while their queued turn still runs the full LLM call
    later. Cost is bounded by the sender's own LLM bucket and the queue
    semantics predate this diff (M1-634); the ack only makes the
    contradiction user-visible. D35 "immediately" scope over queued turns is
    a design question for the user, not an in-model gap of this diff.

OUT-OF-MODEL:
  - restore.sh custom-GGUF recovery fetches an arbitrary URL read from the
    RESTORED secrets.env with an OPTIONALLY-EMPTY SHA (prod/scripts/restore.sh
    :163-167 "elif [[ -n \"$persisted_url\" ]]; then ... fetch_gguf
    \"$persisted_url\" \"$file\" \"$persisted_sha\""; the comment at :164-165
    states "an empty SHA keeps the operator-trusted TLS fetch"). Written by
    4-llm.sh at prod/scripts/4-llm.sh:393-394 from an interactive operator
    prompt where the SHA may be blank (4-llm.sh:338 "blank to skip integrity
    check"). If an adversary could tamper with the pack.sh backup bundle, they
    could repoint INFOCHAT_LLAMACPP_GGUF_URL at an attacker-hosted file and set
    INFOCHAT_LLAMACPP_GGUF_SHA empty, causing restore.sh to download an
    unverified arbitrary file into the infochat-llamacpp-models volume that
    llama-server then loads — with no integrity check and no SSRF allowlist on
    the fetch (unlike the running Collector/Provider outbound path, §SSRF).
    This is OUT-OF-MODEL, not a FINDING, because:
      (a) The URL/SHA source is operator-set config (interactive setup prompt)
          and, on restore, the pack.sh backup bundle — both TRUSTED per
          §Threat model ("Operator-set config ... is trusted").
      (b) Tampering with the backup bundle is a supply-chain attack on operator
          infrastructure, and substituting the fetched bytes over the wire is
          TLS/MITM — both explicitly "Out of scope for v1" (§Threat model).
      (c) The §SSRF allowlist commitment binds "Every outbound connection from
          the Collector ... and from the Provider," not the operator-run
          setup/restore shell scripts, so skipping it here is not a spec gap.
      (d) The pinned-default recovery path is unaffected — it still uses the
          hardcoded, enforced SHA constant (restore.sh:158-159), ignoring the
          persisted values; only an operator-chosen custom override with a
          deliberately-skipped SHA fetches without verification.
    Flagged so the user can decide whether v1's threat model should be widened
    to defend the restore path against a tampered backup bundle (e.g. enforce a
    mandatory SHA on custom-GGUF recovery, or bundle-sign secrets.env), even
    though nothing here is adversary-reachable under the model as written.

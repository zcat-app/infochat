RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - The asset-command freshness guarantee now rests entirely on the Provider reading `price_snapshot` on every invocation and comparing `captured_at` against `2 * refresh_interval` (`AssetSnapshotReader.java:108-110`). With the NOTIFY-based cache-invalidation seam gone there is no longer any in-process cache to go stale, so the previously-documented "flush cache on Postgres reconnect" correctness mechanism is moot. A clock-skew or NTP-manipulation attack against the staleness comparison (serving a stale price as fresh, or a fresh price as stale) is a real concern for a price oracle, but it falls outside the documented threat model (the model treats the DB as internal/trusted and does not commit to monotonic-clock guarantees for the freshness window). Flagging only so the user can decide whether price-oracle freshness deserves an explicit threat-model entry; it is not a gap introduced by this diff.

## Audit notes (skill-recorded)

Falsifier check (from the threat-actor): `AssetSnapshotReader` does NOT consume the
NOTIFY channel — it performs a direct indexed table read (the `(asset, sub_verb,
captured_at DESC)` lookup the diff describes) and computes staleness from
`captured_at`. The old `PriceSnapshotStore` comment claiming the reader "deserialises
by key source" from the NOTIFY payload was stale/inaccurate; the actual reader never
touched a notification path. So removing the emitter leaves no orphaned consumer and
breaks no freshness guarantee.

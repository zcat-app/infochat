    PROMISE: docs/spec/security.md §LLM output sanitizer, "Markdown
             flattening survives canonicalization" (a paragraph this diff
             ADDS): "Flattening runs before the replacement, so the
             redaction marker's own brackets are never consumed as link
             text; and because no flatten runs *after* the replacement,
             the marker is kept from landing directly against a following
             `(` ... **The delivered result of a match therefore never
             contains `](`, by either route.**" Backed by the same
             section's opening commitment that LLM-authored text is
             "passed through a deterministic outbound regex pass" before
             delivery, and by the plain-text/bare-URL surface convention
             (`commands.md` §Surface conventions).
    GAP: The absolute "never contains `](`" commitment is not delivered.
         The two SANITIZER-MANUFACTURED routes the paragraph enumerates
         are genuinely closed — I verified both:
           * marker-consumed-as-link-text is closed by flattening before
             the replacement (LlmOutputSanitizer.java:289 runs the flatten
             on the canonical form, :291-308 replaces afterwards);
           * marker-landing-against-`(` is closed by
             separateMarkerFromFollowingParen (LlmOutputSanitizer.java:312,
             :329-332).
         But the delivered text of a match is now the canonical/flattened
         string (LlmOutputSanitizer.java:312), and the flatten that
         produces it is MARKDOWN_LINK at LlmOutputSanitizer.java:203 —
         `\[([^\]]+)\]\(([^)]+)\)`. The link-text group `[^\]]+` cannot
         span a nested or backslash-escaped `]`, so a CommonMark-valid
         inline link with balanced nested brackets in its label is invisible
         to BOTH flatten invocations (raw at :222 and canonical at :289)
         and is delivered verbatim alongside the redaction. The delivered
         result of a match then contains `](` and, unlike the harmless
         residues, that `](` is part of a label-hiding link a CommonMark
         renderer resolves. This is a pre-existing MARKDOWN_LINK
         limitation, but the diff is what raises "no `](` on the match
         path" to a spec-level commitment, and the new test only pins the
         two enumerated routes (LlmOutputSanitizerTest.java:1067-1110).
    REPRO: 1. Attacker-influenced model context (the threat model concedes
              this: §Prompt-injection defenses, `semanticSearch` row — the
              D28 pre-fetch re-injects feed-derived titles/URLs every turn)
              steers a chat reply / `/summary` prose / digest into emitting:
                 `Run /ban spammer. [Read [the] report](https://evil.example/phish)`
           2. sanitize() raw flatten (LlmOutputSanitizer.java:222): the
              regex tries `[` at "Read", group1 stops at the inner `]`, the
              following `\(` sees a space → no match. Nothing flattens.
           3. canonicalizeForMatching + second flatten (:289): input is
              pure ASCII, so canonicalization is identity and the same
              regex fails identically.
           4. `/ban` matches, one audit row is written, and the delivered
              text is
                 `Run [redacted command] spammer. [Read [the] report](https://evil.example/phish)`
              — a match whose delivered result contains `](`, contradicting
              the paragraph the diff added, and carrying exactly the
              label-hiding markdown link the flatten pass exists to remove.
           5. The system shouldn't have allowed it: the whole point of
              running the flatten twice is that a *matched* output is
              guaranteed link-free. Impact is bounded today only because
              both v1 production adapters assert
              `supportsMarkdownLinks=false` — the spec pins the flattening
              invariant, not the adapter capability flag.

OUT-OF-MODEL:
  - Bidi-reversed VISUAL spoofing plus human retyping. An LLM can emit
    U+202E followed by `nimda-tnarg/`; canonicalizeForMatching
    (LlmOutputSanitizer.java:356-359) strips the RLO and matches against
    `nimda-tnarg/`, which is in no closed-list entry, so the line ships
    unredacted — yet a client renders it as the literal string
    `/grant-admin`, and an admin who RETYPES what they see (rather than
    pasting) dispatches the real command. Parity with the parser is
    intact (the pasted codepoints do not dispatch either), and the spec's
    commitment is explicitly scoped to "the same representation the
    deterministic command parser consumes", so a rendering-layer spoof is
    outside the documented model. Behaviour is identical pre- and
    post-diff. Flagged so the user can decide whether "text that RENDERS
    as a privileged command" belongs in the sanitizer's mandate.
  - Unicode separators that survive NFKC and are outside Java's ASCII
    `\s`: U+1680 OGHAM SPACE MARK, U+180E, U+0085, U+2028/U+2029. I
    re-derived this rather than assuming it: the multi-word patterns'
    `\s+` misses them, but so do the parser's own
    `normalized.split("\\s+", 2)` (InboundRouter.java:1411) and
    `rawText.trim().split("\\s+", 3)` (InviteCommandHandler.java:231), so
    no dispatchable form is missed — `/invite<U+1680>create` yields
    commandName `invite create`, which matches no handler. (The
    separators that DO fold — U+00A0, U+2000..U+200A, U+205F, U+3000 —
    are covered by NFKC and are matched correctly.) This becomes
    reachable only if a messaging client rewrites such a codepoint to a
    real space or newline on copy/paste, which is client behaviour
    outside the documented model.

RED-TEAM VERDICT: CLEAN

No finding: the diff delivers on the threat-model commitments it touches, and
introduces no gap against them. Audit reasoning summarized below.

Scope of the diff: restore.sh (prod/scripts/restore.sh) reconstructs the
Flyway-created NOLOGIN principal `infochat_admin` after Postgres is up but
before `pg_restore`, plus a wiring test pinning that ordering and doc/status/
ticket bookkeeping. The only executable change is the added DO-block that
runs `CREATE ROLE infochat_admin NOLOGIN;` under an `IF NOT EXISTS` guard.

Commitments checked against the diff (docs/spec/security.md):

- §DB roles (least-privilege split; "a SQL-injection bug in the Provider
  cannot ... read unredacted audit rows, or read raw quarantine originals").
  The reconstruction is byte-identical in form to the canonical definition in
  V2__roles.sql:53-57 (`CREATE ROLE infochat_admin NOLOGIN;`, same NOT-EXISTS
  pg_roles guard), so the role attributes match the source (plain NOLOGIN,
  default INHERIT, no password, non-superuser). The admin role's granted
  surface is then reproduced by `pg_restore` applying the dump's object-level
  ACLs verbatim — exactly the source grants, no more. No new privilege is
  conferred on `infochat_collector` / `infochat_provider` (the roles the
  services actually connect as); the DO-block runs as `infochat`
  (postgres-init.sh:31, CREATEROLE non-superuser), which is already the DB
  owner, so no escalation is introduced. The diff FIXES a real defect (the
  co-located service-role grants rolling back when the GRANT-to-missing-role
  entry fails) — it strengthens, not weakens, the least-privilege
  reconstruction.

- Audit-log integrity (append-only, write-only app role). Unaffected: the
  reconstruction creates a Postgres role during operator disaster recovery;
  it is not an application operation and lies outside the audit_log's
  committed intent-logging scope. The `audit_log_view` / quarantine-function
  strings flagged by the sensitive-surface grep are prose inside the added
  comment explaining which grants roll back, not code touching those tables.

- INJECTION surface. The DO-block SQL is a static single-quoted heredoc with
  no interpolation of bundle or network input; `PGPASSWORD` stays inside the
  container (same pattern as the pre-existing pg_restore/schema-check execs,
  restore.sh:355-357,366-367) and never reaches a host command line or log.
  No SQL/command-injection vector.

- Failure-mode direction. A failed ACL application under this restore is
  fail-CLOSED for privilege: a rolled-back GRANT leaves an object at its
  default ACL (owner-only), i.e. under-permissive (availability), never
  over-permissive. In the primary case the diff addresses, the Collector
  then dies on its first heartbeat write and `compose up --wait` times out —
  a loud non-zero exit, not a silent broken clone.

- Trust boundary. restore.sh is operator-run recovery tooling; the target
  is gated FRESH (no infochat-pgdata volume, no pre-existing secrets.env).
  Operator, operator config, and operator infrastructure are trusted
  (§Threat model). The reconstruction SQL is not attacker-reachable.

OUT-OF-MODEL:
  - Tampered restore bundle: a hand-edited/malicious bundle is a supply-chain
    attack on operator infrastructure, explicitly out of the v1 threat model
    (§Threat model: "supply-chain attacks on operator infrastructure" out of
    scope), and restore.sh's own identity-extraction allowlist already notes
    this. The added role SQL is a fixed heredoc and is not influenced by the
    bundle regardless.
  - Silent ACL-error tolerance (informational, not a finding): the
    pre-existing pg_restore step runs without --exit-on-error and its
    post-check verifies only table presence (`\dt`), not ACL correctness
    (restore.sh:354-372). The added comment warns "v1 has exactly one
    Flyway-created principal — add any future ones to this DO block"; if a
    future second Flyway-created role were added to V2 but not here, a clone
    could restore with silently rolled-back grants for objects the Collector
    does not touch on boot. This is a latent maintenance/robustness concern
    inherited by (not introduced by) this diff, and its failure direction is
    under-permissive (availability), not privilege escalation — so it is
    not a threat-model violation. Flagged so the user can decide whether a
    grant-verification step in restore.sh is worth a future ticket.

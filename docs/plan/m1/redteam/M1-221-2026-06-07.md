# Red-team verdicts — M1-221, 2026-06-07 (two audits)

## Audit 1 — in-progress, working tree (base main/fe32971, head uncommitted working tree)

Verbatim threat-actor output:

```
RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: INFO-LEAK
    SEVERITY: medium
    PROMISE: "Exception messages and stack traces emitted via the application logger MUST NOT contain user-authored prose (chat-mode message bodies, post bodies, saved-post annotations, command arguments). The application provides a `SafeLog` utility that drops the exception message body, retains only the exception class name, and truncates the cause chain to class names (depth-capped at 5). The original `Throwable` is never passed to the underlying SLF4J logger." (§Secrets handling — User content in exceptions)
    GAP: The reworked catch block in `infochat-collector/src/main/java/app/zcat/infochat/collector/eval/stage2/Stage2Worker.java:223-226` (the hunk this diff rewrote to return `new Attempt(null, true)`) still passes the raw provider `RuntimeException` directly to the logger: `LOG.warnf(e, "Stage 2 LLM call attempt %d failed ...")`. The exception originates from `provider.generate(...)` whose request payload embeds the **original, pre-redaction post body** (`Stage2Worker.java:215-221` weaves `originalBody` into the prompt; per §Quarantine workflow that pre-redaction content is so sensitive the Provider DB role is denied `SELECT` on it). HTTP-client exceptions routinely echo request/response fragments and target URLs (which for some providers carry the API key as a query parameter), so a 4xx/5xx burst — exactly the condition this M1-221 backoff change is built around and now exercises on every infra-shaped failure — emits the unredacted `Throwable` message and full stack into stdout logs, bypassing the `SafeLog` mechanism the spec commits to. `SafeLog` exists (`infochat-core/src/main/java/app/zcat/infochat/core/log/SafeLog.java`) and is used by the Nostr stream and Provider paths, but not by this worker's failure arm that the diff modified.
    REPRO: (1) Adversary publishes a feed post containing Stage-1-triggering content (e.g. a prompt-injection regex hit) plus a payload they want exfiltrated to operator logs. (2) Stage 2 fires with the original pre-redaction body in the prompt. (3) The LLM endpoint returns 429/503 (attacker can help induce this by flooding the feed with flagged posts, the same rate-limit scenario this ticket targets) or any client-side error whose exception message includes the request/response context. (4) `LOG.warnf(e, ...)` writes the raw exception — potentially carrying pre-redaction post content and provider-call context — to the console log at WARN, the production baseline level, so no operator misconfiguration is required. The spec promises this class of leak is structurally impossible via `SafeLog`.
    SUGGESTED-FIX-CLASS: input-sanitization

OUT-OF-MODEL:
  - `RetryBackoff.sleepBeforeRetry()` (`infochat-collector/src/main/java/app/zcat/infochat/collector/eval/RetryBackoff.java:342-352` in the new file) only validates `backoffMs >= 0`; a pathologically large operator value (> ~2/3 `Long.MAX_VALUE`) overflows `backoffMs + jitterMs` into a negative argument, making `Thread.sleep` throw `IllegalArgumentException` that propagates uncaught out of `invokeWithRetryOnce`, skipping the verdict handler entirely. Operator-set config is trusted per the threat model, so this is advisory only — but an upper-bound sanity check would close it cheaply.
  - The Stage 2 backoff sleeps while holding the concurrency-semaphore permit (`Stage2Worker.java:188-194`, documented as intentional back-pressure). On the `pi` profile (`max-concurrency=1`) a sustained remote-LLM rate-limit window — which an adversary feeding high volumes of Stage-1-flagged content can help induce — serializes the entire Stage 2 path (including the re-eval job's `judgeBody`, which shares the semaphore) at roughly one post per `2×timeout + backoff`. The spec promises only "outage degrades quality, not safety," which is preserved (INFRA_FAILURE still releases with redactions retained), so this is throughput degradation inside the documented degraded mode, not a broken commitment. Flagged in case the user wants a spec-level throughput/queue-depth commitment for the eval pipeline.
```

    REPRO: Adversary publishes a feed post whose body contains a planted secret-looking string plus malformed HTML (Stage 1 path) or content that triggers an embedding-provider error echoing the request (e.g. an oversized body provoking a 4xx whose client exception includes the request payload). The threat model makes no Stage-2-throughput commitment and states "a complete LLM outage degrades quality, not safety"; the durable outbox means no post is lost and the fail paths are unchanged, so this is design-intended degradation, not a finding. Flagged only so the operator-tunable upper end (the properties comment suggests 10000 ms) is sized with the per-source UNKNOWN auto-disable and NEEDS_REVIEW depth alert in mind.

Audit basis: the diff plus full reads of `infochat-core/src/main/java/app/zcat/infochat/core/log/SafeLog.java` (confirmed it drops Throwable bodies and redacts the caller message — the three in-diff conversions are correct), and the eval-package grep that surfaced the remaining raw-Throwable sites listed above. The backoff mechanics themselves are sound: retry count stays at exactly one on every arm, interrupt restores the flag without swallowing the spec-mandated retry, negative config fails startup, and the new SLF4J parameterized log lines carry only UUIDs/counters/enum names — no user-authored prose.

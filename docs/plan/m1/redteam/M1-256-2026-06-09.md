## Audit notes (verbatim adversary reasoning)

The diff's actual effect is a security improvement — it closes a silent-corruption
gap (a non-numeric coordinate coercing to 0.0). The threat model treats LLM output
as untrusted; this guard tightens the LLM↔system boundary.

Gaps considered:

1. INFO-LEAK via exception preview: the exception message includes a preview of the
   LLM response body. The §"User content in exceptions" rule bars user-authored
   prose (chat bodies, post bodies, saved annotations, command arguments) — not
   LLM embedding-API responses. The embedding response is a vector of floats, not
   user prose, and the input texts (post bodies) are NOT echoed in the response. So
   no user prose leaks. Recorded as OUT-OF-MODEL above (pre-existing pattern).

2. The EmbeddingCallFailedException becomes a batch failure → embedding-failure
   path. Per §Failure handling, "Embedding failure → release without a vector; the
   post is otherwise normal and fully visible." So a malicious/buggy LLM returning
   non-numeric coordinates now causes embedding failure rather than a corrupt
   vector. Consistent with the spec — degraded, not unsafe.

The diff is a single, well-scoped validation tightening at a documented system
boundary, matching the pre-existing sibling guards exactly. No promise in the
threat model is broken.

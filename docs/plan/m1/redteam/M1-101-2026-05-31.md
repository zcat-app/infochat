## Structured verdict (verbatim)

```
RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - The spec wording "any peer-IP change observed at the socket layer is a
    hard close" cannot be implemented literally on the JDK because
    `java.net.http.WebSocket` exposes no peer-IP accessor. The diff
    implements a periodic DNS-re-resolve approximation (default 60s) at
    `NostrRelayConnection.java:178-197` and acknowledges the trade-off in
    the class javadoc. A DNS-rebind that flips back to the originally-
    pinned address before the next watcher tick — or that completes inside
    a single 60s window before the attacker's payload arrives — would not
    be detected. This is a fundamental JDK API limitation rather than a
    missed spec commitment; the spec already delegates the peer-IP-change
    mechanism to design notes. Flagging in case the threat model wants to
    either tighten the watcher cadence in design notes or add a socket-
    level interceptor (e.g., a custom `SSLSocketFactory`) to expose the
    live peer address.
  - The orphan-dial window in `NostrRelayConnection.connectAndSubscribe`
    at lines 255-265: if `buildAsync().get(11s)` throws TimeoutException
    because the TLS handshake hangs past TCP-connect-timeout (10s),
    `dial.close()` releases the pin and lock, but the underlying
    `CompletableFuture` returned by `buildAsync` is not cancelled. A
    late-completing dial would post-pin perform any further name
    resolution under an unpinned resolver (the JDK builtin), and the
    resulting connection would carry events into `RelayListener` while
    `currentWebSocket` is null (so `stop()` cannot abort it). In practice
    the TCP target was already pinned during DNS resolution within the
    11s window, so the established peer is a validated IP and there is
    no concrete SSRF escape; flagging as a defense-in-depth observation
    rather than a finding.
```

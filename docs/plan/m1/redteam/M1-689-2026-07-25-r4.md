    PROMISE: docs/spec/security.md §Prompt-injection defenses, the `searchPosts`

             byte-for-byte; CI fails on a mismatch in either direction."

    GAP: The emphasised clause "It cannot outrank later fetches" is false
         against the shipped sort key. The key is
         `COALESCE(published_at, fetched_at) DESC` —
         infochat-provider/src/main/java/app/zcat/infochat/provider/chat/tool/SearchPostsTool.java:165,
         infochat-provider/src/main/java/app/zcat/infochat/provider/summary/EligiblePostQuery.java:277,
         infochat-provider/src/main/java/app/zcat/infochat/provider/digest/DigestPostCollector.java:151
         and :173. A DATED row's key is its `published_at`, which the ingest
         clamp bounds from ABOVE only
         (infochat-collector/src/main/java/app/zcat/infochat/collector/outbox/PostPersister.java:193-194,
         `publishedAt.isAfter(fetchedAt) ? fetchedAt : publishedAt`) — nothing
         bounds it from below, so a dated row from a LATER fetch routinely
         keys arbitrarily EARLIER than an undated row from an EARLIER fetch.
         The undated row therefore does outrank that later fetch. Only the
         preceding clause ("level with the ceiling a dated post from that same
         fetch could claim — and no higher") is accurate, and it is the clause
         the defense actually rests on.
         Scope, stated honestly: NO attacker capability follows. Because the
         clamp pins a future-dated claim to exactly `fetched_at`, a dated post
         from the same fetch can already claim the identical key, so omitting
         the date buys a position a dated post could always take. The delivered
         ordering is safe; the security-tier sentence describing it is not
         true. The three sibling statements of the same bound are all correct
         and do NOT carry the false clause — docs/spec/schema.md ("an undated
         row sorts at the top of its own fetch batch and no higher"),
         docs/spec/commands.md §Content ("That places it at the top of the
         batch it arrived in — no higher"), and the inline comment at
         EligiblePostQuery.java:273-275 — so the divergence is confined to the
         one spec-CLOSED row.
         Why nothing catches it: the structural guard gap named by the round-1
         medium is UNCHANGED by the remediation. The remediation corrected the
         row's content; it did not touch
         infochat-provider/src/test/java/app/zcat/infochat/provider/chat/ChatToolAllowlistSpecParityTest.java,
         which still parses only the Name column, so the spec's own "CI fails
         on a mismatch in either direction" claim still does not cover the
         Notes column, and the build is green with the row carrying a false
         bound. The round-1 medium is therefore substantially — not fully —
         closed.

    REPRO:
      1. Attacker controls any feed inside a scope's D59 world (`/add-source`
         is open to any non-banned user per commands.md §Source management).
      2. On Monday's fetch tick (fetched_at = Mon 12:00) they publish one item
         with `<pubDate>` omitted. RssFeedParser yields null, PostPersister
         binds SQL NULL. Its sort key is COALESCE(NULL, Mon 12:00) = Mon 12:00.
      3. On Tuesday's tick (fetched_at = Tue 12:00) an honest bootstrap feed
         delivers a genuine backfill item dated the previous Friday. Its sort
         key is Fri, i.e. BELOW the attacker's.
      4. Both are inside a `searchPosts window: PT48H` (both `ready_at` are
         recent). The attacker's undated Monday item sorts ABOVE the honest
         Tuesday-fetched item in the JSON re-injected into the chat prompt,
         and identically in `/summary` and the periodic digest.
      5. Why this matters: an auditor reading the closed allowlist row — the
         document security.md itself calls "the source of truth for the *trust
         path*" — concludes a fresher fetch always displaces an undated post.
         It does not. The next change reasoning from that sentence (for
         example, one that removes the `fetched_at` fallback on the grounds
         that "later fetches dominate anyway") would reintroduce the round-1
         high while appearing spec-conformant, and no gate would report it.

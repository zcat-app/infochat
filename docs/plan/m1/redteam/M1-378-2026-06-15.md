RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - SQL-literal interpolation of operator-supplied passwords into the
    CREATE ROLE ... PASSWORD '...' here-doc in docker/postgres-init.sh
    (lines 68-70). A password value containing a single quote would
    break out of the SQL string literal (e.g. INFOCHAT_DB_PASSWORD set
    to "x'; DROP DATABASE infochat; --"). This is NOT a finding: the
    threat model explicitly classifies operator-set config as trusted
    ("Operator-set config (properties files, bootstrap JSON) is
    trusted", security.md §Threat model) and the only writer of these
    env vars is the operator / the wizard's openssl-rand'd secrets.env.
    No adversary in the documented model can set these variables. Noted
    so the user can decide whether to harden the init script with psql
    \getenv / single-quote-safe quoting as defense-in-depth, but it is
    outside the v1 threat model.
  - The pre-existing bootstrap-superuser dev default
    POSTGRES_PASSWORD:-infochat-dev (docker-compose.yml line 24) is a
    known baked credential, but (a) it is pre-existing and unchanged by
    this diff — only the surrounding comment moved — and (b) the
    Postgres port is bound to 127.0.0.1 only, placing this role behind
    the threat model's "DB is internal — only the two services and the
    operator reach it" boundary (security.md §Threat model). The
    §Secrets handling "no 'changeme' baked anywhere" promise concerns
    the service-role credentials, which this diff converts to
    fail-loud empty pass-throughs (strengthening, not weakening, the
    promise). Reaching the loopback-bound superuser requires host-level
    access, which is out of model.

NOTES (not findings):
  - Diff is deployment plumbing only: a Postgres /docker-entrypoint-initdb.d
    init script (docker/postgres-init.sh), its docker-compose.yml wiring,
    a matching design-note correction (07-deployment.md), and STATUS/ticket
    bookkeeping. The mechanically-extracted sensitive-surface inventory
    reports "none touched" across authentication, authorization,
    input-validation, ban-handling, and audit-log writes; this matches the
    diff content. No runtime security code path (auth gate, ban check,
    per-(user,scope) isolation, LLM tool surface, SSRF allowlist, audit
    writer) is reached by any line in the diff.
  - The least-privilege DB-role split the threat model promises
    (security.md §DB roles, D34) is delivered by Flyway migrations
    V2/V4/V31, which this diff does not touch. The init script only mints
    the three roles WITH passwords (CREATE ROLE ... LOGIN PASSWORD ...);
    the GRANT/NOLOGIN/column-scoping that constitutes the privilege split
    is layered later by Flyway as documented in the script header comment.
    The diff neither adds grants nor widens any role's surface, so the
    "SQL-injection in the Provider cannot delete posts / read unredacted
    audit rows" commitment is unaffected.
  - .gitignore acceptance item (operator secrets file not committable) is
    already satisfied by pre-existing entries .env, .env.*, and secrets.*
    (the wizard writes secrets.env). No .gitignore change appears in the
    diff and none is needed.
  - The init script uses set -euo pipefail and ${VAR:?} fail-loud
    expansion, exiting the container non-zero on an unset OR empty
    service-role password rather than minting a passwordless/known-password
    role. This is an availability-safe fail-closed posture, consistent with
    the spec's general fail-closed bias. No set -x, so passwords are not
    echoed to container logs.

RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - Sibling-file sweep on directory targets (operator footgun, no adversary reach).
    prod/scripts/shred-bundle.sh:489-509 marks a directory ELIGIBLE if ANY
    single `*.tgz` / `*.pgc` / `raw-config/` sits at its top level, then
    prod/scripts/shred-bundle.sh:544-545 recursively shreds EVERY file in the
    tree — including unrelated siblings (e.g. an operator's ~/Downloads with
    one bundle plus personal files). The script's own comment ("must not sweep
    sibling files it was not pointed at") is only partially delivered: the
    shape gate limits WHICH directories qualify, not WHAT inside them is
    destroyed. Mitigated by the pre-destruction inventory (file count + size)
    and consent prompt. The invoker is the trusted operator and the script is
    unreachable from any adapter, command, or LLM path, so this is operator
    misconfiguration — the same class security.md explicitly rules out of the
    adversary model (phantom-admin precedent) — not a FINDING.
  - TOCTOU between guard and destruction (requires a local attacker on the
    operator host, which the model excludes). The dangerous-path refusals run
    on `realpath` output at prod/scripts/shred-bundle.sh:463-476, but the
    shred/rm at :541-546 re-dereferences `$TARGET_ABS`; a co-resident local
    attacker could swap the target for a symlink/new tree between consent and
    destruction, or drop files into the directory between the `find -exec
    shred` pass and the `rm -rf` (those late arrivals are removed unshredded).
    security.md's threat model has no local-multiuser-host adversary
    (operator infrastructure is trusted/out of scope), so OUT-OF-MODEL; flag
    in case the user wants the model extended to shared operator hosts.
  - Guard list is exact-match and enumerative, not containment-based.
    prod/scripts/shred-bundle.sh:465-476 refuses only `/`, the exact
    `$HOME`, and the exact repo root. Parents of those (e.g. `/home`), other
    users' homes, `/etc`, `/var/backups`, or any system directory that happens
    to contain a stray `*.tgz` at top level pass the guard and are shredded
    recursively on operator consent. Additionally the HOME guard is skipped
    entirely when `HOME` is unset (:469), and the repo-root guard anchors to
    the script's own location (:423-424), so a copy of the script installed
    outside the repo (e.g. /usr/local/bin) silently protects the wrong
    directory. All variants require the trusted operator to point the tool at
    the wrong place — operator error, not an in-model adversary path.
  - Hardlinked bundle destroys shared content. `shred -uz` on a `*.tgz` that
    is one of several hardlinks overwrites the shared inode, destroying the
    other links' content while their directory entries persist (and
    conversely, shredding one link is NOT sufficient disposal if the operator
    hardlinked a safety copy — the copy's name survives pointing at zeroed
    data, which may give a false sense that a copy still exists). The
    best-effort caveat at prod/scripts/shred-bundle.sh:410-415 covers
    CoW/journaling but not hardlinks. Operator-side disposal hygiene;
    no adversary in the documented model can reach it.

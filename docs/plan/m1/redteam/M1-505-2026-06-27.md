FINDINGS:
  - CATEGORY: PERM-ESCAL
    SEVERITY: critical
    PROMISE: security.md §Trust boundaries (1): "Adapter -> Provider. The
             adapter asserts identity via a stable, cryptographically
             anchored ID. Display names are informational and never used
             for authorization (decision D10)." Reinforced by §Per-adapter
             admin threat profile ("SimpleX admin. The admin's identity is
             a cryptographic queue address ...") and the §Authorization
             model determinism boundary ("Steps 1-9 ... the determinism
             boundary that makes privilege escalation via injection (T3)
             infeasible").
    GAP: SimpleXMessageCodec.java:362-366 derives the DM identity from
         `contact.profile.contactLink` — a peer-supplied, SELF-ASSERTED
         profile field — via canonicalizeAdvertisedAddress
         (SimpleXMessageCodec.java:776-787), then uses it as BOTH the
         `Identity.contactId` and the `ScopeRef.Dm.contactId`
         (SimpleXMessageCodec.java:385-388). That value is the
         `(adapter, contact_id)` authorization join key used by the
         bootstrap-seeded `is_admin` row lookup and by
         GrantAdminCommandHandler. The code's own comment
         (SimpleXMessageCodec.java:356-361) admits "profile.contactLink is
         SELF-ASSERTED by the peer, so a contact could advertise the
         admin's address to be treated as admin." This is a self-asserted
         field used for authorization — precisely what D10 / trust
         boundary 1 forbid. The diff documents an operator-acceptance
         caveat only in deployment.md:80-90 (a different doc); security.md,
         the authoritative trust-path document, retains the cryptographic-
         anchor commitment unamended, and §"What's intentionally NOT in
         v1" does not list this acceptance. The previous code keyed on the
         per-connection decimal `contactId` (the cryptographically anchored
         per-connection id); this diff replaces that anchor with an
         attacker-controlled field.
    REPRO: 1) Operator configures the bootstrap admin as the admin's
           SimpleX queue address; AdminBootstrap seeds users row
           (simplex, <admin-bare-queue-id>, is_admin=true). 2) Adversary
           connects to the bot's published SimpleX address (no invite
           needed yet) and sets their own profile contactLink/address to
           the admin's published queue address (a public value). 3)
           Adversary DMs `/grant-admin <adversary-own-address>`. 4) The
           codec reads contact.profile.contactLink, canonicalizes it to
           <admin-bare-queue-id>, and surfaces ScopeRef.Dm(<admin-bare-
           queue-id>). 5) Because a users row already exists for that
           contact_id (the seeded admin), authorization step 2 (unknown-
           contact invite gate) never fires — the adversary is treated as
           a KNOWN, is_admin=true contact and the admin-only command
           executes. Result: full bot-admin compromise (invite issuance,
           ban, source mutation, audit access) and a complete bypass of
           the invite-code registration gate, achievable by any contact
           who knows the admin's public address.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

  - CATEGORY: INFO-LEAK
    SEVERITY: high
    PROMISE: CLAUDE.md / spec key conventions and security.md prompt-
             injection tool table: "Per-(user, scope) isolation for state,
             memory, saves. Never leak across users or between DM and
             group." The LLM tools recallMemory ("Reads chat_memory for the
             calling (user, scope) only - D28") and listSaves ("never
             returns another user's saves") bind isolation to the resolved
             (user, scope) identity.
    GAP: Because the DM scope identity is now the self-asserted
         `contact.profile.contactLink` (SimpleXMessageCodec.java:362-366,
         385-388), the per-(user, scope) partition key is attacker-
         controlled. Any peer can advertise a victim's queue address and
         have the Provider resolve their inbound DM to the victim's
         `(adapter, contact_id)` identity — the same join key that scopes
         chat_memory, saved_post, /export, /forget, and every scope-
         filtered LLM tool result.
    REPRO: 1) Adversary learns a victim's published SimpleX address. 2)
           Adversary connects to the bot and sets their advertised
           contactLink to the victim's address. 3) Adversary DMs the bot
           (e.g. enters chat mode or `/saved`, `/export`). 4) The codec
           canonicalizes to the victim's bare queue id; if a victim users
           row exists, the adversary is served the victim's scope —
           reading the victim's saved posts, chat memory summaries, and
           exportable state, and able to `/forget` (destroy) it. This
           breaks the cross-user isolation invariant the spec commits to
           "never" violate.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

    PROMISE: docs/spec/security.md §LLM output sanitizer — "Admin commands are
              dispatched only by the deterministic command path, so a
              copy-pasted reply still requires `is_admin=true` to do anything;
              the sanitizer closes the social-engineering surface where a small
              LLM emits plausible-looking admin commands across any of the
              surfaces above. Every match is audit-logged; rows aggregate per
              distinct token per sanitize call and carry the exact occurrence
              count — counted, never throttled." The amended residual keeps
              that surface open for one case only, and justifies keeping it
              open with: "the alternative — one sanitize call over assembled
              multi-author prose — is strictly worse, because the span then
              swallows *other publishers'* bytes and a co-clustered attacker
              can delete a third party's post (the content-suppression vector
              the categorized-render redteam caught)."
    GAP: The amendment widens the accepted residual from "two posts' fields"
         to "two separately-sanitized fields" (docs/spec/security.md:543-545)
         and admits the new within-row instance at docs/spec/security.md:547-558
         ("One publisher now suffices to create that pair"), then carries the
         OLD case's accept-rationale onto it verbatim at
         docs/spec/security.md:560-566 ("unchanged in KIND and still accepted,
         on the same reasoning"). The multi-author half of that rationale
         cannot apply to the new instance: the two fields are one post's
         original and that same post's own English anchor
         (DisplayHeadline.anchorFirst -> derive,
         infochat-provider/src/main/java/app/zcat/infochat/provider/render/DisplayHeadline.java:247-267,
         driven for /saved at
         infochat-provider/src/main/java/app/zcat/infochat/provider/command/SavedCommandHandler.java:442-446).
         A sanitize/detection unit spanning those two values could only ever
         delete the SAME publisher's bytes — self-suppression, not the
         third-party content-suppression vector the spec cites — so "the
         alternative is strictly worse" is asserted where it is not
         established, and a closable defense-in-depth gap is recorded as a
         permanent residual. Only the `is_admin=true` dispatch bound actually
         survives onto the new case. Concretely, `derive` makes two independent
         `LlmOutputSanitizer.sanitize` calls and no joint detection pass, and
         `/list-sources --all` is a flag-bearing closed-list entry while bare
         `/list-sources` is not
         (infochat-core/src/main/java/app/zcat/infochat/core/llm/LlmOutputSanitizerCore.java:117),
         so a pair split across the two lines produces no match, no
         `[redacted command]`, and no `LLM_OUTPUT_SANITIZED` row from either
         call.
    REPRO: 1. Adversary controls one RSS/social source declared non-`en`
              (source.language = 'tr').
           2. They publish one post whose title carries the command word and an
              embedded instruction aimed at the ingest translator, e.g.
              `/list-sources <text steering the translator to emit a line
              containing a bare --all mid-string>`. Trust-boundary assumption
              5 of this threat model ("LLMs ... can be coaxed into emitting
              attacker-chosen output") is what makes the second half
              obtainable; the halves may also be placed the other way round.
           3. The collector's IngestTranslationWorker writes `post.title_en`;
              `/save <uid>` snapshots it into `saved_post.title_en` (V78,
              SaveCommandHandler.java:112-118, :142-147, :383-390).
           4. Any reader runs `/saved` (or the same post reaches a scheduled
              digest / `/summary`, which have rendered the identical
              original+anchor pair since M1-759 — DigestRenderer.java:960-983).
              The block renders as the anchor line plus the publisher's own
              words bracketed beneath. `DisplayHeadline.bracketed` wraps only
              the line's ends, so the flag survives as a clean `\s+` token.
           5. Sanitize call A sees only the command word (not a closed-list
              entry alone); sanitize call B sees only the flag. Neither
              redacts; neither writes an audit row. An operator triaging
              `audit_log` for `LLM_OUTPUT_SANITIZED` sees nothing, while the
              delivered message contains a copy-pasteable admin-only
              `/list-sources ... --all`. Dispatch still requires
              `is_admin=true`, which is why this is low rather than higher —
              but that is the only bound the spec's own rationale actually
              retains for this case, and the spec claims a second one it does
              not have.

    tagged "(M1-765)" and the earlier cross-reference reads "since M1-765"
    (docs/spec/security.md:404), but the original+anchor adjacency shipped with
    M1-759 and is already live on the scheduled digest, `/summary` and the

    DisplayHeadline.usesAnchor / anchorBlock on main). The spec text itself

    retro-audit reading the version tag would scope the residual to `/saved`
    and to this ticket, when it is a group-broadcast exposure that has been in
    production since M1-759.
  - The amendment states the new precondition as "a single hostile publisher",
    which is the weakest framing but not the weakest precondition. Under
    §Trust boundaries item 9 a hostile or compromised LLM endpoint authors
    every byte of `title_en`/`body_en` for arbitrary posts, so it can supply
    one half of the pair against a benign publisher's post, and both halves
    across two rows of one rendered page with no publisher control at all. The
    accepted bound (`is_admin=true` at dispatch) is unchanged, so this does not
    alter the disposition — noted only because the text's stated precondition
    is one notch stronger than reality.
  - The sanitize-call census (docs/spec/security.md:529-533) is accurate for
    what it now names — `anchorFirst` does select the field from the ORIGINAL
    and then take THAT field's anchor, each through its own `renderLine` call,
    and both anchor columns are bounded at `BODY_SCAN_LIMIT` in SQL
    (SavedCommandHandler.java:450-455) and again in Java
    (DisplayHeadline.renderLine:269-271). It remains short by two other
    single-field `/saved` calls that predate this diff: the `/saved <tag>`
    filter echo (SavedCommandHandler.java:385-387) and the display-hit
    translator reply's sanitizer-2 leg (TranslationPipeline.runForDisplayHit).
    Both are one-field calls, so the stated PROPERTY is still delivered; only
    the enumeration is incomplete.
  - Round-1 item 3 (no language verification behind the unbracketed-line
    invariant), deferred to M1-771, was re-derived rather than assumed: with
    the anchor an echo of the original, `derive` still reports `anchored=true`,
    `usesAnchor` is true for an `en` reader, `primaryInReaderLanguage` returns
    true on NO_OP (TranslationPipeline.java:299-312), and `subordinateFor`
    suppresses the duplicate line — the reader sees exactly one bare foreign
    line. A near-echo instead yields a bare foreign primary plus a bracketed
    near-duplicate. Both match the deferral's description; the deferral leaves
    nothing worse than stated, and the impact stays display honesty rather than
    confidentiality, integrity or availability.

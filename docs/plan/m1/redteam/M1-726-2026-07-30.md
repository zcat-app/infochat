FINDINGS:
  - CATEGORY: AUDIT-EVASION
    SEVERITY: medium
    PROMISE: docs/spec/security.md §Failure handling — "**Schema-violating LLM
              output** (wrong JSON shape, unexpected label value, missing
              required field) is treated identically to an unparseable reply at
              every stage: retry once, then apply the stage-specific failure
              path below." and "- **Tagger** failure → fall back to
              `source.bootstrap_tags`, mark the post, throttled admin notify."
    GAP: The diff's new SUCCESS-vs-failure split keys entirely on
         `ValidationResult.invalidCount()`
         (infochat-collector/src/main/java/app/zcat/infochat/collector/eval/tagger/TaggerWorker.java:392-401:
         `validated.invalidCount() == 0 ? AttemptResult.noTags() :
         AttemptResult.zeroValid()`), and `NO_TAGS` short-circuits the whole
         fallback chain via `isAnswered` (same file, lines 289, 322, 347-349) —
         no retry, no `tagger_fallback=true`, no
         `throttledAdminNotifier.notifyOnce` (lines 328-337).
         But `invalidCount` cannot see a wrong-typed `tags` array: `parseTags`
         silently discards every non-textual array element BEFORE validation
         (same file, lines 473-479: `tags.forEach(node -> { if
         (node.isTextual()) out.add(node.asText()); })`), so a reply such as
         `{"tags":[1,2]}`, `{"tags":[null]}`, `{"tags":[{"name":"ai"}]}` or
         `{"tags":[["ai"]]}` yields `parsed = []` → `valid = []`,
         `invalidCount = 0` → `NO_TAGS`. A wrong-JSON-shape reply is therefore
         classified as the model's deliberate "nothing fits" answer and is
         neither retried nor routed to the bootstrap fallback, exactly what the
         quoted rule forbids. Pre-diff the same reply produced `ZERO_VALID` →
         retry → `BOOTSTRAP` + throttled admin notify, so the diff introduces
         the regression.
         The diff's own spec text asserts the invariant the code does not hold:
         docs/spec/llm.md (diff hunk, "+  which is zero exactly when the model
         proposed nothing") and
         docs/design/05-llm-and-embeddings.md (diff hunk, "zero invalid means
         the model proposed nothing"). Neither is true for a non-string tags
         array. security.md §Failure handling was not amended at all.
    REPRO: 1. Operator points the TAGGER task at any endpoint (per
           docs/spec/security.md §Trust boundaries item 9 a hostile or
           compromised endpoint, and per §Threat model a prompt-injecting feed
           author reaching the model through the post body woven into the
           tagger prompt, are both in scope).
           2. The endpoint answers a tagger call with the well-formed-JSON but
           wrong-shape body `{"tags":[0]}` (a shape small local models really do
           emit as `{"tags":[{"name":"ai"}]}`).
           3. `parseTags` drops the non-textual element, `validate` reports
           `valid=[] invalid=0`, `tryOnce` returns `NO_TAGS`, `isAnswered`
           returns true on attempt 1, and `persistCursor` writes
           `tags='{}', tagger_done=TRUE, tagger_fallback=FALSE`.
           4. Observable result: no second attempt (the prompt-shape retry the
           spec mandates for schema violations never runs), no
           `tagger.fallback_to_bootstrap` WARN, no throttled admin
           notification, and no `tagger_fallback` marker on the row. The post
           silently drops out of every tag-keyed retrieval branch
           (`p.tags && ARRAY[?]` in EligiblePostQuery.java:241/245/250,
           SearchPostsTool.java:161, DigestPostCollector.java:169), and the
           operator has no signal that the tagger stage is malfunctioning.
    SUGGESTED-FIX-CLASS: input-sanitization

OUT-OF-MODEL:
  - A feed author who prompt-injects the tagger into answering `{"tags":[]}`
    for their OWN post can make that single post evade topic-keyed retrieval
    (it still reaches bare `/summary` and the D62 Other bucket). Tag control by
    injection is pre-existing — the same injection could already elect any
    in-vocabulary tag — and the effect is self-limiting to the attacker's own
    post, so this is noted rather than filed. It becomes interesting only if a
    future feature makes "untagged" mean "unreviewed" or "excluded from
    moderation sampling".

    infochat-provider/src/test/java/app/zcat/infochat/provider/digest/UntaggedPostRetrievalIT.java:698-705

    only because the pattern is the shape a later edit could turn into a real
    injection if the prefix ever becomes a parameter.

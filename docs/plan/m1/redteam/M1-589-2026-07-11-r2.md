FINDINGS:
  - CATEGORY: DOS
    SEVERITY: low
    PROMISE: "**Chat-mode replies** with the chat-agent LLM unreachable →
              return a localized 'chat assistant is unavailable, try again
              later' friendly error from the bundle (D43); the message never
              reaches the chat agent loop, no `chat_session` advance, no
              `chat_memory` write, no tool invocation."
              (docs/spec/security.md §Failure handling, "Provider-side
              (user-facing) LLM failures")
    GAP: The new deterministic semanticSearch pre-fetch executes BEFORE the
         chat LLM is resolved or called, so on the LLM-unreachable failure
         path a tool invocation (one embedding HTTP round-trip to the local
         backend plus one pgvector k-NN index probe on a pooled DB
         connection) has already run by the time the friendly error is
         returned. Evidence:
         - infochat-provider/src/main/java/app/zcat/infochat/provider/chat/ChatAgent.java:245-247
           (pre-fetch dispatch, doHandle step 3) runs before line 250
           (llmRouter.forTask, step 4) and line 255 (runToolLoop, step 5,
           where unreachability first surfaces).
         - ChatAgent.java:188-190 — the catch-block comment rewrites the
           spec commitment to "no tool invocation *beyond what already ran
           before the failure*", a silent weakening of the absolute "no
           tool invocation" bullet; security.md was amended in this diff
           (the semanticSearch tool-table row) but the §Failure handling
           bullet was NOT amended to match, so the shipped spec still
           promises zero tool work on this path.
         - infochat-provider/src/test/java/app/zcat/infochat/provider/chat/ChatAgentTest.java:962-964
           pins the deviating behavior (dispatcherCalls == 1 on LLM
           failure: "only the deterministic semanticSearch pre-fetch").
    REPRO: 1. Deploy with a per-task-routed chat LLM (e.g. remote provider
              for CHAT_AGENT); take that provider offline or wait for a
              provider-side outage/rate-limit window (no router fallback
              exists in v1 by design, so the outage is a normal, reachable
              condition).
           2. As any registered user (or many), send chat-mode messages up
              to the transport / LLM-bucket rate caps.
           3. Each message returns the friendly "chat assistant is
              unavailable" error — but each one first burned an embedding
              HTTP call and a pgvector HNSW iterative-scan probe (bounded
              only by statement_timeout / hnsw.max_scan_tuples), cost the
              threat model says this failure path must not incur ("no tool
              invocation"). Pre-diff behavior matched the promise: zero
              tool work on an LLM-unavailable turn. Impact is bounded by
              the existing per-user rate buckets — defense-in-depth
              erosion of a stated failure-handling commitment, not
              unbounded amplification.
    SUGGESTED-FIX-CLASS: other

OUT-OF-MODEL:
  - ivfflat-profile density-oracle regression: the leak-freedom argument
    ("retrieval is exact over the caller-visible corpus... observed recall
    carries no signal about unsubscribed-content density") rests on
    `SET LOCAL hnsw.iterative_scan = strict_order`
    (SemanticSearchTool.java:797-801), which is inert for ivfflat indexes —
    the hardware profile picks the pgvector index type (`hnsw` OR
    `ivfflat` per CLAUDE.md/profile sizing), and pgvector's ivfflat has a
    separate `ivfflat.iterative_scan` GUC with no strict_order mode. On an
    ivfflat-profile deployment the subscription/READY/threshold WHERE
    predicates still guarantee no unsubscribed post ever surfaces (the
    in-model commitment holds), but retrieval reverts to a post-filtered
    probe whose recall can shrink with unsubscribed-content density — the
    recall-crowding density oracle the r1 audit classified out-of-model
    returns on those profiles, despite the ticket recording it
    "eliminated by construction". The spec's semanticSearch row promises
    only subscription scoping (delivered), so this stays advisory; flagging
    so the user can decide whether the design-note "both are exact and
    leak-free" claim should be scoped to HNSW profiles or the oracle
    added to the threat model.

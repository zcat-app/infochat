RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: INFO-LEAK
    SEVERITY: medium
    PROMISE: "Per-(user, scope) isolation for state, memory, saves. Never leak across users or between DM and group." (CLAUDE.md §Key conventions) and security.md §Authorization model: "any non-/retry input from the same (user, scope) clears the anchor."
    GAP: InboundRouter.java:479 — `summaryAnchorRepository.clear(anchorActorId, anchorActorId)` passes `actorId` as both `userId` and `scopeId`. After M1-069 fixes chat-mode dispatch to use the group UUID as `scopeId` (line 504), the anchor-clear at line 479 remains inconsistent: a group-scope non-/retry message clears the user's DM-scope anchor (keyed by `(actorId, actorId)`) instead of the group-scope anchor (keyed by `(actorId, groupId)`). This is a cross-scope side effect: a group-scope message silently wipes the DM-scope `/retry` anchor, and the group-scope anchor is never cleared by non-/retry group messages.
    REPRO: (1) User issues `/summary` in DM scope, creating a DM-scope summary anchor. (2) User sends a chat-mode message in a group scope. (3) Step 4.6 fires `summaryAnchorRepository.clear(actorId, actorId)`, which deletes the DM-scope anchor row (keyed by `(actorId, actorId)` matching `WHERE user_id = actorId AND scope_id = actorId`). (4) User returns to DM, issues `/retry`, gets "no anchor found" instead of re-rolling the DM summary. The DM-scope anchor was silently destroyed by a group-scope action, violating per-(user, scope) isolation. Conversely, a group-scope anchor is never cleared by non-/retry group input, so stale group anchors persist indefinitely.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

OUT-OF-MODEL:
  - The `writeAuditRow` method in ChatAgent.java constructs `detailsJson` via string concatenation (`"{\"scope_kind\":\"" + scopeKind + ...`). While currently safe because `scopeKind` is a literal "dm"/"group" and `scopeId` is a UUID, this pattern is fragile — a future caller passing an uncontrolled string into `scopeKind` could break JSON structure or inject keys. Not exploitable today but worth noting as a maintenance risk.

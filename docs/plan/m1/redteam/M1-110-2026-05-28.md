RED-TEAM VERDICT: CLEAN

The diff under audit (M1-110) is an additive Flyway migration (V26)
that adds two columns to the groups table plus a schema-shape
integration test:
  1. approval_status VARCHAR NOT NULL DEFAULT 'pending' with a CHECK
     constraint limiting it to {pending, approved, rejected}.
  2. activated_by UUID REFERENCES users(id), nullable.
  3. UPDATE groups SET approval_status = 'approved' — grandfathers all
     rows existing at migration time.

The migration is explicitly additive; the gate enforcement that reads
approval_status (security.md authorization step 3.5 — silently drop
pending/rejected groups) lands in M1-112. No enforcement logic exists
in this diff, so AUTH-BYPASS / PERM-ESCAL / AUDIT-EVASION findings
cannot attach — there is no gate to bypass, no ban path, no audit
write, and no input-validation surface here. The CHECK values match
the spec's three approval states exactly; the column DEFAULT for new
rows is 'pending' (correct per step 3.5); the activated_by FK is
nullable per the spec ("not recoverable"). The Provider role already
holds UPDATE on groups (V5) — no new grant is introduced.

OUT-OF-MODEL:
  - Grandfather clause `UPDATE groups SET approval_status = 'approved'`
    (V26__d47_group_authorization.sql:30) auto-approves every group row
    that exists at migration time. If a real deployment carried pre-D47
    groups, all of them silently bypass the D47 admin-approval gate that
    M1-112 will enforce. Under the project's stated greenfield assumption
    ("M1 is greenfield, there is no prior version") this set is empty in
    production, and the spec's D47 note explicitly treats pre-D47 groups
    as "already being processed under the pre-D47 model", so this is a
    documented migration trade-off rather than a threat-model gap.
    Flagged only so the user can confirm the greenfield assumption holds
    at the deployment boundary (no manually-seeded groups rows, no
    staging data promoted to prod) before the M1-112 gate lands — if it
    does not, the grandfather scope should be narrowed (e.g. only rows
    with existing approved-equivalent activity) rather than
    blanket-approving.
  - The actual D47 authorization gate (the code that reads
    approval_status and silently drops pending/rejected groups per
    security.md step 3.5) is not in this diff — it is deferred to M1-112.
    No bypass finding can attach to M1-110 because no enforcement path
    exists here yet; the audit of the gate itself must happen against the
    M1-112 diff. Noting so the gate's correctness is not assumed to have
    been reviewed by virtue of this migration passing.

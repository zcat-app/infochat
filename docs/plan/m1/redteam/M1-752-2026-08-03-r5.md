RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - Re-probe outbound volume does not inherit the active fetch path's per-host
    pacing. The amendment specifies the re-probe as running "off the active fetch
    path so re-probes can never delay healthy sources" (docs/spec/decisions.md D42;
    M1-754 §Design constraints, "must not run inside enumerateActiveSources"), and
    M1-754 correctly carries the per-connection SSRF controls across by mandating
    the `Fetcher` SPI (each Fetcher builds its own SsrfGuardedHttpClient), which is
    what security.md §SSRF and outbound connections actually promises (allowlist,
    DNS re-resolution per hop, redirect/body/timeout caps). What it does not carry
    is the *aggregate* control on the enumeration it runs beside:
    `infochat.fetch.host-min-interval` / `FetchScheduler.hostNextAllowed`, pinned by
    FetchSchedulerHostPacingIT, which exists because 27 sources collapsed onto one
    host in a live event. Sources sharing one upstream host tend to park together
    and therefore become probe-due together, so the re-probe path can emit the
    synchronized single-host burst the active path is throttled against. This is
    NOT a threat-model gap — no spec file commits to outbound fetch pacing at any
    tier (the only "per-host" commitments in docs/spec are the asset-command refresh
    cadences), so there is no promise to fail. Flagged so the user can decide
    whether the re-probe scheduler should share the pacing map, and whether that
    commitment belongs in the spec.
  - The recurring parked-set signal has no stated size bound or paging. D42 as
    amended commits to "a recurring operator-visible statement of the whole parked
    set (source ids, park reasons, parked-since ...; silent when the set is empty)"
    and M1-754 extends it to "ALL park reasons, including terminally parked
    sources" — a set that is monotonically non-decreasing until an admin acts.
    `/add-source` is open to any non-banned, post-probation user in a DM (D14), so
    the set's cardinality is partly user-driven, and every cadence re-sends the full
    enumeration to every bot admin. security.md §Failure handling promises only
    count-coalescing ("an outage produces one summary message, not 200 individual
    alerts"), which one recurring message satisfies, so this sits outside the stated
    promise rather than against it. Worth deciding explicitly whether the summary
    needs a cap, paging, or a "+N more" tail before M1-754 implements it.

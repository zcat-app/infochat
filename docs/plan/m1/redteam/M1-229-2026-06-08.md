OUT-OF-MODEL:
  - Reshaped newcomer-registration availability DoS. The diff replaces the
    M1-205 hard capacity-wall lockout with a single shared per-adapter
    "stranger" token bucket sized at `inboundPerMinute`
    (RateCapBucket.java tryAcquireStranger). ALL unregistered inbound on one
    adapter — Sybil-flood ids, never-registered probers, AND banned users
    (BanCommandHandler.invalidate routes a banned contact back to the
    stranger bucket) — now contend for that one budget. Under a *sustained*
    flood the shared bucket is drained continuously, so a legitimate
    newcomer's invite-code message (authorization step 2) is dropped with
    near-certainty: registration is not permanently walled, but it is
    effectively denied for the duration of the flood, and a single sustained
    flooder (including one banned user) can suppress all new-user
    registration on that adapter. This is a real availability coupling
    between hostile strangers/banned floods and legitimate newcomers, and it
    is a regression in cross-contact isolation versus the pre-M1-229 per-id
    model (where one contact's flood could not drain another's bucket). It is
    OUT-OF-MODEL because security.md does not promise newcomer registration
    availability under flood and explicitly defers Sybil resistance to v2
    (§What's intentionally NOT in v1 — "Sybil resistance across adapters";
    the design doc 06-messaging.md amendment also explicitly accepts the loss
    of per-newcomer fairness). Flagging so the user can decide whether to (a)
    size the stranger bucket independently of the per-contact
    `inboundPerMinute`, or (b) route banned contacts to a separate bucket
    from never-seen newcomers so a banned flooder cannot starve registration.
  - Literal deviation from security.md §Authorization model step 1.5 wording
    ("Apply the per-`(adapter, contact_id)` inbound rate cap"): strangers are

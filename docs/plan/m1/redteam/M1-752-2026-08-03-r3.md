    SEVERITY: medium
    PROMISE: security.md §Failure handling — "**Per-source UNKNOWN auto-disable.** A source whose Stage 2 UNKNOWN
              rate exceeds a profile-driven threshold ... has its `source.status` transitioned to `'failed'` (the same
              status used for consecutive HTTP failures, decision D42 — but **excluded from D42's automatic re-probe
              rung**: this park is a security control, its park-reason discriminator marks it manual-only, and recovery
              happens only via `/source-enable`)" (docs/spec/security.md:1551-1557), reinforced by the amendment's own
              justification for the new upgrade rule — "Otherwise a feed that failed its way into a `fetch-failure`
              park before its UNKNOWN verdicts landed would be auto-readmitted on a timer by the very ladder this
              control overrides" (docs/spec/security.md:1560-1566) — and by D42 property (b): "a re-probe-eligible
              reason may never overwrite a manual-only one, and a manual-only reason is never downgraded"
              (docs/spec/decisions.md:59). Also schema.md §Sources and tags — "which selects on `deleted_at IS NULL`
              like every other scheduler enumeration (a soft-deleted source is never probed or revived)"
              (docs/spec/schema.md:281-283).
    GAP: Every eligibility predicate the amendment specifies lives on the SELECTION side; none is required at the
         RESTORE-WRITE side, and the two are necessarily separated by a network probe. D42 property (c)/(d) say "the
         re-probe **selection** includes `deleted_at IS NULL`" / matches only the explicit `fetch-failure` reason
         (docs/spec/decisions.md:59), and M1-754's acceptance repeats the same scoping — "Fail-closed **selection** ...
         the re-probe **predicate** matches ONLY the explicit `fetch-failure` reason"
         (docs/plan/m1/tickets/M1-754-parked-source-reprobe-ladder.md:593-598 of the diff, acceptance item 5) and
         "the re-probe **selection** carries `deleted_at IS NULL`" (item 6). The write is specified with no predicate
         at all: "First successful re-probe restores `status='active'`, zeroes `consecutive_failures`, clears the park
         reason" (item 8), and D42 likewise ("The first successful re-probe restores `status='active'` ...").
         The r3 remediation is what makes the window reachable: before it, `PerSourceUnknownTracker`'s UPDATE was
         guarded on `status='active'` (PerSourceUnknownTracker.java:148) so it could not write to a row the ladder had
         parked; property (b) now REQUIRES that writer to reach parked rows (M1-754 acceptance item 3 widens both
         PerSourceUnknownTracker:114 and :148). So an upgrade to `unknown-rate` can now land between the re-probe
         selection and the restore UPDATE, and the unguarded restore then clears it and sets `status='active'`.
         The racing writers are not covered by D41's single-Collector serialization: the UNKNOWN-rate evaluator is a
         separate scheduled job from the fetch/probe path, and `/remove-source` (the `deleted_at` leg) runs in the
         Provider process entirely.
    REPRO: Leg 1 (security-park lift). Adversary controls an ingested feed. (1) They let it fail N times so the D42
           ladder parks it `fetch-failure` — this is now the state that grants automatic recovery. (2) They resume
           serving, are restored, and start emitting UNKNOWN-verdict content above the per-source threshold; they then
           fail out again into a `fetch-failure` park. (3) On a scheduled re-probe the ladder selects the row
           (reason = `fetch-failure`, due, under cap) and issues the probe; the adversary's endpoint answers slowly,
           holding the probe open to near the read-timeout cap. (4) Inside that window the UNKNOWN-rate evaluator ticks
           and upgrades the row to the manual-only `unknown-rate` reason — the quarantine-exhaustion control firing
           exactly as property (b) intends. (5) The probe returns 200 and the restore UPDATE, which re-checks nothing,
           sets `status='active'`, zeroes the counter and CLEARS the `unknown-rate` reason. The security park is gone,
           no admin acted, and the audit row written for the transition records a legitimate-looking automatic restore.
           The probe schedule is deterministic backoff and the adversary controls both the UNKNOWN arrival rate and the
           probe latency, so the window is retriable every cycle rather than a one-shot coincidence.
           Leg 2 (soft-delete revival). A bot admin `/remove-source`s a hostile feed that is sitting in a
           `fetch-failure` park (hard delete is forbidden by invariant 4, so removal == `deleted_at` set) while a probe
           for that row is already in flight. The selection passed `deleted_at IS NULL` before the removal; the restore
           write does not re-check it, so the row is flipped back to `status='active'` after the admin's removal —
           the outcome D42 property (d) states must not happen ("an admin's `/remove-source` must not be undone by a
           background job"). Impact is smaller than leg 1 (the scheduler still filters `deleted_at`), but the state the
           removal was meant to end is silently restored and re-arms on any later `/source-enable`-free revival path.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

           re-probe the HTTP-failure park now has, citing :1583 verbatim, and the quarantine-exhaustion defense that

           inconsistency rather than by a decision.

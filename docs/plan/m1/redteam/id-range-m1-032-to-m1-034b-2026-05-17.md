## Verdict

**RED-TEAM VERDICT: CLEAN**

The adversary subagent (Opus, fresh-context, read-only) audited the diff against `docs/spec/security.md` and returned no findings against the documented threat model. The implementation tracks the spec's commitments around:

- Stage 1 ordering (entity pre-decode → NFKC → bidi/zero-width strip → regex with watchdog → placeholder redact → OWASP allowlist HTML sanitize, fail-closed on sanitizer exception).
- Per-row random placeholder IDs (≥128 bits of entropy) so attackers cannot forge `[REDACTED:XXXX]` markers in the body.
- Per-call random delimiter UUID wrapping the body in both the Stage 2 judge prompt (`<<<UNTRUSTED_CONTENT id="…">>>` … `<<<END id="…">>>`) and the Tagger prompt — defeating prompt-injection forged-closing-tag attacks.
- Stage 2 verdict-token strict parser (only the four canonical tokens; anything else triggers retry/INFRA_FAILURE rather than silent acceptance).
- DB role grants: `infochat_provider` has no SELECT on `quarantine.original_html` (only the `quarantine_review_view` projection which excludes the unredacted body); `REVOKE DELETE ON post_embedding FROM {collector, provider, PUBLIC}`.
- Audit row on the `local-only` posture conflict release path (`StartupReleaseOnStage2FailureWarn.writeAuditRow`) with `actor_user_id=NULL` (system action), `?::jsonb` cast for the details payload, parameterised statement, controlled-vocabulary action verb.
- No SQL injection surface — all `executeUpdate` / `executeQuery` calls use prepared statements with `?` placeholders.
- No prompt-injection turn-taking — Stage 2 / Tagger return JSON in a constrained schema; outputs are parsed and filtered (controlled-vocabulary tag check) before being persisted; invalid output is silently dropped per the partial-valid rule.
- No reachable secret leakage — log messages reference post IDs, rule IDs, and error classes, never post body content; the OpenAI-compatible providers do not echo `Authorization: Bearer …` into exceptions (covered by the M1-024/M1-025/M1-026 redteam-driven remediations the diff inherits).

## Out-of-model advisories

The adversary flagged three observations that fall outside the documented threat model but may merit either a hardening ticket or a spec amendment to bring them inside the threat model.

### 1. `local-only` posture only inspects the Security-judge base URL

**File:** `infochat-llm-adapter/src/main/java/io/infochat/llm/routing/LlmRouterStartupGuard.java`

**Observation.** `validateLocalOnlyConfiguration` only inspects `infochat.llm.security.base-url` when `infochat.llm.local-only=true`. The Collector also outbound-connects via `infochat.llm.tagger.base-url` and `infochat.embeddings.base-url`. A `local-only=true` posture combined with a non-loopback Tagger or Embedding base URL would not be rejected at startup.

**Threat-model status.** Governed by `docs/spec/llm.md`'s "local-only is the most-restrictive posture" commitment, which is outside `docs/spec/security.md`'s explicit threat model. The per-call SSRF guard (M1-024..M1-026) is the security.md commitment for outbound connections; `local-only` is an additional operator-facing posture rather than a security boundary the threat model promises.

**Suggested disposition.** Either (a) widen the startup guard to all three per-task base-URL keys, or (b) leave as a llm.md-spec concern. The audit flags this for explicit decision, not as a finding.

### 2. Stage 1 string-allocation cost is not bounded ahead of the regex watchdog

**File:** `infochat-collector/src/main/java/io/infochat/collector/eval/stage1/Stage1Pipeline.java:252-264`

**Observation.** `Stage1Pipeline.process` runs `entityDecoded = unescapeHtml4(body)` → `unicodeNormalize(entityDecoded)` (NFKC + bidi/zero-width strip) before reaching the regex watchdog. Each of those produces a fresh full-body String. For an arbitrarily large body the watchdog timeboxes the regex but not the preceding allocations.

**Threat-model status.** The threat model commits to body-size caps in §SSRF at the **fetcher** boundary (`docs/spec/security.md` §SSRF — "body-size, redirect, content-type caps are enforced"), which should bound the input to Stage 1. The Stage 1 pipeline itself does not enforce a separate cap.

**Suggested disposition.** Likely defended by the fetcher-side cap (not visible in this diff). Flagging as a defense-in-depth observation — if the operator raises the fetcher's body cap for a permissive feed, Stage 1 inherits the larger ceiling silently.

### 3. `LlmRouter.forTask` silently falls back to `entries.get(0)`

**File:** `infochat-llm-adapter/src/main/java/io/infochat/llm/routing/LlmRouter.java`

**Observation.** When the configured `infochat.llm.default.provider` names no registered `LlmProvider`, the router silently falls back to `entries.get(0)` (CDI discovery order) with no warning log. An operator typo could route SECURITY_JUDGE calls to an unintended provider that happens to be first in the discovery order.

**Threat-model status.** Operator-set config is in the threat model's trust boundary, so this is hardening rather than a finding. The fallback does not violate any explicit security.md commitment.

**Suggested disposition.** Consider failing startup on unknown default-provider name (rather than silent fallback), or at minimum a WARN log. Out-of-model advisory.

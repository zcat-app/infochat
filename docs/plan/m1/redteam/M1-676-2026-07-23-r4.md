REMEDIATION VERIFICATION (informational; not findings)

  Each of the three properties the diff sets out to deliver was checked
  against the code rather than assumed, and each holds:

  1. Canonical-form matching (docs/spec/security.md §"Canonical-form
     matching"). canonicalizeForMatching (LlmOutputSanitizer.java:387-390)
     is NFKC + IngestTextNormalizer.stripBidiAndZeroWidth. I compared the
     stripped codepoint sets character-for-character against the intake
     path: IngestTextNormalizer.java:60-75 (U+061C, U+200E/F,
     U+202A..U+202E, U+2066..U+2069, U+200B/C/D, U+FEFF) is byte-equal to
     InboundRouter.isBidiControl/isZeroWidth (InboundRouter.java:1740-1755),
     and both compose it with Normalizer.Form.NFKC
     (InboundRouter.java:1729). Parity holds. The intake pass runs per
     line with a fenced-code carve-out while the sanitizer canonicalizes
     the whole string — that asymmetry is over-redaction only (a fenced
     block cannot carry a dispatchable command on line 1), never an
     evasion. The no-match fast path returns the caller's bytes
     (LlmOutputSanitizer.java:356-358), so the "only a match may change
     the representation" claim is delivered.

  2. Per-token case rule. compileClosedListPattern
     (LlmOutputSanitizer.java:194-203) quotes words[0] exactly, wraps a
     later non-`--` word in `(?i:...)`, and quotes a later `--` word
     exactly. Verified against every consumer: exact name at
     InboundRouter.java:1414; folded subcommand at
     InviteCommandHandler.java:232 and QuarantineCommandHandler.java:135;
     exact flag at ListSourcesCommandHandler.java:481/483. The only
     subcommand-bearing entries in CLOSED_LIST are `/invite *` and
     `/quarantine *`, both covered. The ASCII-only `(?i:)` (no
     UNICODE_CASE) is sufficient on the canonical form: I probed for a
     codepoint that survives NFKC yet lower-cases to a bare ASCII letter
     and found none reachable — U+212A KELVIN is folded to ASCII `K` by
     NFKC before the pattern runs, U+017F folds to `s`, and U+0130
     lower-cases to a two-char `i`+U+0307 that does not dispatch either.
     The spec's refusal to state a blanket flag rule is factually
     grounded: QuarantineCommandHandler.java:526 does lower-case flag
     tokens, so a future flag-bearing entry on that handler would need a
     different derivation.

  3. "Delivered output never contains `](`". Verified on both exits of
     applyClosedListStripWithMatches. Match path: the final
     neutralizeResidualLinkSyntax at LlmOutputSanitizer.java:362 runs
     after the replacement, and `String.replace("](", "] (")` cannot
     re-form the pair (the inserted space separates them and the scan
     resumes past the replacement). No-match path: the returned value is
     the caller's `input`, which in production is always
     applyMarkdownLinkStrip(llmOutput) (LlmOutputSanitizer.java:225) and
     therefore already neutralized at line 243. I also checked the
     inverse hazard the double-flatten creates — that the flatten or the
     adjacency break, running AFTER canonicalization but BEFORE the match
     loop, could destroy a token the pasted text would still dispatch.
     It cannot: both transformations only delete `[`/`]` or INSERT
     whitespace, and no CLOSED_LIST token contains `[`, `]`, `(` or `)`,
     so a multi-word entry's `\s+` separator can only gain. Nor can the
     replacement manufacture a command: the word-boundary lookahead
     `(?=$|[^a-zA-Z0-9\-])` prevents mid-word replacement, and the
     inserted `[redacted command]` literal keeps the surrounding
     fragments non-adjacent. Sanitize() is the last transformation on
     every LLM-authored delivery path I traced (ChatAgent.java:507,
     TranslationPipeline.java:114 with the cache storing the
     post-sanitizer form at :120, DigestRenderer.java:131-132,
     ClusterBlockRenderer.java:107, CategoryRollupGenerator.java:148).

  Audit coverage is unchanged and still 1:1: one `matches` element per
  occurrence (LlmOutputSanitizer.java:348), one WARN (:347), one row
  (:404-435), all in one transaction that throws rather than letting a
  partially-audited reply ship. The WARN interpolates only the fixed
  CLOSED_LIST literal and an int offset, so the new pass adds no
  user-content log exposure under §Secrets handling. The test diff is
  purely additive — no existing assertion was weakened or removed.

OUT-OF-MODEL:
  - The "Delivered output never contains `](`" heading is absolute, but
    the sanitizer is not on every byte of a delivered digest. The
    degraded-prose branch at DigestRenderer.java:128-129 ships
    `cp.prose()` with NO sanitizer and no flatten, and that degraded form
    is the headlines + URLs fallback built from feed-derived post titles
    (§Failure handling, "`/summary` ... fall back to the headlines + URLs
    + post UIDs degraded form"). Post titles pass
    IngestTextNormalizer.stripMetadataField, which strips bidi/zero-width/
    control characters but performs no markdown flattening, so an
    attacker-chosen RSS title of `[Read the report](https://evil.example)`
    reaches a user with `](` intact. I read the new paragraph's body as
    scoping the claim to text the flatten pass sees ("any `](` the flatten
    could not consume"), and §LLM output sanitizer already discloses a
    documented residual risk on non-error deterministic output, so I do
    not score this as a delivery gap. Flagged so the user can decide
    whether the heading should be narrowed to "sanitizer output" or the
    guarantee extended to the deterministic render path.
  - Unicode separators that survive NFKC and fall outside Java's ASCII
    `\s`: U+1680 OGHAM SPACE MARK, U+180E, U+0085, U+2028/U+2029. I
    re-derived rather than inherited this: the multi-word patterns' `\s+`
    misses them, but so do the parser's own
    `normalized.split("\\s+", 2)` (InboundRouter.java:1411),
    `rawText.trim().split("\\s+", 3)` (InviteCommandHandler.java:231) and
    `rawText.trim().split("\\s+")` (ListSourcesCommandHandler.java:478),
    so no dispatchable form is missed — `/invite<U+1680>create` yields a
    single token and matches no handler. The separators that DO fold
    (U+00A0, U+2000..U+200A, U+202F, U+205F, U+3000) are handled by NFKC
    on both sides. This becomes reachable only if a messaging client
    rewrites such a codepoint to a real space on copy/paste — client
    behaviour outside the documented model.
  - Bidi-reversed VISUAL spoofing plus human retyping. An LLM can emit
    U+202E followed by `nimda-tnarg/`; canonicalizeForMatching strips the
    RLO and matches against `nimda-tnarg/`, which is in no closed-list
    entry, so the line ships unredacted — yet a client renders it as the
    literal `/grant-admin`, and an admin who RETYPES what they see
    dispatches the real command. Parity with the parser is intact (the
    pasted codepoints do not dispatch either) and the spec scopes its
    commitment to "the same representation the deterministic command
    parser consumes", so a rendering-layer spoof is outside the
    documented model. Behaviour is identical pre- and post-diff.

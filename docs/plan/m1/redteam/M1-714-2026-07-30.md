RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: INJECTION
    SEVERITY: medium
    PROMISE: docs/spec/security.md §LLM output sanitizer —
             "Canonical-form matching. The closed-list pass matches against the
             canonical form of the candidate output ... which is the same
             representation the deterministic command parser consumes ...
             Matching the raw bytes instead left a representation asymmetry the
             sanitizer was blind to: ... a token split by a zero-width space or
             wrapped in bidi isolates, and a multi-word entry joined by U+3000
             each survived sanitization verbatim, yet each parses as a privileged
             command the moment a reader copy-pastes the bot's line back in."
             And: "The detector narrows only for that split case: within one
             field, per-occurrence LLM_OUTPUT_SANITIZED rows fire at least as
             often as before the narrowing."
             And: "Every match is audit-logged (per-occurrence, not throttled)."
    GAP: The new shared derivation applies a whitespace rewrite AFTER the
         sanitizer has already run, so the bytes the sanitizer inspected are not
         the bytes that are delivered.
         infochat-provider/src/main/java/app/zcat/infochat/provider/render/DisplayHeadline.java:73
             return truncate(flattenToOneLine(llmOutputSanitizer.sanitize(source)));
         infochat-provider/src/main/java/app/zcat/infochat/provider/render/DisplayHeadline.java:102-104
             sanitized.replaceAll("(?:\\R|\\s)+", " ").strip()
         Java's `\R` matches U+0085, U+2028 and U+2029 (the class javadoc at
         DisplayHeadline.java:96-97 names them explicitly). The sanitizer does
         NOT treat any of those three as a token separator:
         infochat-provider/src/main/java/app/zcat/infochat/provider/llm/LlmOutputSanitizer.java:392-394
         (`isTokenSeparator` is the ASCII `\s` set only), and the multi-word
         patterns at LlmOutputSanitizer.java:250 join words with a bare `\\s+`,
         which in Java is ASCII-only. `canonicalizeForMatching`
         (LlmOutputSanitizer.java:618-621) does not fold or strip them either —
         NFKC leaves U+2028/U+2029/U+0085 alone and
         `IngestTextNormalizer.stripBidiAndZeroWidth`
         (infochat-core/.../IngestTextNormalizer.java:54-79) deliberately keeps
         them (only `stripMetadataField`, which is applied to `title`/`url` and
         NOT to `body`, removes them — IngestTextNormalizer.java:89-110).
         Consequence: text of the form `/quarantine<U+2028>approve <uuid>`
         reaches `sanitize()` as ONE token, produces no closed-list match, no
         WARN, and no `LLM_OUTPUT_SANITIZED` audit row — and is then rewritten by
         `flattenToOneLine` into the dispatchable ASCII form
         `/quarantine approve <uuid>`, emitted at a group-broadcast line start by
         ClusterBlockRenderer.java:104-107, DegradedDigestRenderer.java:62-66 and
         SummaryProseGenerator.java:229-238.
         The author reasoned about one direction of this hazard only — the
         javadoc at DisplayHeadline.java:98-100 argues runs must be REPLACED not
         DELETED so `/list` and `-sources` cannot be spliced — but the
         replacement direction (a non-ASCII separator becoming an ASCII one) is
         exactly the same splice and is not covered.
         Affected closed-list entries are every multi-word and flag-bearing one:
         `/invite create|list|revoke|bot-contact|pending-contacts`,
         `/quarantine list|approve|reject`, `/list-sources --all`,
         `/list-sources --include-deleted` (LlmOutputSanitizer.java:108-145).
         Reachability note (stated honestly rather than overclaimed): the body
         branch at DisplayHeadline.java:82-91 fires only when the stored title is
         blank, and `PostPersister.normalizeTitle`
         (infochat-collector/.../outbox/PostPersister.java:282-290) already
         rewrites a blank title to the literal "untitled" and caps it at 200
         chars at the sole `post` write path. So for newly ingested posts the
         body fallback is unreachable, and the surface is legacy rows written
         before that normalization landed — which the diff's own corpus evidence
         says exist (DisplayHeadline.java:22-26 cites 729 empty-title Bluesky
         rows and a 24,776-char title, both impossible under normalizeTitle).
         Those same legacy titles are also un-stripped, so the evasion applies to
         the title branch on legacy rows too. Independently of the corpus,
         `DisplayHeadline` is `public` and documented as the single derivation
         for three render surfaces, so the sanitize-then-rewrite order is now a
         reusable primitive any future caller inherits.
    REPRO: 1. Attacker publishes a post on any source the deployment follows
              (or any legacy blank-title row already in `post`) whose headline
              text is `/quarantine<U+2028>approve 11111111-2222-3333-4444-555555555555`
              — or `/list-sources<U+2028>--all`.
           2. Stage 1 body normalization keeps U+2028 (it only strips
              bidi/zero-width from bodies), Stage 2 returns BENIGN, the post goes
              READY and is selected into a group's periodic digest or into a
              `/summary` cluster.
           3. `DisplayHeadline.of` calls `sanitize()`; the sanitizer sees
              `/quarantine approve` as one token, matches nothing, writes no
              audit row, and returns the original bytes.
           4. `flattenToOneLine` converts U+2028 to a space. The group receives a
              broadcast line beginning `/quarantine approve 11111111-...`.
           5. A bot admin copy-pastes the line. Intake step 1.7 normalization and
              the parser's `split("\\s+")` both accept it; it dispatches, lifting
              the Stage 1 redactions on an attacker-chosen quarantine row (or, for
              `/list-sources --all`, disclosing the deployment-wide source
              catalogue that §Source URL visibility and the flag-scan entry exist
              to keep out of broadcast output). No `LLM_OUTPUT_SANITIZED` row
              exists for an operator to notice.
    SUGGESTED-FIX-CLASS: input-sanitization

  - CATEGORY: DOS
    SEVERITY: low
    PROMISE: docs/spec/security.md §LLM output sanitizer — "Flag entries are
             matched by a whitespace tokenizer, not a regex, implemented as a
             single left-to-right scan ... that is linear in the reply length. A
             regex was rejected because ... §Trust boundaries item 9 puts a
             hostile endpoint's reply in scope, so an in-cap reply must not be
             convertible into unbounded CPU."
    GAP: The sanitizer's linearity argument is stated against a bounded input.
         This diff changes the input to an UNBOUNDED one on the group-broadcast
         render path. Before the diff, every sanitize call on this path took
         `post.title`, hard-capped at 200 chars by
         `IngestTextNormalizer.TITLE_MAX_LENGTH`
         (infochat-core/.../IngestTextNormalizer.java:128) at the write boundary.
         After the diff, `DisplayHeadline.headlineSource`
         (.../render/DisplayHeadline.java:82-91) can return the entire `post.body`,
         which has no length cap at any write path (`PostPersister` binds
         `normalized.body()` verbatim at PostPersister.java:181; Stage 1 caps the
         match COUNT and wall-clock regex time but not body length —
         Stage1Pipeline.java:329-349). That whole body is then passed to
         `llmOutputSanitizer.sanitize` (DisplayHeadline.java:73), which runs
         `Normalizer.normalize(..., NFKC)`, the markdown-link regex, 24 compiled
         closed-list matchers and 10 tokenizer scans over it
         (LlmOutputSanitizer.java:559-594), plus this diff's own
         `replaceAll("(?:\\R|\\s)+", " ")` over the same bytes — roughly 35 linear
         passes per post, per render, with no watchdog and no pre-bound. The
         bound is applied last (`truncate`, DisplayHeadline.java:115+), i.e. after
         all the cost has been paid. The digest path renders every post in the
         window through this helper (DegradedDigestRenderer.java:62), so the cost
         multiplies by the digest's post count on the scheduler thread.
         Reachability is gated on the same blank-title condition as the finding
         above, which is why this is low rather than higher.
    REPRO: 1. Attacker publishes (or a legacy row already carries) a blank-title
              post with a multi-megabyte body — an RSS `<description>` is bounded
              only by the feed-level body cap, not per item.
           2. The post enters a group's digest window.
           3. Each digest render pays ~35 full linear passes plus an NFKC
              normalization over the whole body, on the render thread, before the
              200-char display bound is applied.
           4. Repeating across many such posts inflates digest render time for
              every subscribed group with no per-input length guard.
    SUGGESTED-FIX-CLASS: other

OUT-OF-MODEL:
  - Stage 1 placeholder split by the display bound. `truncate`
    (.../render/DisplayHeadline.java:115+) explicitly refuses to split the
    sanitizer's own `[redacted command]` marker ("a half-emitted `[redacted comm`
    reads as content rather than as a redaction") but applies no such rule to the
    spec-committed Stage 1 placeholder `[REDACTED:<id>]` (§Ingest pipeline,
    §Quarantine workflow: "The brackets and `REDACTED:` literal are fixed ... so
    user-facing prose, snapshot bodies, and tests recognise the marker by
    exact-match"). Because the body is now a headline source and Stage 1
    redactions live in the body, an attacker can position a flagged span so its
    placeholder straddles char 200 and the reader sees `... [REDACTED:9f…`, which
    reads as content and conceals that a redaction occurred. No data is
    disclosed, so this is a marker-integrity/UI-deception issue rather than any
    of the six listed categories; flagged so the user can decide whether the
    exact-match commitment should bind display truncation.
  - Body bytes at a group-broadcast line start buy nothing under current ingest.
    `PostPersister.normalizeTitle` (PostPersister.java:282-290) already yields
    "untitled" for a blank title and caps titles at 200 chars at the sole write
    path, so both defects the helper's javadoc cites ("unbounded for social
    sources, blank for Bluesky") are already closed for newly ingested rows. The
    body fallback therefore opens a new untrusted-field-at-line-start surface
    (the one the two findings above exploit) whose only live consumers are legacy
    rows. Not an attack in itself; noted because it changes the cost/benefit of
    accepting the residual risk in finding 1.

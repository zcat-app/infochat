# Red-team audit: M1-190 (2026-06-07)

Verbatim threat-actor verdict follows.

RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: AUTH-BYPASS
    SEVERITY: low
    PROMISE: "Last-admin protection (bot admin only). Cannot revoke the only bot admin's `is_admin`, cannot ban the only bot admin, cannot ban self. ... Enforced at the trigger layer, not just the command layer, so a buggy command cannot bypass it."
    GAP: The lock-then-count TOCTOU defense in `infochat-core/src/main/resources/db/migration/V40__last_admin_lock_scope.sql` (lines 54-64, `LOCK TABLE ... SHARE ROW EXCLUSIVE` followed by `SELECT count(*)`) is only correct under READ COMMITTED isolation. The header comment (lines 17-21) claims the waiter "counts the post-commit state and raises," but under REPEATABLE READ the waiter's `SELECT count(*)` uses the transaction snapshot taken before the lock was granted: two concurrent transactions each demoting (or banning) a different admin both see the other admin as still effective, both pass `remaining >= 1`, and both commit — leaving zero `is_admin=true AND is_banned=false` rows. Postgres raises no serialization error because neither transaction updated a row the other touched. This weakness is carried forward verbatim from V35 (lines 31-58 of `V35__last_admin_errcode.sql`), but V40 re-ships the bodies wholesale and explicitly asserts the race-safety property, so the assertion now papers over an isolation-level dependency that nothing in the migration enforces (e.g. no `SET TRANSACTION ISOLATION LEVEL READ COMMITTED` or snapshot-refresh inside the function).
    REPRO: With exactly two admins A and B, open two application transactions at REPEATABLE READ (a plausible "buggy command" — exactly the actor the trigger layer promises to defend against). T1: `UPDATE users SET is_admin=false WHERE id=A`; T2: `UPDATE users SET is_admin=false WHERE id=B` concurrently. T1 locks, counts B (snapshot-visible), passes, commits. T2 acquires the lock after T1 commits, but its RR snapshot predates T1's commit, still counts A as admin, passes, commits. Deployment now has zero bot admins — the lockout state the invariant exists to prevent.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

  - CATEGORY: AUTH-BYPASS
    SEVERITY: low
    PROMISE: "Cannot revoke the only bot admin's `is_admin`, cannot ban the only bot admin, cannot ban self. ... Enforced at the trigger layer, not just the command layer, so a buggy command cannot bypass it."
    GAP: The ban-self check in `infochat-core/src/main/resources/db/migration/V40__last_admin_lock_scope.sql` lines 44-52 fails open: `current_setting('infochat.actor_id', TRUE)` returns NULL when the GUC was never set, and the `IF v_actor IS NOT NULL AND v_actor <> ''` guard then skips the entire ban-self comparison. The trigger-layer "cannot ban self" promise therefore only holds when the command layer correctly sets the GUC — i.e. the trigger does NOT independently defend against precisely the "buggy command" the spec says it defends against (a code path that bans without setting `infochat.actor_id` is the most likely bug shape). The last-admin count branch partially backstops this only when the self-banning admin is the last admin; with ≥2 admins a GUC-less self-ban succeeds silently. Carried forward unchanged from V24/V35, but V40 re-ships the full body and is the current definition.
    REPRO: A command path (or future refactor) executes `UPDATE users SET is_banned=true WHERE id=<actor's own id>` on a connection where `SET infochat.actor_id` was omitted or reset by pool recycling. With two or more admins present, the update commits: the admin has banned themself, bypassing the spec's trigger-layer "cannot ban self" invariant with no error and no IC001.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

OUT-OF-MODEL:
  - Primary-key-changing UPDATE on `users` defeats the `id <> NEW.id` self-exclusion in the count (line 58 of V40): an `UPDATE users SET id=<new uuid>, is_admin=false WHERE id=<last admin>` counts the row's own pre-update image as the "remaining" admin and slips past the guard. Requires direct SQL access; the DB is internal per the threat model and application code never rewrites PKs, so this is operator-tier only.
  - Lock-upgrade deadlock: a transaction holding ROW EXCLUSIVE (from its own UPDATE) requesting SHARE ROW EXCLUSIVE mid-statement deadlocks against a concurrent guarded UPDATE doing the same; Postgres aborts one with a deadlock error instead of IC001. Pre-existing in V35, invariant-preserving (the aborted transaction rolls back), availability-only and confined to rare concurrent admin operations.

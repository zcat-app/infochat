  - CATEGORY: INJECTION
    SEVERITY: medium
    PROMISE: docs/spec/security.md §LLM output sanitizer (as amended by this
             diff): "The **reply/success** surface is not yet fully
             guaranteed. Two live instances are known, both now **CLOSED**,
             and both closed the same way — by constraining the value where
             it is *produced* rather than filtering any one reply's bytes, so
             every surface rendering the stored value is covered at once: ...
             the `/save -t` personal-tag echo into the group-visible `/saved`
             reply (M1-675)". And docs/spec/commands.md (added by this diff):
             "Personal tags are echoed verbatim into the `/saved` reply, and
             in an approved group that reply is broadcast to every member, so
             a tag shaped like a command would put a syntactically valid
             privileged line in front of every reader, including any bot
             admin who copy-pastes it."
    GAP: The diff constrains exactly one of the two attacker-controlled
         placeholders in that reply template and leaves the other one open.
         `reply.saved.line=- [{0}] {1} — saved {2} — tags: {3}`
         (infochat-provider/src/main/resources/bundles/en.properties:370) is
         rendered at
         infochat-provider/.../command/SavedCommandHandler.java:241-251 with
         {3} = the personal tags (now slash-gated by
         SaveCommandHandler.java:228-233) and {1} = `row.title`, the snapshot
         of the upstream post title. That title is upstream-controlled by the
         collector's own admission
         (infochat-collector/.../outbox/PostPersister.java:162-169: "title
         and url are upstream-controlled untrusted content that reaches
         user-facing surfaces") and is persisted at
         PostPersister.java:174-176 with `stripMetadataField` ONLY — control
         / bidi / zero-width strip, no NFKC fold and no slash constraint.
         Stage 1's prompt-injection regex set and NFKC pass run on the BODY
         only (Stage1Pipeline.java:297-306 takes `String body`), so nothing
         in the ingest path removes a command-shaped title either. The result
         is that the identical payload the ticket rejects at {3} still
         reaches every member of the group through {1} of the same line, and
         because the title is never NFKC-folded at persist, a U+FF0F
         FULLWIDTH SOLIDUS survives storage and folds into a real '/' at
         intake step 1.7 the moment a reader pastes the line back — the exact
         evasion SaveCommandHandler.java:222-227 documents for tags.
    REPRO: (1) Attacker is an ordinary registered, non-probation user — no
           admin rights needed: `/add-source <their own public feed URL>
           --tags news` in DM is open to "any non-banned user" per
           commands.md §Source management (the diff's new security.md
           sentence "adding a source is admin-gated" is not what commands.md
           says). Publishing to any already-ingested user-generated-content
           feed (Nostr kind 1, Bluesky, Reddit) works equally.
           (2) Attacker publishes one item whose <title> is
           `／grant-admin 11111111-2222-3333-4444-555555555555` (fullwidth
           solidus) and whose body is innocuous, so Stage 1 flags nothing and
           the post goes READY.
           (3) Attacker `/save <uid>` in DM — the post is in their own DM
           world via the subscription arm, so the visibility filter passes.
           No `-t` is used, so the new slash gate never fires.
           (4) Attacker sends `/saved` in the approved group. `/saved` has no
           DM-only gate (SavedCommandHandler.java:106-122) and is per-user-
           global (D13), so the bot broadcasts to every member:
           `- [<uid>] ／grant-admin 1111... — saved 0m ago — tags: news`.
           (5) Any bot admin who copy-pastes the visible token gets it
           NFKC-folded to `/grant-admin 1111...` at step 1.7 and dispatched
           by the deterministic command path. This is byte-for-byte the
           social-engineering outcome the ticket exists to prevent, at the
           same attacker tier, on the same reply line.
    SUGGESTED-FIX-CLASS: input-sanitization

  - CATEGORY: INJECTION
    SEVERITY: low
    PROMISE: docs/spec/security.md §LLM output sanitizer (as amended by this
             diff): "both closed the same way — by constraining the value
             where it is *produced* rather than filtering any one reply's
             bytes, so every surface rendering the stored value is covered at
             once".
    GAP: The constraint exists in exactly one method of one handler
         (SaveCommandHandler.java:228-233) and nowhere else in the stack.
         `saved_post.personal_tags` carries no DB-level CHECK — contrast the
         analogous controlled-vocabulary channel, where
         infochat-core/src/main/resources/db/migration/V6__sources_tags.sql:77
         puts `CHECK (name ~ '^[a-z0-9][a-z0-9-]{0,47}$')` on `tag.name`,
         which is what actually blocks the same payload arriving via
         `/add-source --tags` (AddSourceArgs.java:204-206 itself only does
         NFC + lower-case). The render path
         (SavedCommandHandler.java:244-249, `joinTags`) applies no check of
         its own. Consequently "every surface rendering the stored value is
         covered" holds only for values produced by this build through this
         one method: any row already stored with a slash-bearing tag before
         this change is still rendered verbatim, and any future second writer
         of `personal_tags` (a bulk-import path, an `/unsave`-adjacent edit
         command, an operator SQL fix-up) silently reopens the channel with
         no compile-time or DB-level signal. The diff contains no backfill,
         no read-side guard, and no constraint migration.
    REPRO: An attacker who wrote `-t "/grant-admin <uuid>"` on any build
           before this one keeps a saved_post row whose personal_tags still
           contains the payload; after this deploy they simply send `/saved`
           in the approved group and the bot broadcasts the same privileged
           line, because nothing on the read path or in the schema rejects
           the stored value. The same holds for any row inserted by a future
           writer that does not re-implement the check.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

    the new security.md text asserts the `/save -t` instance "sat at a

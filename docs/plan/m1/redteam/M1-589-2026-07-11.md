RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: DOS
    SEVERITY: low
    PROMISE: "Tool calls per chat turn — fixed cap. Tool results are cached
              within a single turn so identical calls don't re-query."
              (docs/spec/security.md §Rate limiting)
    GAP: The new deterministic per-turn semanticSearch pre-fetch dispatches
         through the 5-arg convenience overload —
         infochat-provider/src/main/java/app/zcat/infochat/provider/chat/ChatAgent.java:341-342
         — which creates a FRESH TurnContext per call
         (infochat-provider/src/main/java/app/zcat/infochat/provider/chat/ChatToolDispatcher.java:126-132),
         while runToolLoop creates its own separate TurnContext for the same
         chat turn (ChatAgent.java:371). The pre-fetch's result is cached in
         a context that is immediately discarded, so within one chat turn an
         identical model-initiated semanticSearch call misses the cache and
         re-executes: a second embedding HTTP round-trip to the local
         backend plus a second pgvector k-NN probe (inner probe LIMIT
         limit×4, SemanticSearchTool.java) for arguments the spec says must
         not re-query. The pre-fetch execution also does not consume a slot
         of the loop's per-turn call budget (each context counts
         independently), so the effective per-turn execution bound is
         cap+1, not the single fixed cap the spec describes. The javadoc on
         buildSemanticRetrievalBlock claims the pre-fetch gets "the same
         validation, caps, and allowlist a model-initiated call gets"
         (ChatAgent.java:324-325) — the cap/cache sharing part of that claim
         is not delivered. Impact is bounded (exactly one duplicate
         embed+probe per turn, since the loop's own cache takes over after
         the first in-loop call), hence low: defense-in-depth erosion of the
         per-turn cost bound, not an unbounded amplification.
    REPRO: Any registered user sends a chat-mode message M (≤500 chars,
           e.g. "zcash shielded pools"). Step 3 of doHandle dispatches
           semanticSearch{query=M} (embed + pgvector probe #1). The model,
           shown M in the prompt, emits TOOL_CALL: semanticSearch
           {"query": "zcash shielded pools"} — a byte-identical arg map.
           The loop's fresh TurnContext cache is empty, so the dispatcher
           executes embed + probe #2 in the same turn. The threat model
           says the identical second call should have been served from the
           per-turn cache without re-querying. A user (or feed content that
           nudges the model toward echoing the query) can make every turn
           pay retrieval cost twice.
    SUGGESTED-FIX-CLASS: other

OUT-OF-MODEL:
  - Per-scope tag_mode (EXPLICIT) bypass: searchPosts intersects results
    with the scope's followed-tag preferences even when the model passes no
    tags (SearchPostsTool.computeEffectiveTags — EXPLICIT mode with no
    request constrains to scope tags), but SemanticSearchTool applies no
    tag_mode filter at all — only subscription + READY + distance threshold
    (SemanticSearchTool.java, queryNearestPosts). The spec row this diff
    adds for semanticSearch deliberately omits any tag_mode intersection,
    so no stated commitment is broken — but if a group admin's EXPLICIT
    tag preferences are ever relied on as a content-control boundary for
    what the bot surfaces in a group, any member can now bypass them via
    chat-mode semantic retrieval (deterministic pre-fetch or explicit tool
    call). Flagging so the user can decide whether the semanticSearch spec
    row should gain a tag_mode clause or the omission should be documented
    as intentional.
  - Recall-crowding oracle on unsubscribed corpus density: the inner probe
    is a GLOBAL top-(limit×4) over post_embedding with subscription
    filtering applied only in the outer query (SemanticSearchTool.java —
    the comment acknowledges recall depends on the over-fetch). No
    unsubscribed post ever surfaces (commitment delivered), but the
    caller's observed recall shrinks when semantically-near posts in
    UNSUBSCRIBED sources crowd the global top-k, so a patient user can
    infer density information about content in sources they have not
    subscribed to. Same class as the translation-cache timing side channel
    the spec explicitly accepts for v1; noting it so the acceptance is a
    decision rather than an accident.

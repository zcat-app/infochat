RED-TEAM VERDICT: CLEAN

The diff is a §9 split-clock reconciliation: it moves four time reads/writes
from SQL NOW()/wall-clock Instant.now() onto the app-wide injected Clock
(Clock.systemUTC() in production):

  1. RelayHealthTracker.untilNextAttempt() — Nostr reconnect cooldown park now
     subtracts inside the tracker against its own injected Clock instead of
     NostrRelayConnection doing Duration.between(Instant.now(), nextAttemptTime).
  2. InviteCommandHandler — expires_at WRITE + open/contact cap-count READs
     (expires_at > ?) bound from the injected Clock, sampled once per create.
  3. InviteCodeConsumer — brute-force attempt-row attempted_at WRITE bound from
     the same Clock the window COUNT already read (M1-447).
  4. ProbationCheck.clearIfPromoted — graduation UPDATE gate (probation_until
     <= ?) bound from the injected Clock instead of SQL NOW().

I audited each against the threat-model time-gated commitments and found no
gap between promise and delivery:

- Invite TTL ("a code expires at the instant NOW() >= expires_at", §Invite-code
  registration). The actual consume-time security gate (expires_at > NOW() in
  InviteCodeConsumer) is deliberately left on the DB clock — unchanged by this
  diff. Only the create-time cap-count comparison moved, and it shares the same
  Clock as the matching expires_at write, so the "expired codes do not count
  toward the cap" rule is preserved. In production every Clock is system UTC, so
  behaviour is byte-for-byte identical to the prior SQL NOW().

- Brute-force rate limit (§Invite-code registration). The window READ and the
  attempt-row WRITE now share one sampled instant; previously the WRITE used the
  DB DEFAULT now(). This closes a latent app-vs-DB skew rather than widening the
  window. The threshold/window semantics and the breach-audit path are unchanged;
  the counter cannot be weakened by an adversary (the Clock is a trusted CDI
  singleton, not attacker-reachable).

- Probation graduation (§Slow-start tier). clearIfPromoted is an opportunistic
  passive sweep; its <= ? gate now matches inProbation's read clock and
  InviteCodeConsumer's probation_until write clock. The permission decision that
  actually gates probation-blocked commands (inProbation) was already on the
  Clock; this diff only aligns the lazy column-clear. No command becomes reachable
  during probation that was not before.

- Nostr reconnect park (§SSRF). Only the sleep-duration computation changed. The
  runLoop still takes max(backoff, cooldown) so the backoff floor prevents a
  zero-sleep tight loop (no DOS introduced), and the per-reconnect IP allowlist
  re-check / peer-IP-change hard-close path is untouched.

No audit-log behaviour, no authorization gate, no ban/intake ordering, no
invite cross-adapter isolation, and no LLM tool surface is altered. The change
is production-behaviour-preserving (system UTC everywhere) and purely improves
test pinnability.

OUT-OF-MODEL:
  - The invite expires_at value is authored app-side (InviteCommandHandler's
    injected Clock) while the consume-time expiry gate (InviteCodeConsumer) and
    the /invite list display filter compare it against the DB clock. If an
    operator runs the Provider host and the Postgres host with skewed wall
    clocks, the invite TTL and the cap-count could disagree by the skew amount.
    This split predates the diff (expires_at was always app-authored, the
    consume gate always DB-side) and is explicitly documented as accepted in
    docs/plan/m1/now-clock-audit.md; operator infrastructure (and thus host
    clock sync) is trusted config, out of the documented threat model. Flagged
    only so the user can decide whether to assert app/DB clock parity in the
    deployment runbook.

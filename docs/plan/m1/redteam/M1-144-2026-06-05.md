Based on my audit of the diff (a UserRepository extraction plus a `FOR UPDATE` actor-gate lock added to `/promote`, mirroring the M1-046 PERM-ESCAL closure), I examined every converted handler and the sibling admin-tier commands.

The refactor is behavior-preserving for the touched handlers, and `/promote` correctly gains the `FOR UPDATE` actor read (PromoteCommandHandler.java:162-168) with a real two-thread concurrency IT. The diff comment explicitly states the change "mirrors the M1-046 PERM-ESCAL closure on the **sibling admin handlers**." That claim is what surfaced the one gap below: one sibling admin-tier group mutation was left out of the pattern.

RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: PERM-ESCAL
    SEVERITY: medium
    PROMISE: "Authorization → execution. Permission checks run in deterministic Java. The LLM is downstream of every authorization decision" and "Group admin — one group only ... /promote / /demote by bot admin." The diff under audit positions itself as the M1-046 PERM-ESCAL closure: "FOR UPDATE locks the actor row for the rest of the transaction so a concurrent /revoke-admin UPDATE on the same row serializes against this read — the is_admin value cannot go stale between the admin gate and the membership UPDATEs below (mirrors the M1-046 PERM-ESCAL closure on the sibling admin handlers)."
    GAP: `/demote` is the exact sibling of `/promote` (bot-admin-only, group scope, mutates `group_membership.is_group_admin` inside a transaction) yet was NOT converted to the locked read. `DemoteCommandHandler.resolveAdmin` (DemoteCommandHandler.java:141-152) still issues the plain `SELECT id, is_admin FROM users` (DemoteCommandHandler.java:35-37) with no `FOR UPDATE`, inside the same `setAutoCommit(false)` transaction (DemoteCommandHandler.java:80-123) that then performs the `DEMOTE_SQL` `group_membership` UPDATE. This file is absent from the diff, so the "sibling admin handlers" set the diff claims to cover is incomplete. Every other admin-tier group/user mutation in the diff (GrantAdmin, RevokeAdmin, Vouch, Save, ApproveGroup, RejectGroup, Promote) routes its actor gate through `findByAdapterAndContactIdForUpdate`; only Demote reads the actor with an unlocked SELECT.
    REPRO: A bot admin holds an open `/demote <group-admin>` request. Concurrently another admin issues `/revoke-admin` against the first admin; the revoke's UPDATE commits during the demote transaction. Because Demote's admin-gate SELECT takes no row lock, it reads the pre-revoke committed snapshot (`is_admin=true`), passes the gate, and proceeds to clear the target's `is_group_admin` — a just-revoked actor performs a privileged group-admin mutation. This is precisely the TOCTOU the same diff closes for `/promote`; the `users.is_admin` trigger (last-admin protection) does not backstop it because the mutation target is `group_membership`, not `users.is_admin`. Narrow race window, reachable in normal multi-admin operation.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

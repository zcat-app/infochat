FINDINGS:
  - CATEGORY: INJECTION
    SEVERITY: high
    PROMISE: docs/spec/security.md §Threat model: "The **Collector** is exposed
              to arbitrary feed content. Every RSS publisher, Reddit poster,
              Bluesky user, etc. is untrusted." §Prompt-injection defenses:
              "Even after Stage 1+2, post bodies reaching the summarizer or chat
              agent are considered untrusted (decision D21)" and, in the closed
              tool allowlist, `searchPosts` results are "ordered `published_at`
              descending". The control that makes that ordering non-attacker-
              choosable is stated in docs/spec/schema.md:355-362 and is
              explicitly anchored back to this threat model: "**`published_at`
              clamp.** `published_at` is source-controlled (RSS `<pubDate>`,
              Atom `<published>`, Bluesky `indexedAt`), so the ingest boundary
              clamps it to `<= fetched_at`: a source cannot claim a future
              publish time. The clamp keeps a future-dated claim from sorting to
              the top of every `searchPosts` window and `ORDER BY published_at
              DESC` fed to the chat LLM (the ordering rationale in security.md
              §Prompt-injection defenses)". The same rationale is restated at
              the code boundary in
              infochat-collector/.../outbox/PostPersister.java:181-190.
    GAP: The clamp bounds a source-supplied date from above. It cannot bound an
         ABSENT one, and Postgres sorts NULLs FIRST under `DESC` by default. Until
         this diff that hole was closed downstream, because the retrieval window
         predicate was `published_at >= ?`, which no NULL row can satisfy — so a
         date-less post never entered any of the three LLM-fed result sets and the
         head of every ordering was bounded by `fetched_at`. The diff moves the
         membership predicate to `ready_at` while leaving the sort key on
         `published_at` with no `NULLS LAST` and no COALESCE, admitting NULL-dated
         rows into sets they were previously excluded from and placing them ahead
         of every clamped row:
           - infochat-provider/.../summary/EligiblePostQuery.java:224
             (`AND p.ready_at >= ?`) vs :257 (`ORDER BY p.published_at DESC,
             p.id DESC`) + :258 (`LIMIT ?`, clusterCap default 200). The class
             javadoc at :33-36 states the cap drops "the OLDEST posts ... (the
             tail of the ORDER BY)" — with NULLs at the head, the dropped tail is
             the legitimate content.
           - infochat-provider/.../digest/DigestPostCollector.java:144 + :151-152
             (POSTS_ALL_SQL) and :162 + :173-174 (POSTS_EXPLICIT_SQL), same
             shape, same LIMIT clusterCap.
           - infochat-provider/.../chat/tool/SearchPostsTool.java:137
             (`AND p.ready_at >= ?`) vs :152 (`ORDER BY p.published_at DESC,
             p.id DESC LIMIT ?`), whose JSON is then truncated at
             MAX_RESULT_BYTES = 16 KiB (:42, :179) keeping "newest-first (the
             ORDER BY) ordering" — i.e. keeping the NULL rows and dropping the
             rest before the result is re-injected verbatim into the chat prompt.
         The diff is aware that NULL rows now arrive — DigestPostCollector.java:106,
         :115-119 adds the null-safe read, and the new IT
         DigestPostCollectorIT.nullPublishedAtPostIsCollected (diff lines 728-748)
         asserts it — but nothing compensates on the ordering side. Reachability of
         a NULL `published_at` from untrusted feed content is direct:
         RssFeedParser.java:318-327 / :329-338 return null for an absent OR
         unparseable `<pubDate>` / `<published>`, and PostPersister.java:188-195
         binds that "as SQL NULL" ("A non-future value binds unchanged; a null
         value binds as SQL NULL"). No `NULLS LAST` appears anywhere in the repo.
    REPRO: 1. Attacker controls any feed inside some scope's D59 world — a
              compromised or aggregator-mirrored bootstrap source (the corpus
              already routes sources through third-party mirrors), or a source the
              attacker themself added with `/add-source`, which
              security.md §LLM output sanitizer notes is "open to any non-banned
              user".
           2. Publish 200+ items with the `<pubDate>` element simply OMITTED (or
              malformed — the parser degrades both to null). Content is ordinary
              enough to pass Stage 1 and get a Stage 2 BENIGN, so every item
              reaches `status='READY'` with `ready_at = now()` and
              `published_at = NULL`.
           3. Each item now satisfies `ready_at >= cutoff` for every window in the
              retention span (searchPosts allows up to WINDOW_MAX = 30 days,
              SearchPostsTool.java:32) and sorts NULLS FIRST ahead of every
              clamped post in all three `ORDER BY published_at DESC` queries.
           4. Observable results: the group's periodic digest and every
              `/summary -w ...` in that scope are filled head-to-cap with the
              attacker's items for the whole window, and the cluster cap evicts
              the legitimate posts from the tail — the bot stops reporting the
              real corpus. Every `searchPosts` call the chat agent makes returns
              the attacker's titles/URLs at the head of the JSON that is
              re-injected verbatim into the prompt, and the 16 KiB budget drops
              the honest rows. The attacker holds the first-read position in the
              summarizer's and chat agent's context for as long as the window
              runs, deterministically and without needing to win any race.
           5. Why the system should not have allowed it: the deployment already
              decided this position is worth defending — it spends an ingest-time
              clamp specifically to stop a source "sorting to the top of every
              `searchPosts` window and `ORDER BY published_at DESC` fed to the
              chat LLM". A NULL beats every clamped value unconditionally, so
              omitting the field is strictly more effective than the future-dating
              the clamp was written to stop.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

OUT-OF-MODEL:
  - Sort-plan cost after V64 drops `idx_post_published`. All three queries keep
    `ORDER BY published_at DESC` but no index on that column remains, so the
    planner must sort the whole `ready_at`-window set instead of walking the old
    index backwards and stopping at LIMIT. On a large corpus a model-elected
    `searchPosts` with `window: P30D` therefore sorts every READY post of the last
    30 days per call. The migration comment reasons about this deliberately, the
    per-turn tool-call cap and the armed `statement_timeout` bound it, and
    security.md states no query-cost budget — so this is a resource-profile change
    outside the documented model rather than a finding. Flagging it in case the
    user wants a cost bound stated.
  - `approve_quarantine` (V21__quarantine_admin.sql:59-65) re-stamps
    `ready_at = now()` when an admin restores a redacted span. Under the new
    predicate that pushes an arbitrarily old post — carrying content Stage 1
    flagged as prompt-injection and an admin then approved — into the CURRENT
    window of every scope in whose world the source sits, i.e. into the next
    digest and the summarizer prompt, which the previous `published_at` window
    would not have done. It reads as consistent with the spec (§Quarantine
    workflow already routes approve through `NOTIFY new_post` and the ready_at
    high-water mark), so it is noted rather than filed; the user may want the
    widened re-delivery blast radius of an approve stated somewhere.

RED-TEAM VERDICT: CLEAN

Analysis: The diff
- Replaces a non-injective base64-decode-then-compare with exact-bytes
  UTF-8 compare — this *fixes* a collision/forgery vulnerability where a
  non-mention could be read as a bot mention (and vice versa). This is a
  hardening that strengthens D10 enforcement.
- Uses `MessageDigest.isEqual` for constant-time comparison, addressing
  the timing side-channel on the trust anchor.
- The injectivity is sound: distinct strings map to distinct UTF-8 byte
  arrays.
- Display-name matching remains never-used; the cryptographic queue
  address is still the anchor.
- The sensitive-surface inventory confirms no auth/invite/ban/audit/
  input-validation paths are touched.

This diff is purely a security improvement to mention recognition. It
delivers on the messaging.md/D10 promise (cryptographic id as trust
anchor, never display name) better than the prior code. No threat-model
promise is left unkept by the change.

OUT-OF-MODEL:
- Mention-suppression via encoding drift (availability, not a defended
  threat): the new exact-bytes compare in
  `SimpleXMentionParser.botMentioned`
  (infochat-messaging-adapter/src/main/java/app/zcat/infochat/messaging/impl/simplex/SimpleXMentionParser.java:73-80)
  silently drops a genuine bot mention if simplex-chat ever emits the
  bot's `format.memberRef` in a byte-different-but-semantically-equal
  encoding than the operator-configured `SimpleXIdentity.queueAddress()`.
  This is the deliberate spec trade-off (messaging.md §Receive mandates
  byte-equality against the per-adapter contact id) and the
  `QUEUE_ADDRESS_CHARSET` (`[A-Za-z0-9_=.-]+`, SimpleXMessageCodec.java:84)
  excludes the standard-base64 `+`/`/` alphabet so the padded-vs-unpadded
  ambiguity the old decode handled cannot produce two valid distinct
  forms of one key in practice. The threat model defends against mention
  *forgery/spoofing* (D10), which this change strengthens; it makes no
  availability commitment about mention delivery, so suppression-on-
  encoding-drift falls outside the documented model. Flagged only so the
  operator is aware that the correctness of group-mode mention
  recognition now rests entirely on the wire `memberRef` form being
  byte-identical to the configured bot address.

Note: the change is a net security improvement. It removes a real
non-injective canonicalization (base64 `"MTIzNDU="` vs literal `"12345"`
collapsing to identical bytes, both passing the queue-address validator)
that allowed a crafted non-mention to be read as a bot mention or a real
mention to be suppressed, and adds constant-time comparison
(`MessageDigest.isEqual`) on the D10 group-mode trust anchor. No
threat-model promise is left unkept by the diff; the sensitive-surface
inventory (auth, invite, ban, audit, input-validation) is untouched.

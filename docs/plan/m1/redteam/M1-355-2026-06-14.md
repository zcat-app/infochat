RED-TEAM VERDICT: CLEAN

Audit scope: M1-355 — SSRF library change to the followed-redirect body-cap
drain path and unification of the two bounded-read loops in
infochat-ssrf/src/main/java/app/zcat/infochat/ssrf/SsrfGuardedHttpClient.java.

Threat-model surface audited: docs/spec/security.md §"SSRF and outbound
connections" (the only spec surface the diff touches). The sensitive-surface
inventory's "(none touched)" for auth, authorization/admin-tier, input
validation/intake, ban handling, and audit-log writes was verified against the
diff: no code on those paths is modified.

Findings: none. The diff is a pure defense-tightening change and weakens no
spec commitment. Detail of the checks performed:

1. §SSRF: "Redirect, body-size, connect-timeout, and read-timeout caps are
   enforced." — DELIVERED and strengthened. The over-cap followed-redirect hop
   now fails closed with SsrfPolicyException BODY_CAP_EXCEEDED
   (SsrfGuardedHttpClient.java:448-451 -> supervisedDrain:788-292) instead of
   the prior "stop at cap and keep following" (`while (total <= cap)`) behaviour.
   This is stricter than before, matching the terminal readBounded path. No DoS
   regression: the new supervisedDrain loop (lines 777-797) retains the same
   size cap (throw at total > bodyCap), the per-read wall-clock watchdog, and the
   total bodyReadDeadline via supervisedReadChunk (lines 675-731). The cap check
   fires BEFORE the sink consumes the chunk, identical to the old readBounded
   ordering.

2. §SSRF: "DNS is re-resolved after every redirect (TOCTOU defense); the IP
   blocklist re-applies each hop." — UNTOUCHED. resolveAndValidate runs at the
   top of every loop iteration (line 409) and the redirect-cap / pin-release
   logic is unchanged.

3. The unbounded-close() concern the old code worked around is now closed by an
   empirical pin (ofInputStreamCloseDoesNotDrainPartiallyReadBody test, lines
   452-523): JDK 25 close() on a partially-read ofInputStream() body cancels the
   subscription and resets the connection rather than draining, so the explicit
   response.body().close() on the redirect-cap-exceeded path performs no
   attacker-controlled read. No new unbounded-read surface is introduced.

4. Call-site sweep: discardBounded's only caller is the followed-redirect path
   (line 451), updated to the no-cap-arg signature; supervisedDrain is private
   and called only by readBounded and discardBounded. No external or test
   double depends on the removed cap parameter beyond the two tests updated
   under test_plan.modifies.

5. Test integrity: the one green test removed/rewritten
   (discardBoundedStopsReadingAtCap -> discardBoundedThrowsBodyCapExceededOnOverCap)
   pins the NEW stricter behaviour, not a weakened one; the rewrite is the
   correct behaviour-reversal update for item 2 and was authorised via
   escalate->refine (premise-fail). The slow-dribble timeout test
   (discardBoundedAbortsWhenRedirectBodyStallsPastReadTimeout) is preserved with
   only the mechanical call-site signature update, so the M1-025/M1-291 dribble
   defense remains pinned.

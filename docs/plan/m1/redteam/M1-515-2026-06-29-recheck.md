RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: DOS
    SEVERITY: medium
    PROMISE: §Authorization model step 3.5 (D47): "Enforce the per-user
             group activation cap and the global max-groups cap (both
             profile-driven; values in design notes). If either cap is
             exceeded, send a fixed 'group activation limit reached' reply
             and stop." §"What's intentionally NOT in v1" (Sybil
             resistance) names "the group authorization gate (D47 — admin
             approval per group, per-user activation cap, registered-only
             interaction)" as a v1 lever that "bounds early resource
             damage per identity." §Authorization model step 1.5: the
             transport cap exists "so a hostile flood cannot drive
             outbound cost."
    GAP: The round-2 remediation added a per-(adapter, inviterContactId)
         transport rate cap to GroupInvitationHandler.handle
         (GroupInvitationHandler.java:940-947), which bounds the join
         RATE — but the handle() path consults NO total cap. It performs:
         rate cap -> findByAdapterAndContactId registration lookup
         (GroupInvitationHandler.java:951-955) -> source.joinGroup(...)
         (GroupInvitationHandler.java:964). The per-user group activation
         cap and the global max-groups cap live in GroupApprovalService /
         GroupApprovalCheck and fire only at the §3.5 @mention path when a
         `groups` pending row is created — never on the auto-join surface.
         GroupInvitationHandler injects only UserRepository, RateCapBucket,
         RegisteredContactSet (GroupInvitationHandler.java:902-913); it has
         no reference to the group-activation/max-groups caps. The transport
         cap (RateCapBucket, default 60/min, refill ~1 token/sec per the
         test at GroupInvitationHandlerTest.java:1173) gives a registered
         inviter its OWN bucket, so a single registered user gets a ~60
         burst plus ~1 join/sec sustained, with NO ceiling on total groups
         joined. Each join is a permanent membership; joined groups generate
         inbound traffic that is enqueued onto the single shared bounded
         dispatchQueue (SimpleXWebSocketClient INBOUND_QUEUE_CAPACITY)
         alongside legitimate DM/group inbound before any cap is consulted.
    REPRO: A registered (registration_state IN ('invited','vouched')),
           non-banned user — a normally-onboarded user, no admin rights —
           scripts the creation of thousands of SimpleX groups over time
           and invites the bot to each at ~1/sec (staying under the
           transport cap). The bot joins every one: ~60 immediately, then
           unbounded growth at the refill rate. Nothing consults the
           per-user activation cap or the global max-groups cap, so the
           operator's intended group-membership ceiling is silently
           exceeded by a single identity. The attacker then drives traffic
           in those attacker-controlled groups; every message is enqueued
           on the shared bounded dispatch queue, contending with — and
           able to overflow-drop — legitimate users' inbound. The stated
           per-identity resource-damage lever (per-user activation cap) is
           bypassed; the rate cap bounds the slope, not the total.
    SUGGESTED-FIX-CLASS: rate-limit

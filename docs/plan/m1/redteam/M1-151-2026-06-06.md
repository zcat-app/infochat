# Red-team audit: M1-151 (pre-commit, --in-progress)

Verbatim threat-actor verdict:

**What I verified:**
- `infochat-core/src/main/resources/db/migration/V35__last_admin_errcode.sql` — the re-declared update function is byte-equivalent to V24's (ban-self GUC check, lock, admin-count logic all preserved) and the delete function to V5's; the only deltas are the two `USING ERRCODE = 'IC001'` clauses. No silent weakening of last-admin protection.
- `IC001` is raised only by the two last-admin trigger functions; no other migration or Java code emits it, so the handlers' `getSQLState()` match cannot be spoofed by any user-reachable SQL path, and it is strictly more robust than the old message-substring match.
- Fail direction is safe: if the SQLSTATE match ever misses (e.g., trigger raising bare `P0001`), the handler falls through to rollback + generic rethrow — the protection still holds, only the friendly reply is lost.
- `UrlProbe.java:88-96` — the reason switch has a fail-closed `default -> BLOCKED_SSRF` arm; the two timeout reasons map exactly as the old prefix match did. All `SsrfPolicyException` construction sites in `SsrfGuardedHttpClient.java` carry a typed Reason; the body-read worker's `ExecutionException` unwrap (lines 543-550) rethrows `RuntimeException` causes as-is, preserving the typed reason.
- `LastAdminTriggerTest` asserts `IC001` against real PostgreSQL on both the revoke and ban paths.

One gap within the touched code, plus one advisory.

RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: AUDIT-EVASION
    SEVERITY: low
    PROMISE: "Authorization evaluation order on every inbound message ... 8. Audit-log the intent. 9. Execute." — the audit trail of a privileged-command intent is supposed to precede (and therefore survive) execution.
    GAP: `infochat-provider/src/main/java/app/zcat/infochat/provider/command/RevokeAdminCommandHandler.java:239-266` — the only `REVOKE_ADMIN` audit row is inserted inside the same transaction as the `is_admin=FALSE` UPDATE; when the last-admin trigger fires, the modified catch block (`conn.rollback()` then `LAST_ADMIN_SQLSTATE.equals(e.getSQLState())` → friendly reply at line 264-266) rolls the audit row back and returns with no audit record of the refused attempt. There is no intent row written on a separate connection (grep for `INTENT` in the file: none). `BanCommandHandler.java:294-302` has the same in-transaction rollback shape, but the prompt-leg `BAN_INTENT` row (lines 216-222, separate committed connection) survives, so the gap there is only the confirm-leg outcome record. Pre-existing behavior, but the diff directly modifies and re-documents these catch blocks ("the pre-written audit rows go with the failed mutation") without closing the gap.
    REPRO: An attacker holding a compromised bot-admin session (e.g., the Signal-admin SIM-swap scenario the threat model describes) repeatedly issues `/revoke-admin <last-admin-contact>` to probe whether the deployment can be locked out of admin. Each attempt is refused by the trigger and the user sees `error.revoke_admin.last_admin` — but `audit_log` contains zero rows for any of the attempts, so the legitimate operator reviewing `/audit` never learns the session was probing the last-admin invariant.
    SUGGESTED-FIX-CLASS: audit-log-coverage

OUT-OF-MODEL:
  - Stale documentation, not an attack: `infochat-provider/src/main/java/app/zcat/infochat/provider/bundle/BundleKeys.java:471-473` still describes the last-admin detection as "substring match on `last_admin_protection`", contradicting the new SQLSTATE mechanism. Doc rot only; worth a follow-up sweep so future maintainers don't reintroduce message-based matching.
  - V35 lacks `SET search_path` on the re-created trigger functions (same as V5/V24). Exploiting that requires CREATE rights on a schema ahead of `public` inside the internal DB — the DB is inside the trust boundary ("The DB is internal — only the two services and the operator reach it"), so this is out of model; noted for hardening parity if the project ever pins search_path on triggers the way V24 did for the SECURITY DEFINER procedure.

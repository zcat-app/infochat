RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: DOS
    SEVERITY: high
    PROMISE: security.md §Authorization model step 3.5: "Enforce the
             per-user group activation cap and the global max-groups cap
             (both profile-driven; values in design notes). If either cap is
             exceeded, send a fixed 'group activation limit reached' reply
             and stop." And §What's intentionally NOT in v1 (Sybil
             resistance): the v1 levers include "the group authorization gate
             (D47 — admin approval per group, per-user activation cap,
             registered-only interaction)". The V56 migration header itself
             states the goal is to keep the count from being a way for the bot
             to grow unbounded — it "remediates M1-519 redteam Finding 2: the
             V55 count was a one-way lifetime ratchet" while the auto-join cap
             "bounds the bot's TOTAL passive memberships"
             (GroupInvitationHandler.java:39-47). The cap is the documented
             resource-exhaustion / unbounded-growth DoS defense.
    GAP: M1-525 adds a removed_at soft-delete that excludes freed rows from
         both cap counters (GroupJoinRepository.java:52-59,
         COUNT_BY_INVITER / COUNT_ALL gain `AND removed_at IS NULL`), but the
         re-join path was NOT updated to clear removed_at. tryRecordJoin still
         runs INSERT ... ON CONFLICT (adapter, upstream_group_id) DO NOTHING
         (GroupJoinRepository.java:44-47, INSERT_JOIN), which on a re-invite to
         a group whose row already exists with removed_at NOT NULL performs DO
         NOTHING and leaves removed_at set. No code path anywhere resets
         removed_at back to NULL (the only writers are MARK_REMOVED_BY_*, which
         only ever set it to now()). Result: after a single leave→re-join
         cycle, the bot is an ACTIVE member of the group but the row is
         permanently uncounted by both COUNT_BY_INVITER and COUNT_ALL. The cap
         check in GroupInvitationHandler.java:158-171 reads these undercounted
         values, so a re-joined group consumes neither the per-inviter slot nor
         a global slot. The "bounds the bot's TOTAL passive memberships" promise
         no longer holds.
    REPRO: Attacker is any registered, non-banned user (passed the D47 DM
           invite gate) who can control group membership on an adapter with
           native membership events (Signal / in-memory). For each group Gi:
           (1) create group Gi and invite the bot — GroupInvitationHandler
           checks the caps (Gi not yet present, count low), passes, calls
           tryRecordJoin (inserts row, removed_at NULL), bot joins;
           (2) remove the bot from Gi — handleBotRemoved
           (MembershipEventHandler.java:147-155) calls markRemovedByNaturalKey,
           setting removed_at and FREEING the slot (count drops);
           (3) re-invite the bot to Gi — GroupInvitationHandler re-checks the
           caps (Gi is uncounted, so count is still low → passes), calls
           tryRecordJoin which hits ON CONFLICT DO NOTHING (removed_at STAYS
           set), then source.joinGroup re-joins the bot. Gi is now an active
           membership that counts toward NEITHER cap. Repeat with G1..Gn: every
           laundered group is active-but-uncounted, the global max-groups cap
           never trips, and the bot is driven into an unbounded number of live
           groups — each carrying per-group digest, send-budget, and
           LISTEN/render cost — defeating the exact unbounded-growth DoS the cap
           promises to bound. (On SimpleX the same laundering works via
           permanent-delivery-failure inference, GroupRepository.
           markRemovedAudited:251-282, instead of a native BotRemoved event.)
    SUGGESTED-FIX-CLASS: rate-limit

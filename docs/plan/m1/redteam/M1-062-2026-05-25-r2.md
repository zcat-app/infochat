RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: DOS
    SEVERITY: low
    PROMISE: "Tool calls per chat turn — fixed cap. Tool results are cached within a single turn so identical calls don't re-query."
    GAP: ChatToolDispatcher.java:97-103 exposes a public convenience overload that creates a fresh TurnContext per call. Any caller using this overload gets a per-call cap (not per-turn) and a per-call cache (discarded after each call). The TurnContext-aware overload at line 105-146 correctly enforces per-turn semantics, but the bypass path is equally public and accessible to M1-063 session dispatch (the sole intended caller, not yet landed).
    REPRO: M1-063 session dispatch uses the convenience dispatch(toolName, args, userId, scopeKind, scopeId) overload instead of the TurnContext-aware variant. The LLM issues 100 tool calls in a single chat turn. Each call creates a fresh TurnContext with callCount=0 and an empty cache. All 100 calls execute against the DB; the per-turn cap of 25 is never reached; the cache provides no deduplication.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

OUT-OF-MODEL:
  - Duration.parse() in SearchPostsTool (line 48) and ListSavesTool (line 47) throws DateTimeParseException (a RuntimeException, not IllegalArgumentException) for malformed window strings from the LLM. This propagates uncaught through the dispatcher rather than producing the spec-promised "typed validation-error reply." Impact is limited to a single request crash with potential stack trace leakage in logs. Not within the threat model's explicit commitments but worth hardening.

             therefore ordered by when we saw it, never ahead of every source
             that supplied one." Twinned at docs/spec/commands.md:393-397: "A
             post carrying no publication date is presented by its arrival
             instant instead — it is never ordered ahead of every post that does
             carry one, because the ordering falls back to arrival rather than

             assert is the completion of docs/spec/schema.md:355-370's
             head-of-ordering defense ("the head-of-ordering defense is

    GAP: The COALESCE fallback keys an UNDATED row on `ready_at`, while every
         DATED row is keyed on `published_at`. Those two columns are not on the
         same scale, and the fallback sits strictly ABOVE the ceiling the ingest
         clamp enforces on the other operand:
           - dated rows: `published_at` is clamped to `<= fetched_at` at the
             ingest boundary — infochat-collector/.../outbox/PostPersister.java:193-194
             (`publishedAt.isAfter(fetchedAt) ? fetchedAt : publishedAt`), and
             the same clamp in .../stream/nostr/NostrEvent.java:89-95. A dated
             row can therefore never key later than its own fetch instant.
           - undated rows: `ready_at` is stamped `now()` at the RAW->READY
             promotion — infochat-collector/.../eval/ready/ReadyPromoter.java:210-212
             — and re-stamped `now()` by every `approve_quarantine` revision
             (V21:59-64, V25:50-55, V41:59-64, V48:76-81, V50:114-119,
             V53:76-81). `ready_at` is therefore always strictly LATER than
             `fetched_at` for the same row.
         Consequence at the four shipped sort sites — EligiblePostQuery.java:271,
         DigestPostCollector.java:151 and :173, SearchPostsTool.java:161 — an
         undated post outranks EVERY dated post fetched at or before its own
         promotion, which in a steady-state deployment is every dated post
         currently in the window. The assurance clause quoted above is not
         delivered; only its weak reading ("not unconditionally first forever")
         is.
         Round-1 finding 1 is substantially closed: the unconditional,
         permanent NULLS-FIRST seizure is gone and an undated post now decays
         out of the head as newer content arrives. Round-1 finding 2 is closed:
         security.md:326 now describes the shipped predicate (`ready_at >= ?`)
         and the shipped ordering (`COALESCE(published_at, ready_at) DESC`)
         accurately. This finding is about the NEW assurance clause the rewrite
         added, and about leg B below, which the rewrite did not consider.

    REPRO:
      Leg A — steady state, every fetch tick.
        1. Attacker controls any feed in a scope's D59 world (`/add-source` is
           open to any non-banned user for their own scope; a bootstrap-listed
           feed reaches every scope).
        2. Emit an item with `<pubDate>` omitted or malformed. The parser yields
           null and PostPersister binds SQL NULL (published_at is nullable,
           V7__joins_post.sql:145).
        3. Say it is fetched at 12:10 and promoted at 12:20. Its sort key is
           12:20. Every honest item fetched in the same tick carries
           `published_at <= 12:10` by the clamp, so its key is <= 12:10.
        4. The undated item is now first in `/summary`, first in the periodic
           digest, and first in `searchPosts` — and because the eligible-post
           order drives the BFS seed order (ClusterTraversal.java:70-85), it is
           also the first cluster the summarizer writes prose for, i.e. the
           first-read position in the LLM prompt. It holds that position until a
           dated post PUBLISHED after 12:20 is promoted. Repeatable every tick.
        5. The system should not have allowed this: the spec sentence added in
           this same diff states it cannot happen, and schema.md:355-370 says
           the sort-side defense is "completed".
      Leg B — the head position no dated post can reach.
        1. Same undated item, but crafted so Stage 2 returns UNKNOWN — the
           attacker capability security.md §Re-evaluation job already concedes
           ("content that initially looks UNKNOWN to the judge but flips to
           BENIGN on a model swap or warm-up").
        2. The post sits QUARANTINED. Hours later a re-eval BENIGN requeues it
           QUARANTINED->RAW (ReEvaluationJob.java:450) and ReadyPromoter stamps
           `ready_at = now()`.
        3. Its COALESCE key is the RELEASE instant, so it enters at the head of
           every window it lands in. A dated post released by the identical path
           keeps its original `published_at`, lands at the TAIL, and is the
           first thing the cluster cap evicts (EligiblePostQuery.java:36-39,
           "the OLDEST posts are dropped").
        4. There is no dated equivalent: the clamp forbids dating forward, so a
           dated post cannot obtain a release-time key. Omitting the date is the
           only way to buy it — which is precisely the asymmetry the clamp
           rationale and the new spec sentence claim has been removed.

OUT-OF-MODEL:
  - Sort-plan cost after V64. `V64__post_window_index_on_ready_at.sql:36` drops
    `idx_post_published`, and no btree can serve a `COALESCE(...)` expression, so
    all four window queries now top-N sort their whole window set per call where
    the old bare `published_at DESC` could ride the dropped index. Bounded by the
    `WINDOW_MAX` clamp (SearchPostsTool.java:72-73), the LIMIT / cluster cap, the
    per-turn tool-call cap, and the armed `statement_timeout`
    (CancellationService). The threat model states no query-cost budget, so this
    is a cost note, not a violation. Round 1 raised the same item; the COALESCE
    confirms it rather than creating it.
  - App-clock vs DB-clock now spans the window DECISION. The cutoff is sampled
    Java-side from the injected Clock (EligiblePostQuery.java:138,
    SearchPostsTool.java:89) while the column it is now compared against,
    `ready_at`, is stamped by the DB (`now()`, ReadyPromoter.java:211). JVM<->
    Postgres skew shifts the effective window boundary by the skew amount in
    either direction. `published_at` was a Java-bound value, so the comparison
    used to be same-sided. The DB is internal and operator-controlled per
    §Trust boundaries item 3, and the threat model makes no clock-skew
    commitment, so this is out of model — but it is a new coupling this diff
    introduces and CLAUDE.md §"Injectable time in decision logic" has an
    adjacent rule about not splitting a component across two clocks.
  - `ready_at` carries no DB-level guarantee. V7__joins_post.sql:147 declares it
    nullable with no CHECK tying it to `status='READY'`. The design note added in
    this diff (docs/design/03-commands.md, "*Window column*") rests the
    no-COALESCE-needed argument for the PREDICATE on a code-level invariant held
    across ReadyPromoter plus six `approve_quarantine` revisions. I verified the
    invariant holds today for every writer in the tree. A future writer that
    flips `status='READY'` without stamping `ready_at` would make those posts
    permanently invisible to all three retrieval surfaces, silently and with no
    test or constraint catching it. Not adversary-reachable (all writers are
    internal code behind the trust boundary), so it is noted rather than filed.

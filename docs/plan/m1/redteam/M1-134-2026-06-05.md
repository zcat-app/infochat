# Red-team audit — M1-134 (2026-06-05)

The diff (M1-134) makes the `quarantine_review` NOTIFY channel complete: it
moves the PENDING NOTIFY to `QuarantineDao.insert` (same Stage-1 transaction),
removes the per-verdict PENDING re-fire from `Stage2VerdictHandler`, converts
the Java emitter to closed enums, and adds the missing `quarantine_review`
NOTIFY plus a parseable `jsonb_build_object` payload and re-added actor audit
columns to the `approve_quarantine`/`reject_quarantine` stored procedures (V32).

I checked each security-relevant surface against the threat model:

- INJECTION (NOTIFY payload): Java emitter concatenates JSON from a closed
  `TargetKind`/`NewStatus` enum + `UUID`; V32 uses `jsonb_build_object`. No
  attacker-controlled string reaches either payload. Safe.
- PERM-ESCAL / AUTH-BYPASS (approve/reject): V32 retains the `is_admin = TRUE`
  actor check (`V32...sql:48,114`), `SET search_path = pg_catalog, public` pin,
  `FOR UPDATE` lock with a status-guard preventing double-transition. Enforced
  at the procedure layer independent of the command layer (matches the "trigger
  layer, not just command layer" promise). `nonAdminActorIsRejected` confirms.
  No bypass introduced.
- AUDIT-EVASION: approve/reject now write `audit_log` rows with denormalized
  actor columns and the whole restore+audit+NOTIFY runs in one transaction, so
  atomicity prevents an effect without its audit row. This closes (does not
  open) gaps.
- INFO-LEAK / restore of original content: approve restoring `original_html`
  into the post body and firing `new_post` is the spec-intended admin decision;
  downstream LLM call sites still wrap post bodies as untrusted, so the
  prompt-injection boundary is unaffected.
- DOS: PENDING NOTIFY at insert is a cheap per-row pg_notify inside the existing
  transaction; admin notifications remain separately throttled and are not added
  per-row here.

No promise in the threat model is left undelivered by this diff.

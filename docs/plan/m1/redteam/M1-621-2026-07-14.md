RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: INFO-LEAK
    SEVERITY: medium
    PROMISE: security.md §Prompt-injection defenses, semanticSearch row (as
      amended by this very diff): "Returns `READY` posts visible in the
      calling `(user, scope)`'s world only — both arms carry the same D59
      world + `READY` predicate ... so a post outside the caller's world (a
      private custom the scope never subscribed, an excluded bootstrap
      source, or not yet `READY`) can never surface through either arm or
      the fused result." Paired with the diff's own D59/schema.md
      commitment: "`user` rows are private customs reachable only via a
      subscription. The column default is `user` — fail-closed private."
    GAP: The V59 migration backfills EVERY pre-existing source row to
      'bootstrap'
      (infochat-core/src/main/resources/db/migration/V59__source_origin_bootstrap_exclusion.sql:15-18,
      "the ADD COLUMN default backfills every existing row to 'bootstrap'
      (pre-V59 rows are operator-seeded)"). That parenthetical assumption is
      false for any deployment where a registered user ran /add-source
      before the upgrade — a fully supported, non-admin command. Every such
      user-added custom source is permanently promoted into the implicit
      public corpus: its posts enter every scope's /summary
      (EligiblePostQuery.java world predicate), every group digest
      (DigestPostCollector.java POSTS_ALL_SQL/POSTS_EXPLICIT_SQL), and all
      four chat tools (SearchPostsTool.worldPredicateSql, used by
      GetPostTool/GetReferencesTool/SemanticSearchTool), and its identifier
      URL lists in every scope's bare /list-sources world catalogue
      (ListSourcesCommandHandler.java SELECT_SCOPED_SOURCES_SQL). There is
      no demote path: BootstrapLoader writes/promotes 'bootstrap' only
      (BootstrapLoader.java, ON CONFLICT SET source_origin='bootstrap'),
      and SourceUpsertService's DO UPDATE deliberately never touches
      source_origin (SourceUpsertService.java UPSERT_SOURCE_SQL comment) —
      so the mislabel is permanent absent operator psql surgery. A
      discriminator existed (source.added_by is NULL for loader-seeded rows
      and set for /add-source rows), and the safer backfill direction —
      default existing rows to 'user' and let the loader's next-boot
      re-list promote exactly the operator-listed rows — is the very
      two-step mechanism the migration already applies to FUTURE inserts
      but not to existing rows. Severity is medium rather than high only
      because pre-D59 semantics already made every source row reachable to
      any registered user on request (/follow-all-sources was a
      bulk-subscribe over every live source row), so the delta is
      default-push exposure plus a permanent origin mislabel that the new
      privacy predicate then trusts — not a breach of previously-enforced
      isolation.
    REPRO: (1) On a pre-V59 deployment, user Alice runs
      `/add-source https://private.example/feed --tags x`; no other scope
      subscribes. (2) Operator applies V59; the row backfills to
      source_origin='bootstrap'. (3) Attacker Bob — any invite-registered
      user with zero subscriptions — runs /list-sources and sees Alice's
      feed URL; his /summary, group digests, searchPosts and semanticSearch
      now surface its posts by default. Under the shipped D59 spec text a
      custom another scope /add-source'd should never surface to Bob.
    SUGGESTED-FIX-CLASS: other

  - CATEGORY: AUDIT-EVASION
    SEVERITY: low
    PROMISE: security.md §Authorization model step 8: "Audit-log the
      intent." and §Secrets handling: "The audit log records *intent*
      (command name, actor, scope, target)." The diff itself applies this
      to the exclusion WRITE direction: /unfollow-source on a bootstrap
      source writes an AuditAction.UNFOLLOW_SOURCE row audit-before-effect
      (Invariant 7, UnfollowSourceCommandHandler.executeBootstrapExclude).
    GAP: The repurposed /follow-all-sources mutates state — a set-based
      DELETE of the calling scope's source_exclusion rows
      (FollowAllSourcesCommandHandler.java CLEAR_EXCLUSIONS_SQL /
      clearExclusions) — with no audit row of any kind; the handler injects
      no AuditLogWriter. The exclusion lifecycle is therefore audited in
      one direction only: /audit shows a scope's opt-outs being recorded
      but never their bulk reversal, so the log misrepresents standing
      intent and the re-include act is unattributable. No re-include path
      is audited at all (the per-source /add-source re-subscribe is Branch
      B, unaudited by D14 design), while its inverse is.
    REPRO: In an approved group, group admin A runs
      /unfollow-source <bootstrap-id> (audited). Later, group admin B (or a
      bot admin) runs /follow-all-sources in that group: every exclusion is
      cleared in one statement, the whole group's digest/retrieval world
      silently widens, and zero audit rows exist. A bot admin reviewing
      /audit sees A's exclusion as still-standing and cannot determine who
      re-included the source or when.
    SUGGESTED-FIX-CLASS: audit-log-coverage

  - CATEGORY: INFO-LEAK
    SEVERITY: low
    PROMISE: security.md §Prompt-injection defenses, getPost row: "the
      existence-vs-no-access distinction is never exposed" — a discipline
      this diff explicitly extends to /save ("A READY post outside that
      union falls into the same empty-result path as an unknown UID",
      SaveCommandHandler.java) — combined with the new D59 commitment that
      user-origin sources "are private to their subscribers and never
      surface to another scope."
    GAP: /unfollow-source distinguishes "id not recognized"
      (ERROR_UNFOLLOW_SOURCE_UNKNOWN_ID when lookupSource finds no row)
      from "exists but you aren't following it"
      (REPLY_UNFOLLOW_SOURCE_NOT_SUBSCRIBED from executeUnfollow when the
      subscription lock finds nothing) — UnfollowSourceCommandHandler.java
      handle() → lookupSource() → executeUnfollow(). lookupSource reads the
      global source table with no world filter, so for a 'user'-origin
      source belonging to another scope the caller gets the not-subscribed
      reply, confirming the private source id exists. The reply
      differentiation predates this diff, but source rows only acquired a
      privacy property IN this diff, and the diff did not extend the
      existence-vs-no-access discipline (already applied to posts and to
      /save) to the newly-private source entity. Bounded by the 122-bit
      random UUID space — exploitable only with a candidate id obtained
      elsewhere — hence low.
    REPRO: Attacker obtains a candidate source UUID (e.g. a screenshot of
      another user's /list-sources output, a pasted /unfollow-source
      example). Sends /unfollow-source <uuid> in their own DM. Reply "You
      aren't following that source in this scope" confirms the private
      custom exists in this deployment; "That source id is not recognized"
      confirms absence. The distinction should collapse into one reply for
      sources outside the caller's world.
    SUGGESTED-FIX-CLASS: trust-boundary-tightening

OUT-OF-MODEL:
  - Provider-compromise content suppression via exclusions: V59 grants the
    Provider role table-wide INSERT/DELETE on source_exclusion, so a
    Provider SQL-injection foothold could insert exclusions for every
    (scope, bootstrap-source) pair — silently blanking chosen sources out
    of every scope's digests and retrieval — or delete all exclusions.
    The threat model's DB-roles posture (§DB roles) deliberately accepts
    Provider write on user-state tables, so this is inside the accepted
    residual; flagged because exclusion rows are the first user-state rows
    whose presence/absence reshapes every scope's content world, which an
    operator may want covered by a future row-count invariant or trigger.
  - Operational, not an attack: source_exclusion's FK (REFERENCES
    source(id), no ON DELETE clause) now blocks the Admin role's
    Invariant-4 hard-DELETE escape hatch on any source with exclusion
    rows; the operator must delete exclusion rows first. Worth a runbook
    note.

OUT-OF-MODEL:
  - Provider-compromise content suppression via exclusions: V59 grants the
    Provider role table-wide INSERT/DELETE on source_exclusion, so a Provider
    SQL-injection foothold could insert exclusions for every (scope,
    bootstrap-source) pair (blanking chosen sources out of every scope's
    digest/retrieval) or delete all exclusions. This is inside the accepted
    §DB roles residual (Provider write on user-state tables), but exclusion
    rows are the first user-state rows whose presence/absence reshapes every
    scope's content world — an operator may want a future row-count invariant
    or trigger. Not a threat-model violation.
  - Invariant-4 hard-DELETE escape hatch friction: source_exclusion's FK
    (`source_id UUID NOT NULL REFERENCES source(id)`, no ON DELETE clause)
    now blocks the Admin role's Invariant-4 hard-DELETE of any source that
    has exclusion rows; the operator must delete exclusion rows first.
    Operational (runbook note), not an attack.
  - Digest-cache staleness vs exclusions: /unfollow-source (bootstrap
    exclude) and /follow-all-sources (clear exclusions) do not bump
    scope_preferences.source_subscription_version (the summary-cache key
    component), so a cached group digest can transiently continue to include
    a just-excluded bootstrap source until the next slot recompute. The
    content is public bootstrap corpus (a preference opt-out, not a
    confidentiality control), and non-bumping /unfollow-source is pre-existing
    behavior (schema V7 lists only /add-source and /remove-source as version
    bumpers). Correctness quirk worth confirming, outside the security
    threat model.

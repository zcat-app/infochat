RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: AUDIT-EVASION
    SEVERITY: low
    PROMISE: docs/spec/security.md §LLM output sanitizer — "Every match is
             audit-logged; rows aggregate per distinct token per sanitize
             call and carry the exact occurrence count — counted, never
             throttled." Reinforced two paragraphs later: "Every match is
             audit-logged; rows aggregate per distinct token per sanitize
             call and carry the exact occurrence count — counted, never
             throttled."
    GAP: The diff turns a documented no-op into a real thread interrupt on
         the digest render path, and that interrupt can abort the
         sanitizer's own audit-log transaction.
         - infochat-provider/src/main/java/app/zcat/infochat/provider/digest/DigestWorker.java:222
           now submits the render via `renderExecutor.submit(...)` instead
           of `CompletableFuture.supplyAsync(...)`, and :256
           `renderFuture.cancel(true)` therefore delivers a genuine
           `Thread.interrupt()` into the render's virtual thread (previously
           `CompletableFuture.cancel(true)` was documented as having no
           effect, so no interrupt ever reached that thread).
         - The render thread issues sanitize calls that write audit rows:
           DigestRenderer.java:796 (`llmOutputSanitizer.sanitize(cp.prose())`
           on LLM-authored per-cluster prose), DigestRenderer.java:837
           (`DisplayHeadline.of` on feed titles), and
           TranslationPipeline.java:156 / :288 (sanitizer-2 over translator
           output).
         - Each of those bottoms out in
           infochat-provider/src/main/java/app/zcat/infochat/provider/llm/LlmOutputSanitizer.java:236-267
           `emitAuditRows`, which opens a pooled JDBC connection at :240 and
           commits at :253. On an already-interrupted thread that write can
           fail two ways: Agroal's connection acquisition uses an
           interruptible wait and rethrows as `SQLException` when it has to
           queue for a connection, and pgjdbc socket I/O parked on a virtual
           thread surfaces `InterruptedIOException` when the interrupt flag
           is set (`NioSocketImpl.park`). Either way :264 converts it to
           `IllegalStateException`, the render aborts, and the
           `LLM_OUTPUT_SANITIZED` rows for that sanitize call are never
           written.
         - The diff's own comment (DigestWorker.java:245-255) states the
           interrupt is expected to make "each remaining call in the render
           fail fast", i.e. the interrupt flag is deliberately kept armed
           across the remainder of the render loop — which is exactly the
           window in which those audit writes execute. No enumeration of the
           audit obligation the rerouted path carried appears anywhere in
           the diff.
         Scope of the residual, stated honestly rather than inflated:
         the DELIVERED bytes are still audited. On the degrade branch
         DegradedDigestRenderer.java:78 re-sanitizes EVERY collected post's
         headline on the (uninterrupted) worker thread, so a command-shaped
         FEED title still produces its row. What is lost is the row for
         closed-list tokens the sanitizer found in LLM-authored prose and in
         translator output inside the discarded render — the exact social-
         engineering signal the sanitizer's audit trail exists to surface,
         and the one class the degraded re-render can never reproduce
         because it generates no prose.
    REPRO: 1. Adversary controls (or can inject into) an RSS/Nostr source a
              group is subscribed to — the same attacker tier §LLM output
              sanitizer already names for `/add-source` in a DM.
           2. They post enough items to make the group's next scheduled
              digest expensive: cluster count drives one
              `SummaryProseGenerator` call per lead/full cluster, one
              `CategoryRollupGenerator` roll-up per section, and (M1-756)
              per-headline translator calls for a non-`en` group. The
              scheduled route draws no per-user and no per-group bucket
              (DigestRenderer.java:126-137), so volume is the only input
              needed and it is entirely attacker-side.
           3. The render overruns `slot.windowEnd()`;
              `renderFuture.get(remaining)` times out and :256 interrupts
              the render thread mid-flight.
           4. Content crafted so the summarizer or the translator echoes a
              privileged token (`/ban`, `/grant-admin`, `/list-sources
              --all`) is still matched and stripped by the closed-list pass,
              but `emitAuditRows` fails on the interrupted thread and throws;
              no `LLM_OUTPUT_SANITIZED` row lands.
           5. Operator running `/audit` sees no evidence that the model was
              steered into emitting privileged command strings on that slot.
              The spec's wording is unconditional ("Every match is
              audit-logged ... counted, never throttled") and the diff adds a
              new, attacker-influenceable trigger for suppressing it. The
              system's fail-closed pairing (a failed audit write must stop
              the reply) is still honoured — the render is discarded — which
              is why this is a detection/observability loss and not a
              delivery bypass.
    SUGGESTED-FIX-CLASS: audit-log-coverage

OUT-OF-MODEL:
  - Interrupt-driven breakage of a pooled Postgres connection: when the
    interrupt lands inside `emitAuditRows`' transaction the connection is
    left broken and Agroal destroys rather than reuses it. Verified not to
    produce a dirty-connection reuse (try-with-resources close + Agroal's
    reset/destroy), and the churn is bounded at two scheduled slots per
    group per day, so it is noted rather than filed.
  - The threat model's §Rate limiting states "the aggregate system LLM
    budget is the backstop for digest cost" for periodic digests, but no
    such budget exists in the codebase (only
    `infochat.digest.translation-max-per-render`, which
    DigestRenderer.java:118-124 explicitly says is NOT a bound on the
    render's translator cost as a whole). This is a pre-existing gap that
    motivates the diff rather than one the diff introduces, and prior audits
    (docs/plan/m1/redteam/M1-756-*) already recorded it; flagged here only so
    the user can decide whether the promise should be amended or implemented.
  - Efficacy of the fix rests on an untested external contract: the JDK
    `HttpClient.send` fast-fail on a pre-set interrupt flag plus
    LlmHttpSupport.java:190-195 re-arming it. That chain was verified to hold
    in-repo (SummaryProseGenerator.java:144-148 and
    TranslationPipeline.java:273/:110 catch the resulting RuntimeException
    without clearing the flag, and Redactor's watchdog is deadline-based, not
    interrupt-based, so SafeLog stays fail-closed under interrupt), but a
    future call site that swallows the flag would silently restore unbounded
    spend with no test pinning it.

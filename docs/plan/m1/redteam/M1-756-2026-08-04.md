FINDINGS:
  - CATEGORY: INFO-LEAK
    SEVERITY: low
    PROMISE: docs/spec/security.md §Secrets handling — "The post-setup
              `prod/switch-llm.sh` backend switcher ... prints a per-task
              privacy disclosure naming exactly which generative tasks now
              call a remote provider and what each exposes"; and, for the
              most recent addition to that enumeration, "**`translator` also
              carries the user's saved-post headlines (M1-755).** The
              `/saved` display-hit leg (§Rate limiting) sends each listed
              row's rendered headline ... to `ModelTask.TRANSLATOR`, which
              may be remote. The disclosure text `prod/switch-llm.sh` prints
              at switch time must name this surface (the pending M1-758
              update is scoped to cover it alongside the M1-746
              query-anchoring leg)."
    GAP: The diff adds a third `ModelTask.TRANSLATOR` display-hit consumer —
         the periodic group digest's normal-mode headlines — and amends
         neither §Secrets handling nor anything the M1-758 disclosure ticket
         is scoped to cover (the diff touches no file under docs/spec/).
         Evidence:
           - infochat-provider/src/main/java/app/zcat/infochat/provider/digest/DigestRenderer.java:832-833
             `translationPipeline.runForDisplayHit(headline, p.sourceLanguage(),
             SCOPE_KIND, groupId, langCode)` inside `appendHeadlines`.
           - infochat-provider/src/main/java/app/zcat/infochat/provider/digest/DigestPostCollector.java:144
             and :160/:180 — `s.language` is newly projected so the leg is
             live for real digest rows (before the diff `sourceLanguage` was
             hard-NULL and the leg was a permanent no-op).
           - infochat-provider/src/main/java/app/zcat/infochat/provider/translation/LlmTranslationProvider.java:93-95
             routes the call through `LlmRouter.forTask(ModelTask.TRANSLATOR, ...)`,
             i.e. whichever backend the operator configured for that task —
             which §Rate limiting itself notes "may be remote".
         What is new relative to the already-disclosed legs is not the data
         class but the *trigger*: every prior translator surface is invoked
         by a user action (`/summary` M1-747, `/saved` M1-755, the D28
         pre-fetch M1-746). This one is unattended and scheduled — two slots
         per day per non-English group, forever, with no user in the loop
         (the renderer's own javadoc at DigestRenderer.java:113-115 says so).
         It is also the first path that sends ENGLISH feed headlines off-box
         on a schedule: the ingest anchor leg short-circuits English sources
         with no translator call
         (infochat-collector/.../IngestTranslationWorker.java:264,
         `if ("en".equals(row.language()))`), and V74 records that "the
         entire current corpus is English". So on a deployment whose
         translator is routed remotely, the operator's disclosure says the
         translator sees chat queries and saved-post headlines, while in
         fact a continuous, unprompted stream of the group's digest content
         selection now leaves the deployment.
    REPRO: 1. Operator runs `prod/switch-llm.sh` and routes `translator` to a
              remote provider; the printed disclosure names the surfaces
              §Secrets handling enumerates (chat/query text, saved-post
              headlines) and the operator accepts that exposure.
           2. Any member of an approved group issues `/lang cs` for the group
              scope (`cs` is enabled today per §Rate limiting).
           3. No further user action. At each digest slot the scheduler fires
              `DigestWorker.executeSlot` -> `DigestRenderer.renderSections`,
              and up to `infochat.digest.translation-max-per-render` (default
              5) of that group's feed headlines are POSTed to the remote
              translator endpoint, twice a day, indefinitely.
           4. The remote endpoint operator observes the group's topical
              interests over time. Nothing the deployment printed at switch
              time told the operator this stream would exist.
    SUGGESTED-FIX-CLASS: other

  - CATEGORY: DOS
    SEVERITY: low
    PROMISE: docs/spec/security.md §Rate limiting — "**Per-group LLM rate
              (D47)** ... Periodic digests do NOT count against
              user-initiated per-group LLM budget (they are system-initiated;
              the aggregate system LLM budget is the backstop for digest
              cost)."
    GAP: The diff adds a new generative consumer to the digest path
         (DigestRenderer.java:832-833) and bounds it only with a per-render,
         per-group constant
         (DigestRenderer.java:126-127,
         `@ConfigProperty("infochat.digest.translation-max-per-render")`,
         default 5; declared at
         infochat-provider/src/main/resources/application.properties:618-624).
         The backstop the threat model names for exactly this cost class —
         "the aggregate system LLM budget" — has no implementation: greps for
         an aggregate/global/system LLM budget class or property return
         nothing (only per-task `infochat.llm.<task>.max-concurrency`
         semaphores, which bound concurrency, not volume, and which the
         Provider does not even declare for `translator`). The per-render
         budget therefore does not compose: with N non-English groups the
         scheduler issues up to 5N translator calls per slot with no ceiling
         above it. The renderer's own justification for taking no bucket
         token ("The digest is a SCHEDULED BROADCAST with no user in the
         loop", DigestRenderer.java:113-115) is additionally false on one
         reachable route: `/retry --digest` ->
         DigestRetryService.fallbackRerun (DigestRetryService.java:227) ->
         `digestWorker.execute(slot)` -> the same `renderSections`, i.e. a
         user command that re-spends the full budget. That route is
         indirectly metered (RetryCommandHandler.java:552-556 draws the
         per-user LLM token and the per-group LLM sub-bucket, and
         DigestRetryService enforces a 2-minute per-group cooldown), which is
         why this is low rather than higher — but the translator calls
         themselves are counted by nothing.
    REPRO: 1. Deployment with M non-English groups, `translator` routed to a
              metered/remote provider.
           2. Scheduler fires the morning slot; each group's render spends up
              to 5 translator calls. No counter anywhere sums them, and no
              cap stops the Mth group.
           3. Independently, a non-probation member of a group whose latest
              slot has no persisted sections (degraded slot, zero-post slot,
              or crash-stranded cache row) issues `/retry --digest` once per
              cooldown window; each accepted retry re-renders and re-spends
              the whole 5-call budget in addition to the prose and roll-up
              calls already made on that path.
           4. A feed adversary controlling a subscribed source can guarantee
              the budget is spent every render by publishing fresh distinct
              titles (each distinct headline is a cache miss;
              DigestRenderer.java:827), and by inflating the self-reported
              `reposts`/`likes` prominence signals can ensure their own posts
              occupy the budgeted top-5 slots so legitimate headlines render
              untranslated.
    SUGGESTED-FIX-CLASS: rate-limit

OUT-OF-MODEL:
  - Feed-adversary monopolization of the per-render translation budget (step
    4 above) degrades translation QUALITY for co-published legitimate
    headlines rather than availability or confidentiality. The threat model
    treats feed publishers as untrusted but makes no commitment about which
    headlines get translated, so this is noted rather than filed: the reader
    simply sees some headlines in the source language.
  - `DigestWorker.executeSlot` calls `renderFuture.cancel(true)` on timeout
    (DigestWorker.java:237) with a comment asserting it stops the orphaned
    render. `CompletableFuture.cancel` does not interrupt the running thread,
    so a timed-out render continues to completion and still spends its
    translator budget. This is pre-existing behaviour (the prose and roll-up
    generators already ran on that orphaned path) and the diff only adds a
    bounded 5 calls to it, so it is not counted against this diff — flagged
    so the user can decide whether the comment/behaviour mismatch warrants
    its own ticket.
  - Not findings, verified delivered on the new path (recorded so a later
    audit does not re-derive them): the translated headline is re-sanitized
    through the closed-list pass with the bound -> flatten -> sanitize order
    preserved (DisplayHeadline.prepareTranslatedHeadline, called from
    TranslationPipeline.java:247); the sanitize unit stays ONE author's field
    (§"Flag position mirrors the parser's own scan"); the display-hit cache
    partition is per-(scopeKind, scopeId, language) so the digest cannot read
    a prose-leg or other-scope entry (TranslationPipeline.java:286-288); the
    translator prompt carries the per-call random `<<<UNTRUSTED_CONTENT>>>`
    delimiter (LlmTranslationProvider.java:81-91); the degraded arms make no

RED-TEAM VERDICT: CLEAN

The diff is itself an audit-correctness remediation, and I checked each new surface against the threat-model commitments it touches:

- **Audit-on-intent ordering (spec §Authorization model, step 8 precedes step 9).** All four handlers write the `*_INTENT` row on a separate auto-commit connection that commits BEFORE the mutation transaction. The invariant "execution can never happen without a preceding intent row" holds: intent is committed first, the in-tx `FOR UPDATE` admin gate stays authoritative for execution, and refused probes leave intent-without-effect (acceptable), never effect-without-intent.
- **Non-admin callers stay audit-silent.** Every intent write is gated behind an admin pre-check (`UnbanCommandHandler` step-1 gate at :150-153; Promote :104-108; Demote analogous; Vouch :172/lookupActor). A non-admin cannot drive an append-only `audit_log` row — the implementers explicitly reasoned about this DoS surface and closed it.
- **No SQL/JSON injection.** All target/actor lookups are parameterized. The only string-interpolated SQL values are server-generated UUIDs (`actor.id`, `requestId`) in `SET LOCAL`. The single attacker-influenced value reaching `details_json` (`upstream_group_id`) is run through `JsonEscaper.escape`, which correctly escapes `"`, `\`, and all C0 control chars.
- **Auto-promote guard (GroupAutoPromoteService).** The added `hasActiveAdmin` pre-check plus the `AND is_group_admin = false` UPDATE guard suppress only the spurious true→true re-promotion audit row; genuine promotions still write exactly one `PROMOTE_GROUP_ADMIN` row. Concurrency is still backstopped by the `one_admin_per_group` partial unique index (23505 → false), so the read-outside-transaction TOCTOU cannot mint two admins. Removed members (removed_at not null) remain unpromotable. No coverage loss, no escalation.
- **/unban not-banned no-op (spec §User ban disclosure rule).** The new `!target.isBanned` leg correctly returns the plain reply with no fabricated `UNBAN` row and no `restored_group_admin` claim — nothing was restored because nothing was unreachable. The actual-unban path still discloses restored group-admin roles in both reply and audit row. Reply discrimination across the legs is only reachable by bot admins, who are permitted to know target ban/registration state.

OUT-OF-MODEL:
- A compromised single-adapter bot admin can now spend one append-only `audit_log` row per `/unban`, `/vouch`, `/promote`, `/demote` probe against arbitrary (including unknown) contacts, where the pre-D47 `/unban`-against-unknown path previously wrote zero rows. This is a minor audit-log-growth amplification, but it is strictly within powers a compromised admin already holds (per spec §Per-adapter admin threat profile: ban, source mutation, audit access), and the threat model makes no commitment to bound audit_log growth from a compromised admin. There is no per-bucket rate limit specified for these admin mutation commands; if the user wants defense-in-depth here, a rate-limit bucket for admin mutation commands would be the lever, but it is not a promise the diff fails to keep.

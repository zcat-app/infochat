# Red-team audit: M1-033 (Stage 2 LLM judge + first OpenAI-compatible LlmProvider + (ModelTask, scope_language) router)

RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - **LLM endpoint HTTP calls bypass the `infochat-ssrf` allowlist** (`OpenAiCompatibleProvider.java:176-183`). The SSRF spec (`security.md` §SSRF and outbound connections) lists "feeds, redirects, and StreamSource connections" plus Provider `/add-source` probes as the allowlist's scope — LLM endpoints are not in that scope, and the threat model treats operator-set config (including LLM base-url) as trusted. So this is in-spec by current commitments. If a future feature ever lets non-operators influence `infochat.llm.security.base-url` (e.g., a hypothetical `/llm-config` command), the SSRF guard would not catch a metadata-IP base-url; flag for the operator-config trust boundary.
  - **Non-2xx LLM response body preview is logged at WARN** (`OpenAiCompatibleProvider.java`, `preview()` of `response.body()`). Some misbehaving upstream proxies echo the `Authorization: Bearer …` header back inside an error message body; a logged 200-byte preview could thus capture an API-key fragment in stdout/journald. The audit-log redaction-hook commitment (`security.md` §Secrets handling) covers the audit table only — stdout redaction is M1-019 (deferred). Out-of-model for v1 but worth tracking once M1-019 ships.
  - **Stage 2 audit-log write does not flow through the spec's redaction-hook layer** (`StartupReleaseOnStage2FailureWarn.java:114-156`). The spec says "Audit-log writes pass through a redaction hook." No `RedactionHook` Java middleware exists in the repo today; every `INSERT INTO audit_log` in M1 is raw JDBC. This is a project-wide pattern, not introduced by M1-033, and the new row's fields are operator-trusted enum + system id with no user-supplied content. Flag for the redaction-hook ticket whenever it lands so the existing call sites are migrated atomically.
  - **`Stage1Worker.onPostKey` is `@Incoming` with no `@Blocking` / `@RunOnVirtualThread` annotation**, yet it now invokes `Stage2Worker.judge` which performs a synchronous semaphore acquire + blocking HTTP call. SmallRye Reactive Messaging's default may dispatch this on a Vert.x event-loop thread. The threat model's "blocking-the-event-loop" DOS clause is explicitly scoped to the user-facing messaging adapter (SimpleX/Signal), not internal eval-queue channels, so this is out of model — but if the in-memory channel is ever swapped for Kafka or the worker thread pool shrinks, the bounded-concurrency promise ("a slow provider applies back-pressure to the eval queue rather than exhausting threads") could degrade to "exhausts the event loop." Worth a defensive `@Blocking` annotation in a follow-up.

OUT-OF-MODEL:
  - Tilde-fence widening at
    infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/InboundRouter.java
    (matchFenceOpener) accepts both backtick (`` ` ``) and tilde
    (`~`) fence characters, while `docs/spec/security.md` §Ingest
    pipeline restricts the fence rule to "a line beginning (after up
    to three leading spaces) with a run of three or more backticks".
    Content inside a `~~~` block is preserved verbatim (no NFKC, no
    bidi-control strip, no zero-width strip), which is wider than
    the spec's carve-out. Currently security-neutral because the
    two downstream consumers of the normalized body (the
    slash-prefix dispatch via `normalized.startsWith("/")` and the
    not-yet-implemented invite-code consume which per spec
    §Authorization step 2 uses whole-body equality) require the
    whole body to match a specific shape that any tilde-fence
    wrapper prevents. Surfacing as a spec deviation: future
    chat-mode handlers (T2-D) that consume the normalized body for
    free-form processing would inherit un-normalized in-tilde-fence
    content (bidi controls, zero-width chars, homoglyphs) in a way
    the spec did not authorize.

  - Body-size cap at
    infochat-provider/src/main/java/app/zcat/infochat/provider/messaging/InboundRouter.java
    `onMessage` sends a user-visible reply (`MESSAGE_TOO_LARGE_REPLY`)
    on every oversize inbound, while §Rate limiting promises the
    transport-level cap "drops silently for the rest of the cap
    window — no reply" and §User ban promises a banned user
    receives one fixed (ban) reply per inbound. The T2-A deferral
    comment in `onMessage` says ban / rate-cap will be wired
    upstream of this code; if the T2-A implementer instead wires
    those gates inside `onMessage` AFTER the size cap, an
    oversize-flooding banned user would still get the too-large
    reply per inbound, contradicting the silent-drop promise. Not
    exploitable today (no ban / rate-cap mechanisms in MVP) —
    flagging so the T2-A reviewer can confirm the cap fires only
    after rate cap and ban check.

  - Clock split between ProbationCheck.inProbation and clearIfPromoted.
    The diff moves the probation-expiry *decision* read
    (ProbationCheck.java:85-86) onto the injected Clock
    (clock.instant()) but leaves the lazy-sweep write
    clearIfPromoted gated on SQL NOW() (ProbationCheck.java:50,
    "probation_until <= NOW()"). CLAUDE.md §"Injectable time in
    decision logic" warns "Never split one component across two
    clocks." This is an engineering-rule concern, NOT a
    security.md commitment: security.md makes no clock-injection
    promise (grep of security.md finds no "injected Clock"
    requirement; the only wall-clock language is the watchdog and
    the invite TTL boundary). It is also not exploitable under the
    documented threat model — in production the injected Clock is
    Clock.systemUTC() and DB NOW() is also UTC system time, so the
    two resolve to the same instant within microseconds; the
    divergence only appears under a pinned test Clock. The spec's
    actual probation promise (§Slow-start tier: gate on
    "probation_until IS NULL OR probation_until < NOW()", promote
    "at the instant NOW() > probation_until") is delivered: the
    new code uses isAfter (strict >, matching the spec boundary),
    keys the read by the users PK (no cross-user leak), and uses a
    parameterized PreparedStatement (no injection). Flagged so the
    user can decide whether the engineering-rule clock-split
    warrants a follow-up; it is not a threat-model gap.

    Flagged so the user can decide whether the title overclaims

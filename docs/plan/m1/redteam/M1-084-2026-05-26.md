RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: INFO-LEAK
    SEVERITY: medium
    PROMISE: "Contact IDs are logged in redacted form (prefix + ellipsis + suffix) outside the audit log." (docs/spec/security.md §Secrets handling)
    GAP: MembershipEventHandler.java:69 logs the full unredacted contact ID via `log.warn("UserLeft: unknown user adapter={} contactId={}", adapter, event.contactId())`. This is a non-audit log path (SLF4J warn level), so the contact ID must be redacted per the spec promise, but it is emitted verbatim.
    REPRO: An adapter fires a UserLeft event with a contact ID that has no matching user row (unknown contact). The handler logs the raw contact ID to the application log at WARN level. An attacker who can provoke UserLeft events for arbitrary contact IDs (e.g. by leaving and re-joining groups on the adapter protocol) causes those IDs to appear unredacted in application logs. An operator or log-aggregation system consumer who should only see redacted forms now sees full contact IDs.
    SUGGESTED-FIX-CLASS: input-sanitization

  - CATEGORY: AUDIT-EVASION
    SEVERITY: high
    PROMISE: "Authorization evaluation order on every inbound message: ... 8. Audit-log the intent. 9. Execute." (docs/spec/security.md §Authorization model). The audit log records PROMOTE_GROUP_ADMIN and DEMOTE_GROUP_ADMIN for explicit admin changes, and the spec states group admin is "Bootstrapped by first @mention in a new group; /promote / /demote by bot admin".
    GAP: MembershipEventHandler.java:72 calls membershipRepository.markMemberRemoved(groupId, userId) which sets removed_at on the membership row. The V5 trigger trg_group_membership_clear_admin then clears is_group_admin if the departing user was a group admin. This is a privilege-affecting state mutation (group admin demotion) with zero audit trail. No audit row is written by MembershipEventHandler for UserLeft or BotRemoved events. An adversary who causes a group admin to leave (or spoofs a UserLeft event at the adapter layer) silently strips group-admin status with no entry in audit_log. Similarly, BotRemoved marks an entire group as removed (disabling all memberships) with no audit row.
    REPRO: (1) User A is group admin in group G. (2) The adapter fires a UserLeft event for User A (either User A genuinely leaves, or an adapter-level attacker forges the event). (3) MembershipEventHandler processes it, calling markMemberRemoved. The V5 trigger clears is_group_admin. (4) No DEMOTE_GROUP_ADMIN audit row exists. (5) User B sends an @mention and is auto-promoted to group admin (this IS audited as PROMOTE_GROUP_ADMIN). (6) An admin running /audit sees the promotion but not the preceding demotion — the causal chain is invisible. For BotRemoved: the entire group is silently disabled with no audit trail showing when or why.
    SUGGESTED-FIX-CLASS: audit-log-coverage

OUT-OF-MODEL:
  - GroupDeleted events are silently ignored by the default branch of the switch in MembershipEventHandler.java:55 (explicitly scoped out of this ticket per ticket frontmatter). If an adapter fires GroupDeleted, the group's removed_at is never set and auto-promote continues to work for a group that no longer exists on the platform. This is not a finding because it falls outside the ticket's claimed scope, but it is a residual gap that should be covered by a follow-up ticket.

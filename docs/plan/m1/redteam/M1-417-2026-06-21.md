wizard change only. It adds two llama.cpp compose services (generative

`prod/scripts/4-llm.sh` setup wizard, adds a static-compose + generated-config

Commitments checked against the diff, all delivered or not engaged:

1. Trust boundary 6/7 + §"What's intentionally NOT in v1" loopback posture
   for unauthenticated local services. The new `llama-server` instances speak
   an unauthenticated OpenAI-compatible HTTP API. They bind 0.0.0.0 INSIDE the
   container (required so they are reachable as `llamacpp:8080` on the compose
   network) but publish NO host port (`docker-compose.yml` llamacpp /
   llamacpp-embeddings stanzas carry no `ports:` key; the wizard never adds
   one; `LlamacppWiringTest.llamacppServicesPublishNoHostPort` pins this).
   This mirrors the existing Collector/Postgres compose-network-only posture
   exactly — exposure beyond the host stays an explicit operator action, never
   a default. No gap.

2. Operator config is trusted (threat model line 27). The wizard runs as the
   operator; the GGUF URL/filename it consumes is operator-typed input on a
   trusted boundary. Even so, the model-id sanitization is intact:
   `gguf_basename` strips `#fragment` then `?query` before `basename`, so a
   signed-URL token cannot bleed into `infochat.*.model`; `set_secret` writes
   through `dotenv_escape`; and every volume-touching docker invocation runs
   argv-only with `--entrypoint` (ls/sha256sum/rm), so the operator filename
   is never interpolated into a shell string. No injection regression vs the
   M1-394 baseline.

3. Pinned-default integrity. The two curated GGUFs carry enforced (non-skippable)
   SHA-256 checks; a mismatch removes the file and fails the wizard. Custom
   overrides retain the optional-checksum prompt — consistent with the
   pre-existing operator-trusted-TLS-fetch posture, not a weakening of any
   spec commitment (the spec makes no checksum commitment for operator-supplied
   models).

No threat-model commitment is left undelivered by this diff.

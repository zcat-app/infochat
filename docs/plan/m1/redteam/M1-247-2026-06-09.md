# Red-team audit — M1-247 (in-progress branch)

RED-TEAM VERDICT: CLEAN

The diff under audit (M1-247) makes three changes to `infochat-ssrf`, all of
which tighten or preserve the SSRF trust boundary the threat model commits to
in §"SSRF and outbound connections":

1. `DEFAULT_BODY_CAP` 10 MiB → 5 MiB (`SsrfGuardedHttpClient.java`). This
   *tightens* the body-size cap to match the design-note
   `infochat.fetch.max-body-bytes` default. A smaller cap is a stricter DoS
   bound, not a weaker one; the spec commits only to "body-size cap enforced,"
   which remains true. The new test
   (`noArgClientInheritsCanonicalBodyCapAndRejectsOneByteOver`) proves one byte
   over the cap raises `BODY_CAP_EXCEEDED`.

2. `isCrossOrigin` host comparison moved from raw `getHost().equalsIgnoreCase()`
   to `sameCanonicalHost()`. Falsifier checked: "could two genuinely-different
   hosts canonicalize to the same value, suppressing the credential scrub and
   leaking `Authorization`/`Cookie`/`Proxy-Authorization` across an origin
   boundary?" — they cannot. `canonicalizeHost` is
   `IDN.toASCII → toLowerCase(Locale.ROOT) → single trailing-dot strip`; each
   step is a legitimate host-identity equivalence (case, FQDN trailing dot,
   IDN↔punycode), and the same canonical form is what gets resolved and
   DNS-pinned (`resolveAndValidate`). Distinct registrable hosts map to distinct
   ASCII, so the change only *narrows* spurious cross-origin classifications
   (the same-host case from the test, `Example.COM` vs `example.com.`), never
   collapses two real origins into one. Null `to` host and
   `IllegalArgumentException` from `canonicalizeHost` both fail safe to
   "different host → scrub", preserving the prior `equalsIgnoreCase(null)==false`
   fail-safe. The scrub still fires on `evil.example.org`
   (test `sameHostDifferingByCaseOrTrailingDotIsNotCrossOrigin`). Scheme and
   effective-port legs of `isCrossOrigin` are unchanged.

3. Test-only `LoopbackPermitting` → `LoopbackPermittingBlocklist` rename —
   cosmetic, no behavioral surface.

The sensitive-surface inventory correctly reports auth/invite, authorization,
intake, ban, and audit paths as untouched; the diff does not reach any of them.
The clarity-check WARN (risk-calibration on the T15 host-comparison fix) is a
process note, not a delivered gap — the implemented comparison is correct and
fails safe.

No promise in the threat model is left undelivered by this diff.

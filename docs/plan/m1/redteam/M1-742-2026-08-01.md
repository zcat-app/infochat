RED-TEAM VERDICT: FINDINGS

FINDINGS:
  - CATEGORY: DOS
    SEVERITY: medium
    PROMISE: "A per-post attempt counter bounds retries" (security.md
      §Re-evaluation job) and, for re-eval verdicts: "`INJECTION`,
      `MALWARE`, or `UNKNOWN` on either class → post stays
      `QUARANTINED`, the `stage2_failed` flag is preserved ... and the
      attempt counter increments. After cap exhaustion the post
      transitions to `NEEDS_REVIEW` ... and the admin notifier fires."
    GAP: V70 (infochat-core/.../V70__quarantine_one_pending_stage2_row.sql:584-586)
      adds a partial unique index allowing at most one PENDING
      flagged_by='stage2' row per post, while the same diff makes the
      first-pass non-BENIGN verdict insert that row UNCONDITIONALLY
      (Stage2VerdictHandler.java:198-214). The new pin
      Stage2VerdictPersistenceIT.duplicatePendingStage2RowFailsOnUniqueIndex
      (diff lines 505-527) proves a colliding insert throws
      IllegalStateException, rolling back the ENTIRE verdict transaction
      — the same transaction that carries the post UPDATE and, on the
      re-eval path, the attempt-counter increment. V70's own header
      (diff lines 576-582) concedes the coupling: "a fresh PENDING
      stage2 row IS allowed once the previous one is reviewed (the
      re-eval re-hide path relies on that)" — i.e. before review, the
      re-eval insert fails. A rolled-back transaction cannot increment
      the attempt counter, so the bound the spec promises never
      engages: no cap exhaustion, no NEEDS_REVIEW transition, no admin
      notification — while every re-eval tick spends a judge LLM call.
    REPRO: Attacker controls a feed source (in-model: "Every RSS
      publisher ... is untrusted") and publishes borderline content the
      judge first scores UNKNOWN — a flip the spec itself anticipates
      ("content that initially looks UNKNOWN to the judge but flips to
      BENIGN on a model swap or warm-up", §Re-evaluation job). Under
      M1-742 the first-pass UNKNOWN verdict now ALWAYS leaves a PENDING
      stage2 row (previously it left none when Stage 1 rows existed).
      The post enters the re-eval queue. Admins are backlogged (the
      spec's own quarantine-exhaustion attack shape, §Re-evaluation
      job "Per-source UNKNOWN auto-disable"). On re-eval the judge
      returns INJECTION; the re-hide/verdict insert collides with
      idx_quarantine_one_pending_stage2_row; the transaction rolls
      back; the attempt counter stays at 0. Every subsequent re-eval
      tick repeats the LLM call and the rollback — unbounded judge
      spend per attacker post until a human happens to review the
      first-pass row, with no NEEDS_REVIEW escalation ever firing.
    SUGGESTED-FIX-CLASS: other

  - CATEGORY: INJECTION
    SEVERITY: low
    PROMISE: "Stage 2 infrastructure failure (LLM unreachable, timeout,
      unparseable or schema-violating reply after retry) → release as
      `READY` with the Stage 1 redactions retained" is the fail-OPEN
      default — bounded by "a degraded judge must never auto-release"
      and the Stage 1 analogue "the deterministic guard failing is a
      safety-critical event" that "must never default to release"
      (security.md §Failure handling); trust boundary 4: "No post
      becomes user-visible without passing the layered ingest checks."
    GAP: The V70 unique index is a deterministic guard on the security
      pipeline, and its violation escapes
      Stage2VerdictHandler.apply() as an unclassified
      IllegalStateException (pinned by
      Stage2VerdictPersistenceIT, diff lines 517-523) AFTER the judge
      has already returned a real INJECTION/MALWARE verdict. Nothing in
      the diff classifies this exception at the caller: if it lands in
      the Stage 2 infrastructure-failure path, the spec's fail-open
      default releases the post the judge just judged hostile —
      inverting the guard's purpose. The insert sits in the same
      transaction as updatePostQuarantined
      (Stage2VerdictHandler.java:176, 198-214), so the failure occurs
      strictly after a successful, hostile verdict.
    REPRO: Two Stage 2 evaluations of the same post run concurrently
      (the diff's own "concurrent duplicate evaluation" phantom). Both
      judge the attacker's post INJECTION. Evaluator A commits
      QUARANTINED + the stage2 row. Evaluator B's insert hits the
      unique index and throws out of apply(). If B's failure handling
      classifies the throw as a Stage 2 infrastructure failure, the
      fail-open path marks the post READY with Stage 1 redactions
      retained — overwriting A's QUARANTINED and publishing content
      the judge explicitly classified INJECTION, with the re-eval
      queue as the only (unbounded, per Finding 1) backstop.
    SUGGESTED-FIX-CLASS: other

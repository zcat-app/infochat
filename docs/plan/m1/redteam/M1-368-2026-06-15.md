RED-TEAM VERDICT: CLEAN

No findings. The diff adds a Stage 1 match-count cap
(infochat.security.stage1.max-matches, default 1000) that fails closed
when the accumulated regex match list across all rules reaches the cap
for a single feed body. The implementation faithfully delivers every
threat-model commitment it touches:

- security.md §Failure handling ("Stage 1 infrastructure failure ...
  fail-closed: the post is immediately QUARANTINED and never
  auto-released"): handleMatchOverflow (Stage1Pipeline.java:516-528)
  is a byte-parallel of the existing handleWatchdogAbort — it UPDATEs
  post.status='QUARANTINED', writes one whole-body quarantine row
  (status PENDING), overwrites post.body with a single whole-body
  placeholder, and never auto-releases. Both writes run inside one
  TransactionHelper.inTransaction so a partial commit cannot leave a
  QUARANTINED post without its quarantine row.

- security.md §Ingest pipeline (spec-committed placeholder marker
  "[REDACTED:<id>]"): the overflow path reuses PlaceholderIds.marker,
  the same generator the success and watchdog paths use; the test
  asserts the body starts with "[REDACTED:" and ends with "]". No
  deviation from the fixed bracket/literal commitment.

- The cap is orthogonal to the wall-clock watchdog (the spec's
  ReDoS mitigation, §Ingest pipeline "mitigated by the watchdog
  timeout"); it bounds match *volume*, not scan *time*. The throw
  fires BEFORE the offending match is appended (Stage1Pipeline.java:368),
  so the list never allocates past the cap and is never silently
  truncated — this strengthens, rather than weakens, the existing
  fail-closed posture.

- No authorization, ban, invite, audit-write, or LLM-tool surface is
  touched (consistent with the sensitive-surface inventory). The
  quarantine row carries the verbatim normalized body in
  original_html, which only the Admin role can SELECT per §DB roles —
  unchanged by this diff.

Adversarial probes considered and dismissed:

- Quarantine-exhaustion / forced-quarantine DOS: a feed controller
  could craft a body that trips the cap to force QUARANTINED status.
  But the input is already bounded by the SSRF body-size cap
  (§SSRF), the cap default (1000) sits far above any legitimate
  post, and fail-closed-to-quarantine is the spec's explicitly
  mandated behavior for Stage 1 infra failure — quarantining a
  hostile post is the desired outcome, not a confidentiality or
  availability loss. The per-source UNKNOWN/HTTP auto-disable and
  admin-review TTL (§Re-evaluation job) bound any review-queue
  pressure. No promised property is traded away.

- Silent truncation hiding later injection spans: ruled out — the
  cap throws before append and routes the WHOLE post to fail-closed
  quarantine, so no partial/truncated match set is ever acted on.

- Cap-as-bypass (set cap to 0 to release): the overflow branch
  always quarantines and never releases; a zero cap would quarantine
  more posts, never fewer. Config is operator-trusted per the threat
  model.

RED-TEAM VERDICT: CLEAN

OUT-OF-MODEL:
  - DNS-rebind / multi-A-record window on the loopback check. `isLoopback` (LlmRouterStartupGuard.java:250-271) resolves the host once via `InetAddress.getByName(host)` (single first address) at startup and tests `isLoopbackAddress()`. A host that resolves to a loopback IP at boot but a remote IP at call time, or a host with both a loopback and a remote A-record, could route post title+summary off-host at call time while the startup guard saw only loopback. This is explicitly accepted by the spec: `docs/spec/llm.md` §Per-task routing rules commits the check as "checked once at startup, not per call," and the guard javadoc points the per-call SSRF defense at `infochat-ssrf`'s `SsrfGuardedHttpClient` — except the LLM/embedding call path is documented as NOT SSRF-guarded per-call. Reaching this requires attacker-controlled DNS or a malicious operator config value, both of which fall under the out-of-scope TLS/MITM and trusted-operator-config assumptions in `docs/spec/security.md` §Threat model. Flagging so the user can decide whether the LLM/embedding outbound path should join the per-call `infochat-ssrf` re-resolution discipline in v2; it is not a v1 spec gap.

When monitoring a long background `mvn verify` (resource peaks, container churn) with a sampling loop, DO NOT gate the loop on `pgrep -f '<pattern in the loop itself>'` — `pgrep -f` matches the full command line, so the monitor's own process matches its own pattern and the loop never exits. This hung an M1-542 monitor subagent ~14 min past build end.

**Why:** the user wants a clean, complete resource report from the verify run, and the hang wastes a subagent + confuses "is it still running?".

**How to apply:**
- **Launch the verify itself DETACHED, not as an agent-managed background task** (2026-07-03, M1-546): agent-managed background Bash tasks running the ~11-min verify were externally killed twice mid-build (whole tree died; no OOM). Working pattern: `setsid nohup bash -c 'scripts/verify-serialized.sh > .scratch/<log> 2>&1; ec=$?; mkdir -p target && cp .scratch/<log> target/<log>; echo VERIFY_EXIT=$ec >> .scratch/<marker>' &` then poll the marker file from the session (a Monitor/until-loop, or a plain sleep-poll). The `mkdir -p target` must be INSIDE the wrapper — the build's clean deletes root `target/` and a copy without it fails silently.
- Kill the sampler **by PID only** — `pkill -f <pattern>` is the same self-match trap in pkill form: it matched the killing shell's own compound command line and killed it (exit 143/144).
- Preferred sampler shape: a plain background bash loop forever (`free -m; loadavg; docker ps --filter label=org.testcontainers=true -q | wc -l; sleep 20`), and **stop it from the main thread** when the verify's completion notification arrives (TaskStop, or kill-by-PID). The main thread already gets notified — no self-detection needed.
- If a subagent must self-terminate: use the bracket trick (`pgrep -f '[c]lean verify'` — the literal `[c]lean` in the monitor's own cmdline doesn't match the regex), or poll the build log for `BUILD SUCCESS|FAILURE`.
- The `free -m` two-line capture (`NR==2` + `NR==3`) embeds a newline, so each sample spans two lines — parse accordingly.

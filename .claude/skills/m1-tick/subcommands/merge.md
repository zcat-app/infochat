# /m1-tick merge

Squash-merge the per-ticket branch into `main` and delete the branch. Idempotent: re-running on an already-merged ticket cleans up a stale branch (or no-ops if the branch is already gone).

Preconditions:

- The ticket exists and `status: done`. Refuse with `M1-NNN must be 'done' first; run /m1-tick commit M1-NNN` for any other status.
- The working tree is clean (`git status --porcelain` returns empty). Refuse with `working tree dirty; stash or commit first` — `git checkout main` must not clobber uncommitted edits. When this session runs *inside* a per-ticket worktree (step 2's cross-worktree case), the clean-tree check applies to BOTH the current worktree AND `<main-host>` (`git -C <main-host> status --porcelain`), since the squash commit lands in the host's working tree — but that host check is itself a cross-worktree command, so a refusal there is step 2's fence signal, not a dirty tree; it moves the merge to the hand-off arm, where the host's cleanliness becomes the user's to confirm.
- The per-ticket branch is resolvable per the **branch resolution procedure** in [`docs/process/workflow.md`](../../../../docs/process/workflow.md) §"Naming conventions (slug, branch, ticket file)" OR the canonical ticket commit already exists on `main` (idempotent re-run with the branch already deleted). If neither holds, refuse — see step 1's "neither" arm.

Steps:

1. **Idempotency precheck.** Read the ticket file's `title:` field; if the value is YAML-quoted (surrounded by `"..."` or `'...'`, which YAML requires when the title contains a colon, hash, leading dash, or other reserved character), strip the surrounding quotes so the bare string is used. Construct the canonical implementation-commit subject `M1-NNN: <title>` (e.g. `M1-001: Set up two-module Maven build`; for a ticket with `title: "m1-tick: fix STATUS.md order and review diff capture"` the constructed subject is `M1-002: m1-tick: fix STATUS.md order and review diff capture` — without the surrounding quotes). Count commits on `main` whose subject EQUALS this string: `git log main --format=%s | grep -cFx "M1-NNN: <title>"`. (Fixed-string `-F` + whole-line `-x` match. Preliminary auxiliary commits using the workflow's `M1-NNN: ` prefix — `M1-NNN: draft ticket`, `M1-NNN: refine ticket spec ...`, `M1-NNN: aborted attempt #N`, etc. — have different summaries by convention and so do NOT collide with the canonical subject. A loose `^M1-NNN: ` regex would conflate them.) Three arms:
   - **`0` matches AND branch resolves**: the canonical squash-merge path. Continue at step 2.
   - **`0` matches AND branch does NOT resolve**: refuse with `neither branch m1/M1-NNN-* nor a "M1-NNN: <title>" commit on main found; was /m1-tick commit M1-NNN run? (status is "done" but no committed work is locatable)`. STOP. This indicates ticket-state corruption — escalate to the user, do not silently fix.
   - **`1` match**: the ticket is **already merged on main**. If the per-ticket branch resolves, run `git branch -D <branch>` to delete it; print `M1-NNN already merged on main; deleted stale branch <branch>`. If the branch does NOT resolve, print `M1-NNN already merged on main; no branch to delete`. STOP — success exit. (No new commit, no status change, no `STATUS.md` regen needed.)
   - **`≥2` matches**: refuse with `multiple commits on main match "M1-NNN: <title>" exactly; manual cleanup required (a prior partial merge or hand-amend has produced duplicate canonical ticket commits — the skill will not paper over this)`. STOP. Print the matching SHAs (`git log main --format='%H %s' | grep -F "M1-NNN: <title>"`) so the user can decide. Note: this arm fires only on EXACT duplicate canonical subjects, not on the natural ticket-prefix family (drafts, refines, etc.).

2. **Resolve where `main` is checked out (worktree-topology resolution).** Run `git worktree list`. Exactly one worktree has `main` checked out; call its absolute path `<main-host>`. This determines whether the remaining steps run locally or via `git -C <main-host>`:
   - **`<main-host>` IS the current working directory** — the common single-checkout case, and the `--parallel` case where the main conversation runs in the primary while only the implementation subagent used a worktree. `main` is checkout-able here: run steps 3–6 locally (no `git -C` prefix). This is the historical default; nothing changes.
   - **`<main-host>` is a DIFFERENT worktree** — the session itself is running inside a per-ticket worktree (its cwd is `.claude/worktrees/<id>` and the per-ticket branch is checked out *here*). You CANNOT `git checkout main` locally — git refuses with `fatal: 'main' is already checked out at '<main-host>'`. **Probe the host before assuming you can drive it:** run `git -C <main-host> rev-parse --short HEAD`. The probe decides which of two sub-arms applies, and it is not optional — a harness that fences the session refuses the command rather than failing it, so an unprobed `git -C` in step 4 aborts the merge halfway.
     - **Probe SUCCEEDS** — drive steps 3–6 against the host with a `git -C <main-host>` prefix, skip step 3's checkout (the host is already on `main`), and free the per-ticket branch before step 6 deletes it. Do NOT remove the current worktree's directory mid-session — a shell whose cwd is the directory being removed breaks on its next command; that teardown is step 7.
     - **Probe is REFUSED by the harness** — a worktree-isolated Claude Code session (launched `claude --worktree <id>`) rejects EVERY git command aimed outside its own worktree, at the tool layer, before git runs: *"a worktree-isolated session's git operations must target its own worktree."* Compound commands containing `$(...)` are refused on the same grounds. The squash must create a commit on `main`, `main` lives in the host, and the ref cannot be forced from this side either (git refuses to update a branch checked out in another worktree, and doing so would desync the host's index). **Take the HAND-OFF arm — do not attempt to route around the refusal.** Observed 2026-08-05 (M1-759); the fence appeared mid-session, so a merge that worked earlier in the same session can be refused later. Hand-off:
       1. Run the idempotency precheck (step 1) and the fork-distance check (below) locally — reads of shared refs (`git log main`, `git merge-base main HEAD`, `git rev-list`) are NOT fenced, so the session can still prove the merge is safe and conflict-free before handing it over.
       2. Run `git checkout --detach` in this worktree. This is the one cleanup step the fenced session CAN perform: it frees the per-ticket branch ref so the user's `git branch -D` succeeds.
       3. Print the exact command block for the user to run from `<main-host>` — the step 4 squash, the step 4 STATUS.md regen + `git add`, the step 5 `git commit -C <branch-tip-sha>`, then `git branch -D <branch>`. Tell the user they can run each inline with `! <command>` so the output lands in the session.
       4. When the user reports back, perform step 5's squash audit from here: `git log main --format=%s | grep -cFx "<subject>"` must be 1, and `git diff <new-sha> <branch-tip-sha>` must be EMPTY (identical trees — the strongest form of the audit, available because the branch tip is still reachable). Report the result; do not claim the merge landed without it.
       5. Step 7's worktree removal stays the user's, run after this session ends — see the lock note there.

   **Fork-distance and overlap pre-check.** Before squashing, measure how far `main` has moved since the branch forked: `git [-C <main-host>] rev-list --count $(git merge-base main <branch>)..main`. If `>0`, intersect the two file sets — branch side `git diff --name-only $(git merge-base main <branch>) <branch>`, main side `git [-C <main-host>] diff --name-only $(git merge-base main <branch>) main` — and if they overlap, warn the user BEFORE step 4: the squash will hit the substantive-conflict arm and refuse, so the cheaper path is to rebase the branch onto fresh `main` and re-run `/m1-tick merge`, resolving the conflict once up front instead of discovering it mid-squash. Disjoint sets → proceed normally. (Observed: M1-127 forked early, M1-157 landed touching the same files, 2026-06-05.)

3. **Switch to main** (local case only): `git checkout main`. The working-tree-clean precondition guarantees this is non-destructive. In the `git -C <main-host>` case, skip this step — the host already has `main` checked out.

4. **Squash-merge the branch:** `git [-C <main-host>] merge --squash <branch>`. This stages the branch's cumulative tree against `main` without creating a merge commit and without advancing `HEAD`. On conflict (`git merge --squash` exits non-zero with conflict markers in the working tree), enumerate the conflicted paths via `git [-C <main-host>] diff --name-only --diff-filter=U` and branch:
   - **Conflict set = exactly `{docs/plan/m1/STATUS.md}` (regenerable-artifact-only conflict):** STATUS.md is a deterministic regen of the union of ticket frontmatter, so a divergent regen between the branch tip and a moved `main` is a pseudo-conflict — the post-merge frontmatter union is well-defined and produces a single correct STATUS.md. Resolve in place: run `python3 scripts/regen-status.py 'docs/plan/m1/tickets/M1-*.md' docs/plan/m1/STATUS.md` (with absolute paths against `<main-host>` in the cross-worktree case), then `git [-C <main-host>] add docs/plan/m1/STATUS.md`. The squash continues at step 5. (The "ticket file conflicted" check is implicit: if M1-NNN's own ticket file is in the conflict set, the set has ≥2 entries and this arm does not fire — the substantive-conflict arm below does.)
   - **Conflict set is anything else** (substantive code, design, ticket-body conflict, or a multi-path set that happens to include STATUS.md alongside a substantive file): refuse, print the conflicting paths, and run `git [-C <main-host>] reset --hard HEAD` to clean up; STOP. (NOT `git merge --abort` — squash mode does not set `MERGE_HEAD`, so `--abort` would emit `fatal: There is no merge to abort`. `git reset --hard HEAD` is safe here because the working-tree-clean precondition guarantees nothing is being discarded.) Substantive conflicts indicate `main` advanced between commit and merge in a way that touches the same code or ticket frontmatter the branch touched; the user resolves by rebasing the per-ticket branch onto fresh `main` and re-running `/m1-tick merge`.

   **Regen STATUS.md even when the squash auto-merges cleanly.** A textually successful 3-way merge of two independently regenerated STATUS.md files can be semantically stale: when the branch and a moved `main` each changed the same counter line identically (e.g. both `done=N` → `done=N+1`, for *different* tickets), git merges without conflict but the true frontmatter union is `N+2`. After the squash stages (or after the pseudo-conflict resolution above), always run `python3 scripts/regen-status.py 'docs/plan/m1/tickets/M1-*.md' docs/plan/m1/STATUS.md` against `<main-host>` (absolute paths in the cross-worktree case) and `git [-C <main-host>] add docs/plan/m1/STATUS.md`. The regen is idempotent — when `main` did not move, the output is byte-identical and the add is a no-op. (Observed: M1-150 merge vs mid-flight M1-154, 2026-06-05 — auto-merge kept `done=191` when the union was 192.)

5. **Commit with the branch tip's message verbatim:** `git [-C <main-host>] commit -C $(git rev-parse <branch>)`. The `-C` flag reuses the per-ticket branch tip's full commit metadata — message body (Context paragraph, `Alternatives considered:` block, `Reviewed-by:` trailer), author, and author-date — preserving the audit trail produced by `commit` step 3. The committer line is updated to "now" automatically; this is correct (the merge happens now, the authorship was earlier). (`git rev-parse <branch>` resolves the same in any worktree — branch refs are shared across the repo.) **Audit the squash commit itself:** compare `git [-C <main-host>] show --stat <new-sha>` against the branch's own stat (`git diff --stat $(git merge-base main <branch>) <branch>`). On a shared `main` host a parallel session's commit can land between step 4's `merge --squash` and this step's `commit`, reparenting the squash; auditing with `git diff <forkpoint>..HEAD` would blend the interloper's changes into the view and hide it, while `git show --stat` isolates exactly what this commit contains. Mismatch → surface to the user before step 6. (Observed: M1-175, 2026-06-06.)

6. **Delete the branch:** `-D` (not `-d`) is required because `git merge --squash` does NOT mark the branch as merged from git's POV — git sees the squash result as an unrelated commit on `main`. The branch's content is fully captured in the squash commit, so deletion is safe. **First free the branch if it is still checked out in a worktree** (the cross-worktree case — it is checked out in the current one): `git -C <current-worktree> checkout --detach` detaches that worktree's HEAD onto the branch tip so the ref is no longer occupied. Then `git [-C <main-host>] branch -D <branch>`. On the hand-off arm the detach is the session's (it targets its own worktree, so it is not fenced) and the `branch -D` is the user's, in the block from step 2.

7. **(Cross-worktree case only) Remove the spent per-ticket worktree.** The worktree has served its purpose; its directory (gitignored `target/`, `.scratch/`, `.reviews/` build artifacts and all) should go. Run from a shell NOT parked inside it — i.e. issue it from `<main-host>` *after* the session, or as the session's final action accepting that the current shell's cwd disappears: `git -C <main-host> worktree remove --force .claude/worktrees/<id>`. `--force` covers the gitignored build artifacts that would otherwise make `git worktree remove` refuse. (In the local case there is no per-ticket worktree to remove — skip.)

   **A `claude --worktree` session LOCKS its worktree**, so the removal fails while that session lives: `fatal: cannot remove a locked working tree, lock reason: claude session <id> (pid N ...)`. The lock is held by the live session, not stale — verify with `ps -p <pid>`. END THE SESSION, then remove; `--force` alone then succeeds. Do NOT reach for `remove -f -f` (or `git worktree unlock`) to break a lock whose process is still running: the double-force exists for stale locks, and forcing past a live one deletes the directory out from under a running session. (Observed 2026-08-05, M1-759.)

8. Print:
   ```
   M1-NNN merged into main (commit <new-sha>).
   Branch m1/M1-NNN-<slug> deleted.
   `git revert <new-sha>` cleanly undoes this ticket.
   ```

   **On the hand-off arm, this print is NOT reached when the block is issued** — the session has not merged anything yet and must not say it has. Print the command block and stop. Only after the user reports back AND step 2's audit passes (subject count 1, `git diff <new-sha> <branch-tip>` empty) does the merge line above become a true statement the session may print, with the audit result alongside it.

Do NOT push. Do NOT mutate the ticket's `status` (it stays `done`; the squash commit on `main` IS the merge audit trail — `git log main --grep -F "M1-NNN: <title>"` (with `<title>` filled in from the ticket frontmatter) answers "is this merged?" in one command). Do NOT regenerate `STATUS.md` (counts are unchanged; STATUS.md is in-flight-work-focused, not a merge tracker).
